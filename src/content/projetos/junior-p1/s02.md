A biblioteca tem dois tipos de usuário, com regras diferentes de limite e de prazo. E o prazo também depende do item: livro fica mais tempo que revista. Esta etapa decide onde cada regra mora.

## O prazo que vem do item

Declare em `Item` o método abstrato `diasDeEmprestimo()`. Toda subclasse é obrigada a implementá-lo: `Livro` responde 14 e `Revista` responde 7. Quem tem um `Item` na mão pergunta `item.diasDeEmprestimo()` e recebe a resposta certa, sem saber de que tipo é o objeto. Isso é **polimorfismo**.

## Um enum com regras

Tipos de usuário são um conjunto fechado e conhecido: um **enum**. E enums em Java são classes de verdade, com campos, construtor e métodos, como na temporada [Interfaces e enums](/?t=junior-t4):

```java
enum TipoUsuario {
    ALUNO(3, 1),        // até 3 itens, prazo normal
    PROFESSOR(10, 2);   // até 10 itens, prazo em dobro

    // campos, construtor e métodos aqui
}
```

Cada constante chama o construtor com os seus valores. O método `prazoPara(Item item)` junta as duas regras: os dias do item vezes o fator do tipo.

## O que construir

1. O método abstrato `diasDeEmprestimo()` em `Item`, implementado em `Livro` e `Revista`.
2. O enum `TipoUsuario`, com `getLimite()` e `prazoPara(Item)`.
3. A classe `Usuario`, com nome e tipo, imutável, com `toString` como `Ana (aluno)`.
4. Um `main` que imprime o prazo de cada usuário para cada item, `Rui (professor) leva L-001 por 28 dias`, e o limite de cada tipo, percorrendo `TipoUsuario.values()`.

> [!PENSE]
> Dá para escrever o prazo com um `if (item instanceof Livro) dias = 14; else if (item instanceof Revista) dias = 7;` dentro do enum. Funciona hoje. O que acontece com esse `if` no dia em que a biblioteca ganhar um terceiro tipo de item?

> [!BOAPRATICA]
> "Diga, não pergunte": em vez de perguntar ao objeto o que ele é para decidir por ele, peça que ele mesmo responda. Cada `instanceof` usado para escolher um comportamento é um lugar a mais para lembrar quando o sistema crescer.
