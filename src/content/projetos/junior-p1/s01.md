Todo item do acervo tem código, título e ano; livros e revistas acrescentam o que é só deles. É o caso clássico de herança: uma classe pai com o que é comum e uma filha para cada tipo.

## A classe pai

- `Item` é **abstrata**: a biblioteca não tem um "item genérico" na prateleira, só livros e revistas. `abstract` impede que alguém escreva `new Item(...)`.
- Os campos são `private final`: ninguém de fora mexe neles, e nem a própria classe muda depois do construtor. Para ler, getters (`getCodigo()`, `getTitulo()`, `getAno()`), e nenhum setter.
- O construtor é `protected`: só as filhas chamam, com `super(codigo, titulo, ano)`.

## Quando dois itens são o mesmo

`==` compara **referências**: responde se duas variáveis apontam para o mesmo objeto na memória. Para a biblioteca, dois objetos com o código `L-001` são o mesmo livro, mesmo que tenham sido criados em lugares diferentes. Isso se diz sobrescrevendo `equals`, e quem sobrescreve `equals` sobrescreve `hashCode` junto: objetos iguais precisam ter o mesmo `hashCode`, regra que as coleções do Pleno vão cobrar. A temporada [Herança e polimorfismo](/?t=junior-t3) tem o contrato completo.

## O que construir

1. A classe abstrata `Item`, com `equals` e `hashCode` pelo código e um `toString` como `L-001 Dom Casmurro (1899)`.
2. `Livro`, com o autor, e `Revista`, com a edição. Cada uma sobrescreve `toString` chamando o da classe pai: `L-001 Dom Casmurro (1899), de Machado de Assis`.
3. Um `main` que cria dois objetos `Livro` com o mesmo código e mostra o resultado de `==`, de `equals` e dos `hashCode`, compara um livro com uma revista e imprime uma revista guardada numa variável do tipo `Item`.

> [!PENSE]
> A variável é do tipo `Item`, mas o objeto é uma `Revista`. Qual `toString` roda: o de `Item` ou o de `Revista`? Quem decide, o compilador ou a JVM?

## Na IDE

Ninguém escreve `equals` e `hashCode` à mão no dia a dia: no IntelliJ, dentro da classe, **Alt + Insert** (no macOS, **⌘ + N**) abre o menu *Generate*, e a opção *equals() and hashCode()* pergunta quais campos entram. Escolha só o `codigo`. Gere também os getters pelo mesmo menu. Mesmo assim, entenda o código gerado: é ele que a prova e a entrevista perguntam.

> [!ANTES]
> Esse código repetitivo de getters, `equals`, `hashCode` e `toString` incomodou o Java por duas décadas. Muitos projetos usam o **Lombok**, uma biblioteca que gera tudo com anotações como `@Getter` e `@EqualsAndHashCode`. Desde o Java 16, os **records** geram o mesmo para classes que só carregam dados, e você vai vê-los em [Java moderno](/?t=junior-t5). Para uma hierarquia com herança como esta, a classe comum continua sendo a ferramenta.

> [!IA]
> Peça uma classe `Item` a uma IA e é comum vir um setter para cada campo, o que abre a porta para alguém trocar o código de um livro depois de emprestado, ou um `equals` sem o `hashCode`. Outra variação é o `equals` com `getClass() != o.getClass()`, que tem outro significado numa hierarquia. Leia o que ela gerou com a mesma atenção que leria o código de um colega.
