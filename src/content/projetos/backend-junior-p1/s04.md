Até aqui, a API confia em quem a chama. Mande um JSON quebrado, um título que é número ou um corpo de 20 MB, e ela explode: o handler lança uma exceção, a conexão cai, e o cliente não recebe resposta nenhuma. Nesta etapa, toda entrada ruim vira uma resposta clara, e nenhuma derruba o serviço.

## Erros que viram respostas

Crie uma exceção `ErroHttp extends RuntimeException`, com o status e, quando houver, o campo com problema. Qualquer parte do código que encontra um problema lança `new ErroHttp(422, "titulo é obrigatório", "titulo")` e não se preocupa com mais nada.

Quem transforma o erro em resposta é um método só, `atender`, por onde passam todas as requisições:

- `ErroHttp` vira a resposta com o status e `{"erro": ..., "campo": ...}`;
- qualquer outra exceção é um **bug**: vai para o log com os detalhes e o cliente recebe só `500 {"erro":"erro interno"}`;
- no fim, sempre, a troca é fechada.

## Os status de cada problema

| Problema | Status |
|---|---|
| JSON malformado, ou que não é um objeto | `400 Bad Request` |
| `Content-Type` diferente de `application/json` | `415 Unsupported Media Type` |
| corpo maior que 10.000 bytes | `413 Content Too Large` |
| JSON bem formado, mas título vazio, longo ou que não é texto; `concluida` ausente no `PUT` | `422 Unprocessable Content` |
| qualquer erro que você não previu | `500 Internal Server Error` |

A diferença entre `400` e `422` é sutil e útil: `400` é "não entendi o que você mandou"; `422` é "entendi, e está errado".

## Segurança

- **Limite de tamanho:** leia o corpo com `readNBytes(LIMITE + 1)`. Se vierem mais bytes que o limite, recuse sem ler o resto. `readAllBytes()` leria 2 GB se alguém mandasse 2 GB, e a API cairia sem memória: um ataque de negação de serviço com uma requisição só.
- **Nada interno na resposta:** stack traces contam a um atacante quais bibliotecas, versões e caminhos você usa. Eles vão para o log, nunca para o cliente.

## O que construir

1. `ErroHttp`, o método `atender` e a troca de todas as respostas de erro por `throw`.
2. Validação do título (obrigatório, texto, até 100 caracteres depois do `strip`) e de `concluida` no `PUT`.
3. Os status da tabela acima. O `415` você testa com `curl -i -X POST -d '{"titulo":"x"}' http://127.0.0.1:8080/tarefas`, que manda outro `Content-Type`.
4. Um teste com os casos de erro: JSON cortado, um array no lugar do objeto, título em branco, título numérico, título com 101 caracteres, corpo com 20.000 bytes e `PUT` sem `concluida`. Commit: `feat: validação e erros padronizados`.

> [!IA]
> Revisão de segurança é um ótimo uso para a IA, se o pedido for específico. Um que funciona: "Esta é uma API HTTP em Java puro, com o código abaixo. Procure entradas que derrubam o servidor, travam uma thread ou vazam informação: corpo enorme, JSON malformado, tipos errados, caminhos estranhos, cabeçalhos ausentes. Para cada uma, diga a requisição exata e o status que a API deveria devolver. Não sugira bibliotecas nem reescreva o código." Depois, transforme cada achado num caso do `TesteDaApi`: o que a IA encontrar e você não testar, volta.

> [!ANTES]
> O formato de erro mais usado hoje tem nome: **Problem Details**, da RFC 9457, de 2023, que substituiu a RFC 7807, de 2016. Ele padroniza campos como `type`, `title`, `status` e `detail`, e o Spring o gera sozinho com a classe `ProblemDetail`. Você vai usá-lo no próximo projeto; aqui, o formato simples ensina a ideia.
