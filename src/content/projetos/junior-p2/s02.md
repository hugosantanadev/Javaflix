Três records soltos ainda não formam uma equipe: é preciso um tipo que represente "qualquer contrato". Uma interface resolve, e uma interface **selada** resolve melhor.

## Selada: a lista é fechada

```java
sealed interface Contrato permits Clt, Pj, Estagio {
    String nome();
}
```

`permits` diz exatamente quem pode implementar `Contrato`, e mais ninguém pode. Em troca, o compilador ganha uma informação preciosa: sabe que um `Contrato` é, com certeza, um dos três. Os records já têm o método `nome()`, gerado pelo componente `nome`, e por isso satisfazem a interface sem nenhuma linha a mais.

## O switch que o compilador confere

Num switch sobre um tipo selado, cada `case` testa um tipo, como `case Clt clt ->`, e o `default` deixa de ser necessário. Mais do que isso: se faltar um tipo, o código **não compila**.

```java nao-compila
sealed interface Contrato permits Clt, Pj, Estagio {}
record Clt(String nome) implements Contrato {}
record Pj(String nome) implements Contrato {}
record Estagio(String nome) implements Contrato {}

class Teste {
    static String tipo(Contrato contrato) {
        return switch (contrato) {
            case Clt clt -> "CLT";
            case Pj pj -> "PJ";
        };   // erro: o switch não cobre todos os valores possíveis
    }
}
```

## O que construir

1. A interface selada `Contrato`, com os três records implementando.
2. Um `main` com a equipe do pedido num `Contrato[]`, que imprime cada pessoa com uma descrição calculada por um switch: `Marina Costa: CLT, 1 dependente(s)`, `Sofia Lemos: PJ, nota pendente`, `Caio Ramos: estágio, 30h por semana`.

> [!PENSE]
> Na [biblioteca](/projetos/junior-p1), um tipo novo de item entrava sem mexer em nada. Aqui, um contrato novo, como "temporário", faz **todos** os switches pararem de compilar. Isso é um defeito ou uma vantagem? Pense em quem escreve o sistema e em quem paga as pessoas.

> [!BOAPRATICA]
> As duas modelagens têm o seu lugar. Hierarquia aberta com polimorfismo, como na biblioteca, quando tipos novos devem entrar sem tocar no resto. Hierarquia selada com switch, como aqui, quando a lista de casos é fechada e você **quer** que o compilador obrigue cada parte do sistema a tratar um caso novo. Folha de pagamento, em que esquecer um caso custa dinheiro, é o segundo tipo.

## Na IDE

Com um switch incompleto, a linha fica vermelha, e **Alt + Enter** sobre ela oferece criar os ramos que faltam, um `case` por tipo permitido. É o compilador e a IDE fazendo a lista de verificação por você.
