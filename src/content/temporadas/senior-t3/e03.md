Os streams dos episódios anteriores transportam bytes e caracteres. Mas um programa trabalha com **objetos**: um usuário com nome e idade, um pedido com itens. Para gravar um objeto em arquivo ou mandá-lo pela rede, é preciso transformá-lo numa sequência de bytes e, do outro lado, reconstruí-lo. Isso é a **serialização**. O Java tem um mecanismo embutido para ela desde a versão 1.1, com regras que a prova adora cobrar, e com riscos de segurança que todo sênior precisa conhecer.

## Serializable, writeObject e readObject

Uma classe se torna serializável implementando `java.io.Serializable`, uma interface **marcadora**, sem métodos. O `ObjectOutputStream` grava o objeto com `writeObject`, e o `ObjectInputStream` o reconstrói com `readObject`, que devolve `Object` e precisa de um cast.

```java executar
import java.io.ByteArrayInputStream;
import java.io.ByteArrayOutputStream;
import java.io.IOException;
import java.io.ObjectInputStream;
import java.io.ObjectOutputStream;
import java.io.Serializable;

public class Basico {
    static class Usuario implements Serializable {
        private static final long serialVersionUID = 1L;
        static int criados = 0;
        String nome;
        int idade;
        transient String senha;

        Usuario(String nome, int idade, String senha) {
            this.nome = nome;
            this.idade = idade;
            this.senha = senha;
            criados++;
        }
    }

    public static void main(String[] args) throws IOException, ClassNotFoundException {
        Usuario ana = new Usuario("Ana", 30, "segredo");
        ByteArrayOutputStream bytes = new ByteArrayOutputStream();
        try (ObjectOutputStream out = new ObjectOutputStream(bytes)) {
            out.writeObject(ana);
        }
        Usuario.criados = 99;
        try (ObjectInputStream in = new ObjectInputStream(new ByteArrayInputStream(bytes.toByteArray()))) {
            Usuario copia = (Usuario) in.readObject();
            System.out.println(copia.nome + " " + copia.idade + " " + copia.senha + " " + Usuario.criados);
            System.out.println((copia == ana) + " " + copia.nome.equals(ana.nome));
        }
    }
}
```

```saida
Ana 30 null 99
false true
```

O exemplo serializa para a memória, com `ByteArrayOutputStream`; num arquivo, bastaria trocar por um `FileOutputStream`. Três regras aparecem aqui:

- Campos **`transient`** não são gravados. Na leitura, recebem o valor padrão do tipo: `null`, 0 ou `false`. É o lugar de senhas, caches e conexões.
- Campos **`static`** também não são gravados: pertencem à classe, não ao objeto. O valor lido é o que a classe tiver no momento, 99.
- O objeto lido é **novo**: igual em conteúdo, diferente em identidade.

`readObject` declara `ClassNotFoundException`, uma exceção checked, além de `IOException`: o programa que lê pode não ter a classe do objeto gravado. Um `main` que só declara `IOException` não compila.

## O que é preciso para ser serializável

Todos os campos não `transient` de um objeto serializável também precisam ser serializáveis, recursivamente: o `ObjectOutputStream` grava o **grafo** inteiro de objetos alcançáveis. Os tipos primitivos, `String`, os wrappers, os records que implementam `Serializable` e as coleções comuns são serializáveis. Se algum objeto do caminho não for, a gravação lança `NotSerializableException`, com o nome da classe culpada.

O campo `serialVersionUID` é a **versão** da classe. Na leitura, o Java compara a versão gravada com a da classe atual e, se forem diferentes, lança `InvalidClassException`. Sem o campo declarado, o compilador calcula um valor a partir da estrutura da classe, e qualquer mudança, como acrescentar um método, quebra a leitura de dados antigos. Por isso a recomendação é sempre declarar `private static final long serialVersionUID`.

## Construtores não rodam na leitura

A regra mais cobrada: ao desserializar, o Java **não chama** os construtores da classe serializável, nem executa os inicializadores dos seus campos. Os valores vêm do stream. A exceção é a primeira superclasse **não serializável** da hierarquia: o construtor sem argumentos dela é chamado, e os campos dela recebem os valores desse construtor, não os gravados.

```java executar
import java.io.ByteArrayInputStream;
import java.io.ByteArrayOutputStream;
import java.io.IOException;
import java.io.ObjectInputStream;
import java.io.ObjectOutputStream;
import java.io.Serializable;

public class Construtores {
    static class Animal {
        String especie = "desconhecida";

        Animal() {
            System.out.println("Animal()");
        }
    }

    static class Cachorro extends Animal implements Serializable {
        String nome = "sem nome";
        transient int patas = 4;

        Cachorro(String nome) {
            System.out.println("Cachorro(" + nome + ")");
            this.nome = nome;
            this.especie = "canina";
        }
    }

    public static void main(String[] args) throws IOException, ClassNotFoundException {
        Cachorro rex = new Cachorro("Rex");
        ByteArrayOutputStream bytes = new ByteArrayOutputStream();
        try (ObjectOutputStream out = new ObjectOutputStream(bytes)) {
            out.writeObject(rex);
        }
        System.out.println("lendo");
        try (ObjectInputStream in = new ObjectInputStream(new ByteArrayInputStream(bytes.toByteArray()))) {
            Cachorro copia = (Cachorro) in.readObject();
            System.out.println(copia.nome + " " + copia.patas + " " + copia.especie);
        }
    }
}
```

```saida
Animal()
Cachorro(Rex)
lendo
Animal()
Rex 0 desconhecida
```

Na leitura, só `Animal()` roda. O `nome` vem do stream; o `patas`, `transient`, fica com 0, porque o inicializador `= 4` também não roda; e a `especie`, campo de uma classe não serializável, nem foi gravada: volta ao valor que o construtor de `Animal` dá. Se `Animal` não tivesse um construtor sem argumentos acessível, a leitura falharia com `InvalidClassException`.

## Vários objetos, records e o fim do stream

Um mesmo stream pode guardar vários objetos e também primitivos, com `writeInt`, `writeUTF` e companhia. A leitura deve seguir **a mesma ordem**. Ler além do último lança `EOFException`, e por isso um laço que lê "até acabar" costuma tratar essa exceção.

Os **records** são serializados de um jeito diferente: na leitura, o Java chama o **construtor canônico** com os valores gravados. Assim, as validações do construtor compacto valem também para dados vindos de fora.

```java executar
import java.io.ByteArrayInputStream;
import java.io.ByteArrayOutputStream;
import java.io.EOFException;
import java.io.IOException;
import java.io.NotSerializableException;
import java.io.ObjectInputStream;
import java.io.ObjectOutputStream;
import java.io.Serializable;
import java.util.List;

public class Varios {
    record Ponto(int x, int y) implements Serializable {
        Ponto {
            if (x < 0) {
                throw new IllegalArgumentException("x negativo");
            }
            System.out.println("construtor do record: " + x + "," + y);
        }
    }

    static class Carteira implements Serializable {
        Object dono = new Object();
    }

    public static void main(String[] args) throws IOException, ClassNotFoundException {
        ByteArrayOutputStream bytes = new ByteArrayOutputStream();
        try (ObjectOutputStream out = new ObjectOutputStream(bytes)) {
            out.writeObject(new Ponto(1, 2));
            out.writeObject(List.of("a", "b"));
            out.writeInt(42);
        }
        try (ObjectInputStream in = new ObjectInputStream(new ByteArrayInputStream(bytes.toByteArray()))) {
            Ponto p = (Ponto) in.readObject();
            @SuppressWarnings("unchecked")
            List<String> lista = (List<String>) in.readObject();
            int n = in.readInt();
            System.out.println(p + " " + lista + " " + n);
            in.readObject();
        } catch (EOFException e) {
            System.out.println("fim do stream: " + e.getClass().getSimpleName());
        }
        try (ObjectOutputStream out = new ObjectOutputStream(new ByteArrayOutputStream())) {
            out.writeObject(new Carteira());
        } catch (NotSerializableException e) {
            System.out.println("não serializável: " + e.getMessage());
        }
    }
}
```

```saida
construtor do record: 1,2
construtor do record: 1,2
Ponto[x=1, y=2] [a, b] 42
fim do stream: EOFException
não serializável: java.lang.Object
```

O construtor do record roda duas vezes: na criação e na leitura. A `Carteira` é serializável, mas seu campo aponta para um `Object` comum, e a gravação falha.

Para controlar a serialização de uma classe comum, ela pode declarar os métodos **privados** `writeObject(ObjectOutputStream)` e `readObject(ObjectInputStream)`, que o mecanismo chama no lugar do comportamento padrão. A interface `Externalizable` vai além: a classe grava e lê tudo sozinha, com `writeExternal` e `readExternal`, e precisa de um construtor público sem argumentos, que é chamado na leitura.

> [!PROVA]
> `Serializable` é marcadora. `transient` e `static` não são gravados; na leitura, `transient` volta com o valor padrão. Construtores e inicializadores da classe serializável não rodam na leitura; o construtor sem argumentos da primeira superclasse não serializável roda. `readObject` declara `IOException` e `ClassNotFoundException`. Campo não serializável e não `transient` causa `NotSerializableException`. Ler além do fim lança `EOFException`.

## Por baixo dos panos

O formato gravado começa com um número mágico, `0xACED`, e uma versão. Depois, para cada objeto, vem a **descrição da classe**: nome, `serialVersionUID` e nome e tipo de cada campo. Em seguida, os valores. Se o mesmo objeto aparece duas vezes no grafo, a segunda ocorrência é só uma referência ao número do primeiro, o que preserva ciclos e compartilhamentos.

Para criar o objeto sem chamar o construtor, a JVM usa um truque: gera um construtor especial que aloca a instância da classe serializável, mas executa apenas o construtor da primeira superclasse não serializável. Esse poder de criar objetos sem passar pelas validações do construtor é exatamente o que torna a desserialização perigosa: um invasor que controla os bytes pode montar objetos em estados impossíveis, e, com as classes certas no classpath, encadear chamadas até executar código. Várias das falhas mais graves da história do Java vieram daí. As defesas são não desserializar dados de fontes não confiáveis e, quando necessário, usar o `ObjectInputFilter` (Java 9) para limitar as classes aceitas. Em sistemas novos, formatos como JSON, com bibliotecas que só preenchem objetos por construtores e setters, são a escolha comum.

## Resumo para a prova

- `implements Serializable`; `ObjectOutputStream.writeObject` e `ObjectInputStream.readObject` (com cast)
- `readObject` declara `IOException` e `ClassNotFoundException`
- `transient` e `static` não são gravados; `transient` volta com o valor padrão do tipo
- Na leitura, construtores e inicializadores da classe serializável não rodam; o da primeira superclasse não serializável roda
- Campo não serializável: `NotSerializableException`; versão diferente: `InvalidClassException`; ler além do fim: `EOFException`
- Records são lidos pelo construtor canônico; `Externalizable` exige construtor público sem argumentos
