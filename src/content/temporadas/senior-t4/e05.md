Quando os módulos chegaram, no Java 9, existiam milhões de JARs no mundo sem `module-info`, e nenhum projeto podia esperar que todas as suas dependências fossem modularizadas antes de começar. O sistema de módulos foi desenhado para conviver com esse legado: há dois tipos especiais de módulo, o **sem nome** e o **automático**, que permitem misturar código modular e não modular e migrar aos poucos. Este episódio fecha a temporada com eles e com as estratégias de migração.

## Os três tipos de módulo

| | Nomeado | Automático | Sem nome |
|---|---|---|---|
| De onde vem | JAR com `module-info` no module path | JAR comum no module path | Tudo o que está no classpath |
| Nome | O do descritor | Do manifesto ou do nome do arquivo | Nenhum |
| Exporta | Só o que declara | Todos os pacotes | Todos os pacotes |
| Lê | Só o que requer | Todos os módulos, inclusive o sem nome | Todos os módulos |
| Pode ser requerido por um nomeado | Sim | Sim, pelo nome | **Não** |

A última linha é a mais importante: um módulo nomeado **não consegue requerer** o classpath. Não existe nome para colocar no `requires`. Por isso, quando uma aplicação vira módulo, as bibliotecas de que ela depende precisam ir para o module path, como módulos automáticos.

## O módulo sem nome

Todo código carregado pelo classpath pertence a um único **módulo sem nome**, um por carregador de classes. Ele lê todos os módulos e exporta e abre todos os seus pacotes, imitando o comportamento de antes do Java 9. Por isso programas antigos continuam funcionando sem mudança, inclusive todos os exemplos deste site, que rodam assim.

```java executar
public class SemNome {
    public static void main(String[] args) {
        Module meu = SemNome.class.getModule();
        Module sql = java.sql.Connection.class.getModule();
        System.out.println(meu.isNamed() + " " + meu.getName() + " " + meu.getDescriptor());
        System.out.println(meu.canRead(sql) + " " + sql.canRead(meu));
        System.out.println(meu.isExported("qualquer.pacote") + " " + meu.isOpen("qualquer.pacote"));
    }
}
```

```saida
false null null
true false
true true
```

O módulo sem nome lê o `java.sql`, mas o `java.sql`, nomeado, não lê o módulo sem nome. Ele também não tem descritor: não há `module-info` para ler.

## Módulos automáticos

Um JAR comum, sem `module-info`, colocado no **module path**, vira um **módulo automático**. Ele ganha um nome, exporta e abre todos os seus pacotes e lê todos os outros módulos, inclusive o sem nome. O nome vem, nesta ordem:

1. Do atributo `Automatic-Module-Name` do `META-INF/MANIFEST.MF`, se existir. Bibliotecas que ainda não são modulares costumam declará-lo para reservar um nome estável.
2. Do nome do arquivo: tira-se o `.jar`; a partir do primeiro hífen seguido de um dígito, o resto vira a **versão**; os caracteres que não são letras nem dígitos viram pontos, pontos repetidos se fundem, e pontos no começo e no fim somem.

```java executar
import java.io.IOException;
import java.lang.module.FindException;
import java.lang.module.ModuleDescriptor;
import java.lang.module.ModuleFinder;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.Comparator;
import java.util.List;
import java.util.jar.Attributes;
import java.util.jar.JarOutputStream;
import java.util.jar.Manifest;
import java.util.stream.Stream;

public class Nomes {
    static Path criarJar(Path pasta, String nome, String nomeAutomatico) throws IOException {
        Manifest manifesto = new Manifest();
        manifesto.getMainAttributes().put(Attributes.Name.MANIFEST_VERSION, "1.0");
        if (nomeAutomatico != null) {
            manifesto.getMainAttributes().put(new Attributes.Name("Automatic-Module-Name"), nomeAutomatico);
        }
        Path jar = pasta.resolve(nome);
        try (JarOutputStream out = new JarOutputStream(Files.newOutputStream(jar), manifesto)) {
            out.flush();
        }
        return jar;
    }

    public static void main(String[] args) throws IOException {
        Path pasta = Files.createTempDirectory("jars");
        List<Path> jars = List.of(
            criarJar(pasta, "commons-lang3-3.12.0.jar", null),
            criarJar(pasta, "guava-32.1.2-jre.jar", null),
            criarJar(pasta, "my_util--lib.jar", null),
            criarJar(pasta, "json-1.0.jar", "com.empresa.json"));
        for (Path jar : jars) {
            ModuleDescriptor d = ModuleFinder.of(jar).findAll().iterator().next().descriptor();
            System.out.println(jar.getFileName() + " -> " + d.name() + " (" + d.version().map(Object::toString).orElse("sem versão") + ")");
        }
        try {
            ModuleFinder.of(criarJar(pasta, "cool-2go.jar", null)).findAll();
        } catch (FindException e) {
            System.out.println("cool-2go.jar -> nome inválido");
        }
        try (Stream<Path> todos = Files.walk(pasta)) {
            todos.sorted(Comparator.reverseOrder()).forEach(p -> p.toFile().delete());
        }
    }
}
```

```saida
commons-lang3-3.12.0.jar -> commons.lang3 (3.12.0)
guava-32.1.2-jre.jar -> guava (32.1.2-jre)
my_util--lib.jar -> my.util.lib (sem versão)
json-1.0.jar -> com.empresa.json (1.0)
cool-2go.jar -> nome inválido
```

O `json-1.0.jar` declarou um nome no manifesto, e ele vale mais que o do arquivo; a versão continua vindo do nome. O `cool-2go.jar` produziria `cool.2go`, e `2go` não é um identificador válido: o JAR não pode ser um módulo automático. O nome derivado do arquivo é frágil, porque muda se alguém renomear o JAR, e é por isso que o `Automatic-Module-Name` existe.

Carregado de verdade numa camada, um módulo automático mostra o resto das suas propriedades:

```java executar
import java.io.IOException;
import java.lang.module.Configuration;
import java.lang.module.ModuleFinder;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.Set;
import java.util.jar.Attributes;
import java.util.jar.JarEntry;
import java.util.jar.JarOutputStream;
import java.util.jar.Manifest;

public class Automatico {
    public static void main(String[] args) throws IOException {
        Path pasta = Files.createTempDirectory("auto");
        Path jar = pasta.resolve("commons-lang3-3.12.0.jar");
        Manifest manifesto = new Manifest();
        manifesto.getMainAttributes().put(Attributes.Name.MANIFEST_VERSION, "1.0");
        try (JarOutputStream out = new JarOutputStream(Files.newOutputStream(jar), manifesto)) {
            out.putNextEntry(new JarEntry("org/apache/commons/lang3/StringUtils.class"));
            out.closeEntry();
        }

        Configuration cf = ModuleLayer.boot().configuration().resolve(ModuleFinder.of(jar), ModuleFinder.of(), Set.of("commons.lang3"));
        ModuleLayer camada = ModuleLayer.boot().defineModulesWithOneLoader(cf, ClassLoader.getSystemClassLoader());
        Module lang3 = camada.findModule("commons.lang3").orElseThrow();
        System.out.println(lang3.getDescriptor().isAutomatic() + " " + lang3.getDescriptor().packages());
        System.out.println(lang3.isExported("org.apache.commons.lang3") + " " + lang3.isOpen("org.apache.commons.lang3"));
        System.out.println(lang3.canRead(Automatico.class.getModule()) + " " + lang3.canRead(ModuleLayer.boot().findModule("java.sql").orElseThrow()));

        Files.delete(jar);
        Files.delete(pasta);
    }
}
```

```saida
true [org.apache.commons.lang3]
true true
true true
```

O pacote foi descoberto pelas entradas do JAR, e é exportado e aberto. O módulo automático lê o módulo sem nome e o `java.sql`, sem nenhum `requires`.

## Estratégias de migração

Há duas formas clássicas de levar uma aplicação ao sistema de módulos:

- **De baixo para cima** (*bottom-up*): começa pelas bibliotecas sem dependências, que ganham `module-info` primeiro; depois as que dependem delas, até chegar à aplicação. Cada módulo novo só requer módulos já nomeados. Funciona quando o time controla todo o código.
- **De cima para baixo** (*top-down*): a aplicação vira módulo primeiro, e as dependências vão para o module path como **automáticas**, mesmo sem `module-info`. Cada uma é modularizada depois, se e quando o dono dela quiser. É a estratégia comum quando se depende de bibliotecas de terceiros.

```java
module com.loja.app {
    requires commons.lang3;      // um JAR comum, como módulo automático
    requires com.empresa.json;   // nome vindo do Automatic-Module-Name
    requires java.sql;
}
```

O `jdeps` do [episódio anterior](/assistir/senior-t4-e04) ajuda nas duas: mostra as dependências entre os JARs, e `jdeps --generate-module-info` escreve um primeiro rascunho de `module-info.java` para cada um. Um cuidado: dois JARs com o mesmo pacote funcionavam juntos no classpath, mas viram um *split package* no module path, e a aplicação deixa de iniciar.

> [!PROVA]
> Classpath: módulo sem nome, que lê tudo, exporta tudo e não pode ser requerido por módulos nomeados. JAR sem `module-info` no module path: módulo automático, que exporta e abre tudo, lê tudo, e tem o nome do `Automatic-Module-Name` ou derivado do arquivo (sem `.jar`, sem a versão, com pontos no lugar dos outros caracteres). Bottom-up modulariza das bibliotecas para a aplicação; top-down começa pela aplicação, com as dependências como automáticas.

## Por baixo dos panos

O descritor de um módulo automático é **sintetizado** quando o `ModuleFinder` encontra o JAR: o nome sai do manifesto ou do arquivo, os pacotes saem dos nomes das entradas que terminam em `.class`, e, se o JAR tiver arquivos em `META-INF/services`, eles viram diretivas `provides`, o que permite que bibliotecas antigas forneçam serviços a módulos nomeados. Na resolução, a JVM marca o módulo automático para ler todos os módulos da camada e faz com que ele conceda legibilidade implícita aos outros automáticos: quem requer um automático passa a ler todos eles, porque não há como saber quais deles ele realmente usa.

O módulo sem nome também tem uma regra de resolução própria: quando a aplicação inteira roda pelo classpath, a JVM escolhe como raiz um conjunto padrão de módulos do sistema, todos os que exportam alguma API, e é por isso que `java.sql` e `java.xml` estão disponíveis sem nenhuma opção. Quando a aplicação é um módulo, só entra o que o grafo de `requires` alcança, e um módulo do JDK usado só por reflexão precisa ser pedido com `--add-modules`.

## Resumo para a prova

- Três tipos: nomeado (`module-info` no module path), automático (JAR comum no module path) e sem nome (classpath)
- Sem nome: lê todos, exporta e abre todos, sem descritor; módulos nomeados não podem requerê-lo
- Automático: exporta e abre todos os pacotes, lê todos os módulos, inclusive o sem nome
- Nome automático: `Automatic-Module-Name` do manifesto ou o nome do arquivo sem `.jar`, sem a versão e com pontos
- Bottom-up: das bibliotecas para a aplicação; top-down: aplicação primeiro, dependências como automáticas
- `jdeps --generate-module-info` ajuda a criar descritores; pacotes divididos impedem a migração
