Os módulos dos episódios anteriores se conheciam pelo nome: `com.app` requer `com.loja`, e pronto. Mas muitos sistemas precisam de **extensões** que o código principal não conhece de antemão: um aplicativo de pagamentos que aceita Pix, cartão e boleto, cada um num módulo separado, que pode ou não estar instalado. O Java resolve isso com **serviços**, o mecanismo que o JDK usa internamente para encontrar drivers JDBC, sistemas de arquivos e codificações de caracteres.

## Os quatro papéis

| Papel | O que é | No exemplo |
|---|---|---|
| Interface do serviço | O contrato, uma interface ou classe abstrata | `com.loja.api.Pagamento` |
| Provedor | Uma implementação do serviço | `com.loja.pix.Pix` |
| Localizador | Quem encontra os provedores disponíveis | `java.util.ServiceLoader` |
| Consumidor | O código que usa o serviço | O aplicativo da loja |

O ponto central: o consumidor **não depende** dos provedores. Ele só conhece a interface. Os provedores são descobertos em tempo de execução, e acrescentar um meio de pagamento é colocar mais um JAR no module path, sem recompilar nada.

## Declarando nos módulos

```java
// módulo da API: só a interface
module com.loja.api {
    exports com.loja.api;
}

// um provedor
module com.loja.pix {
    requires com.loja.api;
    provides com.loja.api.Pagamento with com.loja.pix.Pix;
}

// o consumidor
module com.loja.app {
    requires com.loja.api;
    uses com.loja.api.Pagamento;
}
```

- `provides interface with implementação` registra o provedor. O pacote do provedor **não precisa ser exportado**: ninguém usa a classe `Pix` pelo nome, só pelo serviço.
- `uses interface` declara que o módulo vai procurar provedores daquele serviço. Um módulo nomeado que chama `ServiceLoader.load` sem o `uses` correspondente recebe um `ServiceConfigurationError`.
- O consumidor não tem `requires com.loja.pix`. É exatamente isso que permite trocar ou acrescentar provedores.

Um provedor precisa ter um **construtor público sem argumentos** ou, nos módulos, um método `public static` chamado `provider()` que devolva a instância, útil para provedores únicos ou que precisam de configuração.

## ServiceLoader

```java
ServiceLoader<Pagamento> loader = ServiceLoader.load(Pagamento.class);
for (Pagamento p : loader) { ... }                         // instancia cada provedor
Optional<Pagamento> primeiro = loader.findFirst();          // o primeiro, se houver
loader.stream().map(ServiceLoader.Provider::type)...        // os tipos, sem instanciar
```

O carregamento é **preguiçoso**: cada provedor só é instanciado quando o iterador chega nele. O `stream()`, do Java 9, devolve objetos `ServiceLoader.Provider`, com `type()`, que informa a classe sem criá-la, e `get()`, que cria a instância. Isso permite escolher um provedor pelo tipo, ou por uma anotação, antes de pagar o custo de construí-lo.

Nenhum provedor instalado não é erro: o `ServiceLoader` simplesmente fica vazio, e o consumidor decide o que fazer, por exemplo usar uma implementação padrão.

```java executar
import java.util.ServiceLoader;

public class SemProvedor {
    interface Relatorio {
        String gerar();
    }

    public static void main(String[] args) {
        ServiceLoader<Relatorio> loader = ServiceLoader.load(Relatorio.class);
        System.out.println(loader.findFirst() + " " + loader.stream().count() + " " + loader.iterator().hasNext());
        Relatorio r = loader.findFirst().orElse(() -> "relatório padrão");
        System.out.println(r.gerar());
    }
}
```

```saida
Optional.empty 0 false
relatório padrão
```

Fora de módulos, no classpath, o registro é feito por um arquivo de texto em `META-INF/services/`, cujo nome é o nome completo da interface e cujo conteúdo lista as implementações, uma por linha. O exemplo abaixo cria esse arquivo numa pasta temporária e aponta um carregador de classes para ela, reproduzindo o que um JAR de provedor faria:

```java executar
import java.io.IOException;
import java.net.URL;
import java.net.URLClassLoader;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.ServiceLoader;

public class Servicos {
    public interface Pagamento {
        String nome();
        long taxaEmCentavos(long valor);
    }

    public static class Pix implements Pagamento {
        public String nome() { return "pix"; }
        public long taxaEmCentavos(long valor) { return 0; }
    }

    public static class Cartao implements Pagamento {
        public Cartao() {
            System.out.println("Cartao criado");
        }
        public String nome() { return "cartão"; }
        public long taxaEmCentavos(long valor) { return valor * 3 / 100; }
    }

    public static void main(String[] args) throws IOException {
        Path raiz = Files.createTempDirectory("servicos");
        Path arquivo = raiz.resolve("META-INF/services/" + Pagamento.class.getName());
        Files.createDirectories(arquivo.getParent());
        Files.writeString(arquivo, "# provedores de pagamento\n" + Pix.class.getName() + "\n" + Cartao.class.getName() + "\n");

        try (URLClassLoader carregador = new URLClassLoader(new URL[] {raiz.toUri().toURL()}, Servicos.class.getClassLoader())) {
            ServiceLoader<Pagamento> loader = ServiceLoader.load(Pagamento.class, carregador);
            System.out.println(loader.stream().map(p -> p.type().getSimpleName()).toList());
            for (Pagamento p : loader) {
                System.out.println(p.nome() + ": taxa de " + p.taxaEmCentavos(10_000) + " centavos sobre R$ 100");
            }
            System.out.println(loader.findFirst().map(Pagamento::nome).orElse("nenhum"));
        }

        Files.delete(arquivo);
        Files.delete(arquivo.getParent());
        Files.delete(arquivo.getParent().getParent());
        Files.delete(raiz);
    }
}
```

```saida
[Pix, Cartao]
pix: taxa de 0 centavos sobre R$ 100
Cartao criado
cartão: taxa de 300 centavos sobre R$ 100
pix
```

A primeira linha lista os provedores sem criar nenhum: a mensagem do construtor de `Cartao` só aparece quando o laço chega nele. Linhas que começam com `#` no arquivo são comentários. E o `findFirst` não recria o `Cartao`: o `ServiceLoader` guarda os provedores que já instanciou.

## Os serviços do próprio JDK

O JDK é o maior usuário desse mecanismo. O `java.sql` declara `uses java.sql.Driver`, e é assim que o `DriverManager` encontra o driver do banco que estiver no module path. Os sistemas de arquivos do [episódio de Path](/assistir/senior-t3-e04) também são serviços:

```java executar
import java.lang.module.ModuleDescriptor;
import java.nio.file.spi.FileSystemProvider;
import java.util.List;
import java.util.ServiceLoader;
import java.util.TreeSet;

public class ServicosDoJdk {
    public static void main(String[] args) {
        System.out.println(ServiceLoader.load(FileSystemProvider.class).stream().map(p -> p.type().getSimpleName()).sorted().toList());
        System.out.println(new TreeSet<>(ModuleLayer.boot().modules().stream()
            .filter(m -> m.getDescriptor().provides().stream().anyMatch(p -> p.service().equals(FileSystemProvider.class.getName())))
            .map(Module::getName).toList()));
        System.out.println(ModuleLayer.boot().findModule("java.sql").orElseThrow().getDescriptor().uses());

        ModuleDescriptor consumidor = ModuleDescriptor.newModule("com.loja.app")
            .requires("com.loja.api").uses("com.loja.api.Pagamento").build();
        ModuleDescriptor provedor = ModuleDescriptor.newModule("com.loja.pix")
            .requires("com.loja.api").provides("com.loja.api.Pagamento", List.of("com.loja.pix.Pix")).build();
        System.out.println(consumidor.uses() + " " + provedor.provides() + " " + provedor.exports());
    }
}
```

```saida
[JrtFileSystemProvider, ZipFileSystemProvider]
[java.base, jdk.zipfs]
[java.sql.Driver]
[com.loja.api.Pagamento] [com.loja.api.Pagamento with [com.loja.pix.Pix]] []
```

O provedor de arquivos ZIP mora no módulo `jdk.zipfs`, e o do `jrt:/` no próprio `java.base`. O descritor do provedor confirma o que o `module-info` dizia: ele fornece o serviço sem exportar pacote nenhum.

> [!PROVA]
> `provides Interface with Implementacao` fica no provedor; `uses Interface` fica no consumidor, que chama `ServiceLoader.load(Interface.class)`. O consumidor não requer o provedor, e o provedor não precisa exportar seu pacote. O provedor precisa de construtor público sem argumentos ou de um método `public static provider()`. `ServiceLoader` é preguiçoso, e `stream()` dá acesso a `type()` sem instanciar. No classpath, o registro é o arquivo `META-INF/services/nome.da.Interface`.

## Por baixo dos panos

Na resolução da camada de inicialização, a JVM também liga os serviços: para cada `uses`, procura no module path os módulos com `provides` correspondente e os **acrescenta ao grafo**, mesmo que nenhum `requires` aponte para eles. É por isso que basta colocar o JAR de um driver no module path. Essa etapa se chama *service binding*. O `ServiceLoader` depois percorre os módulos da camada, depois as camadas pai, e por fim o classpath, nessa ordem.

No classpath, o `ServiceLoader` pede ao carregador de classes todos os recursos com o nome `META-INF/services/<interface>`, de todos os JARs, lê os nomes de classe de cada arquivo e carrega cada uma com `Class.forName` quando o iterador chega nela. A instância é criada por reflexão, pelo construtor sem argumentos. O mesmo padrão aparece fora do JDK: o Spring Boot descobre suas autoconfigurações por arquivos parecidos dentro dos JARs, e o JUnit encontra seus motores de teste pelo próprio `ServiceLoader`.

## Resumo para a prova

- Papéis: interface do serviço, provedor, localizador (`ServiceLoader`) e consumidor
- Provedor: `provides api.Servico with impl.Classe;`, sem precisar exportar o pacote da implementação
- Consumidor: `uses api.Servico;` e `ServiceLoader.load(Servico.class)`; sem `uses`, `ServiceConfigurationError`
- Provedor com construtor público sem argumentos, ou método `public static provider()` em módulos
- `for`, `findFirst()` e `stream()` com `Provider.type()` e `get()`; tudo preguiçoso
- Classpath: arquivo `META-INF/services/` com o nome completo da interface e uma implementação por linha
