Até o Java 8, um programa era um punhado de JARs jogados no **classpath**. Qualquer classe `public` de qualquer JAR podia ser usada por qualquer outra, inclusive as internas do próprio JDK, como `sun.misc.Unsafe`. Se faltasse um JAR, o erro só aparecia quando o código chegava na classe ausente, às vezes semanas depois do deploy. Se dois JARs trouxessem versões da mesma classe, valia a que aparecesse primeiro. O Java 9 respondeu com o **Sistema de Módulos da Plataforma Java** (JPMS, do Projeto Jigsaw), e o próprio JDK foi dividido em uns 70 módulos.

## O que um módulo resolve

Um **módulo** é um conjunto de pacotes com um nome e uma descrição do que **exporta** e do que **requer**. Isso traz três garantias:

- **Encapsulamento forte**: `public` deixa de significar "visível para todos". Uma classe `public` só é acessível fora do módulo se o pacote dela for **exportado**.
- **Configuração confiável**: na largada, a JVM confere se todos os módulos requeridos estão presentes, e se não estão, recusa iniciar, com uma mensagem clara.
- **Imagens menores**: como as dependências são explícitas, a ferramenta `jlink` monta um runtime só com os módulos usados, assunto do [episódio 4](/assistir/senior-t4-e04).

## module-info.java

A descrição fica num arquivo `module-info.java`, na raiz do código-fonte do módulo, fora de qualquer pacote:

```java
module com.loja {
    requires java.sql;
    exports com.loja.api;
    exports com.loja.dto to com.loja.web;
}
```

- `module com.loja` dá o nome. Por convenção, segue o estilo de pacotes, em DNS reverso; pontos são permitidos, hifens não.
- `requires java.sql` declara uma dependência. O `java.base`, com `java.lang`, `java.util` e companhia, é requerido implicitamente por todos.
- `exports com.loja.api` torna os tipos `public` desse **pacote** acessíveis a quem requer o módulo. Exporta-se pacote, nunca classe, e não há exportação recursiva: `com.loja.api.v2` precisaria do próprio `exports`.
- `exports com.loja.dto to com.loja.web` é uma **exportação qualificada**: só o módulo `com.loja.web` enxerga o pacote.

Uma estrutura típica de pastas, com os comandos para compilar e rodar:

```text
src/com.loja/module-info.java
src/com.loja/com/loja/api/Catalogo.java
src/com.loja/com/loja/interno/Banco.java

javac -d mods --module-source-path src -m com.loja
java --module-path mods --module com.loja/com.loja.api.Catalogo
```

`--module-path` (abreviado `-p`) substitui o classpath para módulos, e `--module` (`-m`) diz o módulo e a classe principal. Também existem regras que o compilador e a JVM impõem:

| Regra | Consequência |
|---|---|
| Sem ciclos de `requires` | `a` requer `b` e `b` requer `a`: não compila |
| Um pacote pertence a um só módulo | Dois módulos com o mesmo pacote (*split package*): a JVM recusa iniciar |
| Todo tipo de um módulo está num pacote nomeado | O pacote padrão, sem `package`, não existe em módulos |
| Uma dependência ausente | A JVM não inicia: `Module java.sql not found` |

## Vendo os módulos em execução

Tudo isso existe também em tempo de execução, na classe `java.lang.Module`. Uma classe rodando no classpath, como os exemplos deste site, pertence ao **módulo sem nome** (*unnamed module*), assunto do [episódio 5](/assistir/senior-t4-e05).

```java executar
public class Modulos {
    public static void main(String[] args) {
        Module base = String.class.getModule();
        Module meu = Modulos.class.getModule();
        System.out.println(base.getName() + " " + base.isNamed());
        System.out.println(meu.getName() + " " + meu.isNamed());
        System.out.println(base.isExported("java.util") + " " + base.isExported("jdk.internal.misc"));
        System.out.println(java.sql.Connection.class.getModule().getName());
    }
}
```

```saida
java.base true
null false
true false
java.sql
```

O `java.base` exporta `java.util`, mas não `jdk.internal.misc`, um pacote interno do JDK: suas classes são `public`, e mesmo assim nenhum código de fora do módulo consegue usá-las. O descritor de um módulo, a versão compilada do `module-info`, também pode ser lido:

```java executar
import java.lang.module.ModuleDescriptor;
import java.lang.module.ModuleDescriptor.Requires;

public class Descritor {
    public static void main(String[] args) {
        ModuleDescriptor sql = ModuleLayer.boot().findModule("java.sql").orElseThrow().getDescriptor();
        System.out.println(sql.requires().stream().map(Requires::name).sorted().toList());
        System.out.println(sql.exports().stream().map(ModuleDescriptor.Exports::source).sorted().toList());
    }
}
```

```saida
[java.base, java.logging, java.transaction.xa, java.xml]
[java.sql, javax.sql]
```

O `java.base` aparece na lista mesmo sem estar escrito no `module-info` do `java.sql`: é a dependência implícita, marcada como `MANDATED`. Pela linha de comando, `java --list-modules` lista os módulos do JDK, e `java --describe-module java.sql` mostra o descritor.

## Montando um descritor

A classe `ModuleDescriptor` tem um construtor que monta descritores em código, útil para ferramentas e para entender o formato. Ele aplica as mesmas regras do compilador:

```java executar
import java.lang.module.ModuleDescriptor;
import java.util.Set;
import java.util.TreeSet;

public class Montando {
    public static void main(String[] args) {
        ModuleDescriptor loja = ModuleDescriptor.newModule("com.loja")
            .requires("java.sql")
            .exports("com.loja.api")
            .exports(Set.of(), "com.loja.dto", Set.of("com.loja.web"))
            .packages(Set.of("com.loja.interno"))
            .build();
        System.out.println(new TreeSet<>(loja.requires().stream().map(r -> r.name() + r.modifiers()).toList()));
        System.out.println(new TreeSet<>(loja.packages()));
        loja.exports().stream()
            .sorted((a, b) -> a.source().compareTo(b.source()))
            .forEach(e -> System.out.println(e.source() + (e.isQualified() ? " só para " + e.targets() : " para todos")));
        try {
            ModuleDescriptor.newModule("minha-loja");
        } catch (IllegalArgumentException e) {
            System.out.println("nome inválido");
        }
    }
}
```

```saida
[java.base[MANDATED], java.sql[]]
[com.loja.api, com.loja.dto, com.loja.interno]
com.loja.api para todos
com.loja.dto só para [com.loja.web]
nome inválido
```

O pacote `com.loja.interno` faz parte do módulo, mas não é exportado: suas classes, mesmo `public`, só são usadas dentro de `com.loja`.

> [!VERSAO]
> O Java 25 trouxe as **declarações de importação de módulo** (JEP 511): `import module java.base;` importa, de uma vez, todos os pacotes que o módulo exporta, e também os que ele repassa por `requires transitive`. Não é preciso que o programa seja um módulo.

```java executar java25
import module java.base;

public class ImportaModulo {
    public static void main(String[] args) {
        List<String> nomes = new ArrayList<>(List.of("bia", "ana"));
        Collections.sort(nomes);
        System.out.println(nomes + " " + Path.of("x.txt").getFileName() + " " + Duration.ofMinutes(90));
    }
}
```

```saida
[ana, bia] x.txt PT1H30M
```

> [!PROVA]
> `module-info.java` fica na raiz do módulo. `requires` declara dependências; `exports` torna públicos os tipos `public` de um **pacote**; `exports ... to` restringe a módulos específicos. `java.base` é requerido implicitamente. Não há ciclos de `requires` nem pacotes divididos entre módulos. Rodar: `java -p pasta -m modulo/pacote.Classe`.

## Por baixo dos panos

O `module-info.java` é compilado para um `module-info.class` com um atributo `Module` no formato de classe, onde ficam nome, versão, `requires`, `exports` e as demais diretivas. Na partida, a JVM monta a **camada de inicialização** (*boot layer*): parte dos módulos raiz, lê os descritores, resolve o grafo de `requires` e cria uma **configuração** em que cada módulo sabe quais outros ele **lê**. Se algo faltar ou se dois módulos trouxerem o mesmo pacote, a resolução falha antes de executar uma linha do programa.

Cada pacote fica associado a exatamente um módulo, e essa tabela é usada pelos carregadores de classe para saber onde procurar cada classe, sem varrer JARs. O acesso também é conferido pela própria JVM, na ligação de cada chamada: além do `public`, ela verifica se o módulo de quem chama lê o módulo da classe e se o pacote está exportado para ele. Por isso o encapsulamento é **forte**: não depende do compilador, e vale também para código gerado em tempo de execução.

## Resumo para a prova

- Módulo: nome, pacotes, `requires` e `exports`, descritos em `module-info.java` na raiz do módulo
- `exports` é por pacote e não é recursivo; `exports pacote to modulo` qualifica
- `public` num pacote não exportado só é visível dentro do módulo
- `java.base` é implícito; sem ciclos; um pacote em um só módulo; sem pacote padrão
- `javac --module-source-path` / `-d`; `java --module-path` (`-p`) e `--module` (`-m modulo/classe`)
- Em execução: `Class.getModule()`, `Module.isNamed()`, `isExported`, `ModuleDescriptor`; Java 25: `import module`
