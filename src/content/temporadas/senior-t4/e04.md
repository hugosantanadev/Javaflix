Os episódios anteriores escreveram descritores de módulo. Este trata do ciclo completo: transformar o código compilado num **JAR modular**, analisar as dependências com o **`jdeps`** e montar, com o **`jlink`**, um runtime Java sob medida, só com os módulos que a aplicação usa. É assim que se entrega uma aplicação Java para um contêiner ou um dispositivo sem levar o JDK inteiro junto.

## JAR modular

Um JAR modular é um JAR comum com um `module-info.class` na raiz. Ele é criado pela ferramenta `jar`:

```bash
javac -d classes/com.loja $(find src/com.loja -name "*.java")
jar --create --file mods/com.loja.jar --main-class com.loja.api.Main -C classes/com.loja .
jar --describe-module --file mods/com.loja.jar
java --module-path mods --module com.loja
```

- `--main-class` grava a classe principal no descritor; por isso o `java` pode receber só o nome do módulo, sem `/classe`.
- `--describe-module` (abreviado `-d`) mostra o descritor gravado no JAR: `exports`, `requires`, pacotes internos (`contains`) e classe principal.

O **mesmo** JAR se comporta de forma diferente conforme onde é colocado:

| Onde | JAR modular | JAR comum, sem `module-info` |
|---|---|---|
| Module path (`-p`) | Módulo nomeado, com o descritor | Módulo **automático** |
| Classpath (`-cp`) | Módulo sem nome: o `module-info` é ignorado | Módulo sem nome |

Os módulos automáticos e o módulo sem nome são o assunto do [próximo episódio](/assistir/senior-t4-e05).

## As ferramentas também são APIs

Quase todas as ferramentas da linha de comando do JDK, como `javac`, `jar`, `jdeps` e `jlink`, também podem ser chamadas de dentro de um programa Java, pela interface `java.util.spi.ToolProvider`:

```java executar
import java.util.List;
import java.util.spi.ToolProvider;

public class Ferramentas {
    public static void main(String[] args) {
        for (String nome : List.of("javac", "jar", "jdeps", "jlink", "jmod", "java")) {
            System.out.println(nome + ": " + ToolProvider.findFirst(nome).map(t -> "disponível").orElse("não é um ToolProvider"));
        }
    }
}
```

```saida
javac: disponível
jar: disponível
jdeps: disponível
jlink: disponível
jmod: disponível
java: não é um ToolProvider
```

O `java` fica de fora porque ele não é uma ferramenta que roda dentro da JVM: é o lançador da própria JVM. O exemplo abaixo usa as outras para fazer o ciclo inteiro: escreve o código de um módulo numa pasta temporária, compila, empacota num JAR modular, lê o descritor de volta, analisa com `jdeps` e, por fim, carrega o módulo numa **camada** nova e executa sua classe principal.

```java executar
import java.io.IOException;
import java.io.PrintWriter;
import java.io.StringWriter;
import java.lang.module.Configuration;
import java.lang.module.ModuleDescriptor;
import java.lang.module.ModuleFinder;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.Comparator;
import java.util.Set;
import java.util.TreeSet;
import java.util.spi.ToolProvider;
import java.util.stream.Stream;

public class Empacotar {
    static void escrever(Path raiz, String caminho, String codigo) throws IOException {
        Path arquivo = raiz.resolve(caminho);
        Files.createDirectories(arquivo.getParent());
        Files.writeString(arquivo, codigo);
    }

    static String ferramenta(String nome, String... argumentos) {
        StringWriter saida = new StringWriter();
        PrintWriter escritor = new PrintWriter(saida);
        int codigo = ToolProvider.findFirst(nome).orElseThrow().run(escritor, escritor, argumentos);
        escritor.flush();
        if (codigo != 0) {
            throw new IllegalStateException(nome + " falhou: " + saida);
        }
        return saida.toString();
    }

    public static void main(String[] args) throws Exception {
        Path base = Files.createTempDirectory("modular");
        Path fonte = base.resolve("src");
        escrever(fonte, "module-info.java", "module com.loja { requires java.sql; exports com.loja.api; }");
        escrever(fonte, "com/loja/api/Main.java", "package com.loja.api; public class Main { public static void main(String[] a) { System.out.println(\"loja no ar\"); } }");
        escrever(fonte, "com/loja/interno/Banco.java", "package com.loja.interno; public class Banco { java.sql.Connection conexao; }");

        Path classes = base.resolve("classes");
        Path jar = base.resolve("mods/com.loja.jar");
        Files.createDirectories(jar.getParent());
        ferramenta("javac", "-d", classes.toString(),
            fonte.resolve("module-info.java").toString(),
            fonte.resolve("com/loja/api/Main.java").toString(),
            fonte.resolve("com/loja/interno/Banco.java").toString());
        ferramenta("jar", "--create", "--file", jar.toString(), "--main-class", "com.loja.api.Main", "-C", classes.toString(), ".");

        ModuleDescriptor d = ModuleFinder.of(jar).find("com.loja").orElseThrow().descriptor();
        System.out.println(d.name() + " " + d.isAutomatic() + " " + d.mainClass().orElse("-") + " " + new TreeSet<>(d.packages()));
        System.out.println(ferramenta("jdeps", "--list-deps", jar.toString()).strip().lines().map(String::strip).toList());

        Configuration configuracao = ModuleLayer.boot().configuration().resolve(ModuleFinder.of(jar.getParent()), ModuleFinder.of(), Set.of("com.loja"));
        ModuleLayer camada = ModuleLayer.boot().defineModulesWithOneLoader(configuracao, ClassLoader.getSystemClassLoader());
        Module loja = camada.findModule("com.loja").orElseThrow();
        System.out.println(loja.isExported("com.loja.api") + " " + loja.isExported("com.loja.interno"));
        Class<?> principal = camada.findLoader("com.loja").loadClass("com.loja.api.Main");
        principal.getMethod("main", String[].class).invoke(null, (Object) new String[0]);

        try (Stream<Path> todos = Files.walk(base)) {
            todos.sorted(Comparator.reverseOrder()).forEach(p -> p.toFile().delete());
        }
    }
}
```

```saida
com.loja false com.loja.api.Main [com.loja.api, com.loja.interno]
[java.base, java.sql]
true false
loja no ar
```

O descritor lido do JAR tem o nome, a classe principal gravada pelo `--main-class` e os dois pacotes, dos quais só um é exportado. O `jdeps` encontrou as duas dependências olhando o bytecode. E a camada nova é, em miniatura, o que o `java --module-path` faz: resolver o grafo a partir de um módulo raiz e carregar as classes de cada módulo.

## jdeps: quem depende de quem

O `jdeps` lê classes e JARs e informa de quais pacotes e módulos eles dependem. É a ferramenta para preparar uma migração ou um `jlink`:

| Comando | Mostra |
|---|---|
| `jdeps app.jar` | As dependências por pacote |
| `jdeps -summary app.jar` | Um resumo por módulo ou JAR |
| `jdeps --list-deps app.jar` | Só a lista dos módulos do JDK necessários |
| `jdeps --jdk-internals app.jar` | Uso de APIs internas do JDK, com a sugestão de substituta |
| `jdeps --generate-module-info pasta app.jar` | Um rascunho de `module-info.java` para um JAR comum |

O `--jdk-internals` é especialmente útil antes de atualizar a versão do Java: ele aponta, por exemplo, o uso de `sun.misc.BASE64Encoder` e sugere `java.util.Base64`.

## jlink: um runtime sob medida

O `jlink` junta módulos num **runtime** completo, com a sua própria pasta `bin/java`, mas só com os módulos pedidos e suas dependências:

```bash
jlink --module-path mods --add-modules com.loja \
      --output loja-runtime \
      --launcher loja=com.loja/com.loja.api.Main \
      --strip-debug --no-header-files --no-man-pages
loja-runtime/bin/loja
```

- `--add-modules` diz os módulos raiz; o `jlink` acrescenta todos os que eles requerem, recursivamente.
- `--launcher` cria um script `bin/loja` que já chama a classe principal.
- `--strip-debug`, `--no-header-files` e `--no-man-pages` removem o que um runtime de produção não precisa, e `--compress` compacta os recursos.

Uma regra importante: o `jlink` só trabalha com módulos **nomeados**. JARs comuns e módulos automáticos não entram numa imagem. O exemplo abaixo chama o `jlink` do mesmo jeito, para o módulo `java.sql`, e lê o arquivo `release` da imagem gerada:

```java executar
import java.io.PrintWriter;
import java.io.StringWriter;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.Comparator;
import java.util.spi.ToolProvider;
import java.util.stream.Stream;

public class Linkar {
    public static void main(String[] args) throws Exception {
        Path base = Files.createTempDirectory("imagem");
        Path saida = base.resolve("runtime");
        StringWriter mensagens = new StringWriter();
        int codigo = ToolProvider.findFirst("jlink").orElseThrow().run(new PrintWriter(mensagens), new PrintWriter(mensagens),
            "--add-modules", "java.sql", "--output", saida.toString(), "--strip-debug", "--no-header-files", "--no-man-pages");
        System.out.println("jlink terminou com código " + codigo);
        System.out.println(Files.readAllLines(saida.resolve("release")).stream().filter(l -> l.startsWith("MODULES")).toList());
        System.out.println(Files.exists(saida.resolve("bin")) + " " + Files.exists(saida.resolve("lib/modules")));
        try (Stream<Path> todos = Files.walk(base)) {
            todos.sorted(Comparator.reverseOrder()).forEach(p -> p.toFile().delete());
        }
    }
}
```

```saida
jlink terminou com código 0
[MODULES="java.base java.logging java.transaction.xa java.xml java.sql"]
true true
```

Pedimos só o `java.sql`, e a imagem veio com mais quatro: o `java.base` e os três que o `java.sql` repassa com `requires transitive`. O arquivo `lib/modules` guarda as classes de todos eles num formato próprio, o **jimage**, otimizado para carregar rápido. A imagem inteira fica na casa dos 50 MB, contra mais de 300 MB de um JDK completo.

> [!VERSAO]
> Até o Java 23, o `jlink` precisava dos arquivos `.jmod` da pasta `jmods` do JDK. Desde o Java 24 (JEP 493), um JDK construído com essa opção monta imagens a partir do próprio runtime, e pode ser distribuído sem a pasta `jmods`, o que o deixa cerca de 25% menor. Para gerar instaladores nativos (`.msi`, `.deb`, `.dmg`), o JDK traz desde o Java 16 o `jpackage`, que usa o `jlink` por baixo.

> [!PROVA]
> JAR modular = JAR com `module-info.class` na raiz. `jar --create --file x.jar --main-class pacote.Classe -C classes .`; `jar --describe-module --file x.jar`. No module path, um JAR modular é módulo nomeado; no classpath, vai para o módulo sem nome. `jdeps` lista dependências (`--list-deps`, `-summary`, `--jdk-internals`). `jlink --module-path ... --add-modules ... --output pasta` cria um runtime; só aceita módulos nomeados.

## Por baixo dos panos

O `jdeps` não executa nada: ele lê os arquivos `.class` e percorre o **pool de constantes** de cada um, a tabela onde o bytecode guarda os nomes das classes, métodos e campos que usa. Cada referência a uma classe de outro pacote vira uma aresta no grafo de dependências, e cada pacote é associado ao módulo que o contém. Por isso o `jdeps` não enxerga dependências criadas por reflexão, como um `Class.forName("org.postgresql.Driver")`: elas são só texto até o programa rodar.

O `jlink` funciona como um **ligador**: copia os módulos resolvidos para o arquivo `lib/modules` e aplica *plugins* que transformam as classes no caminho, como remover a informação de depuração ou pré-calcular a configuração dos módulos. Como o grafo é conhecido inteiro no momento da ligação, a JVM da imagem pula boa parte da resolução na partida. O `ToolProvider` usado nos exemplos é, ele mesmo, um serviço do [episódio anterior](/assistir/senior-t4-e03): cada ferramenta do JDK é um provedor encontrado pelo `ServiceLoader`.

## Resumo para a prova

- JAR modular: `module-info.class` na raiz; `--main-class` grava a classe principal; `--describe-module` mostra o descritor
- Module path: JAR modular vira módulo nomeado, JAR comum vira automático; classpath: tudo vai para o módulo sem nome
- `jdeps`: `--list-deps`, `-summary`, `--jdk-internals`, `--generate-module-info`; analisa bytecode, não reflexão
- `jlink --module-path mods --add-modules raiz --output pasta`, com `--launcher`, `--strip-debug` e `--compress`
- `jlink` inclui as dependências recursivamente e só aceita módulos nomeados
- As ferramentas do JDK também podem ser chamadas por `java.util.spi.ToolProvider`
