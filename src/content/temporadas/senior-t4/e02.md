O [episódio anterior](/assistir/senior-t4-e01) cobriu o essencial: um módulo requer outros e exporta pacotes. Na prática, duas situações pedem mais. A primeira: a API de um módulo devolve tipos de outro, e quem a usa precisaria requerer os dois. A segunda: frameworks como Spring, Hibernate e Jackson leem e alteram campos **privados** por reflexão, e o encapsulamento forte dos módulos os impede. Este episódio trata das duas, com `requires transitive` e `opens`.

## requires transitive: dependência repassada

Imagine o módulo `com.loja`, cujo método público `Catalogo.registrar()` devolve um `java.util.logging.Logger`. Quem usa `com.loja` recebe um `Logger`, e para usá-lo precisaria também de `requires java.logging`. Para não obrigar cada cliente a descobrir isso, o módulo declara:

```java
module com.loja {
    requires transitive java.logging;
    exports com.loja.api;
}
```

Agora, todo módulo que **lê** `com.loja` passa a ler também `java.logging`. Isso se chama **legibilidade implícita** (*implied readability*). A regra prática: use `transitive` quando os tipos do outro módulo aparecem na **sua API pública**, em parâmetros, retornos ou exceções; use o `requires` comum quando o outro módulo é só um detalhe de implementação.

O próprio JDK usa isso. O `java.sql` repassa `java.logging`, `java.xml` e `java.transaction.xa`, e o `java.sql.rowset` repassa o `java.sql`. Por isso o `java.sql.rowset` lê o `java.xml` sem declará-lo:

```java executar
import java.lang.module.ModuleDescriptor.Requires;
import java.util.TreeSet;

public class Transitivo {
    static String requer(String modulo) {
        return new TreeSet<>(ModuleLayer.boot().findModule(modulo).orElseThrow().getDescriptor().requires().stream()
            .filter(r -> !r.modifiers().contains(Requires.Modifier.MANDATED))
            .map(r -> (r.modifiers().contains(Requires.Modifier.TRANSITIVE) ? "transitive " : "") + r.name())
            .toList()).toString();
    }

    public static void main(String[] args) {
        System.out.println("java.sql: " + requer("java.sql"));
        System.out.println("java.sql.rowset: " + requer("java.sql.rowset"));
        Module rowset = ModuleLayer.boot().findModule("java.sql.rowset").orElseThrow();
        Module xml = ModuleLayer.boot().findModule("java.xml").orElseThrow();
        Module desktop = ModuleLayer.boot().findModule("java.desktop").orElseThrow();
        System.out.println(rowset.canRead(xml) + " " + rowset.canRead(desktop));
    }
}
```

```saida
java.sql: [transitive java.logging, transitive java.transaction.xa, transitive java.xml]
java.sql.rowset: [transitive java.logging, transitive java.naming, transitive java.sql]
true false
```

A legibilidade se propaga por cadeias de `transitive`, mas só por elas: o `java.desktop` não está em nenhuma, e o `java.sql.rowset` não o lê.

Há ainda o **`requires static`**: uma dependência obrigatória para **compilar**, mas opcional em **execução**. Serve para bibliotecas de anotações ou para integrações que só funcionam se o outro módulo estiver presente; o código precisa testar se ele existe antes de usá-lo.

## Reflexão e encapsulamento forte

A reflexão permite inspecionar e chamar membros de uma classe em tempo de execução: `getDeclaredField`, `getMethod`, `invoke`. Com `setAccessible(true)`, chega a acessar membros **privados**, a chamada **reflexão profunda**. Antes dos módulos, qualquer código fazia isso com qualquer classe, inclusive as internas do JDK.

Com módulos, a regra mudou. Reflexão sobre membros `public` de pacotes **exportados** continua livre. Mas `setAccessible` em membros privados de outro módulo só funciona se o pacote estiver **aberto** para quem chama. Sem isso, lança `InaccessibleObjectException`. A versão `trySetAccessible()` faz a mesma tentativa e devolve `false` em vez de lançar.

```java executar
import java.lang.reflect.Field;
import java.lang.reflect.Method;

public class Reflexao {
    private String segredo = "interno";

    public static void main(String[] args) throws Exception {
        Field meu = Reflexao.class.getDeclaredField("segredo");
        meu.setAccessible(true);
        System.out.println(meu.get(new Reflexao()));

        Method length = String.class.getMethod("length");
        System.out.println(length.invoke("javaflix"));

        Field valor = String.class.getDeclaredField("value");
        System.out.println(valor.trySetAccessible() + " " + String.class.getModule().isOpen("java.lang"));
        try {
            valor.setAccessible(true);
        } catch (RuntimeException e) {
            System.out.println(e.getClass().getName());
        }
    }
}
```

```saida
interno
8
false false
java.lang.reflect.InaccessibleObjectException
```

Dentro do próprio módulo, a reflexão profunda funciona: a classe abre seu campo privado. Chamar o método público `length` de `String` também funciona, porque `java.lang` é exportado. Mas o campo privado `value` de `String` está num pacote que o `java.base` não abre.

> [!VERSAO]
> Do Java 9 ao 15, o acesso por reflexão às partes internas do JDK ainda era permitido, com um aviso. O Java 16 passou a bloqueá-lo por padrão (JEP 396), e o Java 17 removeu a opção `--illegal-access` que o liberava (JEP 403). Hoje, só a linha de comando com `--add-opens` reabre um pacote do JDK.

## opens: liberando a reflexão profunda

Um módulo libera a reflexão profunda sobre seus pacotes com **`opens`**. Existem três formas:

```java
module com.loja {
    exports com.loja.api;
    opens com.loja.modelo;
    opens com.loja.config to com.fasterxml.jackson.databind;
}

open module com.app {
    requires java.sql;
}
```

- `opens pacote` abre para todos; `opens pacote to modulo` abre só para módulos específicos, como o framework que vai ler as entidades.
- `open module` abre **todos** os pacotes do módulo. Um `open module` não pode ter diretivas `opens`, porque elas seriam redundantes.

`exports` e `opens` são independentes:

| | Compilar contra os tipos `public` | Reflexão nos membros `public` | Reflexão profunda (`setAccessible` em privados) |
|---|---|---|---|
| Nem `exports` nem `opens` | Não | Não | Não |
| Só `exports` | Sim | Sim | Não |
| Só `opens` | Não | Sim | Sim |
| `exports` e `opens` | Sim | Sim | Sim |

Um pacote só aberto é o caso típico das entidades JPA: o código de fora não deve usá-las diretamente, mas o Hibernate precisa preencher seus campos privados.

```java executar
import java.lang.module.ModuleDescriptor;
import java.lang.module.ModuleDescriptor.Requires;
import java.util.Set;
import java.util.TreeSet;

public class Abrindo {
    public static void main(String[] args) {
        ModuleDescriptor aberto = ModuleDescriptor.newOpenModule("com.app").requires("java.sql").build();
        ModuleDescriptor loja = ModuleDescriptor.newModule("com.loja")
            .requires(Set.of(Requires.Modifier.STATIC), "com.relatorios")
            .exports("com.loja.api")
            .opens("com.loja.modelo")
            .opens(Set.of(), "com.loja.config", Set.of("com.fasterxml.jackson.databind"))
            .build();
        System.out.println(aberto.isOpen() + " " + aberto.opens() + " " + loja.isOpen());
        System.out.println(new TreeSet<>(loja.opens().stream().map(o -> o.source() + (o.isQualified() ? " to " + o.targets() : "")).toList()));
        System.out.println(loja.requires().stream().filter(r -> r.name().equals("com.relatorios")).findFirst().orElseThrow().modifiers());
        try {
            ModuleDescriptor.newOpenModule("x").opens("p");
        } catch (IllegalStateException e) {
            System.out.println("open module não declara opens");
        }
    }
}
```

```saida
true [] false
[com.loja.config to [com.fasterxml.jackson.databind], com.loja.modelo]
[STATIC]
open module não declara opens
```

## As válvulas da linha de comando

Quando não dá para mudar o `module-info` de um módulo, como os do JDK ou de uma biblioteca antiga, a linha de comando abre exceções na hora de compilar ou rodar:

| Opção | Faz |
|---|---|
| `--add-opens java.base/java.lang=ALL-UNNAMED` | Abre um pacote para reflexão profunda |
| `--add-exports java.base/sun.nio.ch=com.app` | Exporta um pacote não exportado |
| `--add-reads com.app=java.sql` | Faz um módulo ler outro |
| `--add-modules java.sql` | Inclui um módulo na resolução |

O formato é `modulo/pacote=destino`, e `ALL-UNNAMED` representa o classpath. São remendos: cada um desfaz parte do encapsulamento, e o certo é tirá-los quando a biblioteca for atualizada.

> [!PROVA]
> `requires transitive` repassa a legibilidade a quem requer o módulo. `requires static` é obrigatório na compilação e opcional na execução. `exports` permite compilar e refletir sobre membros `public`; `opens` permite reflexão profunda, inclusive em privados, mas não compilar. `open module` abre todos os pacotes e não aceita `opens`. Sem abertura, `setAccessible` lança `InaccessibleObjectException`.

## Por baixo dos panos

Cada `Module` em execução guarda, numa estrutura interna, para quais módulos cada pacote está exportado e para quais está aberto. Um `setAccessible` chama `checkCanSetAccessible`, que consulta essa tabela: se o membro é público num pacote exportado ao chamador, ou se o pacote está aberto a ele, a flag de acesso é ligada; senão, sai a `InaccessibleObjectException`. As opções `--add-opens` e `--add-exports` simplesmente acrescentam entradas nessa tabela antes de o programa começar.

A legibilidade implícita é resolvida uma vez, na configuração da camada: ao montar o grafo, a JVM acrescenta arestas de leitura extras seguindo os `requires transitive`. Por isso `canRead` responde na hora, sem percorrer cadeias. Há também os métodos `Module.addOpens`, `addExports` e `addReads`, que um módulo pode chamar sobre **si mesmo** em tempo de execução: abrir ou exportar um pacote seu para outro módulo, ou passar a ler um módulo que não declarou.

## Resumo para a prova

- `requires transitive m`: quem lê este módulo passa a ler `m`; use quando `m` aparece na API pública
- `requires static m`: necessário para compilar, opcional ao executar
- `opens pacote` e `opens pacote to modulo`: liberam reflexão profunda; `open module` abre tudo e não aceita `opens`
- `exports` serve para compilar; `opens`, para refletir sobre privados; os dois podem ser combinados
- Sem abertura: `setAccessible` lança `InaccessibleObjectException`; `trySetAccessible` devolve `false`
- Linha de comando: `--add-opens`, `--add-exports`, `--add-reads`, `--add-modules`, com `ALL-UNNAMED` para o classpath
