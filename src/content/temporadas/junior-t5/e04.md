No [episódio de casting](/assistir/junior-t3-e04), o padrão seguro era testar com `instanceof` e, na linha seguinte, repetir o tipo num cast. O **pattern matching** do Java 16 junta as duas coisas: `obj instanceof String s` testa o tipo e, se der certo, declara `s` já convertida. Parece um detalhe de sintaxe, mas traz regras novas de **escopo** que a prova explora bastante.

## Testar e converter de uma vez

```java executar
Object[] coisas = {"Java", 42, 3.5, 'x'};
for (Object o : coisas) {
    if (o instanceof String s) { //> Testa e declara s, já do tipo String.
        System.out.println("texto de " + s.length() + " letras");
    } else if (o instanceof Integer i) {
        System.out.println("inteiro, o dobro é " + i * 2);
    } else if (o instanceof Number n) { //> Integer já foi testado antes; aqui chegam os outros números.
        System.out.println("outro número: " + n.doubleValue());
    } else {
        System.out.println("outra coisa: " + o);
    }
}
```

```saida
texto de 4 letras
inteiro, o dobro é 84
outro número: 3.5
outra coisa: x
```

`String s` depois do `instanceof` é um **padrão de tipo** (*type pattern*), e `s` é a **variável de padrão**. Ela só recebe valor se o teste der verdadeiro, e por isso só existe onde o compilador tem certeza de que o teste deu verdadeiro.

## O escopo segue a lógica

> [!ANTES]
> Até o Java 15, o teste de tipo repetia o tipo três vezes: `if (o instanceof String) { String s = (String) o; ... }`. O padrão de tipo apareceu como prévia no Java 14, e ficou definitivo no Java 16 (JEP 394). Muito código e muita resposta de IA ainda usam a forma antiga, que continua válida.

O escopo da variável de padrão não é o bloco: é o conjunto de lugares em que o teste com certeza deu certo. No `if`, é o corpo. Com `&&`, também é o lado direito, que só é avaliado se o esquerdo for verdadeiro:

```java executar
Object o = "javaflix";
if (o instanceof String s && s.length() > 5) {
    System.out.println(s.toUpperCase());
}
```

```saida
JAVAFLIX
```

Com `||`, o lado direito roda justamente quando o teste **falhou**, e a variável não existe ali:

```java nao-compila
Object o = "a";
if (o instanceof String s || s.isEmpty()) {
    System.out.println("?");
}
```

![Três trechos com a variável de padrão s destacada: ela existe depois de um e lógico e depois de um if negado que sai com return, mas não depois de um ou lógico](/figuras/escopo-do-padrao.svg "A variável existe onde o teste certamente deu verdadeiro.")

> [!ERRO]
> Usar a variável depois de `||` dá `error: cannot find symbol`, com `symbol: variable s`. Parece que o compilador "esqueceu" a declaração, mas é o contrário: ele sabe que, no lado direito do `||`, o teste falhou e `s` não tem valor.

A forma negada inverte o raciocínio. Se o método sai quando o teste falha, a variável existe **depois** do `if`:

```java executar
Object x = 42;
if (!(x instanceof Integer i)) {
    return;
}
System.out.println(i + 1);
```

```saida
43
```

> [!PENSE]
> Se trocar o `return` por um `System.out.println("não é inteiro");`, sem sair do método, o `i + 1` depois do `if` ainda compila?

A variável de padrão não é `final` por padrão: pode ser reatribuída, a não ser que você escreva `instanceof final String s`. Ela também não pode ter o nome de outra variável local que esteja no escopo.

## Um `equals` em uma linha

O pattern matching deixa o `equals` do [episódio de herança](/assistir/junior-t3-e06) bem mais curto:

```java executar
final class Ponto {
    private final int x, y;

    Ponto(int x, int y) {
        this.x = x;
        this.y = y;
    }

    @Override
    public boolean equals(Object o) {
        return o instanceof Ponto p && x == p.x && y == p.y;
    }

    @Override
    public int hashCode() {
        return 31 * x + y;
    }
}

System.out.println(new Ponto(1, 2).equals(new Ponto(1, 2)) + " " + new Ponto(1, 2).equals("ponto") + " " + new Ponto(1, 2).equals(null));
```

```saida
true false false
```

O `instanceof` já devolve `false` para `null`, então a mesma linha trata os três casos.

> [!CONVERSA]
> **instanceof antigo:** Eu respondo sim ou não. Quem quiser o objeto convertido faz o cast na linha de baixo.
>
> **instanceof com padrão:** E se errar o tipo no cast, ou testar uma variável e converter outra? Eu faço as duas coisas juntas, sem chance de desencontro.
>
> **instanceof antigo:** E o custo disso?
>
> **instanceof com padrão:** Nenhum. No bytecode, sou exatamente você mais o cast. A diferença é só o compilador cuidando do escopo.

> [!LAPIS]
> Em quais linhas `s` pode ser usada?
>
> ```java
> if (o instanceof String s && s.length() > 2) { /* A */ }
> if (o instanceof String s) { } else { /* B */ }
> if (!(o instanceof String s)) { throw new IllegalArgumentException(); }
> /* C */
> ```
>
> **Resposta:** A e C. Em A, o `&&` garante o teste; em B, o `else` roda justamente quando ele falhou; em C, o `throw` faz o método sair quando o teste falha, então daí para baixo ele deu certo.

## Padrões que não podem falhar

No Java 17, o tipo do padrão precisa ser **mais específico** que o tipo da expressão. Testar uma `String` contra `String` seria um teste que nunca falha (só para `null`), e o compilador recusa:

```java nao-compila
String s = "abc";
if (s instanceof String t) {
    System.out.println(t.length());
}
```

> [!VERSAO]
> O Java 21 removeu essa restrição, junto com os record patterns (JEP 440), e o código acima compila. Na prova 1Z0-829, é erro de compilação; nas 1Z0-830 e 1Z0-831, compila e imprime 3. Já um teste que nunca pode dar certo, como `String instanceof Integer`, é erro em todas as versões.

```java compila java21
public class Incondicional {
    static int tamanho(String s) {
        if (s instanceof String t) {
            return t.length();
        }
        return -1;
    }
}
```

Com genéricos, o padrão só é aceito se o cast for seguro: `obj instanceof List<String> l` não compila quando `obj` é um `Object`, porque a JVM não tem como conferir o `<String>` em tempo de execução. O assunto volta na temporada de genéricos.

> [!PROVA]
> Para cada variável de padrão, pergunte: neste ponto, o teste com certeza deu verdadeiro? Dentro do `if`, depois de um `&&` e depois de um `if (!(...)) return;`, sim. Depois de um `||`, no `else` de um teste positivo e fora do `if` comum, não. E lembre que, no Java 17, o tipo do padrão precisa ser um subtipo estrito do tipo da expressão.

> [!MATEMATICA]
> A forma antiga escrevia o tipo 3 vezes (`instanceof String`, `String s`, `(String) o`); o padrão, 1. Num `equals` com 4 classes testadas, são 12 menções contra 4, e cada menção a mais é uma chance de testar um tipo e converter outro. O ganho de bytecode é zero: as mesmas 3 instruções (`instanceof`, `checkcast`, `astore`) nos dois casos.

> [!IA]
> A IA às vezes gera `if (o instanceof String s || s.isBlank())`, que não compila, ou mantém o cast antigo logo depois do padrão: `if (o instanceof String s) { String t = (String) o; ... }`. Peça a versão só com o padrão e confira o escopo: depois de `||` e no `else`, a variável não existe.

## Na IDE

- **Converter para padrão.** A inspeção "Pattern variable can be used" marca o par `instanceof` e cast; **Alt + Enter** faz a troca.
- **Ver o escopo.** Com o cursor na variável de padrão, **Ctrl + Shift + F7** destaca todos os usos dela; fora do escopo, ela aparece em vermelho.
- **Inverter o `if`.** **Alt + Enter** num `if` com padrão oferece *Invert 'if' condition*, que gera a forma negada com `return`.

## Por baixo dos panos

O pattern matching não tem custo nenhum: o `javac` gera exatamente o que você escreveria à mão, um `instanceof`, um `checkcast` e o armazenamento numa variável local. A novidade está toda no compilador, na análise de **atribuição definida** que você viu com variáveis locais: ele calcula, para cada ponto do código, se o teste "certamente deu verdadeiro" ou "certamente deu falso", e só deixa a variável ser usada no primeiro caso.

O `instanceof` com padrão foi o primeiro passo de um plano maior, anunciado por Brian Goetz em 2017: padrões em `switch`, padrões que desmontam records e, nas versões mais novas, padrões para tipos primitivos. O [próximo episódio](/assistir/junior-t5-e05) mostra os dois seguintes.

## Resumo para a prova

- `obj instanceof Tipo nome` testa e declara a variável já convertida
- A variável só existe onde o teste certamente deu verdadeiro
- Vale no corpo do `if` e no lado direito de `&&`; não vale depois de `||`
- `if (!(x instanceof T t)) return;` deixa `t` disponível depois do `if`
- A variável de padrão não é `final`, a não ser com `instanceof final T t`
- `null instanceof T t` é `false`, e `t` não recebe valor
- Java 17: o tipo do padrão precisa ser subtipo estrito da expressão; Java 21 aceita o mesmo tipo
- Padrões genéricos só compilam quando o cast é seguro
