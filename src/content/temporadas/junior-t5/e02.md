Um record sem validação aceita qualquer coisa: um e-mail sem arroba, uma faixa com o mínimo maior que o máximo, uma lista que muda depois. Para garantir que só existam records válidos, Java oferece três formas de construtor e permite sobrescrever os métodos gerados. A mais usada, e a mais cobrada, é o **construtor compacto**.

## O construtor compacto

Ele tem o nome do record, **sem parênteses e sem parâmetros**. Dentro dele, os nomes dos componentes se referem aos parâmetros recebidos, e as atribuições aos campos acontecem **sozinhas, no fim**. Serve para validar e normalizar:

```java executar
record Email(String endereco) {
    Email { //> Sem parênteses: é o construtor compacto.
        if (endereco == null || !endereco.contains("@")) {
            throw new IllegalArgumentException("e-mail inválido: " + endereco);
        }
        endereco = endereco.trim().toLowerCase(); //> Reatribui o parâmetro; o campo recebe este valor no fim.
    }
}

System.out.println(new Email("  Ana@Exemplo.COM ").endereco());
try {
    new Email("sem-arroba");
} catch (IllegalArgumentException e) {
    System.out.println(e.getMessage());
}
```

```saida
ana@exemplo.com
e-mail inválido: sem-arroba
```

Reatribuir o **parâmetro** `endereco` muda o valor que será guardado no campo. Atribuir ao **campo**, com `this.`, não compila: os campos são `final` e o compilador vai atribuí-los depois.

![O argumento passa pelo corpo do construtor compacto, que valida e normaliza o parâmetro, e só depois o javac atribui o campo final](/figuras/construtor-compacto.svg "Você mexe no parâmetro; a atribuição ao campo vem sozinha no fim.")

```java nao-compila
record Faixa(int min, int max) {
    Faixa {
        this.min = Math.min(min, max);
    }
}
```

> [!ERRO]
> A mensagem para `this.min = ...` no compacto é `error: cannot assign a value to final variable min`. Parece estranho, porque é um construtor, mas faz sentido: o compilador vai acrescentar a atribuição no fim, e um campo `final` não pode ser atribuído duas vezes. Troque `this.min = x` por `min = x`.

## O construtor canônico por extenso

Também dá para escrever o construtor canônico completo, com a lista de parâmetros. Nesse caso, ele precisa ter **exatamente os tipos e os nomes dos componentes**, e é responsável por atribuir **todos** os campos:

```java executar
record Faixa(int min, int max) {
    Faixa(int min, int max) {
        if (min > max) {
            int t = min;
            min = max;
            max = t;
        }
        this.min = min;
        this.max = max;
    }

    boolean contem(int v) {
        return v >= min && v <= max;
    }
}

Faixa f = new Faixa(10, 1);
System.out.println(f + " " + f.contem(5) + " " + f.contem(11));
```

```saida
Faixa[min=1, max=10] true false
```

```java nao-compila
record Faixa(int min, int max) {
    Faixa(int min, int max) {
        this.min = min;
    }
}
```

> [!PENSE]
> No compacto, as atribuições são automáticas. Por que no canônico por extenso o compilador exige que você atribua todos os campos?

Um record tem um construtor canônico só: ou o compacto, ou o por extenso, nunca os dois.

## Outros construtores

> [!CONVERSA]
> **Construtor compacto:** Eu sou para validar e normalizar. Não repito os parâmetros e não atribuo campos: o compilador faz isso por mim.
>
> **Construtor por extenso:** Eu repito tudo e atribuo cada campo à mão. Mais linhas, mas nada escondido.
>
> **Construtor compacto:** E quase sempre a mesma coisa que eu faço, com mais chance de esquecer um campo.
>
> **Construtor por extenso:** Por isso o mercado prefere você. Eu fico para quando alguém quer deixar a atribuição explícita.

Construtores com outras listas de parâmetros são permitidos, mas **precisam delegar** para outro construtor com `this(...)`, e a cadeia termina sempre no canônico. Assim, toda validação passa por um lugar só:

```java executar
record Moeda(String codigo, int casas) {
    Moeda(String codigo) {
        this(codigo, 2);
    }
}

System.out.println(new Moeda("BRL") + " " + new Moeda("JPY", 0));
```

```saida
Moeda[codigo=BRL, casas=2] Moeda[codigo=JPY, casas=0]
```

```java nao-compila
record Moeda(String codigo, int casas) {
    Moeda(String codigo) {
        this.codigo = codigo;
        this.casas = 2;
    }
}
```

## Cópia defensiva e métodos sobrescritos

O construtor compacto é o lugar natural da cópia defensiva que faltou no [episódio anterior](/assistir/junior-t5-e01). E qualquer método gerado pode ser sobrescrito, como o `toString`:

```java executar
record Turma(String nome, List<String> alunos) {
    Turma {
        alunos = List.copyOf(alunos);
    }

    @Override
    public String toString() {
        return nome + " (" + alunos.size() + " alunos)";
    }
}

List<String> lista = new ArrayList<>(List.of("Ana", "Bia"));
Turma t = new Turma("Java", lista);
lista.add("Caio");
System.out.println(t + " " + t.alunos());
try {
    t.alunos().add("Davi");
} catch (UnsupportedOperationException e) {
    System.out.println("lista imutável");
}
```

```saida
Java (2 alunos) [Ana, Bia]
lista imutável
```

> [!PERGUNTAS]
> **P:** Por que `List.copyOf` e não `new ArrayList<>(alunos)`?
>
> **R:** O `new ArrayList` copia, mas a cópia continua mutável: `t.alunos().add(...)` funcionaria. `List.copyOf` devolve uma lista imutável, e ainda recusa elementos `null`. Se a lista recebida já for imutável, ele nem copia.

Sobrescrever o `toString` também é uma boa prática de segurança: o padrão imprime todos os componentes, e uma senha num record vai parar no log sem ninguém perceber.

```java executar
record Senha(String valor) {
    @Override
    public String toString() {
        return "Senha[****]";
    }
}

Senha s = new Senha("1234");
System.out.println(s + " " + s.valor().length());
```

```saida
Senha[****] 4
```

Os acessores também podem ser sobrescritos, desde que continuem `public`, com o mesmo tipo de retorno e sem `throws`:

```java nao-compila
record Usuario(String login) {
    String login() {
        return login.toLowerCase();
    }
}
```

> [!PROVA]
> As regras dos construtores de record: o compacto não tem parênteses e não atribui `this.campo`; o canônico por extenso repete os nomes e tipos dos componentes e atribui todos os campos; nenhum dos dois pode ter `throws`; e qualquer outro construtor começa com `this(...)`. Acessores sobrescritos precisam ser `public`. E `equals`, `hashCode` e `toString` gerados leem os **campos**, não os acessores: sobrescrever um acessor não muda a comparação.

> [!ANTES]
> Antes dos records, validação em classe imutável era um construtor comum com `if` e atribuições, e era fácil esquecer de copiar uma lista. Com o Lombok, o `@Value` não tinha um lugar natural para validar, e o código ia para um construtor escrito à mão, que anulava parte do ganho. O construtor compacto veio com os records, no Java 16.

> [!MATEMATICA]
> O custo da cópia defensiva: `List.copyOf` com n elementos copia n referências, de 4 bytes cada. Para uma turma de 40 alunos, 160 bytes e algumas dezenas de nanossegundos, uma vez, na criação. Sem a cópia, o custo aparece depois, quando alguém altera a lista original e o record "imutável" muda junto: um bug que pode levar horas para achar.

> [!IA]
> Ao escrever a validação de um record, a IA às vezes gera o construtor compacto com `this.campo = ...`, que não compila, ou cria a cópia defensiva numa variável nova (`var copia = List.copyOf(alunos);`) sem reatribuir o parâmetro, e a cópia se perde. Confira que o compacto só reatribui os parâmetros pelo nome.

## Na IDE

- **Gerar o compacto.** Com o cursor no record, **Alt + Insert**, *Compact Constructor*, cria o bloco vazio pronto para a validação.
- **Converter.** **Alt + Enter** num construtor canônico por extenso oferece *Convert canonical constructor to compact form*, e o caminho inverso também.
- **Ver as atribuições escondidas.** No depurador, um ponto de parada na última linha do compacto mostra os parâmetros com os valores que irão para os campos.

## Por baixo dos panos

O construtor compacto não existe no bytecode. O `javac` o transforma no construtor canônico comum, com os parâmetros declarados e, **depois** do seu código, uma atribuição `this.campo = campo;` para cada componente. É por isso que reatribuir o parâmetro funciona: a atribuição gerada usa o valor que o parâmetro tiver no fim.

Já os métodos `equals`, `hashCode` e `toString` gerados recebem, no `invokedynamic`, uma referência direta a cada **campo**, não aos acessores. Se você sobrescrever `valor()` para devolver o texto em maiúsculas, `equals` continua comparando o texto original. Na prática, sobrescrever acessores para mudar o valor costuma confundir; o lugar de normalizar é o construtor compacto.

## Resumo para a prova

- Compacto: `Nome { ... }`, sem parâmetros; os campos são atribuídos sozinhos no fim
- No compacto, reatribuir o parâmetro muda o valor guardado; `this.campo = ...` não compila
- Canônico por extenso: mesmos nomes e tipos dos componentes, atribuindo todos os campos
- Só um canônico por record: compacto ou por extenso
- Outros construtores precisam começar com `this(...)`
- Cópias defensivas e validações vão no construtor compacto
- Acessores sobrescritos precisam ser `public`; `equals` e `toString` gerados usam os campos
