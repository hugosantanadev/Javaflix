O Java 21 levou os padrões para o `switch`. Em vez de comparar um valor com constantes, cada `case` pode testar um **tipo**, aplicar uma **condição** e até **desmontar um record** nos seus componentes. Combinado com as hierarquias seladas do [episódio 3](/assistir/junior-t5-e03), o resultado é um `switch` que o compilador garante cobrir todos os casos possíveis. Este episódio cai nas provas 1Z0-830 e 1Z0-831.

## Padrões de tipo e guardas

```java executar
public class Descritor {
    static String descrever(Object o) {
        return switch (o) {
            case null -> "nada";
            case Integer i when i < 0 -> "inteiro negativo";
            case Integer i -> "inteiro " + i;
            case String s when s.isBlank() -> "texto vazio";
            case String s -> "texto: " + s;
            default -> "outro: " + o.getClass().getSimpleName();
        };
    }

    public static void main(String[] args) {
        Object[] valores = {7, -3, "oi", " ", null, 2.5};
        for (Object v : valores) {
            System.out.println(descrever(v));
        }
    }
}
```

```saida
inteiro 7
inteiro negativo
texto: oi
texto vazio
nada
outro: Double
```

Cada `case Tipo nome` funciona como o `instanceof` com padrão do [episódio anterior](/assistir/junior-t5-e04). A palavra **`when`** acrescenta uma **guarda**: uma condição que precisa ser verdadeira, além do tipo, para o `case` ser escolhido. Os `case` são testados de cima para baixo, e o primeiro que casa vence.

## `null`, dominância e exaustividade

Um `switch` sobre um objeto que recebe `null` lança `NullPointerException`, a não ser que tenha um **`case null`**. O `default` **não** pega o `null`; para tratar os dois juntos, existe a forma `case null, default ->`.

```java executar
public class SemNull {
    static String f(Object o) {
        return switch (o) {
            case String s -> "texto";
            default -> "outro";
        };
    }

    public static void main(String[] args) {
        try {
            f(null);
        } catch (NullPointerException e) {
            System.out.println("NullPointerException");
        }
        System.out.println(f(1));
    }
}
```

```saida
NullPointerException
outro
```

Como a ordem importa, um `case` mais geral antes de um mais específico tornaria o segundo inalcançável. O compilador chama isso de **dominância** e recusa:

```java nao-compila
public class Dominancia {
    static String f(Object o) {
        return switch (o) {
            case CharSequence cs -> "sequência";
            case String s -> "texto";
            default -> "outro";
        };
    }
}
```

Um `case` com guarda não domina o mesmo tipo sem guarda, porque pode falhar na condição; por isso `case Integer i when i < 0` vem antes de `case Integer i`, e não o contrário.

E todo `switch` com padrões precisa ser **exaustivo**: cobrir todos os valores possíveis do tipo, com `default` ou com `case` suficientes. Isso vale até para o `switch` comando, não só para o expressão:

```java nao-compila
public class Incompleto {
    static String f(Object o) {
        return switch (o) {
            case String s -> "texto";
            case Integer i -> "inteiro";
        };
    }
}
```

## Hierarquias seladas e record patterns

Com uma interface selada, o compilador conhece todos os subtipos, e um `case` para cada um já é exaustivo, **sem `default`**. E um **record pattern** desmonta o record ali mesmo, declarando uma variável para cada componente, com o tipo exato ou com `var`:

```java executar
sealed interface Forma permits Circulo, Retangulo, Triangulo { }
record Circulo(double raio) implements Forma { }
record Retangulo(double largura, double altura) implements Forma { }
record Triangulo(double base, double altura) implements Forma { }

public class Areas {
    static double area(Forma f) {
        return switch (f) {
            case Circulo(double r) -> Math.round(Math.PI * r * r * 100) / 100.0;
            case Retangulo(double l, double a) -> l * a;
            case Triangulo(var b, var a) -> b * a / 2;
        };
    }

    public static void main(String[] args) {
        Forma[] formas = {new Circulo(1), new Retangulo(2, 3), new Triangulo(4, 5)};
        for (Forma f : formas) {
            System.out.println(f + " -> " + area(f));
        }
    }
}
```

```saida
Circulo[raio=1.0] -> 3.14
Retangulo[largura=2.0, altura=3.0] -> 6.0
Triangulo[base=4.0, altura=5.0] -> 10.0
```

Se alguém acrescentar um `Losango` ao `permits`, este `switch` deixa de compilar até ganhar um `case` novo: é exatamente a garantia que se quer. Record patterns também funcionam no `instanceof` e podem ser **aninhados**:

```java executar
record Ponto(int x, int y) { }
record Linha(Ponto inicio, Ponto fim) { }

Object o = new Linha(new Ponto(0, 0), new Ponto(3, 4));
if (o instanceof Linha(Ponto(var x1, var y1), Ponto(int x2, int y2))) {
    int dx = x2 - x1, dy = y2 - y1;
    System.out.println("comprimento " + Math.sqrt(dx * dx + dy * dy));
}
```

```saida
comprimento 5.0
```

> [!VERSAO]
> O Java 22 trouxe os **padrões sem nome** (JEP 456): um `_` no lugar de um componente que não interessa, como em `case Ponto(int x, _)`. Eles fazem parte da prova 1Z0-831, mas não da 830, que é do Java 21.

```java executar java25
record Ponto(int x, int y) { }

Object o = new Ponto(5, 9);
String r = switch (o) {
    case Ponto(int x, _) when x > 0 -> "à direita";
    case Ponto(_, _) -> "à esquerda ou no eixo";
    default -> "não é ponto";
};
System.out.println(r);
```

```saida
à direita
```

> [!PROVA]
> Para um `switch` com padrões: os `case` vêm em ordem do mais específico ao mais geral, senão há dominância; o `switch` precisa ser exaustivo, com `default` ou cobrindo uma hierarquia selada; `null` só é tratado com `case null`, senão lança `NullPointerException`; e a guarda é escrita com `when`, nunca com `&&` ou `if`. Num record pattern, o número e a ordem dos componentes precisam bater com o record.

## Por baixo dos panos

O `switch` com padrões não vira uma sequência de `if`. O `javac` gera uma instrução `invokedynamic` que chama `SwitchBootstraps.typeSwitch`, passando a lista de tipos dos `case`. Na execução, esse método devolve o índice do primeiro `case` que casa, e um `switch` comum sobre esse índice pula para o código certo. A estratégia permite à JVM otimizar a busca sem mudar o bytecode compilado.

E a exaustividade vale também na execução. Se uma biblioteca acrescentar um subtipo à hierarquia selada e o seu código não for recompilado, o `switch` recebe um objeto que nenhum `case` cobre. Nesse caso, a JVM lança `MatchException`, um erro novo do Java 21, em vez de seguir em silêncio.

## Resumo para a prova

- `case Tipo nome ->` testa o tipo e declara a variável, como o `instanceof` com padrão
- `when` acrescenta uma guarda ao `case`
- Os `case` são testados em ordem; um mais geral antes de um mais específico não compila
- Todo `switch` com padrões precisa ser exaustivo; hierarquias seladas dispensam `default`
- Sem `case null`, `null` lança `NullPointerException`; `default` não pega `null`
- `case null, default ->` trata os dois juntos
- Record patterns desmontam records: `case Ponto(int x, var y)`, inclusive aninhados
- `_` como padrão sem nome é do Java 22 em diante (prova 1Z0-831)
