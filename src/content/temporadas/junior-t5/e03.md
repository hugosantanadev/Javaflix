Até aqui, uma classe tinha duas opções: aberta, e qualquer um pode estendê-la, ou `final`, e ninguém pode. Mas muitos domínios têm um meio-termo: um pagamento é Pix, cartão ou dinheiro, e **só isso**. Uma forma geométrica do seu sistema é um círculo, um quadrado ou um triângulo. As **classes e interfaces seladas** (*sealed*), do Java 17, declaram exatamente quem pode estendê-las, e o compilador garante que ninguém mais entre na hierarquia.

## `sealed` e `permits`

Uma classe `sealed` lista as subclasses permitidas na cláusula `permits`. Cada subclasse permitida precisa dizer como continua a hierarquia, com **um** destes modificadores:

| Modificador | Significa |
|---|---|
| `final` | ninguém estende esta subclasse |
| `sealed` | ela também é selada, com o seu próprio `permits` |
| `non-sealed` | ela reabre a hierarquia: qualquer um pode estendê-la |

```java executar
sealed abstract class Forma permits Circulo, Quadrado, Triangulo { }

final class Circulo extends Forma {
    final double raio;
    Circulo(double raio) { this.raio = raio; }
}

final class Quadrado extends Forma {
    final double lado;
    Quadrado(double lado) { this.lado = lado; }
}

non-sealed class Triangulo extends Forma { }

class TrianguloRetangulo extends Triangulo { }

public class Formas {
    public static void main(String[] args) {
        Forma[] formas = {new Circulo(1), new Quadrado(2), new TrianguloRetangulo()};
        for (Forma f : formas) {
            System.out.println(f.getClass().getSimpleName() + " " + (f instanceof Triangulo));
        }
        System.out.println(Forma.class.isSealed() + " " + Forma.class.getPermittedSubclasses().length);
    }
}
```

```saida
Circulo false
Quadrado false
TrianguloRetangulo true
true 3
```

`TrianguloRetangulo` não está no `permits`, mas estende `Triangulo`, que é `non-sealed`. A selagem vale para os filhos **diretos**.

## O que o compilador confere

Uma subclasse permitida sem nenhum dos três modificadores não compila:

```java nao-compila
sealed class Veiculo permits Carro { }

class Carro extends Veiculo { }
```

Uma classe fora do `permits` não pode estender a selada:

```java nao-compila
sealed class Veiculo permits Carro { }

final class Carro extends Veiculo { }

final class Moto extends Veiculo { }
```

E toda classe listada no `permits` precisa, de fato, estendê-la diretamente. As subclasses permitidas precisam estar no mesmo pacote da classe selada (ou no mesmo módulo, quando há módulos). Se estiverem todas **no mesmo arquivo**, o `permits` pode ser omitido: o compilador considera permitidas as subclasses que encontrar ali.

## Interfaces seladas, records e enums

Interfaces também podem ser seladas, e combinam muito bem com **records** e **enums**, que já são implicitamente `final` e por isso não precisam de modificador:

```java executar
sealed interface Pagamento { }

record Pix(String chave) implements Pagamento { }

record Cartao(String numero, int parcelas) implements Pagamento { }

final class Dinheiro implements Pagamento { }

public class Caixa {
    static String descrever(Pagamento p) {
        if (p instanceof Pix pix) return "Pix para " + pix.chave();
        if (p instanceof Cartao c) return "Cartão em " + c.parcelas() + "x";
        return "Dinheiro";
    }

    public static void main(String[] args) {
        Pagamento[] ps = {new Pix("ana@x.com"), new Cartao("4111", 3), new Dinheiro()};
        for (Pagamento p : ps) {
            System.out.println(descrever(p));
        }
        System.out.println(Pagamento.class.getPermittedSubclasses().length);
    }
}
```

```saida
Pix para ana@x.com
Cartão em 3x
Dinheiro
3
```

Aqui o `permits` foi omitido, porque todos os tipos estão no mesmo arquivo. A combinação de interface selada com records é o que a documentação chama de **tipos de dados algébricos**: um conjunto fechado de formas, cada uma com os seus dados. O teste com `instanceof Pix pix` é o pattern matching do [próximo episódio](/assistir/junior-t5-e04), e, no Java 21, um `switch` sobre uma interface selada pode cobrir todos os casos sem `default`, como você verá no [episódio 5](/assistir/junior-t5-e05).

> [!PROVA]
> Diante de uma hierarquia selada, confira: cada subclasse direta está no `permits` (ou no mesmo arquivo, se ele foi omitido)? Cada uma é `final`, `sealed` ou `non-sealed` (ou é um record ou enum)? Cada classe do `permits` estende de fato a selada? Uma interface que estende uma interface selada precisa ser `sealed` ou `non-sealed`, porque interfaces não podem ser `final`.

## Por baixo dos panos

A classe selada ganha, no arquivo `.class`, um atributo `PermittedSubclasses`, com a lista das subclasses autorizadas. A conferência não é só do compilador: quando a JVM carrega uma classe que declara estender uma classe selada, ela consulta esse atributo, e se a nova classe não estiver na lista, a carga falha com `IncompatibleClassChangeError`. Assim, nem um bytecode gerado por outra ferramenta consegue furar a hierarquia.

Selar uma hierarquia é uma decisão de projeto: você troca a extensibilidade por uma garantia, a de conhecer todos os casos. Isso permite ao compilador verificar que um código trata todos eles, algo que, até o Java 17, só existia para enums. É o mesmo raciocínio de linguagens funcionais como Haskell e Scala, que o Java incorporou aos poucos com records, sealed e pattern matching.

## Resumo para a prova

- `sealed class X permits A, B` restringe quem pode estender `X`
- Cada subclasse direta precisa ser `final`, `sealed` ou `non-sealed`
- Records e enums são implicitamente `final` e servem sem modificador extra
- Classe fora do `permits` não pode estender a selada
- Toda classe do `permits` precisa estender diretamente a selada
- Subclasses no mesmo pacote (ou módulo); no mesmo arquivo, o `permits` pode ser omitido
- `non-sealed` reabre a hierarquia a partir daquela subclasse
- Interfaces também podem ser seladas; subinterfaces são `sealed` ou `non-sealed`
