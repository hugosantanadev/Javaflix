Uma classe imutável bem feita, como a do [episódio de imutabilidade](/assistir/junior-t2-e04), exige campos `private final`, construtor, getters, `equals`, `hashCode` e `toString`: dezenas de linhas para dizer "um ponto tem x e y". O **record**, do Java 16, diz exatamente isso numa linha. Ele é uma classe feita para carregar dados, e o compilador escreve todo o resto.

## Uma linha, uma classe completa

```java executar
record Ponto(int x, int y) { }

Ponto a = new Ponto(1, 2);
Ponto b = new Ponto(1, 2);
System.out.println(a);
System.out.println(a.x() + a.y());
System.out.println((a == b) + " " + a.equals(b) + " " + (a.hashCode() == b.hashCode()));
```

```saida
Ponto[x=1, y=2]
3
false true true
```

Os nomes entre parênteses são os **componentes** do record. Para cada um, o compilador gera:

| Gerado | Para `record Ponto(int x, int y)` |
|---|---|
| Campo `private final` | `x` e `y` |
| Construtor canônico | `Ponto(int x, int y)`, com os parâmetros na ordem dos componentes |
| Método de acesso | `x()` e `y()`, sem o prefixo `get` |
| `equals` e `hashCode` | baseados em todos os componentes |
| `toString` | `Ponto[x=1, y=2]` |

O acessor tem **o nome do componente**. Não existe `getX()`, a não ser que você o escreva:

```java nao-compila
record Produto(String nome, double preco) { }

Produto p = new Produto("Caneta", 2.5);
System.out.println(p.getNome());
```

E como os campos são `final`, nenhum método pode alterá-los:

```java nao-compila
record Produto(String nome, double preco) {
    void reajustar(double pct) {
        preco = preco * (1 + pct);
    }
}
```

## O que um record aceita

Um record pode ter métodos, campos e métodos `static`, tipos aninhados e implementar interfaces:

```java executar
interface Forma {
    double area();
}

record Retangulo(double largura, double altura) implements Forma {
    static final Retangulo UNITARIO = new Retangulo(1, 1);

    public double area() {
        return largura * altura;
    }

    Retangulo dobrar() {
        return new Retangulo(largura * 2, altura * 2);
    }

    static Retangulo quadrado(double lado) {
        return new Retangulo(lado, lado);
    }
}

Forma f = Retangulo.quadrado(3).dobrar();
System.out.println(f + " " + f.area() + " " + Retangulo.UNITARIO.area());
```

```saida
Retangulo[largura=6.0, altura=6.0] 36.0 1.0
```

O que ele não aceita: **campos de instância** além dos componentes (o estado é só o que está no cabeçalho) e **herança** (todo record já estende `java.lang.Record` e é implicitamente `final`):

```java nao-compila
record Conta(String titular) {
    private double saldo;
}
```

```java nao-compila
class Base { }

record Filho(int x) extends Base { }
```

## Imutável, mas raso

Os campos do record são `final`, mas, como você viu nas cópias defensivas, `final` protege a referência, não o objeto apontado. Um componente `List` continua sendo uma lista mutável:

```java executar
record Turma(String nome, List<String> alunos) { }

List<String> lista = new ArrayList<>(List.of("Ana"));
Turma t = new Turma("Java", lista);
lista.add("Bia");
t.alunos().add("Caio");
System.out.println(t);
```

```saida
Turma[nome=Java, alunos=[Ana, Bia, Caio]]
```

A correção é a mesma de sempre, uma cópia defensiva, e o lugar certo para ela é o **construtor compacto**, assunto do [próximo episódio](/assistir/junior-t5-e02).

Com `equals` e `hashCode` prontos e coerentes, records são ótimas chaves de `HashMap` e elementos de `HashSet`:

```java executar
record Coordenada(int linha, int coluna) { }

Map<Coordenada, String> tabuleiro = new HashMap<>();
tabuleiro.put(new Coordenada(0, 0), "X");
tabuleiro.put(new Coordenada(1, 1), "O");
System.out.println(tabuleiro.get(new Coordenada(1, 1)) + " " + tabuleiro.containsKey(new Coordenada(2, 2)));
```

```saida
O false
```

> [!PROVA]
> Nas questões de records: os acessores são `nome()`, não `getNome()`; não há setters nem campos de instância extras; um record não estende nada nem pode ser estendido; o `toString` tem o formato `Nome[a=1, b=2]`; e o `equals` compara componente a componente, com `equals` para objetos. Arrays, que não sobrescrevem `equals`, são comparados por referência.

## Por baixo dos panos

O `javap -p Ponto.class` mostra uma classe comum: `final class Ponto extends java.lang.Record`, com os dois campos `private final`, o construtor e os acessores. A surpresa está em `equals`, `hashCode` e `toString`: o corpo deles é uma única instrução `invokedynamic`, que chama o método `ObjectMethods.bootstrap` na primeira execução. A implementação é montada em tempo de execução, a partir da lista de componentes, e não escrita pelo compilador. Assim, melhorias no JDK chegam a records compilados há anos.

O arquivo `.class` também ganha um atributo `Record`, que lista os componentes. É ele que a reflexão lê:

```java executar
record Ponto(int x, int y) { }

System.out.println(Ponto.class.isRecord() + " " + Ponto.class.getSuperclass().getSimpleName() + " " + java.lang.reflect.Modifier.isFinal(Ponto.class.getModifiers()));
for (var c : Ponto.class.getRecordComponents()) {
    System.out.print(c.getName() + ":" + c.getType() + " ");
}
System.out.println();
```

```saida
true Record true
x:int y:int
```

Bibliotecas de serialização, como o Jackson, usam essa informação para converter records em JSON sem anotação nenhuma. E a desserialização de um record sempre passa pelo construtor canônico, o que garante que as validações dele rodem.

## Resumo para a prova

- `record Nome(componentes) { }` gera campos `private final`, construtor canônico, acessores, `equals`, `hashCode` e `toString`
- Acessores têm o nome do componente: `x()`, não `getX()`
- Records são `final`, estendem `java.lang.Record` e não estendem outra classe
- Podem ter métodos, membros `static` e implementar interfaces
- Não podem ter campos de instância além dos componentes
- `toString` no formato `Ponto[x=1, y=2]`; `equals` compara todos os componentes
- A imutabilidade é rasa: componentes mutáveis precisam de cópia defensiva
