Quando uma lambda só repassa os argumentos para um método que já existe, como `s -> s.length()` ou `x -> System.out.println(x)`, dá para escrever só o nome do método: `String::length`, `System.out::println`. Essas são as **referências a métodos**. Elas deixam o código mais curto e, às vezes, mais claro, mas a prova cobra as quatro formas, o que cada uma vira e alguns comportamentos que diferem das lambdas.

> [!ANTES]
> Antes do Java 8, passar "um método" como argumento exigia uma classe anônima ou reflexão, como `Method m = String.class.getMethod("length"); m.invoke(texto);`: lento, sem verificação de tipo pelo compilador e cheio de exceções checked. As referências a métodos, do Java 8, são conferidas na compilação e chamam o método direto.

## As quatro formas

| Forma | Exemplo | Lambda equivalente |
|---|---|---|
| Método estático | `Integer::parseInt` | `s -> Integer.parseInt(s)` |
| Método de instância de um objeto específico | `texto::length` | `() -> texto.length()` |
| Método de instância de um objeto qualquer do tipo | `String::length` | `s -> s.length()` |
| Construtor | `ArrayList::new` | `() -> new ArrayList<>()` |

A terceira forma é a que mais confunde. Em `String::length`, não há objeto à esquerda, só o tipo: o objeto chega como **primeiro argumento** da função. Por isso `String::length` serve a uma `Function<String, Integer>`, e `String::startsWith` serve a uma `BiFunction<String, String, Boolean>`, em que o primeiro `String` é o objeto e o segundo, o argumento.

![Quatro linhas comparando referência e lambda: Integer::parseInt com s para Integer.parseInt de s; texto::length com a lambda sem parâmetros; String::startsWith com a e b, em que a vira o objeto; e ArrayList::new com new ArrayList](/figuras/quatro-formas-de-referencia.svg "Em Tipo::metodoDeInstancia, o primeiro parâmetro da interface é quem recebe a chamada.")

```java executar
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;
import java.util.function.BiFunction;
import java.util.function.Function;
import java.util.function.IntFunction;
import java.util.function.Supplier;

public class Formas {
    static String grito(String s) {
        return s.toUpperCase() + "!";
    }

    public static void main(String[] args) {
        Function<String, Integer> converter = Integer::parseInt;
        Function<String, String> gritar = Formas::grito;
        System.out.println(converter.apply("42") + 1 + " " + gritar.apply("oi"));

        String texto = "abc";
        Supplier<Integer> tamanhoDoTexto = texto::length;
        Function<String, Integer> tamanhoDeQualquer = String::length;
        BiFunction<String, String, Boolean> comeca = String::startsWith; //> O 1º String é o objeto; o 2º, o argumento.
        System.out.println(tamanhoDoTexto.get() + " " + tamanhoDeQualquer.apply("java") + " " + comeca.apply("javaflix", "java"));

        Comparator<String> semCaixa = String::compareToIgnoreCase;
        List<String> letras = new ArrayList<>(List.of("b", "A", "c"));
        letras.sort(semCaixa);

        Supplier<List<String>> nova = ArrayList::new;
        Function<String, StringBuilder> construtor = StringBuilder::new;
        IntFunction<int[]> criarArray = int[]::new;
        System.out.println(letras + " " + nova.get() + " " + construtor.apply("x").append("y") + " " + criarArray.apply(3).length);
    }
}
```

```saida
43 OI!
3 4 true
[A, b, c] [] xy 3
```

`String::compareToIgnoreCase` vira um `Comparator<String>` porque `compare(a, b)` vira `a.compareToIgnoreCase(b)`. E a mesma escrita `ArrayList::new` serve a um `Supplier` ou a uma `Function<Integer, List<String>>`, que chama o construtor com a capacidade: o tipo-alvo escolhe qual construtor.

> [!LAPIS]
> Traduza cada referência para a lambda equivalente: (a) `Math::max`, como `BinaryOperator<Integer>`; (b) `System.out::println`, como `Consumer<String>`; (c) `String::concat`, como `BinaryOperator<String>`; (d) `HashMap::new`, como `Supplier<Map<String, Integer>>`.
>
> **Resposta:** (a) `(a, b) -> Math.max(a, b)`. (b) `s -> System.out.println(s)`. (c) `(a, b) -> a.concat(b)`: o primeiro parâmetro é o objeto. (d) `() -> new HashMap<>()`.

## A referência escolhe o método pelo alvo

Como as lambdas, uma referência não tem tipo próprio: o compilador procura um método compatível com a interface do alvo. Quando acha mais de um, ou nenhum, não compila:

```java nao-compila
import java.util.function.Function;

public class Ambigua {
    public static void main(String[] args) {
        Function<Integer, String> f = Integer::toString;
    }
}
```

`Integer::toString` poderia ser o estático `Integer.toString(int)`, com o `Integer` como argumento, ou o de instância `toString()`, com o `Integer` como objeto. As duas leituras servem, e o compilador recusa. Outros erros comuns: referenciar um método de instância como se fosse estático (`Classe::metodoDeInstancia` num `Supplier`), e escrever parênteses, como `String::length()`.

> [!ERRO]
> Referenciar um método de instância sem objeto, num alvo que não tem de onde tirá-lo: `Supplier<String> s = Pedido::resumo;`, com `resumo()` de instância. O `javac` recusa com `incompatible types: invalid method reference`. Ou passe o objeto, `pedido::resumo`, ou mude o alvo para receber o pedido, `Function<Pedido, String>`.

## Quando o objeto é avaliado

Numa referência com objeto específico, como `texto::length`, a expressão à esquerda é avaliada **uma vez, na criação** da referência. Isso tem três consequências:

```java executar
import java.util.function.Supplier;

public class Avaliacao {
    String prefixo = "> ";

    String marcar(String s) {
        return prefixo + s;
    }

    public static void main(String[] args) {
        String texto = "abc";
        Supplier<Integer> tamanho = texto::length; //> Guarda o objeto "abc" agora.
        texto = "mudou bastante";
        System.out.println(tamanho.get());

        Avaliacao a = new Avaliacao();
        java.util.function.Function<String, String> marca = a::marcar;
        a.prefixo = "# ";
        System.out.println(marca.apply("item"));

        String nulo = null;
        Supplier<Integer> lambda = () -> nulo.length();
        System.out.println("a lambda foi criada");
        try {
            Supplier<Integer> referencia = nulo::length;
            System.out.println("a referência foi criada");
        } catch (NullPointerException e) {
            System.out.println("NullPointerException ao criar a referência");
        }
    }
}
```

```saida
3
# item
a lambda foi criada
NullPointerException ao criar a referência
```

> [!PENSE]
> A variável `texto` mudou depois da criação da referência, mas o resultado continuou 3. E com um objeto `null`, a referência falhou já ao ser criada, enquanto a lambda só falharia ao ser chamada. O que isso diz sobre o momento em que o objeto à esquerda do `::` é lido?

1. A referência guardou o objeto `"abc"`. Reatribuir a variável depois não muda nada, e por isso, ao contrário de uma lambda, a referência **não exige** variável efetivamente final.
2. O que fica guardado é o **objeto**, não uma cópia do estado: alterar um campo dele aparece na chamada.
3. Com um objeto `null`, a referência lança `NullPointerException` já na criação. A lambda equivalente só falharia ao ser chamada.

> [!PERGUNTAS]
> **P:** Referência ou lambda: qual é mais rápida?
>
> **R:** Na prática, iguais. A escolha é de legibilidade, e de comportamento nos três pontos acima.
>
> **P:** Dá para referenciar um método com dois argumentos?
>
> **R:** Dá, se a interface tiver os parâmetros certos: `BiFunction<String, Integer, Character> letra = String::charAt;`, com a `String` como objeto e o `Integer` como argumento.
>
> **P:** Por que escrever `this::nome`, e não só `nome`?
>
> **R:** Sem o `::`, o compilador procuraria uma variável chamada `nome`. O `::` transforma o método num valor que pode ser passado adiante.

> [!MATEMATICA]
> A conta que decide se uma referência encaixa: parâmetros da interface = objeto + argumentos do método. Numa `BiFunction`, que tem 2, `String::startsWith` usa 1 + 1, o objeto e um argumento; `Math::max` usa 0 + 2, porque é estático. Já `String::length` numa `BiFunction` daria 1 + 0 = 1, e sobra um parâmetro: não compila.

## this:: e super::

Dentro de uma classe, `this::metodo` referencia um método do próprio objeto, e `super::metodo` referencia a versão da superclasse, ignorando a sobrescrita:

```java executar
import java.util.function.Supplier;

public class Heranca {
    static class Base {
        String nome() {
            return "base";
        }
    }

    static class Filha extends Base {
        @Override
        String nome() {
            return "filha";
        }

        Supplier<String> daBase() {
            return super::nome; //> A versão da superclasse.
        }

        Supplier<String> deMim() {
            return this::nome;
        }
    }

    public static void main(String[] args) {
        Filha f = new Filha();
        System.out.println(f.daBase().get() + " " + f.deMim().get());
    }
}
```

```saida
base filha
```

> [!PROVA]
> Para traduzir uma referência, conte os parâmetros da interface. Em `Tipo::metodoDeInstancia`, o primeiro parâmetro é o objeto, e os demais viram argumentos; em `objeto::metodo` e `Tipo::metodoEstatico`, todos os parâmetros viram argumentos. E nunca há parênteses depois do nome.

> [!IA]
> Assistentes de IA trocam lambdas por referências "para simplificar" sem perceber que mudam o momento em que o objeto é lido, e escrevem referências ambíguas, como `Integer::toString`. Quando a IA propuser uma referência no lugar de uma lambda, pergunte se o objeto à esquerda do `::` pode mudar ou ser `null` antes da chamada.

## Na IDE

- **Lambda para referência.** Quando a lambda só repassa os argumentos, o IntelliJ oferece, com `Alt+Enter`, *Replace lambda with method reference*; o caminho inverso também existe.
- **Qual método foi escolhido.** `Ctrl+B` sobre o nome depois do `::` leva ao método que o compilador escolheu, útil quando há sobrecargas.
- **A interface da referência.** `Ctrl+Shift+P` sobre a referência mostra a interface funcional que ela implementa ali.

## Por baixo dos panos

Uma referência a método não gera o método sintético `lambda$...` que vimos no [episódio 1](/assistir/pleno-t5-e01): o `invokedynamic` aponta direto para o método referenciado, por um *method handle*. Quando há um objeto à esquerda, ele é avaliado e passa por `Objects.requireNonNull` antes do `invokedynamic`, e é daí que vem a `NullPointerException` imediata.

Joshua Bloch recomenda preferir referências quando elas são mais curtas e claras, e lambdas quando o nome do parâmetro ajuda a entender. `x -> x` é mais legível que `Function.identity()` para muita gente; `service::processar` costuma ser mais claro que `pedido -> service.processar(pedido)`. A escolha é de estilo: o comportamento só difere nos três pontos acima.

## Resumo para a prova

- Quatro formas: `Classe::estatico`, `objeto::metodo`, `Tipo::metodoDeInstancia`, `Classe::new`
- Em `Tipo::metodoDeInstancia`, o primeiro parâmetro da interface é o objeto
- `ArrayList::new` e `int[]::new` são referências a construtores; o alvo escolhe qual
- `Integer::toString` numa `Function<Integer, String>` é ambígua e não compila
- O objeto de `objeto::metodo` é avaliado na criação: não precisa ser efetivamente final, e `null` lança exceção na hora
- `super::metodo` chama a versão da superclasse
