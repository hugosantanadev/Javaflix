A [temporada de interfaces](/assistir/junior-t4-e02) apresentou as lambdas: código que vira objeto, implementando o único método abstrato de uma interface funcional. Esta temporada as leva ao nível da prova, que cobra cada detalhe da sintaxe, as regras de tipo e os casos em que o compilador não consegue decidir. Começamos pela gramática completa.

## As formas de uma lambda

Uma lambda tem uma lista de parâmetros, a seta `->` e um corpo. Cada parte tem variações:

| Parâmetros | Exemplo |
|---|---|
| Nenhum | `() -> 42` |
| Um, sem tipo | `x -> x * 2` ou `(x) -> x * 2` |
| Vários, sem tipo | `(a, b) -> a + b` |
| Com tipo explícito | `(Integer a, Integer b) -> a + b` |
| Com `var` (Java 11) | `(var a, var b) -> a + b` |
| Com modificador | `(final var a, final var b) -> a + b` |

As regras: parênteses são obrigatórios com zero ou mais de um parâmetro, e com qualquer tipo declarado; e os parâmetros seguem **um único estilo**, todos sem tipo, todos com tipo ou todos com `var`. `(Integer a, b)` e `(var a, Integer b)` não compilam. O `var` existe para permitir anotações e `final` sem escrever o tipo inteiro.

O corpo pode ser uma **expressão**, cujo valor é o retorno, ou um **bloco** entre chaves, que segue as regras de um método: precisa de `return` em todos os caminhos se devolver algo.

```java executar
import java.util.function.BiFunction;
import java.util.function.Function;
import java.util.function.Supplier;

public class Formas {
    public static void main(String[] args) {
        BiFunction<Integer, Integer, Integer> a = (x, y) -> x + y;
        BiFunction<Integer, Integer, Integer> b = (Integer x, Integer y) -> x + y;
        BiFunction<Integer, Integer, Integer> c = (var x, var y) -> x + y;
        BiFunction<Integer, Integer, Integer> d = (final var x, final var y) -> {
            int soma = x + y;
            return soma;
        };
        System.out.println(a.apply(1, 2) + b.apply(1, 2) + c.apply(1, 2) + d.apply(1, 2));

        Function<String, String> sem = s -> s.trim();
        Function<String, String> com = (String s) -> { return s.trim(); };
        Supplier<String> nada = () -> "pronto";
        System.out.println("[" + sem.apply("  a ") + com.apply(" b  ") + "] " + nada.get());
    }
}
```

```saida
12
[ab] pronto
```

Os erros de sintaxe que a prova repete:

| Código | Problema |
|---|---|
| `x -> return x + 1` | `return` sem chaves |
| `x -> { x + 1 }` | Chaves sem `return` (e sem ponto e vírgula) |
| `String s -> s.length()` | Tipo declarado sem parênteses |
| `(Integer a, b) -> a + b` | Estilos de parâmetro misturados |
| `() -> { if (ok) return 1; }` | Falta `return` num dos caminhos |

## A lambda não tem tipo próprio

A mesma lambda pode ser um `Supplier<String>` ou um `Callable<String>`, conforme quem a recebe. Ela só faz sentido num contexto que diga qual interface funcional se espera, o **tipo-alvo**: uma atribuição, um parâmetro de método, um retorno ou um cast. Sem contexto, não compila:

```java nao-compila
import java.util.function.Supplier;

public class SemAlvo {
    public static void main(String[] args) {
        var gerador = () -> 42;
        Object o = () -> 42;
    }
}
```

`var` não tem de onde tirar o tipo, e `Object` não é uma interface funcional. Já `Object o = (Runnable) () -> {};` compila: o cast fornece o alvo.

## Expressões que servem a dois mundos

Uma lambda cujo corpo é uma chamada de método, como `s -> lista.add(s)`, é compatível tanto com um método que devolve algo quanto com um `void`: o valor é usado num caso e descartado no outro. Já `() -> 42` só serve a quem devolve um valor, e `() -> System.out.println()` só a quem é `void`. O compilador usa essa diferença para escolher entre sobrecargas:

```java executar
import java.util.concurrent.Callable;

public class Sobrecargas {
    static void executar(Runnable r) {
        System.out.println("Runnable");
    }

    static void executar(Callable<Integer> c) {
        System.out.println("Callable");
    }

    public static void main(String[] args) {
        executar(() -> 42);
        executar(() -> System.out.println());
        executar(() -> { });
    }
}
```

```saida
Callable
Runnable
Runnable
```

`() -> 42` não pode ser um `Runnable`, cujo `run()` é `void`. A chamada a `println` devolve `void` e não pode ser um `Callable`. É exatamente assim que o `ExecutorService.submit` decide entre suas duas versões, assunto da [temporada de threads](/assistir/senior-t1-e03). Quando as duas sobrecargas aceitam a lambda, como `Supplier<Integer>` e `Callable<Integer>` para `() -> 1`, a chamada é **ambígua** e não compila.

> [!ATENCAO]
> O corpo de uma lambda só pode lançar as exceções checked que o método da interface declara. `Runnable r = () -> { throw new Exception(); };` não compila, porque `run()` não declara nada; com `Callable`, cujo `call()` declara `throws Exception`, compila.

## this dentro de uma lambda

Uma lambda não cria um escopo novo de objeto: `this` dentro dela é o objeto da classe que a contém. Numa classe anônima, `this` é a própria instância anônima:

```java executar
public class Quem {
    String nome = "externo";

    void mostrar() {
        Runnable lambda = () -> System.out.println(this.nome);
        Runnable anonima = new Runnable() {
            String nome = "anônima";

            public void run() {
                System.out.println(this.nome);
            }
        };
        lambda.run();
        anonima.run();
    }

    public static void main(String[] args) {
        new Quem().mostrar();
    }
}
```

```saida
externo
anônima
```

Pelo mesmo motivo, um parâmetro de lambda não pode ter o nome de uma variável local já existente: `int x = 1; Function<Integer, Integer> f = x -> x + 1;` não compila, porque os dois `x` estariam no mesmo escopo.

## Por baixo dos panos

Para cada lambda, o `javac` gera um método **privado e sintético** na própria classe, com o corpo dela. Os nomes seguem o padrão `lambda$<método>$<número>`, e a reflexão os mostra:

```java executar
import java.lang.reflect.Method;
import java.lang.reflect.Modifier;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.function.Function;
import java.util.function.Supplier;

public class Sinteticos {
    static Supplier<String> fixo() {
        return () -> "fixo";
    }

    static Supplier<String> capturando(String s) {
        return () -> s;
    }

    public static void main(String[] args) {
        Function<Integer, Integer> dobro = x -> x * 2;
        List<String> nomes = new ArrayList<>();
        for (Method m : Sinteticos.class.getDeclaredMethods()) {
            if (m.getName().startsWith("lambda$")) {
                nomes.add(m.getName() + " " + Modifier.toString(m.getModifiers()));
            }
        }
        Collections.sort(nomes);
        nomes.forEach(System.out::println);
        System.out.println((fixo() == fixo()) + " " + (capturando("a") == capturando("a")));
    }
}
```

```saida
lambda$capturando$0 private static
lambda$fixo$0 private static
lambda$main$0 private static
true false
```

A referência `System.out::println` não gerou método: ela aponta direto para um método que já existe. Na última linha, a lambda de `fixo()` não captura nada, e a implementação atual da JVM cria um único objeto para ela, devolvido em todas as chamadas. A de `capturando` guarda o valor de `s` num campo, e cada chamada cria um objeto novo. A especificação não garante nenhum dos dois comportamentos, então nunca compare lambdas com `==`. O `invokedynamic`, explicado na Júnior T4, liga cada lambda à sua fábrica na primeira execução.

## Resumo para a prova

- Parâmetros: um estilo só (sem tipo, com tipo ou com `var`); parênteses obrigatórios com zero, vários ou tipados
- Corpo de expressão não tem `return`; corpo de bloco precisa de `return` em todos os caminhos que devolvem valor
- A lambda precisa de um tipo-alvo: `var f = () -> 1` e `Object o = () -> 1` não compilam
- Chamadas de método servem a interfaces `void` e com retorno; `() -> 42` só às com retorno
- Sobrecargas que aceitam a mesma lambda tornam a chamada ambígua
- `this` numa lambda é o objeto externo; parâmetros não podem repetir nomes de variáveis locais
