O pacote `java.util.function` tem 43 interfaces. Decorar todas é perda de tempo; entender o **sistema de nomes** resolve quase qualquer questão. A [Júnior T4](/assistir/junior-t4-e02) apresentou as nove principais. Este episódio completa o quadro: as versões para primitivos, as relações de herança entre elas, os métodos estáticos úteis e o que fazer quando nenhuma serve.

> [!ANTES]
> Antes do Java 8, cada biblioteca trazia as próprias interfaces de função: o Guava tinha `Function` e `Predicate` em `com.google.common.base`, e o Apache Commons Collections tinha `Transformer` e `Predicate`. Um mesmo projeto podia ter três `Predicate` diferentes, incompatíveis entre si. O pacote `java.util.function`, do Java 8, padronizou os nomes.

## As quatro famílias

Todas as interfaces do pacote derivam de quatro formas de função:

| Família | Forma | Método | Duas entradas |
|---|---|---|---|
| `Supplier<T>` | nada → `T` | `get()` | (não existe) |
| `Consumer<T>` | `T` → nada | `accept(T)` | `BiConsumer<T, U>` |
| `Predicate<T>` | `T` → `boolean` | `test(T)` | `BiPredicate<T, U>` |
| `Function<T, R>` | `T` → `R` | `apply(T)` | `BiFunction<T, U, R>` |

Os **operadores** são funções em que entrada e saída têm o mesmo tipo, e por isso **estendem** as funções: `UnaryOperator<T>` estende `Function<T, T>`, e `BinaryOperator<T>` estende `BiFunction<T, T, T>`. Um `UnaryOperator<String>` pode ser atribuído a uma `Function<String, String>`; o contrário não compila, porque nem toda função é um operador.

Não existe `BiSupplier` (um fornecedor não recebe nada, então não há o que dobrar) nem `TriFunction`. Para três entradas, crie a sua interface.

## O sistema de nomes dos primitivos

Usar `Function<Integer, Integer>` com números obriga a embrulhar cada `int` num `Integer`, o *autoboxing*. Para evitar esse custo, o pacote tem versões para `int`, `long` e `double` (e um `BooleanSupplier`), com nomes que seguem regras:

| Padrão do nome | Significado | Exemplo | Método |
|---|---|---|---|
| `Int...` | Recebe `int` | `IntPredicate`, `IntFunction<R>` | `test(int)`, `apply(int)` |
| `To...` | Devolve primitivo | `ToIntFunction<T>` | `applyAsInt(T)` |
| `...To...` | Recebe e devolve primitivos diferentes | `IntToLongFunction` | `applyAsLong(int)` |
| `Obj...Consumer` | Recebe objeto e primitivo | `ObjIntConsumer<T>` | `accept(T, int)` |
| `...Supplier` | Fornece primitivo | `IntSupplier`, `BooleanSupplier` | `getAsInt()`, `getAsBoolean()` |
| `...Operator` | Primitivo para o mesmo primitivo | `IntUnaryOperator`, `IntBinaryOperator` | `applyAsInt(...)` |

> [!PENSE]
> `IntFunction<R>` e `ToIntFunction<T>` têm quase o mesmo nome. Antes de ler o próximo parágrafo: qual delas recebe um `int`, qual devolve um `int`, e qual das duas teria um método com `As` no nome?

A regra dos métodos: quando a interface **devolve** um primitivo, o método ganha `As` + tipo (`getAsInt`, `applyAsDouble`); quando devolve objeto, `boolean` de predicado ou nada, o nome é o da família (`apply`, `test`, `accept`). Por isso `IntFunction<R>` tem `apply`, e `ToIntFunction<T>` tem `applyAsInt`.

```java executar
import java.util.function.BooleanSupplier;
import java.util.function.DoubleUnaryOperator;
import java.util.function.IntBinaryOperator;
import java.util.function.IntFunction;
import java.util.function.IntPredicate;
import java.util.function.IntSupplier;
import java.util.function.IntToLongFunction;
import java.util.function.ObjIntConsumer;
import java.util.function.ToDoubleBiFunction;
import java.util.function.ToIntFunction;

public class Primitivos {
    public static void main(String[] args) {
        IntSupplier dado = () -> 4;
        BooleanSupplier sempre = () -> true;
        IntPredicate par = n -> n % 2 == 0;
        IntBinaryOperator soma = (a, b) -> a + b;
        IntFunction<String> estrelas = n -> "*".repeat(n);
        ToIntFunction<String> tamanho = String::length; //> Devolve int: o método é applyAsInt.
        IntToLongFunction quadrado = n -> (long) n * n;
        ToDoubleBiFunction<Integer, Integer> media = (a, b) -> (a + b) / 2.0;
        DoubleUnaryOperator metade = d -> d / 2;
        ObjIntConsumer<StringBuilder> anexar = (sb, n) -> sb.append(n); //> Recebe um objeto e um int.

        StringBuilder sb = new StringBuilder("v");
        anexar.accept(sb, 7);
        System.out.println(dado.getAsInt() + " " + sempre.getAsBoolean() + " " + par.test(3) + " " + soma.applyAsInt(2, 3));
        System.out.println(estrelas.apply(3) + " " + tamanho.applyAsInt("java") + " " + quadrado.applyAsLong(100_000));
        System.out.println(media.applyAsDouble(3, 4) + " " + metade.applyAsDouble(5) + " " + sb);
    }
}
```

```saida
4 true false 5
*** 4 10000000000
3.5 2.5 v7
```

As versões primitivas não têm relação de herança com as genéricas: um `IntPredicate` não é um `Predicate<Integer>`, e atribuir um ao outro não compila. Tipo genérico com primitivo, como `Supplier<int>`, também não.

> [!CONVERSA]
> **Function&lt;Integer, Integer&gt;:** Eu sirvo para qualquer tipo. Números, textos, pedidos: todos cabem em mim.
>
> **IntUnaryOperator:** E cada número que passa por você vira um objeto `Integer` no heap.
>
> **Function&lt;Integer, Integer&gt;:** Só fora da faixa de -128 a 127. O resto vem de um cache.
>
> **IntUnaryOperator:** Num laço de 10 milhões de voltas, isso é muita caixa. Comigo, um `int` entra e um `int` sai.
>
> **Function&lt;Integer, Integer&gt;:** Mas ninguém decora o seu nome nem o do seu método, `applyAsInt`.
>
> **IntUnaryOperator:** Por isso existe a regra: `As` mais o tipo, sempre que a saída é primitiva.

## Métodos estáticos úteis

Algumas interfaces trazem fábricas prontas:

```java executar
import java.util.Comparator;
import java.util.function.BinaryOperator;
import java.util.function.Function;
import java.util.function.Predicate;
import java.util.function.UnaryOperator;

public class Fabricas {
    public static void main(String[] args) {
        System.out.println(Function.<Integer>identity().apply(5) + " " + UnaryOperator.<String>identity().apply("x"));
        System.out.println(Predicate.isEqual("a").test("a") + " " + Predicate.not(String::isEmpty).test("")); //> not inverte uma referência de método.

        BinaryOperator<String> maisCurta = BinaryOperator.minBy(Comparator.comparingInt(String::length));
        BinaryOperator<String> ultimaNaOrdem = BinaryOperator.maxBy(Comparator.naturalOrder());
        System.out.println(maisCurta.apply("abc", "de") + " " + ultimaNaOrdem.apply("abc", "de"));
    }
}
```

```saida
5 x
true false
de de
```

`identity()` devolve a função que não muda nada, útil como valor neutro. `Predicate.not` (Java 11) inverte uma referência a método, algo que `String::isEmpty.negate()` não permite. `minBy` e `maxBy` transformam um `Comparator` num `BinaryOperator` que escolhe um dos dois.

> [!LAPIS]
> Qual interface de `java.util.function` serve para cada caso? (a) gerar o número `int` do próximo pedido; (b) dizer se um CPF, em texto, é válido; (c) somar dois `double`; (d) gravar uma linha de texto no log.
>
> **Resposta:** (a) `IntSupplier`, com `getAsInt()`. (b) `Predicate<String>`, com `test`. (c) `DoubleBinaryOperator`, com `applyAsDouble`. (d) `Consumer<String>`, com `accept`.

> [!PROVA]
> Três perguntas resolvem quase tudo: quantos argumentos entram, o que sai e se algum deles é primitivo. Depois, o nome do método: `get`, `accept`, `test` ou `apply`, com `As` + tipo quando a saída é primitiva. `IntFunction.apply`, `ToIntFunction.applyAsInt`, `IntSupplier.getAsInt`, `BooleanSupplier.getAsBoolean`.

## Quando nenhuma serve

Fora do pacote também há interfaces funcionais: `Runnable` (nada para nada), `Callable<V>` (nada para `V`, podendo lançar exceção) e `Comparator<T>`. Se nenhuma combina, declare a sua com `@FunctionalInterface`, de preferência com um nome que diga o que ela significa no seu domínio, como `CalculoDeFrete`, e não só a forma, como `TriFunction`.

> [!PREVENCAO]
> Anote suas interfaces funcionais com `@FunctionalInterface`. Se alguém acrescentar um segundo método abstrato, o `javac` recusa na própria interface, com `Unexpected @FunctionalInterface annotation` e `CalculoDeFrete is not a functional interface`, em vez de quebrar cada lambda espalhada pelo projeto.

> [!MATEMATICA]
> De onde vêm as 43 interfaces: das combinações de forma com os três primitivos, `int`, `long` e `double`. Só as funções de um primitivo para outro **diferente** são 3 × 2 = **6**: `IntToLongFunction`, `IntToDoubleFunction`, `LongToIntFunction`, `LongToDoubleFunction`, `DoubleToIntFunction` e `DoubleToLongFunction`. Somando operadores, predicados, consumidores e fornecedores de cada primitivo, a conta chega aos 43.

> [!IA]
> Assistentes de IA usam `Function<Integer, Integer>` onde um `IntUnaryOperator` evitaria caixas, erram o nome do método das versões primitivas, como `apply` num `ToIntFunction`, e inventam interfaces que não existem, como `TriFunction` e `BiSupplier`. Compile a sugestão e confira o nome no Javadoc do pacote.

## Na IDE

- **Implementar com o nome certo.** Numa classe que implementa uma interface funcional, `Ctrl+I` gera o método abstrato com o nome exato, como `applyAsInt`.
- **O método da interface.** `Ctrl+Q` sobre `IntBinaryOperator` mostra a documentação, com o único método abstrato e os métodos `default`.
- **A anotação vigiada.** O IntelliJ sublinha uma interface com `@FunctionalInterface` assim que ela ganha um segundo método abstrato.

## Por baixo dos panos

As 43 interfaces existem por causa de uma decisão do Java 5: generics não aceitam primitivos, como vimos na [temporada de generics](/assistir/pleno-t2-e03). Cada `Integer` é um objeto no heap. O `Integer.valueOf` reaproveita os valores de -128 a 127 de um cache, mas fora dessa faixa cada autoboxing cria um objeto novo:

```java executar
import java.util.function.IntSupplier;
import java.util.function.Supplier;

public class Caixas {
    public static void main(String[] args) {
        Supplier<Integer> pequeno = () -> 100;
        Supplier<Integer> grande = () -> 1000;
        IntSupplier primitivo = () -> 1000;
        System.out.println((pequeno.get() == pequeno.get()) + " " + (grande.get() == grande.get()) + " " + (primitivo.getAsInt() == primitivo.getAsInt())); //> 1000 está fora do cache: dois objetos.
    }
}
```

```saida
true false true
```

Com `==`, dois `Integer` de valor 1000 são objetos diferentes; com `int`, são só números. Num laço de milhões de iterações, cada caixa é uma alocação e trabalho extra para o coletor de lixo. As especializações primitivas evitam esse custo, ao preço de uma API maior. O Projeto Valhalla pretende permitir algo como `Function<int, int>` no futuro, e com isso tornar boa parte desse zoológico desnecessária.

## Resumo para a prova

- Quatro famílias: `Supplier.get`, `Consumer.accept`, `Predicate.test`, `Function.apply`, com versões `Bi` (menos `Supplier`)
- `UnaryOperator` estende `Function`, e `BinaryOperator` estende `BiFunction`; o contrário não vale
- `Int...` recebe `int`; `To...` devolve primitivo, com método `applyAsX`; `Obj...Consumer` recebe objeto e primitivo
- Versões primitivas não se misturam com as genéricas, e não existe `Supplier<int>`
- `Function.identity`, `Predicate.not`, `Predicate.isEqual`, `BinaryOperator.minBy` e `maxBy`
- Nenhuma serve? Crie a sua com `@FunctionalInterface`
