Uma lambda pode usar variáveis de fora dela, mas com uma restrição famosa: variáveis **locais** só podem ser usadas se forem `final` ou **efetivamente final**. A regra gera algumas das questões mais traiçoeiras da prova, porque o erro aparece numa linha e a causa está em outra. Este episódio explica o que conta como efetivamente final, o que fica de fora da regra e por que ela existe.

> [!ANTES]
> Até o Java 7, uma classe anônima só podia usar variáveis locais declaradas com `final`, escrito por extenso: `final int limite = 10;`. O Java 8 relaxou a regra para "efetivamente final", que vale para lambdas e classes anônimas. A exigência continua a mesma; só a palavra deixou de ser obrigatória.

## O que é efetivamente final

Uma variável local é **efetivamente final** quando nunca recebe uma segunda atribuição: poderia ganhar a palavra `final` sem que o código deixasse de compilar. Não importa se a mudança vem antes ou depois da lambda:

```java nao-compila
import java.util.function.Supplier;

public class Depois {
    public static void main(String[] args) {
        int n = 1;
        Supplier<Integer> s = () -> n;
        n = 2;
    }
}
```

> [!PENSE]
> A variável muda **depois** da lambda, e a lambda nem chegou a rodar. Por que isso ainda é um problema? E em que linha você acha que o compilador vai apontar o erro?

O erro, `local variables referenced from a lambda expression must be final or effectively final`, aponta para a linha **da lambda**, não para a linha da reatribuição. Na prova, a pergunta "qual linha não compila?" quer a linha em que a variável é usada dentro da lambda.

> [!PREVENCAO]
> Declare como `final` as variáveis que uma lambda vai capturar. Assim, uma reatribuição posterior é apontada na própria linha, com `cannot assign a value to final variable n`, em vez de aparecer como um erro na lambda, às vezes muitas linhas abaixo.

Alguns casos que confundem:

| Situação | Efetivamente final? |
|---|---|
| `int x = 5;` e nunca mais atribuída | Sim |
| `int x;` seguido de uma única atribuição `x = 5;` | Sim |
| `int x = 5; x++;` | Não, mesmo que o `++` venha antes da lambda |
| Parâmetro de método reatribuído no corpo | Não |
| Variável do for-each, `for (String s : lista)` | Sim, uma nova a cada volta |
| Contador do for clássico, `for (int i = 0; ...; i++)` | Não, o `i++` o reatribui |

```java executar
import java.util.ArrayList;
import java.util.List;
import java.util.function.Supplier;

public class Capturas {
    public static void main(String[] args) {
        int x;
        x = 5;
        Supplier<Integer> dobro = () -> x * 2; //> Uma única atribuição: efetivamente final.
        System.out.println(dobro.get());

        List<Runnable> tarefas = new ArrayList<>();
        for (String nome : List.of("a", "b")) {
            tarefas.add(() -> System.out.print(nome));
        }
        for (int i = 0; i < 2; i++) {
            int copia = i; //> Uma variável nova a cada volta.
            tarefas.add(() -> System.out.print(copia));
        }
        tarefas.forEach(Runnable::run);
        System.out.println();
    }
}
```

```saida
10
ab01
```

No for clássico, a saída é copiar o contador para uma variável nova a cada volta, como `copia`, que nunca muda depois de criada.

> [!COMPILADOR]
> Você é o `javac`. A variável `valor` recebe uma atribuição no `try` e outra no `catch`, e cada execução passa por só uma delas. Compila?
>
> ```java nao-compila
> import java.util.function.Supplier;
> public class Leitura {
>     public static void main(String[] args) {
>         int valor;
>         try {
>             valor = Integer.parseInt("42");
>         } catch (NumberFormatException e) {
>             valor = 0;
>         }
>         Supplier<Integer> s = () -> valor;
>     }
> }
> ```
>
> **Resposta:** Não compila. Para o compilador, quando o `catch` roda, `valor` pode já ter recebido a atribuição do `try`: a do `catch` seria uma segunda, e a variável deixa de ser efetivamente final. Com `if`/`else`, em que cada caminho atribui uma vez, compilaria. A saída é calcular num método e guardar numa variável nova.

## O que não está sujeito à regra

A restrição vale só para variáveis **locais** e parâmetros. Fica de fora:

- **Campos** de instância e estáticos: a lambda pode lê-los e alterá-los livremente
- **O estado dos objetos**: a variável não pode apontar para outro objeto, mas o objeto pode mudar por dentro
- **As variáveis da própria lambda**: parâmetros e variáveis declaradas no corpo dela

```java executar
import java.util.List;
import java.util.function.Function;

public class ForaDaRegra {
    static int estatico = 0;
    int campo = 0;

    void contar() {
        Runnable r = () -> {
            campo++;
            estatico++;
        };
        r.run();
        r.run();
        System.out.println(campo + " " + estatico);
    }

    public static void main(String[] args) {
        new ForaDaRegra().contar();

        int[] total = {0};
        List.of(1, 2, 3).forEach(n -> total[0] += n); //> A variável não muda; o conteúdo do array, sim.
        StringBuilder log = new StringBuilder("a");
        Runnable anexar = () -> log.append("b");
        anexar.run();
        System.out.println(total[0] + " " + log);

        Function<Integer, Integer> f = n -> {
            int local = n;
            local++;
            return local;
        };
        System.out.println(f.apply(1));
    }
}
```

```saida
2 2
6 ab
2
```

O array de um elemento, `int[] total = {0}`, é um truque conhecido para acumular dentro de lambdas: a variável `total` nunca muda, só o conteúdo do array. Funciona, mas é sinal de que talvez falte uma ferramenta melhor, como `reduce` ou `sum`, que a [temporada de streams](/assistir/pleno-t6-e02) apresenta.

> [!CONVERSA]
> **Variável local:** Eu moro na pilha e sumo quando o método termina. Se uma lambda quer me usar, leva uma cópia.
>
> **Campo:** Eu moro no objeto, no heap. A lambda leva o objeto e me lê na hora em que roda.
>
> **Variável local:** Por isso eu não posso mudar: a cópia ficaria desatualizada, e o compilador não deixa.
>
> **Campo:** E eu posso mudar quanto quiser. A lambda sempre vê o meu valor atual.
>
> **Variável local:** O que nem sempre é bom: quem esperava o valor da criação leva um susto.

> [!PROVA]
> Procure toda atribuição à variável capturada no método inteiro, inclusive `++`, `+=` e atribuições a parâmetros. Uma só já tira o "efetivamente final", e o erro aparece na lambda. Classes anônimas seguem a mesma regra desde o Java 8, com a mensagem `referenced from an inner class`.

## Lambda e classe anônima: escopos diferentes

Além do `this`, visto no [episódio 1](/assistir/pleno-t5-e01), há outra diferença de escopo. Uma classe anônima é uma classe nova, e dentro dela é possível declarar um campo ou variável com o nome de uma variável externa, que fica escondida. Uma lambda não cria escopo novo: declarar dentro dela uma variável com o nome de uma local de fora não compila.

```java executar
public class Escopos {
    public static void main(String[] args) {
        int y = 1;
        Runnable anonima = new Runnable() {
            int y = 99;

            public void run() {
                System.out.println("anônima " + y);
            }
        };
        anonima.run();
        Runnable lambda = () -> System.out.println("lambda " + y);
        lambda.run();
    }
}
```

```saida
anônima 99
lambda 1
```

> [!IA]
> Diante do erro `must be final or effectively final`, assistentes de IA costumam sugerir o array de um elemento ou um `AtomicInteger`, que fazem compilar mas escondem um acumulador que deveria ser um `reduce` ou um `sum`. Peça a versão sem estado mutável e use o truque só quando não houver alternativa.

## Na IDE

- **Copiar para uma variável final.** No erro de captura, `Alt+Enter` oferece *Copy 'taxa' to effectively final temp variable*, a mesma correção feita à mão nesta aula.
- **Tornar `final`.** Quando a variável não é reatribuída, a ação *Make 'n' final* acrescenta a palavra e protege a captura.
- **As capturas no depurador.** Com um *breakpoint* dentro da lambda, a aba *Variables* mostra os valores capturados, inclusive os campos lidos pelo `this`.

## Por baixo dos panos

Por que a regra existe? Uma variável local vive na **pilha** do método e desaparece quando ele termina. A lambda, porém, pode ser guardada e executada muito depois, até em outra thread. Para funcionar, ela recebe uma **cópia** do valor no momento da criação, guardada num campo do objeto da lambda; é isso que o `lambda$capturando$0` do episódio 1 recebia como parâmetro.

![Em cima, a variável local n igual a 1, na pilha de main, é copiada para o objeto da lambda; se n mudasse depois, haveria duas versões, e por isso não compila; embaixo, o objeto da lambda guarda this e lê o campo desconto da Loja na hora em que roda](/figuras/copia-na-captura.svg "Locais são copiados na criação e por isso não podem mudar; campos são lidos na hora.")

> [!MATEMATICA]
> O tamanho do que a lambda guarda: cada variável capturada vira um campo do objeto da lambda. Com 3 capturas de `int`, são 12 bytes de cabeçalho mais 3 × 4 = 12 de dados, **24 bytes** por objeto. Uma lambda criada dentro de um laço de 1 milhão de voltas ocupa uns 24 MB até o coletor de lixo recolher, enquanto uma lambda sem capturas é um objeto só.

Se a variável pudesse mudar depois, haveria duas versões dela: a da pilha e a cópia da lambda. Qualquer escolha seria confusa. O Java resolveu proibindo a mudança, e assim a cópia é sempre igual ao original. Linguagens como C# e JavaScript fazem diferente: guardam a variável num objeto compartilhado no heap, o que permite alterá-la, mas abre espaço para bugs clássicos, como todas as funções criadas num laço verem o último valor do contador, e para condições de corrida entre threads.

Campos não têm esse problema: a lambda guarda uma referência ao objeto (ou nada, no caso de estáticos) e lê o campo atual quando executa. Por isso campos podem mudar livremente, e por isso uma lambda que altera campos compartilhados entre threads precisa dos cuidados da [temporada de código thread-safe](/assistir/senior-t2-e01).

## Resumo para a prova

- Variáveis locais e parâmetros capturados precisam ser `final` ou efetivamente final
- Qualquer reatribuição, antes ou depois da lambda, impede a captura; o erro aparece na linha da lambda
- A variável do for-each pode ser capturada; o contador do for clássico, não
- Campos, campos estáticos e o estado interno de objetos podem ser alterados dentro da lambda
- Classes anônimas seguem a mesma regra, mas criam escopo próprio e podem esconder nomes externos
- A lambda guarda uma cópia do valor; a regra garante que a cópia nunca fique desatualizada
