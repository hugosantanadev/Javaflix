Você já viu os dois extremos: o C, compilado antes para uma máquina específica, e o bytecode, que roda em qualquer JVM. Este episódio abre a JVM: como ela carrega classes, onde guarda cada coisa na memória e como transforma bytecode em código nativo enquanto o programa roda.

## Três jeitos de executar um programa

| Estratégia | Exemplos | Vantagem | Custo |
|---|---|---|---|
| Compilação antecipada (AOT) | C, C++, Go, Rust | Rápido desde o início | Um binário por plataforma; compila uma vez, sem ver como o programa é usado |
| Interpretação | shell, Python clássico | Portável, começa a rodar na hora | Lento: cada linha é analisada e executada de novo a cada vez |
| Máquina virtual com bytecode e JIT | Java, C#, JavaScript moderno | Portável e rápido depois de aquecer | Início mais lento; o JIT consome CPU e memória |

> [!ANTES]
> A ideia de compilar para uma máquina imaginária é antiga: o Pascal da Universidade da Califórnia em San Diego (UCSD Pascal, 1977) gerava o *p-code*, que rodava em qualquer computador com o interpretador certo. O Java pegou a ideia em 1995, e as primeiras JVMs só interpretavam, o que deu ao Java a fama de lento. A HotSpot, com JIT, virou a JVM padrão no Java 1.3, em 2000.

O Java fica na terceira linha: compila antes para bytecode (rápido de interpretar e portátil) e deixa a compilação para código nativo para depois, quando já se sabe quais partes do programa são usadas.

## Por dentro da JVM

```text
        .class
          │
  ┌───────▼────────┐
  │ Class loaders  │  carregam as classes sob demanda
  └───────┬────────┘
  ┌───────▼────────┐
  │  Verificador   │  confere o bytecode antes de executar
  └───────┬────────┘
  ┌───────▼─────────────────────────────────────────┐
  │ Áreas de memória                                │
  │  heap (objetos)  ·  metaspace (classes)         │
  │  uma pilha e um PC para cada thread             │
  └───────┬─────────────────────────────────────────┘
  ┌───────▼────────┐
  │ Execução       │  interpretador + JIT (C1 e C2) + coletor de lixo
  └────────────────┘
```

**Class loaders.** Nenhuma classe é carregada antes da hora. Quando o código usa uma classe pela primeira vez, um *class loader* procura o `.class` (no classpath, num `.jar` ou nos módulos do JDK), lê os bytes e cria a representação da classe na memória. Existe uma hierarquia: o *bootstrap* carrega o núcleo do Java (`java.lang`), o *platform* carrega o resto do JDK e o *application* carrega as suas classes.

**Verificador.** Antes de executar, a JVM confere se o bytecode é bem comportado: se cada instrução recebe os tipos certos, se a pilha de operandos nunca estoura, se nenhuma variável é lida antes de ser escrita. É o que impede um `.class` adulterado de corromper a memória, algo que um executável nativo não tem como garantir.

**Áreas de memória.** Pela especificação da JVM:

- **Heap**: todos os objetos e arrays. É compartilhado entre as threads e é onde o coletor de lixo trabalha.
- **Metaspace** (a "área de métodos" da especificação): estrutura das classes, bytecode dos métodos, constantes. Também é compartilhado.
- **Pilha da JVM**: uma por thread. Cada chamada de método empilha um *frame* com as variáveis locais e a **pilha de operandos**.
- **PC**: um por thread, com a instrução de bytecode atual.

## Uma máquina de pilha

O bytecode foi desenhado para uma máquina de **pilha**, não de registradores. Para `a * b + c`:

```text
iload_0   // empilha a
iload_1   // empilha b
imul      // desempilha dois, multiplica, empilha o resultado
iload_2   // empilha c
iadd      // desempilha dois, soma, empilha
```

![A pilha de operandos depois de cada instrução de a * b + c: empilha 2, empilha 3, multiplica e fica 6, empilha 4, soma e fica 10](/figuras/maquina-de-pilha.svg "Cada instrução mexe só no topo da pilha.")

Não há nomes de registradores, então o bytecode não depende de quantos registradores o processador tem: x86-64 tem 16, ARM64 tem 31. Quem decide como usar os registradores de cada máquina é o JIT, na hora de gerar o código nativo.

## Inicialização preguiçosa

A inicialização de uma classe (os blocos `static` e os valores iniciais dos campos `static`) acontece no **primeiro uso ativo**: criar um objeto, chamar um método estático ou ler um campo estático. Veja a ordem:

```java executar
class Config {
    static {
        System.out.println("Config inicializada");
    }
    static int porta = 8080;
}

public class Inicio {
    public static void main(String[] args) {
        System.out.println("início");
        System.out.println(Config.porta); //> Primeiro uso ativo: só agora o bloco static roda.
    }
}
```

```saida
início
Config inicializada
8080
```

> [!PENSE]
> No programa abaixo, a única diferença é o `final`. Antes de ver a saída: quem imprime o 8080, a classe `Constantes` ou o próprio `main`?

Agora a pegadinha. Se o campo for uma **constante de compilação** (`static final` com valor constante), o `javac` copia o valor para quem usa, e a classe nem precisa ser inicializada:

```java executar
class Constantes {
    static {
        System.out.println("Constantes inicializada");
    }
    static final int PORTA = 8080; //> Constante de compilação: o valor é copiado para quem usa.
}

public class Inlining {
    public static void main(String[] args) {
        System.out.println("início");
        System.out.println(Constantes.PORTA);
    }
}
```

```saida
início
8080
```

O bloco `static` de `Constantes` nunca roda. É o constant folding do episódio anterior com um efeito visível.

## O JIT

A JVM começa **interpretando** o bytecode e contando quantas vezes cada método e cada laço rodam. Quando um trecho fica "quente", o JIT o compila para código nativo:

- **C1**, o compilador cliente: compila rápido, otimiza pouco
- **C2**, o compilador servidor: demora mais, otimiza muito

> [!CONVERSA]
> **C1:** Eu compilo em milissegundos. O código não fica perfeito, mas já é bem mais rápido que o interpretador.
>
> **C2:** E eu demoro mais, mas faço inlining agressivo, removo checagens e reorganizo laços.
>
> **C1:** Então por que a JVM não chama você logo de cara?
>
> **C2:** Porque eu gastaria tempo compilando métodos que rodam uma vez só. Você segura as pontas e coleta estatísticas; eu fico com o que provou ser quente.

Por padrão a HotSpot usa os dois em camadas (*tiered compilation*): primeiro o C1 para ganhar velocidade logo, depois o C2 nos trechos mais quentes. O JIT faz coisas que um compilador antecipado não consegue, porque **vê o programa rodando**: se um método virtual sempre recebe a mesma classe, ele faz inlining direto daquela implementação. Se a suposição quebrar, ele **desotimiza** e volta ao interpretador.

Dá para ver o JIT trabalhando com a opção `-XX:+PrintCompilation`:

```bash
java -XX:+PrintCompilation MinhaClasse
```

> [!MATEMATICA]
> Quando um método vira "quente"? Na HotSpot, com a compilação em camadas, os limites ficam na casa de milhares de chamadas: um método chamado umas 2.000 vezes vai para o C1, e um com dezenas de milhares de chamadas e voltas de laço vai para o C2 (os valores exatos dependem da versão e das opções). Um serviço que atende 1.000 requisições por segundo aquece os métodos principais em poucos segundos; um programa que roda uma vez e termina talvez nunca chegue ao C2.

Consequência prática: um programa Java fica mais rápido depois de rodar um tempo, o chamado **aquecimento** (*warm-up*). Por isso medir desempenho com um laço e `System.currentTimeMillis()` engana: você mede o interpretador. Medições sérias usam a ferramenta JMH.

> [!PERGUNTAS]
> **P:** Se o JIT é tão bom, por que o `javac` não gera código nativo de uma vez?
>
> **R:** Porque o `javac` não sabe em que processador o programa vai rodar, nem como ele vai ser usado. O JIT sabe as duas coisas: gera instruções do processador real (inclusive as mais novas, que o `.class` nem conhece) e otimiza o caminho que o programa realmente percorre.

> [!ERRO]
> Um bloco `static` que lança exceção derruba a classe para sempre. O primeiro uso dá `ExceptionInInitializerError`, com a exceção original como causa; os usos seguintes dão `NoClassDefFoundError`, que parece um problema de classpath e despista. Quando aparecer um `NoClassDefFoundError` estranho, procure um `ExceptionInInitializerError` mais acima no log.

## O coletor de lixo

Objetos sem nenhuma referência alcançável viram lixo, e o **coletor de lixo** (GC) recupera essa memória. A observação que guia os coletores modernos é a **hipótese geracional**: a maioria dos objetos morre jovem. Por isso o heap é dividido em gerações, e a geração jovem é varrida com frequência e barato. O coletor padrão é o **G1**; o **ZGC** faz pausas de menos de um milissegundo mesmo em heaps enormes. Os detalhes estão no cargo Backend Sênior.

## Java também pode ser AOT

Para quem precisa de início instantâneo, como funções serverless, existe a compilação antecipada de Java: o **GraalVM Native Image** gera um executável nativo, que inicia em milissegundos e usa menos memória, ao custo de um build demorado e de perder otimizações que só o JIT consegue. E o próprio JDK vem ganhando caches de início rápido: o Java 24 trouxe o carregamento e a ligação antecipados de classes (JEP 483), que reaproveita o trabalho de uma execução anterior.

> [!IA]
> A IA costuma repetir mitos antigos sobre a JVM: que o `final` em métodos deixa o código mais rápido, que o `System.gc()` libera memória na hora ou que o Java é interpretado. O JIT torna o primeiro quase sempre irrelevante, o segundo é só um pedido que a JVM pode ignorar, e o terceiro deixou de ser verdade em 2000. Desconfie de dicas de desempenho sem medição com JMH.

## Na IDE

- **Ver o bytecode.** Com uma classe aberta, *View*, *Show Bytecode* mostra o `javap -c` da classe: os `iload`, `imul` e `iadd` deste episódio.
- **Passar opções à JVM.** Em *Run*, *Edit Configurations*, o campo *VM options* recebe `-XX:+PrintCompilation` ou `-Xss` para ver o JIT ou mudar a pilha.
- **Ver as threads.** No depurador, o painel *Threads* lista as threads da JVM, cada uma com a sua pilha, inclusive as do JIT e do coletor de lixo.

## Resumo

- AOT é rápido desde o início; interpretador é portável e lento; VM com JIT junta os dois
- Class loaders carregam sob demanda; o verificador confere o bytecode antes de executar
- Heap e metaspace são compartilhados; cada thread tem a sua pilha e o seu PC
- Bytecode é para uma máquina de pilha; o JIT mapeia para os registradores
- Classes são inicializadas no primeiro uso ativo; constantes `static final` são copiadas e não disparam a inicialização
- O JIT compila os trechos quentes, por isso Java precisa aquecer
