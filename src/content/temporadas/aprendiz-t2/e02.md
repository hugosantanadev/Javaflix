C foi criada em 1972, por Dennis Ritchie, para reescrever o Unix. Ela fica um degrau acima do assembly: você escreve `a + b` em vez de escolher registradores, mas continua mexendo direto na memória. Quase todo software de base é escrito em C ou C++: o kernel do Linux, boa parte do Windows, bancos de dados, e a própria JVM HotSpot, que é escrita em C++. Entender o caminho de um programa C ajuda a enxergar o que o Java faz diferente.

## Hello, world em C

```c
#include <stdio.h>

int main(void) {
    printf("Olá, C!\n");
    return 0;
}
```

Parece com Java, mas não tem classe, e o `main` devolve um `int` para o sistema operacional (0 quer dizer "deu certo").

## As quatro etapas da compilação

O comando `gcc ola.c -o ola` parece fazer uma coisa só, mas são quatro programas em sequência:

| Etapa | Programa | Entrada | Saída | Para ver só ela |
|---|---|---|---|---|
| 1. Pré-processamento | pré-processador | `ola.c` | C expandido | `gcc -E ola.c` |
| 2. Compilação | compilador | C expandido | assembly (`ola.s`) | `gcc -S ola.c` |
| 3. Montagem | montador | `ola.s` | código objeto (`ola.o`) | `gcc -c ola.c` |
| 4. Ligação | ligador (*linker*) | `ola.o` + bibliotecas | executável `ola` | `gcc ola.o -o ola` |

1. O **pré-processador** só manipula texto. `#include <stdio.h>` cola o conteúdo desse arquivo no lugar da linha, e `#define MAX 100` troca toda ocorrência de `MAX` por `100`.
2. O **compilador** transforma C em assembly da máquina de destino. É a etapa difícil, assunto do próximo episódio.
3. O **montador** gera o **código objeto**: código de máquina, mas com buracos. O `ola.o` chama `printf`, só que não sabe onde `printf` está.
4. O **ligador** junta os objetos com as bibliotecas e tapa os buracos, trocando cada referência a `printf` pelo endereço de verdade. Se uma função não existe em lugar nenhum, o erro aparece aqui: `undefined reference to 'printf'`.

Por fim, ao executar `./ola`, o **carregador** do sistema operacional copia o executável para a memória e salta para o começo dele.

## Um executável por plataforma

O resultado é código de máquina para **uma** ISA, num formato de arquivo de **um** sistema operacional: ELF no Linux, PE (o `.exe`) no Windows, Mach-O no macOS. O mesmo `ola` não roda no Windows nem num Mac com ARM. Para cada combinação de processador e sistema, é preciso compilar de novo.

Compare com o Java: o `javac` gera **um** `.class`, e cada JVM, que essa sim foi compilada para cada plataforma, cuida do resto.

## Ponteiros e memória

Em C, você trabalha com endereços de memória explicitamente. Um **ponteiro** é uma variável que guarda um endereço:

```c
int idade = 30;
int *p = &idade;   // p guarda o endereço de idade
*p = 31;           // muda idade através do ponteiro
printf("%d\n", idade);  // 31
```

`&` pega o endereço de uma variável e `*` acessa o que está no endereço. Como em Java, variáveis locais ficam na pilha. Para memória que precisa durar mais que a função, você pede ao sistema com `malloc` e devolve com `free`, **manualmente**:

```c
int *notas = malloc(10 * sizeof(int));  // reserva espaço para 10 ints no heap
notas[0] = 9;
free(notas);                            // devolve; esquecer isso vaza memória
```

## Os bugs que o Java eliminou

Esse poder vem com uma lista de bugs clássicos, responsáveis por boa parte das falhas de segurança da história:

| Bug em C | O que acontece em C | Em Java |
|---|---|---|
| Acesso fora do array (`v[10]` num array de 10) | Comportamento indefinido: lê ou corrompe memória vizinha, sem aviso | `ArrayIndexOutOfBoundsException` |
| Usar memória depois do `free` | Comportamento indefinido | Não existe `free`: o coletor de lixo só libera o que ninguém mais referencia |
| `free` duas vezes | Corrompe o gerenciador de memória | Idem |
| Ponteiro nulo | Em geral, derruba o programa (*segmentation fault*) | `NullPointerException`, com a mensagem dizendo o que estava nulo |
| Overflow de `int` com sinal | Comportamento indefinido | Definido: dá a volta |

"Comportamento indefinido" é um termo técnico do padrão C: o compilador pode assumir que aquilo nunca acontece e gerar qualquer código. O famoso *buffer overflow* nasce do primeiro item: escrever além do fim de um array e sobrescrever, por exemplo, o endereço de retorno guardado na pilha.

No Java, todo acesso a array confere o limite:

```java executar
public class Limite {
    public static void main(String[] args) {
        int[] v = new int[3];
        try {
            v[3] = 10;
        } catch (ArrayIndexOutOfBoundsException e) {
            System.out.println(e.getMessage());
        }
    }
}
```

```saida
Index 3 out of bounds for length 3
```

Essa checagem custa quase nada: o JIT remove as que consegue provar desnecessárias, como num `for` que vai de 0 a `v.length - 1`.

## Tamanhos que mudam de plataforma para plataforma

Em C, `int` tem *no mínimo* 16 bits e `long` pode ter 32 bits (Windows 64 bits) ou 64 (Linux 64 bits). O Java fixou tudo na especificação: `int` tem 32 bits e `long` 64, em qualquer máquina.

```java executar
public class Tamanhos {
    public static void main(String[] args) {
        System.out.println(Integer.SIZE + " " + Long.SIZE + " " + Character.SIZE);
    }
}
```

```saida
32 64 16
```

## Java e C convivem

O Java não substituiu o C: ele roda em cima dele. A JVM é um programa C++, e o Java consegue chamar bibliotecas nativas. O jeito antigo é o JNI; o moderno é a API de funções e memória externas (*Foreign Function & Memory API*), finalizada no Java 22, que chama funções C sem escrever código C.

## Resumo

- C compila em quatro etapas: pré-processador, compilador, montador, ligador
- O ligador resolve referências entre objetos e bibliotecas
- Executável nativo vale para uma ISA e um sistema operacional
- Ponteiro guarda endereço; `&` pega o endereço, `*` acessa o conteúdo
- Em C, memória do heap é devolvida à mão com `free`; em Java, pelo coletor de lixo
- Java confere limites de array, define o overflow e fixa o tamanho dos tipos
