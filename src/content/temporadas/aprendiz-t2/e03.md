Um compilador é um programa que traduz um programa de uma linguagem para outra sem mudar o que ele faz. Parece mágica, mas é uma linha de montagem com etapas bem definidas, e conhecer essas etapas explica de onde vem cada mensagem de erro do `javac`, e várias pegadinhas da prova.

## Front-end, meio e back-end

Todo compilador moderno tem três partes:

- **Front-end**: lê o código-fonte, entende a estrutura e confere se faz sentido. Depende da linguagem.
- **Meio**: transforma o programa numa **representação intermediária** e otimiza.
- **Back-end**: gera o código de destino. Depende da máquina.

Essa divisão é o que permite ao GCC e ao LLVM compilarem C, C++, Rust e outras linguagens para x86, ARM e RISC-V: N front-ends e M back-ends conversando pela mesma representação no meio. O `javac` é um caso mais simples: o front-end é Java e o back-end gera bytecode. A otimização pesada fica para o JIT, dentro da JVM.

## 1. Análise léxica

O código começa como uma sequência de caracteres. O **analisador léxico** (*lexer*) agrupa os caracteres em **tokens**, as "palavras" da linguagem, e descarta espaços e comentários:

```text
int total = preco * 2;

[int]    palavra-chave
[total]  identificador
[=]      operador
[preco]  identificador
[*]      operador
[2]      literal inteiro
[;]      pontuação
```

> [!PENSE]
> Para o analisador léxico, `preco*2` (sem espaços) e `preco * 2` geram os mesmos tokens?

Erros nessa etapa são de "palavra mal escrita": um literal `0b102`, um `'ab'` com dois caracteres entre aspas simples, uma String sem fechar.

## 2. Análise sintática

O **analisador sintático** (*parser*) confere se os tokens formam frases válidas segundo a **gramática** da linguagem e monta uma **árvore sintática abstrata** (AST). Para `2 + 3 * 4`:

```text
      +
     / \
    2   *
       / \
      3   4
```

A precedência dos operadores está na forma da árvore: a multiplicação fica mais funda, então é calculada antes. Parênteses só mudam a forma da árvore e depois desaparecem. Erros sintáticos são de "frase mal formada": `;` faltando, parêntese sem fechar, `else` sem `if`.

> [!CONVERSA]
> **Parser:** Para mim, `int x = "dez";` está perfeito: tipo, nome, igual, expressão, ponto e vírgula.
>
> **Analisador semântico:** E para mim está errado: a expressão é uma `String`, e a variável é `int`.
>
> **Parser:** Então eu deixei passar um erro?
>
> **Analisador semântico:** Não, você fez o seu trabalho: a frase é bem formada. Se ela faz sentido, quem decide sou eu, olhando a tabela de símbolos.

## 3. Análise semântica

Uma frase pode estar bem formada e não fazer sentido, como "a pedra comeu o domingo". A **análise semântica** confere significado: a variável foi declarada? Os tipos combinam? O método existe com esses parâmetros? A variável local tem valor antes de ser lida? É nessa etapa que o compilador monta a **tabela de símbolos**, com cada nome, seu tipo e seu escopo.

## 4. Otimização

Com a árvore validada, o compilador pode melhorar o programa sem mudar o resultado. Algumas otimizações clássicas:

| Otimização | Antes | Depois |
|---|---|---|
| *Constant folding* | `x = 2 + 3 * 4` | `x = 14` |
| Propagação de constantes | `a = 5; b = a * 2` | `b = 10` |
| Eliminação de código morto | `if (false) { ... }` | (some) |
| *Inlining* | chamar um método curto | o corpo do método no lugar da chamada |
| Desenrolar laços | laço de 4 voltas | 4 cópias do corpo |

> [!MATEMATICA]
> O *constant folding* tira o custo da execução e o leva para a compilação, que acontece uma vez. Uma expressão como `60 * 60 * 24 * 365`, os segundos de um ano, vira o literal 31.536.000 no bytecode. Se ela estiver num laço que roda 1 milhão de vezes, são 3 milhões de multiplicações a menos. Cuidado com o estouro: `1000 * 60 * 60 * 24 * 365`, os milissegundos de um ano, dá 31.536.000.000, que não cabe num `int`, e o compilador dobra a conta já com o valor errado.

> [!ANTES]
> O primeiro compilador de alto nível de sucesso foi o do Fortran, da IBM, em 1957, e levou cerca de 18 pessoas-ano para ficar pronto. Antes dele, muita gente duvidava que um programa traduzido automaticamente pudesse ser tão rápido quanto assembly escrito à mão. A teoria das gramáticas, de Noam Chomsky (1956), e a notação BNF, usada para descrever o Algol 60, deram aos compiladores a base que usam até hoje.

## 5. Geração de código

Por fim, a árvore vira código de destino: assembly no GCC, bytecode no `javac`. No episódio de JVM do cargo Estagiário você viu o resultado real: `2 + 3 * 4` chegou ao bytecode como `bipush 14`.

## Cada erro tem a sua etapa

Saber a etapa ajuda a ler a mensagem do compilador:

| Código | Etapa | Mensagem do `javac` |
|---|---|---|
| `char c = 'ab';` | Léxica | `unclosed character literal` |
| `int x = 10` (sem `;`) | Sintática | `';' expected` |
| `int x = "dez";` | Semântica | `incompatible types: String cannot be converted to int` |
| `y = 1;` sem declarar `y` | Semântica | `cannot find symbol` |

> [!PERGUNTAS]
> **P:** Se o `javac` otimiza tão pouco, o Java não fica lento?
>
> **R:** Não, porque a otimização pesada acontece depois, no JIT, que vê o programa rodando: sabe quais métodos são chamados mais, quais tipos realmente aparecem e quais `if` quase nunca são verdadeiros. Com essas informações, ele otimiza melhor do que um compilador que só vê o código-fonte.

## O javac na prática: constantes de compilação

O *constant folding* do `javac` tem consequências visíveis. Uma expressão formada só por literais e variáveis `final` inicializadas com constantes é uma **expressão constante**, calculada na compilação. Strings constantes vão para o *pool* de strings, então duas constantes iguais são o mesmo objeto:

```java executar
public class Dobra {
    public static void main(String[] args) {
        String java = "Java";
        final String ja = "Ja";
        String va = "va";
        System.out.println(java == "Ja" + "va");
        System.out.println(java == ja + "va");
        System.out.println(java == "Ja" + va); //> va não é final: a concatenação acontece na execução.
        System.out.println(java.equals("Ja" + va));
    }
}
```

```saida
true
true
false
true
```

As duas primeiras concatenações foram feitas pelo compilador e viraram o mesmo `"Java"` do pool. A terceira usa `va`, que não é `final`: a concatenação acontece em tempo de execução e cria um objeto novo, então `==` dá `false`, mesmo com o mesmo texto. Por isso Strings se comparam com `equals`.

> [!ERRO]
> Comparar Strings com `==` e ter o teste passando por sorte: com literais e constantes, os textos vêm do mesmo pool e `==` dá `true`. Basta um dos lados vir de uma concatenação em tempo de execução, de um `substring` ou de um arquivo, e o mesmo teste passa a dar `false`. Use sempre `equals`.

Outro efeito: os rótulos de `case` precisam ser constantes de compilação. Uma variável comum não serve, uma `final` inicializada com constante serve.

## Código inalcançável

O compilador recusa código que nunca pode executar, com uma exceção curiosa:

```java nao-compila
while (false) {
    System.out.println("nunca");   // erro: unreachable statement
}
```

```java executar
public class Condicional {
    public static void main(String[] args) {
        if (false) {
            System.out.println("nunca");
        }
        System.out.println("fim");
    }
}
```

```saida
fim
```

O `if (false)` é permitido de propósito, para que você possa desligar um trecho com uma constante (`static final boolean DEBUG = false;`). O compilador então elimina o trecho do bytecode: é a eliminação de código morto acontecendo.

## Escrever um compilador

Parece assunto de pós-graduação, mas um interpretador pequeno cabe em poucas centenas de linhas. O livro gratuito [Crafting Interpreters](https://craftinginterpreters.com/) constrói dois, um deles em Java, explicando cada etapa deste episódio.

> [!IA]
> Quando a IA explica uma mensagem de erro do compilador, ela às vezes atribui o erro à etapa errada ou sugere uma correção para outro problema. Antes de aceitar, leia a linha e a coluna que o `javac` apontou: o primeiro erro da lista é quase sempre a causa dos outros.

## Na IDE

- **Erros por etapa.** A IDE roda as análises léxica, sintática e semântica enquanto você digita: o sublinhado vermelho aparece antes de compilar, com a mesma mensagem que o `javac` daria.
- **Ver a árvore.** O plugin *PsiViewer* mostra a árvore sintática que a IDE monta para o arquivo aberto, nó a nó.
- **Ver a constante dobrada.** *View*, *Show Bytecode* mostra o `bipush 14` no lugar da conta, e os `ldc` com as Strings concatenadas pelo compilador.

## Resumo

- Front-end entende o código, o meio otimiza, o back-end gera o destino
- Léxica: caracteres viram tokens
- Sintática: tokens viram árvore, e a precedência está na forma dela
- Semântica: tipos, declarações e escopo
- Otimização: constant folding, código morto, inlining
- Expressões constantes são calculadas pelo `javac`: afetam `==` com Strings e rótulos de `case`
