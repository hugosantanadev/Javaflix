Na temporada anterior, a CPU de brinquedo executava números como `0x1E` e `0x30`. Processadores reais fazem exatamente isso, só que com centenas de instruções diferentes. Este episódio mostra como é esse código de máquina, como o assembly dá nomes a ele e por que o mesmo programa em C vira código diferente em cada processador.

## Código de máquina é só bytes

Um programa nativo, no fim, é uma sequência de bytes que a CPU busca, decodifica e executa. Em processadores x86-64 (Intel e AMD), alguns exemplos reais:

| Bytes (hexadecimal) | Significado |
|---|---|
| `C3` | `ret`: volta para quem chamou |
| `90` | `nop`: não faz nada |
| `B8 01 00 00 00` | `mov eax, 1`: coloca o número 1 no registrador eax |
| `01 F8` | `add eax, edi`: soma edi em eax |

Instruções x86 têm tamanhos variados, de 1 a 15 bytes. Já processadores ARM (celulares, Macs com chip M) usam instruções de tamanho fixo, 4 bytes cada. Cada família de processadores tem o seu **conjunto de instruções** (*ISA*, de *instruction set architecture*), e um não entende o do outro.

Repare em `B8 01 00 00 00`: o número 1, de 32 bits, aparece como `01 00 00 00`, com o byte menos significativo **primeiro**. Isso se chama **little-endian**, e é como x86 e ARM guardam números na memória.

## Assembly: código de máquina com nomes

Ninguém escreve `B8 01 00 00 00` à mão. O **assembly** é a mesma coisa com nomes legíveis (*mnemônicos*): `mov`, `add`, `jmp`. Um programa chamado **montador** (*assembler*) traduz cada linha para os bytes correspondentes, quase sempre numa relação de um para um. Rótulos (*labels*) dão nome a endereços, para você escrever `jmp laco` em vez de "salte 7 bytes para trás".

## Registradores do x86-64

O x86-64 tem 16 registradores de uso geral de 64 bits: `rax`, `rbx`, `rcx`, `rdx`, `rsi`, `rdi`, `rbp`, `rsp` e `r8` a `r15`. Os nomes com `e` (`eax`, `edi`) são a metade de baixo, de 32 bits, herança da época em que os processadores eram de 32 bits. Dois têm papel especial:

- `rsp` (*stack pointer*): aponta o topo da pilha
- `rip` (*instruction pointer*): é o PC, o endereço da próxima instrução

Para funções conversarem, existe uma **convenção de chamada**. No Linux e no macOS (a convenção System V), os argumentos inteiros chegam em `rdi`, `rsi`, `rdx`, `rcx`, `r8` e `r9`, nessa ordem, e o resultado volta em `rax`. No Windows a ordem é `rcx`, `rdx`, `r8`, `r9`.

## Uma função C vista por dentro

Esta função C soma dois inteiros:

```c
int soma(int a, int b) {
    return a + b;
}
```

Compilada com `gcc -O0` (sem otimização), num Linux x86-64, ela vira:

```asm
soma:
    push    rbp                     ; salva o rbp de quem chamou
    mov     rbp, rsp                ; cria o quadro desta função
    mov     DWORD PTR [rbp-4], edi  ; guarda a na pilha
    mov     DWORD PTR [rbp-8], esi  ; guarda b na pilha
    mov     edx, DWORD PTR [rbp-4]  ; edx = a
    mov     eax, DWORD PTR [rbp-8]  ; eax = b
    add     eax, edx                ; eax = b + a
    pop     rbp                     ; desfaz o quadro
    ret                             ; o resultado volta em eax
```

Sem otimização, o compilador guarda cada variável na pilha e relê na hora de usar. É ineficiente, mas facilita a depuração: cada variável tem um endereço fixo. Com `gcc -O2`, a mesma função vira:

```asm
soma:
    lea     eax, [rdi+rsi]          ; eax = a + b, numa instrução só
    ret
```

O `lea` foi criado para calcular endereços, mas o compilador o usa como uma soma de três operandos. Para ver isso ao vivo com qualquer código, use o [Compiler Explorer](https://godbolt.org/).

## Laços viram saltos

Não existe `for` em assembly. Um laço é uma comparação e um salto condicional. Esta função soma os números de 1 a n:

```c
int somatorio(int n) {
    int total = 0;
    for (int i = 1; i <= n; i++) {
        total += i;
    }
    return total;
}
```

Uma tradução direta para assembly, escrita à mão para ficar legível:

```asm
somatorio:              ; n chega em edi
    mov     eax, 0      ; total = 0
    mov     ecx, 1      ; i = 1
laco:
    cmp     ecx, edi    ; compara i com n (faz i - n e liga as flags)
    jg      fim         ; se i > n, sai do laço
    add     eax, ecx    ; total += i
    inc     ecx         ; i++
    jmp     laco        ; volta para o teste
fim:
    ret                 ; total volta em eax
```

O `cmp` é uma subtração que só liga as flags da ALU, sem guardar o resultado; o `jg` ("jump if greater") olha essas flags. É o mesmo padrão do salto condicional da CPU de brinquedo. Um detalhe curioso: compiladores otimizadores, como o Clang, reconhecem esse laço e o trocam pela fórmula n × (n + 1) / 2, sem laço nenhum.

## O mesmo programa, processadores diferentes

Em ARM64, a mesma função `soma` compilada com otimização vira `add w0, w0, w1` seguido de `ret`: outras instruções, outros registradores (`w0` e `w1` em vez de `edi` e `esi`), outros bytes. Por isso um executável de Windows para Intel não roda num Mac com chip M sem uma camada de tradução, e por isso o Java escolheu o bytecode: o `.class` é o mesmo em toda parte, e cada JVM traduz para o processador onde está.

## Endianness em Java

O Java esconde a ordem dos bytes na maior parte do tempo, mas ela aparece quando você converte números em bytes, por exemplo para gravar um arquivo binário ou mandar pela rede:

```java executar
import java.nio.ByteBuffer;
import java.nio.ByteOrder;

public class Ordem {
    static String hex(byte[] bytes) {
        StringBuilder sb = new StringBuilder();
        for (byte b : bytes) sb.append(String.format("%02x ", b));
        return sb.toString().trim();
    }

    public static void main(String[] args) {
        byte[] grande = ByteBuffer.allocate(4).putInt(0x12345678).array();
        byte[] pequeno = ByteBuffer.allocate(4).order(ByteOrder.LITTLE_ENDIAN).putInt(0x12345678).array();
        System.out.println(hex(grande));
        System.out.println(hex(pequeno));
    }
}
```

```saida
12 34 56 78
78 56 34 12
```

O padrão do `ByteBuffer` é **big-endian** (o byte mais significativo primeiro), que é a ordem usada nos protocolos de rede e no próprio formato `.class`.

## Por que ainda aprender assembly

Quase ninguém escreve sistemas inteiros em assembly: é lento de escrever, cheio de detalhes e preso a um processador. Mas ele ainda aparece no começo do boot de um sistema operacional, em trechos de drivers, em rotinas de criptografia e multimídia que precisam de cada ciclo, e em microcontroladores. E **ler** assembly é útil para qualquer programador: é o jeito de entender por que um código é rápido ou lento e o que o JIT da JVM está fazendo.

## Resumo

- Código de máquina são bytes; cada família de processadores tem sua ISA
- Assembly dá nomes às instruções; o montador traduz quase um para um
- No x86-64 System V, argumentos chegam em `rdi`, `rsi`... e o retorno sai em `rax`
- `-O0` guarda tudo na pilha; `-O2` usa registradores e instruções espertas
- Laços e `if` viram `cmp` mais salto condicional
- x86 e ARM são little-endian; rede e `.class` usam big-endian
