O `for` aprimorado, mais conhecido como **for-each**, percorre todos os elementos de um array ou de uma coleção sem índice e sem condição de parada. É o laço mais legível do Java e também o que esconde mais surpresas: a variável do laço é uma cópia, nem tudo que parece uma coleção pode ser percorrido, e remover elementos durante o laço às vezes lança exceção e às vezes não.

## Sintaxe

```java
for (Tipo elemento : arrayOuIterable) {
    // usa elemento
}
```

Lê-se "para cada elemento em ...". Funciona com **arrays** e com qualquer objeto que implemente **`Iterable`**, como `List`, `Set` e as outras coleções:

```java executar
int[] notas = {7, 9, 4};
int soma = 0;
for (int n : notas) {
    soma += n;
}
System.out.println(soma);
List<String> nomes = List.of("Ana", "Bia");
for (String nome : nomes) {
    System.out.println(nome.toUpperCase());
}
```

```saida
20
ANA
BIA
```

A variável pode ser declarada com `var` ou com `final`. O que não existe é índice: para saber a posição, percorrer de trás para a frente ou andar de dois em dois, use o `for` clássico.

> [!ANTES]
> O for-each chegou no Java 5, em 2004. Antes dele, percorrer uma lista exigia um iterador declarado à mão, `for (Iterator it = lista.iterator(); it.hasNext(); )`, e um cast em cada elemento, porque ainda não havia generics. O `removeIf`, que resolve a remoção durante o laço, veio depois, no Java 8.

> [!CONVERSA]
> **for clássico:** Eu sei onde estou o tempo todo: tenho o índice. Ando para trás, pulo de dois em dois, comparo um elemento com o vizinho.
>
> **for-each:** E eu não preciso de nada disso para o caso mais comum: passar por todos, um por um. Sem índice, sem condição, sem erro por um.
>
> **for clássico:** Sem índice, você nem consegue trocar um valor do array.
>
> **for-each:** Verdade, a minha variável é uma cópia. Mas, quando o elemento é um objeto, eu altero o objeto sem problema.
>
> **for clássico:** E se alguém remover um elemento da lista no meio do caminho?
>
> **for-each:** Aí eu reclamo com uma `ConcurrentModificationException`, quase sempre. Para remover, existe o `removeIf`.

## A variável é uma cópia

A cada volta, o elemento é **copiado** para a variável do laço. Atribuir outro valor a ela não muda o array. Mas, quando o elemento é uma referência, a cópia aponta para o **mesmo objeto**, e alterar o objeto altera o que está no array:

```java executar
int[] v = {1, 2, 3};
for (int x : v) {
    x = x * 10; //> Muda só a cópia; o array não fica sabendo.
}
System.out.println(Arrays.toString(v));
StringBuilder[] textos = {new StringBuilder("a"), new StringBuilder("b")};
for (StringBuilder sb : textos) {
    sb.append("!"); //> A cópia aponta para o mesmo objeto: a mudança aparece no array.
}
System.out.println(Arrays.toString(textos));
```

```saida
[1, 2, 3]
[a!, b!]
```

![Dois casos lado a lado: a cópia de um int muda sem afetar o array; a cópia de uma referência aponta para o mesmo objeto do array](/figuras/copia-no-for-each.svg "À esquerda, x é um número copiado. À direita, sb é uma seta copiada, que ainda aponta para o mesmo objeto.")

> [!LAPIS]
> Qual é a saída deste trecho?
>
> ```java
> String[] nomes = {"ana", "bia"};
> for (String n : nomes) {
>     n = n.toUpperCase();
> }
> System.out.println(nomes[0] + nomes[1]);
> ```
>
> **Resposta:** `anabia`. `toUpperCase` não altera a String, que é imutável: ele cria uma nova, e a atribuição troca só a cópia `n`. Para mudar o array, só com o `for` clássico: `nomes[i] = nomes[i].toUpperCase();`.

É a diferença entre mudar a variável (não afeta o array) e mudar o objeto para o qual ela aponta (afeta), um tema que volta com força no cargo Júnior, em [referências](/assistir/junior-t1-e01).

## Tipos compatíveis

O tipo da variável precisa aceitar cada elemento por uma conversão de atribuição: ampliação, *boxing* ou o próprio tipo:

```java executar
int[] inteiros = {1, 2};
for (long l : inteiros) System.out.print(l);
for (Integer i : inteiros) System.out.print(i);
for (double d : inteiros) System.out.print(d);
System.out.println();
```

```saida
12121.02.0
```

Reduzir não é permitido, e um `Map` **não** é `Iterable`: percorre-se a visão das chaves, dos valores ou dos pares:

```java nao-compila
long[] grandes = {1L, 2L};
for (int x : grandes) {
}
```

```java nao-compila
Map<String, Integer> estoque = Map.of("maçã", 3);
for (String chave : estoque) {
}
```

```java executar
Map<String, Integer> estoque = new TreeMap<>(Map.of("maçã", 3, "pera", 5));
for (Map.Entry<String, Integer> e : estoque.entrySet()) {
    System.out.println(e.getKey() + "=" + e.getValue());
}
for (var chave : estoque.keySet()) {
    System.out.println(chave);
}
```

```saida
maçã=3
pera=5
maçã
pera
```

Um array ou uma coleção `null` lança `NullPointerException` logo no começo do laço.

## Remover durante o laço

Remover elementos de uma coleção enquanto um for-each a percorre costuma lançar **`ConcurrentModificationException`**. O laço usa um iterador, e o iterador percebe que a lista mudou por fora dele:

```java executar
List<String> itens = new ArrayList<>(List.of("a", "b", "c"));
try {
    for (String s : itens) {
        if (s.equals("a")) {
            itens.remove(s);
        }
    }
} catch (ConcurrentModificationException e) {
    System.out.println("ConcurrentModificationException");
}
itens.removeIf(s -> s.equals("b"));
System.out.println(itens);
```

```saida
ConcurrentModificationException
[c]
```

O jeito certo é `removeIf`, como na penúltima linha, ou remover pelo próprio iterador (`iterator.remove()`).

> [!ERRO]
> Remover de uma coleção dentro de um for-each sobre ela mesma: `for (String s : itens) if (...) itens.remove(s);`. Na maioria dos casos a próxima volta lança `ConcurrentModificationException`; em alguns, como o abaixo, o laço termina cedo e pula elementos sem avisar. Use `removeIf`, ou um laço com o iterador e `it.remove()`.

> [!PENSE]
> No próximo trecho, o elemento removido é o do meio, o "b", de uma lista de três. Pela regra acima, deveria lançar a exceção. Será?

E aqui está a pegadinha clássica: remover o **penúltimo** elemento **não** lança exceção:

```java executar
List<String> itens = new ArrayList<>(List.of("a", "b", "c"));
for (String s : itens) {
    if (s.equals("b")) {
        itens.remove(s);
    }
}
System.out.println(itens);
```

```saida
[a, c]
```

Depois de remover o "b", a lista tem 2 elementos e o iterador já está na posição 2. O teste "ainda há próximo?" compara a posição com o tamanho, dá falso, e o laço termina sem nunca chegar à verificação que lançaria a exceção. O "c" nem é visitado. A exceção é uma ajuda de depuração, não uma garantia.

> [!MATEMATICA]
> O iterador guarda um cursor, a posição do próximo elemento, e pergunta `cursor != tamanho` antes de cada volta. Na lista `[a, b, c]`, depois de entregar o "b" o cursor vale 2. Removido o "b", o tamanho cai de 3 para 2, e a pergunta `2 != 2` dá falso: o laço termina sem chamar o `next()`, que é quem lança a exceção. Isso só acontece quando se remove o elemento logo antes do último, porque é o único caso em que o cursor alcança o novo tamanho exatamente.

> [!IA]
> Peça para "remover os itens inválidos de uma lista" e é comum a IA escrever um for-each com `lista.remove(item)` dentro. Às vezes funciona no teste, com poucos itens, e quebra em produção. Peça explicitamente `removeIf` ou um iterador, e teste com o item a remover no começo, no meio e no fim.

> [!ENGENHARIA]
> Prefira o for-each sempre que não precisar do índice: sem contador, não há erro por um, e o laço diz exatamente o que faz, "para cada elemento". É uma das recomendações do livro *Effective Java*, de Joshua Bloch, um dos autores das coleções do Java.

> [!PROVA]
> Arrays não lançam `ConcurrentModificationException`: eles têm tamanho fixo e não podem ser "modificados estruturalmente". E coleções imutáveis, como as de `List.of`, lançam `UnsupportedOperationException` em qualquer tentativa de remoção, dentro ou fora do laço.

## Na IDE

- **Gerar o laço.** Digite `iter` e aperte **Tab**: o IntelliJ escreve um for-each sobre a coleção ou o array mais provável do contexto.
- **Precisou do índice?** Com o cursor no `for`, **Alt + Enter** oferece trocar o for-each por um `for` com índice, e o caminho contrário quando o índice só serve para ler.
- **Remover com segurança.** Num laço com iterador que só remove elementos, a IDE costuma sugerir trocá-lo por `removeIf`.

## Por baixo dos panos

O for-each é açúcar sintático, e a JLS 14.14.2 mostra a tradução exata. Para um array, o `javac` gera um `for` clássico com um índice escondido e uma cópia da referência ao array:

```java
int[] tmp = notas;
for (int i = 0; i < tmp.length; i++) {
    int n = tmp[i];
    // corpo
}
```

Para um `Iterable`, gera um laço com iterador:

```java
for (Iterator<String> it = nomes.iterator(); it.hasNext(); ) {
    String nome = it.next();
    // corpo
}
```

Daí vêm todas as regras: a variável é uma cópia porque é preenchida a cada volta; o `Map` não funciona porque não tem `iterator()`; e a `ConcurrentModificationException` sai do `next()`, que confere um contador de modificações da lista (o `modCount`). Como o `hasNext()` não confere nada, remover o penúltimo elemento passa despercebido.

## Resumo para a prova

- Funciona com arrays e com `Iterable`; `Map` não é `Iterable` (use `entrySet`, `keySet` ou `values`)
- A variável é uma cópia: reatribuí-la não muda o array; alterar o objeto apontado, sim
- Tipo da variável: o mesmo, uma ampliação ou boxing; nunca redução
- Sem índice, sem ordem inversa, sem passo diferente de 1
- Remover da coleção dentro do laço costuma lançar `ConcurrentModificationException`, mas remover o penúltimo não lança
- Use `removeIf` ou `iterator.remove()` para remover durante a iteração
- Array ou coleção `null` lança `NullPointerException`
