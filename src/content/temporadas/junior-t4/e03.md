Os métodos `default` trouxeram para Java um pedaço de herança múltipla: uma classe pode receber código pronto de várias interfaces. E com ele, um problema antigo, o **diamante**: se duas interfaces oferecem o mesmo método com corpos diferentes, qual a classe herda? Java resolve com três regras simples, aplicadas em ordem, e a prova cobra cada uma delas, além da sintaxe para escolher uma versão à mão.

## O conflito e a sintaxe `Interface.super`

Quando duas interfaces sem relação entre si trazem o mesmo método `default`, a classe que implementa as duas **é obrigada** a sobrescrevê-lo. Senão, não compila:

```java nao-compila
interface Cantor {
    default String apresentar() { return "eu canto"; }
}

interface Dancarino {
    default String apresentar() { return "eu danço"; }
}

class Artista implements Cantor, Dancarino {
}
```

Na sobrescrita, a classe pode aproveitar qualquer uma das versões, ou as duas, com `NomeDaInterface.super.metodo()`:

```java executar
interface Cantor {
    default String apresentar() { return "eu canto"; }
}

interface Dancarino {
    default String apresentar() { return "eu danço"; }
}

class Artista implements Cantor, Dancarino {
    @Override
    public String apresentar() {
        return Cantor.super.apresentar() + " e " + Dancarino.super.apresentar();
    }
}

System.out.println(new Artista().apresentar());
```

```saida
eu canto e eu danço
```

A sintaxe só vale para interfaces que a classe implementa **diretamente**. Não dá para pular um nível e chamar a versão de uma interface avó:

```java nao-compila
interface A {
    default String f() { return "A"; }
}

interface B extends A {
    default String f() { return "B"; }
}

class C implements B {
    public String f() { return A.super.f(); }
}
```

## As três regras

**1. A classe sempre vence.** Um método declarado na classe ou herdado de uma superclasse tem prioridade sobre qualquer `default` de interface:

```java executar
interface Saudavel {
    default String cumprimentar() { return "oi (interface)"; }
}

class Pessoa {
    public String cumprimentar() { return "olá (classe)"; }
}

class Aluno extends Pessoa implements Saudavel {
}

System.out.println(new Aluno().cumprimentar());
```

```saida
olá (classe)
```

Um cuidado: o método da superclasse passa a implementar o da interface, e por isso precisa ser `public`. Se `Pessoa` declarasse `cumprimentar()` sem modificador, `Aluno` não compilaria, pelo mesmo motivo de sempre: o acesso não pode ficar mais restrito que o `public` da interface.

**2. A interface mais específica vence.** Se uma interface estende a outra e redefine o método, a versão da subinterface ganha, mesmo que a classe declare as duas:

```java executar
interface Animal {
    default String som() { return "..."; }
}

interface Cachorro extends Animal {
    default String som() { return "au"; }
}

class Vira implements Animal, Cachorro {
}

System.out.println(new Vira().som());
```

```saida
au
```

No diamante clássico, em que duas interfaces herdam o mesmo `default` de uma terceira **sem redefini-lo**, não há conflito nenhum: só existe uma versão.

```java executar
interface A {
    default String quem() { return "A"; }
}

interface B extends A { }
interface C extends A { }

class D implements B, C { }

System.out.println(new D().quem());
```

```saida
A
```

**3. Se nada resolve, a classe resolve.** Qualquer outro caso de duas versões candidatas obriga a classe a sobrescrever. Isso inclui um `default` numa interface e um método **abstrato** com a mesma assinatura em outra: o compilador não escolhe o `default` por conta própria.

```java nao-compila
interface Ligavel {
    default void ligar() { }
}

interface Configuravel {
    void ligar();
}

class Aparelho implements Ligavel, Configuravel {
}
```

> [!PROVA]
> Para cada classe que implementa interfaces com `default`, aplique na ordem: algum método da classe ou de uma superclasse tem essa assinatura? (então ele vence); uma das interfaces estende a outra e redefine o método? (então a mais específica vence); senão, a classe precisa sobrescrever, e pode usar `X.super.m()` só com interfaces diretas. Métodos `static` de interface nunca conflitam, porque não são herdados.

Há ainda um caso sem solução: duas interfaces com o mesmo método e **tipos de retorno incompatíveis**. Nenhuma implementação satisfaz as duas, e a classe não pode implementar ambas:

```java nao-compila
interface Medidor {
    int medir();
}

interface Sensor {
    double medir();
}

class Termometro implements Medidor, Sensor {
    public int medir() { return 1; }
}
```

## Por baixo dos panos

O compilador confere tudo isso, mas a JVM também precisa resolver o conflito na execução, porque as interfaces podem mudar depois que a classe foi compilada. Na ligação, ela procura o método na classe e nas superclasses; se não encontrar, procura entre as interfaces o método **mais específico** que não seja abstrato, as mesmas regras da linguagem, descritas na especificação da JVM.

Isso cria um problema de compatibilidade. Imagine que sua classe implementa `Cantor` e `Dancarino`, mas só `Cantor` tinha `apresentar()` quando você compilou. Se uma versão nova da biblioteca acrescentar `apresentar()` também em `Dancarino`, sua classe não recompilada passa a ter um conflito que ninguém resolveu, e a chamada lança `IncompatibleClassChangeError` em tempo de execução. Já o `Cantor.super.apresentar()` vira um `invokespecial` que aponta direto para o método da interface, sem consultar tabela nenhuma.

## Resumo para a prova

- Duas interfaces sem relação com o mesmo `default`: a classe é obrigada a sobrescrever
- `Interface.super.metodo()` chama a versão de uma interface direta
- Regra 1: método da classe ou da superclasse vence o `default`, e precisa ser `public`
- Regra 2: a subinterface que redefine o método vence a interface mãe
- Diamante sem redefinição no meio: não há conflito
- `default` contra abstrato de mesma assinatura: a classe precisa implementar
- Retornos incompatíveis para a mesma assinatura: impossível implementar as duas
- Métodos `static` de interface não conflitam
