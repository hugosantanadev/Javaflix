No episódio anterior, cada constante era só um nome. Mas um enum é uma classe, e as constantes são objetos: podem ter **campos**, **construtores** e **métodos**, e cada uma pode até ter um **comportamento próprio**. Com isso, um enum deixa de ser uma lista de rótulos e vira um tipo rico, como o planeta que sabe a própria gravidade ou a operação matemática que sabe se calcular.

## Campos, construtor e métodos

Os argumentos entre parênteses depois de cada constante vão para o construtor. Quando há membros depois das constantes, a lista **termina com ponto e vírgula**:

```java executar
enum Planeta {
    MERCURIO(3.7), TERRA(9.8), JUPITER(24.8); //> Os argumentos vão para o construtor; o ponto e vírgula fecha a lista.

    private final double gravidade;

    Planeta(double gravidade) {
        this.gravidade = gravidade;
    }

    double peso(double massaKg) {
        return Math.round(massaKg * gravidade * 10) / 10.0; //> Cada constante usa a própria gravidade.
    }
}

for (Planeta p : Planeta.values()) {
    System.out.println(p + ": " + p.peso(70) + " N");
}
```

```saida
MERCURIO: 259.0 N
TERRA: 686.0 N
JUPITER: 1736.0 N
```

Sem o ponto e vírgula, o compilador não sabe onde terminam as constantes:

```java nao-compila
enum Cor {
    VERMELHO, VERDE

    String hex() {
        return "#000";
    }
}
```

> [!ERRO]
> O erro do ponto e vírgula esquecido é confuso: o `javac` reclama de `',', '}', or ';' expected` na linha da última constante e depois aponta mais erros no método, que está certo. Quando um enum com membros dá vários erros de uma vez, olhe primeiro o fim da lista de constantes.

O construtor é sempre `private`, escrito ou não. Declará-lo `public` ou `protected` não compila, porque ninguém de fora pode criar constantes:

```java nao-compila
enum Moeda {
    REAL("R$");

    private final String simbolo;

    public Moeda(String simbolo) {
        this.simbolo = simbolo;
    }
}
```

## Quando o construtor roda

Cada constante é criada uma vez, quando o enum é inicializado, no primeiro uso, como qualquer classe no [episódio de inicialização](/assistir/junior-t1-e05). Todas as constantes nascem juntas, na ordem de declaração:

```java executar
enum Nivel {
    BAIXO, MEDIO, ALTO;

    Nivel() {
        System.out.println("criando " + name());
    }
}

System.out.println("antes");
Nivel n = Nivel.ALTO;
Nivel m = Nivel.MEDIO;
System.out.println("depois: " + n + " " + m);
```

```saida
antes
criando BAIXO
criando MEDIO
criando ALTO
depois: ALTO MEDIO
```

> [!PENSE]
> O código usa `ALTO` e depois `MEDIO`. Quantas vezes o construtor vai rodar ao todo, e para quais constantes?

Usar `ALTO` disparou a criação das três, e usar `MEDIO` depois não criou nada. Um detalhe que a prova explora: o construtor não pode ler campos `static` do próprio enum (a não ser constantes de compilação), porque as constantes são criadas **antes** dos outros campos `static` receberem valor.

> [!PERGUNTAS]
> **P:** Então como monto um mapa `static` de código para constante?
>
> **R:** Num bloco `static` **depois** das declarações, que roda quando as constantes já existem: `static { for (Status s : values()) POR_CODIGO.put(s.codigo, s); }`. Ou, com poucas constantes, um laço em `values()` dentro do método de busca, como `porCodigo` faz logo abaixo.

## Comportamento por constante

Uma constante pode ter um **corpo próprio**, entre chaves, sobrescrevendo métodos do enum. Combinado com um método `abstract`, isso obriga cada constante a dar a sua implementação:

```java executar
enum Operacao {
    SOMA("+") {
        int aplicar(int a, int b) { return a + b; }
    },
    SUBTRACAO("-") {
        int aplicar(int a, int b) { return a - b; }
    },
    MULTIPLICACAO("*") {
        int aplicar(int a, int b) { return a * b; }
    };

    private final String simbolo;

    Operacao(String simbolo) {
        this.simbolo = simbolo;
    }

    abstract int aplicar(int a, int b);

    String mostrar(int a, int b) {
        return a + " " + simbolo + " " + b + " = " + aplicar(a, b);
    }
}

for (Operacao op : Operacao.values()) {
    System.out.println(op.mostrar(6, 3));
}
```

```saida
6 + 3 = 9
6 - 3 = 3
6 * 3 = 18
```

![O enum Operacao com o método abstrato aplicar e três constantes, cada uma uma subclasse anônima com a sua versão](/figuras/constante-com-corpo.svg "Constante com corpo é uma subclasse anônima do enum.")

> [!CONVERSA]
> **switch:** Eu resolvo isso de fora: `switch (op) { case SOMA -> a + b; ... }`. Um lugar só para todas as operações.
>
> **Corpo por constante:** E se alguém acrescentar `DIVISAO` amanhã? Você esquece, e o `default` devolve qualquer coisa.
>
> **switch:** No `switch` expressão sem `default`, o compilador me avisa.
>
> **Corpo por constante:** Com o método `abstract`, o aviso vem na própria constante, e o código de cada operação mora junto dela. Os dois funcionam; o que muda é onde o código fica.

Se alguma constante esquecer de implementar o método abstrato, não compila:

```java nao-compila
enum Forma {
    CIRCULO {
        double area(double r) { return 3.14 * r * r; }
    },
    QUADRADO;

    abstract double area(double x);
}
```

## Enums com interfaces

Enums não podem estender classes, mas podem implementar interfaces, e é comum darem a si mesmos um método `static` de busca por um código próprio:

```java executar
interface Descrevivel {
    String descricao();
}

enum Status implements Descrevivel {
    ATIVO('A', "em uso"), BLOQUEADO('B', "suspenso"), CANCELADO('C', "encerrado");

    private final char codigo;
    private final String texto;

    Status(char codigo, String texto) {
        this.codigo = codigo;
        this.texto = texto;
    }

    public String descricao() {
        return name().toLowerCase() + " (" + texto + ")";
    }

    static Status porCodigo(char c) {
        for (Status s : values()) {
            if (s.codigo == c) return s;
        }
        throw new IllegalArgumentException("código inválido: " + c);
    }
}

Descrevivel d = Status.porCodigo('B');
System.out.println(d.descricao());
System.out.println(Status.porCodigo('C') == Status.CANCELADO);
```

```saida
bloqueado (suspenso)
true
```

> [!PROVA]
> Nas questões de enum com membros, confira: há ponto e vírgula depois da última constante? O construtor é `public` ou `protected` (proibido)? Toda constante passa argumentos compatíveis com algum construtor? Se há método `abstract`, toda constante o implementa? E lembre que os campos de um enum, se não forem `final`, podem ser alterados, e a mudança vale para todos que usam aquela constante.

> [!ANTES]
> Antes dos enums, o padrão *typesafe enum* do Effective Java (primeira edição, 2001) fazia isso à mão: uma classe `final` com construtor privado e um campo `public static final` para cada valor. Funcionava, mas exigia cuidado com serialização para não criar cópias. O enum do Java 5 é esse padrão com suporte da linguagem, e o enum de uma constante só virou o jeito recomendado de escrever um *singleton*.

> [!MATEMATICA]
> O enum com campos substitui uma tabela. Com 8 planetas e uma gravidade cada, a alternativa seria um array paralelo `double[] gravidades` indexado pelo `ordinal()`: 8 valores que precisam estar na mesma ordem das constantes, para sempre. Inserir um planeta no meio exige deslocar 8 − k valores. Com o campo no enum, cada valor fica ao lado da sua constante, e inserir uma constante não mexe em nenhuma outra.

> [!IA]
> Pedindo um enum "com código", a IA às vezes monta o mapa de busca dentro do construtor, `POR_CODIGO.put(codigo, this)`. Se o mapa for um campo `static`, isso não compila ou, por um método intermediário, lança exceção na carga do enum. Peça o mapa preenchido num bloco `static` depois dos campos.

## Na IDE

- **Gerar o construtor.** Depois de declarar os campos `final`, **Alt + Insert**, *Constructor*, gera o construtor sem `public`, como o enum exige.
- **Implementar por constante.** Com um método `abstract` no enum, **Alt + Enter** numa constante sublinhada oferece *Implement methods* só para ela.
- **Ver as subclasses.** Na janela *Structure* (**Alt + 7**), as constantes com corpo aparecem com uma seta que se expande para os métodos sobrescritos.

## Por baixo dos panos

Uma constante com corpo próprio vira uma **subclasse anônima** do enum, com nome como `Operacao$1`. É por isso que `getClass()` de uma constante pode não ser o próprio enum. Para descobrir o enum, existe `getDeclaringClass()`:

```java executar
enum Animal {
    GATO,
    CAO {
        @Override public String toString() { return "cachorro"; }
    };
}

System.out.println(Animal.GATO.getClass() == Animal.class);
System.out.println(Animal.CAO.getClass() == Animal.class);
System.out.println(Animal.CAO.getDeclaringClass() == Animal.class);
System.out.println(Animal.CAO + " " + Animal.CAO.name());
```

```saida
true
false
true
cachorro CAO
```

O `toString` pode ser sobrescrito, mas o `name()` é `final` em `Enum`: ele sempre devolve o nome declarado, e é o que o `valueOf` usa. Um enum de uma constante só é a forma mais segura de escrever um *singleton*: a JVM garante que a constante é criada uma única vez, com a trava de inicialização de classe, e nem a serialização nem a reflexão conseguem criar uma segunda.

## Resumo para a prova

- Constantes podem receber argumentos, que vão para o construtor
- Com membros depois das constantes, a lista termina com `;`
- O construtor é sempre `private`; `public` ou `protected` não compila
- Todas as constantes são criadas juntas, no primeiro uso do enum
- O construtor não pode ler campos `static` não constantes do próprio enum
- Constantes podem ter corpo próprio; método `abstract` obriga todas a implementá-lo
- Enums podem implementar interfaces
- Constante com corpo é uma subclasse anônima: use `getDeclaringClass()`; `name()` é `final`
