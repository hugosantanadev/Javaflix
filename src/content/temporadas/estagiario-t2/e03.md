Por que `byte a = 1, b = 2; byte c = a + b;` não compila? Por que `(double) (1 / 2)` dá `0.0`? E por que um `int` grande guardado num `float` muda de valor sem nenhum aviso? Tudo isso sai de duas regras: a **promoção numérica**, que o Java aplica sozinho em toda conta, e o **cast**, que você escreve quando quer forçar uma conversão.

## Ampliação: as conversões automáticas

Um valor pode ir para um tipo "maior" sem cast. É a **conversão de ampliação** (*widening*):

```text
byte → short → int → long → float → double
                ↑
              char
```

`long l = 10;`, `double d = 'A';` e `float f = 10L;` compilam sem cast. O `char` entra pelo `int`: ele cabe num `int`, mas **não** num `short` (o `char` vai de 0 a 65.535, e o `short` de −32.768 a 32.767), nem o `short` cabe num `char`, porque o `char` não tem negativos.

## A promoção numérica

Antes de uma operação aritmética, o Java converte os operandos para um tipo comum (JLS 5.6), seguindo esta ordem:

1. Se algum operando é `double`, o outro vira `double`.
2. Senão, se algum é `float`, o outro vira `float`.
3. Senão, se algum é `long`, o outro vira `long`.
4. Senão, **os dois viram `int`**.

A regra 4 é a que pega: `byte`, `short` e `char` nunca são operados como eles mesmos. Somar dois `byte` dá `int`.

```java executar
byte a = 10, b = 20;
int soma = a + b;
short s = 5;
char c = 'A';
System.out.println(s + c);
long l = 5;
float f = 2.5f;
System.out.println(l * f);
System.out.println(1 / 2 + 1.0 / 2);
System.out.println(soma);
```

```saida
70
12.5
0.5
30
```

`s + c` é 5 + 65 = 70, um `int`. `l * f` é `float`, porque `float` está acima de `long` na ordem, mesmo tendo menos bits. E em `1 / 2 + 1.0 / 2`, cada divisão é promovida separadamente: a primeira é inteira (0) e a segunda é `double` (0.5).

Por isso esta linha não compila:

```java nao-compila
byte a = 1, b = 2;
byte c = a + b;
```

A exceção é quando a conta inteira é uma **constante de compilação** que cabe no tipo. Com `final` e valores constantes, o compilador calcula 3, vê que cabe num `byte` e aceita:

```java compila
final byte a = 1, b = 2;
byte c = a + b;
```

## Cast: a conversão forçada

Para ir de um tipo maior para um menor (*narrowing*), é preciso um **cast** explícito, e o programador assume o risco:

```java executar
System.out.println((int) 3.99);
System.out.println((int) -3.99);
System.out.println((byte) 130);
System.out.println((short) 70000);
System.out.println((char) 66);
System.out.println((int) 'z');
System.out.println((long) 1e19);
```

```saida
3
-3
-126
4464
B
122
9223372036854775807
```

De ponto flutuante para inteiro, o cast **trunca em direção a zero** e, se o valor não couber, **satura** no limite do tipo (o `1e19` virou `Long.MAX_VALUE`). Entre inteiros, o cast **descarta os bits de cima**: 130 em 8 bits é −126 e 70.000 em 16 bits é 4.464 (70.000 − 65.536), como você viu no episódio de [complemento de dois](/assistir/aprendiz-t3-e02).

O cast tem precedência alta: vale só para o operando imediatamente à direita. Os parênteses decidem o que é convertido:

```java executar
double x = 3.7;
System.out.println((int) x + 0.5);
System.out.println((int) (x + 0.5));
System.out.println((double) 1 / 2);
System.out.println((double) (1 / 2));
```

```saida
3.5
4
0.5
0.0
```

`(double) 1 / 2` converte o 1 e depois divide em `double`: 0.5. `(double) (1 / 2)` divide primeiro em inteiros (0) e converte o 0 tarde demais.

## Ampliar também pode perder

As setas da ampliação não garantem exatidão. Um `float` tem só 24 bits de precisão, e um `double`, 53 (o [IEEE 754](/assistir/aprendiz-t3-e03)). Um `int` grande vai para `float` arredondado, e um `long` grande vai para `double` arredondado, **sem cast e sem aviso**:

```java executar
int grande = 123456789;
float f = grande;
System.out.println(f);
System.out.println((int) f);
long l = Long.MAX_VALUE;
double d = l;
System.out.println(d);
System.out.println(d == l);
```

```saida
1.2345679E8
123456792
9.223372036854776E18
true
```

O 123.456.789 virou 123.456.792 no `float`. O `println` mostra `1.2345679E8` porque imprime o menor número de dígitos que identifica aquele `float`; convertendo de volta para `int`, aparece o valor guardado de fato. E `d == l` dá `true` porque, na comparação, o `long` também é promovido para `double` e sofre o mesmo arredondamento.

> [!PROVA]
> A promoção acontece **na operação**, não na atribuição. Em `long x = 1000 * 60 * 60 * 24 * 30;`, a multiplicação é toda feita em `int`, estoura, e só o resultado errado vira `long`. Basta um `L` num dos fatores para a conta inteira ser feita em `long`.

## Por baixo dos panos

A regra 4 da promoção não é capricho: ela espelha a JVM. A pilha de operandos da JVM trabalha com valores de 32 bits, e o conjunto de instruções tem `iadd`, `ladd`, `fadd` e `dadd`, mas **não** tem soma de `byte`, `short` ou `char`. Esses tipos existem nos campos e nos arrays; ao serem carregados para uma conta, viram `int`. Somar dois `byte` é, literalmente, um `iadd`.

Os casts viram instruções de conversão: `i2b`, `i2s` e `i2c` cortam um `int` para 8 ou 16 bits; `i2l` amplia com extensão de sinal; `l2i` descarta os 32 bits de cima; `d2i` trunca e satura, exatamente como a especificação da JVM define. Ampliações como `int` para `long` também geram instrução (`i2l`), porque o tamanho na pilha muda; já `byte` para `int` não gera nada, porque o valor já estava na pilha como `int`.

## Resumo para a prova

- Ampliação automática: `byte → short → int → long → float → double`, e `char → int`
- `char` e `short` não convertem entre si sem cast
- Em contas, `byte`, `short` e `char` viram `int`; se houver `long`, `float` ou `double`, vence o maior da ordem
- `byte c = a + b;` não compila, a menos que `a` e `b` sejam constantes `final` e o resultado caiba
- Cast de ponto flutuante para inteiro trunca em direção a zero e satura; entre inteiros, descarta os bits de cima
- O cast vale só para o operando seguinte: `(double) 1 / 2` é 0.5; `(double) (1 / 2)` é 0.0
- `int` para `float` e `long` para `double` compilam sem cast, mas podem arredondar
- O estouro acontece na conta, antes da atribuição
