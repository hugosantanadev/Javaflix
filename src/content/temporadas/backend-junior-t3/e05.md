Uma transferência tira dinheiro de uma conta e põe em outra. Se o sistema cair entre os dois passos, o dinheiro some. Uma venda baixa o estoque; se duas vendas do último item acontecerem ao mesmo tempo, as duas podem passar. As **transações** resolvem os dois problemas: agrupam comandos num bloco que acontece inteiro ou não acontece, e controlam o que cada transação enxerga do trabalho das outras. Quase todo defeito de "valor errado no banco que ninguém consegue reproduzir" é um problema de transação ou de concorrência, e entender os níveis de isolamento é o que permite encontrá-lo.

## ACID

As garantias de uma transação têm um nome clássico:

| Letra | Garantia | Na prática |
|---|---|---|
| **A**tomicidade | Tudo ou nada | Se um comando falha, os anteriores da mesma transação são desfeitos |
| **C**onsistência | As regras valem no fim | Restrições como `CHECK` e chaves estrangeiras nunca ficam violadas |
| **I**solamento | Transações simultâneas não se atrapalham | O nível de isolamento define o quanto |
| **D**urabilidade | O que foi confirmado não se perde | Depois do `COMMIT`, nem uma queda de energia desfaz |

Uma transação começa com `BEGIN` (ou `START TRANSACTION`) e termina com `COMMIT`, que confirma, ou `ROLLBACK`, que desfaz tudo. No JDBC, cada comando é uma transação por conta própria, o *autocommit*, até que se chame `setAutoCommit(false)`, como no [episódio de JDBC](/assistir/senior-t5-e05); no Spring, a anotação `@Transactional` faz isso por você, assunto da temporada de JPA.

## Atomicidade

A transferência de R$ 150 da Ana, que tem R$ 100, para o Bruno. A tabela tem `CHECK (saldo >= 0)`:

```text
T1: UPDATE contas SET saldo = saldo + 150 WHERE id = 2  ->  1 linha(s)
T1: UPDATE contas SET saldo = saldo - 150 WHERE id = 1  ->  ERRO: Check constraint violation
T1: ROLLBACK
T1: SELECT titular || ' ' || saldo FROM contas ORDER BY id  ->  Ana 100.00, Bruno 50.00
```

O crédito do Bruno já tinha sido feito, e o `ROLLBACK` o desfez: ninguém ganhou dinheiro do nada. As saídas desta aula foram obtidas no H2, com duas conexões, `A` e `B`, executando comandos intercalados, como dois usuários ao mesmo tempo.

## O problema da concorrência

O estoque do produto 7 tem 5 unidades, e dois clientes compram ao mesmo tempo. O código de cada venda lê o estoque, subtrai 1 no Java e grava o resultado:

```text
A: SELECT quantidade FROM estoque WHERE produto_id = 7  ->  5
B: SELECT quantidade FROM estoque WHERE produto_id = 7  ->  5
A: UPDATE estoque SET quantidade = 4 WHERE produto_id = 7  ->  1 linha(s)
A: COMMIT
B: UPDATE estoque SET quantidade = 4 WHERE produto_id = 7  ->  1 linha(s)
B: COMMIT
A: SELECT quantidade FROM estoque WHERE produto_id = 7  ->  4
```

Duas vendas, e o estoque baixou uma unidade só: a **atualização perdida**. Nenhum erro, nenhum aviso; só um número errado que aparece semanas depois, no inventário. Há três formas de evitá-la.

### 1. Deixar a conta para o banco

Se o `UPDATE` calcula a partir do valor atual, em vez de gravar um valor calculado no Java, o banco serializa as duas escritas: a segunda **espera** a primeira terminar e trabalha sobre o valor novo.

```text
A: UPDATE estoque SET quantidade = quantidade - 1 WHERE produto_id = 8  ->  1 linha(s)
(B está esperando: true)
A: COMMIT
B: UPDATE estoque SET quantidade = quantidade - 1 WHERE produto_id = 8  ->  1 linha(s)
B: COMMIT
A: SELECT quantidade FROM estoque WHERE produto_id = 8  ->  3
```

Somando a condição de negócio, `... WHERE produto_id = 8 AND quantidade >= 1`, o próprio `UPDATE` vira a verificação: se ele afetar 0 linhas, o estoque acabou.

### 2. Bloquear na leitura

Quando a regra é complexa demais para um `UPDATE`, o `SELECT ... FOR UPDATE` lê **e bloqueia** a linha até o fim da transação. Quem tentar o mesmo espera:

```text
A: SELECT quantidade FROM estoque WHERE produto_id = 7 FOR UPDATE  ->  4
(B está esperando: true)
A: UPDATE estoque SET quantidade = 3 WHERE produto_id = 7  ->  1 linha(s)
A: COMMIT
B: SELECT quantidade FROM estoque WHERE produto_id = 7 FOR UPDATE  ->  3
B: UPDATE estoque SET quantidade = 2 WHERE produto_id = 7  ->  1 linha(s)
B: COMMIT
```

O B só leu depois que o A confirmou, e já viu o 3. É o **bloqueio pessimista**: parte-se do princípio de que haverá conflito.

### 3. Detectar o conflito na gravação

O **bloqueio otimista** não bloqueia nada: cada linha tem uma coluna `versao`, e a gravação só acontece se a versão ainda for a que foi lida. Quem perdeu a corrida descobre pelo número de linhas afetadas, relê e tenta de novo:

```java executar
import java.util.HashMap;
import java.util.Map;

public class Otimista {
    record Linha(int quantidade, int versao) {}

    static final Map<Integer, Linha> ESTOQUE = new HashMap<>();

    /** UPDATE estoque SET quantidade = ?, versao = versao + 1 WHERE produto_id = ? AND versao = ? */
    static int atualizar(int produto, int novaQuantidade, int versaoLida) {
        Linha atual = ESTOQUE.get(produto);
        if (atual.versao() != versaoLida) return 0;
        ESTOQUE.put(produto, new Linha(novaQuantidade, atual.versao() + 1));
        return 1;
    }

    public static void main(String[] args) {
        ESTOQUE.put(7, new Linha(5, 1));
        int lidoA = ESTOQUE.get(7).quantidade();
        int lidoB = ESTOQUE.get(7).quantidade();
        ESTOQUE.put(7, new Linha(lidoA - 1, 1));
        ESTOQUE.put(7, new Linha(lidoB - 1, 1));
        System.out.println("ler, calcular e gravar: " + ESTOQUE.get(7).quantidade() + " (duas vendas, uma perdida)");

        ESTOQUE.put(7, new Linha(5, 1));
        Linha vistaPorA = ESTOQUE.get(7);
        Linha vistaPorB = ESTOQUE.get(7);
        System.out.println("A grava: " + atualizar(7, vistaPorA.quantidade() - 1, vistaPorA.versao()) + " linha");
        System.out.println("B grava: " + atualizar(7, vistaPorB.quantidade() - 1, vistaPorB.versao()) + " linhas, versão mudou");
        Linha releitura = ESTOQUE.get(7);
        System.out.println("B relê " + releitura + " e grava: " + atualizar(7, releitura.quantidade() - 1, releitura.versao()) + " linha");
        System.out.println("final: " + ESTOQUE.get(7));
    }
}
```

```saida
ler, calcular e gravar: 4 (duas vendas, uma perdida)
A grava: 1 linha
B grava: 0 linhas, versão mudou
B relê Linha[quantidade=4, versao=2] e grava: 1 linha
final: Linha[quantidade=3, versao=3]
```

É o que o JPA faz com a anotação `@Version`: um `UPDATE` que afeta 0 linhas vira uma `OptimisticLockException`. O otimista é melhor quando conflitos são raros, como na edição de um cadastro; o pessimista, quando são frequentes, como no último ingresso de um show.

## Níveis de isolamento

O padrão SQL define quatro níveis, conforme as anomalias que cada um permite:

| Nível | Leitura suja | Leitura não repetível | Fantasma |
|---|---|---|---|
| `READ UNCOMMITTED` | possível | possível | possível |
| `READ COMMITTED` | não | possível | possível |
| `REPEATABLE READ` | não | não | possível no padrão |
| `SERIALIZABLE` | não | não | não |

- **Leitura suja**: ver uma alteração que ainda não foi confirmada, e que pode ser desfeita.
- **Leitura não repetível**: ler a mesma linha duas vezes na transação e obter valores diferentes, porque outra transação a alterou e confirmou no meio.
- **Fantasma**: repetir uma consulta e ver linhas novas, inseridas por outra transação.

O padrão do PostgreSQL, do Oracle e do H2 é o **READ COMMITTED**; o do MySQL com InnoDB é o **REPEATABLE READ**. No PostgreSQL, o `READ UNCOMMITTED` funciona como `READ COMMITTED`, e o `REPEATABLE READ` também impede fantasmas.

### READ COMMITTED

Cada comando enxerga o que estava confirmado quando **ele** começou. Na mesma transação, duas leituras podem divergir:

```text
A: SELECT saldo FROM contas WHERE id = 1  ->  100.00
B: UPDATE contas SET saldo = 80 WHERE id = 1  ->  1 linha(s)
B: COMMIT
A: SELECT saldo FROM contas WHERE id = 1  ->  80.00
```

Num relatório que lê o saldo no começo e soma movimentos no fim, essa diferença produz totais que não fecham.

### REPEATABLE READ

A transação enxerga o que estava confirmado quando **ela** começou, do início ao fim, como uma fotografia:

```text
R: SELECT saldo FROM contas WHERE id = 1  ->  80.00
B: UPDATE contas SET saldo = 60 WHERE id = 1  ->  1 linha(s)
B: COMMIT
R: SELECT saldo FROM contas WHERE id = 1  ->  80.00
R: UPDATE contas SET saldo = saldo - 10 WHERE id = 1  ->  ERRO: Deadlock detected. The current transaction was rolled back.
```

A segunda leitura repetiu os 80, embora o valor confirmado já fosse 60. E quando R tentou alterar a linha que mudou depois da sua fotografia, o banco recusou: gravar ali perderia a atualização de B. O H2 descreve a recusa como um impasse; o PostgreSQL, como `could not serialize access due to concurrent update`. Nos dois casos, a transação foi desfeita e a aplicação precisa **repeti-la do começo**. Quem usa `REPEATABLE READ` ou `SERIALIZABLE` precisa estar preparado para isso.

## Impasses

Duas transações que bloqueiam linhas em ordens opostas podem ficar esperando uma pela outra para sempre:

```text
A: UPDATE contas SET saldo = saldo + 1 WHERE id = 1  ->  1 linha(s)
B: UPDATE contas SET saldo = saldo + 1 WHERE id = 2  ->  1 linha(s)
     (A tenta a conta 2 e fica esperando B)
B: UPDATE contas SET saldo = saldo + 1 WHERE id = 1  ->  ERRO: Deadlock detected. The current transaction was rolled back.
A: UPDATE contas SET saldo = saldo + 1 WHERE id = 2  ->  1 linha(s)
```

O banco detecta o ciclo, escolhe uma vítima, desfaz a transação dela e deixa a outra seguir. É o mesmo impasse das [threads do Java](/assistir/senior-t2-e05), com a diferença de que o banco o resolve sozinho. A prevenção também é a mesma: bloquear sempre na mesma ordem, por exemplo, atualizar as contas em ordem crescente de id.

## Boas práticas

- Transações **curtas**: cada bloqueio mantido é alguém esperando.
- Nada de chamadas externas dentro de uma transação aberta, como um HTTP para o gateway de pagamento: se ele demorar 30 segundos, as linhas ficam bloqueadas 30 segundos.
- Atualizações relativas (`SET quantidade = quantidade - 1`) em vez de ler, calcular e gravar.
- Repetir automaticamente as transações recusadas por impasse ou por serialização, um número limitado de vezes, como as [novas tentativas do HttpClient](/assistir/backend-junior-t2-e04).

## Por baixo dos panos

Como o REPEATABLE READ consegue mostrar 80 enquanto o valor atual é 60? Os bancos modernos usam **MVCC** (*multiversion concurrency control*): um `UPDATE` não sobrescreve a linha, mas cria uma **nova versão** dela, marcada com o identificador da transação que a criou. Cada transação tem uma **fotografia**: o conjunto das transações confirmadas que ela pode enxergar. Ler é procurar a versão mais nova criada por uma transação visível. No READ COMMITTED, a fotografia é tirada a cada comando; no REPEATABLE READ, uma vez, no começo. Assim, leituras nunca bloqueiam escritas, e escritas nunca bloqueiam leituras: só duas escritas na mesma linha disputam um bloqueio. As versões antigas ficam guardadas até que nenhuma transação possa mais precisar delas; no PostgreSQL, quem as limpa é o `VACUUM`. O desafio deste episódio implementa exatamente esse mecanismo.

A durabilidade vem de outro mecanismo, o ***write-ahead log*** (WAL): antes de qualquer página da tabela ser alterada no disco, a alteração é gravada num arquivo de registro sequencial, e o `COMMIT` só responde depois que esse registro chegou ao disco. Se o servidor cair, ao reiniciar o banco relê o registro e refaz o que foi confirmado e desfaz o que não foi. Gravar em sequência num único arquivo é muito mais rápido que espalhar escritas pelas páginas das tabelas, que podem ser atualizadas depois, com calma.

## Resumo

- ACID: atomicidade, consistência, isolamento e durabilidade; `BEGIN`, `COMMIT` e `ROLLBACK`
- No JDBC, cada comando é uma transação até `setAutoCommit(false)`; no Spring, `@Transactional`
- Ler, calcular no Java e gravar perde atualizações; prefira `SET coluna = coluna - 1`
- `SELECT ... FOR UPDATE` é o bloqueio pessimista; a coluna de versão (`@Version`) é o otimista
- READ COMMITTED (padrão do PostgreSQL) permite leituras não repetíveis; REPEATABLE READ (padrão do MySQL) usa uma fotografia e pode recusar gravações
- Impasses e falhas de serialização desfazem a transação: a aplicação deve repeti-la
- Transações curtas, sem chamadas externas dentro; MVCC guarda versões, e o WAL garante a durabilidade
