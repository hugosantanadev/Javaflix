Quase todo backend guarda os dados num **banco de dados relacional**: PostgreSQL, MySQL, Oracle, SQL Server. Neles, os dados ficam em **tabelas**, com linhas e colunas de tipos definidos, e são consultados com **SQL**, uma linguagem **declarativa**: você descreve o resultado que quer, e o banco decide como buscá-lo. Frameworks como o JPA geram boa parte do SQL por você, mas quem não sabe ler e escrever SQL não consegue entender por que uma tela está lenta nem conferir se um relatório está certo. Esta temporada inteira usa o mesmo banco, o de uma loja.

## O banco da loja

| Tabela | Colunas |
|---|---|
| `categorias` | `id`, `nome` |
| `produtos` | `id`, `nome`, `preco`, `estoque`, `categoria_id` (pode ser nulo) |
| `clientes` | `id`, `nome`, `email` (único), `cidade` (pode ser nula) |
| `pedidos` | `id`, `cliente_id`, `criado_em`, `status` |
| `itens_pedido` | `pedido_id`, `produto_id`, `quantidade`, `preco_unitario` |

Os exemplos usam SQL padrão, que roda igual no PostgreSQL, no MySQL e no H2, o banco em memória muito usado em testes Java. Os resultados mostrados foram obtidos executando cada consulta no H2, no modo de compatibilidade com o PostgreSQL.

## SELECT

A consulta mais simples lê todas as colunas de todas as linhas:

```sql
SELECT * FROM produtos;
```

```text
 id | nome             | preco   | estoque | categoria_id
----+------------------+---------+---------+--------------
  1 | Teclado mecânico |  349.90 |      12 |            1
  2 | Mouse sem fio    |  129.90 |      40 |            1
  3 | Monitor 27       | 1899.00 |       5 |            2
  4 | Headset          |  259.90 |       0 |            1
  5 | Webcam Full HD   |  219.00 |       8 |
  6 | Monitor 24       | 1099.00 |       0 |            2
(6 linhas)
```

A célula vazia da Webcam é um **`NULL`**: a ausência de valor, que não é zero nem texto vazio. O `*` é prático no terminal, mas no código da aplicação liste as colunas que você usa: uma coluna nova na tabela não deve mudar o que o programa recebe, e trazer colunas desnecessárias custa rede e memória.

## WHERE

O `WHERE` filtra as linhas. Os operadores são os esperados, com dois detalhes: igualdade é `=`, e diferença é `<>` (a maioria dos bancos aceita também `!=`).

```sql
SELECT nome, preco, estoque
FROM produtos
WHERE estoque > 0 AND preco BETWEEN 100 AND 400
ORDER BY preco DESC;
```

```text
 nome             | preco  | estoque
------------------+--------+---------
 Teclado mecânico | 349.90 |      12
 Webcam Full HD   | 219.00 |       8
 Mouse sem fio    | 129.90 |      40
(3 linhas)
```

| Operador | Exemplo | Observação |
|---|---|---|
| `BETWEEN` | `preco BETWEEN 100 AND 400` | Inclui as duas pontas |
| `IN` | `status IN ('PAGO', 'ENTREGUE')` | Atalho para vários `OR` |
| `LIKE` | `nome LIKE 'Monitor%'` | `%` é qualquer sequência; `_`, um caractere só |
| `IS NULL` | `cidade IS NULL` | A única forma de testar se é nulo |
| `NOT` | `NOT status = 'CANCELADO'` | Inverte a condição |

O `LIKE` diferencia maiúsculas no PostgreSQL; para ignorá-las, há o `ILIKE`, que é só do PostgreSQL, ou `LOWER(nome) LIKE 'monitor%'`, que funciona em todos. E texto vai entre **aspas simples**; aspas duplas, no SQL padrão, são para nomes de colunas e tabelas.

### AND antes de OR

O `AND` tem precedência sobre o `OR`, como a multiplicação sobre a soma. A intenção era "periféricos ou monitores, acima de R$ 1.500":

```sql
SELECT nome FROM produtos WHERE categoria_id = 1 OR categoria_id = 2 AND preco > 1500;
```

```text
 nome
------------------
 Teclado mecânico
 Mouse sem fio
 Monitor 27
 Headset
(4 linhas)
```

O banco leu `categoria_id = 1 OR (categoria_id = 2 AND preco > 1500)`: todos os periféricos, de qualquer preço, mais os monitores caros. Com parênteses, o resultado é o pretendido:

```sql
SELECT nome FROM produtos WHERE (categoria_id = 1 OR categoria_id = 2) AND preco > 1500;
```

```text
 nome
------------
 Monitor 27
(1 linha)
```

Na dúvida, use parênteses: eles não custam nada e deixam a intenção explícita.

## NULL

O `NULL` é a maior fonte de surpresas do SQL. Ele significa "valor desconhecido", e qualquer comparação com um valor desconhecido dá um resultado **desconhecido**, nem verdadeiro nem falso. O `WHERE` só mantém as linhas em que a condição é **verdadeira**. Por isso:

```sql
SELECT nome, cidade FROM clientes WHERE cidade = NULL;
```

```text
 nome | cidade
------+--------
(0 linhas)
```

Nenhuma linha, nem a do Diego, que não tem cidade: `NULL = NULL` também é desconhecido. O teste certo é `IS NULL`:

```sql
SELECT nome, cidade FROM clientes WHERE cidade IS NULL;
```

```text
 nome        | cidade
-------------+--------
 Diego Rocha |
(1 linha)
```

A armadilha mais traiçoeira é a contrária. "Clientes que não são de São Paulo" deveria incluir o Diego, mas:

```sql
SELECT nome, cidade FROM clientes WHERE cidade <> 'São Paulo';
```

```text
 nome        | cidade
-------------+----------
 Bruno Souza | Recife
 Elisa Prado | Curitiba
(2 linhas)
```

Para o banco, não se sabe se uma cidade desconhecida é São Paulo, então ela não entra. Se a regra de negócio diz que deve entrar, isso precisa estar escrito: `WHERE cidade <> 'São Paulo' OR cidade IS NULL`. O mesmo vale para o `NOT IN`: com um `NULL` na lista, ele nunca é verdadeiro, e `WHERE categoria_id NOT IN (1, NULL)` devolve **zero** linhas. Isso acontece de verdade quando a lista vem de uma subconsulta que tem um nulo.

Essa lógica de três valores cabe num `enum`, com as tabelas-verdade do SQL:

```java executar
import java.util.Arrays;

public class TresValores {
    enum Logico {
        VERDADEIRO, FALSO, DESCONHECIDO;

        Logico e(Logico outro) {
            if (this == FALSO || outro == FALSO) return FALSO;
            return this == VERDADEIRO && outro == VERDADEIRO ? VERDADEIRO : DESCONHECIDO;
        }

        Logico ou(Logico outro) {
            if (this == VERDADEIRO || outro == VERDADEIRO) return VERDADEIRO;
            return this == FALSO && outro == FALSO ? FALSO : DESCONHECIDO;
        }

        Logico nao() {
            return this == VERDADEIRO ? FALSO : this == FALSO ? VERDADEIRO : DESCONHECIDO;
        }
    }

    static Logico igual(Object a, Object b) {
        if (a == null || b == null) return Logico.DESCONHECIDO;
        return a.equals(b) ? Logico.VERDADEIRO : Logico.FALSO;
    }

    static Logico em(Object valor, Object... lista) {
        return Arrays.stream(lista).map(item -> igual(valor, item)).reduce(Logico.FALSO, Logico::ou);
    }

    public static void main(String[] args) {
        System.out.println("cidade     | cidade <> 'São Paulo' | WHERE mantém?");
        for (String cidade : Arrays.asList("São Paulo", "Recife", null)) {
            Logico r = igual(cidade, "São Paulo").nao();
            System.out.printf("%-10s | %-21s | %s%n", cidade, r, r == Logico.VERDADEIRO ? "sim" : "não");
        }
        System.out.println();
        System.out.println("categoria  | NOT IN (1, NULL)");
        for (Integer categoria : Arrays.asList(1, 2, null)) {
            System.out.printf("%-10s | %s%n", categoria, em(categoria, 1, null).nao());
        }
        System.out.println();
        System.out.println("NULL = NULL: " + igual(null, null));
        System.out.println("DESCONHECIDO OR VERDADEIRO: " + Logico.DESCONHECIDO.ou(Logico.VERDADEIRO));
        System.out.println("DESCONHECIDO AND FALSO: " + Logico.DESCONHECIDO.e(Logico.FALSO));
    }
}
```

```saida
cidade     | cidade <> 'São Paulo' | WHERE mantém?
São Paulo  | FALSO                 | não
Recife     | VERDADEIRO            | sim
null       | DESCONHECIDO          | não

categoria  | NOT IN (1, NULL)
1          | FALSO
2          | DESCONHECIDO
null       | DESCONHECIDO

NULL = NULL: DESCONHECIDO
DESCONHECIDO OR VERDADEIRO: VERDADEIRO
DESCONHECIDO AND FALSO: FALSO
```

O `NOT IN (1, NULL)` é `NOT (categoria = 1 OR categoria = NULL)`. Para a categoria 2, isso é `NOT (FALSO OR DESCONHECIDO)`, que é `NOT DESCONHECIDO`, que continua desconhecido. Note também que o desconhecido "some" quando o resultado já está decidido: `DESCONHECIDO OR VERDADEIRO` é verdadeiro.

Para trocar um nulo por um valor padrão na saída, há o `COALESCE`, que devolve o primeiro argumento não nulo:

```sql
SELECT nome, COALESCE(cidade, 'não informada') AS cidade FROM clientes ORDER BY nome;
```

```text
 nome        | cidade
-------------+---------------
 Ana Lima    | São Paulo
 Bruno Souza | Recife
 Carla Dias  | São Paulo
 Diego Rocha | não informada
 Elisa Prado | Curitiba
(5 linhas)
```

## ORDER BY, LIMIT e DISTINCT

**Sem `ORDER BY`, a ordem das linhas não é garantida.** Ela costuma parecer estável num banco pequeno, e muda quando a tabela cresce, quando o banco decide ler em paralelo ou depois de uma atualização. Toda listagem mostrada ao usuário precisa de um `ORDER BY`, e toda paginação também.

```sql
SELECT nome, cidade FROM clientes ORDER BY cidade, nome;
```

```text
 nome        | cidade
-------------+-----------
 Elisa Prado | Curitiba
 Bruno Souza | Recife
 Ana Lima    | São Paulo
 Carla Dias  | São Paulo
 Diego Rocha |
(5 linhas)
```

A segunda coluna desempata a primeira. E os nulos foram para o fim: no PostgreSQL, o `NULL` é tratado como maior que qualquer valor, e vai para o fim na ordem crescente e para o começo na decrescente. O MySQL faz o contrário. Para não depender disso, escreva `ORDER BY cidade NULLS FIRST` ou `NULLS LAST`, onde o banco aceitar.

O `LIMIT` corta o resultado, e o `OFFSET` pula linhas, a paginação por deslocamento do [episódio de APIs](/assistir/backend-junior-t2-e02):

```sql
SELECT nome, cidade FROM clientes ORDER BY cidade, nome LIMIT 2 OFFSET 2;
```

```text
 nome       | cidade
------------+-----------
 Ana Lima   | São Paulo
 Carla Dias | São Paulo
(2 linhas)
```

O padrão SQL escreve o mesmo como `OFFSET 2 ROWS FETCH FIRST 2 ROWS ONLY`, que o Oracle e o SQL Server exigem. E o `DISTINCT` elimina linhas repetidas do resultado:

```sql
SELECT DISTINCT status FROM pedidos ORDER BY status;
```

```text
 status
------------
 AGUARDANDO
 CANCELADO
 ENTREGUE
 PAGO
(4 linhas)
```

## Expressões e CASE

Colunas podem ser calculadas, e o `AS` dá um nome, um **apelido**, ao resultado. O `CASE` é o `switch` do SQL:

```sql
SELECT nome,
       CASE WHEN estoque = 0 THEN 'esgotado'
            WHEN estoque < 10 THEN 'acabando'
            ELSE 'ok' END AS situacao
FROM produtos
ORDER BY id;
```

```text
 nome             | situacao
------------------+----------
 Teclado mecânico | ok
 Mouse sem fio    | ok
 Monitor 27       | acabando
 Headset          | esgotado
 Webcam Full HD   | acabando
 Monitor 24       | esgotado
(6 linhas)
```

## A ordem em que a consulta é avaliada

O SQL se escreve numa ordem e é avaliado em outra:

```text
FROM → WHERE → SELECT → DISTINCT → ORDER BY → LIMIT/OFFSET
```

Isso explica um erro que todo mundo comete. O apelido criado no `SELECT` pode ser usado no `ORDER BY`, que vem depois, mas não no `WHERE`, que vem antes:

```sql
SELECT nome, preco * 1.1 AS com_aumento FROM produtos WHERE com_aumento > 400;
```

```text
ERRO: Column "com_aumento" not found
```

No `WHERE`, repita a expressão: `WHERE preco * 1.1 > 400`. O [episódio de agregações](/assistir/backend-junior-t3-e03) acrescenta o `GROUP BY` e o `HAVING` a essa ordem.

> [!ATENCAO]
> No código Java, nunca monte SQL concatenando o que veio do usuário: `"... WHERE nome = '" + busca + "'"` permite que uma busca como `' OR '1'='1` mude a consulta. Use sempre parâmetros, com `PreparedStatement` e `?`, como no [episódio de JDBC](/assistir/senior-t5-e05), ou o JPA, que faz o mesmo.

## Por baixo dos panos

Por ser declarativo, o SQL deixa o "como" para o banco. Ao receber uma consulta, ele a analisa, confere tabelas e colunas, e o **otimizador** escolhe um **plano de execução**: ler a tabela inteira ou usar um índice, em que ordem juntar tabelas, se ordena na memória ou em disco. As linhas ficam gravadas em **páginas** de tamanho fixo, de 8 KB no PostgreSQL, e, sem um índice para a coluna do `WHERE`, o banco lê todas as páginas da tabela e testa linha por linha, uma **varredura completa**. Com seis produtos, isso é instantâneo; com seis milhões, é o motivo de uma tela lenta. O [episódio de índices](/assistir/backend-junior-t3-e04) mostra como ver o plano escolhido com `EXPLAIN` e como mudá-lo.

É também por causa das páginas que a ordem sem `ORDER BY` não é garantida: o banco devolve as linhas na ordem em que as encontra, e essa ordem depende de onde cada linha está gravada, do plano escolhido e de leituras em paralelo, coisas que mudam sem aviso.

## Resumo

- Liste as colunas em vez de `*` no código; texto entre aspas simples
- `WHERE` com `=`, `<>`, `BETWEEN`, `IN`, `LIKE` e `IS NULL`; `AND` vem antes de `OR`, use parênteses
- `NULL` é desconhecido: `= NULL` nunca é verdadeiro, `<>` exclui os nulos e `NOT IN` com nulo não devolve nada
- `COALESCE` troca nulos por um valor padrão
- Sem `ORDER BY`, a ordem não é garantida; `NULLS FIRST` e `NULLS LAST` deixam explícito onde ficam os nulos
- `LIMIT` e `OFFSET` paginam; `DISTINCT` remove repetições; `CASE` escolhe valores
- Avaliação: `FROM`, `WHERE`, `SELECT`, `ORDER BY`, `LIMIT`: apelidos do `SELECT` não existem no `WHERE`
- Nunca concatene entrada do usuário no SQL: use parâmetros
