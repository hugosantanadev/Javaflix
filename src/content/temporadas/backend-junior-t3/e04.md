Uma consulta só é tão boa quanto o modelo por trás dela. Tabelas bem desenhadas impedem dados inválidos antes que eles entrem, evitam que a mesma informação exista em dois lugares e diferentes, e permitem consultas rápidas. Este episódio cobre as três ferramentas do desenho: as **chaves**, que identificam e ligam as linhas; as **restrições**, que o banco garante mesmo que a aplicação tenha um defeito; e os **índices**, que fazem a diferença entre uma busca de milissegundos e uma de minutos.

## Chaves primárias

Toda tabela precisa de uma **chave primária**: uma coluna, ou um conjunto delas, que identifica cada linha de forma única e nunca é nula. Há dois estilos:

- **Chave natural**: um dado do próprio negócio, como o CPF ou o e-mail. Parece prático, até o cliente precisar trocar de e-mail e todas as tabelas que o referenciam precisarem mudar junto.
- **Chave substituta** (*surrogate*): um identificador sem significado, gerado pelo banco. É o padrão nos sistemas atuais, e o dado natural ganha uma restrição `UNIQUE` à parte.

O banco gera a chave substituta com uma coluna de identidade (`GENERATED ALWAYS AS IDENTITY`, o padrão SQL; `SERIAL` nas versões antigas do PostgreSQL; `AUTO_INCREMENT` no MySQL) ou com um **UUID**, um identificador de 128 bits que pode ser gerado em qualquer lugar, sem consultar o banco:

```sql
CREATE TABLE tags (
    id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nome VARCHAR(30) NOT NULL UNIQUE
);

INSERT INTO tags (nome) VALUES ('gamer'), ('escritório'), ('sem fio');

SELECT * FROM tags;
```

```text
 id | nome
----+------------
  2 | escritório
  1 | gamer
  3 | sem fio
(3 linhas)
```

Os ids foram gerados na ordem da inserção, e mesmo assim a consulta os devolveu fora de ordem: o banco decidiu ler a tabela pelo índice da coluna `nome`, criado pelo `UNIQUE`, e as linhas vieram em ordem alfabética. É o aviso do [primeiro episódio](/assistir/backend-junior-t3-e01) na prática: sem `ORDER BY`, a ordem é a que o plano escolhido produzir.

## Restrições

As restrições são regras que o banco verifica em toda escrita, venha ela da aplicação, de um script ou de alguém no terminal. Cada uma das tentativas abaixo foi recusada:

```sql
INSERT INTO clientes VALUES (6, 'Ana Lima', 'ana@exemplo.com', 'Recife');
-- ERRO: Unique index or primary key violation: ... ON public.clientes(email ...) VALUES ( /* 1 */ 'ana@exemplo.com' )

INSERT INTO pedidos VALUES (107, 99, DATE '2025-09-20', 'PAGO');
-- ERRO: Referential integrity constraint violation: ... FOREIGN KEY(cliente_id) REFERENCES public.clientes(id) (99)

DELETE FROM clientes WHERE id = 1;
-- ERRO: Referential integrity constraint violation: ... FOREIGN KEY(cliente_id) REFERENCES public.clientes(id) (1)

INSERT INTO categorias VALUES (4, NULL);
-- ERRO: NULL not allowed for column "nome"

ALTER TABLE produtos ADD CONSTRAINT preco_positivo CHECK (preco > 0);
UPDATE produtos SET preco = -10 WHERE id = 2;
-- ERRO: Check constraint violation: "preco_positivo: "
```

| Restrição | Garante |
|---|---|
| `PRIMARY KEY` | Identificador único e não nulo |
| `UNIQUE` | Que não haja dois valores iguais na coluna, como dois clientes com o mesmo e-mail |
| `NOT NULL` | Que a coluna sempre tenha valor |
| `FOREIGN KEY` (`REFERENCES`) | Que o valor exista na outra tabela: nenhum pedido de um cliente inexistente |
| `CHECK` | Uma condição qualquer, como `preco > 0` ou `quantidade BETWEEN 1 AND 99` |
| `DEFAULT` | Um valor padrão quando nenhum é informado, como `DEFAULT CURRENT_TIMESTAMP` |

O `DELETE` da Ana foi recusado porque ela tem pedidos; o da Elisa, que não tem, passou. Esse comportamento é configurável na chave estrangeira:

| `ON DELETE` | Ao apagar o cliente |
|---|---|
| `NO ACTION` / `RESTRICT` (padrão) | Recusa, se houver pedidos |
| `CASCADE` | Apaga os pedidos junto |
| `SET NULL` | Mantém os pedidos, com `cliente_id` nulo |

O `CASCADE` é conveniente para dados que só existem por causa do pai, como as tags de um produto, e perigoso para dados de negócio: ninguém quer que apagar um cliente apague o histórico de vendas. Para esses, muitos sistemas nem apagam: marcam a linha como inativa.

> [!DICA]
> Validar na aplicação não substitui as restrições do banco. Duas requisições simultâneas podem passar ao mesmo tempo pelo "esse e-mail já existe?" do Java; só o `UNIQUE` impede, de verdade, o segundo cadastro.

## Relacionamentos

- **Um para muitos**: um cliente tem muitos pedidos. A chave estrangeira fica no lado "muitos": `pedidos.cliente_id`.
- **Muitos para muitos**: um produto tem várias tags, e uma tag está em vários produtos. Nenhuma das duas tabelas comporta a relação; ela vira uma **tabela associativa**, com uma chave estrangeira para cada lado e uma chave primária composta pelas duas:

```sql
CREATE TABLE produto_tags (
    produto_id INT NOT NULL REFERENCES produtos (id) ON DELETE CASCADE,
    tag_id INT NOT NULL REFERENCES tags (id),
    PRIMARY KEY (produto_id, tag_id)
);

INSERT INTO produto_tags VALUES (1, 1), (2, 1), (2, 3), (2, 2);

SELECT pr.nome, t.nome AS tag
FROM produtos pr
JOIN produto_tags pt ON pt.produto_id = pr.id
JOIN tags t ON t.id = pt.tag_id
ORDER BY pr.nome, t.nome;
```

```text
 nome             | tag
------------------+------------
 Mouse sem fio    | escritório
 Mouse sem fio    | gamer
 Mouse sem fio    | sem fio
 Teclado mecânico | gamer
(4 linhas)
```

A `itens_pedido` da loja é uma tabela associativa entre pedidos e produtos, com colunas a mais, a quantidade e o preço da época.

- **Um para um**: um cliente tem um endereço de cobrança. Normalmente vira colunas na mesma tabela; separa-se quando a parte é opcional, grande ou acessada raramente.

## Normalização

Normalizar é organizar as tabelas para que cada fato fique num lugar só. As três primeiras **formas normais** resolvem quase tudo:

- **1ª forma normal**: cada coluna guarda um valor só. Uma coluna `tags` com `'gamer,sem fio'` não pode ser filtrada, indexada nem ligada a outra tabela; ela deveria ser a `produto_tags`.
- **2ª forma normal**: numa tabela de chave composta, nenhuma coluna depende só de parte da chave. Se `itens_pedido` tivesse o `nome_produto`, ele dependeria só do `produto_id`, e mudaria em todos os itens quando o produto fosse renomeado.
- **3ª forma normal**: nenhuma coluna depende de outra que não seja a chave. Se `clientes` tivesse `cidade` e `estado`, o estado dependeria da cidade, e um cliente de Recife poderia acabar marcado como de Santa Catarina.

O sintoma de uma tabela não normalizada é a **anomalia de atualização**: mudar um fato exige mudar várias linhas, e esquecer uma deixa o banco contradizendo a si mesmo. Às vezes vale **desnormalizar** de propósito: o `preco_unitario` dos itens copia o preço do produto porque o histórico precisa do preço da época, e um painel pode guardar um total pré-calculado para não somar milhões de linhas a cada acesso. A cópia proposital é uma decisão, com um responsável por mantê-la correta; a acidental é um defeito.

## Tipos de dados

| Dado | Tipo | Evite |
|---|---|---|
| Dinheiro | `DECIMAL(10, 2)` ou `NUMERIC` | `FLOAT` e `DOUBLE`, que não guardam centavos exatos |
| Texto curto | `VARCHAR(n)` | Um tamanho tão pequeno que corte nomes reais |
| Texto livre | `TEXT` (PostgreSQL) | |
| Data | `DATE` | Texto como `'16/09/2025'` |
| Instante | `TIMESTAMP WITH TIME ZONE` | `TIMESTAMP` sem fuso, para eventos de usuários em fusos diferentes |
| Sim ou não | `BOOLEAN` | `CHAR(1)` com `'S'` e `'N'` |
| Identificador | `BIGINT` ou `UUID` | `INT` numa tabela que pode passar de 2 bilhões de linhas |

## Índices

Um **índice** é uma estrutura separada da tabela, que guarda os valores de uma ou mais colunas **em ordem**, cada um com a localização da linha correspondente. Ele está para a tabela como o índice remissivo está para um livro: em vez de ler todas as páginas, vai-se direto à certa. O comando `EXPLAIN` mostra o plano que o banco escolheu. Antes de um índice em `status`:

```sql
EXPLAIN SELECT id, criado_em FROM pedidos WHERE status = 'PAGO';
```

```text
SELECT "id", "criado_em"
FROM "public"."pedidos"
    /* public.pedidos.tableScan */
WHERE "status" = 'PAGO'
```

O `tableScan` é a varredura completa: todas as linhas lidas e testadas. Depois de `CREATE INDEX idx_pedidos_status ON pedidos (status)`:

```text
SELECT "id", "criado_em"
FROM "public"."pedidos"
    /* public.idx_pedidos_status: status = 'PAGO' */
WHERE "status" = 'PAGO'
```

Agora o banco vai direto às linhas com `PAGO`. O formato do `EXPLAIN` muda de banco para banco: no PostgreSQL, os nomes são `Seq Scan` para a varredura e `Index Scan` para a busca pelo índice, e o `EXPLAIN ANALYZE` executa a consulta e mostra os tempos reais.

### Quando o índice é usado

Um índice ajuda em `=`, em intervalos (`>`, `<`, `BETWEEN`), no `ORDER BY` da mesma coluna, que já sai ordenado, e nas colunas do `ON` de um JOIN. Mas há situações em que ele **não** pode ser usado, e o banco volta à varredura:

- **Uma função sobre a coluna**: com um índice em `email`, `WHERE LOWER(email) = 'ana@exemplo.com'` faz `tableScan`, porque o índice guarda os e-mails, não os e-mails em minúsculas. A solução é um índice sobre a expressão, `CREATE INDEX ... ON clientes (LOWER(email))`, ou guardar o e-mail já normalizado.
- **`LIKE` começando com `%`**: `nome LIKE 'Monitor%'` vira um intervalo no índice (`nome >= 'Monitor' AND nome < 'Monitos'`), mas `nome LIKE '%27'` não tem por onde começar, e faz `tableScan`. Buscas por trechos no meio do texto pedem busca textual, como o *full-text search* do PostgreSQL.
- **Colunas fora de ordem num índice composto**: veja abaixo.

### Índices compostos

Um índice em `(cidade, nome)` ordena primeiro pela cidade e, dentro de cada cidade, pelo nome, como uma lista telefônica ordenada por sobrenome e nome. Ele serve para buscar por `cidade`, ou por `cidade` e `nome`, mas não por `nome` sozinho, assim como a lista telefônica não ajuda a achar todos os "Ana":

```sql
EXPLAIN SELECT email FROM clientes WHERE cidade = 'Recife';
-- /* public.idx_clientes_cidade_nome: cidade = 'Recife' */

EXPLAIN SELECT email FROM clientes WHERE nome = 'Ana Lima';
-- /* public.clientes.tableScan */
```

É a regra do **prefixo à esquerda**: o índice é útil para qualquer começo da sua lista de colunas. Por isso a ordem das colunas num índice composto importa, e a primeira deve ser a que aparece em mais consultas, de preferência com `=`.

### O preço dos índices

Índices não são de graça. Cada `INSERT`, `UPDATE` e `DELETE` precisa atualizar todos os índices da tabela, e cada índice ocupa espaço em disco e na memória. Uma tabela com dez índices escreve onze vezes. E um índice numa coluna com poucos valores distintos, como um booleano `ativo` em que 95% das linhas são `true`, raramente é usado: ler o índice e depois quase todas as linhas sai mais caro que a varredura. A regra prática: crie índices para as consultas que existem, olhando o `EXPLAIN`, e não "por garantia".

> [!ATENCAO]
> O PostgreSQL **não** cria índices automaticamente para as chaves estrangeiras; o MySQL e o H2 criam. Num PostgreSQL, `pedidos.cliente_id` sem índice faz todo JOIN e todo `DELETE` de cliente varrer a tabela de pedidos. Crie o índice junto com a chave estrangeira.

## Por baixo dos panos

O índice padrão de quase todos os bancos é a **árvore B+**: uma árvore larga e baixa, em que cada nó é uma página de disco com centenas de chaves ordenadas. Os nós internos só guiam a busca; as folhas guardam as chaves com a localização das linhas e são encadeadas umas às outras, o que permite percorrer um intervalo lendo as folhas em sequência. Com centenas de chaves por nó, três ou quatro níveis bastam para centenas de milhões de linhas: achar uma chave custa três ou quatro leituras de página, e as páginas de cima quase sempre já estão na memória.

A ideia central, chaves ordenadas e busca binária, aparece num índice simulado com um vetor ordenado. Cada entrada guarda a chave, o `cliente_id`, nos 32 bits altos de um `long`, e o número da linha nos 32 baixos, como um índice de verdade guarda a chave e a localização da linha:

```java executar
import java.util.Arrays;

public class Indice {
    static long comparacoes;

    /** Primeira posição do índice ordenado cuja chave é maior ou igual à procurada. */
    static int limiteInferior(long[] indice, int chave) {
        int esq = 0, dir = indice.length;
        while (esq < dir) {
            int meio = (esq + dir) >>> 1;
            comparacoes++;
            if ((int) (indice[meio] >>> 32) < chave) esq = meio + 1;
            else dir = meio;
        }
        return esq;
    }

    public static void main(String[] args) {
        int linhas = 1_000_000;
        int[] clienteDaLinha = new int[linhas];
        for (int i = 0; i < linhas; i++) clienteDaLinha[i] = (int) ((i * 7919L) % 50_000);

        comparacoes = 0;
        int achados = 0;
        for (int i = 0; i < linhas; i++) {
            comparacoes++;
            if (clienteDaLinha[i] == 31_337) achados++;
        }
        System.out.println("varredura: " + achados + " pedidos, " + comparacoes + " comparações");

        long[] indice = new long[linhas];
        for (int i = 0; i < linhas; i++) indice[i] = ((long) clienteDaLinha[i] << 32) | i;
        Arrays.sort(indice);

        comparacoes = 0;
        int pos = limiteInferior(indice, 31_337);
        long naBusca = comparacoes;
        int lidos = 0;
        while (pos < indice.length && (int) (indice[pos] >>> 32) == 31_337) {
            lidos++;
            pos++;
        }
        System.out.println("índice: " + lidos + " pedidos, " + naBusca + " comparações na busca binária");
    }
}
```

```saida
varredura: 20 pedidos, 1000000 comparações
índice: 20 pedidos, 20 comparações na busca binária
```

Um milhão de comparações contra vinte, porque log₂ de um milhão é cerca de 20. Depois da busca, as 20 entradas do cliente estão lado a lado no índice ordenado, e basta lê-las em sequência: é o que a árvore B+ faz percorrendo as folhas. O desafio deste episódio leva a mesma ideia para um índice composto e mostra a regra do prefixo à esquerda em números.

## Resumo

- Chave primária única e não nula; chaves substitutas (identidade ou UUID) com `UNIQUE` nos dados naturais
- `UNIQUE`, `NOT NULL`, `FOREIGN KEY` e `CHECK` são garantidas pelo banco em toda escrita; validar no Java não basta
- `ON DELETE`: `RESTRICT` (padrão), `CASCADE` ou `SET NULL`; cuidado com `CASCADE` em dados de negócio
- Um para muitos: chave estrangeira no lado "muitos"; muitos para muitos: tabela associativa
- Formas normais: um valor por coluna, nada dependendo de parte da chave ou de outra coluna; desnormalize só de propósito
- Dinheiro em `DECIMAL`, instantes em `TIMESTAMP WITH TIME ZONE`, ids em `BIGINT` ou `UUID`
- Índices aceleram `=`, intervalos, `ORDER BY` e JOINs; funções na coluna e `LIKE '%...'` os anulam
- Índice composto vale para o prefixo à esquerda; todo índice custa nas escritas; no PostgreSQL, indexe as chaves estrangeiras
