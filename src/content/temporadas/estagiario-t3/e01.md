O `if` é a primeira estrutura de controle que todo mundo aprende, e por isso a prova o usa para testar atenção, não sintaxe: chaves que faltam, um `;` sobrando, um `else` que pertence ao `if` errado, uma variável que não existe fora do bloco. Este episódio cobre o `if` com todas essas armadilhas e o `instanceof` com padrão, que transforma teste de tipo em declaração de variável.

## O básico, com uma regra a mais que em C

```java
if (condição) {
    // executa se a condição for verdadeira
} else {
    // executa se for falsa
}
```

A condição precisa ser uma expressão **`boolean`**. Em C e em JavaScript, `if (x)` com um número é comum; em Java, não compila:

```java nao-compila
int x = 1;
if (x) {
    System.out.println("C faria isso");
}
```

> [!PERGUNTAS]
> **P:** Se C e JavaScript aceitam `if (x)` com número, por que o Java não aceita?
>
> **R:** Para pegar erros na compilação. Em C, `if (x = 0)` compila, atribui 0 e nunca entra no `if`: um erro clássico que ninguém vê. Exigindo `boolean`, o Java transforma esse erro num aviso do compilador para quase todos os tipos.
>
> **P:** E `if (ativo == true)`? Está errado?
>
> **R:** Funciona, mas é redundante: `ativo` já é `boolean`. Escreva `if (ativo)`, que além de mais curto não deixa espaço para trocar `==` por `=` por engano.

O `else` é opcional, e cadeias de `else if` testam condições em ordem, parando na **primeira** verdadeira. Por isso a ordem das condições muda o resultado:

```java executar
int nota = 85;
if (nota >= 60) {
    System.out.println("C");
} else if (nota >= 80) {
    System.out.println("B");
} else if (nota >= 90) {
    System.out.println("A");
}

if (nota >= 90) {
    System.out.println("A");
} else if (nota >= 80) {
    System.out.println("B");
} else if (nota >= 60) {
    System.out.println("C");
}
```

```saida
C
B
```

No primeiro bloco, 85 ≥ 60 já é verdadeiro e os outros testes nem são feitos. Em faixas de valores, comece pela condição mais restritiva.

> [!IA]
> Ao "refatorar para legibilidade", um assistente de IA pode reordenar uma cadeia de `else if`, por exemplo para deixar as faixas em ordem crescente, sem perceber que a ordem decide qual ramo vence. O código continua compilando e passa a dar notas erradas. Toda mudança de ordem numa cadeia de condições precisa de um teste com um valor de cada faixa.

> [!MATEMATICA]
> Cada `if` independente dobra o número de caminhos que o programa pode seguir: com 1 `if`, são 2 caminhos; com 3 `if` em sequência, 2³ = 8; com 10, 1.024. É por isso que métodos cheios de `if` são difíceis de testar por completo. Uma cadeia de `else if` é mais barata: com n condições, existem só n + 1 caminhos, porque apenas um ramo roda.

## Chaves, ponto e vírgula e indentação

Sem chaves, o `if` controla **um único comando**: o próximo. A indentação não significa nada para o compilador:

```java executar
int x = 5;
if (x > 10)
    System.out.println("maior");
    System.out.println("sempre");
if (x > 10);
{
    System.out.println("bloco solto");
}
```

```saida
sempre
bloco solto
```

O segundo `println` está indentado como se fosse do `if`, mas roda sempre. E `if (x > 10);` tem um comando vazio (`;`) como corpo: o bloco entre chaves logo abaixo é um bloco comum, que roda sempre. Os dois erros são clássicos de prova, e o segundo compila sem nenhum aviso.

> [!ERRO]
> Pôr `;` logo depois da condição: `if (saldo < 0);`. O `;` vira o corpo inteiro do `if`, e o bloco seguinte roda sempre, com saldo negativo ou não. O compilador aceita, porque um comando vazio é um comando válido.

> [!PREVENCAO]
> Use chaves em **todo** `if`, mesmo com uma linha só. Em 2014, um `if` sem chaves com uma linha duplicada logo abaixo, `goto fail;`, desligou a verificação de certificados do sistema da Apple: a segunda linha, indentada como se fosse do `if`, rodava sempre. O caso ficou conhecido como *goto fail* e é citado até hoje como argumento para chaves obrigatórias.

> [!PROVA]
> Sem chaves, o corpo do `if` não pode ser uma declaração de variável: `if (ok) int y = 1;` não compila ("declaration not allowed here"), porque a variável não teria utilidade nenhuma. Com chaves, `if (ok) { int y = 1; }` compila.

## A quem pertence o `else`

Com `if` aninhados e sem chaves, um `else` pertence ao `if` **mais próximo** que ainda não tem `else`, não importa a indentação.

> [!PENSE]
> No código abaixo, `a` é positivo e `b` é negativo. O `else` parece pertencer ao primeiro `if`. Se pertencesse, nada seria impresso. O que você acha que aparece?

```java executar
int a = 5, b = -1;
if (a > 0)
    if (b > 0)
        System.out.println("os dois positivos");
else //> Indentado como do primeiro if, mas pertence ao segundo.
    System.out.println("qual else?");
```

```saida
qual else?
```

A indentação sugere que o `else` é do `if (a > 0)`, mas ele é do `if (b > 0)`. Como `a > 0` e `b > 0` é falso, o `else` interno roda. Com `a` negativo, nada seria impresso. Chaves resolvem a ambiguidade, e é por isso que guias de estilo exigem chaves sempre.

## Escopo de bloco

Uma variável declarada dentro de um bloco `{ }` só existe até o fim dele:

```java nao-compila
if (true) {
    int dentro = 1;
}
System.out.println(dentro);
```

Para usar o valor depois do `if`, declare a variável antes dele. E se ela só recebe valor dentro do `if`, o compilador exige que **todo caminho** atribua algo antes da leitura, assunto do [último episódio](/assistir/estagiario-t3-e04) desta temporada.

## `instanceof` com padrão

Desde o Java 16, o `instanceof` pode declarar uma variável já convertida para o tipo testado. Ela só existe onde o teste com certeza deu verdadeiro:

```java executar
Object o = "Javaflix";
if (o instanceof String s && s.length() > 5) {
    System.out.println(s.toUpperCase());
}
if (!(o instanceof Integer n)) {
    System.out.println("não é Integer");
} else {
    System.out.println(n + 1);
}
```

```saida
JAVAFLIX
não é Integer
```

Em `o instanceof String s && s.length() > 5`, o `s` pode ser usado do lado direito do `&&`, porque o [curto-circuito](/assistir/estagiario-t2-e04) garante que ele só é avaliado se o teste passou. Com `||`, não compila: o lado direito roda justamente quando o teste falhou. No segundo `if`, a variável `n` existe no `else`, porque é lá que `o instanceof Integer` é verdadeiro.

> [!ANTES]
> Até o Java 15, testar e converter eram dois passos: `if (o instanceof String) { String s = (String) o; ... }`. O tipo aparecia três vezes, e o cast podia ser trocado por engano por outro tipo, que só quebrava na execução. O padrão do Java 16 junta tudo numa linha só, e o compilador garante que o cast é o certo.

> [!COMPILADOR]
> Você é o `javac`. Este trecho compila?
>
> ```java nao-compila
> Object o = "Javaflix";
> if (o instanceof String s || s.isEmpty()) {
>     System.out.println("texto");
> }
> ```
>
> **Resposta:** Não compila. O lado direito do `||` só roda quando o lado esquerdo é **falso**, ou seja, quando `o` não é uma `String`. Nesse caso, `s` não existe. O compilador acompanha esses caminhos e recusa usar `s` onde ela pode não ter sido declarada.

## Na IDE

- **Formatar revela a verdade.** **Ctrl + Alt + L** reformata o arquivo, e a indentação passa a seguir a estrutura real. No exemplo do `else` pendurado, o `else` anda para a direita e fica alinhado com o `if (b > 0)`: o erro aparece na hora.
- **`if` com corpo vazio.** O IntelliJ marca `if (x > 10);` com o aviso de comando com corpo vazio.
- **Chaves automáticas.** Em **Settings > Editor > Code Style > Java > Wrapping and Braces**, a opção *Force braces* com *Always* faz a formatação acrescentar chaves em todo `if`, `for` e `while`.

## Por baixo dos panos

O bytecode não tem `if` com bloco: tem **saltos condicionais**. O `javac` inverte a condição e pula por cima do bloco quando ela é falsa. Para `if (x > 10) y = 1; else y = 2;`, o `javap -c` mostra algo como:

```text
iload_1          // empilha x
bipush 10        // empilha 10
if_icmple L1     // se x <= 10, pula para o else
iconst_1
istore_2         // y = 1
goto L2          // pula o else
L1: iconst_2
istore_2         // y = 2
L2: ...
```

É o mesmo salto condicional da [CPU de brinquedo](/assistir/aprendiz-t1-e04) e do assembly do episódio de [linguagem de máquina](/assistir/aprendiz-t2-e01). As chaves, a indentação e o `else if` desaparecem: sobram comparações e saltos. Processadores modernos tentam adivinhar para que lado cada salto vai (a *predição de desvio*), e um `if` imprevisível dentro de um laço quente pode custar caro.

## Resumo para a prova

- A condição do `if` precisa ser `boolean`; `if (1)` não compila
- Numa cadeia de `else if`, vale a primeira condição verdadeira: a ordem importa
- Sem chaves, o `if` controla só o próximo comando; a indentação não conta
- `if (cond);` tem corpo vazio: o bloco seguinte roda sempre
- Corpo sem chaves não pode ser uma declaração de variável
- O `else` pertence ao `if` mais próximo sem `else`
- Variáveis de bloco não existem fora dele
- `o instanceof Tipo t` declara `t` onde o teste é verdadeiro: funciona com `&&`, não com `||`
