Muitas questões de "o código compila?" não são sobre sintaxe, e sim sobre **análise de fluxo**: o compilador percorre todos os caminhos possíveis do código e recusa três coisas. Comandos que nunca podem ser executados, variáveis lidas antes de receber valor em algum caminho, e métodos que podem terminar sem `return`. Este episódio mostra as regras exatas, incluindo as exceções que o compilador abre para constantes.

## Código inalcançável

Um comando que não pode ser alcançado por nenhum caminho é **erro de compilação**, não aviso. O caso mais simples é um comando depois de `return`, `throw`, `break` ou `continue` no mesmo bloco:

```java nao-compila
public class Inalcancavel {
    static int f() {
        return 1;
        System.out.println("nunca");
    }
}
```

Laços com condição **constante** também entram na análise. Um `while (true)` sem `break` nunca termina, então o que vem depois é inalcançável; e o corpo de um `while (false)` nunca roda:

```java nao-compila
while (true) {
    System.out.println("x");
}
System.out.println("depois");
```

Com um `break` possível, o laço pode terminar, e o código seguinte volta a ser alcançável:

```java executar
int n = 0;
while (true) {
    if (++n > 3) {
        break;
    }
}
System.out.println(n);
```

```saida
4
```

A grande exceção é o `if`: `if (false) { ... }` **compila**. A linguagem abriu essa porta de propósito, para que se possa ligar e desligar trechos com uma constante (`static final boolean DEBUG = false;`). Você viu o compilador apagar esse código no episódio sobre [compiladores](/assistir/aprendiz-t2-e03).

> [!PROVA]
> "Constante" inclui variáveis `final` inicializadas com constante. Com `final boolean LIGADO = true;`, o laço `while (LIGADO) { }` é tratado como `while (true)`, e o comando seguinte não compila. Sem o `final`, o compilador não sabe o valor, e compila.

## Atribuição definida

Uma variável **local** precisa ter um valor certo antes de cada leitura, em **todos** os caminhos. O compilador não executa o programa: ele só olha a estrutura. Um `if` sem `else` deixa um caminho sem atribuição:

```java nao-compila
int x;
boolean ok = Math.random() > 2;
if (ok) {
    x = 1;
}
System.out.println(x);
```

Mesmo que `ok` seja sempre falso na prática, o erro é "variable x might not have been initialized". As formas de corrigir: um `else`, um valor inicial na declaração, ou um `switch` com `default`. E aqui as constantes de novo mudam a análise: com `if (true)`, o caminho do "falso" não existe, e a variável conta como atribuída:

```java executar
int x;
if (true) {
    x = 1;
}
System.out.println(x);
final boolean SEMPRE = true;
int y;
if (SEMPRE) {
    y = 2;
}
System.out.println(y);
```

```saida
1
2
```

Campos de classe não têm essa exigência: eles começam com o valor padrão (`0`, `false`, `null`). A regra vale só para variáveis locais.

Uma variável `final` local tem a regra inversa: precisa ser atribuída **no máximo uma vez** em cada caminho. Atribuí-la num `if` e de novo depois dele não compila ("variable might already have been assigned").

## Todo caminho precisa de `return`

Num método que devolve valor, nenhum caminho pode chegar ao fim do corpo sem `return` (ou sem lançar uma exceção):

```java nao-compila
public class Retorno {
    static String classificar(int n) {
        if (n > 0) {
            return "positivo";
        } else if (n < 0) {
            return "negativo";
        }
    }
}
```

Para nós, é óbvio que sobra o caso `n == 0`; para o compilador, existe um caminho em que os dois testes falham e o método chega à `}` final. O erro "missing return statement" é apontado nessa chave. Por outro lado, um método cujo único fim possível é um `return` dentro de um laço infinito compila sem `return` no final:

```java executar
public class SemReturn {
    static int primeiroPar(int[] v) {
        int i = 0;
        while (true) {
            if (v[i] % 2 == 0) {
                return v[i];
            }
            i++;
        }
    }

    public static void main(String[] args) {
        System.out.println(primeiroPar(new int[] {3, 7, 8, 5}));
    }
}
```

```saida
8
```

O `while (true)` sem `break` nunca termina normalmente, então a `}` final do método é inalcançável, e não há caminho sem `return`. Se o array não tiver par, o laço passa do fim e lança `ArrayIndexOutOfBoundsException`, o que também é um jeito legítimo de sair do método.

## Escopo e sombreamento

Duas variáveis locais com o mesmo nome não podem estar vivas ao mesmo tempo. Um bloco interno não pode redeclarar uma variável do bloco externo:

```java nao-compila
int total = 0;
if (total == 0) {
    int total = 5;
}
```

Mas blocos **em sequência** podem reaproveitar o nome, porque a primeira variável já deixou de existir quando a segunda é declarada:

```java executar
{
    int temp = 1;
    System.out.println(temp);
}
{
    int temp = 2;
    System.out.println(temp);
}
```

```saida
1
2
```

Um campo, por outro lado, **pode** ser sombreado por uma variável local de mesmo nome: dentro do método vale a local, e o campo continua acessível com `this.nome`. É o padrão dos construtores, assunto do cargo Júnior.

## Por baixo dos panos

Essas três verificações são uma fase específica do `javac`, chamada **flow** na [visão geral da compilação](/assistir/aprendiz-t2-e03) do OpenJDK: depois de conferir os tipos, o compilador monta o grafo de caminhos de cada método e calcula, ponto por ponto, quais variáveis estão certamente atribuídas e se o ponto é alcançável. Isso é análise estática: o compilador não sabe que `Math.random() > 2` é sempre falso, porque não executa nada; só usa constantes.

A JVM refaz parte do trabalho. O verificador de bytecode, que você viu no episódio da [JVM](/assistir/aprendiz-t2-e04), rejeita uma classe que leia uma variável local nunca escrita, mesmo que ela tenha vindo de outro compilador. Desde o Java 7, o `javac` grava no `.class` "fotografias" dos tipos de cada variável nos pontos de desvio (as *stack map frames*), para o verificador checar tudo numa única passada.

## Resumo para a prova

- Comando depois de `return`, `throw`, `break` ou `continue` no mesmo bloco não compila
- `while (true)` sem `break` torna o código seguinte inalcançável; o corpo de `while (false)` também é
- `if (false)` é a exceção: compila
- `final` inicializada com constante conta como constante na análise de fluxo
- Variável local precisa de valor em todos os caminhos antes de ser lida; `if (true)` conta como caminho único
- Campos não precisam de atribuição: têm valor padrão
- Métodos com retorno precisam de `return` ou `throw` em todos os caminhos; um laço infinito dispensa o `return` final
- Bloco interno não redeclara variável local do externo; blocos em sequência podem
