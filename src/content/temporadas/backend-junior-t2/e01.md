Todo backend conversa por **HTTP**. O aplicativo do celular pedindo a lista de pedidos, o site enviando um formulário, um serviço consultando outro: tudo é uma **requisição** HTTP que recebe uma **resposta**. Antes de qualquer framework, vale ver o protocolo como ele é: texto, enviado por uma conexão de rede, num formato simples o bastante para ser escrito à mão. Entender esse texto, os métodos, os códigos de status e os cabeçalhos, é o que separa quem "usa uma API" de quem consegue depurar uma.

## Uma conversa em texto

No HTTP/1.1, o cliente abre uma conexão TCP com o servidor e envia linhas de texto terminadas por `\r\n`. O programa abaixo faz isso com sockets crus, sem biblioteca nenhuma: um servidor numa thread, que imprime o que recebeu, e um cliente que escreve a requisição à mão e imprime a resposta.

```java executar
import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStreamReader;
import java.io.OutputStream;
import java.io.UncheckedIOException;
import java.net.InetAddress;
import java.net.ServerSocket;
import java.net.Socket;
import java.nio.charset.StandardCharsets;
import java.util.List;

public class HttpNaMao {
    public static void main(String[] args) throws Exception {
        try (ServerSocket servidor = new ServerSocket(0, 1, InetAddress.getLoopbackAddress())) {
            Thread atendente = new Thread(() -> atender(servidor));
            atendente.start();
            try (Socket cliente = new Socket(InetAddress.getLoopbackAddress(), servidor.getLocalPort())) {
                String pedido = "GET /produtos/42 HTTP/1.1\r\n"
                        + "Host: loja.exemplo\r\n"
                        + "Accept: application/json\r\n"
                        + "\r\n";
                cliente.getOutputStream().write(pedido.getBytes(StandardCharsets.UTF_8));
                List<String> resposta = new BufferedReader(
                        new InputStreamReader(cliente.getInputStream(), StandardCharsets.UTF_8)).lines().toList();
                System.out.println("--- o cliente recebeu ---");
                resposta.forEach(System.out::println);
            }
            atendente.join();
        }
    }

    static void atender(ServerSocket servidor) {
        try (Socket conexao = servidor.accept()) {
            BufferedReader entrada = new BufferedReader(
                    new InputStreamReader(conexao.getInputStream(), StandardCharsets.UTF_8));
            System.out.println("--- o servidor recebeu ---");
            String linha;
            while (!(linha = entrada.readLine()).isEmpty()) {
                System.out.println(linha);
            }
            byte[] corpo = "{\"id\":42,\"nome\":\"Teclado\"}".getBytes(StandardCharsets.UTF_8);
            OutputStream saida = conexao.getOutputStream();
            saida.write(("HTTP/1.1 200 OK\r\n"
                    + "Content-Type: application/json\r\n"
                    + "Content-Length: " + corpo.length + "\r\n"
                    + "\r\n").getBytes(StandardCharsets.UTF_8));
            saida.write(corpo);
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }
    }
}
```

```saida
--- o servidor recebeu ---
GET /produtos/42 HTTP/1.1
Host: loja.exemplo
Accept: application/json
--- o cliente recebeu ---
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 26

{"id":42,"nome":"Teclado"}
```

As duas mensagens têm a mesma forma:

| Parte | Na requisição | Na resposta |
|---|---|---|
| Primeira linha | Método, alvo e versão: `GET /produtos/42 HTTP/1.1` | Versão, status e frase: `HTTP/1.1 200 OK` |
| Cabeçalhos | Um por linha, `Nome: valor` | Idem |
| Linha em branco | Marca o fim dos cabeçalhos | Idem |
| Corpo | Opcional; num `GET`, normalmente vazio | O conteúdo: JSON, HTML, uma imagem |

O cabeçalho `Host` é obrigatório no HTTP/1.1: o mesmo endereço IP pode hospedar centenas de sites, e é por ele que o servidor sabe qual foi pedido. E o `Content-Length` diz quantos **bytes** de corpo vêm depois da linha em branco; sem ele, o cliente não saberia onde a resposta termina.

## Métodos

O método diz o que o cliente quer fazer com o recurso indicado pelo caminho:

| Método | Uso | Seguro | Idempotente |
|---|---|---|---|
| `GET` | Ler um recurso | sim | sim |
| `HEAD` | Como o `GET`, mas só os cabeçalhos, sem corpo | sim | sim |
| `POST` | Criar um recurso ou disparar um processamento | não | não |
| `PUT` | Substituir o recurso inteiro pelo enviado | não | sim |
| `PATCH` | Alterar parte do recurso | não | não garantido |
| `DELETE` | Remover o recurso | não | sim |
| `OPTIONS` | Perguntar o que o servidor aceita, usado pelo navegador no CORS | sim | sim |

**Seguro** quer dizer que o método não altera nada no servidor: um `GET` pode ser repetido, guardado em cache e chamado por um robô de busca sem efeito colateral. **Idempotente** quer dizer que repetir a mesma requisição deixa o servidor no mesmo estado que uma só: apagar o pedido 42 duas vezes resulta no pedido 42 apagado, e um `PUT` com o mesmo corpo grava o mesmo valor. Já dois `POST /pedidos` criam **dois** pedidos. Isso importa quando a rede falha: um cliente pode reenviar um `PUT` ou um `DELETE` sem medo, mas reenviar um `POST` de pagamento pode cobrar duas vezes.

> [!ATENCAO]
> Um `GET` que altera dados, como `GET /pedidos/42/cancelar`, é um defeito, não uma escolha de estilo. Navegadores pré-carregam links, proxies repetem requisições e robôs seguem tudo o que encontram: o pedido seria cancelado por quem só queria olhar.

## Códigos de status

O status é um número de três dígitos, e o primeiro dígito diz a classe:

| Classe | Significa | Os mais comuns |
|---|---|---|
| `1xx` | Informativo, a resposta continua | `101 Switching Protocols` (WebSocket) |
| `2xx` | Sucesso | `200 OK`, `201 Created`, `204 No Content` |
| `3xx` | Redirecionamento | `301 Moved Permanently`, `302 Found`, `304 Not Modified`, `307` e `308` |
| `4xx` | Erro do **cliente**: repetir igual não vai adiantar | `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found`, `409 Conflict`, `422 Unprocessable Content`, `429 Too Many Requests` |
| `5xx` | Erro do **servidor**: o pedido podia estar certo | `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout` |

Os que mais confundem:

- **`401` ou `403`?** O `401` significa "não sei quem você é": faltam credenciais, ou elas são inválidas. O `403` significa "sei quem você é, e você não pode": um cliente logado tentando ver o pedido de outro cliente.
- **`400` ou `422`?** O `400` é para uma requisição malformada, como um JSON que nem se consegue ler. O `422` é para um JSON bem formado com dados inválidos, como uma quantidade negativa. Muitas APIs usam o `400` para os dois; o importante é ser consistente.
- **`302` ou `307`?** Os dois redirecionam temporariamente, mas o `307` garante que o método e o corpo sejam mantidos; com o `302`, clientes antigos trocavam um `POST` por `GET`. O `308` é o equivalente permanente do `307`.
- **`304 Not Modified`** responde a um `GET` condicional: o cliente manda o `ETag` da versão que já tem em `If-None-Match`, e o servidor responde "nada mudou", sem corpo.

Com o servidor HTTP que vem no JDK, `com.sun.net.httpserver.HttpServer`, e o cliente `java.net.http.HttpClient`, dá para ver os status de uma pequena API de produtos:

```java executar
import com.sun.net.httpserver.HttpExchange;
import com.sun.net.httpserver.HttpServer;
import java.io.IOException;
import java.net.InetAddress;
import java.net.InetSocketAddress;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;

public class Status {
    static void responder(HttpExchange troca) throws IOException {
        String metodo = troca.getRequestMethod();
        String caminho = troca.getRequestURI().getPath();
        if (metodo.equals("GET") && caminho.equals("/produtos/42")) {
            enviar(troca, 200, "{\"id\":42,\"nome\":\"Teclado\"}");
        } else if (metodo.equals("POST") && caminho.equals("/produtos")) {
            troca.getResponseHeaders().add("Location", "/produtos/43");
            enviar(troca, 201, "{\"id\":43,\"nome\":\"Mouse\"}");
        } else if (metodo.equals("DELETE") && caminho.equals("/produtos/42")) {
            troca.sendResponseHeaders(204, -1);
        } else if (caminho.startsWith("/produtos")) {
            enviar(troca, 404, "{\"erro\":\"produto não encontrado\"}");
        }
        troca.close();
    }

    static void enviar(HttpExchange troca, int status, String json) throws IOException {
        byte[] corpo = json.getBytes(StandardCharsets.UTF_8);
        troca.getResponseHeaders().add("Content-Type", "application/json");
        troca.sendResponseHeaders(status, corpo.length);
        troca.getResponseBody().write(corpo);
    }

    public static void main(String[] args) throws Exception {
        HttpServer servidor = HttpServer.create(new InetSocketAddress(InetAddress.getLoopbackAddress(), 0), 0);
        servidor.createContext("/", Status::responder);
        servidor.start();
        String base = "http://127.0.0.1:" + servidor.getAddress().getPort();
        try (HttpClient cliente = HttpClient.newBuilder().version(HttpClient.Version.HTTP_1_1).build()) {
            HttpRequest[] pedidos = {
                HttpRequest.newBuilder(URI.create(base + "/produtos/42")).GET().build(),
                HttpRequest.newBuilder(URI.create(base + "/produtos/99")).GET().build(),
                HttpRequest.newBuilder(URI.create(base + "/produtos"))
                        .header("Content-Type", "application/json")
                        .POST(HttpRequest.BodyPublishers.ofString("{\"nome\":\"Mouse\"}")).build(),
                HttpRequest.newBuilder(URI.create(base + "/produtos/42")).DELETE().build(),
            };
            for (HttpRequest pedido : pedidos) {
                HttpResponse<String> resposta = cliente.send(pedido, HttpResponse.BodyHandlers.ofString());
                System.out.printf("%-6s %-13s -> %d %s%s%n",
                        pedido.method(), pedido.uri().getPath(), resposta.statusCode(),
                        resposta.headers().firstValue("Location").map(l -> "Location: " + l + " ").orElse(""),
                        resposta.body());
            }
        } finally {
            servidor.stop(0);
        }
    }
}
```

```saida
GET    /produtos/42  -> 200 {"id":42,"nome":"Teclado"}
GET    /produtos/99  -> 404 {"erro":"produto não encontrado"}
POST   /produtos     -> 201 Location: /produtos/43 {"id":43,"nome":"Mouse"}
DELETE /produtos/42  -> 204
```

O `201 Created` vem com o cabeçalho `Location`, o endereço do recurso criado. O `204 No Content` é o sucesso sem corpo, típico de um `DELETE`. E o servidor foi criado na porta `0`, o que pede ao sistema operacional uma porta livre qualquer; o `HttpClient` é o assunto de um [episódio inteiro](/assistir/backend-junior-t2-e04) desta temporada.

## Cabeçalhos

Os nomes de cabeçalho **não diferenciam maiúsculas de minúsculas**: `Content-Type` e `content-type` são o mesmo. Os que aparecem todo dia:

| Cabeçalho | Onde | Para quê |
|---|---|---|
| `Content-Type` | Requisição e resposta | O formato do corpo **enviado**: `application/json; charset=utf-8` |
| `Accept` | Requisição | Os formatos que o cliente **aceita** receber |
| `Content-Length` | Requisição e resposta | O tamanho do corpo, em bytes |
| `Authorization` | Requisição | As credenciais: `Bearer <token>` ou `Basic <base64>` |
| `Location` | Resposta | O endereço do recurso criado (`201`) ou do redirecionamento (`3xx`) |
| `Cache-Control` | Resposta | Por quanto tempo a resposta pode ser guardada: `max-age=60`, `no-store` |
| `ETag` / `If-None-Match` | Resposta / requisição | A versão do recurso, para o `304` |
| `Set-Cookie` / `Cookie` | Resposta / requisição | O servidor guarda um valor no navegador, que o devolve a cada requisição |
| `Retry-After` | Resposta | Quanto esperar antes de tentar de novo, com `429` e `503` |

`Content-Type` e `Accept` formam a **negociação de conteúdo**: o cliente diz o que aceita, e o servidor responde num desses formatos, ou com `406 Not Acceptable`.

## Sem estado

Cada requisição HTTP é independente: o servidor não "lembra" das anteriores. Para que um usuário continue logado, alguma informação precisa viajar em **toda** requisição: um cookie de sessão, que o navegador envia sozinho, ou um token no `Authorization`, que o cliente envia. Essa falta de estado é o que permite colocar dez cópias do mesmo servidor atrás de um balanceador de carga: qualquer uma pode atender qualquer requisição.

## Versões e HTTPS

- **HTTP/1.1** (1997, revisado em 2022 nas RFCs 9110 e 9112): texto, uma requisição por vez em cada conexão, mas a conexão é reaproveitada (*keep-alive*).
- **HTTP/2** (2015): os mesmos métodos, status e cabeçalhos, mas em **quadros binários**, várias requisições ao mesmo tempo na mesma conexão e cabeçalhos comprimidos.
- **HTTP/3** (2022): o HTTP/2 sobre o **QUIC**, um protocolo sobre UDP, que evita que um pacote perdido trave todas as requisições da conexão.

**HTTPS** é o HTTP dentro de uma conexão **TLS**: o caminho, os cabeçalhos e o corpo vão cifrados, e o certificado prova que o servidor é quem diz ser. Quem observa a rede ainda vê o endereço IP e, em geral, o nome do site, mas não o que foi pedido. Em produção, nada de HTTP sem o S.

## Por baixo dos panos

Uma conexão TCP é um fluxo contínuo de bytes, sem divisões. Por isso o HTTP/1.1 precisa dizer onde cada mensagem termina: os cabeçalhos terminam na primeira linha em branco, `\r\n\r\n`, e o corpo, depois de `Content-Length` bytes. Quando o servidor não sabe o tamanho de antemão, como numa resposta gerada aos poucos, ele usa `Transfer-Encoding: chunked`: o corpo vem em pedaços, cada um precedido do tamanho em hexadecimal, até um pedaço de tamanho zero. Um erro nessa contagem é grave: se o servidor e um proxy no caminho discordam de onde uma requisição termina, os bytes que sobram viram o começo de outra requisição, um ataque conhecido como *request smuggling*.

O `Content-Length` conta **bytes**, não caracteres. `"Teclado"` tem 7 de cada, mas `"Café"` tem 4 caracteres e 5 bytes em UTF-8, porque o `é` ocupa dois. Usar `String.length()` como `Content-Length` funciona com texto em inglês e corta o fim das respostas em português.

## Resumo

- Requisição: método, alvo e versão; cabeçalhos; linha em branco; corpo. Resposta: versão, status e frase; cabeçalhos; linha em branco; corpo
- `GET` e `HEAD` são seguros; `GET`, `PUT` e `DELETE` são idempotentes; `POST` não é
- `2xx` sucesso, `3xx` redirecionamento, `4xx` erro do cliente, `5xx` erro do servidor; `201` com `Location`, `204` sem corpo
- `401` sem identificação, `403` sem permissão; `400` malformado, `422` inválido
- Cabeçalhos sem diferença de maiúsculas; `Content-Type` diz o que vai, `Accept` diz o que se aceita
- HTTP não tem estado: cookies e tokens viajam em cada requisição; HTTPS cifra tudo com TLS
- `Content-Length` conta bytes, não caracteres
