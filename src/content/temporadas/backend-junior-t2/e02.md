Uma API é um **contrato**. Do outro lado estão o aplicativo do celular, o site, outros serviços do time e, às vezes, sistemas de clientes que você nunca vai conhecer. Depois que alguém começa a usar um endereço, mudá-lo quebra esse alguém. Por isso o desenho de uma API merece mais cuidado que o código por trás dela: o código se refatora numa tarde, e um contrato ruim acompanha o projeto por anos. O estilo dominante para esse desenho é o **REST**, e este episódio mostra as convenções que fazem uma API ser previsível para quem a consome.

## Recursos, não ações

No REST, a API expõe **recursos**, coisas com nome, como pedidos, clientes e produtos, cada um identificado por uma **URI**. O cliente não chama funções: ele aplica os métodos do HTTP, sempre os mesmos, sobre os recursos. Os caminhos são **substantivos**, e o verbo é o método:

| Evite | Prefira |
|---|---|
| `POST /criarPedido` | `POST /pedidos` |
| `GET /buscarPedido?id=42` | `GET /pedidos/42` |
| `POST /pedidos/42/deletar` | `DELETE /pedidos/42` |
| `GET /pedido/42` e `GET /pedidos` | Sempre o plural: `/pedidos` e `/pedidos/42` |
| `GET /Pedidos/42` ou `/itens_pedido` | Minúsculas e hífen: `/itens-do-pedido` |

## O mapa de uma coleção

Uma coleção bem desenhada tem sempre o mesmo formato, e quem usou uma já sabe usar todas:

| Requisição | Faz | Sucesso | Erros comuns |
|---|---|---|---|
| `GET /pedidos` | Lista, com filtros e paginação | `200` | `400` filtro inválido |
| `POST /pedidos` | Cria | `201` + `Location` | `400`, `422` |
| `GET /pedidos/42` | Busca um | `200` | `404` |
| `PUT /pedidos/42` | Substitui o pedido inteiro | `200` ou `204` | `404`, `422` |
| `PATCH /pedidos/42` | Altera alguns campos | `200` ou `204` | `404`, `422` |
| `DELETE /pedidos/42` | Remove | `204` | `404` |
| `GET /pedidos/42/itens` | Lista um **sub-recurso** | `200` | `404` se o pedido não existe |

Duas respostas de erro costumam ser esquecidas. Se o caminho não existe, é `404`. Mas se o caminho existe e o método não, como um `PATCH` numa API que só aceita `PUT`, é `405 Method Not Allowed`, com o cabeçalho `Allow` listando os métodos aceitos. Todo framework web tem um **roteador** que faz essa distinção, e a lógica dele cabe em poucas linhas:

```java executar
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.TreeSet;

public class Rotas {
    record Rota(String metodo, String modelo, String acao) {}

    static final List<Rota> ROTAS = List.of(
            new Rota("GET", "/pedidos", "listar pedidos"),
            new Rota("POST", "/pedidos", "criar pedido"),
            new Rota("GET", "/pedidos/{id}", "buscar pedido"),
            new Rota("PUT", "/pedidos/{id}", "substituir pedido"),
            new Rota("DELETE", "/pedidos/{id}", "apagar pedido"),
            new Rota("GET", "/pedidos/{id}/itens/{item}", "buscar item"));

    static Map<String, String> casar(String modelo, String caminho) {
        String[] m = modelo.split("/"), c = caminho.split("/");
        if (m.length != c.length) return null;
        Map<String, String> parametros = new LinkedHashMap<>();
        for (int i = 0; i < m.length; i++) {
            if (m[i].startsWith("{")) {
                parametros.put(m[i].substring(1, m[i].length() - 1), c[i]);
            } else if (!m[i].equals(c[i])) {
                return null;
            }
        }
        return parametros;
    }

    static String rotear(String metodo, String caminho) {
        TreeSet<String> permitidos = new TreeSet<>();
        for (Rota rota : ROTAS) {
            Map<String, String> parametros = casar(rota.modelo(), caminho);
            if (parametros == null) continue;
            if (rota.metodo().equals(metodo)) return "200 " + rota.acao() + " " + parametros;
            permitidos.add(rota.metodo());
        }
        return permitidos.isEmpty() ? "404 Not Found" : "405 Method Not Allowed, Allow: " + String.join(", ", permitidos);
    }

    public static void main(String[] args) {
        String[][] pedidos = {
            {"GET", "/pedidos"},
            {"GET", "/pedidos/42"},
            {"GET", "/pedidos/42/itens/7"},
            {"PATCH", "/pedidos/42"},
            {"GET", "/clientes/1"},
        };
        for (String[] p : pedidos) {
            System.out.println(p[0] + " " + p[1] + " -> " + rotear(p[0], p[1]));
        }
    }
}
```

```saida
GET /pedidos -> 200 listar pedidos {}
GET /pedidos/42 -> 200 buscar pedido {id=42}
GET /pedidos/42/itens/7 -> 200 buscar item {id=42, item=7}
PATCH /pedidos/42 -> 405 Method Not Allowed, Allow: DELETE, GET, PUT
GET /clientes/1 -> 404 Not Found
```

Os trechos entre chaves são **variáveis de caminho**, extraídas da URI. No Spring, que vem na [temporada 4](/assistir/backend-junior-t4-e03), a mesma ideia aparece como `@GetMapping("/pedidos/{id}")` e `@PathVariable`.

## Ações que não são CRUD

Cancelar um pedido não é criar, ler, alterar nem apagar. Há duas saídas comuns. A mais fiel ao REST é tratar a ação como um recurso: `POST /pedidos/42/cancelamento` cria um cancelamento. A mais pragmática, adotada no guia de APIs do Google, é um método personalizado com dois-pontos: `POST /pedidos/42:cancelar`. O que não se faz é `GET /pedidos/42/cancelar`, porque um `GET` nunca altera nada.

## Filtros, ordenação e paginação

Tudo o que **refina** uma listagem vai na query string, nunca no caminho:

```text
GET /pedidos?status=PAGO&cliente=7&ordenar=-criadoEm&pagina=2&tamanho=20
```

Uma lista sem paginação funciona com 50 pedidos e derruba o servidor com 5 milhões. Defina um tamanho padrão e um máximo, e devolva junto os dados para navegar:

```json
{
  "itens": [
    { "id": 41, "status": "PAGO", "total": 150.00 },
    { "id": 38, "status": "PAGO", "total": 89.90 }
  ],
  "pagina": 2,
  "tamanho": 20,
  "total": 143
}
```

Essa é a paginação por **deslocamento** (*offset*). Ela tem dois defeitos em tabelas grandes: o banco precisa percorrer e descartar todas as linhas das páginas anteriores, e um pedido criado enquanto o usuário navega empurra os outros, que aparecem repetidos na página seguinte. A paginação por **cursor** resolve os dois: a resposta traz um marcador do último item, como `"proximo": "eyJpZCI6Mzh9"`, e a próxima página pede "os 20 depois deste". É o que feeds e APIs grandes usam.

## Erros que ajudam

Um erro precisa de um status correto e de um corpo que explique o problema. Nunca responda `200 OK` com `{"erro": ...}` dentro: clientes, proxies e monitoramento olham o status. A RFC 9457, *Problem Details for HTTP APIs*, padroniza esse corpo, com o tipo `application/problem+json`:

```json
{
  "type": "https://api.loja.exemplo/erros/estoque-insuficiente",
  "title": "Estoque insuficiente",
  "status": 422,
  "detail": "O produto 7 tem 2 unidades, e o pedido pede 5.",
  "instance": "/pedidos",
  "erros": [
    { "campo": "itens[0].quantidade", "mensagem": "máximo de 2" }
  ]
}
```

O `type` identifica a categoria do erro, de preferência um endereço com a documentação; `title` é o resumo; `detail`, a explicação deste caso; e campos extras, como `erros`, são permitidos. O Spring tem a classe `ProblemDetail` exatamente para isso. E jamais devolva o *stack trace* da exceção: ele ensina a um atacante quais bibliotecas e versões você usa.

## Evoluir sem quebrar

Algumas mudanças são seguras, porque um cliente bem escrito as ignora: um campo novo na resposta, um campo **opcional** novo na requisição, um endpoint novo. Outras quebram quem já usa a API: remover ou renomear um campo, mudar o tipo dele, tornar obrigatório um campo que era opcional, mudar o significado de um status. Quando uma mudança incompatível é inevitável, ela vai numa **nova versão**, e a antiga continua no ar por um tempo combinado. O jeito mais comum é a versão no caminho, `/v1/pedidos` e `/v2/pedidos`; outros times preferem um cabeçalho. Do lado do cliente, a regra é ser um **leitor tolerante**: ignorar campos que não conhece, em vez de falhar.

## POST idempotente

O `POST` não é idempotente, e isso é um problema quando a rede falha: o aplicativo enviou o pagamento, a conexão caiu antes da resposta, e ele não sabe se o pagamento foi criado. Reenviar pode cobrar duas vezes. A solução usada por APIs de pagamento é o cabeçalho **`Idempotency-Key`**: o cliente gera um identificador único, como um UUID, para cada operação e o envia em todas as tentativas dela. O servidor guarda a resposta associada à chave e, ao ver a mesma chave de novo, devolve a resposta guardada, sem refazer a cobrança. A proposta de padrão da IETF para esse cabeçalho define os erros: `400` se a chave obrigatória faltar, `422` se a mesma chave vier com outro corpo, e `409` se a primeira requisição ainda estiver em processamento.

## O modelo de maturidade

Leonard Richardson descreveu quatro níveis, que ajudam a avaliar uma API:

| Nível | Característica | Exemplo |
|---|---|---|
| 0 | Um endpoint só, tudo via `POST`, a ação no corpo | `POST /api` com `{"acao": "buscarPedido", "id": 42}` |
| 1 | Recursos com URIs próprias | `POST /pedidos/42` |
| 2 | Métodos e status do HTTP usados com o significado certo | `GET /pedidos/42` → `200` ou `404` |
| 3 | Hipermídia: as respostas trazem links para as próximas ações | `"_links": {"cancelar": {"href": "/pedidos/42/cancelamento"}}` |

A grande maioria das APIs chamadas de REST está no nível 2, e esse é o alvo realista de um projeto: recursos bem nomeados, métodos e status corretos.

## Por baixo dos panos

O REST não é um protocolo nem um padrão com especificação: é um **estilo de arquitetura**, descrito por Roy Fielding em 2000, na tese de doutorado em que ele resumiu os princípios que tinham guiado o desenho do HTTP/1.1, do qual era um dos autores. Um sistema é REST quando respeita um conjunto de restrições: cliente e servidor separados; **sem estado** entre requisições; respostas que declaram se podem ir para **cache**; uma **interface uniforme**, com recursos identificados por URIs, manipulados por representações e com hipermídia guiando o cliente; e um **sistema em camadas**, em que o cliente não sabe se fala com o servidor final ou com um intermediário.

Cada restrição compra uma propriedade. Sem estado, qualquer cópia do servidor atende qualquer requisição, e escalar é só adicionar cópias atrás de um balanceador. Com respostas cacheáveis e camadas, uma CDN pode responder milhões de `GET` sem que eles cheguem ao servidor. Por isso "usar JSON sobre HTTP" não basta para ser REST, e por isso também, na prática, quase ninguém implementa o nível 3: as restrições são uma régua, e cada time decide até onde ir.

## Resumo

- URIs são substantivos no plural; o verbo é o método: `GET /pedidos/42`, não `GET /buscarPedido?id=42`
- Coleção: `GET` lista, `POST` cria (`201` + `Location`), `GET`/`PUT`/`PATCH`/`DELETE` em `/pedidos/{id}`
- Caminho inexistente é `404`; método não aceito é `405` com `Allow`
- Filtros, ordenação e paginação na query string; paginação por cursor em listas grandes
- Erros com o status certo e corpo no formato Problem Details (RFC 9457), sem *stack trace*
- Mudanças aditivas são seguras; as que quebram vão numa nova versão
- `Idempotency-Key` torna seguro reenviar um `POST`; a maioria das APIs REST está no nível 2 de Richardson
