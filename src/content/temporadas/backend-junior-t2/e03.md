Quase toda API moderna fala **JSON**: o corpo das requisições e das respostas do [episódio anterior](/assistir/backend-junior-t2-e02) era JSON, montado à mão com concatenação de strings. Num projeto de verdade, ninguém faz isso. Uma biblioteca converte objetos Java em JSON e de volta, e no ecossistema Java essa biblioteca é o **Jackson**, que o Spring Boot usa por padrão. Este episódio cobre as regras do formato, as armadilhas com números, o Jackson na prática e as diferenças entre as versões 2 e 3, que convivem nos projetos de hoje.

## O formato

O JSON (RFC 8259) tem só seis tipos de valor:

| JSON | Exemplo | Em Java, costuma virar |
|---|---|---|
| Objeto | `{"sku": "TEC-1", "quantidade": 2}` | Um `record`, uma classe ou um `Map` |
| Lista | `[1, 2, 3]` | `List` |
| Texto | `"Ana"` | `String`, `LocalDate`, um `enum` |
| Número | `150.00`, `-3`, `1e6` | `int`, `long`, `BigDecimal`, `double` |
| Booleano | `true`, `false` | `boolean` |
| Nulo | `null` | `null` |

As regras são estritas, e quase todo erro de "JSON inválido" vem de uma delas:

- Nomes e textos usam **aspas duplas**. `{'nome': 'Ana'}` e `{nome: "Ana"}` não são JSON.
- **Não há vírgula sobrando**: `[1, 2,]` e `{"a": 1,}` são inválidos.
- **Não há comentários.**
- Números não têm zero à esquerda (`007`), não são hexadecimais e não incluem `NaN` nem `Infinity`.
- Dentro de um texto, aspas e barras vão escapadas: `"disse \"oi\""`, `"C:\\pasta"`, e uma quebra de linha é `\n`.

## Cuidado com os números

O JSON não define precisão para números, mas o JavaScript, que consome muitas APIs, guarda todo número como um `double` do IEEE 754. Um `double` representa inteiros exatos só até 2⁵³ (9.007.199.254.740.992). Acima disso, o navegador arredonda o número sem avisar:

```java executar
import java.math.BigDecimal;

public class Precisao {
    public static void main(String[] args) {
        long id = 9007199254740993L;
        double comoNoJavaScript = id;
        System.out.println(id);
        System.out.println((long) comoNoJavaScript);
        System.out.println(0.1 + 0.2);
        System.out.println(new BigDecimal("0.1").add(new BigDecimal("0.2")));
    }
}
```

```saida
9007199254740993
9007199254740992
0.30000000000000004
0.3
```

Um id de pedido que vira outro id no frontend é um defeito difícil de achar. Daí duas regras práticas: identificadores que podem passar de 2⁵³, como os gerados por algoritmos do tipo Snowflake, trafegam como **texto** (`"id": "9007199254740993"`); e dinheiro nunca é `double`, nem no Java nem no JSON. No Java, use `BigDecimal`; no JSON, um número decimal lido direto para `BigDecimal`, ou o valor em centavos como inteiro.

## Jackson

O Jackson tem duas gerações em uso. O **Jackson 3**, lançado em 2025, é o padrão do Spring Boot 4 e fica no pacote `tools.jackson`; o **Jackson 2**, do pacote `com.fasterxml.jackson`, é o dos projetos com Spring Boot 3 ou anterior. A API é quase a mesma, e as diferenças estão numa tabela mais abaixo. Os exemplos usam o Jackson 3.1, com a dependência `tools.jackson.core:jackson-databind`.

A classe central é o `ObjectMapper`, que converte nos dois sentidos:

```java
import tools.jackson.databind.ObjectMapper;

record Item(String sku, int quantidade) {}

record Pedido(long id, String cliente, List<Item> itens, BigDecimal total,
              LocalDateTime criadoEm, String cupom) {}

ObjectMapper mapper = new ObjectMapper();
Pedido p = new Pedido(42, "Ana", List.of(new Item("TEC-1", 2)), new BigDecimal("150.00"),
        LocalDateTime.of(2025, 9, 16, 14, 30), null);

String json = mapper.writeValueAsString(p);     // objeto → JSON
Pedido lido = mapper.readValue(json, Pedido.class); // JSON → objeto
```

```text
{"id":42,"cliente":"Ana","itens":[{"sku":"TEC-1","quantidade":2}],"total":150.00,"criadoEm":"2025-09-16T14:30:00","cupom":null}
Pedido[id=42, cliente=Ana, itens=[Item[sku=TEC-1, quantidade=2]], total=150.00, criadoEm=2025-09-16T14:30, cupom=null]
```

`record`s funcionam diretamente: os componentes viram os campos do JSON, na ordem em que foram declarados, e o construtor canônico é usado na leitura. Classes comuns precisam de um construtor sem argumentos e de *getters* e *setters*, ou de um construtor anotado com `@JsonCreator`. O `BigDecimal` preservou o `150.00`, e o `LocalDateTime` virou um texto no formato ISO 8601. O `ObjectMapper` é caro de criar e seguro para usar em várias threads: crie um só e reaproveite, que é o que o Spring faz.

Para JSON formatado, há o `mapper.writerWithDefaultPrettyPrinter()`:

```text
{
  "sku" : "MOU-2",
  "quantidade" : 1
}
```

### Listas e tipos genéricos

Por causa do apagamento de tipos, `List<Item>.class` não existe, e `readValue(json, List.class)` não tem como saber o tipo dos elementos: ele devolve uma lista de `LinkedHashMap`. A solução é uma `TypeReference`, uma subclasse anônima que guarda o tipo genérico completo:

```java
List<Item> itens = mapper.readValue(json, new TypeReference<List<Item>>() {});
List<?> crua = mapper.readValue(json, List.class);
```

```text
[Item[sku=A, quantidade=1], Item[sku=B, quantidade=3]] Item
[{sku=A, quantidade=1}] LinkedHashMap
```

### A árvore de nós

Quando não existe uma classe para o JSON, ou só um campo interessa, o `readTree` devolve uma árvore de `JsonNode`. O `get` devolve `null` para um campo que não existe; o `path` devolve um nó "ausente", que permite encadear sem `NullPointerException`:

```java
JsonNode raiz = mapper.readTree(json);
raiz.get("itens").get(0).get("sku").asString();  // "TEC-1"
raiz.path("naoExiste").isMissingNode();          // true
```

### Anotações

As anotações ficam no pacote `com.fasterxml.jackson.annotation`, nas duas versões:

```java
@JsonInclude(JsonInclude.Include.NON_NULL)
record Resumo(@JsonProperty("valor_total") BigDecimal total,
              String cupom,
              @JsonIgnore String senhaInterna) {}

mapper.writeValueAsString(new Resumo(new BigDecimal("99.90"), null, "segredo"));
```

```text
{"valor_total":99.90}
```

O `@JsonProperty` troca o nome no JSON, o `@JsonIgnore` deixa o campo de fora, e o `@JsonInclude(NON_NULL)` omite os nulos, como o `cupom`. Para mudar o padrão de nomes de todas as classes de uma vez, configura-se o mapper:

```java
ObjectMapper snake = JsonMapper.builder()
        .propertyNamingStrategy(PropertyNamingStrategies.SNAKE_CASE)
        .build();
snake.writeValueAsString(new Entrega("01001-000", LocalDate.of(2025, 9, 20)));
```

```text
{"cep":"01001-000","prevista":"2025-09-20"}
```

### Erros

Cada tipo de problema tem a sua exceção, e as mensagens são precisas:

```text
{"sku":"X",}               → StreamReadException: Unexpected character ('}' (code 125)): was expecting double-quote to start property name
{"sku":"X","quantidade":"dois"} → InvalidFormatException: Cannot deserialize value of type `int` from String "dois": not a valid `int` value
{"sku":"X"}                → MismatchedInputException: Cannot map `null` into type `int`
```

Num controller do Spring, essas exceções viram `400 Bad Request` automaticamente.

## Jackson 2 ou 3?

Os dois mappers abaixo foram criados com `new ObjectMapper()`, sem configuração nenhuma:

| | Jackson 2.21 | Jackson 3.1 |
|---|---|---|
| Pacote | `com.fasterxml.jackson.databind` | `tools.jackson.databind` |
| Anotações | `com.fasterxml.jackson.annotation` | as mesmas |
| Exceções | Verificadas, filhas de `IOException` | Não verificadas, filhas de `RuntimeException` |
| `java.time` | Exige o módulo `jackson-datatype-jsr310` | Embutido |
| `LocalDateTime` com o módulo | `[2025,9,16,14,30]` | `"2025-09-16T14:30:00"` |
| Campo desconhecido no JSON | Falha com `UnrecognizedPropertyException` | Ignorado |
| `int` ausente no JSON | Vira `0` | Falha com `MismatchedInputException` |
| Ordem dos campos de uma classe comum | A da declaração | Alfabética (os `record`s mantêm a da declaração) |

Os três últimos itens mudam o comportamento de uma API sem mudar uma linha de código, numa migração. E o Spring Boot não usa o `new ObjectMapper()` puro: ele cria um mapper com ajustes próprios, por exemplo deixando de falhar com campos desconhecidos já no Jackson 2. Na dúvida, escreva um teste que leia o JSON que importa.

> [!ATENCAO]
> Não converta o JSON da requisição direto na entidade do banco. Se a classe `Cliente` tem um campo `administrador`, um cliente malicioso só precisa enviar `"administrador": true`. Receba um `record` com só os campos que o cliente pode enviar, um DTO, e copie para a entidade. E nunca ative a "tipagem padrão" do Jackson (`activateDefaultTyping`) com dados de fora: ela deixa o JSON escolher que classe instanciar, e foi a origem de dezenas de vulnerabilidades.

## Por baixo dos panos

Como o Jackson descobre os campos de um `record`? Por **reflexão**. A classe `Class` tem o método `getRecordComponents()`, que lista os componentes na ordem de declaração, cada um com o nome e o método de acesso. Com isso e um `instanceof` para cada tipo de valor, dá para escrever um serializador que produz exatamente o mesmo JSON do Jackson para o pedido acima:

```java executar
import java.lang.reflect.RecordComponent;
import java.math.BigDecimal;
import java.time.LocalDateTime;
import java.time.format.DateTimeFormatter;
import java.time.temporal.Temporal;
import java.util.Collection;
import java.util.List;
import java.util.Map;
import java.util.StringJoiner;

public class MiniJackson {
    record Item(String sku, int quantidade) {}

    record Pedido(long id, String cliente, List<Item> itens, BigDecimal total, LocalDateTime criadoEm, String cupom) {}

    static String json(Object valor) throws ReflectiveOperationException {
        if (valor == null) return "null";
        if (valor instanceof Number || valor instanceof Boolean) return valor.toString();
        if (valor instanceof LocalDateTime data) return texto(DateTimeFormatter.ISO_LOCAL_DATE_TIME.format(data));
        if (valor instanceof String || valor instanceof Temporal) return texto(valor.toString());
        if (valor instanceof Collection<?> lista) {
            StringJoiner sj = new StringJoiner(",", "[", "]");
            for (Object item : lista) sj.add(json(item));
            return sj.toString();
        }
        if (valor instanceof Map<?, ?> mapa) {
            StringJoiner sj = new StringJoiner(",", "{", "}");
            for (Map.Entry<?, ?> e : mapa.entrySet()) sj.add(texto(e.getKey().toString()) + ":" + json(e.getValue()));
            return sj.toString();
        }
        if (valor.getClass().isRecord()) {
            StringJoiner sj = new StringJoiner(",", "{", "}");
            for (RecordComponent c : valor.getClass().getRecordComponents()) {
                sj.add(texto(c.getName()) + ":" + json(c.getAccessor().invoke(valor)));
            }
            return sj.toString();
        }
        throw new IllegalArgumentException("tipo não suportado: " + valor.getClass());
    }

    static String texto(String s) {
        StringBuilder sb = new StringBuilder("\"");
        for (char ch : s.toCharArray()) {
            switch (ch) {
                case '"' -> sb.append("\\\"");
                case '\\' -> sb.append("\\\\");
                case '\n' -> sb.append("\\n");
                default -> {
                    if (ch < 0x20) sb.append(String.format("\\u%04x", (int) ch));
                    else sb.append(ch);
                }
            }
        }
        return sb.append('"').toString();
    }

    public static void main(String[] args) throws Exception {
        Pedido p = new Pedido(42, "Ana", List.of(new Item("TEC-1", 2)), new BigDecimal("150.00"),
                LocalDateTime.of(2025, 9, 16, 14, 30), null);
        System.out.println(json(p));
        System.out.println(json(Map.of("obs", "disse \"oi\"\nfoi embora")));
    }
}
```

```saida
{"id":42,"cliente":"Ana","itens":[{"sku":"TEC-1","quantidade":2}],"total":150.00,"criadoEm":"2025-09-16T14:30:00","cupom":null}
{"obs":"disse \"oi\"\nfoi embora"}
```

Um detalhe mostra o cuidado necessário: o `toString()` do `LocalDateTime` omite os segundos quando são zero, e daria `"2025-09-16T14:30"`; o Jackson usa o formatador ISO, que sempre os inclui, e por isso o serializador trata a data à parte. O Jackson de verdade faz o mesmo trabalho de forma muito mais eficiente: na primeira vez em que vê uma classe, ele a inspeciona, monta um serializador específico para ela e o guarda em cache, para que as próximas conversões não precisem de reflexão; e escreve o texto direto num fluxo de saída, sem montar `String`s intermediárias. A leitura é o caminho inverso, com um analisador que lê o texto como uma sequência de *tokens*: início de objeto, nome de campo, valor, fim de objeto.

## Resumo

- JSON: objeto, lista, texto, número, booleano e `null`; aspas duplas, sem vírgula sobrando e sem comentários
- Inteiros acima de 2⁵³ perdem precisão no JavaScript: ids grandes como texto; dinheiro como `BigDecimal`, nunca `double`
- `ObjectMapper`: `writeValueAsString` e `readValue`; crie um só e reaproveite
- `record`s funcionam direto; listas genéricas pedem `TypeReference`; `readTree` dá a árvore de `JsonNode`
- `@JsonProperty`, `@JsonIgnore`, `@JsonInclude(NON_NULL)` e estratégias de nomes no `JsonMapper.builder()`
- Jackson 3 (`tools.jackson`, Spring Boot 4) e Jackson 2 (`com.fasterxml.jackson`) diferem em exceções, datas, campos desconhecidos e primitivos ausentes
- Receba DTOs, não entidades, e nunca ative a tipagem padrão com dados de fora
