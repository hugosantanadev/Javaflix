Escrever um programa Java para testar cada endpoint seria lento demais. No dia a dia, quem trabalha com APIs usa três ferramentas: o **curl**, no terminal, para disparar requisições e ver exatamente o que vai e o que volta; um **cliente gráfico**, como o Postman, para guardar coleções de requisições; e a **OpenAPI**, a especificação que descreve o contrato da API num arquivo que pessoas e programas conseguem ler. Os exemplos deste episódio foram executados contra uma pequena API de produtos em Spring Boot 4, a mesma estrutura que você vai construir na [temporada de Spring](/assistir/backend-junior-t4-e03).

## curl

O curl vem instalado no Linux, no macOS e no Windows 10 em diante. Sem opções, ele faz um `GET` e imprime o corpo da resposta:

```text
$ curl http://localhost:8086/produtos/42
{"id":42,"nome":"Teclado","preco":199.90}
```

As opções que resolvem quase tudo:

| Opção | Faz |
|---|---|
| `-X MÉTODO` | Escolhe o método: `-X DELETE`, `-X PUT` |
| `-H 'Nome: valor'` | Acrescenta um cabeçalho |
| `-d 'corpo'` | Envia um corpo, e muda o método para `POST` se nenhum foi dado |
| `-d @pedido.json` | Lê o corpo de um arquivo |
| `--json 'corpo'` | Atalho do curl 7.82 em diante: envia o corpo com `Content-Type` e `Accept` de JSON |
| `-i` | Mostra os cabeçalhos da resposta junto com o corpo |
| `-v` | Mostra tudo: a conexão, a requisição enviada e a resposta |
| `-s` | Silencioso: sem barra de progresso nem mensagens |
| `-o arquivo` | Grava o corpo num arquivo |
| `-w '%{http_code}'` | Imprime informações da transferência, como o status |
| `-L` | Segue redirecionamentos |

Com `-i`, a resposta aparece inteira:

```text
$ curl -i http://localhost:8086/produtos/42
HTTP/1.1 200
Content-Type: application/json
Transfer-Encoding: chunked
Date: Mon, 19 Oct 2026 13:41:22 GMT

{"id":42,"nome":"Teclado","preco":199.90}
```

Dois detalhes do [primeiro episódio](/assistir/backend-junior-t2-e01) aparecem aqui. O Tomcat, servidor padrão do Spring Boot, não envia a frase depois do status, que é opcional no HTTP/1.1. E, em vez de `Content-Length`, ele usou `Transfer-Encoding: chunked`, porque escreveu o JSON enquanto o gerava.

Criar, apagar e provocar erros:

```text
$ curl -i --json '{"nome":"Mouse","preco":89.90}' http://localhost:8086/produtos
HTTP/1.1 201
Location: /produtos/43
Content-Type: application/json
Transfer-Encoding: chunked
Date: Mon, 19 Oct 2026 13:41:23 GMT

{"id":43,"nome":"Mouse","preco":89.90}

$ curl -i -X DELETE http://localhost:8086/produtos/43
HTTP/1.1 204
Date: Mon, 19 Oct 2026 13:41:23 GMT

$ curl -i -X PATCH http://localhost:8086/produtos/42
HTTP/1.1 405
Allow: DELETE, GET
Content-Type: application/problem+json
Transfer-Encoding: chunked
Date: Mon, 19 Oct 2026 13:41:23 GMT

{"detail":"Method 'PATCH' is not supported.","instance":"/produtos/42","status":405,"title":"Method Not Allowed"}

$ curl -i -H "Content-Type: application/json" -d '{"nome": "Mouse",' http://localhost:8086/produtos
HTTP/1.1 400
Content-Type: application/problem+json
Transfer-Encoding: chunked
Date: Mon, 19 Oct 2026 13:41:23 GMT
Connection: close

{"detail":"Failed to read request","instance":"/produtos","status":400,"title":"Bad Request"}
```

O `405` com `Allow` e o corpo no formato Problem Details são exatamente o que o [episódio de desenho de APIs](/assistir/backend-junior-t2-e02) recomendava; o Spring os produz sozinho, com a propriedade `spring.mvc.problemdetails.enabled=true`. Para depurar, o `-v` mostra a conversa inteira: as linhas com `>` são a requisição, as com `<`, a resposta, e as com `*`, o que o curl fez por conta própria:

```text
$ curl -v http://localhost:8086/produtos/42

* IPv6: ::1
* IPv4: 127.0.0.1
*   Trying [::1]:8086...
* Connected to localhost (::1) port 8086

> Host: localhost:8086
> User-Agent: curl/8.7.1

>

< HTTP/1.1 200
< Content-Type: application/json
< Transfer-Encoding: chunked
< Date: Mon, 19 Oct 2026 13:41:23 GMT
<

* Connection #0 to host localhost left intact
```

E, em scripts, só o status interessa:

```text
$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8086/produtos/42
200
```

### Aspas e o Windows

O corpo vai entre **aspas simples**, para que o terminal não interprete as aspas duplas do JSON. Se o próprio texto tiver uma aspa simples, ela é fechada, escapada e reaberta: `'Pão d'\''Ouro'`. No Windows, três cuidados: no Windows PowerShell 5.1, `curl` é um apelido de outro comando, o `Invoke-WebRequest`, e o curl de verdade se chama `curl.exe`; o Prompt de Comando não entende aspas simples; e acentos passados como argumento podem chegar corrompidos ao servidor, dependendo do terminal. Para corpos com acentos, ou grandes, use um arquivo: `curl --json @pedido.json ...`.

As ferramentas de desenvolvedor do navegador e o Postman têm a opção **Copiar como cURL**, que transforma uma requisição num comando pronto. A conversão, com o cuidado das aspas, cabe em poucas linhas:

```java executar
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.StringJoiner;

public class ComoCurl {
    record Requisicao(String metodo, String url, Map<String, String> cabecalhos, String corpo) {}

    static String aspas(String texto) {
        return "'" + texto.replace("'", "'\\''") + "'";
    }

    static String curl(Requisicao r) {
        StringJoiner sj = new StringJoiner(" \\\n  ");
        sj.add("curl -X " + r.metodo() + " " + aspas(r.url()));
        r.cabecalhos().forEach((nome, valor) -> sj.add("-H " + aspas(nome + ": " + valor)));
        if (r.corpo() != null) sj.add("-d " + aspas(r.corpo()));
        return sj.toString();
    }

    public static void main(String[] args) {
        Map<String, String> cabecalhos = new LinkedHashMap<>();
        cabecalhos.put("Content-Type", "application/json");
        cabecalhos.put("Authorization", "Bearer abc123");
        System.out.println(curl(new Requisicao("POST", "http://localhost:8086/produtos?origem=app&teste=1",
                cabecalhos, "{\"nome\":\"Pão d'Ouro\",\"preco\":12.50}")));
    }
}
```

```saida
curl -X POST 'http://localhost:8086/produtos?origem=app&teste=1' \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer abc123' \
  -d '{"nome":"Pão d'\''Ouro","preco":12.50}'
```

A URL também vai entre aspas: sem elas, o `&` da query string mandaria o terminal rodar o comando em segundo plano, e o `teste=1` viraria outro comando.

> [!ATENCAO]
> Um comando copiado como cURL leva junto o `Authorization` e os cookies. Antes de colar num chat, numa issue ou num pull request, apague o token: ele dá acesso à conta de quem o gerou.

## Clientes gráficos

O **Postman**, o **Insomnia** e o **Bruno** guardam requisições em **coleções**, com **variáveis de ambiente** (`{{baseUrl}}`, `{{token}}`) para trocar entre desenvolvimento, homologação e produção sem reescrever nada. O Bruno e o cliente HTTP do IntelliJ guardam as requisições em arquivos de texto, que podem ir para o Git junto com o código. No IntelliJ, um arquivo `.http` fica assim:

```text
### Busca um produto
GET http://localhost:8086/produtos/42
Accept: application/json

### Cria um produto
POST http://localhost:8086/produtos
Content-Type: application/json

{"nome": "Mouse", "preco": 89.90}
```

Cada bloco tem um botão para executar. Os valores secretos ficam num arquivo de ambiente privado, fora do Git.

## OpenAPI

A **OpenAPI** é uma especificação para descrever APIs HTTP: os endereços, os métodos, os parâmetros, os corpos e as respostas, num arquivo YAML ou JSON. Ela nasceu como a Especificação Swagger e foi doada à Linux Foundation em 2015; hoje, "OpenAPI" é o formato, e "Swagger" é o nome de um conjunto de ferramentas que o usam, como o Swagger UI e o Swagger Editor. A versão 3.1, de 2021, alinhou os esquemas ao JSON Schema.

Num projeto Spring Boot, a biblioteca **springdoc-openapi** gera o documento a partir do código. Basta a dependência `org.springdoc:springdoc-openapi-starter-webmvc-ui`, na linha 3.x para o Spring Boot 4, e a aplicação ganha três endereços: `/v3/api-docs`, com o documento em JSON; `/v3/api-docs.yaml`, em YAML; e `/swagger-ui/index.html`, uma página que lista os endpoints e permite testá-los pelo navegador.

Gerado só a partir do código, o documento da API de produtos tinha problemas: o `POST` aparecia respondendo `200`, e não `201`; o `DELETE`, `200` em vez de `204`; nenhum `404` estava documentado; e o tipo do conteúdo era `*/*`. A razão é que o `ResponseEntity.created(...)` decide o status **durante a execução**, e uma ferramenta que só lê as assinaturas dos métodos não tem como saber. As anotações completam o que o código não diz:

```java
@Tag(name = "Produtos", description = "Catálogo da loja")
@RestController
@RequestMapping(path = "/produtos", produces = "application/json")
public class ProdutoController {

    @Operation(summary = "Cria um produto")
    @ApiResponse(responseCode = "201", description = "Produto criado")
    @PostMapping
    public ResponseEntity<Produto> criar(@RequestBody NovoProduto novo) { ... }

    @Operation(summary = "Busca um produto pelo id")
    @ApiResponse(responseCode = "200", description = "Produto encontrado")
    @ApiResponse(responseCode = "404", description = "Produto não existe", content = @Content)
    @GetMapping("/{id}")
    public ResponseEntity<Produto> buscar(@PathVariable long id) { ... }
}
```

Com elas, e um `@Bean` do tipo `OpenAPI` com o título e a versão, o documento gerado passou a ser este (um trecho):

```yaml
openapi: 3.1.0
info:
  title: API da Loja
  version: "1.0"
paths:
  /produtos:
    post:
      tags:
      - Produtos
      summary: Cria um produto
      operationId: criar
      requestBody:
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/NovoProduto"
        required: true
      responses:
        "201":
          description: Produto criado
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/Produto"
  /produtos/{id}:
    get:
      tags:
      - Produtos
      summary: Busca um produto pelo id
      operationId: buscar
      parameters:
      - name: id
        in: path
        required: true
        schema:
          type: integer
          format: int64
      responses:
        "200":
          description: Produto encontrado
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/Produto"
        "404":
          description: Produto não existe
components:
  schemas:
    Produto:
      type: object
      properties:
        id:
          type: integer
          format: int64
        nome:
          type: string
        preco:
          type: number
```

As partes principais: `info` identifica a API; `paths` tem uma entrada por caminho e, dentro dela, uma por método, com `parameters`, `requestBody` e `responses`; e `components/schemas` define os formatos dos objetos uma vez só, referenciados com `$ref`. O `long` virou `integer` com `format: int64`, e o `BigDecimal`, `number`.

### Código primeiro ou contrato primeiro?

O que foi feito acima é **código primeiro**: escreve-se a API e gera-se o documento. É rápido, mas o contrato só existe depois que o código está pronto, e as anotações precisam acompanhar cada mudança. No **contrato primeiro**, o time escreve o YAML antes, revisa-o num pull request com quem vai consumir a API, e só então implementa; ferramentas como o OpenAPI Generator produzem, a partir do mesmo arquivo, as interfaces Java do servidor e clientes em várias linguagens. O frontend pode até começar a trabalhar contra um servidor simulado, gerado do contrato. Times com muitos consumidores tendem ao contrato primeiro; os outros, ao código primeiro.

Em qualquer dos dois, o documento serve para muito mais que ler: gerar clientes, validar requisições num *gateway*, alimentar testes de contrato e publicar um portal de desenvolvedores.

## Por baixo dos panos

Como o springdoc descobre os endpoints? Durante a inicialização, o Spring MVC registra cada método anotado com `@GetMapping`, `@PostMapping` e companhia numa tabela, o `RequestMappingHandlerMapping`, com o caminho, o método HTTP e o método Java correspondente. O springdoc percorre essa tabela e, para cada entrada, usa **reflexão** nos parâmetros e no tipo de retorno: um `@PathVariable long id` vira um parâmetro `in: path` do tipo `integer`; um `record` vira um esquema com uma propriedade por componente, a mesma inspeção que o Jackson faz. As anotações `@Operation` e `@ApiResponse` são lidas da mesma forma e se sobrepõem ao que foi deduzido. O Swagger UI, por sua vez, é só uma página estática em JavaScript: ela baixa o `/v3/api-docs` e desenha, a partir dele, a lista de endpoints e os formulários para testá-los.

Um esquema também serve para **validar**: cada propriedade pode dizer o tipo, se é obrigatória, um mínimo, um tamanho máximo ou uma lista de valores aceitos, e qualquer corpo pode ser conferido contra essas regras antes de chegar ao código da aplicação. É o que o desafio deste episódio faz.

## Resumo

- `curl`: `-X`, `-H`, `-d` ou `--json`, `-i` para cabeçalhos, `-v` para depurar, `-s -o /dev/null -w '%{http_code}'` em scripts
- Corpo e URL entre aspas simples; no Windows, `curl.exe` e corpos em arquivo com `-d @arquivo.json`
- "Copiar como cURL" leva tokens junto: apague antes de compartilhar
- Postman, Insomnia, Bruno e arquivos `.http`: coleções e variáveis de ambiente, segredos fora do Git
- OpenAPI descreve `paths`, operações, parâmetros, corpos, respostas e `components/schemas`; Swagger são as ferramentas
- springdoc gera `/v3/api-docs` e o Swagger UI; anotações documentam o que o código só decide em execução, como o `201`
- Contrato primeiro permite revisar e gerar código antes; código primeiro é mais rápido, mas o documento pode se desatualizar
