No primeiro dia num time de backend, antes de escrever qualquer linha de Java, você vai clonar um repositório, criar uma branch e abrir um pull request. O **Git** é a ferramenta que guarda o histórico de todo o código, permite que dezenas de pessoas trabalhem no mesmo projeto sem se atropelar e deixa voltar a qualquer versão anterior. E quase tudo nele acontece no **terminal**. Este episódio cobre o básico dos dois: o suficiente para versionar o seu próprio trabalho com segurança.

> [!ANTES]
> Antes do Git, criado por Linus Torvalds em 2005 para o código do Linux, os times usavam sistemas **centralizados**, como o CVS e o Subversion: o histórico ficava só no servidor, cada commit exigia rede, e criar uma branch era caro o bastante para ser evitado. No Git, cada clone tem o histórico inteiro, e branch é só um arquivo com um hash dentro.

## O terminal em cinco minutos

O terminal é onde se digitam comandos em vez de clicar. No Linux e no macOS, ele vem pronto; no Windows, o Git instala o **Git Bash**, que aceita os mesmos comandos. Os que você vai usar todo dia:

| Comando | Faz |
|---|---|
| `pwd` | Mostra a pasta atual |
| `ls` / `ls -la` | Lista os arquivos, com `-la` inclusive os ocultos |
| `cd pasta` / `cd ..` | Entra numa pasta / sobe um nível |
| `mkdir pasta` | Cria uma pasta |
| `cat arquivo` | Mostra o conteúdo de um arquivo |
| `echo texto > arquivo` | Escreve o texto no arquivo, **substituindo** o conteúdo |
| `echo texto >> arquivo` | Acrescenta o texto ao fim do arquivo |
| `comando1 \| comando2` | Manda a saída de um comando para a entrada do outro |

A tecla Tab completa nomes de arquivos e comandos, e a seta para cima traz os comandos anteriores. Com isso, você já anda pelo projeto.

## Configurando o Git

Todo commit leva o nome e o e-mail de quem o fez. A configuração é feita uma vez por máquina:

```bash
git config --global user.name "Ana Lima"
git config --global user.email "ana@exemplo.com"
git config --global init.defaultBranch main
```

Use o mesmo e-mail da sua conta no GitHub: é por ele que os commits aparecem ligados ao seu perfil.

## As três áreas

O Git separa o trabalho em três lugares, e entender isso resolve metade das dúvidas:

```text
 diretório de trabalho  --git add-->  área de preparação  --git commit-->  repositório
 (os arquivos que você     (o que vai entrar no           (o histórico de
  edita)                    próximo commit)                 commits, na pasta .git)
```

- O **diretório de trabalho** são os arquivos do projeto como estão no disco.
- A **área de preparação** (*staging area* ou *index*) é a lista do que vai entrar no próximo commit. Ela permite commitar só parte das mudanças.
- O **repositório** guarda os **commits**: fotografias completas do projeto, cada uma com autor, data, mensagem e um ponteiro para a anterior.

## O primeiro repositório

```bash
git init loja
cd loja
echo "Loja Javaflix" > README.md
git status
```

```text
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md

nothing added to commit but untracked files present (use "git add" to track)
```

O `git status` é o comando mais importante: ele diz em que branch você está e o estado de cada arquivo. Aqui, o `README.md` é **não rastreado** (*untracked*): o Git o vê, mas ainda não o versiona. O `git add` o coloca na área de preparação, e o `git commit` grava a fotografia:

```bash
git add README.md
git commit -m "Cria o README"
```

Depois de alterar o `README.md` e criar um `App.java`, a forma curta do status mostra a situação de cada arquivo em duas colunas, a primeira para a área de preparação e a segunda para o diretório de trabalho:

```text
$ git status --short
 M README.md
?? App.java
```

| Código | Significa |
|---|---|
| `??` | Não rastreado |
| `A ` | Novo, já preparado para o commit |
| ` M` | Modificado, ainda **não** preparado |
| `M ` | Modificado e preparado |
| `MM` | Preparado, e modificado de novo depois do `add` |

> [!LAPIS]
> Você cria `Frete.java`, roda `git add Frete.java`, edita o `README.md` (já commitado) e depois edita `Frete.java` de novo. O que o `git status --short` mostra para cada arquivo?
>
> **Resposta:** `AM Frete.java` e ` M README.md`. O `Frete.java` é novo e foi preparado (`A` na primeira coluna), e ganhou uma mudança depois do `add` (`M` na segunda). O `README.md` foi modificado e ainda não foi preparado.

## Vendo o que mudou

`git diff` mostra as mudanças do diretório de trabalho que ainda não foram preparadas; `git diff --staged` mostra as que já estão na área de preparação. As linhas com `+` foram acrescentadas, e as com `-`, removidas:

```text
$ git diff
diff --git a/README.md b/README.md
index ef70a67..7355c16 100644
--- a/README.md
+++ b/README.md
@@ -1 +1,2 @@
 Loja Javaflix
+Vende cursos
```

Feito o segundo commit, o `git log --oneline` lista o histórico, do mais recente ao mais antigo, com o começo do identificador de cada commit:

```text
$ git log --oneline
f3a5aaf Adiciona a classe App
483e0d2 Cria o README
```

> [!PENSE]
> Você rodou `git add App.java`, editou o arquivo de novo e fez o commit. Qual versão do `App.java` foi gravada: a do momento do `add` ou a do momento do `commit`?

## Desfazendo

| Situação | Comando |
|---|---|
| Descartar as mudanças de um arquivo no diretório de trabalho | `git restore arquivo` |
| Tirar um arquivo da área de preparação, sem perder a mudança | `git restore --staged arquivo` |
| Corrigir a mensagem ou o conteúdo do último commit | `git commit --amend` |

> [!ATENCAO]
> `git restore arquivo` apaga mudanças que nunca foram commitadas, e não há como recuperá-las. E o `--amend` cria um commit **novo** no lugar do antigo: use só em commits que ainda não foram enviados para o servidor.

No Windows, o Git avisa às vezes que "LF will be replaced by CRLF": ele converte as quebras de linha do Windows para o padrão do Unix ao guardar, e de volta ao tirar. É normal.

> [!PERGUNTAS]
> **P:** Se eu errei e o arquivo já foi commitado, perdi tudo?
>
> **R:** Não. Tudo o que foi commitado fica no histórico, e `git log` mais `git restore --source=<hash> arquivo` trazem qualquer versão de volta. O que se perde de verdade é o que nunca foi commitado.
>
> **P:** Preciso fazer `git add` de cada arquivo?
>
> **R:** Não: `git add .` prepara tudo da pasta atual. Mas olhe o `git status` antes, para não levar junto um arquivo que não deveria ir.
>
> **P:** Qual a diferença entre o Git e o GitHub?
>
> **R:** O Git é o programa que guarda o histórico na sua máquina. O GitHub é um serviço que hospeda repositórios Git na internet, com pull requests e revisões, assunto do episódio 4.

## O que não versionar

Arquivos gerados pelo build, configurações da sua IDE e senhas não entram no repositório. Eles são listados num arquivo `.gitignore`, na raiz do projeto:

```text
target/
build/
*.class
.idea/
*.iml
.env
```

Um arquivo já commitado continua sendo rastreado mesmo depois de entrar no `.gitignore`; é preciso tirá-lo com `git rm --cached arquivo`. E uma senha que chegou a ser commitada deve ser considerada vazada, mesmo que o commit seja apagado depois.

> [!PREVENCAO]
> Crie o `.gitignore` **antes** do primeiro commit e, nos commits seguintes, prefira `git add -p`, que mostra cada trecho e pergunta se ele entra. É a forma mais barata de nunca commitar um `.env`, um *dump* do banco ou um `System.out.println` de depuração esquecido.

## Boas mensagens de commit

A mensagem é lida por quem investiga um defeito meses depois. Uma linha de resumo curta, de até uns 50 caracteres, no imperativo ("Adiciona", "Corrige", não "Adicionei"), e, se preciso, uma linha em branco e um corpo explicando o **porquê**. Muitos times adotam o padrão *Conventional Commits*, com um prefixo do tipo da mudança: `feat: adiciona cálculo de frete`, `fix: corrige arredondamento do desconto`, `docs:`, `test:`, `refactor:`.

> [!IA]
> Assistentes escrevem mensagens de commit a partir do `git diff --staged`, e escrevem bem o **o quê**. O **porquê**, que é a parte que importa meses depois, eles não sabem: inventam um motivo plausível. Revise a mensagem, troque o motivo inventado pelo real e confira que o assistente não pôs no commit um arquivo que você não preparou.

## Na IDE

- **Painel de commit.** No IntelliJ, **Ctrl + K** abre o commit com a lista de arquivos alterados; marcar e desmarcar arquivos é o `git add` visual, e dá para escolher trechos de um arquivo.
- **Diferenças na margem.** Linhas alteradas ganham uma faixa colorida na margem do editor; clicar nela mostra o trecho anterior e permite desfazê-lo.
- **Histórico de um arquivo.** Botão direito no arquivo, *Git > Show History*, lista os commits que o mudaram, com o diff de cada um.

## Por baixo dos panos

A pasta `.git` é um banco de dados de **objetos**, cada um identificado pelo **hash SHA-1** do seu conteúdo. Há três tipos principais: o **blob**, com o conteúdo de um arquivo; a **árvore**, que lista os arquivos e pastas de um diretório, apontando para blobs e outras árvores; e o **commit**, que aponta para uma árvore, para o commit anterior e guarda autor, data e mensagem. O comando `git cat-file -p HEAD` mostra o commit mais recente como ele está guardado:

```text
tree f33ecbdf7262f83187b175b9365f0c4b6a11ed1a
parent 483e0d22485266b527433d2295247b2b1b80dc6d
author Ana Lima <ana@exemplo.com> 1758031200 -0300
committer Ana Lima <ana@exemplo.com> 1758031200 -0300

Adiciona a classe App
```

O hash de um blob é o SHA-1 de um cabeçalho, com o tipo e o tamanho, seguido do conteúdo. Dá para calculá-lo em Java e chegar ao mesmo valor que o Git mostrou no `diff` acima, `ef70a67` para a primeira versão do README:

```java executar
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.util.HexFormat;

public class HashGit {
    static String hashDeBlob(String conteudo) throws Exception {
        byte[] dados = conteudo.getBytes(StandardCharsets.UTF_8);
        byte[] cabecalho = ("blob " + dados.length + "\0").getBytes(StandardCharsets.UTF_8); //> O tamanho é em bytes, não em caracteres.
        MessageDigest sha1 = MessageDigest.getInstance("SHA-1");
        sha1.update(cabecalho);
        sha1.update(dados); //> O hash cobre cabeçalho e conteúdo juntos.
        return HexFormat.of().formatHex(sha1.digest());
    }

    public static void main(String[] args) throws Exception {
        System.out.println(hashDeBlob("Loja Javaflix\n"));
        System.out.println(hashDeBlob("Loja Javaflix\nVende cursos\n"));
    }
}
```

```saida
ef70a67cf975bb4bfe632a012955d98dee441bf7
7355c165057a348a93b667f40fdd779d2b454e33
```

Os dois hashes são exatamente os da linha `index ef70a67..7355c16` do `diff`. Isso tem consequências práticas: o mesmo conteúdo sempre gera o mesmo hash, e por isso o Git guarda cada versão de um arquivo uma vez só, mesmo que ela apareça em mil commits; e mudar um único byte de qualquer commit antigo mudaria o hash dele e de todos os seguintes, o que torna o histórico à prova de adulteração silenciosa. Versões recentes do Git também aceitam repositórios com SHA-256, mais resistente a colisões.

> [!MATEMATICA]
> O SHA-1 tem 160 bits, impressos como 40 dígitos hexadecimais (4 bits cada). O `git log --oneline` mostra só os 7 primeiros, que são 28 bits: 2²⁸ ≈ 268 milhões de prefixos. Pelo paradoxo do aniversário, a chance de dois de n objetos terem o mesmo prefixo é perto de n² ÷ (2 × 2²⁸). Com 10.000 objetos, 10⁸ ÷ (5,4 × 10⁸) ≈ **19%**; por isso o Git aumenta a abreviação sozinho em repositórios grandes. Com os 40 dígitos inteiros, a mesma conta dá um número com dezenas de zeros depois da vírgula.

## Resumo

- Terminal: `pwd`, `ls`, `cd`, `mkdir`, `cat`, `>`, `>>` e `|`; Tab completa
- `git config --global user.name` e `user.email` antes do primeiro commit
- Três áreas: diretório de trabalho, área de preparação (`git add`) e repositório (`git commit`)
- `git status` (e `--short`), `git diff`, `git diff --staged` e `git log --oneline`
- `git restore`, `git restore --staged` e `git commit --amend` (só em commits locais)
- `.gitignore` para build, IDE e segredos; commits são objetos identificados pelo SHA-1 do conteúdo
