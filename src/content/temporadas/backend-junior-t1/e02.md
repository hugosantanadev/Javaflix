Num time, várias pessoas mexem no mesmo código ao mesmo tempo: uma cria o cálculo de frete, outra corrige um defeito no login, uma terceira testa uma ideia que talvez nem vá para produção. As **branches** são o que permite isso sem que um trabalho atrapalhe o outro, e o **merge** é como elas se juntam de novo. Às vezes, duas pessoas alteram a mesma linha, e o Git não sabe qual versão escolher: é o **conflito**, que todo desenvolvedor resolve várias vezes por semana.

## O que é uma branch

No [episódio anterior](/assistir/backend-junior-t1-e01), cada commit apontava para o commit pai. Uma **branch** é só um **nome que aponta para um commit**: o mais recente daquela linha de trabalho. Criar uma branch é criar um ponteiro novo, o que é instantâneo, e cada commit novo empurra o ponteiro da branch atual para a frente. Um ponteiro especial, o **`HEAD`**, indica em qual branch você está.

| Comando | Faz |
|---|---|
| `git branch` | Lista as branches; a atual tem um `*` |
| `git switch -c feature/frete` | Cria a branch e passa para ela |
| `git switch main` | Passa para uma branch existente |
| `git merge feature/frete` | Traz os commits de `feature/frete` para a branch atual |
| `git branch -d feature/frete` | Apaga a branch, se ela já foi mesclada |
| `git log --oneline --graph --all` | Desenha o histórico de todas as branches |

O `git switch` é do Git 2.23; em material mais antigo, você verá `git checkout -b`, que faz o mesmo. Os nomes com prefixo, como `feature/`, `fix/` e `hotfix/`, são uma convenção comum dos times, não uma regra do Git.

## Merge fast-forward

Se a `main` não andou desde que a branch foi criada, o merge não precisa juntar nada: basta mover o ponteiro da `main` para a frente, até o último commit da branch. Isso se chama **fast-forward**:

```text
$ git switch -c feature/frete
$ # edita e commita "Aumenta o frete"
$ git switch main
$ git merge feature/frete
Updating c8f5854..c3c13c8
Fast-forward
 config.txt | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

$ git log --oneline --graph --all
* c3c13c8 Aumenta o frete
* c8f5854 Configuração inicial
```

O histórico continua uma linha reta, sem commit de merge.

## Merge de três vias

Se as duas branches andaram, o Git faz um **merge de três vias**: compara as duas pontas com o **ancestral comum**, o último commit que as duas têm. O que mudou só num lado entra; o que mudou nos dois lados de forma diferente é conflito. O resultado é um **commit de merge**, com dois pais:

```text
$ git merge --no-edit feature/desconto
Merge made by the 'ort' strategy.
 config.txt | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

$ git log --oneline --graph --all
*   7447ff6 Merge branch 'feature/desconto'
|\
| * 34709a3 Cria desconto
* | ff2da81 Adiciona README
|/
* c3c13c8 Aumenta o frete
```

A `main` ganhou o README enquanto a branch criava o desconto; as mudanças não se tocavam, e o Git juntou as duas sozinho. O `ort` é o algoritmo de merge padrão desde o Git 2.34.

## Conflitos

Agora a `main` muda o frete para 20 e uma branch o muda para 0, na mesma linha:

```text
$ git merge feature/frete-gratis
Auto-merging config.txt
CONFLICT (content): Merge conflict in config.txt
Automatic merge failed; fix conflicts and then commit the result.

$ git status --short
UU config.txt
```

O merge para no meio, e o arquivo fica com **marcadores de conflito**:

```text
<<<<<<< HEAD
frete=20
=======
frete=0
>>>>>>> feature/frete-gratis
desconto=5
```

Entre `<<<<<<<` e `=======` está a versão da branch atual (`HEAD`); entre `=======` e `>>>>>>>`, a da branch que está chegando. A linha `desconto=5`, igual nos dois lados, ficou fora do conflito. Para resolver:

1. Edite o arquivo e deixe o conteúdo certo, **sem os marcadores**. Pode ser um lado, o outro ou uma combinação dos dois.
2. Rode `git add config.txt` para marcar o conflito como resolvido.
3. Rode `git commit` para concluir o merge.

Se preferir desistir, `git merge --abort` volta tudo para antes do merge. A decisão de qual versão vale é de negócio, não de Git: na dúvida, converse com quem fez a outra mudança.

A lógica do merge de três vias, linha a linha, cabe num método. O exemplo compara cada linha das duas versões com a do ancestral: se só um lado mudou, vale a mudança; se os dois mudaram de forma diferente, sai o conflito com os mesmos marcadores do Git.

```java executar
import java.util.ArrayList;
import java.util.List;

public class Mescla {
    static List<String> mesclar(List<String> base, List<String> nossa, List<String> deles, String nomeDeles) {
        List<String> resultado = new ArrayList<>();
        for (int i = 0; i < base.size(); i++) {
            String b = base.get(i), n = nossa.get(i), d = deles.get(i);
            if (n.equals(d)) {
                resultado.add(n);
            } else if (n.equals(b)) {
                resultado.add(d);
            } else if (d.equals(b)) {
                resultado.add(n);
            } else {
                resultado.add("<<<<<<< HEAD");
                resultado.add(n);
                resultado.add("=======");
                resultado.add(d);
                resultado.add(">>>>>>> " + nomeDeles);
            }
        }
        return resultado;
    }

    public static void main(String[] args) {
        List<String> base = List.of("frete=15", "desconto=0", "parcelas=3");
        List<String> main = List.of("frete=20", "desconto=0", "parcelas=3");
        List<String> outra = List.of("frete=0", "desconto=0", "parcelas=6");
        mesclar(base, main, outra, "feature/frete-gratis").forEach(System.out::println);
    }
}
```

```saida
<<<<<<< HEAD
frete=20
=======
frete=0
>>>>>>> feature/frete-gratis
desconto=0
parcelas=6
```

As parcelas mudaram só na outra branch e entraram sem conflito; o frete mudou nos dois lados e precisa de uma decisão humana.

> [!DICA]
> Conflitos ficam menores quanto mais curtas forem as branches. Integrar com a `main` todo dia, em vez de uma vez por mês, é a forma mais eficaz de evitá-los. E o IntelliJ e o VS Code têm telas de resolução com as três versões lado a lado, mais fáceis que editar os marcadores à mão.

## Por baixo dos panos

Uma branch é literalmente um arquivo de texto: `.git/refs/heads/main` contém só os 40 caracteres do hash do commit para onde ela aponta. Por isso criar uma branch não copia arquivo nenhum e leva milissegundos. O `HEAD` é outro arquivo, `.git/HEAD`, que contém `ref: refs/heads/main`, a branch atual. Um commit novo grava o objeto e atualiza esse ponteiro; um fast-forward apenas reescreve o arquivo com o hash mais novo.

Para um merge de três vias, o Git calcula o **ancestral comum** com o comando `git merge-base`, percorrendo o grafo de pais das duas pontas. O algoritmo `ort` então compara as árvores das três versões, arquivo por arquivo; dentro de cada arquivo alterado nos dois lados, compara as linhas com um algoritmo de *diff*, como o do exemplo, mas capaz de lidar com linhas inseridas e removidas. Também detecta arquivos renomeados, para que uma mudança num arquivo movido não vire um conflito. Durante um conflito, a área de preparação guarda as três versões do arquivo, chamadas de estágios 1, 2 e 3, e é isso que as ferramentas gráficas mostram lado a lado.

## Resumo

- Uma branch é um ponteiro para um commit; `HEAD` aponta para a branch atual
- `git switch -c nome` cria e troca; `git switch nome` troca; `git branch -d nome` apaga
- Fast-forward: a branch de destino não andou, e o ponteiro só avança
- Merge de três vias: compara as pontas com o ancestral comum e cria um commit de merge com dois pais
- Conflito: os dois lados mudaram a mesma parte; edite, tire os marcadores, `git add` e `git commit`
- `git merge --abort` desiste; branches curtas e integração frequente evitam conflitos
