Um projeto de verdade não se compila com `javac` na mão. Ele tem dezenas de bibliotecas, cada uma com as suas próprias dependências, testes que precisam rodar antes de cada entrega e um JAR para gerar no fim. As **ferramentas de build** cuidam de tudo isso a partir de um arquivo de configuração: baixam as bibliotecas, montam o classpath, compilam, testam e empacotam. No mundo Java, são duas: o **Maven**, de 2004, configurado em XML e famoso pelas convenções, e o **Gradle**, de 2012, configurado em código Kotlin ou Groovy e famoso pela velocidade. Todo projeto Spring Boot nasce com um dos dois, e você vai ler e mexer nesses arquivos toda semana.

## Coordenadas e repositórios

Toda biblioteca é identificada por três **coordenadas**:

| Coordenada | Exemplo | Significa |
|---|---|---|
| `groupId` | `com.fasterxml.jackson.core` | A organização, em geral um domínio invertido |
| `artifactId` | `jackson-databind` | O nome do artefato |
| `version` | `2.17.2` | A versão |

Juntas, costumam ser escritas como `com.fasterxml.jackson.core:jackson-databind:2.17.2`. As bibliotecas públicas ficam no **Maven Central**, que o Maven e o Gradle usam por padrão. Na primeira vez em que uma versão é pedida, ela é baixada para um cache local, e daí em diante vem do disco: no Maven, `~/.m2/repository`; no Gradle, `~/.gradle/caches`.

## A estrutura padrão

Os dois seguem a mesma organização de pastas, e quem a respeita não precisa configurar nada:

```text
loja/
├── pom.xml                  (ou build.gradle.kts)
├── src/
│   ├── main/java/           o código da aplicação
│   ├── main/resources/      configurações, como o application.properties
│   ├── test/java/           os testes
│   └── test/resources/      arquivos usados só nos testes
└── target/                  saída do Maven (no Gradle, build/), fora do Git
```

## O pom.xml

O Maven lê o **POM** (*Project Object Model*), o arquivo `pom.xml` na raiz do projeto:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0">
    <modelVersion>4.0.0</modelVersion>

    <groupId>br.com.javaflix</groupId>
    <artifactId>loja</artifactId>
    <version>1.0.0-SNAPSHOT</version>

    <properties>
        <maven.compiler.release>21</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>
        <dependency>
            <groupId>com.fasterxml.jackson.core</groupId>
            <artifactId>jackson-databind</artifactId>
            <version>2.17.2</version>
        </dependency>
        <dependency>
            <groupId>org.junit.jupiter</groupId>
            <artifactId>junit-jupiter</artifactId>
            <version>5.12.2</version>
            <scope>test</scope>
        </dependency>
    </dependencies>

    <build>
        <pluginManagement>
            <plugins>
                <plugin><artifactId>maven-compiler-plugin</artifactId><version>3.14.1</version></plugin>
                <plugin><artifactId>maven-surefire-plugin</artifactId><version>3.5.6</version></plugin>
                <!-- e os demais plugins do ciclo: clean, resources, jar, install -->
            </plugins>
        </pluginManagement>
    </build>
</project>
```

O próprio projeto tem coordenadas, as do topo. A propriedade `maven.compiler.release` define a versão do Java, como o `--release` do `javac`. E o bloco `pluginManagement` fixa as versões dos plugins que fazem o trabalho: sem ele, cada versão do Maven usa as suas, e o mesmo projeto pode se comportar diferente em duas máquinas. Projetos Spring Boot herdam essas versões do *parent* do Spring.

## O ciclo de vida do Maven

O Maven organiza o build em **fases**, sempre na mesma ordem. Pedir uma fase executa todas as anteriores:

```text
validate → compile → test → package → verify → install → deploy
```

| Comando | Faz |
|---|---|
| `mvn compile` | Compila o código de `src/main/java` |
| `mvn test` | Compila e roda os testes |
| `mvn package` | Compila, testa e gera o JAR em `target/` |
| `mvn install` | Tudo isso e copia o JAR para o `~/.m2` local, para outros projetos da máquina usarem |
| `mvn clean package` | Apaga o `target/` antes, para um build do zero |
| `mvn package -DskipTests` | Empacota sem rodar os testes |

Cada fase é executada por **goals** de plugins: a fase `compile` chama o goal `compile` do `maven-compiler-plugin`, e a `test` chama o `surefire`. Um trecho do `mvn package` mostra isso:

```text
$ mvn package
[INFO] --- compiler:3.14.1:compile (default-compile) @ loja ---
[INFO] Compiling 1 source file with javac [debug release 21] to target\classes
[INFO] --- compiler:3.14.1:testCompile (default-testCompile) @ loja ---
[INFO] Compiling 1 source file with javac [debug release 21] to target\test-classes
[INFO] --- surefire:3.5.6:test (default-test) @ loja ---
[INFO] Running br.com.javaflix.loja.FreteTest
[INFO] Tests run: 2, Failures: 0, Errors: 0, Skipped: 0, Time elapsed: 0.085 s -- in br.com.javaflix.loja.FreteTest
[INFO] --- jar:3.4.2:jar (default-jar) @ loja ---
[INFO] Building jar: C:\...\loja\target\loja-1.0.0-SNAPSHOT.jar
[INFO] BUILD SUCCESS
```

Se um teste falha, o build para na fase `test`, e o JAR não é gerado.

## Escopos

O `<scope>` diz em que momento a dependência é necessária:

| Escopo | Compilação | Testes | Execução | Exemplo |
|---|---|---|---|---|
| `compile` (padrão) | sim | sim | sim | Jackson, Spring |
| `provided` | sim | sim | não, o servidor fornece | API de Servlet num servidor de aplicação |
| `runtime` | não | sim | sim | O driver JDBC do banco |
| `test` | não, só no código de teste | sim | não | JUnit, Mockito |

## Dependências transitivas e conflitos

O `jackson-databind` depende do `jackson-core` e do `jackson-annotations`, que entram no projeto sem ser declarados: são dependências **transitivas**. O `mvn dependency:tree` desenha a árvore inteira. Agora o projeto ganha também o `jackson-datatype-jsr310`, que traz o suporte às datas do `java.time`, numa versão mais nova, a 2.19.2, que depende do Jackson 2.19.2. Com `-Dverbose`, a árvore mostra o que foi descartado (sem o prefixo `[INFO]` de cada linha):

```text
$ mvn dependency:tree -Dverbose
br.com.javaflix:loja:jar:1.0.0-SNAPSHOT
+- com.fasterxml.jackson.core:jackson-databind:jar:2.17.2:compile
|  +- com.fasterxml.jackson.core:jackson-annotations:jar:2.17.2:compile
|  \- com.fasterxml.jackson.core:jackson-core:jar:2.17.2:compile
+- com.fasterxml.jackson.datatype:jackson-datatype-jsr310:jar:2.19.2:compile
|  +- (com.fasterxml.jackson.core:jackson-annotations:jar:2.19.2:compile - omitted for conflict with 2.17.2)
|  +- (com.fasterxml.jackson.core:jackson-core:jar:2.19.2:compile - omitted for conflict with 2.17.2)
|  \- (com.fasterxml.jackson.core:jackson-databind:jar:2.19.2:compile - omitted for conflict with 2.17.2)
\- org.junit.jupiter:junit-jupiter:jar:5.12.2:test
```

Só uma versão de cada biblioteca pode ir para o classpath, e o Maven escolhe pela regra da **mais próxima**: vence a versão declarada mais perto da raiz da árvore e, em caso de empate na profundidade, a que foi declarada primeiro. O `jackson-databind` 2.17.2 foi declarado direto, na profundidade 1, e vence o 2.19.2 que o `jsr310` pedia, na profundidade 2. A regra cabe numa busca em largura:

```java executar
import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.Deque;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class MaisProxima {
    static final Map<String, List<String>> POMS = Map.of(
            "loja:1.0", List.of("jackson-databind:2.17.2", "jackson-datatype-jsr310:2.19.2"),
            "jackson-databind:2.17.2", List.of("jackson-annotations:2.17.2", "jackson-core:2.17.2"),
            "jackson-datatype-jsr310:2.19.2", List.of("jackson-annotations:2.19.2", "jackson-core:2.19.2", "jackson-databind:2.19.2"),
            "jackson-annotations:2.17.2", List.of(),
            "jackson-core:2.17.2", List.of());

    public static void main(String[] args) {
        Map<String, String> escolhidas = new LinkedHashMap<>();
        List<String> omitidas = new ArrayList<>();
        Deque<String> fila = new ArrayDeque<>(POMS.get("loja:1.0"));
        while (!fila.isEmpty()) {
            String dependencia = fila.poll();
            String[] partes = dependencia.split(":");
            String ja = escolhidas.get(partes[0]);
            if (ja == null) {
                escolhidas.put(partes[0], partes[1]);
                fila.addAll(POMS.get(dependencia));
            } else if (!ja.equals(partes[1])) {
                omitidas.add(dependencia + ", conflito com " + ja);
            }
        }
        escolhidas.forEach((artefato, versao) -> System.out.println(artefato + ":" + versao));
        omitidas.forEach(o -> System.out.println("omitida: " + o));
    }
}
```

```saida
jackson-databind:2.17.2
jackson-datatype-jsr310:2.19.2
jackson-annotations:2.17.2
jackson-core:2.17.2
omitida: jackson-annotations:2.19.2, conflito com 2.17.2
omitida: jackson-core:2.19.2, conflito com 2.17.2
omitida: jackson-databind:2.19.2, conflito com 2.17.2
```

O build passa, mas o projeto agora roda o `jsr310` 2.19.2 em cima de um `databind` 2.17.2, mais antigo que o que ele espera. Se o `jsr310` chamar um método que só existe na 2.19, o erro aparece só **em produção**, como um `NoSuchMethodError`.

> [!ATENCAO]
> Conflitos de versão não quebram a compilação. Quando um `NoSuchMethodError` ou um `ClassNotFoundException` aparecer numa biblioteca que "está no pom", rode o `mvn dependency:tree -Dverbose` e procure o `omitted for conflict`.

A solução é declarar as versões num só lugar, o `<dependencyManagement>`. Bibliotecas formadas por vários módulos publicam um **BOM** (*bill of materials*), um POM só com as versões de todos eles, que se importa assim:

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>com.fasterxml.jackson</groupId>
            <artifactId>jackson-bom</artifactId>
            <version>2.19.2</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

Com o BOM, as dependências do Jackson são declaradas **sem** `<version>`, e todos os módulos ficam alinhados:

```text
+- com.fasterxml.jackson.core:jackson-databind:jar:2.19.2:compile
|  +- com.fasterxml.jackson.core:jackson-annotations:jar:2.19.2:compile
|  \- com.fasterxml.jackson.core:jackson-core:jar:2.19.2:compile
+- com.fasterxml.jackson.datatype:jackson-datatype-jsr310:jar:2.19.2:compile
\- org.junit.jupiter:junit-jupiter:jar:5.12.2:test
```

É exatamente o que o *parent* do Spring Boot faz por você, para centenas de bibliotecas.

## Gradle

O Gradle descreve o mesmo projeto em código. O padrão atual é o Kotlin DSL, no arquivo `build.gradle.kts`, ao lado de um `settings.gradle.kts` com `rootProject.name = "loja"`:

```kotlin
plugins {
    java
}

group = "br.com.javaflix"
version = "1.0.0-SNAPSHOT"

repositories {
    mavenCentral()
}

dependencies {
    implementation("com.fasterxml.jackson.core:jackson-databind:2.11.1")
    implementation("com.fasterxml.jackson.datatype:jackson-datatype-jsr310:2.21.5")
    testImplementation(platform("org.junit:junit-bom:6.0.3"))
    testImplementation("org.junit.jupiter:junit-jupiter")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

tasks.withType<JavaCompile> {
    options.release = 21
}

tasks.test {
    useJUnitPlatform()
}
```

Em vez de escopos, o Gradle tem **configurações**:

| Gradle | Equivale no Maven a |
|---|---|
| `implementation` | `compile` |
| `compileOnly` | `provided` |
| `runtimeOnly` | `runtime` |
| `testImplementation` | `test` |
| `api` (com o plugin `java-library`) | `compile`, exposto a quem usa a sua biblioteca |
| `platform(...)` | Importar um BOM |

Em vez de fases, **tarefas** (*tasks*) que dependem umas das outras. O `build` depende do `assemble`, que depende do `jar`, e assim por diante:

```text
$ ./gradlew clean build
> Task :clean
> Task :compileJava
> Task :processResources NO-SOURCE
> Task :classes
> Task :jar
> Task :assemble
> Task :compileTestJava
> Task :processTestResources NO-SOURCE
> Task :testClasses
> Task :test
> Task :check
> Task :build

BUILD SUCCESSFUL in 10s
5 actionable tasks: 5 executed
```

Rodando de novo sem mudar nada, o Gradle percebe que as entradas de cada tarefa são as mesmas da última vez e não refaz nada. É o **build incremental**, a principal razão da fama de rápido:

```text
$ ./gradlew build
> Task :compileJava UP-TO-DATE
> Task :test UP-TO-DATE
> Task :build UP-TO-DATE

BUILD SUCCESSFUL in 8s
4 actionable tasks: 4 up-to-date
```

E os conflitos? O Gradle não usa a mais próxima: ele escolhe a **versão mais alta** pedida em qualquer ponto da árvore. O `gradle dependencies` mostra a troca com uma seta:

```text
$ ./gradlew dependencies --configuration runtimeClasspath
runtimeClasspath - Runtime classpath of source set 'main'.
+--- com.fasterxml.jackson.core:jackson-databind:2.11.1 -> 2.21.5
|    +--- com.fasterxml.jackson.core:jackson-annotations:2.21
|    +--- com.fasterxml.jackson.core:jackson-core:2.21.5
|    |    \--- com.fasterxml.jackson:jackson-bom:2.21.5
|    |         +--- com.fasterxml.jackson.core:jackson-annotations:2.21 (c)
|    |         +--- com.fasterxml.jackson.core:jackson-core:2.21.5 (c)
|    |         +--- com.fasterxml.jackson.core:jackson-databind:2.21.5 (c)
|    |         \--- com.fasterxml.jackson.datatype:jackson-datatype-jsr310:2.21.5 (c)
|    \--- com.fasterxml.jackson:jackson-bom:2.21.5 (*)
\--- com.fasterxml.jackson.datatype:jackson-datatype-jsr310:2.21.5
     +--- com.fasterxml.jackson.core:jackson-annotations:2.21
     +--- com.fasterxml.jackson.core:jackson-core:2.21.5 (*)
     +--- com.fasterxml.jackson.core:jackson-databind:2.21.5 (*)
     \--- com.fasterxml.jackson:jackson-bom:2.21.5 (*)
```

O `databind` foi declarado como 2.11.1, mas o `jsr310` pedia 2.21.5, e a mais alta venceu. Os `(c)` são **restrições** que o próprio Jackson publica para o Gradle, ligando todos os módulos ao BOM: por isso o `jackson-core` também subiu junto. A partir da 2.20, o `jackson-annotations` passou a usar só dois números na versão, por isso o `2.21`. A versão mais alta costuma ser a escolha mais segura, porque as bibliotecas tendem a manter compatibilidade com as versões anteriores, mas não é garantia: uma versão nova pode remover algo que outra biblioteca usava.

## O wrapper

Projetos não pedem que você instale o Maven ou o Gradle. Eles trazem um **wrapper**: os scripts `mvnw` e `mvnw.cmd`, ou `gradlew` e `gradlew.bat`, e um arquivo de propriedades, em `.mvn/wrapper/` ou `gradle/wrapper/`, com a versão exata da ferramenta. Na primeira execução, o wrapper baixa essa versão, e todo mundo do time e o CI passam a usar a mesma. Os arquivos do wrapper vão para o Git, e os comandos passam a ser `./mvnw package` e `./gradlew build`, ou `mvnw.cmd` e `gradlew.bat` no Prompt de Comando do Windows.

## Maven ou Gradle?

| | Maven | Gradle |
|---|---|---|
| Configuração | XML declarativo | Código Kotlin ou Groovy |
| Filosofia | Convenção rígida, pouca margem para inventar | Flexível, programável |
| Velocidade | Pula a compilação quando nada mudou, mas refaz os outros passos, inclusive os testes | Build incremental em todas as tarefas, cache e daemon |
| Conflito de versões | A mais próxima vence | A mais alta vence |
| Onde é mais comum | Projetos corporativos Java | Android e projetos grandes |

Os dois usam o Maven Central e geram o mesmo tipo de JAR. Na prática, quem escolhe é o time, e o Spring Initializr gera qualquer um dos dois. Saber ler os dois é o que importa.

## Versões

Um sufixo `-SNAPSHOT`, como em `1.0.0-SNAPSHOT`, marca uma versão **em desenvolvimento**: ela pode mudar, e o Maven procura a mais nova de tempos em tempos. Versões sem o sufixo são **releases** e nunca mudam depois de publicadas no Maven Central. Muitas bibliotecas seguem o **versionamento semântico**, `MAIOR.MENOR.CORREÇÃO`: a correção só conserta defeitos, a menor acrescenta recursos sem quebrar nada, e a maior pode quebrar. E versões se comparam **número a número**, não como texto: `2.10.0` é mais nova que `2.9.0`, embora `"2.10.0".compareTo("2.9.0")` diga o contrário.

## Por baixo dos panos

O repositório local é só uma árvore de pastas: os pontos do `groupId` viram diretórios, e cada versão tem a sua pasta:

```text
~/.m2/repository/com/fasterxml/jackson/core/jackson-databind/2.17.2/
    jackson-databind-2.17.2.jar
    jackson-databind-2.17.2.jar.sha1
    jackson-databind-2.17.2.pom
    jackson-databind-2.17.2.pom.sha1
```

Para resolver as dependências, o Maven baixa primeiro o `.pom` de cada biblioteca, lê as dependências declaradas nele e repete o processo, montando a árvore; só depois baixa os JARs das versões escolhidas. Os arquivos `.sha1` conferem que nada se corrompeu no caminho. O Gradle publica e lê ainda um terceiro arquivo, o `.module`, um JSON mais rico que o POM, onde vêm as restrições `(c)` da árvore acima. No fim, todo esse trabalho produz uma lista de JARs, que vira o `-cp` do `javac` e do `java`: o mesmo classpath que você montaria à mão, só que calculado.

## Resumo

- Coordenadas `groupId:artifactId:version`; bibliotecas no Maven Central e em cache local (`~/.m2` ou `~/.gradle`)
- Estrutura padrão: `src/main/java`, `src/main/resources`, `src/test/java`; saída em `target/` ou `build/`
- Maven: `pom.xml`, fases `compile`, `test`, `package`, `install`; plugins fazem o trabalho
- Escopos `compile`, `provided`, `runtime`, `test`; no Gradle, `implementation`, `compileOnly`, `runtimeOnly`, `testImplementation`
- Conflitos: o Maven escolhe a mais próxima; o Gradle, a mais alta. `dependency:tree -Dverbose` e `gradle dependencies` mostram a decisão
- BOM no `dependencyManagement` ou com `platform()` alinha as versões
- Wrapper (`mvnw`, `gradlew`) fixa a versão da ferramenta e vai para o Git
