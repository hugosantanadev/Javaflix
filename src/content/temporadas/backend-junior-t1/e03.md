O merge do [episódio anterior](/assistir/backend-junior-t1-e02) junta duas linhas de trabalho preservando tudo o que aconteceu, inclusive os commits de merge. Em projetos movimentados, isso vira um emaranhado de linhas no `git log --graph`. O **rebase** é a alternativa: em vez de juntar as branches, ele **reaplica** os seus commits em cima da versão mais nova da `main`, como se você tivesse começado o trabalho agora. O resultado é um histórico em linha reta, fácil de ler. E o **rebase interativo** vai além: permite juntar, reordenar, renomear e apagar commits antes de mostrá-los ao time.

## O que o rebase faz

A `feature/cupom` tem dois commits, e a `main` ganhou um README depois que ela foi criada:

```text
$ git log --oneline --graph --all
* 3edf437 Adiciona README
| * b7faed6 Adiciona cupom de frete grátis
| * 2301874 Cria a lista de cupons
|/
* 28f1fa9 Configuração inicial
```

Em vez de mesclar, rode o rebase de dentro da branch:

```text
$ git switch feature/cupom
$ git rebase main
Successfully rebased and updated refs/heads/feature/cupom.

$ git log --oneline --graph --all
* 03b5130 Adiciona cupom de frete grátis
* c321861 Cria a lista de cupons
* 3edf437 Adiciona README
* 28f1fa9 Configuração inicial
```

O Git encontrou o ancestral comum, guardou as mudanças de cada commit da branch, moveu a branch para a ponta da `main` e reaplicou as mudanças, uma por uma. Repare que os hashes **mudaram**: `2301874` virou `c321861`. São commits novos, com o mesmo conteúdo e a mesma mensagem, mas outro pai. Agora a `main` está atrás da branch em linha reta, e o merge é um fast-forward:

```text
$ git switch main
$ git merge feature/cupom
Updating 3edf437..03b5130
Fast-forward
 cupons.txt | 2 ++
 1 file changed, 2 insertions(+)
 create mode 100644 cupons.txt
```

## Merge ou rebase?

| | Merge | Rebase |
|---|---|---|
| Histórico | Preserva tudo, com commits de merge | Linha reta, como se tudo fosse sequencial |
| Commits existentes | Intactos | Substituídos por cópias com hashes novos |
| Conflitos | Resolvidos uma vez, no commit de merge | Podem aparecer em cada commit reaplicado |
| Seguro em branch compartilhada | Sim | Não |

Não existe resposta universal: é uma convenção do time. Um padrão comum é usar rebase para **atualizar a sua branch** com a `main` enquanto trabalha, e merge (ou o *squash merge* do GitHub, do [próximo episódio](/assistir/backend-junior-t1-e04)) para **integrar** a branch pronta.

## A regra de ouro

> [!ATENCAO]
> Nunca faça rebase de commits que outras pessoas já baixaram. O rebase troca os commits por cópias; quem tinha os originais fica com um histórico que não bate mais com o do servidor, e o próximo `pull` dele duplica os commits ou gera conflitos sem sentido.

Na sua própria branch de feature, mesmo já enviada para abrir um pull request, o rebase é normal, e o servidor recusa o `git push` comum porque o histórico mudou. Nesse caso, use `git push --force-with-lease`: ele só sobrescreve a branch remota se ela ainda estiver como você a viu da última vez, e recusa se alguém tiver enviado um commit nesse meio-tempo. O `--force` puro apagaria o commit da outra pessoa sem aviso.

## git pull com rebase

O `git pull` é um `git fetch`, que baixa os commits novos, seguido de um `git merge`. Se você e um colega commitaram na mesma branch, cada `pull` cria um commit "Merge branch 'main' of ...", que não diz nada a ninguém. Com `git pull --rebase`, os seus commits locais, ainda não enviados, são reaplicados em cima dos que chegaram, e a regra de ouro é respeitada, porque só os seus commits locais mudam. Muitos times deixam isso como padrão:

```bash
git config --global pull.rebase true
```

## Rebase interativo

`git rebase -i main` abre um editor com a lista de commits que serão reaplicados, do mais antigo ao mais novo. Cada linha começa com uma ação, e você pode trocar a ação ou mudar a ordem das linhas:

| Ação | Faz |
|---|---|
| `pick` | Mantém o commit como está |
| `reword` | Mantém o commit e abre o editor para mudar a mensagem |
| `edit` | Para no commit, para você alterar o conteúdo |
| `squash` | Junta ao commit anterior, combinando as mensagens |
| `fixup` | Junta ao commit anterior, descartando a mensagem deste |
| `drop` | Apaga o commit |

O uso mais comum é limpar a branch antes do pull request. Imagine que, depois de criar o Pix, você notou algo que faltava no primeiro commit e criou uma correção com `git commit --fixup`, que gera a mensagem `fixup! ` seguida da mensagem do commit corrigido:

```text
$ git commit --fixup a0b54ca
$ git log --oneline main..
29c7f46 wip
f10f2b6 fixup! Cria pagamento por Pix
efc08d3 Valida a chave Pix
a0b54ca Cria pagamento por Pix
```

Com `--autosquash`, o rebase interativo já monta a lista com cada `fixup!` logo depois do commit que ele corrige:

```text
$ git rebase -i --autosquash main
pick a0b54ca Cria pagamento por Pix
fixup f10f2b6 fixup! Cria pagamento por Pix
pick efc08d3 Valida a chave Pix
pick 29c7f46 wip
```

Trocando também o `pick` do `wip` por `fixup`, para juntá-lo ao commit da validação, a branch termina com dois commits limpos, cada um com uma mudança completa:

```text
$ git log --oneline main..
3f8dede Valida a chave Pix
465c620 Cria pagamento por Pix
```

> [!DICA]
> O editor aberto pelo rebase é o configurado em `core.editor`. Se for o Vim e você não souber sair dele: `Esc`, depois `:wq` e Enter para salvar, ou `:q!` para desistir. Para usar o VS Code: `git config --global core.editor "code --wait"`.

## Conflitos durante o rebase

Como cada commit é reaplicado separadamente, um conflito pode aparecer no meio do caminho. A `main` mudou o frete para 20, e a branch, para 0:

```text
$ git rebase main
Auto-merging config.txt
CONFLICT (content): Merge conflict in config.txt
error: could not apply 36fff0f... Zera o frete
hint: Resolve all conflicts manually, mark them as resolved with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".
hint: You can instead skip this commit: run "git rebase --skip".
hint: To abort and get back to the state before "git rebase", run "git rebase --abort".
```

```text
<<<<<<< HEAD
frete=20
=======
frete=0
>>>>>>> 36fff0f (Zera o frete)
desconto=0
parcelas=3
```

Atenção à inversão: no rebase, o `HEAD` é a **`main`**, mais os commits já reaplicados, e o lado de baixo é o **seu** commit, que está sendo aplicado. No merge era o contrário. Para seguir:

1. Edite o arquivo e tire os marcadores.
2. `git add config.txt`.
3. `git rebase --continue`, que cria o commit e passa para o próximo.

`git rebase --skip` descarta o commit que deu conflito, e `git rebase --abort` desiste de tudo e volta a branch ao estado anterior. Numa branch com muitos commits que mexem no mesmo trecho, o mesmo conflito pode voltar várias vezes; juntar os commits com um rebase interativo antes de atualizar com a `main` costuma resolver.

## Desfazendo commits

| Situação | Comando |
|---|---|
| Desfazer o último commit, mantendo as mudanças preparadas | `git reset --soft HEAD~1` |
| Desfazer o último commit, mantendo as mudanças no diretório de trabalho | `git reset HEAD~1` |
| Desfazer o último commit **e descartar** as mudanças | `git reset --hard HEAD~1` |
| Desfazer um commit já enviado, sem reescrever o histórico | `git revert <hash>` |

O `reset` move o ponteiro da branch para trás e, como o rebase, reescreve o histórico: use só em commits locais. O `revert` cria um commit **novo**, com as mudanças inversas, e é o jeito seguro de desfazer algo que já está na `main` compartilhada.

E se um rebase ou um `reset --hard` deu errado? O **reflog** registra cada posição pela qual o `HEAD` passou, inclusive as de commits que nenhuma branch aponta mais:

```text
$ git reflog -5
3f8dede HEAD@{0}: rebase (finish): returning to refs/heads/feature/pix
3f8dede HEAD@{1}: rebase (fixup): Valida a chave Pix
19fe499 HEAD@{2}: rebase (start): checkout main
095a7db HEAD@{3}: rebase (finish): returning to refs/heads/feature/pix
095a7db HEAD@{4}: rebase (pick): wip
```

A branch estava em `095a7db` antes do último rebase; `git reset --hard 095a7db` a devolve exatamente para lá. Logo depois de um rebase, `git reset --hard ORIG_HEAD` faz o mesmo, porque o Git guarda a posição anterior nessa referência.

> [!ATENCAO]
> O reflog só recupera o que foi commitado. Mudanças descartadas por `git reset --hard` ou `git restore` antes de qualquer commit não ficam registradas em lugar nenhum. Na dúvida, faça um commit provisório antes de experimentar.

## Por baixo dos panos

Por que o rebase muda os hashes? O `git cat-file -p` mostra o commit `Zera o frete` antes e depois do rebase com conflito:

```text
tree 9b2d0a086195165b09779fea7cfda42b6e66ed1c
parent 03b51303ad87c5b336993966d6a03cacf3963844
author Ana Lima <ana@exemplo.com> 1758049200 -0300
committer Ana Lima <ana@exemplo.com> 1758049200 -0300

Zera o frete
```

```text
tree 9b2d0a086195165b09779fea7cfda42b6e66ed1c
parent 92c8f8c3f50ff1b6bf96d88b994395b2a29ed169
author Ana Lima <ana@exemplo.com> 1758049200 -0300
committer Ana Lima <ana@exemplo.com> 1758050400 -0300

Zera o frete
```

A árvore é a mesma, porque a resolução do conflito manteve `frete=0` e o resto já era igual. O autor e a data de autoria também foram preservados. Mudaram só o **pai**, que agora é o commit da `main`, e a **data do committer**, a hora em que o rebase rodou. Como o hash de um commit é o SHA-1 de todo esse texto, como vimos no [primeiro episódio](/assistir/backend-junior-t1-e01), isso basta para gerar outro identificador:

```java executar
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.util.HexFormat;

public class Reaplica {
    static String hashDeCommit(String parent, long dataDoCommitter) throws Exception {
        String conteudo = "tree 9b2d0a086195165b09779fea7cfda42b6e66ed1c\n"
                + "parent " + parent + "\n"
                + "author Ana Lima <ana@exemplo.com> 1758049200 -0300\n"
                + "committer Ana Lima <ana@exemplo.com> " + dataDoCommitter + " -0300\n"
                + "\n"
                + "Zera o frete\n";
        byte[] dados = conteudo.getBytes(StandardCharsets.UTF_8);
        MessageDigest sha1 = MessageDigest.getInstance("SHA-1");
        sha1.update(("commit " + dados.length + "\0").getBytes(StandardCharsets.UTF_8));
        sha1.update(dados);
        return HexFormat.of().formatHex(sha1.digest()).substring(0, 7);
    }

    public static void main(String[] args) throws Exception {
        System.out.println("antes:  " + hashDeCommit("03b51303ad87c5b336993966d6a03cacf3963844", 1758049200));
        System.out.println("depois: " + hashDeCommit("92c8f8c3f50ff1b6bf96d88b994395b2a29ed169", 1758050400));
    }
}
```

```saida
antes:  36fff0f
depois: a11306b
```

São exatamente o `36fff0f` da mensagem de conflito e o `a11306b` que o rebase gravou. E, como cada commit inclui o hash do pai, trocar o pai do primeiro commit da branch muda o hash de todos os seguintes, em cascata. É por isso que o rebase "reescreve" o histórico: ele não altera commits, que são imutáveis, mas cria cópias e move a branch para elas. Os originais continuam no banco de objetos, alcançáveis pelo reflog, até que o `git gc` os apague; por padrão, as entradas do reflog de commits que nenhuma branch alcança expiram em 30 dias.

## Resumo

- `git rebase main` reaplica os commits da branch atual em cima da `main`, gerando commits novos e um histórico linear
- Merge preserva o histórico; rebase o reescreve. Rebase para atualizar a sua branch, merge para integrar é um padrão comum
- Regra de ouro: não faça rebase de commits compartilhados; na sua branch, `git push --force-with-lease`
- `git pull --rebase` evita commits de merge inúteis
- `git rebase -i`: `pick`, `reword`, `edit`, `squash`, `fixup`, `drop`; `git commit --fixup` com `--autosquash`
- Conflito no rebase: o `HEAD` é a `main`; edite, `git add`, `git rebase --continue`, ou `--skip` e `--abort`
- `reset` desfaz commits locais; `revert` desfaz commits compartilhados; `reflog` e `ORIG_HEAD` recuperam o que foi perdido
