Até aqui, o repositório morava só na sua máquina. Num time, ele mora também num **servidor**, quase sempre o GitHub, o GitLab ou o Bitbucket, e cada pessoa tem uma cópia completa. Mudanças não vão direto para a `main`: elas chegam por um **pull request** (no GitLab, *merge request*), um pedido para mesclar uma branch, onde o time lê o código, comenta, sugere melhorias e aprova. Esse ciclo de **code review** é onde um júnior mais aprende, e saber conduzi-lo bem, dos dois lados, conta tanto quanto saber programar.

## Repositórios remotos

Um **remoto** é outro repositório com o qual o seu troca commits. Ao clonar, o Git cria um chamado `origin`, apontando para o endereço de onde veio. Nos exemplos deste episódio, o servidor é uma pasta local, `../loja.git`, criada com `git init --bare`: um repositório sem diretório de trabalho, que para o Git funciona exatamente como o GitHub.

```text
$ git remote add origin ../loja.git
$ git remote -v
origin	../loja.git (fetch)
origin	../loja.git (push)

$ git push -u origin main
branch 'main' set up to track 'origin/main'.
To ../loja.git
 * [new branch]      main -> main
```

O `-u` liga a branch local à remota, e daí em diante basta `git push` e `git pull`. Quem clona o repositório recebe a `main` já ligada:

```text
$ git clone ../loja.git bruno
$ git branch -vv
* main 31ee9ad [origin/main] Cria o README
```

O `origin/main` é uma **branch remota**: a sua cópia local de onde a `main` do servidor estava na última vez que você conversou com ele. Ela não se atualiza sozinha.

| Comando | Faz |
|---|---|
| `git fetch` | Baixa os commits e branches novos do servidor e atualiza as branches remotas, sem tocar nas suas |
| `git pull` | `fetch` seguido de merge (ou rebase, com `--rebase`) na branch atual |
| `git push` | Envia os seus commits para a branch ligada no servidor |
| `git push -u origin nome` | Envia uma branch nova e a liga à remota |
| `git branch -a` | Lista as branches locais e as remotas |

```text
$ git fetch
 * [new branch]      feature/frete -> origin/feature/frete

$ git branch -a
* main
  remotes/origin/HEAD -> origin/main
  remotes/origin/feature/frete
  remotes/origin/main
```

Se outra pessoa enviou commits que você ainda não tem, o servidor recusa o seu push, para não perder o trabalho dela:

```text
$ git push
To ../loja.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to '../loja.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.

$ git pull --rebase
From ../loja
   31ee9ad..579b99f  main       -> origin/main
Successfully rebased and updated refs/heads/main.
$ git push
To ../loja.git
   579b99f..90cd9d3  main -> main
```

## Autenticação

O GitHub não aceita a senha da conta nas operações do Git desde 2021. Há dois caminhos:

- **HTTPS com token**: um *personal access token*, criado nas configurações da conta, com permissões e validade limitadas. O Git Credential Manager, que vem com o Git para Windows, cuida disso pelo navegador.
- **SSH**: um par de chaves gerado com `ssh-keygen -t ed25519 -C "ana@exemplo.com"`. A chave **pública**, o arquivo `.pub`, é cadastrada no GitHub; a **privada** nunca sai da sua máquina. Os endereços ficam no formato `git@github.com:empresa/loja.git`.

> [!ATENCAO]
> Tokens e chaves privadas são senhas. Nunca os coloque no código, num commit ou num print de tela. O GitHub varre repositórios públicos atrás de tokens vazados, mas o estrago pode acontecer antes.

## O fluxo do pull request

1. Atualize a `main`: `git switch main` e `git pull`.
2. Crie a branch: `git switch -c feature/frete-por-peso`.
3. Trabalhe em commits pequenos, com mensagens claras.
4. Envie: `git push -u origin feature/frete-por-peso`.
5. Abra o pull request no GitHub, que oferece um botão para isso logo depois do push, ou pelo terminal com `gh pr create`.
6. O CI roda os testes, e os revisores comentam.
7. Ajuste o que foi pedido com commits novos **na mesma branch**: o pull request se atualiza sozinho a cada push.
8. Aprovado, o pull request é mesclado, e a branch é apagada.

Em projetos em que você não tem permissão de escrita, como os de código aberto, o primeiro passo é um **fork**: uma cópia do repositório na sua conta. Você clona o fork, trabalha nele e abre o pull request do fork para o original. Um segundo remoto, por convenção chamado `upstream`, aponta para o original, para você buscar as novidades com `git fetch upstream`.

## Uma boa descrição

O revisor não estava na sua cabeça enquanto você programava. Uma descrição que responde **o quê**, **por quê** e **como testar** economiza uma rodada inteira de perguntas:

```markdown
## O que muda
Calcula o frete pelo peso do pedido, em vez do valor fixo de R$ 15.

## Por quê
Pedidos pesados davam prejuízo no frete (issue #12).

## Como testar
`./mvnw test`, ou um POST em /pedidos com peso acima de 10 kg.

Closes: #12
```

As palavras `close`, `fix` e `resolve`, em qualquer conjugação do inglês, seguidas de `#` e o número de uma issue, fazem o GitHub **fechar a issue** quando o pull request é mesclado na branch padrão do repositório. A regra cabe numa expressão regular:

```java executar
import java.util.ArrayList;
import java.util.List;
import java.util.regex.Matcher;
import java.util.regex.Pattern;

public class FechaIssues {
    static final Pattern FECHAMENTO = Pattern.compile(
            "\\b(?:close[sd]?|fix(?:e[sd])?|resolve[sd]?):?\\s+#(\\d+)", Pattern.CASE_INSENSITIVE);

    static List<Integer> issuesFechadas(String descricao) {
        List<Integer> numeros = new ArrayList<>();
        Matcher m = FECHAMENTO.matcher(descricao);
        while (m.find()) {
            numeros.add(Integer.parseInt(m.group(1)));
        }
        return numeros;
    }

    public static void main(String[] args) {
        String descricao = """
                Adiciona o cálculo de frete por peso.

                Closes: #12. Também fixes #7.
                Relacionado a #41, que fica para depois.
                """;
        System.out.println(issuesFechadas(descricao));
    }
}
```

```saida
[12, 7]
```

A issue `#41` é só mencionada: ganha um link para o pull request, mas continua aberta.

## Code review

**Como autor:**

- Mantenha o pull request **pequeno** e focado num assunto. Algumas centenas de linhas são revisadas com atenção; duas mil recebem um "LGTM" (*looks good to me*) sem leitura.
- Revise o seu próprio diff antes de pedir revisão: é onde aparecem o `System.out.println` esquecido e o arquivo que não devia estar ali.
- Responda a todos os comentários, mesmo que seja com "feito". Discordar é permitido, com argumentos.
- O comentário é sobre o código, não sobre você.

**Como revisor:**

- Procure, nesta ordem: o código faz o que promete? Tem testes? O desenho é simples? Há algum risco de segurança? Os nomes são claros?
- Explique o **porquê** de cada pedido, e pergunte quando não entender: "o que acontece se a lista vier vazia?" ensina mais que "isso está errado".
- Marque o que é detalhe com o prefixo `nit:` (de *nitpick*), para o autor saber que não bloqueia.
- Aprove quando o pull request **melhora** o código, mesmo que não esteja perfeito. O guia de revisão do Google usa exatamente esse critério.

No GitHub, a revisão termina de três formas: **Comment**, só comentários; **Approve**, aprovado; ou **Request changes**, que pede mudanças antes do merge. Um comentário pode ainda trazer uma **sugestão**, um bloco que o autor aplica com um clique.

## Integrando o pull request

O GitHub oferece três botões de merge, e o repositório pode habilitar só alguns:

| Botão | Resultado na `main` |
|---|---|
| Create a merge commit | Todos os commits da branch, mais um commit de merge |
| Squash and merge | Um único commit com todas as mudanças da branch |
| Rebase and merge | Os commits da branch reaplicados em linha reta, sem commit de merge |

O *squash and merge* é muito usado porque cada pull request vira um commit na `main`, e os commits "wip" e "corrige teste" da branch somem do histórico principal.

Nos times, a `main` costuma ser uma **branch protegida**: ninguém faz push direto nela, o merge exige aprovação e testes passando, e o push forçado é bloqueado. Um arquivo `CODEOWNERS` ainda define quem precisa aprovar mudanças em cada parte do código:

```text
# .github/CODEOWNERS
*                @empresa/backend
/src/pagamento/  @empresa/time-pagamentos
*.sql            @ana-lima
```

## O GitHub pelo terminal

O **GitHub CLI**, o comando `gh`, faz o ciclo inteiro sem sair do terminal:

```bash
gh pr create --fill          # abre o pull request com o título e o corpo dos commits
gh pr list                   # lista os pull requests abertos
gh pr checkout 42            # baixa a branch do pull request 42, para testar
gh pr review 42 --approve    # aprova
gh pr merge 42 --squash --delete-branch
```

## Por baixo dos panos

O pull request não é um conceito do Git: é uma funcionalidade do GitHub, construída sobre branches. O servidor guarda cada um numa referência especial, `refs/pull/42/head`, e é por isso que `git fetch origin pull/42/head:pr-42` traz a branch de qualquer pull request, mesmo de um fork.

A aba de arquivos alterados mostra o diff do **ancestral comum** até a ponta da branch, o que o Git chama de diff de três pontos: `git diff main...feature/frete`. Assim, o revisor vê só o que a branch mudou, e não o que a `main` ganhou depois. E as branches remotas também são arquivos: `.git/refs/remotes/origin/main` guarda o hash que o servidor informou no último `fetch`, e o `git status` compara a sua `main` com ele para dizer "Your branch is ahead of 'origin/main' by 1 commit".

## Resumo

- `origin` é o remoto padrão; `origin/main` é a cópia local do estado do servidor no último `fetch`
- `fetch` baixa sem mexer nas suas branches; `pull` = `fetch` + merge ou rebase; `push -u` envia e liga a branch
- Push recusado: alguém enviou antes; `git pull --rebase` e `git push` de novo
- GitHub: token pelo HTTPS ou chave SSH, nunca a senha, e nunca segredos no código
- Pull request: branch, push, descrição com o quê, por quê e como testar; `Closes #12` fecha a issue
- Review: PRs pequenos, revisão própria antes, comentários com o porquê, `nit:` para detalhes
- Merge commit, squash and merge ou rebase and merge; branches protegidas e `CODEOWNERS`
