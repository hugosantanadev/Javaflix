Você já tem uma ALU que calcula e uma memória que guarda. Falta o maestro: a parte que lê o programa, uma instrução por vez, e diz à ALU o que fazer. Neste episódio você entende o ciclo que todo processador repete bilhões de vezes por segundo, e roda uma CPU de brinquedo escrita em Java.

## A arquitetura de von Neumann

Em 1945, John von Neumann descreveu o desenho que quase todo computador segue até hoje:

- **CPU**, com a unidade de controle, a ALU e os registradores
- **Memória**, que guarda **o programa e os dados juntos**, como números
- **Entrada e saída**: teclado, tela, disco, rede
- **Barramentos**, os fios que levam endereços e dados entre as partes

A ideia central é a segunda: o programa é só mais um monte de números na memória. Isso permite carregar programas novos sem religar fios, e é o motivo de um compilador poder gerar um programa que outro programa executa.

## Os registradores

Registradores são as poucas posições de memória **dentro** da CPU, as únicas onde a ALU opera de verdade. Além dos registradores de uso geral, dois são especiais:

- **PC** (*program counter*, contador de programa): guarda o endereço da **próxima** instrução
- **IR** (*instruction register*): guarda a instrução que está sendo executada agora

## O ciclo de instrução

A CPU repete três passos, para sempre:

1. **Busca**: lê da memória a instrução no endereço do PC, coloca no IR e avança o PC
2. **Decodifica**: separa a instrução em partes: o **opcode** (qual operação) e os **operandos** (com quais dados)
3. **Executa**: a ALU calcula, ou a memória é lida ou escrita, ou o PC recebe um novo endereço (um salto)

Instruções de máquina são só números. Numa CPU didática de 8 bits, os 4 bits de cima podem dizer a operação e os 4 de baixo, o endereço. A instrução `0x1E` seria "carregar no registrador A o conteúdo do endereço 14" (`1` = LOAD_A, `E` = 14).

## Uma CPU de brinquedo

Este programa Java simula essa CPU, com dois registradores (A e B), 16 posições de memória e cinco instruções. Leia o laço com atenção: ele **é** o ciclo de instrução.

```java executar
public class CpuDeBrinquedo {
    static final int LOAD_A = 0x1, LOAD_B = 0x2, ADD = 0x3, STORE_A = 0x4, HALT = 0xF;

    public static void main(String[] args) {
        int[] memoria = new int[16];
        // o programa (instrução = opcode nos 4 bits de cima, endereço nos 4 de baixo)
        memoria[0] = 0x1E; // LOAD_A 14
        memoria[1] = 0x2F; // LOAD_B 15
        memoria[2] = 0x30; // ADD      (A = A + B)
        memoria[3] = 0x4D; // STORE_A 13
        memoria[4] = 0xF0; // HALT
        // os dados, na mesma memória
        memoria[14] = 5;
        memoria[15] = 3;

        int pc = 0, a = 0, b = 0, ciclos = 0;
        while (true) {
            int instrucao = memoria[pc];      // busca
            pc++;
            int opcode = instrucao >> 4;      // decodifica
            int endereco = instrucao & 0xF;
            ciclos++;
            if (opcode == LOAD_A) a = memoria[endereco];          // executa
            else if (opcode == LOAD_B) b = memoria[endereco];
            else if (opcode == ADD) a = a + b;
            else if (opcode == STORE_A) memoria[endereco] = a;
            else if (opcode == HALT) break;
        }
        System.out.println("memoria[13] = " + memoria[13]);
        System.out.println("ciclos = " + ciclos);
    }
}
```

```saida
memoria[13] = 8
ciclos = 5
```

Repare que programa e dados dividem o mesmo array `memoria`. Se uma instrução `STORE_A` escrevesse no endereço 2, o programa se reescreveria enquanto roda. Em computadores reais, o sistema operacional marca as áreas de código como somente leitura justamente para impedir isso.

Para ter `if` e laços, basta uma instrução que mude o PC: um **salto** (`JUMP`), e um **salto condicional** que só pula se a última conta deu zero ou negativo (olhando as flags da ALU). Todo `if`, `for` e `while` do Java vira, no fim, comparação mais salto condicional.

## O clock e o pipeline

O clock dita o ritmo: um processador de 3 GHz tem 3 bilhões de pulsos por segundo. Uma instrução simples pode levar alguns ciclos, mas processadores modernos usam um **pipeline**: enquanto uma instrução executa, a seguinte já está sendo decodificada e a outra, buscada, como uma linha de montagem. Processadores atuais ainda executam várias instruções no mesmo ciclo e até fora de ordem, quando uma não depende da outra.

## A hierarquia de memória

A CPU é muito mais rápida que a RAM. Para não ficar esperando, existem camadas de memória cada vez maiores e mais lentas. As ordens de grandeza aproximadas:

| Onde | Tempo de acesso aproximado | Tamanho típico |
|---|---|---|
| Registrador | menos de 1 ns | dezenas de valores |
| Cache L1 | ~1 ns | dezenas de KiB |
| Cache L2 | ~4 ns | centenas de KiB a poucos MiB |
| Cache L3 | ~10 a 40 ns | dezenas de MiB |
| RAM | ~100 ns | GiB |
| SSD | ~100.000 ns (0,1 ms) | centenas de GiB a TiB |

A RAM é umas cem vezes mais lenta que o cache L1. Quando a CPU lê um endereço, o cache traz junto os vizinhos (uma **linha de cache**, em geral 64 bytes). Por isso **percorrer um array em ordem é rápido**: os próximos elementos já vieram junto. É também por isso que um `ArrayList`, com os elementos lado a lado, costuma ser mais rápido de percorrer que uma `LinkedList`, com nós espalhados pela memória.

## A pilha de chamadas

Quando um método chama outro, a CPU precisa lembrar para onde voltar. Ela usa uma região da memória chamada **pilha** (*stack*) e um registrador que aponta o topo dela. Cada chamada empilha um **quadro** (*frame*) com o endereço de retorno e as variáveis locais do método; cada `return` desempilha.

A pilha tem tamanho limitado. Uma recursão sem condição de parada empilha quadros até estourar, e a JVM avisa com um erro:

```java executar
public class SemFim {
    static int chamadas = 0;

    static void desce() {
        chamadas++;
        desce();
    }

    public static void main(String[] args) {
        try {
            desce();
        } catch (StackOverflowError e) {
            System.out.println("a pilha estourou");
        }
    }
}
```

```saida
a pilha estourou
```

O número de chamadas até estourar varia com a máquina e com a JVM, por isso o exemplo não imprime. Objetos criados com `new` não ficam na pilha: vão para o **heap**, outra região da memória, gerenciada pelo coletor de lixo do Java.

## Resumo

- Von Neumann: CPU, memória com programa e dados juntos, entrada e saída
- PC guarda o endereço da próxima instrução; o ciclo é busca, decodifica, executa
- Instrução de máquina = opcode + operandos, tudo número
- `if` e laços viram comparações e saltos condicionais
- Cache L1 é ~100 vezes mais rápido que a RAM; acesso sequencial aproveita o cache
- A pilha guarda endereço de retorno e variáveis locais; recursão infinita a estoura
