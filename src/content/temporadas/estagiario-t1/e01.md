Antes de decorar regras de sintaxe, vale entender o caminho que o seu código percorre até virar algo que o computador executa. Boa parte das questões do tipo "o que acontece quando você roda isso?" fica fácil quando esse caminho está claro na cabeça.

## Do .java ao processador

Você escreve código-fonte num arquivo `.java`. O compilador `javac` lê esse arquivo e gera um `.class`, que contém **bytecode**: instruções para a Java Virtual Machine, não para o seu processador. Quem executa o bytecode é a JVM.

![O caminho de Ola.java até três sistemas: o javac gera um único Ola.class, que roda nas JVMs de Windows, Linux e macOS](/figuras/jvm-caminho.svg "Compila uma vez, roda em qualquer lugar: o mesmo bytecode vai para três JVMs, e cada uma gera código para o seu processador.")

A JVM começa interpretando o bytecode. Quando percebe que um trecho roda muitas vezes, o compilador **JIT** (just-in-time) transforma esse trecho em código nativo, otimizado para a máquina onde está rodando. É por isso que o mesmo `.class` roda em Windows, Linux ou macOS: o que muda de um sistema para outro é a JVM, não o seu programa.

## JDK, JRE e JVM

![O JDK por fora, o runtime dentro dele e a JVM no centro, com as ferramentas do JDK ao lado](/figuras/jdk-jre-jvm.svg "Uma caixa dentro da outra: a JVM executa, o runtime soma a biblioteca padrão e o JDK soma as ferramentas de desenvolvimento.")

| Sigla | O que é | Para que serve |
|---|---|---|
| **JVM** | A máquina virtual que executa bytecode | Rodar programas |
| **JRE** | JVM mais a biblioteca padrão | Rodar programas (termo histórico) |
| **JDK** | Runtime mais as ferramentas de desenvolvimento | Escrever, compilar e empacotar |

As ferramentas do JDK que mais aparecem na prova e no dia a dia:

- `javac`: compila `.java` em `.class`
- `java`: inicia a JVM e executa uma classe
- `jar`: empacota classes num arquivo `.jar`
- `jshell`: console interativo para testar trechos de código
- `javadoc`: gera documentação HTML a partir dos comentários `/** */`
- `jdeps` e `jlink`: analisam dependências e montam runtimes enxutos (você verá na temporada de módulos)

> [!DICA]
> Desde o Java 11 não existe mais um JRE separado para baixar no site da Oracle. Quem precisa de um runtime pequeno monta um com `jlink`.

> [!PERGUNTAS]
> **P:** Preciso instalar o JRE e o JDK?
>
> **R:** Só o JDK. Ele já traz o runtime inteiro, e desde o Java 11 nem existe JRE separado para baixar.
>
> **P:** Um `.class` roda em qualquer versão do Java?
>
> **R:** Roda na versão para a qual foi compilado e nas mais novas. Um `.class` compilado no Java 25 recusa rodar numa JVM 21, com um `UnsupportedClassVersionError`. Para mirar uma versão mais antiga, compile com `javac --release 21`.
>
> **P:** Se a JVM interpreta o bytecode, o Java não é lento?
>
> **R:** Só no começo. Os trechos que rodam muito viram código nativo pelo JIT, otimizado com informações que só existem durante a execução, como quais caminhos do código são usados de verdade.

## Compilar e executar

O fluxo clássico tem dois comandos:

```bash
javac Ola.java     # gera Ola.class na mesma pasta
java Ola           # executa a classe Ola
```

```java executar
public class Ola { //> Classe `public`: o arquivo se chama `Ola.java`.
    public static void main(String[] args) { //> A JVM começa por aqui.
        System.out.println("Olá, Javaflix!"); //> Imprime e pula linha. Termina com `;`.
    }
}
```

```saida
Olá, Javaflix!
```

> [!PENSE]
> O `javac` recebeu `Ola.java`, com extensão. O que você acha que o `java` recebe: `Ola.java`, `Ola.class` ou só `Ola`? Responda antes de ler o próximo parágrafo.

Repare na assimetria: `javac` recebe o **nome do arquivo**, com a extensão `.java`. Já `java` recebe o **nome da classe**, sem extensão nenhuma.

> [!PROVA]
> `java Ola.class` não funciona. A JVM procura uma classe chamada literalmente `Ola.class` e termina com `Could not find or load main class Ola.class`. Do mesmo jeito, `javac Ola` sem a extensão é erro.

> [!ERRO]
> Salvar a classe `public class Ola` num arquivo `ola.java`, com letra minúscula. O `javac` recusa com `class Ola is public, should be declared in a file named Ola.java`, inclusive no Windows, que não diferencia maiúsculas nos nomes de arquivo: quem confere é o compilador, não o sistema.

> [!CONVERSA]
> **javac:** Eu faço o trabalho pesado. Leio o seu código inteiro, confiro cada tipo e só gravo o `.class` se estiver tudo certo.
>
> **JVM:** E eu faço o programa existir de verdade. Você entrega um arquivo; eu entrego algo rodando.
>
> **javac:** Se não fosse eu, você receberia `int x = "texto";` e quebraria na frente do usuário.
>
> **JVM:** Tem coisa que só aparece rodando: um índice fora do array, uma divisão por zero, um arquivo que sumiu. Essas são comigo.
>
> **javac:** Pelo menos o meu trabalho acontece uma vez só. O seu se repete a cada execução.
>
> **JVM:** E fica melhor a cada uma. Quando vejo um trecho rodar milhares de vezes, compilo de novo, agora para o processador desta máquina. Você nem sabe em que máquina o programa vai rodar.
>
> **javac:** Justo. Combinado: eu pego os erros de compilação, você pega os erros de execução.

Essa divisão de trabalho volta o tempo todo: **erro de compilação** é o `javac` recusando o código, e nenhum `.class` sai; **erro de execução** é a JVM parando no meio, com uma exceção.

```imas executar
public class Ordem {
    public static void main(String[] args) {
        System.out.println("primeiro");
        System.out.println("segundo");
    }
}
```

```saida
primeiro
segundo
```

## Modo arquivo-fonte

Desde o Java 11 dá para pular o `javac` em programas pequenos:

```bash
java Ola.java
```

Nesse modo a JVM compila o arquivo **em memória** e executa a primeira classe declarada nele. Nenhum `.class` é gravado em disco. É ótimo para scripts e testes rápidos. A partir do Java 22 o modo arquivo-fonte também encontra outras classes em arquivos `.java` da mesma pasta, o que permite programas com vários arquivos sem build.

## O método main

O ponto de entrada clássico de um programa Java é este:

```java
public static void main(String[] args)
```

Cada palavra tem um motivo:

- `public`: a JVM precisa enxergar o método de fora da classe
- `static`: o método roda sem que exista um objeto da classe
- `void`: o método não devolve valor
- `main`: o nome é fixo, com m minúsculo
- `String[] args`: os argumentos da linha de comando

Algumas variações continuam valendo, porque não mudam o significado da assinatura:

```java
public static void main(String... args)        // varargs
public static void main(String args[])         // colchetes depois do nome
static public void main(String[] argumentos)   // ordem dos modificadores e nome do parâmetro
public static void main(final String[] args)   // parâmetro final
```

O que **não** pode mudar é a posição do tipo de retorno: ele vem imediatamente antes do nome do método. `public void static main(...)` nem compila.

> [!PROVA]
> Um `main` sem `static`, com retorno `int` ou com parâmetro `String` (sem array) **compila normalmente**: é só um método comum. O problema aparece ao executar, quando a JVM não encontra um ponto de entrada válido. Leia com atenção se a pergunta é "compila?" ou "executa?".

> [!COMPILADOR]
> Você é o `javac`. Este arquivo compila? Se compilar, o que acontece com `java Teste`?
>
> ```java compila
> public class Teste {
>     public static int main(String[] args) {
>         System.out.println("rodou");
>         return 0;
>     }
> }
> ```
>
> **Resposta:** Compila: para o compilador, é um método comum que devolve `int`. Mas a JVM não aceita um ponto de entrada que não seja `void`, então o programa nem começa e `rodou` nunca aparece. Quem vem do C estranha, porque lá o `main` devolve `int` de propósito.

> [!PREVENCAO]
> Quando o `javac` mostra vários erros, corrija o **primeiro** e compile de novo. Um `;` ou uma chave esquecida confunde o compilador, e as mensagens seguintes costumam ser consequência da primeira, não problemas de verdade.

> [!VERSAO]
> **Java 25 (1Z0-831).** O Java 25 finalizou os arquivos-fonte compactos e os métodos `main` de instância. Um arquivo pode conter só um método `void main()`, sem declarar classe, sem `public`, sem `static` e sem parâmetros. A JVM prefere `main(String[])` a `main()` e, se o método não for `static`, cria um objeto da classe antes de chamá-lo. No Java 17 e no 21 sem recursos em preview, isso não vale: o ponto de entrada precisa ser `public static void main(String[])`.

```java executar java25
void main() {
    IO.println("Olá do Java 25");
}
```

```saida
Olá do Java 25
```

`IO` é uma classe nova do pacote `java.lang` no Java 25, feita para programas simples. Ela tem `println`, `print` e `readln`.

## Argumentos de linha de comando

Tudo o que vem depois do nome da classe vira um elemento de `args`:

```bash
java Saudacao Ana "Bia Souza" 42
```

| Expressão | Valor |
|---|---|
| `args.length` | `3` |
| `args[0]` | `"Ana"` |
| `args[1]` | `"Bia Souza"` |
| `args[2]` | `"42"`, uma String, não um número |

As aspas servem só para juntar palavras com espaço; elas não fazem parte do valor. E quando o programa roda sem argumentos, `args` é um array **vazio**, nunca `null`:

```java executar
public class Argumentos {
    public static void main(String[] args) {
        System.out.println("Recebi " + args.length + " argumento(s)");
    }
}
```

```saida
Recebi 0 argumento(s)
```

Nesse mesmo cenário, ler `args[0]` lança `ArrayIndexOutOfBoundsException`, porque o array não tem posição 0.

## print, println e o JShell

`System.out.println` imprime e pula linha. `System.out.print` imprime sem pular. Um `println()` sem argumento imprime só a quebra de linha, o que gera uma linha em branco.

Para testar uma expressão sem criar classe, abra o terminal e digite `jshell`. Você escreve `10 / 4` e ele responde `$1 ==> 2`. É o jeito mais rápido de tirar uma dúvida durante o estudo.

## Por baixo dos panos

Afinal, o que o `javac` grava no `.class`? Dá para ver com outra ferramenta do JDK, o `javap`, que desmonta o bytecode. Pegue este programa:

```java executar
public class Soma {
    static int soma(int a, int b) {
        return a + b;
    }

    public static void main(String[] args) {
        int x = 2 + 3 * 4;
        System.out.println(soma(x, 1));
    }
}
```

```saida
15
```

Compile e desmonte:

```bash
javac Soma.java
javap -c Soma
```

O trecho que importa da saída real do `javap -c` (os comentários depois de `//` são nossos):

```text
static int soma(int, int);
  Code:
     0: iload_0       // empilha o 1º parâmetro (a)
     1: iload_1       // empilha o 2º parâmetro (b)
     2: iadd          // desempilha os dois, soma e empilha o resultado
     3: ireturn       // devolve o que está no topo da pilha

public static void main(java.lang.String[]);
  Code:
     0: bipush 14     // 2 + 3 * 4 já virou 14 na compilação
     2: istore_1      // guarda na variável local 1 (x)
     3: getstatic     // pega System.out
     6: iload_1
     7: iconst_1
     8: invokestatic  // chama soma(x, 1)
    11: invokevirtual // chama println
    14: return
```

Três coisas para reparar:

- A JVM é uma **máquina de pilha**. As instruções não falam de registradores: só empilham e desempilham valores. Um processador de verdade (x86, ARM) trabalha com registradores, e é o JIT que traduz uma coisa na outra.
- O `javac` já calculou `2 + 3 * 4`. Expressões feitas só de constantes são resolvidas na compilação, o chamado *constant folding*. Isso reaparece na prova em pegadinhas com String e `switch`.
- Cada instrução ocupa pouquíssimo espaço: `iadd` é um único byte. É daí que vem o nome **byte**code.

Todo arquivo `.class` começa com os mesmos quatro bytes, um "número mágico" que a JVM confere antes de carregar a classe. Um programa pode ler o próprio `.class` e mostrar:

```java executar
import java.io.InputStream;

public class Magico {
    public static void main(String[] args) throws Exception {
        try (InputStream in = Magico.class.getResourceAsStream("Magico.class")) { //> Abre o próprio .class, gerado pelo javac.
            byte[] b = in.readNBytes(4); //> Lê só os 4 primeiros bytes.
            System.out.printf("%02X %02X %02X %02X%n", b[0], b[1], b[2], b[3]); //> `%02X`: hexadecimal com 2 dígitos.
            System.out.println(0xCA + " " + 0xFE + " " + 0xBA + " " + 0xBE); //> Os mesmos bytes em decimal.
        }
    }
}
```

```saida
CA FE BA BE
202 254 186 190
```

> [!MATEMATICA]
> Hexadecimal é a base 16: os dígitos vão de 0 a 9 e depois de A (10) a F (15). Como 16 = 2⁴, cada dígito hexa representa exatamente 4 bits, e dois dígitos formam um byte (8 bits, de 00 a FF, ou 0 a 255). Para converter, multiplique o primeiro dígito por 16 e some o segundo: CA = 12 × 16 + 10 = 202, e FE = 15 × 16 + 14 = 254. Por isso programadores leem bytes em hexa: é a forma mais curta de escrever bits.

Agora compare com o que um compilador de C gera para a mesma função `soma` num processador x86-64, com otimização ligada (`gcc -O2`):

```text
soma:
    lea  eax, [rdi+rsi]   ; eax = a + b (os argumentos chegam nos registradores rdi e rsi)
    ret                   ; o resultado volta em eax
```

Esse código só roda em processadores x86-64. O bytecode roda em qualquer JVM, e é a JVM de cada máquina que, com o JIT, acaba produzindo algo parecido com esse assembly. Para ver isso acontecendo, cole a função no [Compiler Explorer](https://godbolt.org/) e escolha C ou Java.

## Resumo para a prova

- `javac Arquivo.java` gera bytecode; `java NomeDaClasse` executa, sem extensão
- `java Arquivo.java` compila em memória e executa, sem gravar `.class`
- Até o Java 21, o ponto de entrada é `public static void main(String[] args)`, com as variações de varargs, colchetes, ordem de modificadores e `final`
- O tipo de retorno fica colado no nome do método
- `args` nunca é `null`; sem argumentos, `args.length` é 0
- No Java 25, `void main()` sozinho num arquivo é um programa válido
