Todo arquivo `.java` segue uma ordem fixa, e a prova adora embaralhar essa ordem para ver se você percebe. Neste episódio você aprende a montar um arquivo do jeito que o compilador espera: pacote, imports, tipos e comentários.

## A ordem dentro do arquivo

Um arquivo-fonte tem, nesta ordem:

1. **No máximo uma** declaração `package`
2. **Zero ou mais** declarações `import`
3. **Uma ou mais** declarações de tipo: `class`, `interface`, `enum` ou `record`

```java
package br.com.javaflix.loja; //> 1. O pacote, no máximo um, sempre primeiro.

import java.util.List; //> 2. Os imports, quantos precisar.
import java.time.LocalDate;

public class Pedido { //> 3. Os tipos: classes, interfaces, enums e records.
    List<String> itens;
    LocalDate data;
}
```

Comentários e linhas em branco podem aparecer em qualquer lugar, inclusive antes do `package`. Qualquer outra coisa fora da ordem é erro de compilação.

![As três camadas de um arquivo Java, pacote, imports e tipos, ligadas à árvore de pastas src/br/com/loja/Pedido.java](/figuras/anatomia-do-arquivo.svg "O pacote vira pastas, e a classe public dá o nome do arquivo. Fora dessa ordem, o javac recusa.")

> [!PROVA]
> Um `import` depois de uma classe, ou um `package` depois de um `import`, não compila. O erro costuma aparecer como `class, interface, enum, or record expected`, apontando a linha fora de lugar.

## Comentários

Java tem três formas de comentário:

```java
// comentário de uma linha

/* comentário
   de várias linhas */

/**
 * Comentário de documentação (javadoc).
 * Vira HTML com a ferramenta javadoc.
 */
```

Comentários de bloco **não se aninham**. O primeiro `*/` fecha o comentário, e o que vem depois volta a ser código:

```java nao-compila
/* externo /* interno */ isto aqui já é código */
```

E o que está dentro de uma String não é comentário, é texto:

```java executar
public class Textos {
    public static void main(String[] args) {
        // System.out.println("não aparece");
        System.out.println("isto // aparece");
        System.out.println("/* isto também */");
    }
}
```

```saida
isto // aparece
/* isto também */
```

> [!ANTES]
> Até o Java 22, comentários de documentação eram só `/** */`, escritos em HTML (`<p>`, `<code>`). Desde o Java 23, também dá para escrever cada linha começando com `///`, em Markdown, como este site. Você vai ver os dois estilos em projetos reais.

Uma curiosidade que já caiu em prova: antes de qualquer outra coisa, o compilador traduz os escapes Unicode, como `\u000a`, em caracteres. Se essa tradução cair dentro de um comentário, o comentário pode acabar antes do que parece:

```java executar
public class Escape {
    public static void main(String[] args) {
        // isto é só um comentário \u000a System.out.println("e isto roda");
        System.out.println("fim");
    }
}
```

```saida
e isto roda
fim
```

> [!MATEMATICA]
> Um escape Unicode é `\u` seguido de quatro dígitos hexadecimais, que dão o número do caractere. `000A` é 0 × 16³ + 0 × 16² + 0 × 16 + 10 = 10, o código da quebra de linha. Por isso `\u000a` vira um "Enter" no meio do comentário de linha, e o resto da linha volta a ser código. Do mesmo jeito, `A` é 4 × 16 + 1 = 65, a letra `A`.

## Classes e arquivos

Um arquivo pode declarar várias classes de topo, mas com duas regras:

- No máximo **uma** delas pode ser `public`
- Se houver uma classe `public`, o arquivo **precisa** ter o nome dela

```java executar
class Motor {
    String ligar() {
        return "vrum";
    }
}

public class Carro {
    public static void main(String[] args) {
        System.out.println(new Motor().ligar());
    }
}
```

```saida
vrum
```

> [!PENSE]
> Esse arquivo tem duas classes. Quantos arquivos `.class` o `javac` grava ao compilá-lo?

Esse código vive em `Carro.java`. Ao compilar, o `javac` gera **dois** arquivos: `Carro.class` e `Motor.class`. Cada tipo vira o seu próprio `.class`.

> [!PROVA]
> Duas classes `public` no mesmo arquivo não compilam. E uma classe `public Produto` dentro de `Loja.java` também não: o erro diz que a classe pública deveria estar em `Produto.java`.

## Pacotes

Pacotes organizam classes e evitam conflito de nomes. A convenção é usar o domínio ao contrário, em minúsculas: `br.com.javaflix.loja`. A estrutura de pastas espelha o pacote, e quem executa precisa usar o **nome totalmente qualificado** da classe:

```bash
javac -d out src/br/com/javaflix/loja/Pedido.java   # grava out/br/com/javaflix/loja/Pedido.class
java -cp out br.com.javaflix.loja.Pedido             # classpath + nome qualificado
```

A opção `-d` diz onde gravar os `.class`, já criando as pastas do pacote. A opção `-cp` (ou `-classpath`, ou `--class-path`) diz ao `java` onde procurar as classes. Uma classe sem `package` fica no **pacote padrão**, o que funciona para exemplos, mas não é usado em projetos reais.

> [!ERRO]
> Compilar sem `-d` uma classe que tem `package`. O `javac Pedido.java` grava o `Pedido.class` na pasta atual, fora da estrutura `br/com/javaflix/loja`, e depois o `java br.com.javaflix.loja.Pedido` não encontra a classe. O erro é `ClassNotFoundException`, e o código está certo: o que está errado é onde o `.class` foi parar.

> [!ENGENHARIA]
> O domínio ao contrário não é capricho: como cada empresa tem um domínio próprio, `br.com.javaflix.loja.Pedido` e `com.outraempresa.Pedido` nunca se confundem, mesmo dentro do mesmo programa. Duas bibliotecas de autores diferentes podem ter uma classe `Pedido` sem nenhum conflito.

> [!LAPIS]
> O arquivo `src/br/com/padaria/Pao.java` começa com `package br.com.padaria;` e tem um `main`. Escreva os dois comandos: um que compila para a pasta `out` e outro que executa.
>
> **Resposta:** `javac -d out src/br/com/padaria/Pao.java` e `java -cp out br.com.padaria.Pao`. O `javac` recebe o caminho do arquivo, com barras e `.java`; o `java` recebe o nome qualificado da classe, com pontos e sem extensão.

## Imports

Sem `import`, você pode usar qualquer classe pelo nome completo:

```java
java.time.LocalDate hoje = java.time.LocalDate.now();
```

O `import` só serve para encurtar esse nome. Ele não carrega nada, não deixa o programa mais lento e não tem efeito em tempo de execução. Há dois tipos:

```java
import java.util.List;   // importa uma classe específica
import java.util.*;      // importa todas as classes do pacote java.util
```

Três regras que caem sempre:

- `java.lang` é importado automaticamente: `String`, `System`, `Math` e `Integer` funcionam sem `import`
- O curinga `*` importa as classes do pacote, **não** os subpacotes. `import java.util.*;` não importa `java.util.function.Function`
- Imports redundantes compilam: `import java.lang.String;` ou o mesmo `import java.util.*;` duas vezes

> [!PERGUNTAS]
> **P:** O curinga `import java.util.*;` deixa o programa mais pesado que importar só `List`?
>
> **R:** Não. Nenhum import copia ou carrega código: ele só ensina ao compilador o nome curto. O `.class` gerado é idêntico nos dois casos. O curinga só pesa na leitura, porque esconde de onde cada classe vem.
>
> **P:** Então por que as IDEs preferem imports explícitos?
>
> **R:** Para quem lê saber de onde vem cada nome e para evitar conflitos como o do `Date`, logo abaixo: com imports explícitos, uma classe nova num pacote importado com curinga nunca quebra o seu código.
>
> **P:** Se `java.lang` vem de graça, por que `java.lang.String` também funciona?
>
> **R:** Porque o nome completo sempre funciona, com ou sem import. O import automático só permite escrever `String` em vez dele.

> [!IA]
> Assistentes de IA às vezes inventam o pacote de uma classe, como `import java.util.LocalDate;` (o certo é `java.time.LocalDate`), ou colocam `import java.util.*;` e `import java.sql.*;` juntos, criando o conflito de `Date` que você vai ver a seguir. Compile antes de aceitar: um pacote inventado não passa do `javac`.

## Conflito de nomes

`java.util` e `java.sql` têm, cada um, uma classe `Date`. Se você importa os dois pacotes com curinga e usa `Date`, o compilador não sabe qual é:

```java nao-compila
import java.util.*;
import java.sql.*;

public class Agenda {
    Date dia;   // reference to Date is ambiguous
}
```

Um import **explícito** vence o curinga, então este compila e usa `java.util.Date`:

```java executar
import java.util.Date;
import java.sql.*;

public class Agenda {
    public static void main(String[] args) {
        Date d = new Date(0);
        System.out.println(d.getClass().getName());
    }
}
```

```saida
java.util.Date
```

Dois imports explícitos com o mesmo nome simples (`import java.util.Date;` e `import java.sql.Date;`) não compilam, mesmo que você nunca use `Date`. Se precisar das duas, importe uma e use a outra pelo nome completo.

> [!COMPILADOR]
> Você é o `javac`. Este arquivo compila? Se compilar, de que pacote vêm `Date` e `Timestamp`?
>
> ```java compila
> import java.util.*;
> import java.sql.*;
> import java.util.Date;
>
> public class Agenda {
>     Date hoje;
>     Timestamp agora;
> }
> ```
>
> **Resposta:** Compila. O import explícito de `java.util.Date` vence os dois curingas e acaba com a ambiguidade. `Timestamp` só existe em `java.sql`, então chega pelo curinga sem conflito nenhum.

> [!VERSAO]
> **Java 25 (1Z0-831).** Existe também o import de módulo: `import module java.base;` importa de uma vez todas as classes públicas dos pacotes que o módulo `java.base` exporta, como `java.util`, `java.io` e `java.nio.file`. Nos arquivos-fonte compactos, esse import é automático.

```java executar java25
import module java.base;

public class Modulo {
    public static void main(String[] args) {
        List<String> nomes = List.of("Ana", "Bia");
        Path arquivo = Path.of("dados.txt");
        System.out.println(nomes.size() + " " + arquivo);
    }
}
```

```saida
2 dados.txt
```

## Na IDE

O IntelliJ cuida de quase tudo deste episódio sozinho:

- **Pacotes.** Clique com o botão direito em `src` e escolha **New > Package**. A IDE cria as pastas, e cada classe criada dentro do pacote (**New > Java Class**) já nasce com a linha `package` certa.
- **Imports.** Basta usar a classe: ela fica vermelha, e **Alt + Enter** escreve o `import` no lugar certo. **Ctrl + Alt + O** (*Optimize Imports*) apaga os que não são usados e põe o resto em ordem.
- **Comentários.** **Ctrl + /** comenta ou descomenta a linha; **Ctrl + Shift + /**, um bloco. Digitar `/**` e Enter acima de um método monta o esqueleto do javadoc.

![O editor do IntelliJ com LocalDate em vermelho e a sugestão de importar java.time.LocalDate](/figuras/intellij-import.svg "1: a classe sem import fica vermelha. 2: a IDE sugere o pacote certo; Alt + Enter escreve o import.")

Repare que a IDE mostra **qual** `LocalDate` vai importar. Quando existir mais de uma classe com o mesmo nome, como `Date`, ela pergunta qual você quer, em vez de chutar. Por padrão, quando você usa cinco ou mais classes do mesmo pacote, o IntelliJ troca os imports por um curinga `*`; dá para mudar isso em **Settings > Editor > Code Style > Java > Imports**.

## Por baixo dos panos

Imports existem só para você e para o compilador. No `.class`, toda classe aparece pelo nome completo, com barras no lugar dos pontos. Desmontando o `Ola.class` do episódio anterior com `javap -c Ola`, a chamada ao `println` aparece assim:

```text
getstatic     #7    // Field java/lang/System.out:Ljava/io/PrintStream;
invokevirtual #15   // Method java/io/PrintStream.println:(Ljava/lang/String;)V
```

Repare em `java/lang/System` e `java/io/PrintStream`: o bytecode não sabe o que é um import. Por isso imports não deixam o programa mais lento, e por isso dois `.class` de pacotes diferentes com o mesmo nome simples convivem sem problema: para a JVM, o nome de verdade é sempre o completo.

O pacote também vira estrutura de pastas por um motivo prático: quando a JVM precisa da classe `br.com.loja.Pedido`, o *class loader* procura o arquivo `br/com/loja/Pedido.class` a partir de cada entrada do classpath. Classe em pasta errada é classe que não é encontrada. O carregamento de classes, que acontece sob demanda durante a execução, é assunto do episódio sobre [a JVM por dentro](/assistir/aprendiz-t2-e04), na trilha Aprendiz.

## Resumo para a prova

- Ordem: `package`, depois `import`, depois tipos. Comentários podem vir em qualquer lugar
- No máximo uma classe `public` por arquivo, e ela dá nome ao arquivo
- Cada tipo vira o seu próprio `.class`
- `java.lang` vem de graça; o curinga não pega subpacotes
- Curinga contra curinga com o mesmo nome dá ambiguidade; o import explícito vence o curinga
- Comentários de bloco não se aninham; comentário dentro de String é texto
