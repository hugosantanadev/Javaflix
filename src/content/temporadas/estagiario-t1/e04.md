Último episódio do primeiro dia. Você vai aprender que nomes uma variável pode ter, quando o compilador exige que ela tenha valor, como o `var` funciona e até onde uma variável existe. São regras pequenas que derrubam muita gente na prova.

## Identificadores

O nome de uma variável, método ou classe é um **identificador**. As regras:

- Começa com letra, `$` ou `_`
- Depois pode ter letras, dígitos, `$` e `_`
- Não pode ser uma palavra reservada
- Maiúsculas e minúsculas são diferentes: `total` e `Total` são dois nomes

```java
int $preco = 10;      // ok
int _quantidade = 5;  // ok
int valor2 = 3;       // ok
int 2valor = 3;       // erro: começa com dígito
int valor-total = 1;  // erro: hífen não é permitido
int class = 7;        // erro: palavra reservada
```

Algumas palavras são reservadas mesmo sem uso, como `goto` e `const`. E `true`, `false` e `null` são literais, então também não servem como nome.

> [!MATEMATICA]
> Quantos nomes de duas letras são válidos, contando só as letras sem acento? O primeiro caractere tem 54 opções: 26 minúsculas, 26 maiúsculas, `$` e `_`. O segundo tem essas 54 mais os 10 dígitos, 64 opções. Pelo princípio multiplicativo, são 54 × 64 = 3.456 combinações. Tirando as duas palavras reservadas de duas letras, `do` e `if`, sobram 3.454. Repare que o dígito só entra na conta da segunda posição: é a mesma regra que barra o `2valor`.

### Palavras que parecem reservadas, mas não são

`var`, `record`, `yield`, `sealed` e `permits` são **palavras-chave contextuais**: só têm significado especial em certos lugares. Fora deles, viram identificadores comuns:

```java executar
public class Contextuais {
    public static void main(String[] args) {
        String var = "var";
        String record = "record";
        int sealed = 1;
        System.out.println(var + record + sealed);
    }
}
```

```saida
varrecord1
```

Ninguém escreve assim de propósito, mas a prova escreve.

> [!VERSAO]
> **O underscore sozinho.** Desde o Java 9, `_` sozinho não é um nome válido. No Java 22 ele ganhou outro papel: **variável sem nome**. No Java 25 (1Z0-831), `int _ = 10;` compila, mas a variável não pode ser lida, e dá para declarar várias `_` no mesmo bloco. No Java 17 e 21, essa linha não compila.

## Declarar várias variáveis de uma vez

Uma declaração pode criar várias variáveis do **mesmo tipo**:

```java
int a, b, c;            // três ints sem valor
int x = 1, y, z = 3;    // só x e z inicializadas
int p = 1, double q = 2;  // erro: um tipo por declaração
int m, int n;             // erro: o tipo não se repete
```

> [!ERRO]
> Ler `int a, b = 0;` como "a e b valem zero". O inicializador vale só para a variável colada nele: `b` vale 0, e `a` continua sem valor. Usar `a` em seguida não compila. Quando quiser os dois zerados, escreva `int a = 0, b = 0;`, ou melhor, uma declaração por linha.

## Variáveis locais precisam de valor

Campos de classe ganham valor padrão. Variáveis **locais**, declaradas dentro de métodos, não. O compilador só deixa você ler uma variável local quando consegue provar que ela recebeu valor em **todos** os caminhos possíveis.

> [!PENSE]
> No trecho abaixo, `deposito` vale 100, então o `if` sempre entra e `saldo` sempre recebe valor. Por que o compilador reclamaria?

```java nao-compila
int saldo;
int deposito = 100;
if (deposito > 50) {
    saldo = deposito;
}
System.out.println(saldo);   // erro: saldo pode não ter sido inicializada
```

O compilador não executa o `if` para saber que a condição é verdadeira. Para ele, existe um caminho em que `saldo` fica sem valor. Com um `else` que também atribui, todos os caminhos ficam cobertos:

```java executar
public class Situacao {
    public static void main(String[] args) {
        int nota = 7;
        String situacao; //> Declarada sem valor. Ainda não pode ser lida.
        if (nota >= 6) {
            situacao = "aprovado"; //> Um caminho atribui...
        } else {
            situacao = "reprovado"; //> ...e o outro também.
        }
        System.out.println(situacao); //> Todos os caminhos atribuíram: compila.
    }
}
```

```saida
aprovado
```

> [!PROVA]
> Declarar sem inicializar não é erro. O erro só acontece quando a variável é **lida** antes de receber valor com certeza.

## var

Desde o Java 10, variáveis locais podem usar `var` no lugar do tipo. O compilador olha o valor e decide o tipo:

```java executar
public class Inferencia {
    public static void main(String[] args) {
        var nome = "Ana";       // String
        var idade = 30;         // int
        var saldo = 10L;        // long
        var media = 7.5f;       // float
        var letra = 'x';        // char
        System.out.println(nome + idade + saldo + media + letra);
    }
}
```

```saida
Ana30107.5x
```

O `var` **não** deixa a variável dinâmica. O tipo é decidido na compilação e nunca muda. Se `idade` é `int`, receber uma String depois é erro.

As regras do `var`:

- Só em **variáveis locais**: não vale para campos, parâmetros de método nem tipo de retorno
- Precisa de inicializador na mesma linha: `var x;` não compila
- O inicializador não pode ser `null` sozinho: `var x = null;` não compila
- Não aceita inicializador de array solto: `var notas = {7, 8};` não compila, mas `var notas = new int[] {7, 8};` compila
- Uma variável por declaração: `var a = 1, b = 2;` não compila

> [!DICA]
> `var` também vale no `for`, no `for-each` e no try-with-resources, que você vai ver em outras temporadas.

> [!ANTES]
> Até o Java 9, todo tipo era escrito por extenso: `String nome = "Ana";`. Quem queria inferência usava o `val` do **Lombok**, uma biblioteca que gera código durante a compilação: `val nome = "Ana";` criava uma variável `final` com o tipo inferido. Com o `var` nativo do Java 10, o `val` caiu em desuso. Muitos sistemas ainda rodam em Java 8, então você vai ver código sem `var` por um bom tempo.

> [!BOAPRATICA]
> Use `var` quando o tipo está óbvio do lado direito, como em `var lista = new ArrayList<String>();`. Evite quando ele esconde o tipo: em `var total = calcular();`, quem lê precisa abrir outro método para saber se `total` é `int`, `double` ou `BigDecimal`.

> [!IA]
> Assistentes de IA escrevem `var` em campos, parâmetros e tipos de retorno, onde ele não compila, e às vezes dizem que `var` deixa a variável "dinâmica", como em JavaScript. Não deixa: o tipo é decidido na compilação e nunca muda.

## Escopo

Uma variável local existe do ponto em que é declarada até o fim do **bloco** `{ }` onde foi declarada. Fora dele, ela não existe:

```java executar
public class Blocos {
    public static void main(String[] args) {
        int x = 1;
        {
            int y = x + 1;
            System.out.println(y);
        }
        {
            int y = 10;     // outro y, em outro bloco
            System.out.println(x + y);
        }
    }
}
```

```saida
2
11
```

![O código do exemplo Blocos com os dois blocos destacados e, ao lado, barras mostrando de que linha a que linha x e cada y existem](/figuras/escopo-dos-blocos.svg "x existe do começo ao fim; cada y nasce na sua declaração e morre no } do seu bloco, por isso os dois nunca se encontram.")

Dentro de um bloco aninhado você enxerga as variáveis de fora, mas **não pode declarar outra com o mesmo nome** enquanto a de fora ainda existe:

```java nao-compila
int total = 0;
{
    int total = 5;   // erro: total já está definida
}
```

A variável do `for` também tem escopo limitado ao laço:

```java nao-compila
for (int i = 0; i < 3; i++) { }
System.out.println(i);   // erro: i não existe aqui
```

> [!COMPILADOR]
> Você é o `javac`. Este arquivo compila? Se não compilar, em que linha você reclama?
>
> ```java nao-compila
> public class Frete {
>     public static void main(String[] args) {
>         int peso = 12;
>         if (peso > 10) {
>             int taxa = 15;
>         }
>         System.out.println("Taxa: " + taxa);
>     }
> }
> ```
>
> **Resposta:** Não compila, na linha 7. A `taxa` nasce dentro do bloco do `if` e morre no `}` da linha 6. Para usar depois, declare antes do `if`, já com um valor para o caso em que ele não entra: `int taxa = 0;`.

> [!PREVENCAO]
> Declare cada variável no **menor escopo** em que ela é usada e, se possível, já com valor. Uma variável que só existe dentro do laço não pode ser lida por engano depois dele, e uma variável que nasce com valor nunca cai no erro de "pode não ter sido inicializada".

> [!CONVERSA]
> **Campo:** Eu moro no objeto. Nasço com valor padrão, `0`, `false` ou `null`, e vivo enquanto o objeto viver.
>
> **Variável local:** Eu moro na pilha do método. Nasço na minha declaração, morro no fim do meu bloco, e ninguém me dá valor de graça.
>
> **Campo:** Que vida curta. E se alguém tentar ler você antes de você ter valor?
>
> **Variável local:** O compilador não deixa. É por isso que não preciso de valor padrão: ninguém nunca me lê vazia.
>
> **Campo:** Comigo é diferente. Um método pode me ler a qualquer hora, então a JVM zera a memória do objeto antes de qualquer coisa.
>
> **Variável local:** E eu ganho em outro ponto: como só existo dentro de um método, duas threads rodando o mesmo método têm cada uma a sua cópia de mim. Você, compartilhado, dá dor de cabeça no Sênior.

```imas executar
public class Placar {
    public static void main(String[] args) {
        int pontos = 0;
        for (int rodada = 1; rodada <= 3; rodada++) {
            pontos += rodada * 10;
        }
        System.out.println("Total: " + pontos);
    }
}
```

```saida
Total: 60
```

## Na IDE

Três recursos do IntelliJ ligados a este episódio:

- **Ver o tipo de um `var`.** Com o cursor no nome da variável, **Ctrl + Shift + P** mostra o tipo que o compilador inferiu.
- **Trocar `var` pelo tipo, e o contrário.** **Alt + Enter** sobre o `var` oferece *Replace 'var' with explicit type*. Sobre um tipo escrito, a mesma tecla oferece *Replace explicit type with 'var'*.
- **Renomear com segurança.** **Shift + F6** renomeia uma variável e todos os seus usos, respeitando o escopo: um `y` de outro bloco não é tocado. Trocar o nome na mão, com localizar e substituir, troca também o que não devia.

![O menu do Alt + Enter sobre um var no IntelliJ, com a opção de trocar pelo tipo explícito e a prévia do resultado](/figuras/intellij-var.svg "1: o cursor sobre o var. 2: a opção do Alt + Enter. 3: a prévia mostra o código com o tipo que o compilador inferiu.")

A IDE também avisa os erros deste episódio enquanto você digita: *Variable 'saldo' might not have been initialized*, a mesma mensagem do `javac`, e uma variável declarada e nunca usada fica em cinza.

## Por baixo dos panos

Nomes de variáveis locais, `var` e escopo existem só na compilação. No bytecode, uma variável local vira uma **posição numerada** num array do método (os *slots*). Compare dois métodos:

```java
static int a() { var x = 10; return x * 2; }
static int b() { int x = 10; return x * 2; }
```

O `javap -c` dos dois é idêntico:

```text
0: bipush 10
2: istore_0      // guarda 10 no slot 0
3: iload_0
4: iconst_2
5: imul
6: ireturn
```

Não sobra nenhum rastro do `var`: ele é só o compilador escrevendo o tipo por você. O nome `x` também some (a não ser que você compile com `javac -g`, que guarda nomes para o depurador). E o escopo de bloco? Quando um bloco termina, o compilador pode reaproveitar o mesmo slot para outra variável. É por isso que a JVM não precisa "apagar" nada no fim do bloco.

A regra de "variável local precisa de valor antes de ser lida" também é coisa do compilador, e existe por segurança: o verificador de bytecode da JVM rejeita uma classe que leia um slot nunca escrito. Campos não têm esse problema porque a JVM zera a memória de todo objeto novo, e daí vêm os valores padrão (`0`, `false`, `null`).

## Resumo para a prova

- Identificador começa com letra, `$` ou `_`, sem palavras reservadas
- `var`, `record`, `yield`, `sealed` e `permits` podem ser nomes de variável
- `_` sozinho não compila até o Java 21; no Java 25 é variável sem nome
- Variável local só pode ser lida depois de receber valor em todos os caminhos
- `var` é só para locais, com inicializador, sem `null`, sem `{}` solto e sem declaração múltipla
- Escopo termina no `}` do bloco; não dá para redeclarar um nome que ainda está no escopo
