No cargo Estagiário você viu que `0.1 + 0.2` não dá `0.3`. Este episódio abre o `double` para mostrar exatamente o que está guardado lá dentro, por que alguns números cabem e outros não, quais valores estranhos existem (infinito, NaN, zero negativo) e como lidar com dinheiro sem perder centavos. Tudo segue o padrão **IEEE 754**, de 1985, usado por praticamente todo processador e toda linguagem.

## Notação científica em base 2

Em física, você escreve 602.000.000.000.000.000.000.000 como 6,02 × 10²³: um número com um dígito antes da vírgula (a **mantissa**) vezes uma potência da base (o **expoente**). O ponto flutuante faz o mesmo em base 2:

```text
6,5 (decimal) = 110,1 (binário) = 1,101 × 2²
```

Normalizado, todo número binário diferente de zero começa com `1,`. Como esse 1 é sempre o mesmo, o IEEE 754 **nem o guarda**: é o **bit implícito**, um bit de precisão de graça.

## Os três campos

| Tipo | Total | Sinal | Expoente | Fração | Bias | Dígitos decimais |
|---|---|---|---|---|---|---|
| `float` | 32 bits | 1 | 8 | 23 | 127 | cerca de 7 |
| `double` | 64 bits | 1 | 11 | 52 | 1023 | cerca de 16 |

O valor de um número normalizado é:

```text
valor = (−1)ˢ × 1,fração × 2^(expoente − bias)
```

O expoente é guardado **somado ao bias** (127 no `float`) para não precisar de sinal: o expoente 2 vira 129, o −4 vira 123. Assim, comparar dois floats positivos é quase o mesmo que comparar os bits como inteiros.

Decodificando −6,5: sinal 1; 6,5 = 1,101 × 2², então expoente 2 + 127 = 129 = `10000001`; fração `101` seguida de zeros. Confira com o Java:

```java executar
public class Campos {
    static String campos(float f) {
        String b = String.format("%32s", Integer.toBinaryString(Float.floatToIntBits(f))).replace(' ', '0');
        return b.substring(0, 1) + " " + b.substring(1, 9) + " " + b.substring(9);
    }

    public static void main(String[] args) {
        System.out.println(campos(1.0f));
        System.out.println(campos(-6.5f));
        System.out.println(campos(0.1f));
        System.out.println(Integer.toHexString(Float.floatToIntBits(-6.5f)));
    }
}
```

```saida
0 01111111 00000000000000000000000
1 10000001 10100000000000000000000
0 01111011 10011001100110011001101
c0d00000
```

O 1,0 tem expoente 127 (2⁰) e fração zero. O 0,1 tem uma fração que repete `1001 1001 1001...` e termina arredondada para cima (`...1101`). É ali que mora o erro.

## Por que 0,1 não cabe

Para converter uma fração decimal para binário, multiplique por 2 e anote a parte inteira, repetidamente:

| Passo | Conta | Bit |
|---|---|---|
| 1 | 0,1 × 2 = 0,2 | 0 |
| 2 | 0,2 × 2 = 0,4 | 0 |
| 3 | 0,4 × 2 = 0,8 | 0 |
| 4 | 0,8 × 2 = 1,6 | 1 |
| 5 | 0,6 × 2 = 1,2 | 1 |
| 6 | 0,2 × 2 = 0,4 | 0 |
| 7 | volta ao passo 2 | ... |

O 0,2 reapareceu no passo 6, então o padrão `0011` se repete para sempre: 0,1 = 0,0001100110011... em binário. Com 52 bits de fração, a dízima é cortada e arredondada.

A regra geral: uma fração p/q (simplificada) tem representação finita em base 2 **só se q for uma potência de 2**. Em base 10, só se q tiver apenas os fatores 2 e 5. Por isso 1/10 é exato em decimal e infinito em binário, 1/4 é exato nos dois e 1/3 não é exato em nenhum. Dá para ver o valor que o `double` guarda de verdade com `BigDecimal`:

```java executar
System.out.println(new BigDecimal(0.1));
System.out.println(new BigDecimal("0.1"));
System.out.println(0.1 + 0.2);
System.out.println((0.1 + 0.2) + 0.3);
System.out.println(0.1 + (0.2 + 0.3));
```

```saida
0.1000000000000000055511151231257827021181583404541015625
0.1
0.30000000000000004
0.6000000000000001
0.6
```

As duas últimas linhas mostram que a soma de ponto flutuante **não é associativa**: a ordem muda o arredondamento. É por isso que um compilador não pode reordenar contas com `double` livremente (o `-ffast-math` do GCC permite, trocando exatidão por velocidade).

## Precisão: o espaçamento cresce com o número

Com 53 bits significativos (52 guardados mais o implícito), entre 1 e 2 existem 2⁵² doubles igualmente espaçados. Entre 2 e 4, também 2⁵², mas com o dobro do espaçamento. A distância até o próximo `double` se chama **ulp** (*unit in the last place*) e cresce junto com o número:

```java executar
float f = 16_777_216f;
System.out.println(f + 1 == f);
double d = 9_007_199_254_740_992.0;
System.out.println(d + 1 == d);
System.out.println(Math.ulp(1.0));
System.out.println(Math.ulp(1e16));
```

```saida
true
true
2.220446049250313E-16
2.0
```

O `float` representa todo inteiro até 2²⁴ = 16.777.216, e o `double`, até 2⁵³ = 9.007.199.254.740.992. Depois disso começam a faltar inteiros: perto de 10¹⁶, os doubles vão de 2 em 2. O que fica constante é o **erro relativo**: cerca de 10⁻¹⁶ para `double` e 10⁻⁷ para `float`, seja o número grande ou pequeno. Por isso todo `int` cabe num `double`, mas nem todo `long` cabe.

## Valores especiais

Os expoentes extremos são reservados:

| Expoente | Fração | Significado |
|---|---|---|
| todos 0 | zero | ±0 (existe zero negativo) |
| todos 0 | diferente de zero | subnormais: números minúsculos, perto de zero |
| todos 1 | zero | ±infinito |
| todos 1 | diferente de zero | NaN (*not a number*) |

Por causa deles, divisão de `double` por zero **não lança exceção**, ao contrário da divisão de inteiros:

```java executar
System.out.println(1.0 / 0);
System.out.println(1 / -0.0);
System.out.println(0.0 / 0 == 0.0 / 0);
System.out.println(Double.isNaN(Math.sqrt(-1)));
System.out.println(0.0 == -0.0);
System.out.println(Double.valueOf(0.0).equals(-0.0));
System.out.println(Double.MIN_VALUE);
```

```saida
Infinity
-Infinity
false
true
true
false
4.9E-324
```

NaN é diferente de tudo, **inclusive dele mesmo**: o único jeito de testar é `Double.isNaN(x)`. E `0.0 == -0.0` é verdadeiro pela regra numérica do `==`, mas `equals` compara os bits e diz que são diferentes. A última linha é uma pegadinha clássica: `Double.MIN_VALUE` **não** é o double mais negativo, e sim o menor positivo (um subnormal). O mais negativo é `-Double.MAX_VALUE`.

## Convertendo para inteiro

O cast de `double` para `int` **descarta a parte fracionária** (arredonda em direção a zero) e, se o valor não couber, **satura** no limite em vez de dar a volta. NaN vira 0.

```java executar
System.out.println((int) 3.99);
System.out.println((int) -3.99);
System.out.println((int) 1e20);
System.out.println((int) Double.NaN);
System.out.println(Math.round(2.5) + " " + Math.round(-2.5));
```

```saida
3
-3
2147483647
0
3 -2
```

`Math.round` soma 0,5 e arredonda para baixo, então os empates vão sempre para +∞: 2,5 vira 3 e −2,5 vira −2. Em 1996, o foguete Ariane 5 explodiu 37 segundos depois do lançamento porque um valor de ponto flutuante de 64 bits foi convertido para um inteiro de 16 bits e não coube. Em Java ele teria saturado; no software do foguete, gerou uma exceção que derrubou o sistema de navegação.

## Comparando com tolerância

Erros pequenos se acumulam. Nunca compare resultados de contas com `==`:

```java executar
double soma = 0;
for (int i = 0; i < 10; i++) {
    soma += 0.1;
}
System.out.println(soma);
System.out.println(soma == 1.0);
System.out.println(Math.abs(soma - 1.0) < 1e-9);
```

```saida
0.9999999999999999
false
true
```

A tolerância fixa (`1e-9`) serve para números perto de 1. Para valores de qualquer tamanho, use uma tolerância **relativa**: `Math.abs(a - b) <= 1e-9 * Math.max(Math.abs(a), Math.abs(b))`.

## Dinheiro: `BigDecimal` ou centavos

Dinheiro precisa de exatidão decimal, e aí `double` é a ferramenta errada. As duas soluções corretas:

- **Centavos num `long`**: R$ 19,90 vira `1990`. Simples e rápido, bom quando só há somas e subtrações.
- **`BigDecimal`**: guarda um inteiro gigante e uma escala (quantas casas depois da vírgula), em base 10. Crie sempre a partir de `String`, nunca de `double`.

```java executar
BigDecimal total = new BigDecimal("100.00");
BigDecimal parcela = total.divide(new BigDecimal("3"), 2, RoundingMode.HALF_EVEN);
System.out.println(parcela);
System.out.println(total.subtract(parcela.multiply(new BigDecimal("2"))));
System.out.println(new BigDecimal("2.50").equals(new BigDecimal("2.5")));
System.out.println(new BigDecimal("2.50").compareTo(new BigDecimal("2.5")) == 0);
```

```saida
33.33
33.34
false
true
```

Três regras do `BigDecimal` que derrubam sistemas de verdade:

- `divide` sem escala e sem arredondamento lança `ArithmeticException` quando o resultado é uma dízima, como 100 ÷ 3.
- `equals` considera a escala: `2.50` e `2.5` são diferentes. Para comparar valores, use `compareTo`.
- `HALF_EVEN`, o "arredondamento do banqueiro", manda os empates para o vizinho par (2,345 vira 2,34 e 2,355 vira 2,36). Ao longo de milhões de operações, os erros para cima e para baixo se cancelam.

> [!DICA]
> Por baixo dos panos: até o Java 16, a JVM podia usar a precisão estendida de 80 bits dos antigos coprocessadores x87 em contas intermediárias, e um mesmo programa podia dar resultados diferentes em máquinas diferentes. O modificador `strictfp` existia para proibir isso. Desde o Java 17 (JEP 306), toda conta de ponto flutuante é estrita: o resultado é idêntico em qualquer plataforma, e `strictfp` não faz mais diferença.

## Resumo

- `float` (32 bits) e `double` (64 bits): sinal, expoente com bias e fração com bit implícito
- p/q só é exato em binário se q for potência de 2: 0,5 e 0,375 cabem; 0,1 e 0,2 não
- Soma de ponto flutuante não é associativa; compare com tolerância, não com `==`
- `float` tem cerca de 7 dígitos e `double` cerca de 16; inteiros exatos até 2²⁴ e 2⁵³
- Divisão por zero em `double` dá infinito ou NaN; NaN ≠ NaN; existe −0,0
- `Double.MIN_VALUE` é o menor **positivo**
- Cast para `int` trunca em direção a zero e satura; `Math.round` manda empates para +∞
- Dinheiro: `BigDecimal` a partir de `String`, ou centavos em `long`; compare com `compareTo`
