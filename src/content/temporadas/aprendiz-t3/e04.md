O resto da divisão parece assunto do ensino fundamental, mas está em todo lugar na programação: testar se um número é par, andar num buffer circular, calcular o dia da semana, validar um CPF, escolher a posição de uma chave num `HashMap`, cifrar uma conexão HTTPS. Este episódio mostra a matemática que une tudo isso, a **aritmética modular**, e a armadilha que o Java esconde no operador `%` com números negativos.

## A divisão euclidiana

Dividir um inteiro a por um inteiro b > 0 é encontrar o **quociente** q e o **resto** r tais que:

```text
a = q · b + r,   com 0 ≤ r < b
```

Para 17 ÷ 5: 17 = 3 · 5 + 2, então q = 3 e r = 2. Esses q e r existem e são únicos, e o resto fica sempre entre 0 e b − 1. Na matemática, essa é a definição de "a mod b".

## Como o Java divide inteiros

O Java não segue essa definição quando há negativos. O `/` arredonda o quociente **em direção a zero**, e o `%` é calculado para que esta identidade valha sempre (JLS 15.17.3):

```text
(a / b) * b + (a % b) == a
```

Consequência: o resto do Java tem o **sinal do dividendo**, e pode ser negativo. Para a versão matemática, existem `Math.floorDiv` e `Math.floorMod`, que arredondam o quociente para baixo (em direção a −∞):

```java executar
public class Restos {
    public static void main(String[] args) {
        int[][] pares = {{7, 3}, {-7, 3}, {7, -3}, {-7, -3}};
        System.out.println("a   b   a/b a%b floorDiv floorMod");
        for (int[] p : pares) {
            int a = p[0], b = p[1];
            System.out.printf("%-3d %-3d %-3d %-3d %-8d %d%n",
                    a, b, a / b, a % b, Math.floorDiv(a, b), Math.floorMod(a, b));
        }
    }
}
```

```saida
a   b   a/b a%b floorDiv floorMod
7   3   2   1   2        1
-7  3   -2  -1  -3       2
7   -3  -2  1   -3       -2
-7  -3  2   -1  2        -1
```

A segunda linha é a que importa: −7 = (−2) · 3 + (−1) para o `%`, e −7 = (−3) · 3 + 2 para o `floorMod`. Com divisor positivo, `floorMod` sempre devolve um valor de 0 a b − 1.

Isso derruba código que parece óbvio:

| Intenção | Errado para negativos | Certo |
|---|---|---|
| n é ímpar? | `n % 2 == 1` (−3 % 2 é −1) | `n % 2 != 0` ou `(n & 1) == 1` |
| Posição anterior num círculo de tamanho t | `(i - 1) % t` (dá −1 quando i é 0) | `Math.floorMod(i - 1, t)` |
| Posição de um hash num array | `hash % t` (hash pode ser negativo) | `Math.floorMod(hash, t)` |

Dois detalhes: dividir um inteiro por zero, com `/` ou `%`, lança `ArithmeticException`; e o `%` também funciona com `double` (`5.5 % 2` é `1.5`).

## Congruência

Dois inteiros são **congruentes módulo n** quando deixam o mesmo resto na divisão por n, ou seja, quando n divide a diferença:

```text
a ≡ b (mod n)   ⟺   n divide (a − b)
```

O relógio é o exemplo clássico: 10 h + 5 h = 15 h, e 15 ≡ 3 (mod 12). A propriedade que torna a aritmética modular útil é que ela **respeita soma e multiplicação**: se a ≡ b e c ≡ d (mod n), então a + c ≡ b + d e a · c ≡ b · d. Na prática, você pode reduzir módulo n **a cada passo**, e o resultado final é o mesmo:

```text
(a + b) mod n = ((a mod n) + (b mod n)) mod n
(a · b) mod n = ((a mod n) · (b mod n)) mod n
```

Isso resolve contas que seriam impossíveis de fazer diretamente. Qual é o último dígito de 7¹⁰⁰? O último dígito é o resto por 10, e as potências de 7 módulo 10 andam em ciclo: 7, 9, 3, 1, 7, 9, 3, 1... O ciclo tem tamanho 4 e 100 é múltiplo de 4, então 7¹⁰⁰ termina em **1**, sem calcular um número de 85 dígitos.

## O dia da semana

Numere os dias de 0 (domingo) a 6 (sábado). Andar k dias é somar k módulo 7. O dia 10/10/2026 cai num sábado (6):

```java executar
String[] dias = {"domingo", "segunda", "terça", "quarta", "quinta", "sexta", "sábado"};
int hoje = 6;
System.out.println(dias[(hoje + 100) % 7]);
System.out.println(dias[Math.floorMod(hoje - 100, 7)]);
System.out.println(DayOfWeek.SATURDAY.plus(100) + " " + DayOfWeek.SATURDAY.minus(100));
```

```saida
segunda
quinta
MONDAY THURSDAY
```

Daqui a 100 dias: 106 mod 7 = 1, segunda. Há 100 dias: (6 − 100) = −94, e aqui o `%` daria −3, um índice inválido. O `floorMod` dá 4: quinta. O `DayOfWeek` do Java faz exatamente essa conta por dentro.

## Dígitos verificadores: o CPF

Os dois últimos dígitos de um CPF são calculados a partir dos nove primeiros, com módulo 11. Para o primeiro dígito, multiplique os nove dígitos pelos pesos 10, 9, ..., 2, some, e tire o resto por 11. Se o resto for menor que 2, o dígito é 0; senão, é 11 − resto. Para o segundo, repita com os dez dígitos (os nove mais o primeiro verificador) e pesos de 11 a 2. Com o número fictício 123.456.789:

| Dígito | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9 | Soma |
|---|---|---|---|---|---|---|---|---|---|---|
| Peso | 10 | 9 | 8 | 7 | 6 | 5 | 4 | 3 | 2 | |
| Produto | 10 | 18 | 24 | 28 | 30 | 30 | 28 | 24 | 18 | 210 |

210 mod 11 = 1, menor que 2, então o primeiro dígito é 0. Fazendo a segunda rodada, sai 9: o CPF completo é 123.456.789-09.

Por que módulo 11 e pesos diferentes? Porque assim o dígito pega os erros de digitação mais comuns. Trocar um dígito d por d' muda a soma em p · (d − d'), e como 11 é primo e nem o peso nem a diferença são múltiplos de 11, o resto sempre muda. Inverter dois dígitos vizinhos a e b muda a soma em exatamente (a − b), que também não é múltiplo de 11. O dígito verificador muda junto com o resto, com uma única exceção: os restos 0 e 1 dão o mesmo dígito 0, então um erro que leve o resto de um para o outro passa despercebido. Números de cartão de crédito usam uma ideia parecida, o algoritmo de Luhn, com módulo 10.

## O algoritmo de Euclides

O **máximo divisor comum** de dois números aparece ao simplificar frações, calcular o mínimo múltiplo comum (mmc(a, b) = a · b ÷ mdc(a, b)) e em criptografia. O algoritmo mais antigo ainda em uso, de Euclides, cerca de 300 a.C., se apoia numa única observação: todo divisor comum de a e b também divide a mod b. Então:

```text
mdc(a, b) = mdc(b, a mod b),   e   mdc(a, 0) = a
```

Para mdc(252, 105):

| a | b | a mod b |
|---|---|---|
| 252 | 105 | 42 |
| 105 | 42 | 21 |
| 42 | 21 | 0 |
| 21 | 0 | fim: mdc = 21 |

```java executar
public class Euclides {
    static int mdc(int a, int b) {
        return b == 0 ? a : mdc(b, a % b);
    }

    public static void main(String[] args) {
        System.out.println(mdc(252, 105));
        System.out.println(4 * 6 / mdc(4, 6));
        int g = mdc(84, 126);
        System.out.println(84 / g + "/" + 126 / g);
    }
}
```

```saida
21
12
2/3
```

O número de passos cresce com o **logaritmo** dos números, não com o tamanho deles: o pior caso, demonstrado por Lamé em 1844, são dois números de Fibonacci consecutivos, e mesmo assim o número de divisões não passa de cinco vezes a quantidade de dígitos decimais do menor. Mdc de números com centenas de dígitos sai instantâneo. Para números enormes, o Java tem `BigInteger.gcd`.

## Exponenciação modular rápida

A criptografia de chave pública (RSA, Diffie-Hellman, que protegem o HTTPS) vive de contas como 7¹⁰⁰⁰⁰⁰⁰ mod m. Multiplicar 7 um milhão de vezes seria lento, e o número intermediário teria quase um milhão de dígitos. A saída é combinar duas ideias:

1. **Reduzir módulo m a cada multiplicação**, para os números ficarem pequenos.
2. **Elevar ao quadrado** em vez de multiplicar um a um. Como 13 = 1101 em binário, 7¹³ = 7⁸ · 7⁴ · 7¹: basta calcular 7, 7², 7⁴, 7⁸ (cada um é o quadrado do anterior) e multiplicar os que correspondem a bits 1.

```java executar
import java.math.BigInteger;

public class PotenciaModular {
    static long powMod(long base, long exp, long mod) {
        long resultado = 1;
        base %= mod;
        while (exp > 0) {
            if ((exp & 1) == 1) {
                resultado = resultado * base % mod;
            }
            base = base * base % mod;
            exp >>= 1;
        }
        return resultado;
    }

    public static void main(String[] args) {
        System.out.println(powMod(7, 100, 10));
        System.out.println(powMod(3, 200, 13));
        System.out.println(powMod(2, 30, 1_000_000_007));
        System.out.println(BigInteger.TWO.modPow(BigInteger.valueOf(30), BigInteger.valueOf(1_000_000_007)));
    }
}
```

```saida
1
9
73741817
73741817
```

O laço roda uma vez por bit do expoente: para um expoente de um milhão, são 20 voltas em vez de um milhão de multiplicações. É a ideia de "dividir pela metade" que vai aparecer no próximo episódio com o nome de O(log n). O `long` aguenta porque, com módulo menor que 2³¹, todo produto fica abaixo de 2⁶²; para módulos maiores, use `BigInteger.modPow`.

> [!DICA]
> Por baixo dos panos: dividir é a operação aritmética mais cara do processador. Uma soma leva um ciclo; uma divisão inteira leva de 10 a quase 100 ciclos, conforme o processador e o tamanho dos números. Por isso os compiladores trocam divisões por constantes por uma multiplicação e um deslocamento ("número mágico"), e o `HashMap` usa capacidades que são potências de 2: assim o índice é `hash & (capacidade - 1)`, uma operação de um ciclo, que ainda por cima nunca é negativa. Em complemento de dois, `x & (2ᵏ − 1)` é exatamente `Math.floorMod(x, 2ᵏ)`.

## Resumo

- Divisão euclidiana: a = q · b + r com 0 ≤ r < b
- Em Java, `/` arredonda para zero e `%` tem o sinal do dividendo; `(a / b) * b + a % b == a`
- `Math.floorMod` devolve sempre de 0 a b − 1 (com b positivo); use para índices circulares e hashes
- Para testar ímpar: `n % 2 != 0`, nunca `n % 2 == 1`
- Congruência respeita soma e produto: reduza módulo n a cada passo
- Dígitos verificadores (CPF, módulo 11) detectam um dígito errado e dois vizinhos trocados
- mdc(a, b) = mdc(b, a mod b), em tempo logarítmico
- Exponenciação modular por quadrados: uma volta por bit do expoente
