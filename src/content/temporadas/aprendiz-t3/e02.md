Em 2014, o vídeo "Gangnam Style" passou de 2.147.483.647 visualizações e o YouTube teve de trocar o contador para 64 bits. Em 2015, a FAA mandou reiniciar os geradores do Boeing 787 a cada poucos meses, porque um contador interno estourava depois de 248 dias ligado. Os dois casos são a mesma matemática: complemento de dois e overflow. Este episódio mostra por que os inteiros do computador formam um círculo, e não uma reta.

## Três tentativas de representar negativos

Com 4 bits existem 16 combinações. Como gastar metade delas com números negativos? Houve três ideias:

| Bits | Sem sinal | Sinal e magnitude | Complemento de um | Complemento de dois |
|---|---|---|---|---|
| `0000` | 0 | +0 | +0 | 0 |
| `0011` | 3 | +3 | +3 | 3 |
| `0111` | 7 | +7 | +7 | 7 |
| `1000` | 8 | −0 | −7 | −8 |
| `1011` | 11 | −3 | −4 | −5 |
| `1101` | 13 | −5 | −2 | −3 |
| `1111` | 15 | −7 | −0 | −1 |

> [!ANTES]
> As três representações existiram em máquinas reais. O IBM 7090, de 1959, usava sinal e magnitude; o CDC 6600, de 1964, e o UNIVAC 1100 usavam complemento de um, com o seu "zero negativo". O complemento de dois venceu com os minicomputadores dos anos 1960, como o PDP-8, e hoje é universal: o C++20 e o C23 passaram a exigi-lo, e o Java o fixou desde a primeira versão.

**Sinal e magnitude** usa o primeiro bit como sinal. É intuitivo, mas tem dois zeros e o somador comum dá resultado errado: 3 + (−3) vira `0011` + `1011` = `1110`, que seria −6. **Complemento de um** inverte todos os bits para negar, mas ainda tem dois zeros. O **complemento de dois** resolveu tudo: um zero só, e o mesmo circuito somador funciona para positivos e negativos, como você viu no [somador](/assistir/aprendiz-t1-e03).

## A definição: o bit mais alto vale negativo

Em complemento de dois com n bits, os pesos são as potências de 2 de sempre, exceto o bit mais alto, que vale **−2ⁿ⁻¹**:

```text
valor = −b₍ₙ₋₁₎·2ⁿ⁻¹ + b₍ₙ₋₂₎·2ⁿ⁻² + ... + b₁·2 + b₀
```

> [!PENSE]
> Se o bit mais alto vale −8, qual é o maior número que cabe em 4 bits? E o menor?

Com 4 bits, os pesos são −8, 4, 2 e 1. Então `1101` = −8 + 4 + 1 = −3, e `1000` = −8. O maior positivo é `0111` = 7.

Daí saem as faixas de todos os inteiros do Java:

| Tipo | Bits | Mínimo | Máximo |
|---|---|---|---|
| `byte` | 8 | −2⁷ = −128 | 2⁷ − 1 = 127 |
| `short` | 16 | −2¹⁵ = −32.768 | 2¹⁵ − 1 = 32.767 |
| `int` | 32 | −2³¹ = −2.147.483.648 | 2³¹ − 1 = 2.147.483.647 |
| `long` | 64 | −2⁶³ ≈ −9,2 × 10¹⁸ | 2⁶³ − 1 ≈ 9,2 × 10¹⁸ |

A faixa é **assimétrica**: há um negativo a mais, porque o zero ocupa uma das combinações "não negativas". Guarde isso, vai voltar.

## Por que inverter e somar 1 funciona

A regra prática para negar é: inverta todos os bits e some 1. A prova cabe em duas linhas. Somando x com ~x (x com os bits invertidos), cada coluna tem exatamente um bit 1, então não há vai-um:

```text
x + ~x = 111...1   (n uns)
```

E n uns, em complemento de dois, valem −2ⁿ⁻¹ + (2ⁿ⁻¹ − 1) = −1. Logo x + ~x = −1, e isolando: **−x = ~x + 1**. Em Java, `~5` é −6 e `~(-1)` é 0.

## O relógio de 2ⁿ posições

A melhor imagem para inteiros de computador é um relógio. Com 3 bits há 8 posições:

```text
              000 = 0
     111 = -1           001 = 1
  110 = -2                 010 = 2
     101 = -3           011 = 3
              100 = -4
```

![Os 8 valores de 3 bits num relógio: de 0 a 3 no sentido horário, e depois de 3 vem −4, seguido de −3, −2 e −1](/figuras/relogio-de-inteiros.svg "Inteiros de computador formam um círculo: depois do maior vem o menor.")

Somar 1 anda uma posição no sentido horário. De 3 (`011`) para 4 seria `100`, que já é −4: é o **overflow**, a passagem do maior positivo para o menor negativo. Formalmente, a aritmética de inteiros com n bits é a aritmética **módulo 2ⁿ**: o resultado verdadeiro é reduzido para caber na faixa, somando ou subtraindo 2ⁿ quantas vezes for preciso. O episódio de [aritmética modular](/assistir/aprendiz-t3-e04) explora essa ideia.

## Overflow em Java

A especificação do Java é explícita: as operações com inteiros **não avisam** quando estouram (JLS 4.2.2). O resultado simplesmente dá a volta no relógio:

```java executar
public class Overflow {
    public static void main(String[] args) {
        int max = Integer.MAX_VALUE;
        System.out.println(max + 1);
        System.out.println(Math.abs(Integer.MIN_VALUE)); //> O positivo correspondente não cabe num int.
        System.out.println(-Integer.MIN_VALUE == Integer.MIN_VALUE);
        System.out.println(Integer.MIN_VALUE / -1);
        long certo = max + 1L;
        System.out.println(certo);
    }
}
```

```saida
-2147483648
-2147483648
true
-2147483648
2147483648
```

As linhas 2 a 4 são a assimetria da faixa: +2.147.483.648 não cabe num `int`, então negar o mínimo dá ele mesmo, e `Math.abs` devolve um número **negativo**. Em C, `INT_MIN / -1` é comportamento indefinido e costuma derrubar o programa; em Java o resultado é definido.

> [!CONVERSA]
> **Math.abs:** Me dê um número e eu devolvo o valor absoluto. Sempre positivo.
>
> **Integer.MIN_VALUE:** Sempre? Tente comigo: −2.147.483.648.
>
> **Math.abs:** Seria +2.147.483.648... que não cabe num `int`. Dou a volta e devolvo você mesmo.
>
> **Integer.MIN_VALUE:** Por isso a documentação avisa: para mim, o resultado é negativo. Quem usa você para calcular índices de array costuma descobrir isso em produção.

O overflow mais traiçoeiro é o que acontece **antes** da atribuição:

```java executar
long microsPorDia = 24 * 60 * 60 * 1000 * 1000;
long certo = 24L * 60 * 60 * 1000 * 1000; //> O L faz a conta inteira ser feita em 64 bits.
System.out.println(microsPorDia);
System.out.println(certo);
```

```saida
500654080
86400000000
```

A variável é `long`, mas a conta da direita é toda feita em `int`, e só o resultado (já estourado) é convertido. Dá para prever o valor errado: 86.400.000.000 mod 2³² = 86.400.000.000 − 20 × 4.294.967.296 = 500.654.080. Basta um `L` no primeiro número para a conta inteira ser feita em `long`.

## Detectando overflow

> [!ERRO]
> Calcular o balde de uma tabela hash com `Math.abs(chave.hashCode()) % n`. Para a raríssima chave cujo `hashCode` é `Integer.MIN_VALUE` (a String `"polygenelubricants"` é uma delas), o `abs` devolve um negativo, o resto também sai negativo e o acesso ao array lança `ArrayIndexOutOfBoundsException`. Use `Math.floorMod(chave.hashCode(), n)`, que sempre devolve um valor de 0 a n − 1.

Uma soma só pode estourar quando os dois números têm o **mesmo sinal**, e aí o resultado sai com o sinal **trocado**. Positivo com negativo nunca estoura. Essa regra vira uma expressão de bits: o sinal de `a ^ r` é negativo quando `a` e o resultado `r` têm sinais diferentes.

```java executar
public class Detecta {
    static boolean estourou(int a, int b) {
        int r = a + b;
        return ((a ^ r) & (b ^ r)) < 0;
    }

    public static void main(String[] args) {
        System.out.println(estourou(2_000_000_000, 2_000_000_000));
        System.out.println(estourou(-5, 3));
        try {
            Math.addExact(2_000_000_000, 2_000_000_000);
        } catch (ArithmeticException e) {
            System.out.println(e.getMessage());
        }
    }
}
```

```saida
true
false
integer overflow
```

Esse teste é, linha por linha, o código do `Math.addExact` no JDK. Na prática, use os métodos prontos: `Math.addExact`, `subtractExact`, `multiplyExact`, `negateExact` e `toIntExact` lançam `ArithmeticException` em vez de dar a volta. Para números sem limite, use `BigInteger`.

> [!DICA]
> Por baixo dos panos, o processador já detecta overflow em toda soma: a ALU liga o flag **OF** (overflow, para números com sinal) e o flag **CF** (carry, para números sem sinal). É o mesmo circuito; só muda a interpretação. A JVM HotSpot transforma o `Math.addExact` numa instrução de soma seguida de um salto condicional nesse flag (`jo`, *jump if overflow*), então a verificação custa quase nada.

## O bug da busca binária

Em 2006, Joshua Bloch contou que a busca binária do próprio JDK tinha um bug havia nove anos. A linha era esta:

```java
int meio = (inicio + fim) / 2;
```

Com arrays de mais de um bilhão de posições, `inicio + fim` passa de 2³¹ − 1 e o meio fica negativo:

```java executar
int inicio = 1_500_000_000;
int fim = 2_000_000_000;
System.out.println((inicio + fim) / 2);
System.out.println(inicio + (fim - inicio) / 2);
System.out.println((inicio + fim) >>> 1);
```

```saida
-397483648
1750000000
1750000000
```

As duas correções funcionam por motivos diferentes. `inicio + (fim - inicio) / 2` nunca passa de `fim`. Já `(inicio + fim) >>> 1` deixa a soma estourar, mas o deslocamento sem sinal reinterpreta os 32 bits como um número positivo de 0 a 2³² − 1 antes de dividir por 2. A segunda é a que está no JDK hoje.

## Estreitar e estender

Converter para um tipo menor (*narrowing*) simplesmente **descarta os bits de cima** (JLS 5.1.3). E converter um negativo para um tipo maior copia o bit de sinal para a esquerda: é a **extensão de sinal**.

```java executar
byte b = (byte) 200;
System.out.println(b);
System.out.println(b & 0xFF);
System.out.println(Byte.toUnsignedInt(b));
System.out.println(Integer.toHexString(b));
```

```saida
-56
200
200
ffffffc8
```

200 é `1100 1000`. Num `byte`, o bit de cima vale −128: −128 + 64 + 8 = −56. Na última linha, o `byte` foi promovido a `int` com extensão de sinal: os 24 bits novos viraram 1 (`ff ff ff`). Quem lê bytes de arquivo ou de rede usa `b & 0xFF` o tempo todo, para tratar o byte como um número de 0 a 255.

## Deslocamentos: `>>` e `>>>`

`>>` é o deslocamento **aritmético**: preenche a esquerda com cópias do bit de sinal, então preserva o sinal. `>>>` é o **lógico**: preenche com zeros.

```java executar
System.out.println(-16 >> 2);
System.out.println(-16 >>> 28);
System.out.println(-7 >> 1);
System.out.println(-7 / 2);
```

```saida
-4
15
-4
-3
```

`x >> k` divide por 2ᵏ arredondando para **baixo** (em direção a −∞), enquanto `/` arredonda em direção a **zero**. Para positivos dá no mesmo; para negativos, não: −7 >> 1 é −4, e −7 / 2 é −3.

## Sem sinal em Java

O Java não tem `unsigned int`; o único tipo sem sinal é o `char`, de 16 bits. Quando precisa tratar um `int` como sem sinal (um checksum, um endereço IP, um hash), use os métodos da classe `Integer`: `toUnsignedString`, `compareUnsigned`, `divideUnsigned` e `remainderUnsigned`. Por exemplo, `Integer.toUnsignedString(-1)` é `"4294967295"`: os mesmos 32 bits uns, lidos de outro jeito.

## A matemática dos casos reais

Saber o tamanho do relógio permite prever quando um sistema vai quebrar:

| Caso | Contador | Conta | Estoura em |
|---|---|---|---|
| Boeing 787 (2015) | centésimos de segundo num `int` | 2³¹ ÷ 100 ÷ 86.400 | 248,5 dias |
| Problema do ano 2038 | segundos desde 1970 num inteiro de 32 bits | 2³¹ ÷ 31.556.952 | 68 anos: 19/01/2038 |
| Milissegundos num `int` | `System.currentTimeMillis()` guardado errado | 2³¹ ÷ 1000 ÷ 86.400 | 24,8 dias |
| Gangnam Style (2014) | visualizações num `int` | 2³¹ − 1 | 2.147.483.647 views |

> [!MATEMATICA]
> A conta do Boeing, passo a passo: o maior `int` é 2³¹ − 1 = 2.147.483.647 centésimos de segundo. Dividindo por 100, são 21.474.836 segundos; por 86.400 segundos num dia, 248,55 dias. No 249º dia ligado, o contador dá a volta e fica negativo. A mesma conta com `long`: 2⁶³ centésimos são cerca de 2,9 bilhões de anos.

Por isso o Java usa `long` para tempo (`currentTimeMillis`, `nanoTime`, `Instant`): 2⁶³ milissegundos dão quase 300 milhões de anos.

> [!PERGUNTAS]
> **P:** Se o overflow é tão perigoso, por que o Java não lança exceção sempre?
>
> **R:** Por desempenho e por compatibilidade com o hardware: a soma "que dá a volta" é uma instrução só, e muitos algoritmos dependem dela, como cálculos de hash e de checksum. Quem precisa de verificação usa `Math.addExact` e parentes, que custam quase nada; quem precisa de números ilimitados usa `BigInteger`.

> [!IA]
> Código de IA costuma usar `int` para tempos em milissegundos, contadores de visualizações e IDs que crescem, e escreve `(a + b) / 2` para o meio da busca binária. Ao revisar, procure contas com números grandes feitas em `int` e pergunte: quanto esse valor pode crescer em um ano? Se passar de 2,1 bilhões, é `long`.

## Na IDE

- **Ver os bits.** No depurador, *View as*, *Binary* mostra os 32 bits de um `int`; um negativo aparece com o bit de sinal e os 1 à esquerda.
- **Estouro em constantes.** A inspeção "Numeric overflow" sublinha `24 * 60 * 60 * 1000 * 1000` e avisa que a conta estoura em `int`.
- **Contas rápidas.** **Alt + F8** avalia `Integer.toBinaryString(-5)` ou `(byte) 200` sem escrever um programa.

## Resumo

- Complemento de dois: o bit mais alto vale −2ⁿ⁻¹; faixa de −2ⁿ⁻¹ a 2ⁿ⁻¹ − 1
- Um zero só e um negativo a mais: `Math.abs(Integer.MIN_VALUE)` é negativo
- −x = ~x + 1, porque x + ~x = −1
- Inteiros de n bits são aritmética módulo 2ⁿ: o overflow dá a volta, sem aviso
- Conta com `int` estoura antes de virar `long`: use `24L * ...`
- Soma estoura só com sinais iguais e resultado de sinal trocado; use `Math.addExact`
- O meio da busca binária é `inicio + (fim - inicio) / 2` ou `(inicio + fim) >>> 1`
- Estreitar descarta os bits de cima; estender copia o sinal; `b & 0xFF` lê o byte sem sinal
- `>>` mantém o sinal e arredonda para baixo; `>>>` preenche com zeros
