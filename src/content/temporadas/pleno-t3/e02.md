Um `Set` é uma coleção **sem repetidos**: o mesmo elemento não entra duas vezes. Saber o que conta como "o mesmo" é o centro deste episódio, porque cada implementação decide isso de um jeito: `HashSet` e `LinkedHashSet` usam `hashCode` e `equals`; `TreeSet` usa a comparação.

> [!ANTES]
> O Java 1.0 não tinha `Set`: o jeito era usar as chaves de um `Hashtable`, com um valor qualquer. É o que o `HashSet` faz por dentro até hoje, como você vai ver no fim da aula. O `Set` chegou com o Collections Framework, no Java 1.2; o `LinkedHashSet`, no 1.4; e o `NavigableSet`, com `floor` e `ceiling`, no Java 6. Antes dele, o `TreeSet` só oferecia as visões `headSet`, `tailSet` e `subSet` do `SortedSet`.

## O contrato de Set

`Set` não acrescenta métodos a `Collection`; muda o significado deles. `add` devolve `true` se o elemento entrou e `false` se ele já estava lá. Não há índice, então não existem `get(i)` nem `set(i, e)`. As três implementações principais diferem na ordem de iteração:

| Implementação | Ordem | Base | `null` |
|---|---|---|---|
| `HashSet` | Nenhuma garantida | Tabela hash | Aceita um |
| `LinkedHashSet` | De inserção | Tabela hash mais lista ligada | Aceita um |
| `TreeSet` | Ordenada | Árvore rubro-negra | `NullPointerException` |

```java executar
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Set;
import java.util.TreeSet;

public class Conjuntos {
    public static void main(String[] args) {
        Set<String> frutas = new LinkedHashSet<>();
        System.out.println(frutas.add("uva") + " " + frutas.add("uva")); //> O segundo add devolve false.
        frutas.addAll(List.of("banana", "maçã", "banana"));
        System.out.println(frutas);

        Set<Integer> a = new TreeSet<>(List.of(4, 1, 3, 2));
        Set<Integer> b = Set.of(3, 4, 5);
        Set<Integer> uniao = new TreeSet<>(a);
        uniao.addAll(b);
        Set<Integer> intersecao = new TreeSet<>(a);
        intersecao.retainAll(b);
        Set<Integer> diferenca = new TreeSet<>(a);
        diferenca.removeAll(b);
        System.out.println(a + " " + uniao + " " + intersecao + " " + diferenca);
    }
}
```

```saida
true false
[uva, banana, maçã]
[1, 2, 3, 4] [1, 2, 3, 4, 5] [3, 4] [1, 2]
```

`addAll`, `retainAll` e `removeAll` fazem união, interseção e diferença, alterando o conjunto que recebe a chamada. Por isso as operações começam de cópias.

Os exemplos imprimem só `LinkedHashSet` e `TreeSet`. A ordem de um `HashSet` depende dos códigos hash e do tamanho da tabela; código que depende dela quebra sem aviso.

## HashSet: hashCode e equals

Para saber se um elemento já está lá, o `HashSet` calcula o `hashCode` dele, vai direto ao compartimento correspondente e só ali compara com `equals`. Duas consequências que caem na prova, já vistas na [temporada de herança](/assistir/junior-t3-e06):

- Uma classe que sobrescreve `equals` sem sobrescrever `hashCode` deixa entrar "iguais" repetidos, porque cada um cai num compartimento diferente
- Alterar um campo usado no `hashCode` **depois** de inserir o objeto o perde dentro do conjunto

```java executar
import java.util.HashSet;
import java.util.Objects;
import java.util.Set;

public class ChaveMutavel {
    static class Ponto {
        int x;
        int y;

        Ponto(int x, int y) {
            this.x = x;
            this.y = y;
        }

        @Override
        public boolean equals(Object o) {
            return o instanceof Ponto p && p.x == x && p.y == y;
        }

        @Override
        public int hashCode() {
            return Objects.hash(x, y);
        }
    }

    public static void main(String[] args) {
        Set<Ponto> pontos = new HashSet<>();
        Ponto p = new Ponto(1, 2);
        pontos.add(p);
        System.out.println(pontos.contains(new Ponto(1, 2)));
        p.x = 9; //> Muda o hash: o elemento fica no compartimento antigo.
        System.out.println(pontos.contains(p) + " " + pontos.contains(new Ponto(1, 2)) + " " + pontos.size());
    }
}
```

```saida
true
false false 1
```

> [!PENSE]
> O ponto continua no conjunto: `size()` diz 1. Por que `contains` não o encontra, nem pelo objeto alterado nem por um ponto com os valores antigos?

O objeto continua lá dentro, contado em `size()`, mas guardado no compartimento do hash antigo. Procurando por ele, o conjunto olha o compartimento do hash novo e não o encontra; procurando pelo valor antigo, acha o compartimento certo, mas `equals` falha. Por isso elementos de `Set` e chaves de `Map` devem ser imutáveis, como `String`, `Integer` e records.

![Uma tabela de 16 compartimentos; o Ponto de 1 e 2, com hashCode 994, fica no compartimento 2; depois de x virar 9, o hashCode 1242 aponta para o compartimento 10, vazio, onde o contains procura](/figuras/hashset-por-dentro.svg "O hash escolhe o compartimento; o equals só compara quem está lá dentro.")

> [!PREVENCAO]
> Use records com campos imutáveis como elementos de `Set` e chaves de `Map`: `equals` e `hashCode` vêm gerados com os mesmos campos, e nada muda depois da inserção. Cuidado com um record que guarda uma `List` mutável: o `hashCode` dele muda junto com a lista, e o problema volta.

## TreeSet e NavigableSet

O `TreeSet` mantém os elementos ordenados, pela ordem natural (`Comparable`) ou por um `Comparator` passado ao construtor. Ele implementa `NavigableSet`, com métodos de busca por proximidade que a prova cobra com números:

| Método | Devolve |
|---|---|
| `first()` / `last()` | O menor e o maior |
| `floor(x)` / `ceiling(x)` | O maior `<= x` e o menor `>= x` |
| `lower(x)` / `higher(x)` | O maior `< x` e o menor `> x` |
| `headSet(x)` / `tailSet(x)` | Os `< x` e os `>= x` |
| `subSet(a, b)` | De `a` (inclusive) até `b` (exclusive) |
| `pollFirst()` / `pollLast()` | Remove e devolve o menor e o maior |
| `descendingSet()` | Uma visão em ordem inversa |

Os métodos de busca devolvem `null` quando não há resposta. `headSet`, `tailSet` e `subSet` devolvem **visões**: alterações nelas aparecem no conjunto original, dentro da faixa.

```java executar
import java.util.List;
import java.util.TreeSet;

public class Navegando {
    public static void main(String[] args) {
        TreeSet<Integer> t = new TreeSet<>(List.of(10, 5, 20, 15));
        System.out.println(t.first() + " " + t.last());
        System.out.println(t.floor(12) + " " + t.ceiling(12) + " " + t.lower(10) + " " + t.higher(20)); //> floor e ceiling incluem o valor; lower e higher, não.
        System.out.println(t.headSet(15) + " " + t.tailSet(15) + " " + t.subSet(5, 20));
        System.out.println(t.headSet(15, true) + " " + t.descendingSet());
        System.out.println(t.pollFirst() + " " + t);
    }
}
```

```saida
5 20
10 15 5 null
[5, 10] [15, 20] [5, 10, 15]
[5, 10, 15] [20, 15, 10, 5]
5 [10, 15, 20]
```

> [!LAPIS]
> Com `t = [3, 6, 9, 12]`, quanto vale cada chamada? `floor(7)`, `ceiling(7)`, `lower(3)`, `higher(12)`, `headSet(9)` e `tailSet(9)`.
>
> **Resposta:** `6`, `9`, `null`, `null`, `[3, 6]` e `[9, 12]`. `floor` e `ceiling` aceitam o próprio valor; `lower` e `higher` não, e devolvem `null` quando não há vizinho; `headSet` exclui o limite, e `tailSet` o inclui.

> [!ATENCAO]
> O `TreeSet` decide igualdade pela comparação, não por `equals`. Com `String.CASE_INSENSITIVE_ORDER`, "a" e "A" comparam como iguais, e só o primeiro entra. E guardar um objeto que não é `Comparable`, sem `Comparator`, lança `ClassCastException` já no primeiro `add`.

## Set.of e Set.copyOf

`Set.of` cria um conjunto imutável e é mais rígido que `List.of`: além de rejeitar `null`, lança `IllegalArgumentException` se receber **repetidos**. `Set.copyOf` aceita uma coleção com repetidos e simplesmente os descarta.

```java executar
import java.util.List;
import java.util.Set;

public class Fabricas {
    public static void main(String[] args) {
        try {
            Set.of("a", "b", "a");
        } catch (IllegalArgumentException e) {
            System.out.println(e.getMessage());
        }
        System.out.println(Set.copyOf(List.of("a", "a", "b")).size());
        System.out.println(Set.of(1, 2).equals(Set.of(2, 1)));
    }
}
```

```saida
duplicate element: a
2
true
```

O `equals` de conjuntos ignora a ordem: dois `Set` são iguais quando têm os mesmos elementos.

> [!CONVERSA]
> **HashSet:** Eu acho qualquer elemento em tempo constante: calculo o hash e vou direto ao compartimento.
>
> **TreeSet:** E eu devolvo tudo em ordem, e ainda respondo quem é o maior elemento abaixo de 12.
>
> **HashSet:** Ordem custa caro: cada busca sua desce a árvore, em O(log n).
>
> **TreeSet:** E você depende de `hashCode` e `equals` bem escritos. Eu só preciso de uma comparação.
>
> **HashSet:** Que, se disser que dois elementos diferentes são iguais, faz você perder um deles sem avisar ninguém.

> [!PROVA]
> Três regras que derrubam muita gente: `add` repetido devolve `false`, sem exceção; `Set.of` com repetidos lança `IllegalArgumentException`; `TreeSet.add(null)` lança `NullPointerException`, enquanto `HashSet` aceita um `null`.

> [!IA]
> Ao gerar `equals` e `hashCode`, assistentes de IA às vezes usam campos diferentes nos dois métodos, ou incluem campos mutáveis, e o `Set` passa a guardar repetidos ou a perder elementos. Peça um record quando a classe é só dados, e confira com um teste: dois objetos iguais num `HashSet` precisam dar `size()` igual a 1.

## Na IDE

- **Gerar os dois juntos.** `Alt+Insert` > *equals() and hashCode()* gera os dois métodos com os mesmos campos, escolhidos numa única tela.
- **Par incompleto.** A inspeção *'equals()' and 'hashCode()' not paired* marca a classe que sobrescreve um sem o outro.
- **Ver os compartimentos.** No depurador, com *View as > Object* num `HashSet`, abra `map` e depois `table` para ver em que posição cada elemento caiu.

## Por baixo dos panos

O `HashSet` é um `HashMap` disfarçado. Cada elemento vira uma **chave** de um `HashMap` interno, com um mesmo objeto de enfeite, `PRESENT`, como valor. O `add` é um `put` que confere se a chave já existia. Da mesma forma, o `TreeSet` guarda os elementos como chaves de um `TreeMap`, e o `LinkedHashSet` usa um `LinkedHashMap`. Entender o mapa, assunto do [próximo episódio](/assistir/pleno-t3-e03), é entender os conjuntos.

O `TreeMap` por trás do `TreeSet` é uma **árvore rubro-negra**: uma árvore binária de busca que pinta cada nó de vermelho ou preto e segue regras que mantêm a altura em O(log n), girando nós a cada inserção ou remoção. É uma versão balanceada da árvore de busca vista em [árvores e tabelas hash](/assistir/aprendiz-t4-e05), agora pronta na biblioteca. Por isso `add`, `contains` e `floor` custam O(log n) no `TreeSet`, contra O(1) em média no `HashSet`.

> [!MATEMATICA]
> O que O(log n) significa na prática: com 1 milhão de elementos, log₂ de 1.000.000 é quase 20, e uma árvore rubro-negra tem altura de no máximo 2 · log₂(n + 1), uns 40 níveis. Uma busca no `TreeSet` faz de 20 a 40 chamadas a `compareTo`. No `HashSet`, a mesma busca faz um `hashCode` e, em média, um `equals`. Com 1 bilhão de elementos, a árvore passaria a uns 30 a 60 níveis: o custo cresce devagar, mas cresce.

## Resumo para a prova

- `Set` não tem repetidos; `add` repetido devolve `false`
- `HashSet` sem ordem, `LinkedHashSet` na ordem de inserção, `TreeSet` ordenado
- `HashSet` usa `hashCode` e `equals`; `TreeSet` usa `compareTo` ou o `Comparator`
- Mudar um campo do `hashCode` depois de inserir perde o elemento
- `floor`/`ceiling` incluem o valor; `lower`/`higher` não; `headSet(x)` exclui `x`, `tailSet(x)` inclui
- `Set.of` rejeita `null` e repetidos; `Set.copyOf` descarta repetidos
