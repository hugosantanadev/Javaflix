Coleções imutáveis evitam uma família inteira de bugs: ninguém altera por engano a lista que você devolveu, threads podem compartilhá-las sem travas e elas podem servir de chave sem medo. Mas o Java tem três níveis de "não pode mudar", e confundi-los é uma armadilha clássica. Este episódio fecha a temporada com eles e com os utilitários da classe `Collections`.

## Inalterável não é imutável

| Forma | O que é | Mudanças na origem aparecem? |
|---|---|---|
| `Collections.unmodifiableList(l)` | Uma **visão** somente leitura de `l` | Sim |
| `List.copyOf(l)` | Uma **cópia** imutável | Não |
| `List.of(...)` | Uma lista imutável nova | Não há origem |

As três recusam alterações com `UnsupportedOperationException`. A diferença está no que acontece **depois**: quem guardou uma visão inalterável continua vendo cada mudança feita pela referência original.

```java executar
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public class Niveis {
    public static void main(String[] args) {
        List<String> base = new ArrayList<>(List.of("a", "b"));
        List<String> visao = Collections.unmodifiableList(base);
        List<String> copia = List.copyOf(base);
        base.add("c");
        System.out.println(visao + " " + copia);
        try {
            visao.add("d");
        } catch (UnsupportedOperationException e) {
            System.out.println("a visão não aceita alterações");
        }

        List<StringBuilder> textos = List.of(new StringBuilder("x"));
        textos.get(0).append("y");
        System.out.println(textos);
    }
}
```

```saida
[a, b, c] [a, b]
a visão não aceita alterações
[xy]
```

A última linha mostra o outro limite: a lista imutável impede trocar, acrescentar e remover **elementos**, mas não protege o **estado** de cada elemento. Uma lista imutável de objetos mutáveis não é totalmente imutável. Para isso, os elementos também precisam ser, como `String`, `Integer` e records com componentes imutáveis.

## Cópias defensivas

Um record ou uma classe que recebe uma lista deveria copiá-la, para que quem a criou não possa alterá-la depois por fora. O construtor compacto é o lugar natural, como no [episódio de records](/assistir/junior-t5-e02):

```java executar
import java.util.ArrayList;
import java.util.List;

public class Defensiva {
    record Turma(String nome, List<String> alunos) {
        Turma {
            alunos = List.copyOf(alunos);
        }
    }

    public static void main(String[] args) {
        List<String> nomes = new ArrayList<>(List.of("Ana"));
        Turma t = new Turma("A", nomes);
        nomes.add("Bia");
        System.out.println(t.alunos());
        try {
            t.alunos().add("Caio");
        } catch (UnsupportedOperationException e) {
            System.out.println("a turma é imutável");
        }
    }
}
```

```saida
[Ana]
a turma é imutável
```

`List.copyOf` resolve as duas direções: a turma não vê as mudanças de quem a criou, e quem lê a turma não consegue alterá-la. Como `List.of`, ele rejeita `null` com `NullPointerException`.

## A classe Collections

`Collections` (com "s") é uma classe utilitária, cheia de métodos estáticos que operam sobre coleções:

| Método | O que faz |
|---|---|
| `sort`, `binarySearch` | Ordena e busca, como no [episódio 5](/assistir/pleno-t3-e05) |
| `reverse`, `shuffle`, `swap`, `rotate` | Reorganizam uma lista no lugar |
| `max`, `min`, `frequency` | Maior, menor e quantas vezes um valor aparece |
| `nCopies(n, x)` | Lista imutável com `x` repetido `n` vezes |
| `fill(lista, x)` | Troca todos os elementos por `x` |
| `addAll(colecao, a, b, ...)` | Acrescenta vários valores de uma vez |
| `disjoint(a, b)` | `true` se não há elemento em comum |
| `emptyList()`, `singletonList(x)` | Listas imutáveis vazia e de um elemento |
| `unmodifiableX`, `synchronizedX`, `checkedX` | Embrulham uma coleção existente |

```java executar
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public class Utilitarios {
    public static void main(String[] args) {
        List<Integer> l = new ArrayList<>(List.of(3, 1, 4, 1, 5, 9, 2));
        System.out.println(Collections.max(l) + " " + Collections.min(l) + " " + Collections.frequency(l, 1));
        Collections.reverse(l);
        System.out.println(l);
        Collections.swap(l, 0, 6);
        System.out.println(l);
        Collections.rotate(l, 2);
        System.out.println(l);
        System.out.println(String.join("", Collections.nCopies(3, "ab")));
        System.out.println(Collections.disjoint(List.of(1, 2), List.of(3, 4)));
    }
}
```

```saida
9 1 2
[2, 9, 5, 1, 4, 1, 3]
[3, 9, 5, 1, 4, 1, 2]
[1, 2, 3, 9, 5, 1, 4]
ababab
true
```

`rotate(l, 2)` desloca cada elemento duas posições para a frente, e os dois últimos dão a volta para o começo.

## Arrays e coleções

Para sair de uma coleção para um array, `toArray()` sem argumentos devolve um `Object[]`; para um array tipado, passe um array do tipo (`toArray(new String[0])`) ou, desde o Java 11, um gerador (`toArray(String[]::new)`). No sentido contrário, `Arrays.asList` dá uma visão e `List.of(array)` uma cópia imutável, como no [primeiro episódio](/assistir/pleno-t3-e01).

> [!PROVA]
> Toda alteração numa coleção de `List.of`, `Set.of`, `Map.of`, `copyOf`, `unmodifiableX`, `nCopies`, `emptyList` ou `singletonList` lança `UnsupportedOperationException`, inclusive `sort` e o `remove` do iterador. A visão de `unmodifiableX` reflete as mudanças da original; `copyOf` não. E `toArray()` sem argumentos devolve `Object[]`.

## Por baixo dos panos

`List.of` não devolve um `ArrayList` travado. Ele devolve classes internas de `java.util.ImmutableCollections`, escolhidas pelo tamanho: `List12` guarda um ou dois elementos em campos, sem array, e `ListN` guarda um array exatamente do tamanho necessário. Por não precisarem de espaço para crescer nem de contador de modificações, são mais compactas que um `ArrayList`. E, como a documentação avisa, `List.copyOf` de uma lista que já é imutável em geral devolve a própria lista, sem copiar.

`Set.of` e `Map.of` guardam um detalhe proposital: a ordem de iteração **muda entre execuções** do programa. Rodando quatro vezes o mesmo `System.out.println(Set.of("a", "b", "c", "d", "e"))`:

```text
[e, d, c, b, a]
[e, a, b, c, d]
[e, d, c, b, a]
[a, b, c, d, e]
```

As classes usam um valor aleatório, `SALT`, sorteado quando a JVM inicia, para escolher onde cada elemento fica. É uma vacina: código que dependesse por acaso da ordem de um conjunto quebraria logo nos testes, em vez de anos depois numa atualização do JDK. Por isso nenhuma questão desta temporada imprime um `Set.of` ou um `HashSet` direto.

As coleções de `Collections.unmodifiableList` e companhia seguem outro desenho: são o padrão *decorator*, um objeto que embrulha a coleção original e repassa as leituras a ela, lançando exceção nas escritas. É por isso que elas veem as mudanças da original, e é por isso que embrulhar uma coleção já embrulhada só acrescenta uma camada.

## Resumo para a prova

- `unmodifiableX` é uma visão somente leitura; `copyOf` é uma cópia imutável; `of` cria do zero
- Imutável é a coleção, não necessariamente os elementos
- Cópias defensivas com `List.copyOf` no construtor compacto de records
- `Collections`: `reverse`, `swap`, `rotate`, `max`, `min`, `frequency`, `nCopies`, `fill`, `disjoint`
- `toArray()` devolve `Object[]`; `toArray(new String[0])` e `toArray(String[]::new)` devolvem `String[]`
- A ordem de `Set.of` e `Map.of` muda entre execuções, de propósito
