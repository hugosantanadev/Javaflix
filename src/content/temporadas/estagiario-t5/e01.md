`String` é provavelmente a classe mais usada do Java, e a mais cobrada na prova. Ela tem uma característica que explica metade das pegadinhas: é **imutável**. Nenhum método muda uma `String` existente; todos devolvem uma nova. Este episódio mostra o que isso significa na prática, por que a linguagem foi desenhada assim e como uma `String` é guardada na memória.

## Uma `String` é um objeto

`String` é uma classe do pacote `java.lang` (importado automaticamente), mas tem dois privilégios que nenhuma outra classe tem: **literais** entre aspas (`"Javaflix"`) e o operador **`+`** para concatenar. Uma variável `String` guarda uma **referência** para o objeto, e pode guardar `null`.

O tamanho vem de `length()` (um método, ao contrário do `length` dos arrays), e cada caractere de `charAt(i)`, com índices a partir de 0:

```java executar
String nome = "Javaflix";
System.out.println(nome.length());
System.out.println(nome.charAt(0) + "" + nome.charAt(nome.length() - 1)); //> O "" vira tudo em texto: char + char seria uma soma.
try {
    nome.charAt(8);
} catch (StringIndexOutOfBoundsException e) {
    System.out.println("fora do limite");
}
```

```saida
8
Jx
fora do limite
```

O último índice válido é `length() - 1`. O `+ ""` entre os dois `charAt` está ali porque `char + char` é soma de números, como você viu nos [operadores](/assistir/estagiario-t2-e01).

## Imutável: os métodos devolvem uma nova `String`

Nenhum método de `String` altera o objeto. `toUpperCase()`, `concat()`, `replace()`, `trim()` e todos os outros **devolvem uma `String` nova** e deixam a original como estava. Chamar o método e ignorar o resultado não faz nada:

```java executar
String s = "java";
s.toUpperCase(); //> Devolve "JAVA", mas ninguém guarda: s continua "java".
System.out.println(s);
String t = s.toUpperCase();
System.out.println(s + " " + t);
s = s + "flix"; //> Objeto novo; a variável passa a apontar para ele.
System.out.println(s);
```

```saida
java
java JAVA
javaflix
```

Na última atribuição, o que muda é a **variável**: ela passa a apontar para um objeto novo, `"javaflix"`. O objeto `"java"` continua intacto. Por isso duas variáveis que apontavam para a mesma `String` não se afetam.

> [!PENSE]
> No trecho abaixo, `a` e `b` apontam para o mesmo objeto, e depois `a` "muda". O `b` vê a mudança?


```java executar
String a = "café";
String b = a;
a = a + " com leite";
System.out.println(a);
System.out.println(b);
```

```saida
café com leite
café
```

O objeto antigo não é tocado, e b continua apontando para ele.")

> [!PROVA]
> Procure chamadas de método de `String` cujo resultado é jogado fora: `s.trim();`, `s.replace("a", "b");`, `s.concat("x");` sozinhos numa linha não mudam `s`. A pegadinha aparece em quase toda prova.

> [!ERRO]
> Chamar um método de `String` esperando que ele altere a variável: `nome.trim();` e depois gravar `nome` no banco com os espaços. Sempre guarde o resultado, `nome = nome.trim();`, ou use-o direto na expressão seguinte.

> [!LAPIS]
> Qual é a saída?
>
> ```java
> String s = "  Java  ";
> s.trim();
> s = s.toUpperCase();
> System.out.println("[" + s + "]");
> ```
>
> **Resposta:** `[  JAVA  ]`. O `trim()` devolveu uma `String` sem espaços que ninguém guardou. O `toUpperCase()`, sim, foi guardado em `s`, e por isso só as letras mudaram.

## Vazia, em branco e nula

São três coisas diferentes. `""` é uma `String` de tamanho 0. `"   "` tem tamanho 3, mas só espaços. E `null` não é `String` nenhuma: chamar um método nela lança `NullPointerException`, embora concatenar funcione:

```java executar
String vazia = "";
String espacos = "   ";
String nula = null;
System.out.println(vazia.isEmpty() + " " + espacos.isEmpty() + " " + espacos.isBlank());
System.out.println(nula + "!");
try {
    System.out.println(nula.length());
} catch (NullPointerException e) {
    System.out.println("NullPointerException");
}
```

```saida
true false true
null!
NullPointerException
```

`isBlank()` (Java 11) é verdadeiro para strings vazias ou só com espaços em branco. Para testar "não preenchido" em formulários, `s == null || s.isBlank()` cobre os três casos.

> [!PREVENCAO]
> Teste o `null` **primeiro**: `s == null || s.isBlank()`. Na ordem inversa, `s.isBlank() || s == null`, o método é chamado antes do teste e lança `NullPointerException` justamente no caso que o teste queria pegar. O [curto-circuito](/assistir/estagiario-t2-e04) do `||` é o que protege a segunda parte.

## Por que imutável?

A imutabilidade não é um acaso; ela sustenta várias garantias:

- **Compartilhamento.** Como ninguém consegue alterar uma `String`, a JVM pode reaproveitar o mesmo objeto para literais iguais, o **pool de strings** do [último episódio](/assistir/estagiario-t5-e05).
- **Segurança.** Nomes de arquivo, URLs e nomes de classe são `String`. Se fosse possível alterá-los depois de validados, um código malicioso poderia trocar `/tmp/arquivo` por `/etc/senhas` entre a verificação e o uso.
- **Threads.** Um objeto imutável pode ser lido por várias threads ao mesmo tempo sem nenhum cuidado.
- **Hash.** O `hashCode()` de uma `String` é calculado uma vez e guardado, o que torna `String` uma ótima chave de `HashMap`.

A classe também é `final`: ninguém pode criar uma subclasse que quebre essas garantias.

```java nao-compila
class MinhaString extends String {
}
```

> [!ANTES]
> Em C, a linguagem que inspirou a sintaxe do Java, uma string é só um array de `char` terminado por um byte zero, e qualquer função pode escrever nele. Copiar um texto maior que o array (`strcpy`) sobrescreve a memória vizinha, o famoso *buffer overflow*, por décadas a falha de segurança mais explorada. O Java de 1995 fez da `String` um objeto fechado, com tamanho conhecido e conteúdo que ninguém altera.

> [!PERGUNTAS]
> **P:** Então não existe nenhum jeito de mudar o texto de uma `String`?
>
> **R:** Não pelos métodos públicos. Para montar texto aos poucos existe o `StringBuilder`, que é mutável e aparece no [episódio 3](/assistir/estagiario-t5-e03).
>
> **P:** Mas `s += "x"` funciona. Não é uma mudança?
>
> **R:** É uma reatribuição: cria-se uma `String` nova com o texto junto, e `s` passa a apontar para ela. A antiga continua igual, e é recolhida pelo coletor de lixo se ninguém mais apontar para ela.
>
> **P:** Criar um objeto a cada operação não é desperdício?
>
> **R:** Em poucas operações, não faz diferença. Num laço com milhares de concatenações, faz, e é o motivo de o `StringBuilder` existir.
>
> **P:** `final String s` e `String` imutável são a mesma coisa?
>
> **R:** Não. `final` impede a **variável** de apontar para outro objeto. Imutável quer dizer que o **objeto** não muda. Uma `String` é imutável mesmo numa variável que não é `final`.

> [!MATEMATICA]
> O `hashCode()` de uma `String` é um polinômio na base 31: para os caracteres c₀, c₁, ..., cₙ₋₁, vale c₀ × 31ⁿ⁻¹ + c₁ × 31ⁿ⁻² + ... + cₙ₋₁, com as contas em `int` (estourando, se preciso). Para `"ab"`, com `'a'` = 97 e `'b'` = 98: 97 × 31 + 98 = **3105**. Como o texto nunca muda, o resultado também não, e a classe o calcula uma vez e guarda.
>
> ```java executar
> System.out.println("ab".hashCode());
> ```
>
> ```saida
> 3105
> ```

> [!IA]
> Ao revisar código, a IA costuma achar chamadas de `String` com o retorno ignorado, e vale pedir isso explicitamente. Ao gerar código, porém, ela às vezes escreve `nome.trim();` numa linha e usa `nome` depois, principalmente em código de validação. Leia cada chamada de `trim`, `replace` e `toUpperCase` e procure o `=` que guarda o resultado.

## Por baixo dos panos

Por dentro, uma `String` guarda os caracteres num array privado e `final`, e nenhum método o expõe. Até o Java 8, era um `char[]`: 2 bytes por caractere, sempre. Desde o Java 9 (JEP 254, *Compact Strings*), é um `byte[]` com um marcador de codificação: se todos os caracteres cabem em Latin-1 (inglês, português, a maior parte dos textos de sistemas), cada caractere ocupa **1 byte**; senão, a `String` inteira usa UTF-16, com 2 bytes por unidade. Num servidor típico, isso reduz bastante a memória ocupada por strings, sem mudar nada no código.

Um detalhe que vem do UTF-16: `length()` conta **unidades de 16 bits**, não caracteres visíveis. Caracteres fora do plano básico do Unicode, como os emojis, ocupam duas unidades (você viu as codificações de texto no episódio de [bits e bytes](/assistir/aprendiz-t1-e01)):

```java executar
String emoji = "😀";
System.out.println(emoji.length());
System.out.println(emoji.codePointCount(0, emoji.length()));
System.out.println("ação".length());
```

```saida
2
1
4
```

O "ç" e o "ã" cabem numa unidade cada; o emoji precisa de duas. Para contar caracteres "de verdade", use `codePointCount`.

## Resumo para a prova

- `String` é objeto; a variável guarda uma referência e pode ser `null`
- `length()` é método; índices vão de 0 a `length() - 1`; fora disso, `StringIndexOutOfBoundsException`
- Imutável: os métodos devolvem uma nova `String`; ignorar o retorno não muda nada
- Reatribuir a variável não altera outras variáveis que apontavam para o mesmo objeto
- `""` está vazia; `"   "` está em branco (`isBlank`); `null` lança exceção ao chamar métodos, mas concatena como `"null"`
- `String` é `final`
- Desde o Java 9, strings Latin-1 usam 1 byte por caractere; `length()` conta unidades UTF-16
