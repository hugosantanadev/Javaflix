"Use `equals` para comparar strings" é a primeira regra que todo mundo aprende. A prova vai além: quer saber **quando** `==` dá verdadeiro mesmo assim, e por quê. A resposta é o **pool de strings**, uma área em que a JVM guarda uma única cópia de cada literal, e as regras de constante de compilação que decidem o que vai para lá.

## `==` compara referências; `equals` compara conteúdo

Com objetos, `==` responde "são **o mesmo objeto**?". O `equals` da `String` responde "têm **os mesmos caracteres**?":

```java executar
String a = "java";
String b = "java";
String c = new String("java");
System.out.println(a == b);
System.out.println(a == c);
System.out.println(a.equals(c));
System.out.println(a == c.intern());
```

```saida
true
false
true
true
```

`a` e `b` vêm do mesmo literal, e o literal só existe uma vez no pool: são o mesmo objeto. `new String("java")` cria **sempre** um objeto novo no heap, fora do pool, mesmo com o mesmo conteúdo. E `intern()` devolve a cópia do pool, criando-a se ainda não existir.

## O pool de strings

Quando uma classe é carregada, cada literal de texto dela é procurado numa tabela global da JVM: se já existe uma `String` igual, o literal passa a apontar para ela; senão, a nova é guardada ali. Isso só é seguro porque `String` é [imutável](/assistir/estagiario-t5-e01): se alguém pudesse alterar o "java" de `a`, alteraria o de `b` também.

O que vai para o pool são as **constantes de compilação**: literais, text blocks e expressões que o compilador consegue calcular sozinho, como concatenações de literais e de variáveis `final` inicializadas com constantes. Você viu esse cálculo no episódio de [compiladores](/assistir/aprendiz-t2-e03):

```java executar
String ab = "ab";
String a = "a";
final String fa = "a";
System.out.println(ab == "a" + "b");
System.out.println(ab == a + "b");
System.out.println(ab == fa + "b");
System.out.println(ab == (a + "b").intern());
```

```saida
true
false
true
true
```

`"a" + "b"` e `fa + "b"` são calculados pelo `javac` e viram o mesmo `"ab"` do pool. Já `a + "b"`, com `a` não `final`, é calculado em tempo de execução e cria um objeto novo. Qualquer chamada de método também quebra a constância: `"Ja" + "va".toLowerCase()` é calculado na execução.

> [!PROVA]
> Resultados de métodos (`substring`, `toUpperCase`, `concat`, `toString` de um `StringBuilder`) e de concatenações com variáveis comuns são objetos novos, fora do pool. Comparados com `==` a um literal, dão `false`, mesmo com o mesmo texto. A exceção documentada é o `trim()`: quando não há espaços nas pontas, ele devolve a própria `String`, e a documentação garante isso.

```java executar
String s = "abc";
System.out.println(s.trim() == s);
System.out.println(s.substring(1) == "bc");
System.out.println(" abc".trim() == s);
```

```saida
true
false
false
```

## Comparando do jeito certo

| Situação | Use |
|---|---|
| Mesmo conteúdo, diferenciando maiúsculas | `a.equals(b)` |
| Mesmo conteúdo, sem diferenciar maiúsculas | `a.equalsIgnoreCase(b)` |
| Ordem alfabética | `a.compareTo(b)`, como no episódio de [métodos](/assistir/estagiario-t5-e02) |
| Um dos lados pode ser `null` | `"literal".equals(x)` ou `Objects.equals(a, b)` |
| Conteúdo de um `StringBuilder` | `s.contentEquals(sb)` |

Chamar `equals` numa variável nula lança `NullPointerException`; passar `null` como argumento apenas devolve `false`. Por isso o hábito de escrever o literal à esquerda:

```java executar
String entrada = null;
System.out.println("SIM".equalsIgnoreCase("sim"));
System.out.println("sim".equals(entrada));
System.out.println(Objects.equals(entrada, null));
```

```saida
true
false
true
```

O `switch` com `String` usa `equals` por baixo dos panos, como você viu no episódio do [switch](/assistir/estagiario-t3-e02): um `new String("sair")` cai no `case "sair"` normalmente.

## Por que `==` às vezes "funciona"

Código que compara strings com `==` costuma passar nos testes, porque nos testes as strings são literais, e literais iguais são o mesmo objeto. Em produção, as strings vêm de fora (um formulário, um arquivo, um banco de dados), são criadas em tempo de execução e nunca estão no pool. O `==` passa a dar `false` para textos iguais, e o bug só aparece com dados reais. Por isso a regra é simples: `==` com `String` só para comparar com `null`.

## Por baixo dos panos

O pool é uma tabela hash interna da JVM (a *StringTable*). Até o Java 6, ela ficava na *PermGen*, uma área de tamanho fixo, e chamar `intern()` demais derrubava o programa com `OutOfMemoryError: PermGen space`. Desde o Java 7, as strings internadas ficam no heap comum e são coletadas pelo GC quando ninguém mais as referencia. Dá para ver o tamanho da tabela com a opção `-XX:+PrintStringTableStatistics`.

O `equals` é rápido: compara primeiro as referências (o mesmo objeto é igual a si mesmo), depois o tamanho e a codificação, e só então os bytes, com instruções vetoriais. E o coletor G1 tem uma otimização opcional, a *String Deduplication* (`-XX:+UseStringDeduplication`, JEP 192): ele procura strings iguais criadas em tempo de execução e faz todas compartilharem o mesmo array de bytes, sem mudar a identidade dos objetos. Os `==` continuam dando `false`; só a memória é economizada.

## Resumo para a prova

- `==` compara referências; `equals` compara o conteúdo
- Literais iguais são o mesmo objeto (pool); `new String(...)` sempre cria outro
- Constantes de compilação (literais, `final` com constante e suas concatenações) vão para o pool
- Concatenação com variável comum ou chamada de método é feita em tempo de execução: objeto novo
- `intern()` devolve a cópia do pool
- `trim()` devolve a mesma `String` quando não há espaços a remover
- `x.equals(...)` com `x` nulo lança exceção; `"literal".equals(x)` e `Objects.equals` não
- `equalsIgnoreCase` ignora maiúsculas; `switch` com `String` usa `equals`
