A loja já calcula totais, cupons e frete. Como saber que continua calculando certo depois da próxima mudança? Abrir a aplicação e conferir à mão funciona uma vez, e não escala: ninguém refaz cinquenta conferências a cada *commit*. Um **teste automatizado** é um programa que exercita o código e verifica o resultado, e roda em segundos, quantas vezes for preciso. Ele protege contra regressões, documenta o comportamento esperado com exemplos que executam e dá coragem para refatorar. No mundo Java, a base de tudo é o **JUnit**. O Spring Boot 4.1 traz o JUnit 6, e todos os resultados deste episódio saíram de execuções reais com ele e o Maven.

## O primeiro teste

O `spring-boot-starter-test`, que todo projeto do Spring Initializr já traz no escopo de teste, inclui o JUnit, o AssertJ e o Mockito, os assuntos desta temporada. Os testes ficam em `src/test/java`, no mesmo pacote da classe testada:

```java
class CarrinhoTest {

    private Carrinho carrinho;

    @BeforeEach
    void prepararCarrinho() {
        carrinho = new Carrinho();
    }

    @Test
    void carrinhoNovoComecaVazio() {
        assertTrue(carrinho.vazio());
        assertEquals(BigDecimal.ZERO, carrinho.total());
    }

    @Test
    @DisplayName("o total soma o subtotal de cada item")
    void totalSomaOsItens() {
        carrinho.adicionar("Teclado mecânico", new BigDecimal("349.90"), 1);
        carrinho.adicionar("Mouse sem fio", new BigDecimal("129.90"), 2);

        BigDecimal total = carrinho.total();

        assertEquals(new BigDecimal("609.70"), total);
    }
}
```

Um método com `@Test` é um teste. Nem a classe nem os métodos precisam ser públicos. As asserções, como `assertEquals` e `assertTrue`, vêm de `org.junit.jupiter.api.Assertions` (com `import static`) e lançam um erro quando a condição não vale. O segundo teste segue a estrutura mais comum, com três partes separadas por uma linha em branco: **preparar** o cenário, **agir** chamando o código testado e **verificar** o resultado. Em inglês, *Arrange, Act, Assert*.

## Rodando

`mvn test` compila os testes e roda todos pelo plugin Surefire:

```text
[INFO] Running br.com.javaflix.loja.CarrinhoTest
[INFO] Tests run: 4, Failures: 0, Errors: 0, Skipped: 0, Time elapsed: 0.094 s -- in br.com.javaflix.loja.CarrinhoTest
[INFO] Running br.com.javaflix.loja.FreteTest
[INFO] Tests run: 4, Failures: 0, Errors: 0, Skipped: 0, Time elapsed: 0.121 s -- in br.com.javaflix.loja.FreteTest
```

Na IDE, um clique no ícone ao lado da classe faz o mesmo. Um *build* com um teste falhando não gera o pacote: o `mvn package` para no `test`, como visto no [episódio de Maven](/assistir/backend-junior-t1-e05).

## Quando falha

Um teste para dois mouses de R$ 129,90:

```java
@Test
void totalDeDoisMouses() {
    Carrinho carrinho = new Carrinho();
    carrinho.adicionar("Mouse sem fio", new BigDecimal("129.90"), 2);

    assertEquals(new BigDecimal("259.8"), carrinho.total());
}
```

```text
[ERROR] br.com.javaflix.loja.EscalaTest.totalDeDoisMouses -- Time elapsed: 0.007 s <<< FAILURE!
org.opentest4j.AssertionFailedError: expected: <259.8> but was: <259.80>
	at org.junit.jupiter.api.AssertionFailureBuilder.build(AssertionFailureBuilder.java:158)
	...
	at br.com.javaflix.loja.EscalaTest.totalDeDoisMouses(EscalaTest.java:15)

[ERROR] Tests run: 9, Failures: 1, Errors: 0, Skipped: 0
[INFO] BUILD FAILURE
```

A mensagem diz o esperado e o obtido, e a última linha da pilha que é do seu código aponta a linha do teste. O valor está certo, mas o `equals` de `BigDecimal` compara também a escala, e 259.8 tem uma casa, enquanto 259.80 tem duas. O teste encontrou um detalhe que um humano conferindo a tela não veria. A correção é escrever o esperado com a escala certa, ou comparar com `compareTo`, como o [próximo episódio](/assistir/backend-junior-t6-e02) faz de um jeito mais legível.

A ordem dos argumentos importa: `assertEquals(esperado, obtido)`. Invertidos, o teste passa e falha nos mesmos casos, mas a mensagem mente, chamando de esperado o que o código produziu.

O Surefire separa **falhas** (*failures*), quando uma asserção não vale, de **erros** (*errors*), quando o teste lança uma exceção inesperada, como um `NullPointerException`. Uma falha diz que o código fez a coisa errada; um erro, que nem chegou ao fim.

## Exceções

Testar o caminho triste é tão importante quanto o feliz. O `assertThrows` executa o código e verifica que ele lança a exceção esperada, devolvendo-a para conferir a mensagem:

```java
@Test
void quantidadeZeroEhRecusada() {
    IllegalArgumentException erro = assertThrows(IllegalArgumentException.class,
            () -> carrinho.adicionar("Headset", new BigDecimal("259.90"), 0));

    assertEquals("quantidade deve ser positiva: 0", erro.getMessage());
}
```

Se o código não lançar nada, ou lançar outra exceção, o teste falha.

## O ciclo de vida

Os métodos com `@BeforeEach` rodam antes de cada teste, e os com `@AfterEach`, depois. O `@BeforeAll`, estático, roda uma vez antes de todos. Com uma linha impressa em cada um:

```text
@BeforeAll: uma vez, antes de tudo
@BeforeEach antes de "carrinhoNovoComecaVazio()", objeto de teste 58ce9668
@AfterEach
@BeforeEach antes de "o total soma o subtotal de cada item", objeto de teste 38089a5a
@AfterEach
@BeforeEach antes de "quantidadeZeroEhRecusada()", objeto de teste 6581dc0a
@AfterEach
```

O número no fim é a identidade do objeto, e ele muda a cada teste: o JUnit cria uma **instância nova da classe de teste para cada método**. O campo `carrinho` de um teste nunca é o do anterior. É isso que permite que cada teste rode isolado, em qualquer ordem. E a ordem não deve importar: o JUnit usa uma ordem determinística, mas propositalmente difícil de prever, para que ninguém escreva um teste que dependa de outro.

## Nomes, grupos e testes desligados

O `@DisplayName` dá ao teste um nome legível. O `@Nested` agrupa testes numa classe interna, não estática: antes de cada teste dela, rodam primeiro os `@BeforeEach` da classe externa e depois os da interna. O `@Disabled` desliga um teste, com o motivo:

```java
@Test
@Disabled("frete por CEP ainda não existe")
void fretePorCep() {
}

@Nested
@DisplayName("com cupom")
class ComCupom {

    @BeforeEach
    void doisMouses() {
        carrinho.adicionar("Mouse sem fio", new BigDecimal("129.90"), 2);
    }

    @Test
    @DisplayName("DEZ dá 10% de desconto")
    void dez() {
        assertEquals(new BigDecimal("233.82"), carrinho.totalComCupom("DEZ"));
    }

    @Test
    @DisplayName("cupom desconhecido é recusado")
    void desconhecido() {
        IllegalArgumentException erro = assertThrows(IllegalArgumentException.class,
                () -> carrinho.totalComCupom("NATAL"));

        assertEquals("cupom inválido: NATAL", erro.getMessage());
    }
}
```

Os nomes que o JUnit gerou, na árvore que as IDEs mostram:

```text
CarrinhoTest
  ✔ carrinhoNovoComecaVazio()
  ✔ o total soma o subtotal de cada item
  ↷ fretePorCep() (frete por CEP ainda não existe)
  ✔ quantidadeZeroEhRecusada()
  com cupom
    ✔ DEZ dá 10% de desconto
    ✔ cupom desconhecido é recusado
```

Um teste desligado aparece como pulado (*skipped*) no relatório. Use com parcimônia: um `@Disabled` esquecido é um teste que não protege nada.

## Testes parametrizados

O frete muda na fronteira de R$ 200,00, e é ali que os erros moram: um `>` no lugar de `>=` passa em quase todos os casos. Em vez de quatro métodos quase iguais, um teste parametrizado recebe os casos como dados:

```java
@ParameterizedTest(name = "total {0} para {1} paga {2}")
@CsvSource({
        "199.99, SP, 15.00",
        "199.99, BA, 25.00",
        "200.00, BA, 0",
        "350.00, SP, 0",
})
void calculaOFrete(BigDecimal total, String uf, BigDecimal esperado) {
    assertEquals(esperado, Frete.calcular(total, uf));
}
```

```text
FreteTest
  calculaOFrete(BigDecimal, String, BigDecimal)
    ✔ total "199.99" para "SP" paga "15.00"
    ✔ total "199.99" para "BA" paga "25.00"
    ✔ total "200.00" para "BA" paga "0"
    ✔ total "350.00" para "SP" paga "0"
```

Cada linha do CSV vira uma execução, e o JUnit converte o texto para o tipo de cada parâmetro, aqui `BigDecimal` e `String`. No nome, o JUnit 6 põe os argumentos de texto entre aspas. Os casos de 199.99 e 200.00 testam os dois lados da fronteira: são os **valores-limite**, os mais valiosos de qualquer teste. Além do `@CsvSource`, existem `@ValueSource`, para um parâmetro só, `@EnumSource` e `@MethodSource`, que lê os casos de um método.

## O que faz um bom teste

- **Rápido**: testes de unidade rodam em milissegundos, para rodar sempre
- **Isolado**: não depende de outro teste, da ordem, da hora nem da rede
- **Repetível**: o mesmo resultado em qualquer máquina, a qualquer hora
- **Um comportamento por teste**, com um nome que diz qual; quando falha, o nome já explica o problema
- **Testa comportamento, não implementação**: verifica o que o código entrega, e não como ele faz por dentro, para não quebrar a cada refatoração

## Por baixo dos panos

O JUnit é, no fundo, reflexão: procura os métodos anotados, cria um objeto da classe de teste para cada um, roda o preparo, invoca o teste e classifica o que acontecer. Um executor mínimo:

```java executar
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;
import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Method;
import java.math.BigDecimal;
import java.util.Arrays;
import java.util.Comparator;
import java.util.List;

public class MiniJUnit {
    @Retention(RetentionPolicy.RUNTIME)
    @Target(ElementType.METHOD)
    @interface Teste {}

    @Retention(RetentionPolicy.RUNTIME)
    @Target(ElementType.METHOD)
    @interface AntesDeCada {}

    static void verificarIgual(Object esperado, Object obtido) {
        if (!esperado.equals(obtido)) {
            throw new AssertionError("expected: <" + esperado + "> but was: <" + obtido + ">");
        }
    }

    public static class CarrinhoTeste {
        static int instancias = 0;
        BigDecimal total;

        public CarrinhoTeste() {
            instancias++;
        }

        @AntesDeCada
        public void preparar() {
            total = new BigDecimal("129.90").multiply(BigDecimal.valueOf(2));
        }

        @Teste
        public void totalComparadoPorValor() {
            verificarIgual(0, total.compareTo(new BigDecimal("259.8")));
        }

        @Teste
        public void totalComparadoComEquals() {
            verificarIgual(new BigDecimal("259.8"), total);
        }

        @Teste
        public void divisaoPorZero() {
            int zero = 0;
            System.out.println(10 / zero);
        }

        public void auxiliar() {
            throw new IllegalStateException("não é um teste");
        }
    }

    public static void main(String[] args) throws Exception {
        Class<?> classe = CarrinhoTeste.class;
        List<Method> testes = Arrays.stream(classe.getDeclaredMethods())
                .filter(m -> m.isAnnotationPresent(Teste.class))
                .sorted(Comparator.comparing(Method::getName))
                .toList();
        int falhas = 0;
        int erros = 0;
        for (Method teste : testes) {
            Object instancia = classe.getDeclaredConstructor().newInstance();
            for (Method m : classe.getDeclaredMethods()) {
                if (m.isAnnotationPresent(AntesDeCada.class)) m.invoke(instancia);
            }
            try {
                teste.invoke(instancia);
                System.out.println("✔ " + teste.getName());
            } catch (InvocationTargetException e) {
                Throwable causa = e.getCause();
                if (causa instanceof AssertionError) {
                    falhas++;
                    System.out.println("✘ " + teste.getName() + ": FALHA, " + causa.getMessage());
                } else {
                    erros++;
                    System.out.println("✘ " + teste.getName() + ": ERRO, " + causa);
                }
            }
        }
        System.out.println("Tests run: " + testes.size() + ", Failures: " + falhas + ", Errors: " + erros
                + " (objetos de teste criados: " + CarrinhoTeste.instancias + ")");
    }
}
```

```saida
✘ divisaoPorZero: ERRO, java.lang.ArithmeticException: / by zero
✘ totalComparadoComEquals: FALHA, expected: <259.8> but was: <259.80>
✔ totalComparadoPorValor
Tests run: 3, Failures: 1, Errors: 1 (objetos de teste criados: 3)
```

Três testes, três objetos, e o método `auxiliar`, sem anotação, nunca foi chamado. A diferença entre falha e erro é só o tipo do que foi lançado: `AssertionError` é falha; qualquer outra coisa, erro. O `getDeclaredMethods` não garante ordem nenhuma, por isso o executor ordena por nome; o JUnit tem a sua ordem própria pelo mesmo motivo. O JUnit de verdade é dividido em duas partes: a **plataforma**, que descobre e executa testes e conversa com o Maven e as IDEs, e o **Jupiter**, o motor que entende `@Test`, `@BeforeEach` e companhia.

## Resumo

- Testes ficam em `src/test/java`; `spring-boot-starter-test` traz JUnit, AssertJ e Mockito
- `@Test` marca o teste; estrutura preparar, agir, verificar
- `assertEquals(esperado, obtido)`, nessa ordem; `assertThrows` devolve a exceção para conferir
- Falha é asserção que não vale; erro é exceção inesperada
- Uma instância da classe de teste por método: cada teste começa do zero, em qualquer ordem
- `@BeforeEach`, `@AfterEach`, `@BeforeAll`; `@DisplayName`, `@Nested`, `@Disabled`
- `@ParameterizedTest` com `@CsvSource` para muitos casos, sempre com os valores-limite
