O `@DataJpaTest` do [episódio anterior](/assistir/backend-junior-t6-e04) trocou o banco pelo H2 em memória. É rápido e prático, mas a loja roda com PostgreSQL em produção, e os dois não são iguais. Esta temporada já esbarrou em diferenças: o H2 cria índices para chaves estrangeiras sozinho e o PostgreSQL não, o H2 não tem `FULL OUTER JOIN`, e o Hibernate usa um tipo `enum` próprio do H2 para os status. Some a isso funções, tipos como `jsonb`, ordenação de textos com acento e mensagens de erro diferentes. Um teste que passa no H2 pode estar testando um banco que ninguém usa. O **Testcontainers** resolve isso subindo o banco de verdade, num contêiner Docker descartável, durante os testes.

## O que é preciso

O Testcontainers conversa com o Docker da máquina, então o Docker precisa estar instalado e rodando, como o Docker Desktop no Windows e no macOS. No projeto, três dependências de teste, com versões gerenciadas pelo Spring Boot:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-testcontainers</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>testcontainers-postgresql</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <scope>runtime</scope>
</dependency>
```

O Spring Boot 4.1 usa o Testcontainers 2.0, que mudou os nomes: os módulos ganharam o prefixo `testcontainers-`, e as classes de cada banco foram para pacotes próprios. O contêiner do PostgreSQL agora é `org.testcontainers.postgresql.PostgreSQLContainer`; o antigo, em `org.testcontainers.containers`, ainda existe, mas marcado como obsoleto. Exemplos na internet costumam usar os nomes antigos.

## A configuração

O jeito do Spring Boot, que o Spring Initializr gera quando se escolhe Testcontainers, é declarar o contêiner como um bean de teste:

```java
@TestConfiguration(proxyBeanMethods = false)
class TestcontainersConfiguration {

    @Bean
    @ServiceConnection
    PostgreSQLContainer postgres() {
        return new PostgreSQLContainer("postgres:18-alpine");
    }
}
```

E qualquer teste que precise do banco importa essa configuração:

```java
@SpringBootTest
@Import(TestcontainersConfiguration.class)
class ProdutoPostgresTest {

    @Autowired
    ProdutoRepository produtos;

    @Test
    void salvaNoPostgres() {
        produtos.save(new Produto("Headset", new BigDecimal("259.90")));

        assertThat(produtos.findByNomeContainingIgnoreCaseOrderByNome("head")).hasSize(1);
    }
}
```

Não há URL, usuário nem senha em lugar nenhum. O `@ServiceConnection` faz o Spring Boot ler esses dados do próprio contêiner e montar o `DataSource` com eles. Use a mesma versão principal do PostgreSQL de produção na imagem.

## O que acontece ao rodar

Quando o contexto do teste sobe, o bean do contêiner é criado e o Spring Boot o inicia. O Testcontainers então:

1. Encontra o Docker da máquina.
2. Baixa a imagem `postgres:18-alpine`, se ela ainda não estiver no computador. Só a primeira execução paga esse preço.
3. Cria o contêiner com banco, usuário e senha `test`, e inicia o PostgreSQL com `-c fsync=off`, que deixa o banco mais rápido abrindo mão de uma garantia contra queda de energia, aceitável para um banco que vai ser jogado fora.
4. Liga a porta 5432 do contêiner a uma **porta livre e aleatória** da máquina. Assim, dois projetos podem rodar testes ao mesmo tempo, e um PostgreSQL instalado na máquina não atrapalha.
5. **Espera o banco ficar pronto**: lê o log do contêiner até a mensagem "database system is ready to accept connections" aparecer **duas vezes**, com limite de 60 segundos.
6. Entrega ao Spring Boot a URL, com a porta aleatória, o usuário e a senha. O `DataSource` aponta para o contêiner, e as migrações do Flyway, se houver, rodam nele.

No fim, quando o contexto é fechado, o contêiner é parado e apagado. Se a JVM dos testes morrer no meio, um segundo contêiner auxiliar do Testcontainers, o Ryuk, apaga os que ficaram para trás.

Os itens 3 e 5 estão no código da classe `PostgreSQLContainer`. A mensagem esperada duas vezes tem um motivo: na primeira subida, a imagem oficial do PostgreSQL inicia um servidor temporário, roda os scripts de inicialização, desliga esse servidor e sobe o definitivo. A primeira mensagem é do temporário, que vai ser desligado em seguida. O desafio deste episódio simula essa espera.

## Sem Docker

Rodar esse teste com o Docker desligado, como foi feito para este episódio, mostra a mensagem que todo mundo encontra um dia:

```text
INFO  org.testcontainers.DockerClientFactory   : Testcontainers version: 2.0.5
ERROR o.t.d.DockerClientProviderStrategy       : Could not find a valid Docker environment. Please check configuration. Attempted configurations were:
As no valid configuration was found, execution cannot continue.

```

E a cadeia de causas mostra como o `@ServiceConnection` funciona por dentro, de baixo para cima:

```text
Caused by: ... Error creating bean with name 'dataSource' ...
Caused by: ... Error creating bean with name 'jdbcContainerConnectionDetailsForPostgres': Error creating bean with name 'postgres' ...
```

O `dataSource` depende de um bean de detalhes de conexão, criado pelo Spring Boot a partir do contêiner `postgres`, que depende do Docker. A correção é iniciar o Docker. Nos executores Linux do GitHub Actions, o Docker já vem instalado, e os mesmos testes rodam na integração contínua sem configuração extra.

## Velocidade: um contêiner para muitos testes

Subir um PostgreSQL leva alguns segundos. Fazer isso a cada teste seria inviável, e o cache de contextos do episódio anterior resolve: o contêiner é um bean, vive enquanto o contexto viver, e todas as classes de teste com a mesma configuração dividem o mesmo contexto e o mesmo banco. Por isso vale importar sempre a mesma `TestcontainersConfiguration`, sem variações. A contrapartida é a do episódio anterior: o banco é compartilhado, e cada teste precisa limpar o que cria ou não depender do que os outros deixaram.

Sem o Spring, o módulo `testcontainers-junit-jupiter` oferece a extensão `@Testcontainers`, com campos `@Container`. Um campo estático é iniciado uma vez por classe de teste; um campo de instância, uma vez por teste.

## Também em desenvolvimento

A mesma configuração serve para rodar a aplicação na sua máquina, sem instalar o PostgreSQL. Uma classe em `src/test/java`, que o Initializr também gera:

```java
public class TestLojaApplication {
    public static void main(String[] args) {
        SpringApplication.from(LojaApplication::main).with(TestcontainersConfiguration.class).run(args);
    }
}
```

Executar essa classe sobe o contêiner e a aplicação apontando para ele.

## A pirâmide completa

| Tipo | Ferramentas | Quantidade | Tempo |
|---|---|---|---|
| Unidade | JUnit, AssertJ, Mockito | Muitos | Milissegundos |
| Integração de uma camada | `@WebMvcTest`, `@DataJpaTest` | Vários | Décimos de segundo, com o contexto em cache |
| Integração completa | `@SpringBootTest`, Testcontainers | Alguns | Segundos para subir, depois rápidos |
| Ponta a ponta | A aplicação implantada, um navegador | Poucos | Minutos |

A base larga, de testes rápidos, dá a resposta em segundos a cada mudança. O topo, mais caro, confirma que as peças funcionam juntas.

![Pirâmide de testes com unidade na base, integração no meio e ponta a ponta no topo](/figuras/piramide-de-testes.svg "Quanto mais alto na pirâmide, mais lento e mais caro é cada teste, e menos deles a suíte deve ter.")

> [!MATEMATICA]
> A forma de pirâmide vem de uma conta de tempo. Uma suíte com 800 testes de unidade de 5 ms, 60 de integração de 200 ms e 5 de ponta a ponta de 30 s leva 800 × 0,005 + 60 × 0,2 + 5 × 30 = 4 + 12 + 150 = 166 segundos. Os 5 testes do topo são 90% do tempo. Com a pirâmide invertida, 800 testes de ponta a ponta levariam 800 × 30 = 24.000 segundos, quase 7 horas por execução.

## Por baixo dos panos

O que o Testcontainers faz com o contêiner se resume a três ideias: subir o serviço numa porta escolhida pelo sistema, esperar que ele diga que está pronto e garantir que ele seja parado no fim. Com um `HttpServer` do JDK no papel do banco, um serviço que só fica pronto na terceira verificação de saúde:

```java executar
import com.sun.net.httpserver.HttpServer;
import java.io.IOException;
import java.net.InetSocketAddress;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.util.concurrent.atomic.AtomicInteger;

public class Conteiner implements AutoCloseable {
    private final HttpServer servidor;
    private final AtomicInteger verificacoes = new AtomicInteger();

    /** Sobe o "serviço" numa porta livre, escolhida pelo sistema operacional. */
    Conteiner() throws IOException {
        servidor = HttpServer.create(new InetSocketAddress("127.0.0.1", 0), 0);
        servidor.createContext("/saude", troca -> {
            boolean pronto = verificacoes.incrementAndGet() >= 3;
            troca.sendResponseHeaders(pronto ? 200 : 503, -1);
            troca.close();
        });
        servidor.start();
    }

    int porta() {
        return servidor.getAddress().getPort();
    }

    /** A estratégia de espera: só devolve quando o serviço responde que está pronto. */
    void esperarFicarPronto(int maximoDeTentativas) throws Exception {
        try (HttpClient cliente = HttpClient.newHttpClient()) {
            HttpRequest saude = HttpRequest.newBuilder(URI.create("http://127.0.0.1:" + porta() + "/saude")).build();
            for (int tentativa = 1; tentativa <= maximoDeTentativas; tentativa++) {
                int status = cliente.send(saude, HttpResponse.BodyHandlers.discarding()).statusCode();
                System.out.println("verificação " + tentativa + ": " + status);
                if (status == 200) return;
                Thread.sleep(20);
            }
        }
        throw new IllegalStateException("não ficou pronto em " + maximoDeTentativas + " tentativas");
    }

    @Override
    public void close() {
        servidor.stop(0);
        System.out.println("parado");
    }

    public static void main(String[] args) throws Exception {
        try (Conteiner banco = new Conteiner()) {
            System.out.println("porta escolhida pelo sistema, acima de 1023: " + (banco.porta() > 1023));
            banco.esperarFicarPronto(10);
            System.out.println("o teste roda aqui, com a porta " + (banco.porta() == 5432 ? "padrão" : "mapeada"));
        }
    }
}
```

```saida
porta escolhida pelo sistema, acima de 1023: true
verificação 1: 503
verificação 2: 503
verificação 3: 200
o teste roda aqui, com a porta mapeada
parado
```

A porta 0 pede ao sistema operacional qualquer porta livre, como o Docker faz ao mapear a 5432 do contêiner. Sem a espera, o teste tentaria conectar enquanto o serviço ainda respondia 503, e falharia de forma intermitente, o pior tipo de falha. E o `try` com recursos garante o `close`, mesmo se o teste lançar exceção, o papel que o Spring e o Ryuk cumprem para os contêineres. O Testcontainers de verdade tem várias estratégias de espera prontas: por mensagem no log, como a do PostgreSQL, por porta aberta, por uma rota HTTP de saúde e pelo *healthcheck* do próprio Docker.

## Resumo

- H2 nos testes e PostgreSQL em produção divergem; o Testcontainers sobe o banco real no Docker
- Precisa do Docker rodando; sem ele, "Could not find a valid Docker environment"
- No Spring Boot, um `@Bean` `@ServiceConnection` com o contêiner e `@Import` nos testes
- Testcontainers 2: módulos `testcontainers-*` e classes em novos pacotes, como `org.testcontainers.postgresql`
- Porta aleatória, espera até o serviço ficar pronto e limpeza no fim, até se a JVM morrer
- O cache de contextos reaproveita o contêiner entre as classes de teste de mesma configuração
- Muitos testes de unidade, alguns de integração, poucos de ponta a ponta
