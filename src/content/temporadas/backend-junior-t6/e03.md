O `Carrinho` dos episódios anteriores era fácil de testar: recebe dados, devolve resultados. O serviço que finaliza a compra não é assim. Ele reserva os produtos no estoque, salva o pedido no banco e manda um e-mail de confirmação:

```java
public class CheckoutService {

    private final Estoque estoque;
    private final Pedidos pedidos;
    private final Notificador notificador;

    public CheckoutService(Estoque estoque, Pedidos pedidos, Notificador notificador) {
        this.estoque = estoque;
        this.pedidos = pedidos;
        this.notificador = notificador;
    }

    public long finalizar(Carrinho carrinho, String email) {
        if (carrinho.vazio()) {
            throw new IllegalArgumentException("carrinho vazio");
        }
        for (Carrinho.Item item : carrinho.itens()) {
            if (!estoque.reservar(item.produto(), item.quantidade())) {
                throw new SemEstoqueException(item.produto());
            }
        }
        long id = pedidos.salvar(carrinho, email);
        notificador.pedidoConfirmado(email, id);
        return id;
    }
}
```

Testar com as dependências reais exigiria o sistema de estoque no ar, um banco e um servidor de e-mail, e cada execução mandaria uma mensagem de verdade. E o caso "sem estoque" dependeria de esvaziar o estoque antes. A saída é trocar as dependências por **dublês de teste**: objetos que se passam pelas reais, controlados pelo teste. Como as dependências chegam pelo construtor, como no [episódio de injeção de dependências](/assistir/backend-junior-t4-e01), a troca é natural. O **Mockito** cria esses dublês, e vem no `spring-boot-starter-test`. Tudo aqui saiu de execuções reais do Mockito 5.23 com o JUnit 6.

## Mocks

```java
@ExtendWith(MockitoExtension.class)
class CheckoutServiceTest {

    @Mock
    Estoque estoque;

    @Mock
    Pedidos pedidos;

    @Mock
    Notificador notificador;

    @InjectMocks
    CheckoutService checkout;
```

A extensão do Mockito cria um *mock* para cada campo com `@Mock` e, no `@InjectMocks`, constrói o serviço passando os mocks pelo construtor. Um mock implementa a interface, mas não faz nada: sem configuração, cada método devolve um valor padrão.

```text
reservar sem configuração: false
salvar sem configuração: 0
toString do mock: estoque
```

`false` para `boolean`, zero para números, `null` para objetos e coleções vazias para `List`, `Set` e `Map`.

## Configurando respostas

O `when(...).thenReturn(...)` ensina ao mock o que responder:

```java
@Test
void finalizaReservandoSalvandoENotificando() {
    when(estoque.reservar(anyString(), anyInt())).thenReturn(true);
    when(pedidos.salvar(any(Carrinho.class), eq("ana@exemplo.com"))).thenReturn(42L);

    long id = checkout.finalizar(carrinho, "ana@exemplo.com");

    assertThat(id).isEqualTo(42L);
    verify(estoque).reservar("Teclado mecânico", 1);
    verify(estoque).reservar("Mouse sem fio", 2);
    verify(notificador).pedidoConfirmado("ana@exemplo.com", 42L);
}
```

Os `any`, `anyString` e `anyInt` são *matchers*: aceitam qualquer valor do tipo. O `eq` aceita um valor específico. Sem matcher nenhum, os argumentos são comparados com `equals`. Para simular um erro, `thenThrow(new RuntimeException("estoque fora do ar"))`. E o carrinho é real: só as dependências do serviço viram mocks. Objetos de valor, como o carrinho, não precisam de dublê.

O caminho triste é tão fácil quanto o feliz: basta configurar o estoque para negar o mouse.

```java
@Test
void semEstoqueNaoSalvaNemNotifica() {
    when(estoque.reservar("Teclado mecânico", 1)).thenReturn(true);
    when(estoque.reservar("Mouse sem fio", 2)).thenReturn(false);

    assertThatThrownBy(() -> checkout.finalizar(carrinho, "ana@exemplo.com"))
            .isInstanceOf(SemEstoqueException.class)
            .hasMessage("sem estoque: Mouse sem fio");

    verify(pedidos, never()).salvar(any(), anyString());
    verify(notificador, never()).pedidoConfirmado(anyString(), anyLong());
}
```

## Verificando interações

O `verify` confere que um método **foi chamado**, com certos argumentos. O `never()` confere o contrário, e `times(2)`, `atLeastOnce()` e `atMost(3)` contam. As mensagens de falha são detalhadas:

```text
Wanted but not invoked:
notificador.pedidoConfirmado(
    "ana@exemplo.com",
    1L
);
-> at br.com.javaflix.loja.FalhasMockitoTest.naoFoiChamado(FalhasMockitoTest.java:44)
Actually, there were zero interactions with this mock.
```

E quando a chamada aconteceu, mas com outros argumentos:

```text
Argument(s) are different! Wanted:
notificador.pedidoConfirmado(
    "ana@exemplo.com",
    41L
);
-> at br.com.javaflix.loja.FalhasMockitoTest.argumentosDiferentes(FalhasMockitoTest.java:52)
Actual invocations have different arguments at position [1]:
notificador.pedidoConfirmado(
    "ana@exemplo.com",
    42L
);

```

A mensagem aponta a linha do teste e a linha do código que fez a chamada real.

## Capturando argumentos e a ordem das chamadas

Às vezes o argumento é um objeto montado dentro do código testado, e o teste quer examiná-lo. O `ArgumentCaptor` guarda o que foi passado:

```java
@Captor
ArgumentCaptor<Carrinho> carrinhoSalvo;

@Test
void salvaOCarrinhoInteiroAntesDeNotificar() {
    when(estoque.reservar(anyString(), anyInt())).thenReturn(true);
    when(pedidos.salvar(any(), anyString())).thenReturn(7L);

    checkout.finalizar(carrinho, "bruno@exemplo.com");

    verify(pedidos).salvar(carrinhoSalvo.capture(), eq("bruno@exemplo.com"));
    assertThat(carrinhoSalvo.getValue().total()).isEqualByComparingTo("609.70");
    InOrder ordem = inOrder(pedidos, notificador);
    ordem.verify(pedidos).salvar(any(), anyString());
    ordem.verify(notificador).pedidoConfirmado("bruno@exemplo.com", 7L);
}
```

O `InOrder` verifica a sequência: notificar antes de salvar seria mandar um e-mail de um pedido que pode nem ter sido gravado.

## Os erros de uso

O Mockito reclama de dois erros comuns. O primeiro é misturar matchers com valores:

```java
when(estoque.reservar(anyString(), 1)).thenReturn(true);
```

```text
org.mockito.exceptions.misusing.InvalidUseOfMatchersException: 
Invalid use of argument matchers!
2 matchers expected, 1 recorded:
-> at br.com.javaflix.loja.FalhasMockitoTest.misturaDeMatchers(FalhasMockitoTest.java:65)
This exception may occur if matchers are combined with raw values:
    //incorrect:
    someMethod(any(), "raw String");
When using matchers, all arguments have to be provided by matchers.
For example:
    //correct:
    someMethod(any(), eq("String by matcher"));
For more info see javadoc for Matchers class.
```

Ou todos os argumentos são matchers, ou nenhum: o certo é `reservar(anyString(), eq(1))`. O segundo é configurar uma resposta que nunca é usada:

```text
org.mockito.exceptions.misusing.UnnecessaryStubbingException: 
Unnecessary stubbings detected.
Clean & maintainable test code requires zero unnecessary code.
Following stubbings are unnecessary (click to navigate to relevant line of code):
  1. -> at br.com.javaflix.loja.FalhasMockitoTest.configuracaoDesnecessaria(FalhasMockitoTest.java:59)
Please remove unnecessary stubbings or use 'lenient' strictness. More info: javadoc for UnnecessaryStubbingException class.
```

A `MockitoExtension` usa o modo estrito: uma configuração sobrando costuma indicar um teste copiado de outro, ou um código que deixou de chamar a dependência. Apague a linha.

O Mockito 5 cria mocks alterando o *bytecode* das classes já carregadas, o que permite até mockar classes `final`. Para isso, ele precisa de um agente Java, e carregá-lo com a JVM já rodando vai ser proibido. A correção, da documentação do Mockito, é carregar o agente na partida da JVM dos testes:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-dependency-plugin</artifactId>
    <executions>
        <execution>
            <goals>
                <goal>properties</goal>
            </goals>
        </execution>
    </executions>
</plugin>
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-surefire-plugin</artifactId>
    <configuration>
        <argLine>-javaagent:${org.mockito:mockito-core:jar}</argLine>
    </configuration>
</plugin>
```

O objetivo `properties` cria uma propriedade com o caminho de cada dependência, e o Surefire passa o do Mockito como `-javaagent`. Com isso, os avisos somem.

## Quando não usar mocks

Mocks são poderosos e fáceis de abusar:

- **Não mocke objetos de valor**, como o carrinho, um `BigDecimal` ou um DTO: use os reais.
- **Prefira verificar resultados** a verificar chamadas. Um `verify` para cada linha do código testado transforma o teste numa cópia da implementação, que quebra a cada refatoração. Verifique as interações que são o objetivo do código, como o e-mail enviado e o pedido salvo.
- **Muitos mocks num teste** são um sintoma: a classe testada faz coisas demais.
- **Às vezes um *fake* é melhor**: uma implementação simples de verdade, como um repositório em memória com um `HashMap`, que se comporta como o real sem configurar resposta por resposta.
- **Mocks não testam a integração**: o teste com o `Pedidos` mockado não sabe se o SQL está certo. Isso fica para os testes de integração, nos [próximos episódios](/assistir/backend-junior-t6-e04).

## Por baixo dos panos

O `when(estoque.reservar("Teclado", 1))` parece mágica: como o `when` sabe o que configurar, se recebe só o valor devolvido, um `false`? A resposta é que ele **ignora o argumento**. Chamar `estoque.reservar(...)` num mock registra a chamada como "a última", e o `when` configura essa última. O `verify(mock)` liga um modo em que a próxima chamada ao mock verifica em vez de executar. Um Mockito mínimo com `java.lang.reflect.Proxy`:

```java executar
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;
import java.util.ArrayList;
import java.util.Arrays;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

public class MiniMockito {
    record Chamada(Object mock, Method metodo, List<Object> argumentos) {
        String chave() {
            return System.identityHashCode(mock) + "." + this;
        }

        @Override
        public String toString() {
            return metodo.getName() + argumentos.toString().replace('[', '(').replace(']', ')');
        }
    }

    interface Configuracao<T> {
        void entaoRetorna(T valor);
    }

    static final List<Chamada> chamadas = new ArrayList<>();
    static final Map<String, Object> respostas = new HashMap<>();
    static Chamada ultima;
    static Object verificando;

    static Object padrao(Class<?> tipo) {
        if (tipo == boolean.class) return false;
        if (tipo == int.class) return 0;
        if (tipo == long.class) return 0L;
        return null;
    }

    @SuppressWarnings("unchecked")
    static <T> T mock(Class<T> tipo) {
        return (T) Proxy.newProxyInstance(tipo.getClassLoader(), new Class<?>[] {tipo}, (proxy, metodo, args) -> {
            Chamada chamada = new Chamada(proxy, metodo, args == null ? List.of() : Arrays.asList(args));
            if (verificando == proxy) {
                verificando = null;
                boolean houve = chamadas.stream().anyMatch(c -> c.chave().equals(chamada.chave()));
                if (!houve) throw new AssertionError("Wanted but not invoked: " + chamada);
                return padrao(metodo.getReturnType());
            }
            chamadas.add(chamada);
            ultima = chamada;
            Object resposta = respostas.get(chamada.chave());
            return resposta != null ? resposta : padrao(metodo.getReturnType());
        });
    }

    /** O argumento é ignorado: o que importa é a última chamada feita a um mock. */
    static <T> Configuracao<T> quando(T ignorado) {
        Chamada configurada = ultima;
        chamadas.remove(configurada);
        return valor -> respostas.put(configurada.chave(), valor);
    }

    /** A próxima chamada a este mock vai verificar, e não executar. */
    static <T> T verificar(T mock) {
        verificando = mock;
        return mock;
    }

    interface Estoque {
        boolean reservar(String produto, int quantidade);
    }

    interface Notificador {
        void pedidoConfirmado(String email, long pedidoId);
    }

    public static void main(String[] args) {
        Estoque estoque = mock(Estoque.class);
        Notificador notificador = mock(Notificador.class);

        System.out.println("sem configuração: " + estoque.reservar("Headset", 1));
        quando(estoque.reservar("Teclado mecânico", 1)).entaoRetorna(true);
        System.out.println("configurado: " + estoque.reservar("Teclado mecânico", 1));
        System.out.println("outros argumentos: " + estoque.reservar("Teclado mecânico", 2));

        notificador.pedidoConfirmado("ana@exemplo.com", 42L);
        verificar(notificador).pedidoConfirmado("ana@exemplo.com", 42L);
        System.out.println("verificação com 42: passou");
        try {
            verificar(notificador).pedidoConfirmado("ana@exemplo.com", 41L);
        } catch (AssertionError e) {
            System.out.println(e.getMessage());
        }
        System.out.println("chamadas registradas: " + chamadas);
    }
}
```

```saida
sem configuração: false
configurado: true
outros argumentos: false
verificação com 42: passou
Wanted but not invoked: pedidoConfirmado(ana@exemplo.com, 41)
chamadas registradas: [reservar(Headset, 1), reservar(Teclado mecânico, 1), reservar(Teclado mecânico, 2), pedidoConfirmado(ana@exemplo.com, 42)]
```

A chamada usada para configurar foi tirada do registro, como o Mockito faz, para não contar numa verificação. É esse estado guardado entre chamadas que explica os erros de uso: os matchers, como `anyString()`, também deixam um registro e devolvem um valor qualquer, e por isso o Mockito sabe contar quantos foram usados, como mostra o desafio. O Mockito real não usa `Proxy`, que só funciona com interfaces: ele gera e altera classes com a biblioteca ByteBuddy, e por isso mocka também classes concretas.

## Resumo

- Dublês substituem dependências lentas ou com efeitos; o Mockito cria mocks
- `@ExtendWith(MockitoExtension.class)`, `@Mock` e `@InjectMocks`, que usa o construtor
- `when(...).thenReturn(...)` e `thenThrow`; sem configuração, valores padrão
- `verify(mock).metodo(...)`, `never()`, `times(n)`; `ArgumentCaptor` e `InOrder`
- Matchers em todos os argumentos ou em nenhum; o modo estrito recusa configurações sem uso
- No JDK 21 em diante, carregue o Mockito como agente no Surefire
- Não mocke objetos de valor; verifique resultados e as interações que importam
