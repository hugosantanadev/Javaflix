As asserções do JUnit resolvem o básico, mas dizem pouco quando falham. Verificar se um produto está na lista vira `assertTrue(produtos.contains("Headset"))`, e a falha é esta:

```text
expected: <true> but was: <false>
```

Esperava verdadeiro, veio falso. Qual era a lista? O que faltou? O **AssertJ** responde com uma API fluente, em que cada verificação é um método encadeado, descoberto pelo autocompletar da IDE, e com mensagens que explicam a falha. A mesma verificação:

```java
assertThat(produtos).contains("Headset");
```

```text
Expecting ArrayList:
  ["Teclado mecânico", "Mouse sem fio"]
to contain:
  ["Headset"]
but could not find the following element(s):
  ["Headset"]
```

O AssertJ já vem no `spring-boot-starter-test`, e tudo nele começa por um único `import static org.assertj.core.api.Assertions.assertThat;`. Todas as mensagens deste episódio saíram do AssertJ 3.27, a versão do Spring Boot 4.1.

## Valores e encadeamento

O `assertThat` recebe o valor real e devolve um objeto de asserções próprio para o tipo dele: para `String`, métodos de texto; para `BigDecimal`, de números; para listas, de coleções. Cada método verifica e devolve o mesmo objeto, para encadear:

```java
assertThat(erro.getMessage()).startsWith("cupom").contains("NATAL");
```

O detalhe da escala do `BigDecimal`, do [episódio anterior](/assistir/backend-junior-t6-e01), tem uma asserção própria. O `isEqualTo` usa o `equals`, e falha:

```text
expected: 609.7
 but was: 609.70
```

O `isEqualByComparingTo` usa o `compareTo`, que só olha o valor, e passa:

```java
assertThat(carrinho.total()).isEqualByComparingTo("609.70");
```

Repare que o esperado pode ser escrito como texto. Quando o valor está errado, a mensagem é a mesma de sempre:

```text
expected: 600
 but was: 609.70
```

## Coleções

É nas coleções que o AssertJ mais se destaca. O `hasSize` mostra a lista inteira quando falha:

```text
Expected size: 3 but was: 2 in:
[Item[produto=Teclado mecânico, precoUnitario=349.90, quantidade=1],
    Item[produto=Mouse sem fio, precoUnitario=129.90, quantidade=2]]
```

O `extracting` transforma cada elemento antes de verificar, sem laço nenhum no teste. O `containsExactly` exige os mesmos elementos, na mesma ordem, e aponta cada diferença:

```java
assertThat(carrinho.itens())
        .extracting(Carrinho.Item::produto)
        .containsExactly("Mouse sem fio", "Teclado mecânico");
```

```text
Expecting actual:
  ["Teclado mecânico", "Mouse sem fio"]
to contain exactly (and in same order):
  ["Mouse sem fio", "Teclado mecânico"]
but there were differences at these indexes:
  - element at index 0: expected "Mouse sem fio" but was "Teclado mecânico"
  - element at index 1: expected "Teclado mecânico" but was "Mouse sem fio"
```

Se a ordem não importa, `containsExactlyInAnyOrder`; se só alguns elementos importam, `contains`. Para verificar vários campos de uma vez, o `extracting` aceita mais de uma função e compara com tuplas:

```java
assertThat(carrinho.itens())
        .extracting(Carrinho.Item::produto, Carrinho.Item::quantidade)
        .containsExactly(tuple("Teclado mecânico", 1), tuple("Mouse sem fio", 3));
```

```text
Expecting actual:
  [("Teclado mecânico", 1), ("Mouse sem fio", 2)]
to contain exactly (and in same order):
  [("Teclado mecânico", 1), ("Mouse sem fio", 3)]
but some elements were not found:
  [("Mouse sem fio", 3)]
and others were not expected:
  [("Mouse sem fio", 2)]
```

Outras úteis: `isEmpty`, `doesNotContain`, `allSatisfy` (cada elemento passa por um bloco de asserções), `anyMatch` e `filteredOn`, que filtra antes de verificar.

## Exceções

O `assertThatThrownBy` executa o código e devolve asserções sobre a exceção:

```java
assertThatThrownBy(() -> carrinho.totalComCupom("NATAL"))
        .isInstanceOf(IllegalArgumentException.class)
        .hasMessage("cupom inexistente: NATAL");
```

```text
Expecting message to be:
  "cupom inexistente: NATAL"
but was:
  "cupom inválido: NATAL"

Throwable that failed the check:

java.lang.IllegalArgumentException: cupom inválido: NATAL
	at br.com.javaflix.loja.Carrinho.totalComCupom(Carrinho.java:44)
	...
```

A mensagem traz até a pilha da exceção real. Se nada for lançado, a falha é `Expecting code to raise a throwable.` Para as exceções mais comuns, há uma forma que se lê como uma frase: `assertThatIllegalArgumentException().isThrownBy(() -> ...).withMessage("...")`.

## Optional, texto e contexto

```java
Optional<String> nome = clientes.nomePorEmail("ana@exemplo.com");

assertThat(nome).contains("Ana");
```

```text
Expecting Optional to contain:
  "Ana"
but was empty.
```

Para dar contexto a uma asserção cujo valor não explica nada sozinho, como um booleano, o `as` acrescenta uma descrição, que aparece entre colchetes:

```java
assertThat(carrinho.vazio()).as("carrinho com %d itens", carrinho.itens().size()).isTrue();
```

```text
[carrinho com 2 itens] 
Expecting value to be true but was false
```

O `as` precisa vir **antes** da asserção: depois dela, a verificação já aconteceu.

## Comparação campo a campo

Um cliente salvo ganha um id que o teste não sabe de antemão. Comparar com `equals` falharia por causa dele. A comparação recursiva compara campo por campo, entrando nos objetos internos, e pode ignorar campos:

```java
assertThat(salvo).usingRecursiveComparison().ignoringFields("id").isEqualTo(esperado);
```

```text
Expecting actual:
  Cliente[id=42, nome=Ana Lima, email=ana.lima@exemplo.com, tags=[vip]]
to be equal to:
  Cliente[id=null, nome=Ana Lima, email=ana@exemplo.com, tags=[vip]]
when recursively comparing field by field, but found the following difference:

field/property 'email' differ:
- actual value  : "ana.lima@exemplo.com"
- expected value: "ana@exemplo.com"
```

A mensagem continua, descrevendo a configuração usada na comparação. É a forma de comparar uma entidade com um DTO, ou objetos que não implementam `equals`.

## Várias falhas de uma vez

Uma asserção que falha interrompe o teste, e as seguintes nem rodam. Quando se quer o diagnóstico completo, as **asserções suaves** guardam as falhas e só reclamam no fim:

```java
SoftAssertions soft = new SoftAssertions();
soft.assertThat(carrinho.itens()).hasSize(3);
soft.assertThat(carrinho.total()).isEqualByComparingTo("600");
soft.assertThat(carrinho.vazio()).isFalse();
soft.assertAll();
```

```text
Multiple Failures (2 failures)
-- failure 1 --
Expected size: 3 but was: 2 in:
[Item[produto=Teclado mecânico, precoUnitario=349.90, quantidade=1],
    Item[produto=Mouse sem fio, precoUnitario=129.90, quantidade=2]]
at Mensagens.lambda$main$15(Mensagens.java:55)
-- failure 2 --
expected: 600
 but was: 609.70
at Mensagens.lambda$main$15(Mensagens.java:56)
```

Cada falha vem com a linha do teste onde aconteceu. Sem o `assertAll` no fim, nada é verificado. A forma `assertSoftly(soft -> { ... })` chama o `assertAll` sozinha.

> [!ATENCAO]
> `assertThat(carrinho.vazio());`, sem nenhum método depois, **não verifica nada** e passa sempre. O `assertThat` só cria o objeto de asserções; quem verifica é o método encadeado. É um erro fácil de cometer e difícil de ver, porque o teste fica verde.

## Por baixo dos panos

Uma API fluente é só um objeto cujos métodos devolvem a si mesmos, ou um objeto novo do mesmo tipo de asserção. O `extracting` é um `map` que devolve asserções sobre a lista transformada, com outro tipo genérico:

```java executar
import java.util.ArrayList;
import java.util.List;
import java.util.function.Function;

public class MiniAssertJ {
    static class ListaAssert<T> {
        private final List<T> atual;
        private String descricao = "";

        private ListaAssert(List<T> atual) {
            this.atual = atual;
        }

        static <T> ListaAssert<T> afirmarQue(List<T> atual) {
            return new ListaAssert<>(atual);
        }

        ListaAssert<T> como(String descricao) {
            this.descricao = "[" + descricao + "] ";
            return this;
        }

        ListaAssert<T> temTamanho(int esperado) {
            if (atual.size() != esperado) {
                falhar("Expected size: " + esperado + " but was: " + atual.size() + " in: " + atual);
            }
            return this;
        }

        @SafeVarargs
        final ListaAssert<T> contem(T... esperados) {
            List<T> faltando = new ArrayList<>();
            for (T e : esperados) {
                if (!atual.contains(e)) faltando.add(e);
            }
            if (!faltando.isEmpty()) {
                falhar("Expecting " + atual + " to contain " + List.of(esperados) + " but could not find " + faltando);
            }
            return this;
        }

        <R> ListaAssert<R> extraindo(Function<T, R> extrator) {
            ListaAssert<R> nova = new ListaAssert<>(atual.stream().map(extrator).toList());
            nova.descricao = descricao;
            return nova;
        }

        private void falhar(String mensagem) {
            throw new AssertionError(descricao + mensagem);
        }
    }

    record Item(String produto, int quantidade) {}

    static void tentar(Runnable afirmacao) {
        try {
            afirmacao.run();
            System.out.println("passou");
        } catch (AssertionError e) {
            System.out.println("falhou: " + e.getMessage());
        }
    }

    public static void main(String[] args) {
        List<Item> itens = List.of(new Item("Teclado mecânico", 1), new Item("Mouse sem fio", 2));

        tentar(() -> ListaAssert.afirmarQue(itens).temTamanho(2).extraindo(Item::produto).contem("Mouse sem fio"));
        tentar(() -> ListaAssert.afirmarQue(itens).como("itens do carrinho").extraindo(Item::produto).contem("Headset", "Mouse sem fio"));
        tentar(() -> ListaAssert.afirmarQue(itens).extraindo(Item::quantidade).temTamanho(3));
    }
}
```

```saida
passou
falhou: [itens do carrinho] Expecting [Teclado mecânico, Mouse sem fio] to contain [Headset, Mouse sem fio] but could not find [Headset]
falhou: Expected size: 3 but was: 2 in: [1, 2]
```

O `extraindo(Item::produto)` transformou um `ListaAssert<Item>` num `ListaAssert<String>`, e por isso o `contem` seguinte aceita textos e o compilador recusaria um número. A descrição acompanha a transformação. O AssertJ real tem uma classe de asserções para cada tipo do JDK, e o `assertThat` é sobrecarregado: o compilador escolhe a versão pelo tipo do argumento, e é isso que faz o autocompletar mostrar `startsWith` para textos e `hasSize` para listas. As asserções suaves vão além: o `soft.assertThat` devolve um *proxy* gerado em tempo de execução com a biblioteca ByteBuddy, que intercepta cada asserção e guarda a falha em vez de lançá-la.

## Resumo

- `assertThat(atual)` e uma cadeia de verificações; mensagens que mostram o valor real
- `isEqualByComparingTo` para `BigDecimal`, sem a armadilha da escala
- Coleções: `hasSize`, `contains`, `containsExactly`, `containsExactlyInAnyOrder`, `extracting` com tuplas
- Exceções com `assertThatThrownBy(...).isInstanceOf(...).hasMessage(...)`
- `usingRecursiveComparison().ignoringFields("id")` compara campo a campo
- `as(...)` antes da asserção dá contexto; `SoftAssertions` junta várias falhas
- `assertThat(x)` sozinho não verifica nada
