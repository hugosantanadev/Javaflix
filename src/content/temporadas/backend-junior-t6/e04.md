Os testes com mocks do [episódio anterior](/assistir/backend-junior-t6-e03) provam que a lógica do serviço está certa, mas não sabem nada do que acontece em volta dela. A rota está mapeada no caminho certo? O JSON sai com os nomes esperados? A validação recusa um nome em branco? A consulta do repositório funciona no banco? Um produto inexistente vira 404 ou 500? Essas perguntas só se respondem com o Spring de verdade rodando, nos **testes de integração**. O Spring Boot tem um suporte completo para eles, e tudo deste episódio saiu de execuções reais com o Spring Boot 4.1 e a API de produtos da loja.

> [!ANTES]
> Nas aplicações Java corporativas dos anos 2000, testar um controller ou uma consulta exigia empacotar a aplicação, implantá-la num servidor de aplicação, esperar minutos pela subida e clicar nas telas. Por isso, quase ninguém testava essas camadas automaticamente. O módulo de testes do Spring passou a subir o contexto dentro do próprio JUnit, e o Spring Boot acrescentou as fatias, que sobem só a parte que interessa.

## Três tamanhos de teste

| Anotação | O que sobe | Para testar |
|---|---|---|
| `@WebMvcTest` | Controllers, tratadores de erro, JSON e validação | A camada web, com os serviços mockados |
| `@DataJpaTest` | Entidades, repositórios e um banco em memória | Consultas e mapeamentos |
| `@SpringBootTest` | A aplicação inteira | O fluxo completo, ponta a ponta |

As duas primeiras são **fatias** (*slices*): sobem só uma parte da aplicação, e por isso são mais rápidas e mais focadas. No Spring Boot 4, as fatias ficam em módulos de teste próprios, que entram com o `spring-boot-starter-webmvc-test` e o `spring-boot-starter-data-jpa-test`.

## A camada web com MockMvc

```java
@WebMvcTest(ProdutoController.class)
class ProdutoControllerTest {

    @Autowired
    MockMvc mvc;

    @MockitoBean
    ProdutoService service;

    @Test
    void buscaUmProduto() throws Exception {
        when(service.buscar(1L)).thenReturn(new ProdutoResposta(1L, "Teclado mecânico", new BigDecimal("349.90")));

        mvc.perform(get("/produtos/1"))
                .andDo(print())
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.nome").value("Teclado mecânico"))
                .andExpect(jsonPath("$.preco").value(349.90));
    }
```

O `MockMvc` executa a requisição por todo o caminho do Spring MVC, o mesmo do [episódio do DispatcherServlet](/assistir/backend-junior-t4-e03): roteamento, conversão do JSON, validação e tratadores de erro. Só não há rede: não sobe servidor nem abre porta. O `@MockitoBean` coloca um mock do Mockito no contexto do Spring, no lugar do serviço real. Ele vem do próprio Spring Framework e substitui o antigo `@MockBean`, que não existe mais no Spring Boot 4. O `print()` mostra a troca completa:

```text

      HTTP Method = GET
      Request URI = /produtos/1
       Parameters = {}
          Headers = []
             Body = null
    Session Attrs = {}

Handler:
             Type = br.com.javaflix.loja.ProdutoController
           Method = br.com.javaflix.loja.ProdutoController#buscar(long)
...
```

Os casos de erro são onde esses testes mais valem:

```java
@Test
void produtoInexistenteDa404() throws Exception {
    when(service.buscar(99L)).thenThrow(new ProdutoNaoEncontradoException(99L));

    mvc.perform(get("/produtos/99"))
            .andExpect(status().isNotFound())
            .andExpect(jsonPath("$.detail").value("produto 99 não encontrado"));
}

@Test
void nomeEmBrancoDa400() throws Exception {
    mvc.perform(post("/produtos")
                    .contentType(MediaType.APPLICATION_JSON)
                    .content("""
                            {"nome": "", "preco": 10}
                            """))
            .andExpect(status().isBadRequest());

    verifyNoInteractions(service);
}
```

O segundo teste prova que a validação do `@Valid` barrou a requisição antes de chegar ao serviço.

## Uma fatia é só uma fatia

O `@WebMvcTest` não sobe serviços nem repositórios. Sem o `@MockitoBean`, o contexto nem carrega:

```text
***************************
APPLICATION FAILED TO START
***************************

Description:

Parameter 0 of constructor in br.com.javaflix.loja.ProdutoController required a bean of type 'br.com.javaflix.loja.ProdutoService' that could not be found.
```

É o comportamento esperado: a fatia web testa a camada web, e o que está fora dela precisa ser mockado.

> [!PENSE]
> Se o `@SpringBootTest` sobe tudo e testa mais, por que não usá-lo em todos os testes? Pense no que acontece com uma suíte de 300 testes que sobem a aplicação inteira, e no que cada falha consegue dizer sobre onde está o problema.

## MockMvcTester: o MockMvc com AssertJ

O Spring Framework 6.2 trouxe uma versão do `MockMvc` com asserções do AssertJ, que as fatias do Spring Boot já configuram:

```java
@Autowired
MockMvcTester mvc;

@Test
void buscaComAssertJ() {
    when(service.buscar(1L)).thenReturn(new ProdutoResposta(1L, "Teclado mecânico", new BigDecimal("349.90")));

    assertThat(mvc.get().uri("/produtos/1"))
            .hasStatusOk()
            .bodyJson()
            .extractingPath("$.nome").isEqualTo("Teclado mecânico");
}
```

Sem `throws Exception` e com as mensagens do [episódio de AssertJ](/assistir/backend-junior-t6-e02):

```text

```

## Repositórios com @DataJpaTest

```java
@DataJpaTest
class ProdutoRepositoryTest {

    @Autowired
    ProdutoRepository produtos;

    @Test
    void buscaPorTrechoDoNome() {
        produtos.save(new Produto("Mouse sem fio", new BigDecimal("129.90")));
        produtos.save(new Produto("Teclado mecânico", new BigDecimal("349.90")));
        produtos.save(new Produto("Monitor 27", new BigDecimal("1899.00")));

        assertThat(produtos.findByNomeContainingIgnoreCaseOrderByNome("MO"))
                .extracting(Produto::getNome)
                .containsExactly("Monitor 27", "Mouse sem fio");
    }

    @Test
    void cadaTesteComecaComOBancoVazio() {
        assertThat(produtos.count()).isZero();
    }
}
```

A fatia sobe o JPA, os repositórios e um banco em memória, trocando o banco configurado pelo H2, e mostra o SQL:


Cada teste roda numa transação que é **desfeita no fim**. Com o log de transações de teste ligado:


Por isso o segundo teste encontra a tabela vazia. Só os ids não voltam: num teste seguinte, o próximo produto ganhou o id 2, e não 1, porque as sequências e colunas de identidade do banco não participam da transação. Nunca escreva um teste que espere um id fixo.

> [!LAPIS]
> Numa classe `@DataJpaTest`, o teste A salva dois produtos e o teste B salva um. Rodando A e depois B, qual é o id do produto de B, e quantas linhas `produtos.count()` devolve no fim de B?
>
> **Resposta:** O id é **3**, porque a sequência continuou depois dos dois de A, mesmo com o rollback. O `count()` devolve **1**: as linhas de A foram desfeitas, e só a de B existe dentro da transação dele.

## A aplicação inteira, com servidor de verdade

O `@SpringBootTest` sobe tudo. Com `webEnvironment = RANDOM_PORT`, sobe também o Tomcat, numa porta livre qualquer, e o teste conversa com ele por HTTP de verdade. O `RestTestClient`, novo no Spring Framework 7, faz as requisições:

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureRestTestClient
class LojaIntegracaoTest {

    @Autowired
    RestTestClient client;

    @Test
    void criaEBuscaPeloHttp() {
        ProdutoResposta criado = client.post().uri("/produtos")
                .contentType(MediaType.APPLICATION_JSON)
                .body(new NovoProduto("Headset", new BigDecimal("259.90")))
                .exchange()
                .expectStatus().isCreated()
                .expectHeader().location("/produtos/1")
                .expectBody(ProdutoResposta.class)
                .returnResult()
                .getResponseBody();

        client.get().uri("/produtos/{id}", criado.id())
                .exchange()
                .expectStatus().isOk()
                .expectBody()
                .jsonPath("$.nome").isEqualTo("Headset");
    }
```

```text
Tomcat started on port 49914 (http) with context path '/'
Started LojaIntegracaoTest in 3.352 seconds (process running for 5.382)
```

Aqui não há transação de teste para desfazer: a requisição é atendida por outra *thread*, a do Tomcat, que faz e confirma a própria transação. Um segundo teste da mesma classe encontrou o produto do primeiro:

```text
produtos no banco: 1
```

Testes assim precisam limpar o que criam, com um `@BeforeEach` que apaga as tabelas, ou não depender do estado do banco.

> [!PERGUNTAS]
> **P:** Preciso de `@SpringBootTest` para testar um serviço?
>
> **R:** Quase nunca. Um serviço com as dependências no construtor se testa com o Mockito, em milissegundos, como no [episódio anterior](/assistir/backend-junior-t6-e03).
>
> **P:** O H2 basta para testar as consultas?
>
> **R:** Para consultas simples, ajuda. Mas funções, tipos e índices do PostgreSQL ou do MySQL não existem no H2, e uma consulta pode passar nele e falhar em produção. O [próximo episódio](/assistir/backend-junior-t6-e05) usa o banco de verdade.
>
> **P:** Colocar `@Transactional` no teste com `RANDOM_PORT` resolve a limpeza?
>
> **R:** Não: a requisição é atendida por outra thread, com outra transação, já confirmada. Limpe as tabelas num `@BeforeEach`.

## O cache de contextos

Subir a aplicação inteira levou 3,3 segundos; a fatia web, 0,4. Com centenas de testes, subir um contexto por classe seria inviável, e por isso o Spring **guarda os contextos** e reaproveita entre classes de teste com a mesma configuração. Na execução da aula, a segunda classe de testes do controller nem aparece com "Started": usou o contexto da primeira. No fim, cinco classes de teste tinham criado três contextos:

```text
Spring test ApplicationContext cache statistics: [DefaultContextCache@d919544 size = 3, maxSize = 32, ...]
```

Qualquer diferença na configuração cria um contexto novo: outro conjunto de `@MockitoBean`, outras propriedades, outros perfis. Padronizar a configuração dos testes de integração é a forma mais simples de deixar a suíte rápida. E o `@DirtiesContext`, que descarta o contexto depois do teste, deve ser raro.

> [!MATEMATICA]
> O preço de um contexto novo: se a aplicação leva 3,3 segundos para subir, 40 classes `@SpringBootTest` com 40 configurações diferentes gastam 40 × 3,3 = **132 segundos** só em subidas. Padronizadas em 5 configurações, são 5 × 3,3 = **16,5 segundos**, e os outros 35 reaproveitam o que já existe. Cada `@MockitoBean` diferente, cada propriedade a mais e cada `@DirtiesContext` acrescenta uma subida.

> [!ATENCAO]
> Um `application.properties` em `src/test/resources` **substitui** o de `src/main/resources`, em vez de complementar: os dois têm o mesmo nome no *classpath*, e o de teste vem primeiro. Na aula, um arquivo de teste com duas linhas de log fez o banner do Spring, desligado no arquivo principal, voltar a aparecer. Para ajustar só algumas propriedades nos testes, use um perfil (`application-test.properties` com `@ActiveProfiles("test")`) ou o atributo `properties` do `@SpringBootTest`.

> [!ERRO]
> Usar `@SpringBootTest` em todo teste, até nos de uma regra de cálculo, e acrescentar um `@MockitoBean` diferente em cada classe. A suíte fica lenta, os contextos não se reaproveitam, e o time passa a rodar os testes só no servidor. Teste regras com JUnit puro, a web com `@WebMvcTest`, as consultas com `@DataJpaTest` e reserve o `@SpringBootTest` para alguns fluxos completos.

> [!IA]
> Peça um teste de controller a uma IA e ela costuma gerar um `@SpringBootTest` com `@MockBean`, que não existe mais no Spring Boot 4. Diga a versão do Spring Boot, peça `@WebMvcTest` com `@MockitoBean` e `MockMvcTester`, e confira no log quantos contextos a suíte subiu.

## Na IDE

- **Rodar uma fatia.** No IntelliJ, o ícone ao lado da classe `@WebMvcTest` roda só ela; o console mostra o tempo de subida do contexto, um bom indicador de configuração exagerada.
- **Requisições HTTP.** O cliente HTTP da IDE, em arquivos `.http`, chama a aplicação rodando localmente para comparar com o que os testes fazem.
- **Ver o cache.** Com `logging.level.org.springframework.test.context.cache=DEBUG`, o console mostra as estatísticas do cache de contextos.

## Por baixo dos panos

O cache de contextos é um mapa cuja chave é a configuração do teste, e é por isso que configurações iguais reaproveitam e qualquer diferença cria outro. Com um `record` como chave, a igualdade vem de graça:

```java executar
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Set;

public class CacheDeContextos {
    /** O que o Spring compara para decidir se dois testes podem dividir o mesmo contexto. */
    record Configuracao(String tipo, Set<String> mocks, Map<String, String> propriedades) {}

    record ClasseDeTeste(String nome, Configuracao configuracao) {}

    static int contextosCriados = 0;

    public static void main(String[] args) {
        Configuracao webProduto = new Configuracao("@WebMvcTest(ProdutoController)", Set.of("ProdutoService"), Map.of());
        List<ClasseDeTeste> classes = List.of(
                new ClasseDeTeste("ProdutoControllerTest", webProduto),
                new ClasseDeTeste("ProdutoControllerTesterTest", webProduto),
                new ClasseDeTeste("ProdutoRepositoryTest", new Configuracao("@DataJpaTest", Set.of(), Map.of())),
                new ClasseDeTeste("LojaIntegracaoTest", new Configuracao("@SpringBootTest", Set.of(), Map.of())),
                new ClasseDeTeste("CheckoutIntegracaoTest", new Configuracao("@SpringBootTest", Set.of(), Map.of())),
                new ClasseDeTeste("EmailIntegracaoTest", new Configuracao("@SpringBootTest", Set.of("Notificador"), Map.of())),
                new ClasseDeTeste("FreteIntegracaoTest",
                        new Configuracao("@SpringBootTest", Set.of(), Map.of("loja.frete.gratis-a-partir-de", "300"))));

        Map<Configuracao, Integer> cache = new HashMap<>();
        for (ClasseDeTeste classe : classes) {
            boolean novo = !cache.containsKey(classe.configuracao()); //> Configurações iguais são records iguais: mesmo contexto.
            int contexto = cache.computeIfAbsent(classe.configuracao(), c -> ++contextosCriados); //> Só sobe um contexto quando a chave é nova.
            System.out.printf("%-28s contexto %d %s%n", classe.nome(), contexto, novo ? "(criado)" : "(reaproveitado)");
        }
        System.out.println(classes.size() + " classes de teste, " + contextosCriados + " contextos criados");
    }
}
```

```saida
ProdutoControllerTest        contexto 1 (criado)
ProdutoControllerTesterTest  contexto 1 (reaproveitado)
ProdutoRepositoryTest        contexto 2 (criado)
LojaIntegracaoTest           contexto 3 (criado)
CheckoutIntegracaoTest       contexto 3 (reaproveitado)
EmailIntegracaoTest          contexto 4 (criado)
FreteIntegracaoTest          contexto 5 (criado)
7 classes de teste, 5 contextos criados
```

Um único `@MockitoBean Notificador` ou uma propriedade diferente bastaram para pagar uma subida inteira a mais. A chave real, a `MergedContextConfiguration`, tem bem mais campos: classes de configuração, inicializadores, perfis ativos, fontes de propriedades e os personalizadores, entre eles o que registra os `@MockitoBean`. O cache guarda até 32 contextos por padrão e descarta o usado há mais tempo quando enche. E ele vive dentro de uma JVM: rodar os testes em JVMs separadas multiplica as subidas.

## Resumo

- Testes de integração rodam o Spring de verdade: rotas, JSON, validação, consultas
- `@WebMvcTest` com `MockMvc` ou `MockMvcTester`, e `@MockitoBean` para o que está fora da fatia
- `@DataJpaTest` sobe JPA e um banco em memória, com rollback no fim de cada teste
- `@SpringBootTest(webEnvironment = RANDOM_PORT)` com `RestTestClient` testa por HTTP; aí não há rollback
- Ids gerados não voltam com o rollback: não espere ids fixos
- O cache reaproveita contextos de configuração igual; padronize a configuração dos testes
- `application.properties` de teste substitui o principal; prefira perfis ou `properties`
