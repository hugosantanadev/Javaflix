O [episódio anterior](/assistir/backend-junior-t8-e01) mostrou que o modelo continua o texto que recebe. A consequência prática é direta: **a resposta só pode ser tão boa quanto o pedido**. Engenharia de prompt não é decorar frases mágicas. É escrever o pedido como você escreveria um chamado para um colega competente que nunca viu o seu projeto: com o contexto, a tarefa, os limites e um jeito de saber se deu certo. Cada aula deste site traz um pedido de exemplo no quadro "IA na prática"; aqui você aprende a montar os seus.

## As cinco partes

![Cinco blocos empilhados: contexto, tarefa, restrições, formato e verificação, cada um com uma frase de exemplo ao lado](/figuras/anatomia-do-pedido.svg "As cinco partes de um pedido; as restrições, em laranja, são as mais esquecidas.")

Compare dois pedidos para o mesmo problema:

```text
Fraco:
  Meu teste não funciona, me ajuda?

Bom:
  Projeto em Java 25 com Spring Boot 4.1 e JUnit 6.
  Este teste com @WebMvcTest falha ao subir o contexto com o erro abaixo.
  <cole o teste, o controller e a mensagem de erro inteira>
  Explique a causa e mostre só as linhas que mudam no teste.
  Não suba @SpringBootTest e não altere o controller.
  Diga como confirmo que o contexto sobe só com a fatia web.
```

O primeiro obriga o modelo a adivinhar a versão, o código e o erro, e ele vai adivinhar o mais provável, que é o caso mais comum dos textos de treino, não o seu. O segundo deixa pouco para adivinhar.

> [!PENSE]
> No pedido bom, qual frase impede a "solução" mais comum e errada para esse erro? O que aconteceria sem ela?

## Contexto: o que ele não vê

O assistente não conhece o seu projeto, a menos que alguém mande os arquivos. Os itens que mais mudam a resposta, em ordem:

1. **Versões.** Java, Spring Boot, bibliotecas. Uma linha que evita metade das alucinações do episódio anterior.
2. **O código envolvido**, não o projeto inteiro: a classe, a interface que ela usa, o teste.
3. **A mensagem de erro inteira**, com o *stack trace*, e não "dá erro de nulo".
4. **O que você já tentou**, para ele não sugerir de novo.

Um pedido também pode vir com **exemplos** do que você espera (*few-shot*). Dois pares de entrada e saída ensinam o formato melhor que um parágrafo de explicação:

```text
Converta as mensagens de commit para o padrão do projeto.
Exemplos:
  "arrumei o calculo do frete"    -> "fix(frete): corrige cálculo na fronteira de 200"
  "tela nova de pedidos"          -> "feat(pedidos): adiciona listagem paginada"
Agora:
  "coloquei trava no cancelamento"
```

## Restrições: segurança e manutenção

É a parte que separa um pedido de júnior de um de profissional. Sem restrições, o modelo resolve o problema pelo caminho mais curto, que muitas vezes é o mais inseguro ou o que quebra o resto do projeto. As de sempre:

- **Segurança:** "nada de concatenar SQL", "não logue dados pessoais", "não ponha senhas no código".
- **Padrões do projeto:** "use `BigDecimal` para dinheiro", "DTOs em record", "exceções de negócio estendem `RegraDeNegocioException`".
- **Escopo:** "não altere a interface pública", "não acrescente dependências".

> [!ERRO]
> Pedir "corrija o erro" sem restrições e aceitar a correção que **desliga** a verificação: `@SuppressWarnings`, um `catch (Exception e) {}`, um `@Disabled` no teste que falhava, ou `spring.flyway.validate-on-migrate=false`. O erro some, e o problema continua lá, agora escondido.

## Formato e verificação

Peça a resposta num formato que você consiga conferir rápido: "só o diff", "uma tabela com causa, correção e risco", "JSON com os campos X e Y". Quando a resposta vai ser lida por um programa, o formato é obrigatório, e o seu código precisa **validar** o que chegou, como validaria a entrada de qualquer usuário:

```java executar
import java.util.ArrayList;
import java.util.List;

public class ValidarResposta {
    record Item(String sku, int quantidade) {}

    static List<Item> ler(String resposta, List<String> erros) {
        List<Item> itens = new ArrayList<>();
        for (String linha : resposta.strip().split("\n")) {
            String[] p = linha.split(";");
            if (p.length != 2 || !p[0].matches("[A-Z0-9-]+")) { //> Formato combinado: SKU;quantidade.
                erros.add("formato: " + linha);
                continue;
            }
            try {
                int q = Integer.parseInt(p[1].strip());
                if (q <= 0) erros.add("quantidade: " + linha);
                else itens.add(new Item(p[0], q));
            } catch (NumberFormatException e) {
                erros.add("número: " + linha); //> O modelo escreveu "dois" em vez de 2.
            }
        }
        return itens;
    }

    public static void main(String[] args) {
        String doModelo = """
                CANECA;3
                CAFE-500G;dois
                Aqui está a lista que você pediu!
                FONE;0
                """;
        List<String> erros = new ArrayList<>();
        System.out.println(ler(doModelo, erros));
        erros.forEach(System.out::println);
    }
}
```

```saida
[Item[sku=CANECA, quantidade=3]]
número: CAFE-500G;dois
formato: Aqui está a lista que você pediu!
quantidade: FONE;0
```

Uma linha de cortesia no meio dos dados, um número por extenso: o modelo segue o formato **quase** sempre. Quase não serve para um programa, e por isso a resposta é tratada como entrada não confiável.

> [!MATEMATICA]
> Se o modelo segue o formato em 98% das respostas e o seu sistema faz 5.000 chamadas por dia, são 5.000 × 0,02 = **100 respostas fora do formato por dia**. Sem validação, são 100 erros silenciosos; com validação e uma nova tentativa, a chance de errar duas vezes seguidas cai para 0,02 × 0,02 = 0,0004, umas **2 por dia**, que podem ir para revisão humana.

> [!CONVERSA]
> **Pedido vago:** Eu só disse "melhore este método". Ele me devolveu tudo reescrito, com outro nome e uma biblioteca nova.
>
> **Pedido completo:** Você não disse o que era "melhor". Ele escolheu o que é mais comum nos textos dele.
>
> **Pedido vago:** E como você evita isso?
>
> **Pedido completo:** Eu digo o que é melhor ("legível, sem mudar a assinatura"), o que não pode mudar e como vou conferir ("os testes atuais continuam passando"). Sobra pouco para ele inventar.

## Iterar, em vez de acertar de primeira

Para tarefas maiores, peça **o plano antes do código**: "liste os passos e os arquivos que você mudaria, sem escrever código ainda". Você corrige o plano, que é curto, antes de ler 300 linhas que partiram de uma premissa errada. Depois, peça um passo de cada vez, rodando os testes entre um e outro.

E quando a resposta vier errada, **diga o que deu errado**, com a saída real: "o teste falhou com esta mensagem". O modelo não roda o seu código; a saída do compilador e dos testes é o contexto que ele precisa para acertar a próxima.

> [!PERGUNTAS]
> **P:** Preciso escrever tudo isso a cada pergunta?
>
> **R:** Para perguntas rápidas, não. Para tarefas que viram código no projeto, sim, e vale guardar um modelo de pedido. Muitos assistentes leem um arquivo de instruções do projeto, como o `CLAUDE.md` deste site, com as versões e os padrões, para você não repetir.
>
> **P:** Pedir "aja como um especialista sênior" ajuda?
>
> **R:** Pouco. O que ajuda é dar o que um sênior teria: o contexto, os padrões e os critérios. O papel sozinho não acrescenta informação.
>
> **P:** Em português ou em inglês?
>
> **R:** Os modelos atuais entendem bem os dois. Escreva na língua em que você descreve melhor o problema; nomes de classes e mensagens de erro, deixe como estão.

> [!ANTES]
> Antes dos assistentes, a habilidade equivalente era **perguntar bem no Stack Overflow**: versão, código mínimo que reproduz o erro, o que já foi tentado, o resultado esperado e o obtido. Pedidos sem isso eram fechados em minutos. As regras de um bom pedido à IA são praticamente as mesmas, e pelo mesmo motivo: quem responde não está vendo a sua tela.

## Por baixo dos panos

Para o modelo, o seu pedido é só o começo de um texto. Antes dele, o serviço acrescenta um **prompt de sistema**, instruções do fornecedor ou do aplicativo, e às vezes os arquivos do projeto. Tudo vira uma sequência de tokens, e a resposta é a continuação mais provável dessa sequência inteira. Por isso a forma importa: um pedido que parece um bom chamado técnico puxa a continuação para o tipo de resposta que costuma seguir bons chamados técnicos nos textos de treino. Montar o pedido com um modelo fixo, como uma classe faria, deixa essa forma estável:

```java executar
import java.util.List;

public class Pedido {
    record PedidoIA(String contexto, String tarefa, List<String> restricoes, String formato, String verificacao) {
        String texto() {
            StringBuilder sb = new StringBuilder();
            sb.append("Contexto: ").append(contexto).append('\n');
            sb.append("Tarefa: ").append(tarefa).append('\n');
            restricoes.forEach(r -> sb.append("- Não ").append(r).append('\n')); //> Cada restrição numa linha.
            sb.append("Formato: ").append(formato).append('\n');
            return sb.append("Como conferir: ").append(verificacao).toString();
        }
    }

    public static void main(String[] args) {
        System.out.println(new PedidoIA(
                "Java 25, Spring Boot 4.1; PedidoService abaixo",
                "escreva os testes de unidade de cancelar()",
                List.of("use @SpringBootTest", "acrescente dependências"),
                "um arquivo de teste completo",
                "cada transição proibida tem um teste que espera 409").texto());
    }
}
```

```saida
Contexto: Java 25, Spring Boot 4.1; PedidoService abaixo
Tarefa: escreva os testes de unidade de cancelar()
- Não use @SpringBootTest
- Não acrescente dependências
Formato: um arquivo de teste completo
Como conferir: cada transição proibida tem um teste que espera 409
```

Para a base de como um texto vira uma sequência e uma sequência vira estatística, volte ao [episódio anterior](/assistir/backend-junior-t8-e01); para o lado formal das gramáticas e dos formatos que um programa consegue validar, veja [compiladores por dentro](/assistir/aprendiz-t2-e03).

> [!IA]
> Peça ao assistente para **criticar o seu pedido** antes de executá-lo: "que informação falta neste pedido para você responder sem adivinhar?". Ele costuma apontar a versão ausente, o trecho de código que falta e o critério de pronto. É um jeito rápido de treinar o olho para as cinco partes.

## Na IDE

- **Instruções do projeto.** Assistentes como o Claude Code leem um `CLAUDE.md` na raiz; o GitHub Copilot lê `.github/copilot-instructions.md`. Versões, padrões e comandos ficam ali uma vez só.
- **Contexto por seleção.** Selecionar o trecho antes de perguntar manda exatamente aquele código, em vez do arquivo inteiro.
- **Modelos de pedido.** *Live Templates* do IntelliJ guardam o esqueleto das cinco partes, com os campos para preencher.

## Resumo

- Um bom pedido tem contexto, tarefa, restrições, formato e verificação.
- Versões, o código envolvido e o erro inteiro são o contexto que mais muda a resposta.
- Restrições de segurança, de padrões e de escopo evitam a solução mais curta e errada.
- Resposta lida por programa é entrada não confiável: valide o formato.
- Para tarefas grandes, peça o plano antes do código e itere com a saída real dos testes.
