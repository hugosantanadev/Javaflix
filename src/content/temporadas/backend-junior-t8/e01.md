Desde o Estagiário, toda aula deste site tem um quadro "IA na prática" e uma seção sobre como pedir e conferir. Esta temporada explica **por que** essas regras existem. Para usar bem um assistente de código, você não precisa saber treinar um modelo, mas precisa entender o que ele faz por dentro: prever o próximo pedaço de texto. Quase todo erro da IA que você já viu nas aulas, da anotação que não existe mais ao método inventado, sai daí.

## Tokens: os pedaços de texto

O modelo não lê letras nem palavras: lê **tokens**, pedaços de texto de tamanho variável, escolhidos para que os trechos comuns virem um token só. `public` costuma ser um token; `Pedido` talvez dois; uma palavra rara em português, três ou quatro. O espaço normalmente vai grudado no início da palavra seguinte.

O jeito mais usado de montar esse vocabulário é o **BPE** (*byte pair encoding*): começa com caracteres soltos e funde, repetidamente, o par vizinho mais frequente. O programa abaixo faz três fusões num texto pequeno:

```java executar
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

public class Bpe {
    public static void main(String[] args) {
        List<String> tokens = new ArrayList<>(List.of("p,e,d,i,d,o,_,p,e,d,i,r,_,p,e,d,a,l".split(",")));
        for (int rodada = 1; rodada <= 3; rodada++) {
            Map<String, Integer> pares = new HashMap<>();
            for (int i = 0; i + 1 < tokens.size(); i++) {
                pares.merge(tokens.get(i) + "|" + tokens.get(i + 1), 1, Integer::sum); //> Conta cada par de vizinhos.
            }
            String melhor = pares.entrySet().stream()
                    .max(Map.Entry.<String, Integer>comparingByValue().thenComparing(Map.Entry.comparingByKey()))
                    .get().getKey();
            String[] ab = melhor.split("[|]");
            List<String> novos = new ArrayList<>();
            for (int i = 0; i < tokens.size(); i++) {
                if (i + 1 < tokens.size() && tokens.get(i).equals(ab[0]) && tokens.get(i + 1).equals(ab[1])) {
                    novos.add(ab[0] + ab[1]);
                    i++;
                } else {
                    novos.add(tokens.get(i));
                }
            }
            tokens = novos;
            System.out.println("fusão " + rodada + ": " + ab[0] + ab[1] + " -> " + tokens.size() + " tokens");
        }
        System.out.println(tokens);
    }
}
```

```saida
fusão 1: pe -> 15 tokens
fusão 2: ped -> 12 tokens
fusão 3: pedi -> 10 tokens
[pedi, d, o, _, pedi, r, _, ped, a, l]
```

Com milhões de fusões sobre bilhões de textos, o vocabulário final tem de 50 a 200 mil tokens. Como a maior parte do texto de treino é em inglês, o português e os nomes do seu domínio quebram em mais pedaços.

> [!MATEMATICA]
> Em média, um token de texto em inglês tem uns 4 caracteres; em português, perto de 3. Uma classe Java de 300 linhas, com uns 12.000 caracteres, ocupa por volta de 3.000 a 4.000 tokens. Uma janela de contexto de 200 mil tokens comporta então umas 50 classes dessas, contando o seu pedido e a resposta. Parece muito, até você colar o log inteiro de uma aplicação: 50 MB de log são uns 15 milhões de tokens, 75 janelas.

## Prever o próximo token

Dado o contexto, o modelo calcula uma **probabilidade para cada token do vocabulário**, sorteia um, acrescenta ao texto e repete. É só isso, milhares de vezes por resposta.

![O contexto public static void entra no modelo, que dá 72% para main, 9% para run e porcentagens menores para outros tokens; o escolhido volta para o contexto](/figuras/proximo-token.svg "Cada token da resposta é um sorteio entre os prováveis, e o escolhido vira contexto do próximo.")

O modelo aprendeu essas probabilidades ajustando bilhões de números (os **parâmetros**) para acertar o próximo token em textos reais. Ninguém programou a regra "depois de `public static void` vem `main`": ela é estatística do que o modelo viu.

> [!PENSE]
> Se o modelo só sabe o que é provável depois de um contexto, o que ele responde quando você pergunta sobre uma biblioteca lançada depois do fim do treino? Ele tem como "saber que não sabe"?

## Temperatura

As probabilidades saem de números brutos (os **logits**) por uma conta chamada *softmax*. A **temperatura** divide os logits antes da conta: abaixo de 1, o mais provável fica ainda mais provável; acima de 1, as chances se espalham.

```java executar
import java.util.Arrays;

public class Temperatura {
    static double[] softmax(double[] logits, double t) {
        double[] e = Arrays.stream(logits).map(x -> Math.exp(x / t)).toArray(); //> Dividir por t antes do exp.
        double soma = Arrays.stream(e).sum();
        return Arrays.stream(e).map(x -> Math.round(x / soma * 100) / 100.0).toArray();
    }

    public static void main(String[] args) {
        double[] logits = {4.0, 2.0, 1.0}; // main, run, print
        for (double t : new double[] {0.5, 1.0, 2.0}) {
            System.out.println("t=" + t + " " + Arrays.toString(softmax(logits, t)));
        }
    }
}
```

```saida
t=0.5 [0.98, 0.02, 0.0]
t=1.0 [0.84, 0.11, 0.04]
t=2.0 [0.63, 0.23, 0.14]
```

Para código, temperatura baixa é a escolha comum: você quer o mais provável, não criatividade. Mesmo com temperatura zero, porém, a resposta não fica **certa**: fica só **repetível**. O mais provável continua podendo ser falso.

> [!PERGUNTAS]
> **P:** Então o modelo "entende" o código ou só imita?
>
> **R:** Para prever bem o próximo token em milhões de programas, ele precisou aprender padrões profundos de sintaxe, tipos e intenção. Isso funciona como entendimento na maioria dos casos, mas falha de formas que um humano não falharia, e sem avisar.
>
> **P:** Por que a mesma pergunta dá respostas diferentes?
>
> **R:** Pelo sorteio. Com temperatura acima de zero, cada execução pode seguir outro token no meio do caminho, e o resto da resposta muda junto.
>
> **P:** O modelo aprende com as minhas conversas?
>
> **R:** Não durante a conversa: os parâmetros não mudam enquanto você usa. O que muda é o contexto. Se o serviço usa seus dados para treinos futuros depende da política dele, e é assunto do último episódio da temporada.

## Contexto e corte de conhecimento

Tudo o que o modelo "sabe" numa conversa vem de duas fontes: os parâmetros, fixados no treino, e a **janela de contexto**, o texto que você manda agora. Daí duas consequências práticas:

- **Corte de conhecimento.** O treino para numa data. Uma API que mudou depois, como o `@MockBean` removido no Spring Boot 4, continua "provável" para o modelo, porque ele viu milhares de exemplos com ela.
- **Esquecimento do meio.** Contextos longos funcionam pior no meio do que nas pontas. Instruções importantes vão no começo ou no fim do pedido, não enterradas entre 2.000 linhas de código.

## Alucinação

Quando o contexto pede algo que o modelo não viu, a conta continua produzindo os tokens mais prováveis, e o resultado é um texto **plausível e falso**: um método `List.removeIf(int)`, um parâmetro de configuração com nome convincente, um link para uma página que nunca existiu. Não é mentira, porque não há intenção; é a mesma máquina que acerta, funcionando fora do que conhece.

> [!LAPIS]
> Você pede "como configurar o tempo limite do HttpClient do Java" e recebe `HttpClient.newBuilder().readTimeout(Duration.ofSeconds(5))`. Como descobrir, em menos de um minuto, se é alucinação?
>
> **Resposta:** Compile, ou abra o Javadoc de `HttpClient.Builder`. O método não existe: o *builder* do cliente tem `connectTimeout`, e o tempo da resposta se define por requisição, com `HttpRequest.Builder.timeout`. O nome inventado é plausível porque existe em outras bibliotecas, como o OkHttp.

> [!ERRO]
> Confiar mais numa resposta porque ela veio bem formatada, com explicação confiante e código limpo. O tom é sempre o mesmo, acerte ou erre: a confiança do texto não diz nada sobre a correção. Só o compilador, os testes e a documentação dizem.

> [!ANTES]
> Os assistentes de código antes de 2021 eram autocompletar estatístico de poucas palavras, treinados no seu próprio projeto, ou buscas em fóruns. O que mudou com os modelos de linguagem foi a escala: a mesma ideia de prever o próximo token, com bilhões de parâmetros e quase todo o código aberto do mundo como treino.

## Por baixo dos panos

O modelo é uma pilha de multiplicações de matrizes. Cada token vira um vetor de milhares de números (o *embedding*), e camadas de **atenção** misturam esses vetores: para cada posição, o modelo calcula o quanto cada token anterior importa e soma os vetores com esses pesos. É assim que `void` "olha" para `public static` e não para a linha de cinquenta tokens atrás. A conta de atenção compara cada token com todos os anteriores, então o custo cresce com o **quadrado** do tamanho do contexto: dobrar o texto custa umas quatro vezes mais nessa etapa. Por isso contexto longo é mais lento e mais caro, e por isso a janela tem limite. Para a base de vetores, potências e por que o quadrado cresce tão rápido, veja [potências, logaritmos e Big-O](/assistir/aprendiz-t3-e05).

> [!IA]
> O próprio assistente pode explicar tokens e temperatura, e explica bem. Use a aula como teste: pergunte a ele sobre uma API recente do Java 25, como os *gatherers*, e compare com o Javadoc. O resultado mostra, na prática, onde fica o corte de conhecimento dele.

## Na IDE

- **Ver o contexto.** Os assistentes da IDE mostram quais arquivos entraram no contexto do pedido; confira antes de perguntar sobre um código que não está ali.
- **Contar tokens.** Muitas extensões mostram o tamanho do pedido em tokens; arquivos gerados e logs enormes costumam ser os maiores.
- **Conferir na hora.** Uma sugestão aceita fica sublinhada em vermelho se o método não existe: o compilador da IDE é o primeiro detector de alucinação.

## Resumo

- O modelo lê e escreve tokens, pedaços de texto montados por fusões como o BPE.
- Ele calcula a probabilidade de cada próximo token e sorteia um, repetidamente.
- A temperatura concentra ou espalha essas chances; temperatura baixa dá repetição, não correção.
- O conhecimento vem dos parâmetros, fixados num corte, e do contexto da conversa.
- Alucinação é texto provável e falso; o tom confiante não indica acerto.
