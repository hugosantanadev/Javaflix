O [episódio anterior](/assistir/backend-junior-t8-e03) terminou com uma regra: o diff do agente passa por você. Este episódio é sobre **como** passar. Código gerado tem um perfil de erro próprio: quase sempre compila, quase sempre parece certo, e erra nas bordas, nas regras que o modelo não conhecia e em dependências que ele inventou. Revisar bem não é ler com mais atenção; é saber **onde** olhar e ter ferramentas que conferem o que os olhos não pegam.

## O funil de conferência

![Um funil de quatro camadas: compilador, testes existentes, testes novos e revisão humana, cada uma com o tipo de erro que barra](/figuras/funil-de-revisao.svg "Cada camada barra uma parte dos erros; a revisão humana fica com o que as máquinas não sabem julgar.")

A ordem importa. Deixe a máquina pegar o que ela pega, de graça: compile e rode a suíte **antes** de ler. Sua atenção é cara e vai para o que só uma pessoa julga: a regra de negócio está certa? Isso é seguro? Precisava de uma dependência nova?

## Onde o código gerado erra

Os erros mais comuns têm padrão, e vale procurá-los de propósito:

| Onde | Exemplo | Como pegar |
|---|---|---|
| Fronteiras | `>` no lugar de `>=`, laço que para um antes | teste no valor exato do limite |
| Regra do negócio | arredonda por item quando a loja arredonda no total | teste com o exemplo do critério de aceitação |
| Tipos numéricos | `double` para dinheiro, divisão inteira | busca por `double` e por `/` no diff |
| Igualdade | `==` entre `Integer` ou `String` | inspeção da IDE e teste com valores fora do cache |
| APIs recentes | anotação removida, método de outra versão | compilar com as versões do projeto |
| Dependências | biblioteca que não existe ou não é a que parece | conferir o nome exato no repositório central |

> [!PENSE]
> O assistente gerou um método que valida CPF e mais 10 testes, todos passando. Por que esses 10 testes, sozinhos, provam pouco?

## O teste diferencial

Testes escritos pelo mesmo modelo que escreveu o código tendem a ter os mesmos pontos cegos. Uma técnica que não depende de ninguém imaginar os casos é o **teste diferencial**: comparar o código novo, otimizado ou gerado, com uma versão **simples e óbvia** do mesmo cálculo, em milhares de entradas sorteadas.

```java executar
import java.util.Random;

public class Diferencial {
    // a versão "otimizada" que o assistente sugeriu para arredondar centavos para cima, em múltiplos de 5
    static int gerada(int centavos) {
        return (centavos + 4) / 5 * 5;
    }

    // a versão óbvia, lenta mas fácil de conferir
    static int obvia(int centavos) {
        int r = centavos;
        while (r % 5 != 0) r++;
        return r;
    }

    public static void main(String[] args) {
        Random sorteio = new Random(42); //> Semente fixa: a mesma sequência a cada execução.
        int divergencias = 0;
        Integer primeira = null;
        for (int i = 0; i < 10_000; i++) {
            int x = sorteio.nextInt(-1_000, 1_000);
            if (gerada(x) != obvia(x)) {
                divergencias++;
                if (primeira == null) primeira = x;
            }
        }
        System.out.println(divergencias + " divergências; primeira em " + primeira);
        System.out.println("gerada(-3) = " + gerada(-3) + ", obvia(-3) = " + obvia(-3));
    }
}
```

```saida
4092 divergências; primeira em -237
gerada(-3) = 0, obvia(-3) = 0
```

A segunda linha mostra por que o sorteio é útil: em `-3`, as duas concordam, e um teste escrito à mão com esse valor passaria. O sorteio encontrou a divergência em negativos como `-237`, porque a divisão inteira do Java **trunca em direção ao zero**, e a fórmula `(x + 4) / 5 * 5` só funciona para números positivos. Se a regra só recebe valores positivos, documente e valide isso; se não, a fórmula está errada.

> [!MATEMATICA]
> Para um erro que aparece em 1 a cada 1.000 entradas, a chance de um teste com 10 valores escolhidos à mão acertar algum é de uns 1 − 0,999¹⁰ ≈ **1%**. Com 10.000 entradas sorteadas, a chance de **não** encontrar é 0,999¹⁰⁰⁰⁰ ≈ e⁻¹⁰ ≈ **0,005%**. O sorteio não é mais inteligente: ele só tenta muito mais vezes, e é isso que pega os erros raros.

## Dependências que não existem

Um risco novo, que nasceu com os assistentes: o modelo sugere uma dependência com nome plausível que **não existe**, como `com.google.utils:string-helpers`. Se alguém publicar uma biblioteca maliciosa com esse nome, quem copiar a sugestão instala o ataque. O golpe já tem nome em inglês: *slopsquatting*.

```java executar
import java.util.List;
import java.util.Set;

public class Dependencias {
    static final Set<String> CONHECIDAS = Set.of( //> No mundo real: o Maven Central e a política do time.
            "org.springframework.boot:spring-boot-starter-web",
            "org.flywaydb:flyway-core",
            "org.assertj:assertj-core");

    public static void main(String[] args) {
        List<String> sugeridas = List.of(
                "org.assertj:assertj-core",
                "org.springframework.boot:spring-boot-starter-validator",
                "com.google.utils:string-helpers");
        for (String d : sugeridas) {
            System.out.println((CONHECIDAS.contains(d) ? "ok        " : "conferir  ") + d);
        }
    }
}
```

```saida
ok        org.assertj:assertj-core
conferir  org.springframework.boot:spring-boot-starter-validator
conferir  com.google.utils:string-helpers
```

O segundo nome parece oficial, mas o starter de verdade se chama `spring-boot-starter-validation`. Para toda dependência nova sugerida: procure o nome exato em [search.maven.org](https://search.maven.org), confira quem publica, a data e o número de usuários, e pergunte se ela é necessária.

> [!ERRO]
> Aprovar um diff que acrescenta uma dependência porque "o código compila". Compilar prova que o pacote existe e foi baixado, não que ele é o que parece. Uma biblioteca maliciosa compila perfeitamente.

## Segurança no diff

Os pontos de segurança que mais aparecem em código gerado, e o que procurar:

- **SQL montado com `+`**: procure aspas e `+` perto de `select`, `where`, `order by`.
- **Dados pessoais em log**: `log.info` com o objeto inteiro do cliente.
- **Exceção engolida**: `catch` vazio ou só com `printStackTrace`.
- **Validação desligada**: `@Valid` removido, verificação de certificado desligada "para funcionar".
- **Segredos**: senhas, tokens e chaves no código ou no `application.properties`.

> [!LAPIS]
> O diff gerado tem a linha `String sql = "select * from pedidos where situacao = '" + situacao + "'";`, em que `situacao` vem da query string. Qual entrada de um usuário mostra o problema, e qual é a correção?
>
> **Resposta:** Algo como `PAGO' or '1'='1` devolve todos os pedidos, de todos os clientes. A correção é a consulta parametrizada (`where situacao = ?`, ou o método derivado do Spring Data), em que o valor nunca vira parte do SQL.

> [!PERGUNTAS]
> **P:** Se eu revisar tudo, a IA ainda economiza tempo?
>
> **R:** Economiza na escrita, que é a parte mais lenta para quem começa. Revisar um diff de 40 linhas com testes é bem mais rápido do que escrever as 40 linhas. O que não vale é aceitar diffs grandes demais para revisar.
>
> **P:** Posso pedir para a própria IA revisar o código que ela gerou?
>
> **R:** Pode, e ela acha coisas, principalmente numa conversa nova, sem o contexto da geração. Mas é uma camada a mais, não substitui o compilador, os testes e você.
>
> **P:** Qual é o tamanho máximo de diff que dá para revisar bem?
>
> **R:** Estudos de revisão de código apontam que a atenção cai muito depois de umas 200 a 400 linhas. Peça mudanças menores.

> [!ANTES]
> Revisão de código antes dos assistentes já era a principal defesa contra bugs: as inspeções formais da IBM, nos anos 1970, encontravam a maior parte dos defeitos antes dos testes. O que mudou foi o volume: quando escrever ficou barato, a revisão virou o gargalo, e as ferramentas automáticas de conferência passaram a ser obrigatórias, não opcionais.

## Por baixo dos panos

A divergência do teste diferencial vem de uma regra da linguagem. A JLS §15.17.2 define que a divisão inteira arredonda **em direção ao zero**: `-7 / 5` é `-1`, e não `-2`. Por isso `(x + 4) / 5 * 5` arredonda para cima nos positivos e para o lado errado em alguns negativos. A JVM implementa isso com a instrução `idiv`, que segue o comportamento da divisão das CPUs comuns. Quando a regra matemática que você quer é "arredondar para baixo" mesmo nos negativos, o Java tem `Math.floorDiv`; para "para cima", combinações com `Math.floorMod` ou o `BigDecimal` com `RoundingMode.CEILING`. Para a base de divisão inteira e resto, veja [aritmética modular e divisão inteira](/assistir/aprendiz-t3-e04).

> [!IA]
> Para revisar código gerado com a ajuda de outra IA, abra uma conversa nova, sem o histórico da geração, e peça uma revisão com foco: "procure erros de fronteira, de tipos numéricos e de segurança neste diff; para cada um, diga a linha e um caso de teste que mostra o problema". O caso de teste é o que permite conferir se o problema é real.

## Na IDE

- **Inspeções.** *Code > Inspect Code* roda centenas de verificações, como `==` entre objetos e resultado de método ignorado, no diff inteiro.
- **Dependências vulneráveis.** O IntelliJ marca no `pom.xml` as dependências com vulnerabilidades conhecidas; o plugin OWASP Dependency-Check faz o mesmo no Maven.
- **Revisão local.** *Commit* com *Analyze code* ligado roda as inspeções antes de cada commit.

## Resumo

- Deixe o compilador e os testes pegarem o que pegam antes de gastar atenção humana.
- Código gerado erra em padrões conhecidos: fronteiras, regras de negócio, tipos numéricos, igualdade e APIs recentes.
- O teste diferencial compara o código com uma versão óbvia em milhares de entradas e acha erros raros.
- Toda dependência sugerida é conferida pelo nome exato, pela origem e pela necessidade.
- Segurança no diff: SQL montado com `+`, dados pessoais em log, exceção engolida, validação desligada e segredos.
