Tratar uma exceção é decidir **onde** o programa se recupera e **o que** sempre precisa acontecer, com erro ou sem erro. O `try` marca o trecho vigiado, cada `catch` trata um tipo de problema e o `finally` roda no fim, aconteça o que acontecer. As regras parecem simples, mas a prova monta programas que imprimem de todos os blocos, com `return` no meio, e pergunta a saída.

## A ordem de execução

```java executar
public class Ordem {
    static void executar(int caso) {
        try {
            System.out.print("try ");
            if (caso == 1) throw new IllegalStateException();
            System.out.print("fim-try ");
        } catch (IllegalStateException e) {
            System.out.print("catch ");
        } finally {
            System.out.print("finally ");
        }
        System.out.println("depois");
    }

    public static void main(String[] args) {
        executar(0);
        executar(1);
    }
}
```

```saida
try fim-try finally depois
try catch finally depois
```

Sem exceção, o `try` roda inteiro, os `catch` são pulados e o `finally` roda. Com exceção, o `try` é abandonado no ponto do erro, o **primeiro** `catch` compatível roda, e depois o `finally`. Se nenhum `catch` servir, o `finally` roda mesmo assim, e a exceção continua subindo.

Um `try` precisa de pelo menos um `catch` ou um `finally` (ou de recursos, como você verá no episódio 4). E a ordem é fixa: `try`, depois os `catch`, depois no máximo um `finally`.

```java nao-compila
public class Sozinho {
    public static void main(String[] args) {
        try {
            System.out.println("oi");
        }
    }
}
```

## A ordem dos `catch`

Os `catch` são testados de cima para baixo. Por isso, um `catch` de uma superclasse antes de um de subclasse deixaria o segundo inalcançável, e o compilador recusa. Do mais específico para o mais geral:

```java nao-compila
public class Ordem {
    public static void main(String[] args) {
        try {
            Integer.parseInt("x");
        } catch (IllegalArgumentException e) {
            System.out.println("argumento");
        } catch (NumberFormatException e) {
            System.out.println("número");
        }
    }
}
```

`NumberFormatException` é uma `IllegalArgumentException`, como você viu no [episódio anterior](/assistir/pleno-t1-e01). Invertendo os dois, compila.

## `finally` e `return`

O `finally` roda até quando o `try` ou o `catch` saem com `return`. O valor de retorno é calculado **antes** do `finally`: mudar uma variável primitiva ali não altera o que já foi decidido. Mas um `return` **dentro** do `finally` substitui qualquer outro:

```java executar
public class Retorno {
    static int valor() {
        int x = 1;
        try {
            return x;
        } finally {
            x = 99;
            System.out.println("finally viu x = " + x);
        }
    }

    static String sobrescreve() {
        try {
            return "do try";
        } finally {
            return "do finally";
        }
    }

    public static void main(String[] args) {
        System.out.println(valor());
        System.out.println(sobrescreve());
    }
}
```

```saida
finally viu x = 99
1
do finally
```

Com um objeto mutável, a história muda: o `return` guarda a **referência**, e o `finally` pode alterar o objeto antes de quem chamou recebê-lo.

```java executar
public class Mutavel {
    static StringBuilder montar() {
        StringBuilder sb = new StringBuilder("a");
        try {
            return sb;
        } finally {
            sb.append("b");
        }
    }

    public static void main(String[] args) {
        System.out.println(montar());
    }
}
```

```saida
ab
```

## Quando o `finally` atrapalha

Uma exceção lançada no `finally` **substitui** a que estava subindo, e a original se perde sem deixar rastro:

```java executar
public class Perdida {
    public static void main(String[] args) {
        try {
            try {
                throw new IllegalStateException("original");
            } finally {
                throw new RuntimeException("do finally");
            }
        } catch (RuntimeException e) {
            System.out.println(e.getMessage() + " " + e.getSuppressed().length);
        }
    }
}
```

```saida
do finally 0
```

O mesmo vale para um `return` no `finally`: ele engole qualquer exceção pendente. Por isso a regra prática é nunca lançar nem retornar de dentro de um `finally`. O `try` com recursos, do [episódio 4](/assistir/pleno-t1-e04), resolve esse problema guardando a exceção do fechamento como "suprimida".

E há um único jeito comum de o `finally` não rodar: encerrar a JVM antes, com `System.exit`.

```java executar
public class Saida {
    public static void main(String[] args) {
        try {
            System.out.println("encerrando");
            System.exit(0);
        } finally {
            System.out.println("finally");
        }
    }
}
```

```saida
encerrando
```

> [!PROVA]
> Em questões de ordem, siga o fluxo: o `try` para no primeiro erro; roda só o primeiro `catch` compatível; o `finally` roda sempre, exceto com `System.exit`; um `return` no `finally` vence tudo; uma exceção no `finally` substitui a anterior. E o valor de um `return` primitivo é fixado antes do `finally`.

## Por baixo dos panos

A JVM não tem uma instrução de `finally`. O `javac` **copia** o código do bloco para cada caminho de saída: o fim normal do `try`, o fim de cada `catch` e um tratador extra, que pega qualquer exceção (*catch-any*) na tabela de exceções, roda a cópia do `finally` e relança a exceção com `athrow`. Um `finally` grande com muitos `catch` aparece várias vezes no bytecode.

Antes do Java 7, o compilador usava as instruções `jsr` e `ret`, uma espécie de sub-rotina dentro do método, para não duplicar o código. Elas complicavam demais a verificação de tipos do bytecode e foram proibidas nos arquivos de classe a partir da versão 51. No caso do `return` com `finally`, o valor a devolver é guardado numa variável local escondida antes da cópia do `finally` rodar, e é por isso que mudar `x` ali não altera o resultado.

## Resumo para a prova

- `try` exige ao menos um `catch` ou um `finally` (ou recursos)
- Ordem fixa: `try`, `catch`, `finally`
- Só o primeiro `catch` compatível roda; superclasse antes de subclasse não compila
- O `finally` roda sempre, com ou sem exceção, com ou sem `return`
- `System.exit` impede o `finally`
- O valor de um `return` é calculado antes do `finally`; objetos mutáveis ainda podem ser alterados
- `return` no `finally` substitui o retorno e engole exceções
- Exceção no `finally` substitui a exceção original, que se perde
