Você já viu várias exceções pelo caminho: `NullPointerException`, `ArrayIndexOutOfBoundsException`, `NumberFormatException`. Esta temporada trata delas como assunto principal. Uma exceção é um objeto que representa um problema e interrompe o fluxo normal do programa até alguém tratá-la. O primeiro passo é conhecer a **hierarquia**, porque é ela que decide o que o compilador obriga você a fazer.

## A árvore

```text
Throwable
├── Error                      problemas graves da JVM: não trate
│   ├── StackOverflowError
│   └── OutOfMemoryError
└── Exception                  checked: o compilador exige tratar ou declarar
    ├── IOException
    │   └── FileNotFoundException
    └── RuntimeException       unchecked: erros de programação
        ├── NullPointerException
        ├── ArithmeticException
        └── IllegalArgumentException
            └── NumberFormatException
```

Tudo o que pode ser lançado estende `Throwable`. A divisão que importa é entre **checked** (verificadas) e **unchecked** (não verificadas):

| Tipo | Quem são | O compilador exige |
|---|---|---|
| Checked | `Exception` e subclasses, **exceto** `RuntimeException` | tratar com `catch` ou declarar com `throws` |
| Unchecked | `RuntimeException`, `Error` e subclasses | nada |

```java executar
Throwable[] exemplos = {
    new ArithmeticException(), new java.io.IOException(), new StackOverflowError(), new NumberFormatException()
};
for (Throwable t : exemplos) {
    String tipo = t instanceof Error ? "Error" : t instanceof RuntimeException ? "unchecked" : "checked";
    System.out.println(t.getClass().getSimpleName() + ": " + tipo);
}
```

```saida
ArithmeticException: unchecked
IOException: checked
StackOverflowError: Error
NumberFormatException: unchecked
```

A ideia por trás da divisão: exceções **checked** representam problemas que um programa correto pode encontrar e deve prever, como um arquivo que não existe ou uma rede fora do ar. As **unchecked** representam bugs, como dividir por zero ou acessar `null`, que se corrigem no código, não com `catch`. E os **erros** (`Error`) indicam que a própria JVM está em apuros; o programa raramente tem o que fazer.

## A regra de tratar ou declarar

Um método que pode lançar uma exceção checked precisa **tratá-la** (com `try`/`catch`) ou **declará-la** (com `throws` na assinatura), passando a responsabilidade para quem chama. Sem nenhum dos dois, não compila:

```java nao-compila
public class Leitura {
    static String ler() {
        throw new java.io.IOException("disco cheio");
    }
}
```

Com `throws`, quem chama passa a ter a mesma obrigação. `throw` (sem s) **lança** uma exceção; `throws` (com s) **declara** que o método pode lançá-la:

```java executar
import java.io.IOException;

public class Leitura {
    static String ler(String nome) throws IOException {
        if (nome.isEmpty()) {
            throw new IOException("nome vazio");
        }
        return "conteúdo de " + nome;
    }

    public static void main(String[] args) {
        try {
            System.out.println(ler("notas.txt"));
            System.out.println(ler(""));
            System.out.println("não chega aqui");
        } catch (IOException e) {
            System.out.println("falhou: " + e.getMessage());
        }
    }
}
```

```saida
conteúdo de notas.txt
falhou: nome vazio
```

Assim que a exceção é lançada, o resto do bloco `try` é abandonado. A execução salta para o primeiro `catch` compatível.

O compilador também recusa o contrário: um `catch` de uma exceção checked que o bloco `try` **nunca** poderia lançar é código morto. A exceção é `Exception` (e `Throwable`), que também cobre as unchecked, sempre possíveis:

```java nao-compila
public class Inutil {
    public static void main(String[] args) {
        try {
            System.out.println("oi");
        } catch (java.io.IOException e) {
            System.out.println("nunca");
        }
    }
}
```

## A exceção sobe a pilha

Uma exceção não tratada sai do método e vai para quem o chamou, e assim por diante, até encontrar um `catch` ou derrubar a thread. O caminho fica registrado no **stack trace**:

```java executar
public class Pilha {
    static int dividir(int a, int b) {
        return a / b;
    }

    static int media(int soma, int n) {
        return dividir(soma, n);
    }

    public static void main(String[] args) {
        try {
            media(10, 0);
        } catch (ArithmeticException e) {
            System.out.println(e.getMessage());
            for (StackTraceElement el : e.getStackTrace()) {
                System.out.println("  em " + el.getMethodName());
            }
        }
    }
}
```

```saida
/ by zero
  em dividir
  em media
  em main
```

Leia um stack trace de cima para baixo: a primeira linha é onde o problema aconteceu; as seguintes, quem chamou quem.

## As exceções mais comuns

| Exceção | Tipo | Quando |
|---|---|---|
| `ArithmeticException` | unchecked | divisão inteira por zero |
| `ArrayIndexOutOfBoundsException` | unchecked | índice fora do array |
| `ClassCastException` | unchecked | cast para um tipo que o objeto não é |
| `NullPointerException` | unchecked | uso de uma referência `null` |
| `IllegalArgumentException` | unchecked | argumento inválido; `NumberFormatException` é subclasse dela |
| `IllegalStateException` | unchecked | método chamado na hora errada |
| `IOException` | checked | falha de entrada e saída; `FileNotFoundException` é subclasse |
| `StackOverflowError` | error | recursão sem fim |
| `ExceptionInInitializerError` | error | exceção num inicializador `static` |

> [!PROVA]
> A prova adora perguntar se um trecho compila. Para cada exceção lançada, pergunte: ela é checked? Se for, está num `try` com `catch` compatível, ou o método declara `throws`? E para cada `catch` de checked, o `try` pode mesmo lançá-la? Lembre que `NumberFormatException` é uma `IllegalArgumentException`, e que `Error` não é `Exception`: um `catch (Exception e)` não pega um `StackOverflowError`.

## Por baixo dos panos

No bytecode, `throw` é a instrução `athrow`. E os blocos `try`/`catch` não viram instruções: cada método tem uma **tabela de exceções**, que diz "se uma exceção do tipo X acontecer entre as instruções N e M, pule para a instrução K". Quando algo é lançado, a JVM consulta a tabela do método atual; se não houver entrada compatível, desfaz o quadro da pilha e repete a busca no método de quem chamou. Por isso um `try` que não lança nada não custa praticamente nada.

O que custa caro é **criar** a exceção: o construtor de `Throwable` chama `fillInStackTrace`, que percorre a pilha inteira para montar o stack trace. Usar exceções como fluxo normal do programa, num laço quente, é lento por isso. A HotSpot tem até uma otimização para exceções implícitas, como `NullPointerException`, lançadas muitas vezes no mesmo lugar: depois de um tempo, ela passa a lançar um objeto pré-alocado, sem stack trace, o que explica logs de produção com uma `NullPointerException` sem nenhuma linha de origem.

## Resumo para a prova

- `Throwable` tem dois ramos: `Error` e `Exception`; `RuntimeException` é uma `Exception`
- Checked: `Exception` e subclasses, menos as `RuntimeException`
- Unchecked: `RuntimeException`, `Error` e subclasses
- Checked precisa ser tratada (`catch`) ou declarada (`throws`)
- `throw` lança; `throws` declara
- `catch` de uma checked que o `try` nunca lança não compila (exceto `Exception` e `Throwable`)
- A exceção sobe a pilha até encontrar um `catch` compatível
- `catch (Exception e)` não pega `Error`
