Arquivos, conexões de banco e *sockets* precisam ser fechados, e fechados mesmo quando algo dá errado. Com `finally`, isso exige um código cheio de `if (x != null)` e de `try` aninhados, e ainda corre o risco de perder exceções, como você viu no [episódio 2](/assistir/pleno-t1-e02). O **try-with-resources**, do Java 7, resolve as duas coisas: fecha tudo sozinho, na ordem certa, e guarda as exceções do fechamento como **suprimidas**, sem esconder a original.

## A ordem completa

Os recursos são declarados entre parênteses, separados por `;`, e precisam implementar `AutoCloseable`. Eles abrem na ordem da declaração, fecham na ordem **inversa** e fecham **antes** de qualquer `catch` ou `finally` rodar:

```java executar
public class Ordem {
    static class Recurso implements AutoCloseable {
        private final String nome;

        Recurso(String nome) {
            this.nome = nome;
            System.out.println("abre " + nome);
        }

        @Override
        public void close() {
            System.out.println("fecha " + nome);
        }
    }

    public static void main(String[] args) {
        try (Recurso a = new Recurso("A"); Recurso b = new Recurso("B")) {
            System.out.println("usa");
            throw new IllegalStateException("erro");
        } catch (IllegalStateException e) {
            System.out.println("catch " + e.getMessage());
        } finally {
            System.out.println("finally");
        }
    }
}
```

```saida
abre A
abre B
usa
fecha B
fecha A
catch erro
finally
```

Quando o `catch` roda, os recursos já estão fechados. Por isso a variável do recurso só existe dentro do bloco `try`: ela não é visível no `catch` nem no `finally`. E, ao contrário do `try` comum, o try-with-resources pode não ter nem `catch` nem `finally`.

## Exceções suprimidas

E se o corpo lança uma exceção e o `close()` também? Com `finally`, a segunda substituiria a primeira. No try-with-resources, a do corpo continua sendo a **principal**, e a do fechamento é anexada a ela como **suprimida**, acessível por `getSuppressed()`:

```java executar
public class Suprimida {
    static class Conexao implements AutoCloseable {
        @Override
        public void close() {
            throw new IllegalStateException("falha ao fechar");
        }
    }

    public static void main(String[] args) {
        try (Conexao c = new Conexao()) {
            throw new RuntimeException("falha na consulta");
        } catch (RuntimeException e) {
            System.out.println("principal: " + e.getMessage());
            for (Throwable s : e.getSuppressed()) {
                System.out.println("suprimida: " + s.getMessage());
            }
        }
    }
}
```

```saida
principal: falha na consulta
suprimida: falha ao fechar
```

Se só o `close()` falhar, não há o que suprimir: a exceção do fechamento é a principal.

```java executar
public class SoFechamento {
    static class Arquivo implements AutoCloseable {
        @Override
        public void close() {
            throw new IllegalStateException("falha ao fechar");
        }
    }

    public static void main(String[] args) {
        try (Arquivo a = new Arquivo()) {
            System.out.println("corpo sem erro");
        } catch (IllegalStateException e) {
            System.out.println("principal: " + e.getMessage() + ", suprimidas: " + e.getSuppressed().length);
        }
    }
}
```

```saida
corpo sem erro
principal: falha ao fechar, suprimidas: 0
```

## As exceções do `close()`

O `close()` de `AutoCloseable` declara `throws Exception`. Se o tipo declarado do recurso for `AutoCloseable`, ou uma classe cujo `close()` declara exceções checked, o fechamento implícito pode lançá-las, e a regra de tratar ou declarar vale para ele também:

```java nao-compila
public class Generico {
    public static void main(String[] args) {
        AutoCloseable recurso = () -> System.out.println("fechou");
        try (recurso) {
            System.out.println("usando");
        }
    }
}
```

Uma classe pode sobrescrever `close()` sem `throws`, como as dos exemplos, e aí nada precisa ser tratado. A subinterface `java.io.Closeable`, das classes de I/O, restringe o `close()` a `IOException`.

## Recursos declarados antes (Java 9)

Desde o Java 9, um recurso já declarado antes do `try` pode ser usado só pelo nome, desde que seja `final` ou efetivamente final:

```java executar
public class Java9 {
    static class Log implements AutoCloseable {
        public void close() {
            System.out.println("log fechado");
        }
    }

    public static void main(String[] args) {
        final Log log = new Log();
        Log outro = new Log();
        try (log; outro) {
            System.out.println("no try");
        }
    }
}
```

```saida
no try
log fechado
log fechado
```

E as variáveis declaradas no cabeçalho são implicitamente `final`:

```java nao-compila
public class Reatribui {
    static class Log implements AutoCloseable {
        public void close() { }
    }

    public static void main(String[] args) {
        try (Log l = new Log()) {
            l = new Log();
        }
    }
}
```

Um detalhe: se um recurso for `null`, o `close()` dele simplesmente não é chamado, sem `NullPointerException`.

> [!PROVA]
> Ordem de um try-with-resources com `catch` e `finally`: recursos abrem na ordem, corpo, recursos fecham na ordem inversa, `catch`, `finally`. Exceção do `close()` com o corpo já falhando vira suprimida; sozinha, vira a principal. Se um recurso falha **ao abrir**, só os que já abriram são fechados. Recursos precisam implementar `AutoCloseable`, são `final` e não existem no `catch` nem no `finally`.

## Por baixo dos panos

O try-with-resources é açúcar sintático. O `javac` o transforma num `try`/`finally` com uma variável escondida para a exceção principal: se o corpo lançar algo, ela guarda a exceção e, ao fechar, chama `principal.addSuppressed(excecaoDoClose)`; se não, deixa a exceção do `close()` subir normalmente. Recursos aninhados viram blocos aninhados, o que produz a ordem inversa de fechamento sem nenhuma lógica extra.

O método `addSuppressed` foi acrescentado a `Throwable` no Java 7 justamente para isso, e o `printStackTrace` mostra as suprimidas numa seção `Suppressed:`. Exceções criadas com o construtor protegido que desativa a supressão, como algumas que a JVM pré-aloca, ignoram as chamadas a `addSuppressed`.

## Resumo para a prova

- Recursos precisam implementar `AutoCloseable` (ou `Closeable`)
- Abrem na ordem da declaração e fecham na ordem inversa, antes do `catch` e do `finally`
- O try-with-resources dispensa `catch` e `finally`
- Exceção do `close()` com o corpo já falhando vira suprimida (`getSuppressed()`)
- Exceção só do `close()` é a principal
- Exceções checked do `close()` precisam ser tratadas ou declaradas
- Java 9: recursos `final` ou efetivamente final declarados antes podem ser usados pelo nome
- Variáveis de recurso são `final` e não existem no `catch` nem no `finally`; recurso `null` não é fechado
