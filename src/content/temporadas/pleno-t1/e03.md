Às vezes, exceções diferentes merecem o mesmo tratamento. Em outras, o método não sabe tratar o erro, mas precisa registrá-lo ou dar a ele um contexto antes de passá-lo adiante. Para o primeiro caso, existe o **multi-catch**; para o segundo, o **relançamento** e o **encadeamento** de exceções. Os dois chegaram no Java 7 e têm regras precisas de compilação.

## Multi-catch

Um `catch` pode listar vários tipos, separados por `|`. O bloco roda para qualquer um deles:

```java executar
import java.io.IOException;
import java.util.concurrent.TimeoutException;

public class Servico {
    static String buscar(int caso) throws IOException, TimeoutException {
        if (caso == 1) throw new IOException("disco");
        if (caso == 2) throw new TimeoutException("rede");
        return "dados";
    }

    public static void main(String[] args) {
        for (int caso = 0; caso <= 2; caso++) {
            try {
                System.out.println(buscar(caso));
            } catch (IOException | TimeoutException e) {
                System.out.println("falha (" + e.getClass().getSimpleName() + "): " + e.getMessage());
            }
        }
    }
}
```

```saida
dados
falha (IOException): disco
falha (TimeoutException): rede
```

Duas regras. Primeira: os tipos listados não podem ter **relação de herança** entre si. Se um é subclasse do outro, basta o mais geral, e o compilador recusa a redundância:

```java nao-compila
import java.io.FileNotFoundException;
import java.io.IOException;

public class Relacionadas {
    static void abrir() throws IOException {
        throw new FileNotFoundException("x");
    }

    public static void main(String[] args) {
        try {
            abrir();
        } catch (FileNotFoundException | IOException e) {
            System.out.println(e);
        }
    }
}
```

Segunda: a variável do multi-catch é implicitamente `final`. Ela não pode receber outro valor:

```java nao-compila
public class Reatribui {
    public static void main(String[] args) {
        try {
            Integer.parseInt("x");
        } catch (NumberFormatException | NullPointerException e) {
            e = new NumberFormatException("outra");
        }
    }
}
```

Dentro do bloco, o tipo de `e` é o **supertipo comum** das alternativas (no exemplo do serviço, `Exception`): só os métodos desse supertipo podem ser chamados sem cast.

## Relançar com precisão

Um `catch` pode registrar o problema e relançar a mesma exceção com `throw e`. Desde o Java 7, se `e` não for reatribuída, o compilador sabe quais exceções checked o `try` podia lançar de fato, e o método só precisa declarar essas, mesmo que o `catch` seja de `Exception`:

```java executar
import java.io.IOException;

public class Relanca {
    static void ler(boolean falhar) throws IOException {
        if (falhar) throw new IOException("falhou");
    }

    static void processar(boolean falhar) throws IOException {
        try {
            ler(falhar);
        } catch (Exception e) {
            System.out.println("registrando: " + e.getMessage());
            throw e;
        }
    }

    public static void main(String[] args) {
        try {
            processar(true);
        } catch (IOException e) {
            System.out.println("main tratou: " + e.getMessage());
        }
    }
}
```

```saida
registrando: falhou
main tratou: falhou
```

`processar` declara só `IOException`, embora o `catch` seja de `Exception`. Se a variável `e` fosse reatribuída dentro do `catch`, o compilador perderia essa precisão e passaria a exigir `throws Exception`.

## Embrulhar com a causa

Muitas vezes, a exceção original não faz sentido para quem chama: uma `IOException` vazando de dentro de um repositório de pedidos revela detalhes que o resto do sistema não deveria conhecer. A saída é **traduzir** a exceção, embrulhando a original como **causa** da nova. Todas as exceções da biblioteca têm um construtor que recebe a causa:

```java executar
import java.io.IOException;

public class Embrulha {
    static class RepositorioException extends RuntimeException {
        RepositorioException(String msg, Throwable causa) {
            super(msg, causa);
        }
    }

    static void salvar() {
        try {
            throw new IOException("disco cheio");
        } catch (IOException e) {
            throw new RepositorioException("não foi possível salvar o pedido", e);
        }
    }

    public static void main(String[] args) {
        try {
            salvar();
        } catch (RepositorioException e) {
            System.out.println(e.getMessage());
            System.out.println("causa: " + e.getCause());
        }
    }
}
```

```saida
não foi possível salvar o pedido
causa: java.io.IOException: disco cheio
```

No stack trace completo, a causa aparece numa seção `Caused by:`, e nada se perde. Embrulhar uma checked numa unchecked também é a forma comum de atravessar código que não pode declarar `throws`, como uma lambda; a biblioteca até tem uma pronta para I/O, a `UncheckedIOException`.

> [!PROVA]
> No multi-catch: tipos com relação de herança não compilam, a variável é `final` e o tipo dela é o supertipo comum. No relançamento: `catch (Exception e) { throw e; }` só exige declarar as checked que o `try` lança de verdade, desde que `e` não seja reatribuída. E nunca "engula" uma exceção com um `catch` vazio: no mínimo, registre ou relance.

## Por baixo dos panos

O multi-catch não duplica código: o bytecode tem **um** tratador, e a tabela de exceções ganha uma linha para cada tipo da lista, todas apontando para o mesmo endereço. Antes do Java 7, escrever dois `catch` com o mesmo corpo gerava o código duas vezes. O relançamento preciso, por sua vez, é só análise do compilador: no bytecode, `throw e` é um `athrow` como outro qualquer.

A causa fica guardada no campo `cause` de `Throwable`, e o `printStackTrace` percorre a corrente de causas, imprimindo cada uma. Para não repetir linhas, ele resume as partes do stack trace que a causa compartilha com a exceção de cima, com a indicação `... N more`, que aparece em quase todo log de produção.

## Resumo para a prova

- `catch (A | B e)` trata vários tipos com o mesmo bloco
- Tipos com relação de herança no mesmo multi-catch não compilam
- A variável do multi-catch é implicitamente `final`
- O tipo da variável é o supertipo comum das alternativas
- `catch (Exception e) { throw e; }` só exige declarar as checked que o `try` lança, se `e` não for reatribuída
- Embrulhar com causa: `new MinhaException("contexto", e)`; a original fica em `getCause()`
- `UncheckedIOException` embrulha uma `IOException` numa unchecked
