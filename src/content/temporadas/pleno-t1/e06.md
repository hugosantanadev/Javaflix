A [temporada de herança](/assistir/junior-t3-e02) apresentou a regra: um método sobrescrito não pode declarar exceções checked novas ou mais amplas. Este episódio a explora a fundo, porque ela se combina com polimorfismo, interfaces, construtores e lambdas de formas que a prova adora. Tudo sai de uma pergunta: **o que o código que usa o tipo mais geral pode esperar?**

## O que a sobrescrita pode e não pode

| Na subclasse, o método pode | Exemplo, se a original declara `throws IOException` |
|---|---|
| Não declarar nada | `String ler()` |
| Declarar a mesma exceção | `String ler() throws IOException` |
| Declarar uma subclasse dela | `String ler() throws FileNotFoundException` |
| Declarar qualquer unchecked | `String ler() throws IllegalStateException` |
| **Não pode** declarar uma checked mais ampla ou nova | `String ler() throws Exception` não compila |

```java executar
import java.io.FileNotFoundException;
import java.io.IOException;

public class Regras {
    static class Leitor {
        String ler() throws IOException {
            return "genérico";
        }
    }

    static class LeitorDeArquivo extends Leitor {
        @Override
        String ler() throws FileNotFoundException {
            return "arquivo";
        }
    }

    static class LeitorDeMemoria extends Leitor {
        @Override
        String ler() {
            return "memória";
        }
    }

    static class LeitorInstavel extends Leitor {
        @Override
        String ler() throws IllegalStateException {
            throw new IllegalStateException("instável");
        }
    }

    public static void main(String[] args) {
        Leitor[] leitores = {new LeitorDeArquivo(), new LeitorDeMemoria(), new LeitorInstavel()};
        for (Leitor l : leitores) {
            try {
                System.out.println(l.ler());
            } catch (IOException e) {
                System.out.println("I/O: " + e.getMessage());
            } catch (IllegalStateException e) {
                System.out.println("estado: " + e.getMessage());
            }
        }
    }
}
```

```saida
arquivo
memória
estado: instável
```

O código do `main` só conhece `Leitor` e se preparou para `IOException`. Toda subclasse respeita isso. Uma que declarasse `throws Exception` quebraria a promessa:

```java nao-compila
import java.io.IOException;

class Leitor {
    String ler() throws IOException {
        return "";
    }
}

class LeitorGeral extends Leitor {
    @Override
    String ler() throws Exception {
        return "";
    }
}
```

Nem uma checked nova, quando a original não declara nenhuma:

```java nao-compila
class Servico {
    void executar() { }
}

class ServicoRemoto extends Servico {
    @Override
    void executar() throws java.io.IOException { }
}
```

As mesmas regras valem para quem implementa um método de interface ou um método abstrato.

## O tipo da referência decide o que tratar

O compilador olha a cláusula `throws` do método **que ele enxerga**, pelo tipo da referência, como na [sobrecarga e no polimorfismo](/assistir/junior-t3-e03). Se a subclasse não lança nada, mas a chamada é feita por uma referência da superclasse, que declara `throws Exception`, é preciso tratar mesmo assim:

```java executar
public class Referencia {
    static class Animal {
        String som() throws Exception {
            return "...";
        }
    }

    static class Gato extends Animal {
        @Override
        String som() {
            return "miau";
        }
    }

    public static void main(String[] args) {
        Gato g = new Gato();
        System.out.println(g.som());
        Animal a = g;
        try {
            System.out.println(a.som());
        } catch (Exception e) {
            System.out.println("nunca acontece aqui");
        }
    }
}
```

```saida
miau
miau
```

Sem o `try`, a chamada `a.som()` não compilaria, embora o objeto seja o mesmo gato que nunca lança nada.

```java nao-compila
public class Referencia {
    static class Animal {
        String som() throws Exception {
            return "...";
        }
    }

    static class Gato extends Animal {
        @Override
        String som() {
            return "miau";
        }
    }

    public static void main(String[] args) {
        Animal a = new Gato();
        System.out.println(a.som());
    }
}
```

## Construtores invertem a regra

Construtores não são sobrescritos, e a lógica deles é a oposta. O construtor da subclasse **chama** o da superclasse, e não há como pôr esse `super()` num `try`. Então, se o construtor da superclasse declara uma checked, o da subclasse **precisa** declará-la também, ou uma mais ampla:

```java nao-compila
import java.io.IOException;

class Arquivo {
    Arquivo() throws IOException { }
}

class Planilha extends Arquivo {
    Planilha() { }
}
```

```java compila
import java.io.IOException;

class Arquivo {
    Arquivo() throws IOException { }
}

class Planilha extends Arquivo {
    Planilha() throws Exception { }
}
```

## Lambdas e exceções checked

Uma lambda implementa o método de uma interface funcional, e por isso segue a cláusula `throws` dele. `Runnable.run()` e as interfaces de `java.util.function` não declaram exceções checked, então uma lambda delas não pode lançar uma. Se a interface declarar, como `Callable.call() throws Exception`, a lambda pode. A saída comum é embrulhar a checked numa unchecked, como no [episódio 3](/assistir/pleno-t1-e03).

> [!PROVA]
> Três casos que caem juntos: sobrescrita com `throws` mais amplo não compila; chamada pela referência da superclasse exige tratar o que **ela** declara, mesmo que o objeto não lance nada; e o construtor da subclasse precisa declarar as checked do construtor da superclasse. Exceções unchecked ficam fora de todas essas regras.

## Por baixo dos panos

A regra das checked é **só do compilador**. No arquivo `.class`, a cláusula `throws` vira um atributo `Exceptions`, que serve de documentação e para a reflexão, mas a JVM nunca o confere. Com um truque de genéricos, é possível lançar uma checked de um método que não a declara, o chamado *sneaky throw*:

```java executar
import java.io.IOException;

public class Sorrateiro {
    @SuppressWarnings("unchecked")
    static <E extends Throwable> void lancar(Throwable t) throws E {
        throw (E) t;
    }

    static void semThrows() {
        Sorrateiro.<RuntimeException>lancar(new IOException("checked escondida"));
    }

    public static void main(String[] args) {
        try {
            semThrows();
        } catch (Exception e) {
            System.out.println(e.getClass().getSimpleName() + ": " + e.getMessage());
        }
    }
}
```

```saida
IOException: checked escondida
```

O compilador acredita que `lancar` só lança `RuntimeException`; o cast para `E` desaparece na execução, pelo apagamento de tipos que você verá na [próxima temporada](/assistir/pleno-t2-e03), e a `IOException` sai intacta. Bibliotecas como o Lombok usam o truque. Outras linguagens da JVM, como Kotlin e Scala, nem têm exceções checked: para a máquina, todas são iguais.

## Resumo para a prova

- O método sobrescrito pode declarar menos exceções, subclasses delas ou qualquer unchecked
- Não pode declarar checked novas ou mais amplas; vale também para interfaces e métodos abstratos
- A chamada é conferida pelo `throws` do tipo da referência, não do objeto
- O construtor da subclasse precisa declarar as checked do construtor da superclasse (ou mais amplas)
- Lambdas seguem o `throws` do método da interface funcional
- As exceções checked são uma regra do compilador; a JVM não as confere
