`IllegalArgumentException("valor inválido")` funciona, mas diz pouco. Um sistema de verdade tem erros com nome e sobrenome: saldo insuficiente, produto não encontrado, CPF inválido. Criar as suas próprias exceções dá a esses erros um **tipo**, que pode ser tratado separadamente num `catch`, e **dados**, que ajudam quem trata a decidir o que fazer.

## Criando uma exceção

Uma exceção customizada é só uma classe que estende `Exception` (para ser checked) ou `RuntimeException` (para ser unchecked). O mínimo é um construtor que repassa a mensagem com `super`. Como qualquer classe, ela pode ter campos com informações do problema:

```java executar
public class Banco {
    static class SaldoInsuficienteException extends Exception {
        private final double faltam;

        SaldoInsuficienteException(double faltam) {
            super("saldo insuficiente, faltam " + faltam);
            this.faltam = faltam;
        }

        double getFaltam() {
            return faltam;
        }
    }

    static double saldo = 100;

    static void sacar(double valor) throws SaldoInsuficienteException {
        if (valor > saldo) {
            throw new SaldoInsuficienteException(valor - saldo);
        }
        saldo -= valor;
    }

    public static void main(String[] args) {
        try {
            sacar(30);
            sacar(120);
        } catch (SaldoInsuficienteException e) {
            System.out.println(e.getMessage() + " | faltam " + e.getFaltam());
        }
        System.out.println("saldo: " + saldo);
    }
}
```

```saida
saldo insuficiente, faltam 50.0 | faltam 50.0
saldo: 70.0
```

As regras de sempre valem: sendo checked, quem lança precisa declarar, e quem chama precisa tratar ou declarar.

```java nao-compila
public class Validador {
    static class CpfInvalidoException extends Exception {
        CpfInvalidoException(String cpf) {
            super("CPF inválido: " + cpf);
        }
    }

    static void validar(String cpf) {
        if (cpf.length() != 11) {
            throw new CpfInvalidoException(cpf);
        }
    }
}
```

A convenção é terminar o nome em `Exception`. As exceções da biblioteca costumam oferecer quatro construtores (sem argumentos, com mensagem, com mensagem e causa, só com causa), e é uma boa prática repetir pelo menos o de mensagem e causa, para permitir o encadeamento do [episódio 3](/assistir/pleno-t1-e03).

## Uma hierarquia para o domínio

Num sistema maior, vale criar uma exceção base do domínio e especializá-la. Quem chama escolhe o nível de detalhe com que quer tratar os erros, pela ordem dos `catch`:

```java executar
public class Loja {
    static class LojaException extends RuntimeException {
        LojaException(String msg) { super(msg); }
        LojaException(String msg, Throwable causa) { super(msg, causa); }
    }

    static class ProdutoNaoEncontradoException extends LojaException {
        ProdutoNaoEncontradoException(String codigo) {
            super("produto não encontrado: " + codigo);
        }
    }

    static class EstoqueEsgotadoException extends LojaException {
        EstoqueEsgotadoException(String codigo) {
            super("estoque esgotado: " + codigo);
        }
    }

    static void comprar(String codigo) {
        switch (codigo) {
            case "X1" -> System.out.println("comprado: " + codigo);
            case "X2" -> throw new EstoqueEsgotadoException(codigo);
            default -> throw new ProdutoNaoEncontradoException(codigo);
        }
    }

    public static void main(String[] args) {
        for (String c : new String[] {"X1", "X2", "Z9"}) {
            try {
                comprar(c);
            } catch (EstoqueEsgotadoException e) {
                System.out.println("avise quando chegar: " + e.getMessage());
            } catch (LojaException e) {
                System.out.println("erro da loja: " + e.getMessage());
            }
        }
    }
}
```

```saida
comprado: X1
avise quando chegar: estoque esgotado: X2
erro da loja: produto não encontrado: Z9
```

## Checked ou unchecked?

O critério do Effective Java: **checked** para condições que um programa correto pode encontrar e das quais quem chama pode se recuperar (o saldo insuficiente, que pede outro valor); **unchecked** para violações de contrato e erros de programação (um argumento nulo onde não podia). Na prática, frameworks modernos como o Spring preferem exceções unchecked para erros de domínio, tratadas num lugar central, e esse é o padrão na maioria dos projetos atuais.

O que **não** se faz: estender `Throwable` diretamente (nem checked nem unchecked fica claro) ou `Error` (reservado a problemas da JVM). E um record não pode ser exceção, porque records não estendem classes:

```java nao-compila
record ErroDeValidacao(String campo) extends RuntimeException { }
```

> [!PROVA]
> Exceção customizada é uma classe comum: as regras de construtores da [temporada de herança](/assistir/junior-t3-e01) valem para ela. Se a superclasse só tem um construtor com `String`, a subclasse precisa chamar `super(mensagem)`. Estendeu `Exception`? É checked e entra na regra de tratar ou declarar. Estendeu `RuntimeException`? Não precisa de `throws`.

## Por baixo dos panos

O custo de uma exceção está na criação, não no `throw`: o construtor de `Throwable` chama `fillInStackTrace`, que percorre a pilha inteira. Para exceções usadas como sinal de controle num laço muito frequente, `Throwable` tem um construtor protegido de quatro argumentos que desliga o stack trace e a supressão:

```java executar
public class Leve {
    static class FimDaFila extends RuntimeException {
        FimDaFila() {
            super("fila vazia", null, false, false);
        }
    }

    public static void main(String[] args) {
        FimDaFila e = new FimDaFila();
        System.out.println(e.getMessage() + " " + e.getStackTrace().length);
        e.addSuppressed(new RuntimeException("x"));
        System.out.println(e.getSuppressed().length);
    }
}
```

```saida
fila vazia 0
0
```

Sem o stack trace, criar a exceção custa quase o mesmo que criar um objeto comum. Bibliotecas de alto desempenho usam o truque, mas ele tem preço: quando algo der errado de verdade, o log não dirá de onde a exceção veio. `Throwable` também implementa `Serializable`, e por isso o compilador, com `-Xlint`, sugere declarar um `serialVersionUID` em cada exceção customizada.

## Resumo para a prova

- Exceção customizada estende `Exception` (checked) ou `RuntimeException` (unchecked)
- O nome termina em `Exception`; a mensagem é passada com `super(mensagem)`
- Ofereça o construtor com mensagem e causa: `super(msg, causa)`
- Campos guardam dados úteis do problema
- Hierarquias de domínio permitem tratar erros em níveis diferentes, do mais específico ao mais geral
- Não estenda `Throwable` nem `Error`; records não podem ser exceções
- As regras de construtor de herança valem: sem construtor sem parâmetros na mãe, chame `super(...)`
- O construtor de quatro argumentos permite exceções sem stack trace nem supressão
