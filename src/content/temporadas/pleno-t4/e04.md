Duas vezes por ano, em boa parte do mundo, o relógio pula uma hora para a frente ou volta uma hora. Num desses dias, existe um horário que **não acontece**; no outro, um horário que acontece **duas vezes**. Sistemas de agendamento, cobrança por hora e relatórios diários tropeçam nisso todo ano, e a prova cobra exatamente esses dois casos.

> [!ANTES]
> No Brasil, as regras do horário de verão mudaram várias vezes por decreto. Em 2017, o início passou de outubro para o primeiro domingo de novembro, a pedido do TSE, para não coincidir com o segundo turno das eleições; em 2019, o Decreto 9.772 aboliu o horário de verão. Cada mudança exigiu atualizar o banco de fusos de servidores, celulares e JDKs, e sistemas desatualizados mostraram horários errados.

## Os dois problemas

Usaremos `America/New_York`, que ainda tem horário de verão. Em 2024:

| Data | O que acontece | Efeito |
|---|---|---|
| 10 de março | Às 2h, o relógio pula para 3h | As horas entre 2h e 3h **não existem** (a lacuna) |
| 3 de novembro | Às 2h, o relógio volta para 1h | As horas entre 1h e 2h acontecem **duas vezes** (a sobreposição) |

Fora do horário de verão, Nova York está em `-05:00`; durante, em `-04:00`.

![Duas linhas de horários em Nova York: em 10 de março, de 01:30 o relógio salta para 03:00, e as horas de 2h não existem; em 3 de novembro, 01:00 e 01:30 aparecem em -04:00 e de novo em -05:00; embaixo de cada horário, o instante em UTC, sempre crescente](/figuras/lacuna-e-sobreposicao.svg "Na lacuna, horários somem; na sobreposição, se repetem; em UTC, o tempo só anda para a frente.")

## A lacuna: um horário que não existe

Criar um `ZonedDateTime` para 2h30 de 10 de março não lança exceção. O Java empurra o horário para a frente pelo tamanho da lacuna:

```java executar
import java.time.Duration;
import java.time.LocalDateTime;
import java.time.ZoneId;
import java.time.ZonedDateTime;

public class Lacuna {
    public static void main(String[] args) {
        ZoneId ny = ZoneId.of("America/New_York");
        System.out.println(ZonedDateTime.of(LocalDateTime.of(2024, 3, 10, 2, 30), ny)); //> 2h30 não existe: vira 3h30.

        ZonedDateTime uma = ZonedDateTime.of(LocalDateTime.of(2024, 3, 10, 1, 0), ny);
        ZonedDateTime tres = ZonedDateTime.of(LocalDateTime.of(2024, 3, 10, 3, 0), ny);
        System.out.println(Duration.between(uma, tres));
        System.out.println(uma.plusHours(1) + " " + uma.plusMinutes(90));
    }
}
```

```saida
2024-03-10T03:30-04:00[America/New_York]
PT1H
2024-03-10T03:00-04:00[America/New_York] 2024-03-10T03:30-04:00[America/New_York]
```

> [!PENSE]
> O código criou a 1h e as 3h do mesmo domingo. Quanto tempo passou de verdade entre as duas? E o que deveria acontecer com um pedido para as 2h30, um horário que o relógio pulou?

Entre 1h e 3h da manhã daquele domingo passou só **uma** hora de verdade. E somar uma hora à 1h dá 3h: o relógio de parede salta, o tempo não.

## A sobreposição: um horário que acontece duas vezes

Em 3 de novembro, 1h30 acontece primeiro em `-04:00` e, uma hora depois, de novo em `-05:00`. Diante da ambiguidade, o Java escolhe o deslocamento **anterior**, o primeiro 1h30. Os métodos `withLaterOffsetAtOverlap` e `withEarlierOffsetAtOverlap` escolhem explicitamente:

```java executar
import java.time.LocalDateTime;
import java.time.ZoneId;
import java.time.ZonedDateTime;

public class Sobreposicao {
    public static void main(String[] args) {
        ZoneId ny = ZoneId.of("America/New_York");
        ZonedDateTime primeira = ZonedDateTime.of(LocalDateTime.of(2024, 11, 3, 1, 30), ny);
        ZonedDateTime segunda = primeira.withLaterOffsetAtOverlap(); //> A segunda 1h30, em -05:00.
        System.out.println(primeira);
        System.out.println(segunda);
        System.out.println(primeira.plusHours(1));
        System.out.println(primeira.isBefore(segunda) + " " + primeira.toLocalDateTime().equals(segunda.toLocalDateTime()));
    }
}
```

```saida
2024-11-03T01:30-04:00[America/New_York]
2024-11-03T01:30-05:00[America/New_York]
2024-11-03T01:30-05:00[America/New_York]
true true
```

Somar uma hora à primeira 1h30 dá... 1h30 de novo, agora em `-05:00`. Os dois objetos têm a mesma hora de parede e instantes diferentes.

> [!CONVERSA]
> **Relógio de parede:** Hoje eu pulei das 2h para as 3h. Para mim, as 2h30 simplesmente não existiram.
>
> **UTC:** Para mim, nada pulou: foram 60 minutos como outros quaisquer.
>
> **Relógio de parede:** E em novembro eu volto das 2h para a 1h, e mostro 1h30 duas vezes.
>
> **UTC:** E eu continuo andando para a frente. Por isso, quando alguém quer saber quanto tempo passou, pergunta para mim.
>
> **Relógio de parede:** E quando quer saber a que horas o alarme toca, pergunta para mim.

## Um dia nem sempre tem 24 horas

Aqui o [episódio 2](/assistir/pleno-t4-e02) cobra a conta. Somar um `Period` de um dia mantém o horário de parede; somar uma `Duration` de 24 horas mantém o tempo decorrido:

```java executar
import java.time.Duration;
import java.time.LocalDateTime;
import java.time.ZoneId;
import java.time.ZonedDateTime;
import java.time.temporal.ChronoUnit;

public class DiaCurto {
    public static void main(String[] args) {
        ZonedDateTime sabado = ZonedDateTime.of(LocalDateTime.of(2024, 3, 9, 12, 0), ZoneId.of("America/New_York"));
        ZonedDateTime domingo = sabado.plusDays(1); //> Mantém o meio-dia: o dia teve 23 horas.
        System.out.println(domingo);
        System.out.println(sabado.plus(Duration.ofHours(24)));
        System.out.println(Duration.between(sabado, domingo) + " " + ChronoUnit.HOURS.between(sabado, domingo));
    }
}
```

```saida
2024-03-10T12:00-04:00[America/New_York]
2024-03-10T13:00-04:00[America/New_York]
PT23H 23
```

O domingo do início do horário de verão tem 23 horas. Um alarme "todo dia ao meio-dia" deve usar `plusDays`; um temporizador "daqui a 24 horas" deve usar `Duration`.

> [!LAPIS]
> Um plantão em Nova York começa às 22h de sábado, 9 de março de 2024, e termina às 6h de domingo, 10 de março. Quantas horas o plantão teve?
>
> **Resposta:** 7 horas. As 22h de sábado, em `-05:00`, são 3h de domingo em UTC; as 6h de domingo, já em `-04:00`, são 10h em UTC. De 3h a 10h são 7 horas, uma a menos que as 8 do relógio de parede.

> [!MATEMATICA]
> O custo de contar todo dia como 24 horas: em Nova York, um dia por ano tem 23 horas e outro tem 25. Um sistema que paga plantões noturnos pelo relógio de parede paga 1 hora a mais em março e 1 a menos em novembro, por pessoa. Com 500 vigias de plantão nas duas noites, são 500 horas pagas a mais numa e 500 a menos na outra, e as duas folhas de pagamento estão erradas.

> [!PROVA]
> Na lacuna, o horário inexistente é empurrado para a frente pelo tamanho dela: 2h30 vira 3h30. Na sobreposição, vale o deslocamento anterior. `Duration.between` mede tempo real: da 1h às 3h do dia da lacuna passa uma hora. Para resolver essas questões, converta para UTC e conte.

## No Brasil

O Brasil teve horário de verão até 2019, com uma particularidade: a mudança acontecia à **meia-noite**. No primeiro domingo de novembro de 2018, o relógio de São Paulo pulou de 0h para 1h, e o dia começou à 1h da manhã. É por isso que `atStartOfDay` tem uma versão que recebe o fuso:

```java executar
import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.ZoneId;
import java.time.ZonedDateTime;

public class Brasil {
    public static void main(String[] args) {
        ZoneId sp = ZoneId.of("America/Sao_Paulo");
        LocalDate eleicao = LocalDate.of(2018, 11, 4);
        System.out.println(eleicao.atStartOfDay() + " " + eleicao.atStartOfDay(sp));

        ZonedDateTime fimDoVerao = ZonedDateTime.of(LocalDateTime.of(2019, 2, 16, 23, 30), sp);
        System.out.println(fimDoVerao + " " + fimDoVerao.withLaterOffsetAtOverlap());
    }
}
```

```saida
2018-11-04T00:00 2018-11-04T01:00-02:00[America/Sao_Paulo]
2019-02-16T23:30-02:00[America/Sao_Paulo] 2019-02-16T23:30-03:00[America/Sao_Paulo]
```

Sem fuso, `atStartOfDay()` devolve um `LocalDateTime` à meia-noite, um horário que em São Paulo simplesmente não existiu naquele dia. Com o fuso, o Java devolve o primeiro instante real do dia: 1h. A segunda linha mostra o fim daquele horário de verão: em 16 de fevereiro de 2019, à meia-noite, o relógio voltou para 23h, e 23h30 aconteceu duas vezes. Código que agendava tarefas para "meia-noite" em fusos brasileiros quebrava todo mês de novembro.

> [!PREVENCAO]
> Teste o código de datas com um fuso que tem horário de verão, como `America/New_York` ou `Europe/Lisbon`, e com as datas exatas de mudança. Um fuso sem horário de verão, como o de São Paulo desde 2019, faz todos os testes passarem e esconde os bugs deste episódio até o código rodar em outro país.

> [!IA]
> Assistentes de IA calculam durações com `LocalDateTime`, que ignora o horário de verão, e somam 24 horas onde deveriam somar um dia. Como o Brasil não tem mais horário de verão, os testes daqui passam com qualquer uma das versões. Peça testes com `America/New_York` em 10 de março e 3 de novembro de 2024 e confira os resultados.

## Na IDE

- **A próxima transição.** Com *Evaluate Expression*, `Alt+F8`, `ZoneId.of("America/New_York").getRules().nextTransition(Instant.now())` mostra a próxima mudança de horário.
- **Parar na mudança de deslocamento.** Clique com o botão direito num *breakpoint* e escreva uma *Condition*, como `z.getOffset().getTotalSeconds() != -18000`, para o depurador parar só quando o deslocamento mudar.
- **Testes com as datas certas.** `Ctrl+Shift+T` cria a classe de teste; acrescente casos para as duas datas de transição do ano no fuso que o sistema atende.

## Por baixo dos panos

Um `ZoneId` como `America/New_York` carrega um objeto `ZoneRules`, com a lista de **transições** do fuso: cada momento em que o deslocamento mudou ou vai mudar. Para transformar uma data e hora de parede num instante, o Java pergunta às regras quais deslocamentos são válidos para aquele horário:

```java executar
import java.time.Instant;
import java.time.LocalDateTime;
import java.time.ZoneId;
import java.time.zone.ZoneRules;

public class Transicoes {
    public static void main(String[] args) {
        ZoneRules regras = ZoneId.of("America/New_York").getRules();
        System.out.println(regras.nextTransition(Instant.parse("2024-01-01T00:00:00Z")));
        System.out.println(regras.getValidOffsets(LocalDateTime.of(2024, 6, 1, 12, 0)));
        System.out.println(regras.getValidOffsets(LocalDateTime.of(2024, 3, 10, 2, 30)));
        System.out.println(regras.getValidOffsets(LocalDateTime.of(2024, 11, 3, 1, 30)));
    }
}
```

```saida
Transition[Gap at 2024-03-10T02:00-05:00 to -04:00]
[-04:00]
[]
[-04:00, -05:00]
```

Um horário normal tem **um** deslocamento válido. Na lacuna, **nenhum**, e o Java ajusta a hora para a frente. Na sobreposição, **dois**, e o Java fica com o primeiro, a menos que você peça o outro. Essas três respostas explicam todo o comportamento deste episódio.

O horário de verão em si é uma convenção política. Ele foi adotado em larga escala na Primeira Guerra Mundial para economizar carvão, e a economia de energia que justificaria mantê-lo é disputada até hoje; foi esse o argumento do governo brasileiro para aboli-lo em 2019. Para quem programa, a lição é outra: nunca calcule fusos à mão, e guarde o `ZoneId` junto com a hora de parede de eventos futuros, porque as regras podem mudar antes de o evento acontecer.

## Resumo para a prova

- Lacuna (o relógio adianta): o horário inexistente é empurrado para a frente pelo tamanho da lacuna
- Sobreposição (o relógio atrasa): vale o deslocamento anterior; `withLaterOffsetAtOverlap` escolhe o outro
- `plusDays(1)` mantém a hora de parede; `plus(Duration.ofHours(24))` mantém o tempo decorrido
- `Duration.between` mede tempo real: no dia da lacuna, da 1h às 3h passa uma hora
- No Brasil, a mudança era à meia-noite: `atStartOfDay(zona)` podia devolver 1h
- `ZoneRules.getValidOffsets` devolve zero, um ou dois deslocamentos para um horário de parede
