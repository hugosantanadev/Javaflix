"A reunião é às 10h" só faz sentido se alguém sabe **onde**. As 10h de São Paulo e as 10h de Lisboa são momentos diferentes do tempo. Até aqui, as classes `Local` ignoravam isso. Este episódio apresenta as que não ignoram: `Instant`, um ponto absoluto na linha do tempo, e `ZonedDateTime`, uma data e hora presa a um fuso.

> [!ANTES]
> O antigo `java.util.Date` guardava milissegundos desde 1970, um instante de verdade, mas o `toString` imprimia no fuso da máquina e fazia parecer que a data tinha fuso. E `TimeZone.getTimeZone("America/Brasilia")`, com um nome que não existe, não dava erro: devolvia o GMT em silêncio. No `java.time`, do Java 8, o mesmo nome lança `ZoneRulesException`.

## Instant: um ponto na linha do tempo

Um `Instant` conta segundos e nanossegundos desde a **época Unix**, 1º de janeiro de 1970 à meia-noite em UTC. Ele não tem fuso, não tem calendário e não sabe o que é "mês": é a forma de registrar quando algo aconteceu, como num log ou num banco de dados. O `toString` sempre mostra o horário em UTC, com um `Z` no fim (de *Zulu*, o nome militar do fuso zero).

```java executar
import java.time.Duration;
import java.time.Instant;
import java.time.temporal.ChronoUnit;

public class Instantes {
    public static void main(String[] args) {
        System.out.println(Instant.ofEpochSecond(0) + " " + Instant.ofEpochMilli(1500));
        Instant pedido = Instant.parse("2024-03-15T13:00:00Z"); //> Z: o horário está em UTC.
        System.out.println(pedido.getEpochSecond() + " " + pedido.toEpochMilli());
        System.out.println(pedido.plus(Duration.ofHours(25)) + " " + pedido.plus(2, ChronoUnit.DAYS) + " " + pedido.truncatedTo(ChronoUnit.DAYS));
    }
}
```

```saida
1970-01-01T00:00:00Z 1970-01-01T00:00:01.500Z
1710507600 1710507600000
2024-03-16T14:00:00Z 2024-03-17T13:00:00Z 2024-03-15T00:00:00Z
```

`Instant` aceita unidades até dias, que para ele são sempre 86.400 segundos. Somar meses ou anos lança `UnsupportedTemporalTypeException`, porque o tamanho de um mês depende de um calendário e de um fuso que o instante não tem.

## Fusos: ZoneId e ZoneOffset

Um **deslocamento** (`ZoneOffset`) é uma diferença fixa em relação ao UTC, como `-03:00`. Um **fuso** (`ZoneId`) é uma região com regras que mudam com o tempo, como `America/Sao_Paulo`: hoje ele é `-03:00`, mas em 2018 passava parte do ano em `-02:00`, no horário de verão. Os nomes seguem o padrão `Continente/Cidade` do banco de dados de fusos da IANA.

| Fuso | Deslocamento em 2024 |
|---|---|
| `America/Sao_Paulo` | `-03:00` (Brasília) |
| `America/Manaus` | `-04:00` |
| `America/Rio_Branco` | `-05:00` |
| `America/Noronha` | `-02:00` |

Não existe `America/Brasilia`: `ZoneId.of` com um nome desconhecido lança `ZoneRulesException`. `ZoneId.of("-03:00")` e `ZoneOffset.of("-03:00")` criam deslocamentos fixos, e `ZoneOffset.UTC` é o zero.

> [!ERRO]
> Inventar o nome de um fuso, como `ZoneId.of("America/Brasilia")`. A JVM recusa com `ZoneRulesException: Unknown time-zone ID: America/Brasilia`. O horário de Brasília é `America/Sao_Paulo`; os nomes válidos vêm do banco da IANA e estão em `ZoneId.getAvailableZoneIds()`.

> [!PERGUNTAS]
> **P:** Para guardar o fuso de um usuário, uso `ZoneId` ou `ZoneOffset`?
>
> **R:** `ZoneId`. Ele conhece as regras do lugar, inclusive mudanças futuras de horário de verão; um deslocamento fixo fica errado quando a regra muda.
>
> **P:** Que tipo uso para gravar quando algo aconteceu?
>
> **R:** Um instante: `Instant` no Java e uma coluna com fuso no banco. O fuso de exibição é decidido na tela, para cada pessoa.
>
> **P:** `ZoneId.systemDefault()` é seguro?
>
> **R:** Num servidor, ele depende da configuração da máquina. Passe o fuso explicitamente, e rode os servidores em UTC.

## ZonedDateTime: data, hora e fuso

Um `ZonedDateTime` junta um `LocalDateTime`, um `ZoneId` e o deslocamento em vigor naquele momento. É ele que representa "10h em São Paulo". As conversões entre os três mundos são diretas:

```java executar
import java.time.Instant;
import java.time.LocalDateTime;
import java.time.ZoneId;
import java.time.ZoneOffset;
import java.time.ZonedDateTime;

public class Fusos {
    public static void main(String[] args) {
        ZoneId sp = ZoneId.of("America/Sao_Paulo");
        Instant i = Instant.parse("2024-03-15T13:00:00Z");
        ZonedDateTime emSp = i.atZone(sp); //> O mesmo instante, visto em São Paulo.
        System.out.println(emSp + " " + emSp.getOffset());
        System.out.println(emSp.toLocalDateTime() + " " + emSp.toInstant());

        LocalDateTime parede = LocalDateTime.of(2024, 3, 15, 10, 0);
        System.out.println(parede.atZone(sp) + " " + parede.toInstant(ZoneOffset.ofHours(-3)));
    }
}
```

```saida
2024-03-15T10:00-03:00[America/Sao_Paulo] -03:00
2024-03-15T10:00 2024-03-15T13:00:00Z
2024-03-15T10:00-03:00[America/Sao_Paulo] 2024-03-15T13:00:00Z
```

> [!PENSE]
> Por que `ZonedDateTime.toInstant()` não precisa de argumento, e `LocalDateTime.toInstant(...)` precisa? O que um tem que o outro não tem?

Um `LocalDateTime` não vira `Instant` sozinho: falta saber onde. Por isso `toInstant` exige um `ZoneOffset` como argumento, e `ldt.toInstant()` sem argumentos não compila.

## Mudando de fuso: mesmo instante ou mesma hora

Há duas formas de "trocar o fuso", e elas respondem perguntas diferentes:

```java executar
import java.time.Duration;
import java.time.LocalDateTime;
import java.time.ZoneId;
import java.time.ZonedDateTime;

public class TrocandoFuso {
    public static void main(String[] args) {
        ZonedDateTime sp = ZonedDateTime.of(LocalDateTime.of(2024, 3, 15, 10, 0), ZoneId.of("America/Sao_Paulo"));
        ZonedDateTime mesmoInstante = sp.withZoneSameInstant(ZoneId.of("Europe/Lisbon")); //> 13h em Lisboa: o mesmo momento.
        ZonedDateTime mesmaHora = sp.withZoneSameLocal(ZoneId.of("Europe/Lisbon"));
        System.out.println(mesmoInstante + " " + mesmaHora);
        System.out.println(sp.equals(mesmoInstante) + " " + sp.isEqual(mesmoInstante));

        ZonedDateTime partida = ZonedDateTime.of(LocalDateTime.of(2024, 7, 10, 22, 0), ZoneId.of("America/Sao_Paulo"));
        ZonedDateTime chegada = ZonedDateTime.of(LocalDateTime.of(2024, 7, 11, 12, 30), ZoneId.of("Europe/Lisbon"));
        System.out.println("voo: " + Duration.between(partida, chegada));
    }
}
```

```saida
2024-03-15T13:00Z[Europe/Lisbon] 2024-03-15T10:00Z[Europe/Lisbon]
false true
voo: PT10H30M
```

`withZoneSameInstant` responde "que horas são em Lisboa **neste mesmo momento**?". `withZoneSameLocal` responde "e se fossem 10h em Lisboa?", outro instante. Repare também em `equals` e `isEqual`: `equals` compara data, hora e fuso, e dá `false` para o mesmo momento em fusos diferentes; `isEqual` compara só o instante.

O voo mostra o caso clássico de prova: 22h em São Paulo (`-03:00`) é 01h UTC; 12h30 em Lisboa no verão (`+01:00`) é 11h30 UTC. A diferença é de 10 horas e meia, não as 14h30 que a conta ingênua sugeriria.

> [!LAPIS]
> Um voo sai do Rio, no fuso `America/Sao_Paulo`, às 23h de 10 de julho de 2024, e chega a Nova York às 7h de 11 de julho, quando lá vale o horário de verão, `-04:00`. Quanto dura o voo?
>
> **Resposta:** 9 horas. A partida, 23h em `-03:00`, é 2h do dia 11 em UTC; a chegada, 7h em `-04:00`, é 11h em UTC. De 2h a 11h são 9 horas, e `Duration.between` dá `PT9H`.

> [!PROVA]
> Converta tudo para UTC antes de fazer a conta. Para o deslocamento, lembre que `-03:00` significa "três horas **atrás** do UTC": some 3 para chegar ao UTC. `equals` compara também o fuso; `isEqual`, `isBefore` e `isAfter` comparam só o instante.

> [!IA]
> Assistentes de IA costumam guardar momentos em `LocalDateTime`, inventar fusos como `America/Brasilia` e usar `ZoneId.systemDefault()` sem pensar no servidor. Peça `Instant` para registrar e `ZonedDateTime` só para exibir, e teste a conversão com dois fusos diferentes, um deles com horário de verão.

## Na IDE

- **Os fusos válidos.** Com *Evaluate Expression*, `Alt+F8`, `ZoneId.getAvailableZoneIds()` lista os nomes do banco embutido no JDK.
- **O fuso da JVM nos testes.** Em *Run > Edit Configurations*, a opção `-Duser.timezone=UTC` em *VM options* fixa o fuso padrão e expõe códigos que dependem do fuso da máquina.
- **As partes no depurador.** Um `ZonedDateTime` aparece com `dateTime`, `offset` e `zone` separados, o jeito mais rápido de ver qual deslocamento foi aplicado.

## Por baixo dos panos

As regras de cada fuso vêm do **tz database** da IANA, mantido por voluntários desde os anos 1980 e usado por Linux, macOS, Android e pelo próprio Java, que o embute num arquivo `tzdb.dat`. Governos mudam regras com frequência, às vezes com poucas semanas de aviso, e cada mudança gera uma nova versão do banco. O Brasil aboliu o horário de verão em abril de 2019, pelo Decreto 9.772: um JDK antigo, sem a atualização, continuaria adiantando os relógios de `America/Sao_Paulo` em novembro. A Oracle distribui a ferramenta `tzupdater` justamente para atualizar o banco sem trocar o JDK.

```java executar
import java.time.Instant;
import java.time.ZoneId;

public class Regras {
    public static void main(String[] args) {
        ZoneId sp = ZoneId.of("America/Sao_Paulo");
        System.out.println(sp.getRules().isDaylightSavings(Instant.parse("2018-12-01T12:00:00Z")));
        System.out.println(sp.getRules().isDaylightSavings(Instant.parse("2024-12-01T12:00:00Z")));
        System.out.println(sp.getRules().nextTransition(Instant.parse("2024-01-01T00:00:00Z")));
    }
}
```

```saida
true
false
null
```

Não há próxima transição em São Paulo: desde 2019, o fuso é fixo. A época Unix também guarda uma curiosidade. Sistemas que contam os segundos num `int` de 32 bits estouram em 19 de janeiro de 2038, às 03:14:07 UTC, o "problema do ano 2038". O `Instant` usa um `long`, e vai até o ano um bilhão.

> [!MATEMATICA]
> A conta do ano 2038: o maior `int` é 2³¹ - 1 = 2.147.483.647. Dividindo pelos 31.556.952 segundos de um ano médio, dá uns **68 anos**: 1970 + 68 = 2038, e o estouro cai em 19 de janeiro, às 03:14:07 UTC. Com um `long`, o limite seria de uns 292 bilhões de anos; o `Instant` para no ano 1.000.000.000 por escolha da API.

## Resumo para a prova

- `Instant`: segundos desde 1970-01-01T00:00Z; `toString` sempre em UTC com `Z`; não aceita meses nem anos
- `ZoneOffset` é fixo (`-03:00`); `ZoneId` tem regras que mudam (`America/Sao_Paulo`)
- `ZonedDateTime` = `LocalDateTime` + `ZoneId` + deslocamento em vigor
- `LocalDateTime.toInstant` exige um `ZoneOffset`
- `withZoneSameInstant` muda o fuso mantendo o momento; `withZoneSameLocal` mantém a hora de parede
- `equals` compara o fuso; `isEqual` compara só o instante
