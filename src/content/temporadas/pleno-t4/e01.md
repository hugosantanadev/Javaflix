Datas parecem simples até o primeiro bug: um ano bissexto, um mês de 30 dias, um fuso horário. O Java levou quase vinte anos para ter uma API de datas que não atrapalhasse. Esta temporada cobre o pacote `java.time`, do Java 8, começando pelas três classes sem fuso horário: `LocalDate`, `LocalTime` e `LocalDateTime`.

> [!ANTES]
> Antes do Java 8, uma conta simples de datas era assim: `Calendar c = Calendar.getInstance(); c.set(2024, Calendar.MARCH, 15); c.add(Calendar.DAY_OF_MONTH, 10);`, com um objeto mutável que qualquer método podia alterar. Por quase dez anos, a saída foi a biblioteca Joda-Time, de 2005, que todo projeto sério incluía. O `java.time`, do Java 8, de 2014, é a evolução dela dentro do JDK.

## Por que java.time

As classes antigas, `java.util.Date` e `Calendar`, eram conhecidas pelos tropeços: objetos mutáveis, meses contados a partir de **zero**, o ano de `Date` contado a partir de 1900, e um formatador, `SimpleDateFormat`, que corrompia resultados quando usado por várias threads. `new Date(2024, 2, 15)` representa 15 de **março** do ano **3924**.

O `java.time` nasceu da JSR 310, liderada por Stephen Colebourne, autor da biblioteca Joda-Time, e corrige tudo isso:

- Todos os objetos são **imutáveis** e seguros entre threads
- Meses vão de 1 a 12, e existe o enum `Month`
- Cada conceito tem a sua classe: data, hora, data com hora, instante, fuso, período

| Classe | Representa | Exemplo de `toString` |
|---|---|---|
| `LocalDate` | Uma data, sem hora nem fuso | `2024-03-15` |
| `LocalTime` | Uma hora do dia, sem data nem fuso | `14:30` |
| `LocalDateTime` | Data e hora, sem fuso | `2024-03-15T14:30` |

"Local" significa "como se lê num calendário e num relógio de parede", sem dizer onde. Um aniversário é um `LocalDate`; o horário de abertura de uma loja é um `LocalTime`.

## Criando datas e horas

Não há construtores públicos: `new LocalDate()` não compila. Os objetos nascem de métodos estáticos de fábrica:

```java executar
import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.LocalTime;
import java.time.Month;

public class Criando {
    public static void main(String[] args) {
        LocalDate d1 = LocalDate.of(2024, 3, 15);
        LocalDate d2 = LocalDate.of(2024, Month.MARCH, 15); //> O enum Month evita o número solto.
        LocalDate d3 = LocalDate.parse("2024-03-15");
        System.out.println(d1 + " " + d1.equals(d2) + " " + d2.equals(d3));

        System.out.println(LocalTime.of(14, 30) + " " + LocalTime.of(14, 30, 5) + " " + LocalTime.of(14, 30, 5, 500_000_000));

        LocalDateTime reuniao = LocalDateTime.of(2024, 3, 15, 9, 5);
        System.out.println(reuniao + " " + d1.atTime(18, 0) + " " + d1.atStartOfDay());
        System.out.println(d1.getDayOfWeek() + " " + d1.getMonth() + " " + d1.getMonthValue() + " " + d1.getDayOfYear() + " " + d1.isLeapYear());
    }
}
```

```saida
2024-03-15 true true
14:30 14:30:05 14:30:05.500
2024-03-15T09:05 2024-03-15T18:00 2024-03-15T00:00
FRIDAY MARCH 3 75 true
```

Repare no `toString` de `LocalTime`: os segundos só aparecem quando não são zero, e as frações, só quando existem. `LocalDate.now()` e companhia leem o relógio do sistema; os exemplos desta temporada usam datas fixas para que a saída seja sempre a mesma.

Valores impossíveis lançam `DateTimeException` na hora da criação: `LocalDate.of(2023, 2, 29)` (2023 não é bissexto), mês 13, `LocalTime.of(24, 0)`. Um texto fora do formato ISO em `parse`, como `"2024-3-15"`, lança `DateTimeParseException`.

> [!ERRO]
> Criar uma data que não existe, como `LocalDate.of(2023, 2, 29)`. A falha vem na hora, com `DateTimeException: Invalid date 'February 29' as '2023' is not a leap year`; uma hora 24 dá `Invalid value for HourOfDay (valid values 0 - 23): 24`. Quando a data vem de um formulário, trate a exceção e mostre uma mensagem clara, em vez de deixar o erro subir.

> [!PERGUNTAS]
> **P:** `LocalDateTime` serve para gravar quando um pedido foi feito?
>
> **R:** Não sozinho: ele não diz o fuso, e o mesmo valor significa momentos diferentes em São Paulo e em Lisboa. Para um momento, use `Instant` ou `OffsetDateTime`, assunto do [episódio 3](/assistir/pleno-t4-e03).
>
> **P:** Posso comparar datas com `==`?
>
> **R:** Não. As classes são *value-based*: compare com `equals`, `isEqual` ou `compareTo`.
>
> **P:** Como testar um código que usa `LocalDate.now()`?
>
> **R:** Receba um `Clock` e passe `Clock.fixed(...)` nos testes: `LocalDate.now(relogio)` passa a devolver sempre a mesma data.

## Imutáveis: todo cálculo devolve um objeto novo

Os métodos `plusX`, `minusX` e `withX` não alteram o objeto; devolvem outro. Ignorar o retorno é a armadilha mais comum da prova:

```java executar
import java.time.LocalDate;
import java.time.LocalTime;

public class Calculos {
    public static void main(String[] args) {
        LocalDate d = LocalDate.of(2024, 3, 15);
        d.plusDays(10); //> Resultado descartado: d não muda.
        System.out.println(d);
        d = d.plusDays(10);
        System.out.println(d);

        LocalDate fimDeJaneiro = LocalDate.of(2024, 1, 31);
        System.out.println(fimDeJaneiro.plusMonths(1) + " " + fimDeJaneiro.plusMonths(2));
        System.out.println(LocalDate.of(2024, 2, 29).plusYears(1));
        System.out.println(LocalTime.of(23, 0).plusHours(2) + " " + LocalTime.of(0, 15).minusMinutes(30));
    }
}
```

```saida
2024-03-15
2024-03-25
2024-02-29 2024-03-31
2025-02-28
01:00 23:45
```

> [!PENSE]
> Por que 31 de janeiro mais um mês deu 29 de fevereiro, e não 2 ou 3 de março? E 31 de janeiro mais dois meses deu 31 de março, e não 29: o que isso diz sobre como o cálculo é feito?

Quando o dia não existe no mês de destino, o cálculo usa o **último dia válido**: 31 de janeiro mais um mês é 29 de fevereiro (2024 é bissexto), e 29 de fevereiro mais um ano é 28 de fevereiro. Horas dão a volta na meia-noite sem mudar data nenhuma, porque um `LocalTime` não tem data.

![Em cima, 31 de janeiro mais um mês vira 29 de fevereiro, o último dia válido, e mais um mês a partir dele dá 29 de março; embaixo, 31 de janeiro mais dois meses, a partir da data original, dá 31 de março](/figuras/ultimo-dia-valido.svg "Quando o dia não existe, vale o último dia válido; encadeando, o ajuste se propaga.")

> [!PROVA]
> Cada classe só aceita as unidades que fazem sentido para ela: `LocalDate` não tem `plusHours`, e `LocalTime` não tem `plusDays`. Chamar um deles **não compila**. E `d.plusDays(1);` sem atribuir o resultado não muda `d`.

## Ajustando com with

`withDayOfMonth`, `withMonth`, `withYear` e companhia trocam um campo. Para ajustes mais espertos, `with` recebe um `TemporalAdjuster`, e a classe `TemporalAdjusters` traz os prontos:

```java executar
import java.time.DayOfWeek;
import java.time.LocalDate;
import java.time.temporal.TemporalAdjusters;

public class Ajustes {
    public static void main(String[] args) {
        LocalDate d = LocalDate.of(2024, 3, 15);
        System.out.println(d.withDayOfMonth(1) + " " + d.with(TemporalAdjusters.lastDayOfMonth()));
        System.out.println(d.with(TemporalAdjusters.next(DayOfWeek.MONDAY)) + " " + d.with(TemporalAdjusters.firstInMonth(DayOfWeek.FRIDAY))); //> next: a próxima segunda, estritamente depois.
        System.out.println(d.isBefore(LocalDate.of(2024, 4, 1)) + " " + d.isAfter(d) + " " + d.isEqual(LocalDate.parse("2024-03-15")));
    }
}
```

```saida
2024-03-01 2024-03-31
2024-03-18 2024-03-01
true false true
```

Para comparar, use `isBefore`, `isAfter`, `isEqual`, `equals` ou `compareTo`. Os enums `Month` e `DayOfWeek` também fazem contas: `Month.JANUARY.plus(13)` é `FEBRUARY`, e `DayOfWeek.SUNDAY.plus(1)` é `MONDAY`.

> [!LAPIS]
> Com `d = 2024-03-15`, uma sexta-feira, quanto valem `d.with(TemporalAdjusters.previous(DayOfWeek.FRIDAY))`, `d.with(TemporalAdjusters.nextOrSame(DayOfWeek.FRIDAY))` e `d.withDayOfMonth(31)`?
>
> **Resposta:** `2024-03-08`, `2024-03-15` e `2024-03-31`. `previous` é estrito e volta uma semana; `nextOrSame` aceita o próprio dia; e março tem 31 dias, então o `withDayOfMonth(31)` é válido.

> [!IA]
> Assistentes de IA ainda geram código com `Date`, `Calendar` e `SimpleDateFormat`, ou misturam as duas APIs no mesmo método. Peça `java.time` explicitamente e, nos cálculos de fim de mês e de ano bissexto, rode os casos de 31 de janeiro e de 29 de fevereiro antes de confiar no resultado.

## Na IDE

- **API antiga marcada.** A inspeção *Use of obsolete date-time API* destaca `Date`, `Calendar` e `SimpleDateFormat` no código.
- **Resultado ignorado.** O IntelliJ avisa quando o resultado de `plusDays` ou de `withMonth` é descartado, o erro clássico com objetos imutáveis.
- **Testar uma conta na hora.** No depurador, *Evaluate Expression*, `Alt+F8`, calcula `LocalDate.of(2024, 1, 31).plusMonths(1)` sem rodar o programa de novo.

## Por baixo dos panos

Um `LocalDate` guarda três campos, `year` (`int`), `month` e `day` (`short`), e nada mais. Para fazer contas de dias, ele converte para o **dia da época**, a quantidade de dias desde 1º de janeiro de 1970 (`toEpochDay()`), soma e converte de volta. O calendário usado é o gregoriano *proléptico*: as regras de hoje aplicadas para trás no tempo, mesmo antes de 1582, quando o calendário gregoriano foi adotado.

> [!MATEMATICA]
> A regra do ano bissexto: divisível por 4, menos os divisíveis por 100, a não ser que também sejam por 400. Por isso 1900 não foi bissexto e 2000 foi. Num ciclo de 400 anos, são 100 - 4 + 1 = **97** bissextos, e o ano médio tem 365 + 97/400 = **365,2425** dias, a 26 segundos do ano solar. É essa conta que `isLeapYear()` faz por você.

As classes de `java.time` são *value-based*: o que importa é o valor, não a identidade do objeto. A documentação avisa para não usar `==`, não sincronizar sobre elas e não depender de dois `LocalDate.of(...)` iguais serem ou não o mesmo objeto. Esse cuidado prepara o terreno para o Projeto Valhalla, que pretende transformá-las em *value classes*, sem identidade e guardadas direto nos arrays, sem referências.

## Resumo para a prova

- `LocalDate`, `LocalTime` e `LocalDateTime` não têm fuso; criam-se com `of`, `parse` e `now`, nunca com `new`
- Meses vão de 1 a 12; valores impossíveis lançam `DateTimeException`
- Objetos imutáveis: `plus`, `minus` e `with` devolvem um novo objeto
- Dia inexistente no destino vira o último dia válido do mês
- `LocalDate` não tem métodos de hora; `LocalTime` não tem métodos de data
- O `toString` de `LocalTime` omite segundos e frações quando são zero
