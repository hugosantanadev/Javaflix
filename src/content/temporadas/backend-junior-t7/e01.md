As seis temporadas anteriores deram as peças: Git, HTTP, SQL, Spring Boot, JPA e testes. Esta temporada junta tudo numa **API de pedidos** de uma loja, feita do zero, como num primeiro trabalho. Antes de abrir o Spring Initializr, porém, vem a etapa que separa um projeto que termina de um que vira remendo: **planejar**. Neste episódio, você sai com o contrato da API, as regras do pedido escritas como código e a lista do que precisa ser testado.

## O que a API faz

O pedido de quem encomendou o projeto chega assim: "o cliente monta um pedido com produtos, paga, a loja envia e marca como entregue; até ser enviado, dá para cancelar". Uma frase dessas esconde dezenas de decisões. O primeiro trabalho é transformá-la em **histórias** com **critérios de aceitação**, frases que dizem quando cada coisa está pronta:

- Como cliente, quero criar um pedido com itens, e o total é a soma de preço vezes quantidade.
- Como cliente, quero cancelar um pedido ainda não enviado; um pedido enviado não pode ser cancelado.
- Como loja, quero listar os pedidos por situação, do mais novo para o mais antigo, em páginas de 20.

Cada critério vira, mais tarde, pelo menos um teste. Se você não consegue escrever o teste, o critério ainda está vago.

> [!PENSE]
> "Até ser enviado, dá para cancelar." Um pedido criado e ainda não pago pode ser cancelado? E um pedido pago: o dinheiro volta? Antes de seguir, anote as perguntas que você faria a quem pediu o projeto.

## O ciclo de vida do pedido

O coração da API é a situação do pedido e as mudanças permitidas entre elas. Escrever isso como uma **máquina de estados** deixa a regra num lugar só, em vez de espalhada em `if`s pelos controllers:

```java executar
import java.util.EnumSet;
import java.util.Set;

public class Ciclo {
    enum Situacao {
        CRIADO, PAGO, ENVIADO, ENTREGUE, CANCELADO;

        Set<Situacao> proximas() {
            return switch (this) {
                case CRIADO -> EnumSet.of(PAGO, CANCELADO);
                case PAGO -> EnumSet.of(ENVIADO, CANCELADO); //> O pago ainda pode ser cancelado, com estorno.
                case ENVIADO -> EnumSet.of(ENTREGUE);
                case ENTREGUE, CANCELADO -> EnumSet.noneOf(Situacao.class); //> Estados finais: nada sai deles.
            };
        }

        boolean podeIrPara(Situacao destino) {
            return proximas().contains(destino);
        }
    }

    public static void main(String[] args) {
        System.out.println(Situacao.CRIADO.podeIrPara(Situacao.PAGO));
        System.out.println(Situacao.ENVIADO.podeIrPara(Situacao.CANCELADO));
        System.out.println(Situacao.ENTREGUE.proximas());
    }
}
```

```saida
true
false
[]
```

O `switch` sobre o próprio enum tem uma vantagem escondida: se alguém acrescentar uma situação nova, como `DEVOLVIDO`, o `switch` deixa de compilar até a regra dela ser escrita.

![Cinco caixas: CRIADO, PAGO, ENVIADO e ENTREGUE ligadas por setas verdes em sequência, e setas tracejadas laranja de CRIADO e de PAGO para CANCELADO](/figuras/ciclo-do-pedido.svg "Cada seta é uma regra de negócio; uma transição que falta vira 409, não 500.")

> [!LAPIS]
> Usando a máquina acima, quantas sequências diferentes levam um pedido de `CRIADO` até um estado final?
>
> **Resposta:** Três. `CRIADO → CANCELADO`, `CRIADO → PAGO → CANCELADO` e `CRIADO → PAGO → ENVIADO → ENTREGUE`. Cada uma é um cenário de teste de ponta a ponta.

## O contrato antes do código

Com as regras na mão, desenhe as rotas. A API segue o que a [temporada de HTTP](/assistir/backend-junior-t2-e02) ensinou: substantivos no caminho, verbos no método e o status certo para cada resposta.

| Método e caminho | Faz | Sucesso | Erros esperados |
|---|---|---|---|
| `POST /pedidos` | cria um pedido | 201 com `Location` | 400 dados inválidos, 422 produto inexistente |
| `GET /pedidos/{id}` | busca um pedido | 200 | 404 |
| `GET /pedidos?situacao=PAGO&page=0` | lista, paginado | 200 | 400 situação inválida |
| `POST /pedidos/{id}/pagamento` | paga | 200 | 404, 409 se não estiver `CRIADO` |
| `POST /pedidos/{id}/cancelamento` | cancela | 200 | 404, 409 se já foi enviado |

Repare nas ações: "pagar" e "cancelar" não são um `PUT` que troca a situação à mão. São recursos próprios (`/pagamento`, `/cancelamento`), e quem decide se a mudança é permitida é a máquina de estados, no servidor. Um `PATCH {"situacao": "ENTREGUE"}` deixaria o cliente pular etapas.

> [!ENGENHARIA]
> Escreva o contrato num arquivo OpenAPI ou numa tabela como esta **antes** do código e combine com quem vai consumir a API. Mudar uma linha de tabela custa um minuto; mudar uma rota que um aplicativo de celular já usa custa uma versão nova do aplicativo e meses de compatibilidade.

## A conta do tamanho

Antes de escolher tecnologias, estime o volume. Isso decide se uma tabela simples dá conta ou se você precisa de algo mais elaborado.

> [!MATEMATICA]
> A loja espera 3.000 pedidos por dia, com média de 4 itens. Em um ano: 3.000 × 365 = 1.095.000 pedidos e 4.380.000 itens. Com uns 200 bytes por linha de pedido e 100 por item, são cerca de 219 MB + 438 MB, menos de 1 GB por ano: um PostgreSQL comum guarda isso com folga. No pico, se metade dos pedidos chega em 4 horas, são 1.500 ÷ 14.400 s ≈ 0,1 pedido por segundo. Nenhum cache, fila ou microsserviço se justifica por volume aqui.

Essa conta é o que impede o projeto de nascer complicado. A API vai ser um **monolito em camadas**, com um banco só, e isso é uma decisão de engenharia, não falta de ambição.

> [!PERGUNTAS]
> **P:** Não seria melhor começar com microsserviços, já que é o que as vagas pedem?
>
> **R:** Não. Microsserviços resolvem problemas de times grandes e de escala, que esta API não tem. Um monolito bem dividido em pacotes se separa depois, se precisar; o contrário é muito mais caro.
>
> **P:** Preciso desenhar todas as rotas antes de começar?
>
> **R:** As do primeiro corte, sim. As outras entram quando surgir a história que pede cada uma.
>
> **P:** Onde guardo essas decisões?
>
> **R:** Num `README.md` e em registros curtos de decisão (ADRs) na pasta `docs/`, no próprio repositório, que é onde o próximo desenvolvedor vai procurar.

## A estrutura do projeto

O projeto sai do [Spring Initializr](/assistir/backend-junior-t4-e02) com Spring Web, Validation, Data JPA, PostgreSQL, Flyway e os starters de teste. Os pacotes seguem a funcionalidade, não a camada:

```text
br.com.loja.pedidos
├── pedido
│   ├── PedidoController.java
│   ├── PedidoService.java
│   ├── PedidoRepository.java
│   ├── Pedido.java
│   └── Situacao.java
├── produto
│   └── ...
└── comum
    └── TratadorDeErros.java
```

Com pacotes por funcionalidade, tudo o que muda junto fica junto, e as classes podem ser package-private: `PedidoRepository` não precisa ser visível fora de `pedido`.

> [!ANTES]
> Os projetos Java dos anos 2000 começavam com um documento de requisitos de dezenas de páginas, aprovado antes de qualquer linha de código, e com os pacotes `dao`, `bo` e `vo` separados por camada. As metodologias ágeis trocaram o documento por histórias curtas e entregas pequenas, mas não aboliram o planejamento: só o deixaram do tamanho do próximo passo.

## Por baixo dos panos

A rota que o Spring escolhe para cada requisição sai de uma tabela parecida com a do contrato. Este programa imita o que o `DispatcherServlet` faz ao casar método e caminho, com variáveis entre chaves:

```java executar
import java.util.List;

public class Rotas {
    record Rota(String metodo, String padrao, String acao) {
        boolean casa(String m, String caminho) {
            String[] p = padrao.split("/"), c = caminho.split("/");
            if (!metodo.equals(m) || p.length != c.length) return false;
            for (int i = 0; i < p.length; i++) {
                if (!p[i].startsWith("{") && !p[i].equals(c[i])) return false; //> {id} casa com qualquer trecho.
            }
            return true;
        }
    }

    public static void main(String[] args) {
        List<Rota> rotas = List.of(
                new Rota("POST", "/pedidos", "criar"),
                new Rota("GET", "/pedidos/{id}", "buscar"),
                new Rota("POST", "/pedidos/{id}/cancelamento", "cancelar"));
        for (String req : List.of("GET /pedidos/42", "POST /pedidos/42/cancelamento", "DELETE /pedidos/42")) {
            String[] partes = req.split(" ");
            String acao = rotas.stream().filter(r -> r.casa(partes[0], partes[1]))
                    .map(Rota::acao).findFirst().orElse("405 ou 404");
            System.out.println(req + " -> " + acao);
        }
    }
}
```

```saida
GET /pedidos/42 -> buscar
POST /pedidos/42/cancelamento -> cancelar
DELETE /pedidos/42 -> 405 ou 404
```

O Spring real usa o `PathPattern`, que compila cada padrão uma vez e responde 405 quando o caminho existe com outro método. A ideia, porém, é essa: o contrato que você desenhou vira, literalmente, a tabela de rotas da aplicação. Uma máquina de estados é um grafo dirigido; percorrer as sequências possíveis, como no exercício de lápis, é o que a [busca em profundidade](/assistir/aprendiz-t4-e06) faz.

> [!IA]
> Peça à IA para revisar o contrato, não para inventá-lo. Ela costuma propor `PUT /pedidos/{id}` com a situação no corpo, o que deixa o cliente pular etapas, e responder 500 ou 400 para uma transição proibida, quando o certo é 409. Leve as regras escritas e peça para ela listar os cenários que faltam.

## Na IDE

- **Gerar o projeto.** No IntelliJ, *New Project > Spring Boot* usa o Initializr por baixo e já abre o Maven configurado.
- **Enum exaustivo.** Ao acrescentar uma constante ao enum, o `switch` com setas fica vermelho em todos os lugares que não tratam o caso novo.
- **Arquivo HTTP.** Um arquivo `pedidos.http` na raiz guarda as requisições do contrato, e o botão de executar ao lado de cada uma testa a API sem sair da IDE.

## Resumo

- Transforme o pedido em histórias com critérios de aceitação; cada critério vira teste.
- As situações do pedido e as transições permitidas ficam numa máquina de estados, num lugar só.
- Ações como pagar e cancelar são recursos próprios; transição proibida é 409.
- Escreva o contrato antes do código e estime o volume antes de escolher a arquitetura.
- Pacotes por funcionalidade mantêm junto o que muda junto.
