As camadas do [episódio anterior](/assistir/backend-junior-t7-e02) precisam de um banco embaixo. Neste episódio, a API de pedidos ganha as tabelas, as migrations do Flyway, as entidades JPA e as consultas que a listagem e o detalhe vão usar. Cada decisão aqui responde a uma pergunta do negócio: o que acontece com o pedido se o preço do produto mudar amanhã? E se o cliente pagar e cancelar no mesmo segundo?

## O modelo

![Quatro tabelas: clientes, pedidos, itens_pedido e produtos, ligadas de um para muitos; pedidos tem situacao, criado_em e versao em destaque; itens_pedido tem preco_unitario](/figuras/modelo-de-pedidos.svg "O item guarda o preço da compra, e o pedido guarda uma versão para as atualizações concorrentes.")

Duas colunas merecem atenção:

- **`itens_pedido.preco_unitario`.** O item **copia** o preço do produto no momento da compra. Se ele apontasse só para `produtos.preco`, um reajuste amanhã mudaria o total de todos os pedidos antigos, inclusive dos já faturados.
- **`pedidos.versao`.** Um número que sobe a cada atualização e serve de trava otimista, como você vai ver adiante.

O total fica guardado em `pedidos.total`, calculado pelo servidor ao criar. É uma redundância deliberada: a listagem mostra o total sem somar os itens de cada pedido.

> [!PENSE]
> Se o total está guardado e os itens também, o que garante que os dois concordam? Em que lugar do código essa regra precisa estar para nunca ser esquecida?

## As migrations

Com o [Flyway](/assistir/backend-junior-t5-e05), cada mudança no banco é um arquivo versionado, e `ddl-auto=validate` só confere que as entidades batem com as tabelas.

```sql
-- V1__pedidos.sql
create table pedidos (
    id          bigserial primary key,
    cliente_id  bigint        not null references clientes (id),
    situacao    varchar(20)   not null,
    total       numeric(12,2) not null check (total >= 0),
    criado_em   timestamptz   not null default now(),
    versao      bigint        not null default 0
);

create table itens_pedido (
    id             bigserial primary key,
    pedido_id      bigint        not null references pedidos (id) on delete cascade,
    produto_id     bigint        not null references produtos (id),
    quantidade     int           not null check (quantidade > 0),
    preco_unitario numeric(10,2) not null
);

-- V2__indice_listagem.sql
create index idx_pedidos_situacao_criado on pedidos (situacao, criado_em desc);
```

O `numeric(12,2)` é o tipo exato do banco para dinheiro, par do `BigDecimal`. Os `check` repetem no banco as regras mais básicas: se um bug no Java tentar gravar quantidade zero, o banco recusa.

> [!ERRO]
> Editar a `V1` depois que ela rodou em algum ambiente quebra o Flyway: o *checksum* gravado no histórico não bate mais, e a aplicação não sobe. Mudança em tabela que já existe é sempre uma migration nova, como a `V2` do índice.

## As entidades

```java
@Entity
@Table(name = "pedidos")
class Pedido {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Enumerated(EnumType.STRING) //> Grava "PAGO", e não a posição 1 do enum.
    private Situacao situacao = Situacao.CRIADO;

    @OneToMany(mappedBy = "pedido", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<ItemPedido> itens = new ArrayList<>();

    private BigDecimal total = BigDecimal.ZERO;

    @Version
    private long versao;

    void adicionar(Produto produto, int quantidade) {
        itens.add(new ItemPedido(this, produto, quantidade, produto.getPreco())); //> O preço é copiado aqui.
        total = total.add(produto.getPreco().multiply(BigDecimal.valueOf(quantidade)));
    }
}
```

O `adicionar` é a resposta ao "Pense": a entidade só aceita itens por esse método, que atualiza o total junto. Ninguém de fora mexe na lista direto.

O `EnumType.STRING` evita uma armadilha antiga: com o padrão, `ORDINAL`, o banco guarda 0, 1, 2. Se alguém acrescentar uma situação no meio do enum, todos os pedidos antigos mudam de situação sem nenhuma linha de SQL.

```java executar
public class Ordinal {
    enum SituacaoV1 { CRIADO, PAGO, ENVIADO }
    enum SituacaoV2 { CRIADO, AGUARDANDO_PAGAMENTO, PAGO, ENVIADO } //> Alguém inseriu uma constante no meio.

    public static void main(String[] args) {
        int gravadoNoBanco = SituacaoV1.PAGO.ordinal();
        System.out.println("gravado: " + gravadoNoBanco);
        System.out.println("lido depois do deploy: " + SituacaoV2.values()[gravadoNoBanco]);
    }
}
```

```saida
gravado: 1
lido depois do deploy: AGUARDANDO_PAGAMENTO
```

## Pagar e cancelar ao mesmo tempo

O cliente clica em "cancelar" enquanto o gateway confirma o pagamento. Duas requisições leem o pedido `CRIADO` na versão 3, uma muda para `PAGO`, a outra para `CANCELADO`. Sem trava, a última a gravar vence, e a loja fica com um pedido cancelado e pago. Com `@Version`, o Hibernate acrescenta a versão no `where` do `update`:

```sql
update pedidos set situacao = 'CANCELADO', versao = 4 where id = 42 and versao = 3
```

Quem chega em segundo atualiza **zero** linhas, e o Hibernate lança `OptimisticLockException`, que a API traduz para 409. O programa abaixo simula as duas requisições:

```java executar
import java.util.HashMap;
import java.util.Map;

public class TravaOtimista {
    record Linha(String situacao, long versao) {}
    static final Map<Long, Linha> tabela = new HashMap<>(Map.of(42L, new Linha("CRIADO", 3)));

    static int update(long id, String novaSituacao, long versaoLida) {
        Linha atual = tabela.get(id);
        if (atual.versao() != versaoLida) return 0; //> O "and versao = ?" do SQL.
        tabela.put(id, new Linha(novaSituacao, versaoLida + 1));
        return 1;
    }

    public static void main(String[] args) {
        long lidaPeloPagamento = tabela.get(42L).versao();
        long lidaPeloCancelamento = tabela.get(42L).versao();
        System.out.println("pagamento: " + update(42L, "PAGO", lidaPeloPagamento) + " linha");
        System.out.println("cancelamento: " + update(42L, "CANCELADO", lidaPeloCancelamento) + " linhas");
        System.out.println("final: " + tabela.get(42L));
    }
}
```

```saida
pagamento: 1 linha
cancelamento: 0 linhas
final: Linha[situacao=PAGO, versao=4]
```

> [!LAPIS]
> Depois do 409, o aplicativo recarrega o pedido e tenta cancelar de novo. O que acontece agora, pela máquina de estados do e01?
>
> **Resposta:** O pedido está `PAGO`, versão 4. Cancelar a partir de `PAGO` é permitido, então o `update` com `versao = 4` passa, e o pedido vai para `CANCELADO` (com estorno). A trava não decidiu a regra: só garantiu que ela fosse aplicada sobre o estado verdadeiro.

## As consultas

A listagem usa um método derivado com paginação:

```java
interface PedidoRepository extends JpaRepository<Pedido, Long> {
    Page<Pedido> findBySituacaoOrderByCriadoEmDesc(Situacao situacao, Pageable pagina);

    @Query("select p from Pedido p join fetch p.itens i join fetch i.produto where p.id = :id")
    Optional<Pedido> buscarComItens(Long id); //> Uma consulta só para o detalhe, sem N+1.
}
```

O índice `(situacao, criado_em desc)` da `V2` atende exatamente o `where` e o `order by` da listagem, e o banco lê as linhas já na ordem, sem ordenar. No detalhe, o `join fetch` traz pedido, itens e produtos de uma vez.

> [!MATEMATICA]
> A página 50 da listagem, com 20 itens por página, é `limit 20 offset 1000`: o banco percorre 1.020 linhas e descarta 1.000. Para a página n, o custo cresce como 20 × (n + 1). Na página 5.000, são 100.020 linhas lidas para mostrar 20. Para uma tela de loja, ninguém passa da página 10; para exportar tudo, a saída é paginar pela chave (`where criado_em < :ultimo`), que custa o mesmo em qualquer página.

> [!PERGUNTAS]
> **P:** Por que não guardar a situação num `int` para economizar espaço?
>
> **R:** A diferença é de poucos bytes por linha, e o texto deixa o banco legível e imune à ordem do enum.
>
> **P:** `cascade = ALL` não é perigoso?
>
> **R:** Entre pedido e itens, não: o item não existe sem o pedido. Nunca use cascata para entidades independentes, como de item para produto.
>
> **P:** E se eu precisar de mais campos na listagem, como o nome do cliente?
>
> **R:** Faça uma projeção em DTO na própria consulta (`select new ...`), em vez de carregar as entidades inteiras.

> [!ANTES]
> Antes do Flyway e do Liquibase, o banco evoluía com scripts soltos numa pasta, rodados à mão pelo DBA, numa ordem que só ele conhecia. Era comum o banco de homologação ter uma coluna que o de produção não tinha, e descobrir isso no dia do deploy.

## Por baixo dos panos

O `@Version` não usa nenhum recurso especial do banco: é só uma coluna e um `where`. Quem faz o trabalho é o contador de linhas que o JDBC devolve. O `executeUpdate` retorna quantas linhas o `update` alterou, e o Hibernate compara esse número com 1. Se vier 0, ele sabe que outra transação mudou a linha entre a leitura e a gravação. É a mesma ideia do *compare-and-set* das classes atômicas do Java, como o `AtomicLong.compareAndSet`: "troque só se o valor ainda for o que eu li".

Para a base de como o banco guarda um índice em ordem e por que ele evita a ordenação, veja as [árvores](/assistir/aprendiz-t4-e05) da trilha Aprendiz.

> [!IA]
> Ao gerar entidades, a IA costuma esquecer o `@Enumerated(EnumType.STRING)` e o `@Version`, e escrever o item apontando só para o produto, sem copiar o preço. Peça as migrations e as entidades juntas e confira coluna por coluna com o `validate` ligado.

## Na IDE

- **Ver o SQL.** `spring.jpa.show-sql=true` com `logging.level.org.hibernate.orm.jdbc.bind=trace` mostra cada consulta e os valores dos parâmetros no console.
- **Navegar no banco.** No IntelliJ Ultimate, a aba *Database* conecta no PostgreSQL local e mostra as tabelas, os índices e a `flyway_schema_history`.
- **Conferir o plano.** Rode `explain analyze` na consulta da listagem e veja se aparece `Index Scan using idx_pedidos_situacao_criado`.

## Resumo

- O item copia o preço do produto: pedidos antigos não mudam com reajustes.
- Migrations versionadas criam as tabelas, com `numeric` para dinheiro e `check` para as regras básicas; nunca edite uma que já rodou.
- `EnumType.STRING` evita que a ordem do enum mude dados antigos.
- `@Version` faz a trava otimista: a segunda atualização concorrente vira 409.
- O índice acompanha o `where` e o `order by` da listagem, e o detalhe usa `join fetch`.
