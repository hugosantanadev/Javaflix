A API de pedidos já cria, lista, paga e cancela. Falta provar que ela faz isso **sempre**, inclusive depois da próxima mudança. Neste episódio, você monta a suíte de testes do projeto com o que a [temporada de testes](/assistir/backend-junior-t6-e01) ensinou: o que testar em cada camada, quantos testes de cada tipo, e como saber se os testes testam alguma coisa. A cobertura de linhas é parte da resposta, e o episódio mostra por que ela sozinha engana.

## Dos critérios aos testes

Os critérios de aceitação do [e01](/assistir/backend-junior-t7-e01) já são a lista de testes. Cada um vira um ou mais casos, no formato *dado, quando, então*:

| Critério | Teste | Camada |
|---|---|---|
| O total é a soma de preço vezes quantidade | `totalSomaOsItens` | entidade |
| Pedido enviado não pode ser cancelado | `cancelarEnviadoLanca` | entidade |
| Cancelar um enviado responde 409 | `cancelamentoDeEnviadoDa409` | web |
| Produto inexistente responde 422 | `produtoInexistenteDa422` | web |
| A listagem vem do mais novo para o mais antigo | `listagemOrdenadaPorData` | repositório |
| Pagar e cancelar juntos não gravam os dois | `segundaGravacaoConcorrenteFalha` | integração |

Repare na última coluna. A regra do 409 aparece duas vezes, de propósito: a entidade testa que a **regra** existe, e o teste web testa que ela vira o **status** certo. São duas coisas que podem quebrar separadamente.

> A tabela acima tem um teste por critério. A máquina de estados tem 5 situações. Quantas combinações de "situação atual" e "situação pedida" existem, e quantas a tabela cobre?

## A máquina de estados inteira

São 5 × 5 = 25 combinações, e só 5 são permitidas. Escrever 25 métodos de teste é inviável; um **teste parametrizado** cobre todas a partir de uma tabela:

```java
@ParameterizedTest(name = "{0} -> {1}: {2}")
@CsvSource(textBlock = """
        CRIADO,    PAGO,      true
        CRIADO,    CANCELADO, true
        CRIADO,    ENTREGUE,  false
        PAGO,      ENVIADO,   true
        ENVIADO,   CANCELADO, false
        ENTREGUE,  CANCELADO, false
        """)
void transicoes(Situacao de, Situacao para, boolean permitida) {
    assertThat(de.podeIrPara(para)).isEqualTo(permitida);
}
```

![Uma grade de 5 por 5, com as situações de origem nas linhas e as de destino nas colunas; cinco casas verdes marcadas 200 e vinte casas laranja](/figuras/matriz-de-transicoes.svg "As 25 combinações da máquina de estados: 5 permitidas e 20 que precisam de teste também.")

Mesmo com a tabela, é fácil esquecer linhas. Uma alternativa é gerar todas as combinações e comparar com a lista das permitidas, que é curta:

```java executar
import java.util.EnumSet;
import java.util.Set;

public class Matriz {
    enum Situacao {
        CRIADO, PAGO, ENVIADO, ENTREGUE, CANCELADO;

        Set<Situacao> proximas() {
            return switch (this) {
                case CRIADO -> EnumSet.of(PAGO, CANCELADO);
                case PAGO -> EnumSet.of(ENVIADO, CANCELADO);
                case ENVIADO -> EnumSet.of(ENTREGUE);
                case ENTREGUE, CANCELADO -> EnumSet.noneOf(Situacao.class);
            };
        }
    }

    static final Set<String> PERMITIDAS = Set.of(
            "CRIADO>PAGO", "CRIADO>CANCELADO", "PAGO>ENVIADO", "PAGO>CANCELADO", "ENVIADO>ENTREGUE");

    public static void main(String[] args) {
        int casos = 0, falhas = 0;
        for (Situacao de : Situacao.values()) {
            for (Situacao para : Situacao.values()) {
                casos++;
                boolean esperado = PERMITIDAS.contains(de + ">" + para); //> A regra escrita de outro jeito, como especificação.
                if (de.proximas().contains(para) != esperado) falhas++;
            }
        }
        System.out.println(casos + " casos, " + falhas + " falhas");
    }
}
```

```saida
25 casos, 0 falhas
```

No JUnit, o mesmo laço vira um `@MethodSource` que devolve as 25 combinações. Se alguém acrescentar uma situação, o laço passa a gerar 36 casos sozinho.

## A pirâmide deste projeto

| Tipo | Quantos | Quanto tempo cada | O que cobre |
|---|---|---|---|
| Unidade (entidade, service com fakes) | uns 60 | milissegundos | regras e cálculos |
| Fatia web (`@WebMvcTest`) | uns 20 | dezenas de ms | rotas, JSON, validação, status |
| Repositório (`@DataJpaTest` + Testcontainers) | uns 10 | centenas de ms | consultas, migrations, `@Version` |
| Ponta a ponta (`@SpringBootTest`) | 3 ou 4 | segundos | os fluxos principais inteiros |

> [!MATEMATICA]
> Com 60 testes de unidade a 5 ms, 20 de fatia web a 40 ms, 10 de repositório a 300 ms e 4 ponta a ponta a 2 s, a suíte custa 0,3 + 0,8 + 3 + 8 = 12,1 segundos, mais uns 15 segundos para subir o contêiner e os contextos uma vez. Se os 94 testes fossem todos `@SpringBootTest` a 2 s, seriam 188 segundos: mais de 3 minutos a cada `mvn test`, e o time deixaria de rodar os testes antes do commit.

## O que a cobertura mede

O JaCoCo instrumenta o bytecode e conta quais linhas e quais **ramos** (cada lado de um `if`) os testes executaram. É útil para achar código que nenhum teste toca. O problema é o contrário: uma linha executada não quer dizer uma linha conferida.

```java executar
public class Cobertura {
    static int executadas = 0;

    static String frete(double total) {
        executadas++;
        return total >= 200 ? "grátis" : "R$ 15,00"; //> Os dois ramos estão nesta linha.
    }

    public static void main(String[] args) {
        frete(250); // o "teste": chama, mas não confere nada
        System.out.println("linhas executadas: " + executadas + " de 1");
        System.out.println("ramo de 'R$ 15,00' testado? não");
    }
}
```

```saida
linhas executadas: 1 de 1
ramo de 'R$ 15,00' testado? não
```

A cobertura de linhas diz 100%, a de ramos diz 50%, e o teste não tem nem uma asserção. Por isso, olhe a cobertura de **ramos**, e use o relatório para encontrar o que falta, nunca como meta a bater.

> [!ERRO]
> Exigir 80% de cobertura no CI sem revisar os testes gera exatamente o código acima: testes que chamam métodos para "subir o número", sem conferir o resultado. A métrica sobe, e a proteção continua zero.

## Testando os testes

Quem testa os testes é o **teste de mutação**. A ferramenta PIT faz pequenas mudanças no código, os **mutantes** (troca `>=` por `>`, `+` por `-`, apaga uma chamada), e roda a suíte para cada um. Se algum teste falha, o mutante foi "morto". Se todos passam, ele sobreviveu, e há uma lacuna nos testes.

> [!LAPIS]
> O teste do frete confere `frete(250)` é `"grátis"` e `frete(100)` é `"R$ 15,00"`. O PIT troca `total >= 200` por `total > 200`. O mutante sobrevive?
>
> **Resposta:** Sobrevive. Para 250 e 100, `>=` e `>` dão o mesmo resultado. Só um teste com exatamente 200, a **fronteira**, distingue os dois. É o caso que o critério "a partir de 200" exige, e que ninguém lembra de escrever.

> [!PERGUNTAS]
> **P:** Qual porcentagem de cobertura é boa?
>
> **R:** Não há um número mágico. Regras de negócio, como a máquina de estados e o cálculo do total, merecem perto de 100% de ramos e de mutantes mortos. Configuração e DTOs, quase nada.
>
> **P:** O PIT não é lento demais?
>
> **R:** Ele roda a suíte uma vez por mutante, então use só nos pacotes de regras e só com os testes de unidade, num job separado do CI.
>
> **P:** Devo testar os getters?
>
> **R:** Não diretamente. Se eles importam, algum teste de comportamento já passa por eles.

> [!ANTES]
> Até os anos 2000, era comum o projeto ter uma equipe de testes separada, que recebia o sistema pronto e testava à mão, seguindo planilhas. O JUnit, criado por Kent Beck e Erich Gamma em 1997, e o TDD trouxeram o teste para dentro do trabalho de quem programa, rodando em segundos a cada mudança.

## Por baixo dos panos

O JaCoCo não lê o seu código-fonte: ele se instala como **agente Java** (`-javaagent`) e, quando cada classe é carregada, acrescenta ao bytecode um vetor de `boolean` e uma instrução que marca `true` em cada trecho executado, as **sondas** (*probes*). No fim, ele cruza esses vetores com as linhas e os ramos do `.class`. É a mesma API de instrumentação (`java.lang.instrument`) que o Mockito usa para criar mocks de classes finais, e o motivo do aviso de agente da [temporada de testes](/assistir/backend-junior-t6-e03). Para ver o bytecode que o JaCoCo modifica, `javap -c` mostra cada `if` como uma instrução de desvio, como `if_icmplt`, que é exatamente o "ramo" que ele conta; a trilha Aprendiz explica essas instruções em [interpretadores e a JVM](/assistir/aprendiz-t2-e04).

> [!IA]
> A IA escreve testes rápido, mas tende a testar o caminho feliz e a copiar a implementação para calcular o valor esperado. Peça os casos de fronteira explicitamente (exatamente 200, a página 0, a última página, o segundo pagamento) e rode o PIT nos testes que ela gerou: mutantes sobreviventes mostram o que ela deixou de conferir.

## Na IDE

- **Cobertura na hora.** *Run with Coverage* no IntelliJ pinta as linhas: verde executada, vermelho não, e amarelo para ramos cobertos pela metade.
- **Rodar só os que falharam.** O botão *Rerun Failed Tests* repete só os testes vermelhos, útil numa suíte de minutos.
- **Plugin do PIT.** O *PIT mutation testing* roda os mutantes de uma classe e mostra os sobreviventes no editor.

## Resumo

- Cada critério de aceitação vira teste, às vezes em mais de uma camada.
- Teste a máquina de estados inteira, com as 25 combinações, num teste parametrizado.
- A pirâmide mantém a suíte em segundos: muitos testes de unidade, poucos de ponta a ponta.
- Cobertura de linhas mostra o que nenhum teste toca, mas não prova que algo foi conferido; prefira a de ramos.
- O teste de mutação mostra se os testes pegariam um erro de verdade, como a fronteira do `>=`.
