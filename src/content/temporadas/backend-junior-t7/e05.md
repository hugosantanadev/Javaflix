A API de pedidos funciona e tem testes. Para virar um projeto que outra pessoa consegue usar, manter e pôr no ar, faltam três coisas: **documentação** que não envelhece, **configuração** que muda por ambiente sem mudar o código, e um **caminho de entrega** em que nada chega à produção sem passar pelos testes. É o último episódio da temporada e o que transforma o código do repositório em portfólio.

## A documentação da API

Com a dependência `springdoc-openapi-starter-webmvc-ui`, a aplicação publica o contrato em `/v3/api-docs` e uma tela interativa em `/swagger-ui.html`. Como o documento sai do código, ele não fica desatualizado como um PDF esquecido numa pasta. E os erros esperados, que o e01 listou, aparecem para quem consome a API.

## A configuração por ambiente

O mesmo `.jar` vai para homologação e produção. O que muda é o **ambiente**: a URL do banco, a senha, o nível de log. Nada disso fica no código nem no Git:

```properties
spring.datasource.url=${DB_URL:jdbc:postgresql://localhost:5432/pedidos}
spring.datasource.username=${DB_USUARIO:pedidos}
spring.datasource.password=${DB_SENHA}
springdoc.swagger-ui.enabled=${SWAGGER_LIGADO:false}
```

O `${NOME:padrão}` lê a variável de ambiente e usa o padrão quando ela não existe. A senha não tem padrão de propósito: sem ela, a aplicação não sobe, em vez de subir com uma senha de exemplo. Este programa faz a mesma resolução que o Spring:

```java executar
import java.util.Map;
import java.util.regex.Matcher;
import java.util.regex.Pattern;

public class Placeholders {
    static final Pattern MARCA = Pattern.compile("\\$\\{([A-Z_]+)(?::([^}]*))?}");

    static String resolver(String valor, Map<String, String> ambiente) {
        Matcher m = MARCA.matcher(valor);
        if (!m.matches()) return valor;
        String nome = m.group(1), padrao = m.group(2);
        if (ambiente.containsKey(nome)) return ambiente.get(nome);
        if (padrao != null) return padrao; //> Sem ":" na marca, não há padrão.
        throw new IllegalStateException("Could not resolve placeholder '" + nome + "'");
    }

    public static void main(String[] args) {
        Map<String, String> producao = Map.of("DB_URL", "jdbc:postgresql://db-prod:5432/pedidos");
        System.out.println(resolver("${DB_URL:jdbc:postgresql://localhost:5432/pedidos}", producao));
        System.out.println(resolver("${SWAGGER_LIGADO:false}", producao));
        try {
            resolver("${DB_SENHA}", producao);
        } catch (IllegalStateException e) {
            System.out.println(e.getMessage());
        }
    }
}
```

```saida
jdbc:postgresql://db-prod:5432/pedidos
false
Could not resolve placeholder 'DB_SENHA'
```

> [!ERRO]
> Um `application-prod.properties` com a senha de produção, commitado "só por enquanto", fica para sempre no histórico do Git, mesmo depois de apagado. Se aconteceu, a senha precisa ser **trocada**, não só removida do arquivo.

## O caminho da entrega

![Cinco etapas em sequência: git push com tag, CI com mvn verify, o artefato jar, o deploy com java -jar e o health check com UP](/figuras/caminho-da-entrega.svg "Nada chega ao deploy sem passar pelo CI, e o mesmo jar serve a todos os ambientes.")

O **CI** (integração contínua) roda a cada push. Um arquivo do GitHub Actions basta para o projeto:

```yaml
# .github/workflows/ci.yml
on: [push, pull_request]
jobs:
  verificar:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: 25, cache: maven }
      - run: ./mvnw -B verify
```

O executor do GitHub já tem Docker, então os testes com Testcontainers rodam como na sua máquina. Com a proteção de branch exigindo esse job, nenhum pull request entra na `main` com testes falhando.

Depois do deploy, o **health check** confirma que a aplicação subiu e alcança o banco. O Spring Boot Actuator expõe `/actuator/health`, que responde `{"status":"UP"}` quando tudo está bem e 503 quando o banco está fora.

> [!LAPIS]
> O deploy subiu a versão nova, e o `/actuator/health` responde 503 com `"db": {"status": "DOWN"}`. O CI tinha passado. Qual é o primeiro lugar para olhar, e o que fazer com o tráfego enquanto isso?
>
> **Resposta:** As variáveis de ambiente do servidor novo: os testes usaram o banco do Testcontainers, e só o ambiente de verdade tem `DB_URL` e `DB_SENHA`. Enquanto isso, o tráfego continua na versão anterior, que é para isso que o health check existe: o balanceador só manda requisições para instâncias `UP`.

## As versões

Cada entrega ganha um número no formato do **versionamento semântico**: `MAIOR.MENOR.CORREÇÃO`. Correção de bug sobe o último; recurso novo compatível sobe o do meio; mudança que quebra quem consome a API, como renomear um campo do JSON, sobe o primeiro.

> [!MATEMATICA]
> Versões se comparam número a número, não como texto. Como texto, `"1.10.0"` vem antes de `"1.9.3"`, porque o caractere `1` é menor que `9`. Como números, 1 = 1, e então 10 > 9, e a 1.10.0 é a mais nova. O programa abaixo faz a comparação certa.

```java executar
import java.util.Arrays;
import java.util.Comparator;
import java.util.List;

public class Versoes {
    static int[] partes(String v) {
        return Arrays.stream(v.split("\\.")).mapToInt(Integer::parseInt).toArray();
    }

    public static void main(String[] args) {
        List<String> versoes = List.of("1.9.3", "1.10.0", "1.2.11", "2.0.0");
        System.out.println("como texto:  " + versoes.stream().sorted().toList());
        System.out.println("como versão: " + versoes.stream()
                .sorted(Comparator.comparing(Versoes::partes, Arrays::compare)).toList()); //> Compara posição por posição.
    }
}
```

```saida
como texto:  [1.10.0, 1.2.11, 1.9.3, 2.0.0]
como versão: [1.2.11, 1.9.3, 1.10.0, 2.0.0]
```

Uma tag no Git marca cada versão (`git tag v1.0.0`), e um `CHANGELOG.md` diz o que mudou em cada uma, em linguagem de quem usa a API.

## Por baixo dos panos

O `pedidos-1.0.0.jar` que o Spring Boot gera é um **jar executável** com uma estrutura própria: as suas classes ficam em `BOOT-INF/classes`, as dependências, como jars inteiros, em `BOOT-INF/lib`, e o `META-INF/MANIFEST.MF` aponta `Main-Class: org.springframework.boot.loader.launch.JarLauncher`. O `java -jar` não roda a sua classe `main` direto: roda o *launcher*, que monta um *class loader* capaz de ler jars dentro do jar, algo que o Java padrão não faz, e só então chama a sua aplicação. Abra o arquivo com `jar tf pedidos-1.0.0.jar` e veja. Para entender como a JVM carrega classes, veja [interpretadores e a JVM](/assistir/aprendiz-t2-e04), na trilha Aprendiz.
