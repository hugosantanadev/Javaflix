Com o contrato do [episódio anterior](/assistir/backend-junior-t7-e01) pronto, a API ganha o seu esqueleto: três **camadas**, cada uma com uma responsabilidade, e os **DTOs**, os objetos que atravessam a fronteira entre o JSON e o seu código. É a parte do projeto em que os atalhos parecem inofensivos, como devolver a entidade direto no controller, e cobram o preço semanas depois.

## Uma responsabilidade por camada

| Camada | Sabe de | Não sabe de |
|---|---|---|
| Controller | HTTP: caminhos, status, cabeçalhos, validação de entrada | regras do pedido, SQL |
| Service | regras de negócio e transações | HTTP, JSON |
| Repository | o banco: consultas e gravação | HTTP, regras |

A regra prática: o controller **traduz**, o service **decide** e o repository **guarda**. Um controller com `if (pedido.getSituacao() == ENVIADO)` está decidindo, e essa regra não vai valer quando outro ponto de entrada, como uma fila ou um job noturno, cancelar o mesmo pedido.

## DTOs com records

O DTO (*Data Transfer Object*) é o formato do JSON escrito em Java. Os [records](/assistir/junior-t5-e01) servem perfeitamente: imutáveis, com `equals` e `toString` prontos, e sem lógica.

```java
public record NovoPedido(
        @NotNull Long clienteId,
        @NotEmpty List<@Valid ItemPedido> itens) {}

public record ItemPedido(
        @NotBlank String sku,
        @Positive int quantidade) {}

public record PedidoResposta(
        Long id, String situacao, BigDecimal total, List<ItemResposta> itens) {}
```

A requisição traz só o que o cliente pode informar. Repare no que **não** está em `NovoPedido`: id, situação, total e preço. Esses o servidor calcula, e o cliente não tem como mandá-los.

> [!PENSE]
> Se o `NovoPedido` tivesse um campo `BigDecimal total`, o que impediria um cliente de mandar um pedido de R$ 3.000 com `"total": 0.01`?

## Por que não devolver a entidade

O atalho tentador é usar a própria entidade JPA no `@RequestBody` e no retorno. Ele causa três problemas concretos:

1. **Atribuição em massa.** O Jackson preenche qualquer campo que vier no JSON, inclusive `situacao` e `total`.
2. **Contrato preso ao banco.** Renomear uma coluna muda o JSON e quebra o aplicativo de quem consome a API.
3. **Lazy loading fora da transação.** Ao serializar `pedido.getCliente()`, o Jackson dispara uma consulta, ou um `LazyInitializationException`, depois que o service já terminou.

Este programa imita o Jackson preenchendo campos pelo nome, como ele faz com uma entidade de setters públicos:

```java executar
import java.math.BigDecimal;
import java.util.Map;

public class AtribuicaoEmMassa {
    static class Pedido {
        String situacao = "CRIADO";
        BigDecimal total = new BigDecimal("3000.00");

        void preencher(Map<String, String> json) {
            json.forEach((campo, valor) -> {
                switch (campo) {
                    case "situacao" -> situacao = valor; //> Nada impede o cliente de escolher a situação.
                    case "total" -> total = new BigDecimal(valor);
                    default -> { }
                }
            });
        }
    }

    public static void main(String[] args) {
        Pedido p = new Pedido();
        p.preencher(Map.of("situacao", "ENTREGUE", "total", "0.01"));
        System.out.println(p.situacao + " " + p.total);
    }
}
```

```saida
ENTREGUE 0.01
```

Com um DTO que não tem esses campos, o mesmo JSON é inofensivo: o Jackson ignora o que não conhece, ou recusa, se `FAIL_ON_UNKNOWN_PROPERTIES` estiver ligado.

> [!ERRO]
> Expor a entidade com `@JsonIgnore` nos campos sensíveis parece resolver, mas cada campo novo nasce exposto até alguém lembrar de anotá-lo. Com DTO, o padrão é o contrário: um campo só aparece no JSON quando alguém o acrescenta ao record de propósito.

> [!CONVERSA]
> **Entidade:** Para que dois objetos com os mesmos campos? Eu já tenho id, situação e total. É só me devolver.
>
> **DTO:** Você tem também o custo do produto, a versão da trava e um cliente que nem foi carregado. Se você for para o JSON, vai tudo junto, ou explode no meio.
>
> **Entidade:** E se alguém renomear uma coluna?
>
> **DTO:** Muda você, e o aplicativo de quem consome a API quebra. Comigo no meio, o banco muda e o contrato continua o mesmo. Você cuida dos dados; eu cuido da conversa com o mundo.

## O mapeamento

Alguém precisa converter DTO em entidade e entidade em DTO. O jeito mais simples, e o mais fácil de depurar, é um método estático no próprio record de resposta:

```java executar
import java.math.BigDecimal;
import java.util.List;

public class Mapeamento {
    record Item(String sku, int quantidade, BigDecimal precoUnitario) {}
    record Pedido(Long id, String situacao, List<Item> itens) {}

    record ItemResposta(String sku, int quantidade, BigDecimal subtotal) {}
    record PedidoResposta(Long id, String situacao, BigDecimal total, List<ItemResposta> itens) {
        static PedidoResposta de(Pedido p) {
            List<ItemResposta> itens = p.itens().stream()
                    .map(i -> new ItemResposta(i.sku(), i.quantidade(),
                            i.precoUnitario().multiply(BigDecimal.valueOf(i.quantidade()))))
                    .toList();
            BigDecimal total = itens.stream().map(ItemResposta::subtotal) //> O total é derivado, nunca recebido.
                    .reduce(BigDecimal.ZERO, BigDecimal::add);
            return new PedidoResposta(p.id(), p.situacao(), total, itens);
        }
    }

    public static void main(String[] args) {
        Pedido p = new Pedido(42L, "CRIADO", List.of(
                new Item("CANECA", 3, new BigDecimal("19.90")),
                new Item("CAFE-500G", 1, new BigDecimal("42.50"))));
        System.out.println(PedidoResposta.de(p));
    }
}
```

```saida
PedidoResposta[id=42, situacao=CRIADO, total=102.20, itens=[ItemResposta[sku=CANECA, quantidade=3, subtotal=59.70], ItemResposta[sku=CAFE-500G, quantidade=1, subtotal=42.50]]]
```

Bibliotecas como o MapStruct geram esse código na compilação e valem a pena com dezenas de DTOs. Com cinco, o método à mão é mais claro e não tem mágica para investigar.

> [!PERGUNTAS]
> **P:** Um DTO por rota não é exagero?
>
> **R:** Um por **formato**. Se a listagem e o detalhe mostram os mesmos campos, use o mesmo record. Se a listagem mostra só id, situação e total, crie um `PedidoResumo` e economize consultas.
>
> **P:** A validação fica no DTO ou no service?
>
> **R:** Nos dois, com papéis diferentes. No DTO, o formato: campo obrigatório, número positivo. No service, as regras que precisam do banco: o produto existe, há estoque.
>
> **P:** O service pode receber o DTO?
>
> **R:** Pode receber o DTO de entrada, que é só dados. O que ele não deve fazer é devolver nada de HTTP, como `ResponseEntity`.

## O service

```java
@Service
class PedidoService {
    private final PedidoRepository pedidos;
    private final ProdutoRepository produtos;

    PedidoService(PedidoRepository pedidos, ProdutoRepository produtos) {
        this.pedidos = pedidos;
        this.produtos = produtos;
    }

    @Transactional
    PedidoResposta criar(NovoPedido novo) {
        Pedido pedido = new Pedido(novo.clienteId());
        for (ItemPedido item : novo.itens()) {
            Produto produto = produtos.findBySku(item.sku())
                    .orElseThrow(() -> new ProdutoInexistente(item.sku())); //> Vira 422 no tratador de erros.
            pedido.adicionar(produto, item.quantidade());
        }
        return PedidoResposta.de(pedidos.save(pedido));
    }
}
```

O preço vem do `Produto`, lido do banco, e não do cliente. E o `@Transactional` garante que, se o terceiro item não existir, os dois primeiros não ficam gravados pela metade.

> [!MATEMATICA]
> Arredondar cada item ou só o total muda o resultado. Três itens de R$ 0,333 cada (um preço por grama, por exemplo): arredondando cada um, 0,33 + 0,33 + 0,33 = **0,99**; arredondando só no fim, 0,999 vira **1,00**. A diferença é de 1 centavo por pedido; em 1.095.000 pedidos por ano, até R$ 10.950. Escolha uma regra, escreva-a num teste e use a mesma regra na nota fiscal.

> [!ANTES]
> Nos sistemas Java EE dos anos 2000, o padrão *Transfer Object* existia para outra coisa: as chamadas remotas aos EJBs eram caras, e o DTO juntava vários dados numa ida só pela rede. O nome ficou, e hoje o motivo principal é separar o contrato da API do modelo do banco.

## Por baixo dos panos

Quando o controller devolve um `PedidoResposta`, o Jackson descobre os campos de um record pelos **componentes**, que a reflexão do Java expõe desde o Java 16. É o que torna os records tão práticos como DTO: não há getters a escrever, e a ordem do JSON segue a ordem dos componentes.

```java executar
import java.lang.reflect.RecordComponent;
import java.math.BigDecimal;

public class Componentes {
    record PedidoResposta(Long id, String situacao, BigDecimal total) {}

    public static void main(String[] args) throws Exception {
        PedidoResposta r = new PedidoResposta(42L, "PAGO", new BigDecimal("102.20"));
        StringBuilder json = new StringBuilder("{");
        for (RecordComponent c : PedidoResposta.class.getRecordComponents()) {
            Object valor = c.getAccessor().invoke(r); //> O acessor id(), situacao(), total().
            if (json.length() > 1) json.append(", ");
            json.append('"').append(c.getName()).append("\": ");
            json.append(valor instanceof String ? "\"" + valor + "\"" : valor);
        }
        System.out.println(json.append("}"));
    }
}
```

```saida
{"id": 42, "situacao": "PAGO", "total": 102.20}
```

O Jackson faz o mesmo, com cache dessas informações por classe, para não refletir a cada requisição. Os componentes ficam gravados no `.class`, no atributo `Record`, definido na JVMS §4.7.30.

> [!IA]
> Ao pedir "um CRUD de pedidos", a IA quase sempre devolve a entidade no controller, com `@RequestBody Pedido`, porque é o que mais aparece em tutoriais. Peça explicitamente DTOs de entrada e de saída, e confira que o de entrada não tem id, situação nem total.

## Na IDE

- **Classe que vira record.** A inspeção "Class can be a record" aponta DTOs escritos como classe com getters, e o **Alt + Enter** converte para record.
- **Encontrar quem expõe entidade.** *Find Usages* na classe `Pedido`, filtrando pelo pacote dos controllers, mostra todo lugar em que ela vaza para o HTTP.
- **Ver o JSON gerado.** Com o arquivo `.http` do episódio anterior, a resposta abre num painel com o JSON formatado.

## Resumo

- Controller traduz HTTP, service decide e guarda as transações, repository fala com o banco.
- DTOs de entrada e de saída, em records, separam o contrato da API do modelo do banco.
- O DTO de entrada não tem id, situação, total nem preço: o servidor calcula.
- Expor a entidade abre atribuição em massa, prende o JSON às colunas e dispara lazy loading fora da transação.
- Um mapeamento à mão, num método `de(...)` do record, basta enquanto os DTOs forem poucos.
