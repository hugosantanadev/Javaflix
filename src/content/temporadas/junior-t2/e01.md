"Em Java, primitivos são passados por valor e objetos por referência." A frase é repetida em muito curso, e está errada. Java passa **tudo por valor**, sempre. A confusão vem de que, para objetos, o valor copiado é uma **referência**. Entender essa diferença é o que permite prever, sem rodar, o que um método consegue e o que não consegue mudar em quem o chamou.

## Primitivos: o método recebe uma cópia

Na chamada, o valor de cada argumento é **copiado** para o parâmetro, que é uma variável local nova do método. Mudar o parâmetro muda a cópia:

```java executar
public class Valor {
    static void dobrar(int n) {
        n = n * 2;
        System.out.println("dentro: " + n);
    }

    public static void main(String[] args) {
        int x = 5;
        dobrar(x);
        System.out.println("fora: " + x);
    }
}
```

```saida
dentro: 10
fora: 5
```

Para devolver um resultado, o método usa o `return`, e quem chamou precisa guardá-lo: `x = dobrar(x)`, se `dobrar` devolvesse o valor.

## Referências: a cópia aponta para o mesmo objeto

Com objetos, o que se copia é a referência. O parâmetro e a variável de quem chamou passam a apontar para o **mesmo objeto**. Então o método pode **alterar o objeto**, e quem chamou vê a mudança. Mas **reatribuir o parâmetro** só muda para onde a cópia aponta:

```java executar
public class Referencia {
    static void alterar(StringBuilder sb) {
        sb.append(" mundo");
    }

    static void trocar(StringBuilder sb) {
        sb = new StringBuilder("outro");
        sb.append("!");
    }

    public static void main(String[] args) {
        StringBuilder texto = new StringBuilder("olá");
        alterar(texto);
        trocar(texto);
        System.out.println(texto);
    }
}
```

```saida
olá mundo
```

`alterar` seguiu a referência e mexeu no objeto. `trocar` fez a sua cópia apontar para um objeto novo, e tudo o que fez depois foi nesse objeto novo, que ninguém de fora enxerga.

O teste definitivo é o da troca. Numa linguagem com passagem por referência de verdade, como o C++ com `int&`, uma função consegue trocar as variáveis de quem a chamou. Em Java, não:

```java executar
public class Troca {
    static void trocar(int[] a, int[] b) {
        int[] tmp = a;
        a = b;
        b = tmp;
    }

    static void trocarConteudo(int[] a, int[] b) {
        int tmp = a[0];
        a[0] = b[0];
        b[0] = tmp;
    }

    public static void main(String[] args) {
        int[] x = {1};
        int[] y = {2};
        trocar(x, y);
        System.out.println(x[0] + " " + y[0]);
        trocarConteudo(x, y);
        System.out.println(x[0] + " " + y[0]);
    }
}
```

```saida
1 2
2 1
```

O primeiro método trocou as cópias, e as variáveis do `main` continuaram onde estavam. O segundo trocou o **conteúdo** dos arrays, que são compartilhados.

## Strings e wrappers parecem primitivos

`String` e os wrappers, como `Integer`, são objetos, mas [imutáveis](/assistir/estagiario-t5-e01): não têm nenhum método que altere o objeto. Qualquer "mudança" cria um objeto novo e reatribui a variável local. Na prática, para quem chamou, eles se comportam como primitivos:

```java executar
public class Texto {
    static void gritar(String s) {
        s = s.toUpperCase();
    }

    static String gritarDeVerdade(String s) {
        return s.toUpperCase();
    }

    public static void main(String[] args) {
        String nome = "ana";
        gritar(nome);
        System.out.println(nome);
        nome = gritarDeVerdade(nome);
        System.out.println(nome);
    }
}
```

```saida
ana
ANA
```

> [!PROVA]
> Para cada chamada de método numa questão, pergunte: o método **altera o objeto** (chama um método que muda o estado, mexe num campo, escreve num array) ou só **reatribui o parâmetro**? Só a primeira forma é vista por quem chamou. E com `String`, `Integer` e afins, nenhuma alteração é possível: o original nunca muda.

## Regras do `return`

Um método com tipo de retorno precisa terminar com `return` em **todos** os caminhos possíveis. O compilador não avalia as condições, só a estrutura: dois `if` que, juntos, cobrem todos os casos não bastam.

```java nao-compila
public class Sinal {
    static String sinal(int n) {
        if (n > 0) {
            return "positivo";
        } else if (n < 0) {
            return "negativo";
        }
    }
}
```

Um `else` final, ou um `return` depois dos `if`, resolve. Código depois de um `return` nunca roda, e o compilador o recusa como inalcançável:

```java nao-compila
public class Morto {
    static int dobro(int n) {
        return n * 2;
        System.out.println("nunca");
    }
}
```

Métodos `void` podem usar `return;`, sem valor, para sair mais cedo. E um parâmetro pode ser `final`, o que impede reatribuí-lo dentro do método, uma forma de deixar explícito que ele é só de leitura:

```java nao-compila
public class Fixo {
    static int somar(final int a, int b) {
        a = a + b;
        return a;
    }
}
```

## Por baixo dos panos

Cada chamada cria um quadro na pilha da thread com duas áreas: um vetor de **variáveis locais** e uma **pilha de operandos**. Antes de chamar, quem chama empilha os argumentos; a instrução `invokestatic` ou `invokevirtual` os move para as primeiras posições do vetor de variáveis locais do método chamado. Os parâmetros são, literalmente, as primeiras variáveis locais do método, e por isso se comportam como cópias.

Num método de instância, a posição 0 guarda `this`, e os parâmetros começam na 1. Ou seja, até o `this` é passado por valor: é uma referência copiada como as outras. No bytecode, ler um `int` local é `iload`, e uma referência, `aload`; em nenhum dos dois casos existe uma forma de chegar à variável de quem chamou. Em C, o que se faz para "devolver por parâmetro" é passar um ponteiro para a variável (`&x`), e mesmo assim o ponteiro é copiado. Java simplesmente não tem o operador `&`.

## Resumo para a prova

- Java passa tudo por valor; para objetos, o valor copiado é a referência
- O método pode alterar o objeto recebido, e quem chamou vê a mudança
- Reatribuir o parâmetro não afeta a variável de quem chamou
- Um método não consegue trocar as variáveis de quem o chamou
- `String` e wrappers são imutáveis: o original nunca muda
- Métodos com retorno precisam de `return` em todos os caminhos, pela estrutura, não pelas condições
- Código depois de `return` não compila; parâmetro `final` não pode ser reatribuído
