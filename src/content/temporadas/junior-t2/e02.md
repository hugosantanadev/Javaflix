`System.out.println` aceita um `int`, um `double`, uma `String`, um `char[]` ou qualquer objeto. Não são vários nomes: é um nome só, com várias versões. Isso é **sobrecarga** (*overloading*): métodos com o mesmo nome e listas de parâmetros diferentes. Escrever sobrecargas é fácil; o difícil, e o que a prova cobra, é saber **qual versão o compilador escolhe** quando várias poderiam servir.

## O que diferencia uma sobrecarga

A **assinatura** de um método é o nome mais os tipos dos parâmetros, na ordem. Duas versões precisam ter assinaturas diferentes: outro número de parâmetros, outros tipos ou outra ordem.

```java executar
public class Somas {
    static int somar(int a, int b) {
        return a + b;
    }

    static int somar(int a, int b, int c) {
        return a + b + c;
    }

    static double somar(double a, double b) {
        return a + b;
    }

    static String somar(String a, String b) {
        return a + b;
    }

    public static void main(String[] args) {
        System.out.println(somar(1, 2) + " " + somar(1, 2, 3) + " " + somar(1.5, 2) + " " + somar("1", "2"));
    }
}
```

```saida
3 6 3.5 12
```

O tipo de retorno, os nomes dos parâmetros, os modificadores e as exceções declaradas **não** fazem parte da assinatura. Dois métodos que só diferem no retorno não compilam, porque numa chamada como `ler("5");` o compilador não teria como escolher:

```java nao-compila
public class Duplicado {
    static int ler(String s) {
        return Integer.parseInt(s);
    }

    static double ler(String s) {
        return Double.parseDouble(s);
    }
}
```

## A ordem de escolha

Quando mais de uma versão aceita os argumentos, o compilador procura em fases, e para na primeira que encontrar alguma candidata:

1. **Tipo exato** ou alargamento: primitivo para um primitivo maior (`int` para `long`), ou referência para um supertipo (`String` para `Object`), sem embrulhar nada
2. **Autoboxing** e unboxing (`int` para `Integer`)
3. **Varargs**, assunto do [próximo episódio](/assistir/junior-t2-e03)

Dentro de uma fase, vence a versão **mais específica**: a de tipo mais próximo do argumento.

```java executar
public class Escolha {
    static void m(long x) { System.out.println("long"); }
    static void m(Integer x) { System.out.println("Integer"); }
    static void m(Object x) { System.out.println("Object"); }
    static void m(int... x) { System.out.println("varargs"); }

    public static void main(String[] args) {
        int i = 5;
        m(i);
        Integer embrulhado = 5;
        m(embrulhado);
        m("texto");
        m();
    }
}
```

```saida
long
Integer
Object
varargs
```

O `int` foi para `long`, e não para `Integer`: alargar vem antes de embrulhar. Tire a versão `long`, e a escolha muda:

```java executar
public class Escolha2 {
    static void m(Integer x) { System.out.println("Integer"); }
    static void m(Object x) { System.out.println("Object"); }
    static void m(int... x) { System.out.println("varargs"); }

    public static void main(String[] args) {
        m(5);
        m(5L);
        m(5, 6);
    }
}
```

```saida
Integer
Object
varargs
```

O `5L` vira `Long`, que não é um `Integer`, mas é um `Object`. Embrulhar e depois subir para um supertipo é permitido. O contrário, alargar e depois embrulhar, não: um `int` nunca vira `Long`, como você viu nos [wrappers](/assistir/estagiario-t6-e04).

```java nao-compila
public class SemDuasConversoes {
    static void pagar(Long valor) {
        System.out.println(valor);
    }

    public static void main(String[] args) {
        pagar(10);
    }
}
```

`char` alarga para `int`, e `float` e `long` alargam para `double`:

```java executar
public class Caractere {
    static void m(int x) { System.out.println("int " + x); }
    static void m(double x) { System.out.println("double " + x); }

    public static void main(String[] args) {
        m('A');
        m(3L);
        m(2.5f);
    }
}
```

```saida
int 65
double 3.0
double 2.5
```

## Ambiguidade

Se, na mesma fase, duas versões servem e nenhuma é mais específica que a outra, a chamada é **ambígua** e não compila. O erro aparece na chamada, não na declaração:

```java nao-compila
public class Ambiguo {
    static void m(int a, long b) { }
    static void m(long a, int b) { }

    public static void main(String[] args) {
        m(1, 2);
    }
}
```

O `null` é um caso clássico. Ele cabe em qualquer referência, então vence a versão de tipo mais específico. Com `String` e `Object`, ganha `String`, porque `String` é um `Object`. Com `String` e `Integer`, nenhum é mais específico, e a chamada `m(null)` é ambígua.

## A escolha é feita na compilação

A sobrecarga é resolvida pelo **tipo declarado** dos argumentos, não pelo tipo real do objeto em tempo de execução:

```java executar
public class Nulo {
    static void m(Object o) { System.out.println("Object"); }
    static void m(String s) { System.out.println("String"); }

    public static void main(String[] args) {
        m(null);
        Object o = "texto";
        m(o);
        m((String) o);
    }
}
```

```saida
String
Object
String
```

`o` aponta para uma `String`, mas está declarada como `Object`, e o compilador só sabe disso. É a grande diferença em relação à **sobrescrita**, que escolhe em tempo de execução, assunto da [temporada de herança](/assistir/junior-t3-e02).

> [!PROVA]
> Para resolver uma questão de sobrecarga: liste as versões, descarte as que não aceitam os argumentos, e aplique as fases na ordem (exato e alargamento, depois boxing, depois varargs). Se duas sobram empatadas na mesma fase, a resposta é "não compila". E lembre que literais inteiros são `int` e literais com ponto são `double`.

## Por baixo dos panos

O compilador grava a escolha no bytecode. Cada chamada carrega o **descritor** completo do método: `m(long)` vira `m:(J)V`, e `m(Object)`, `m:(Ljava/lang/Object;)V`. A JVM não faz escolha nenhuma: procura exatamente o método com aquele nome e aquele descritor. Por isso trocar a ordem de declaração dos métodos ou acrescentar uma sobrecarga nova numa biblioteca não muda o comportamento de código já compilado, mas recompilar pode mudar.

Um detalhe curioso: para a JVM, o descritor inclui o **tipo de retorno**. Dois métodos com os mesmos parâmetros e retornos diferentes são perfeitamente válidos num arquivo `.class`. Quem proíbe isso é a linguagem Java, não a máquina, e o próprio compilador se aproveita da brecha ao gerar os *métodos ponte* que você verá com herança e genéricos.

## Resumo para a prova

- Sobrecarga: mesmo nome, lista de parâmetros diferente (número, tipos ou ordem)
- Retorno, nomes de parâmetros e modificadores não diferenciam sobrecargas
- Ordem: exato e alargamento, depois autoboxing, depois varargs
- Dentro de uma fase, vence a versão mais específica
- Alargar e depois embrulhar não existe: `int` não vira `Long`
- Embrulhar e depois subir para um supertipo existe: `int` vira `Integer` e então `Object`
- Duas versões empatadas tornam a chamada ambígua: erro de compilação
- A escolha usa o tipo declarado, na compilação
