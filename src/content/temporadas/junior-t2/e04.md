Uma conta bancária com saldo público pode ser zerada por qualquer linha do sistema. **Encapsular** é esconder o estado do objeto atrás de métodos que garantem as regras dele, as *invariantes*: o saldo nunca fica negativo, a hora nunca passa de 23. Levada ao extremo, a ideia vira **imutabilidade**: objetos que, depois de criados, nunca mudam. `String`, `Integer` e `LocalDate` são assim, e a prova cobra a receita para criar os seus.

## Encapsulamento: campos privados, métodos que validam

O padrão é simples: campos `private`, e métodos públicos que leem e alteram o estado com as validações necessárias.

```java executar
class Conta {
    private double saldo;

    public double getSaldo() {
        return saldo;
    }

    public boolean sacar(double valor) {
        if (valor <= 0 || valor > saldo) return false; //> A regra mora num lugar só: ninguém saca mais do que tem.
        saldo -= valor;
        return true;
    }

    public void depositar(double valor) {
        if (valor <= 0) throw new IllegalArgumentException("valor inválido: " + valor);
        saldo += valor;
    }
}

Conta c = new Conta();
c.depositar(100);
System.out.println(c.sacar(30) + " " + c.sacar(500) + " " + c.getSaldo());
try {
    c.depositar(-5);
} catch (IllegalArgumentException e) {
    System.out.println(e.getMessage());
}
```

```saida
true false 70.0
valor inválido: -5.0
```

Não há `setSaldo`: o saldo só muda por operações que fazem sentido no negócio. Os métodos de leitura seguem a convenção **JavaBeans**: `getNome()` para ler, `setNome(valor)` para alterar e, para `boolean`, `isAtivo()`. Frameworks como o Spring e o Jackson descobrem as propriedades de um objeto por esses nomes.

> [!ANTES]
> A primeira classe de datas do Java, a `java.util.Date`, de 1996, era mutável: qualquer código que recebesse uma data podia mudá-la com `setTime`, e bibliotecas inteiras faziam cópias defensivas de cada `Date` por precaução. O problema só foi resolvido no Java 8, em 2014, com o pacote `java.time`: `LocalDate` e companhia são imutáveis, e "somar um dia" devolve uma data nova.

## A receita da classe imutável

Uma classe é imutável quando nenhum objeto dela pode mudar depois de construído. A receita que a prova cobra tem cinco passos:

1. Marque a classe como `final`, ou torne os construtores `private`, para que nenhuma subclasse acrescente estado mutável
2. Declare todos os campos `private` e `final`
3. Não ofereça métodos `set`
4. Não deixe escapar referências a objetos mutáveis: faça **cópias defensivas** ao receber e ao devolver
5. Operações que "mudariam" o objeto devolvem um objeto **novo**

O passo 4 é o que mais falha. Um campo `final` impede trocar a referência, não alterar o objeto apontado.

> [!PENSE]
> A classe `Turma` abaixo é `final`, o campo é `private final` e não há nenhum setter. Ela passa na receita? Procure por onde alguém de fora consegue mexer nos alunos.

```java executar
final class Turma {
    private final String[] alunos;

    Turma(String[] alunos) {
        this.alunos = alunos; //> Guarda a mesma seta de quem chamou.
    }

    String[] getAlunos() {
        return alunos; //> Entrega a seta do array interno.
    }
}

String[] nomes = {"Ana", "Bia"};
Turma t = new Turma(nomes);
nomes[0] = "Caio";
t.getAlunos()[1] = "Davi";
System.out.println(Arrays.toString(t.getAlunos()));
```

```saida
[Caio, Davi]
```

O array foi alterado por fora duas vezes: pela variável de quem criou a turma e pelo array devolvido no getter. A correção é copiar na entrada e na saída:

```java executar
final class Turma {
    private final String[] alunos;

    Turma(String[] alunos) {
        this.alunos = alunos.clone(); //> Um array só da turma.
    }

    String[] getAlunos() {
        return alunos.clone(); //> Quem pede recebe outra cópia.
    }
}

String[] nomes = {"Ana", "Bia"};
Turma t = new Turma(nomes);
nomes[0] = "Caio";
t.getAlunos()[1] = "Davi";
System.out.println(Arrays.toString(t.getAlunos()));
```

```saida
[Ana, Bia]
```

Com cópia, nomes aponta para o array de quem criou, e alunos para um array só da turma, com Ana e Bia](/figuras/copia-defensiva.svg "A cópia na entrada corta a ligação com quem criou o objeto; a cópia na saída, com quem chamou o getter.")

> [!ERRO]
> Devolver no getter a lista ou o array interno: `return itens;`. Quem recebe pode adicionar, remover ou trocar elementos, passando por cima de todas as regras da classe. Devolva uma cópia, uma lista imutável (`List.copyOf`) ou, se precisar de desempenho, uma visão somente leitura, sabendo que ela acompanha a original.

Com listas, `List.copyOf` faz a cópia e já devolve uma lista imutável, que pode ser entregue no getter sem nova cópia. Cuidado com `Collections.unmodifiableList`: ela é só uma **visão** somente leitura da lista original, e mudanças na original aparecem nela.

> [!LAPIS]
> Qual é a saída?
>
> ```java
> final class Lista {
>     private final List<String> itens;
>     Lista(List<String> itens) { this.itens = itens; }
>     List<String> getItens() { return Collections.unmodifiableList(itens); }
> }
>
> List<String> base = new ArrayList<>(List.of("x"));
> Lista l = new Lista(base);
> base.add("y");
> System.out.println(l.getItens());
> ```
>
> **Resposta:** `[x, y]`. O getter protege a saída: quem recebe a visão não consegue alterá-la. Mas a entrada não foi copiada, e `base` continua sendo a mesma lista guardada no campo. Um `List.copyOf` no construtor fecharia essa porta.

```java executar
List<String> origem = new ArrayList<>(List.of("a", "b"));
List<String> visao = Collections.unmodifiableList(origem);
List<String> copia = List.copyOf(origem);
origem.add("c");
System.out.println(visao + " " + copia);
try {
    copia.add("d");
} catch (UnsupportedOperationException e) {
    System.out.println("cópia imutável");
}
```

```saida
[a, b, c] [a, b]
cópia imutável
```

> [!MATEMATICA]
> Copiar custa: `clone()` de um array de n elementos copia n referências. Se o getter é chamado k vezes, são k × n cópias. Com 1.000 alunos e um getter chamado 10.000 vezes, 10.000 × 1.000 = **10 milhões** de referências copiadas. Guardando uma `List.copyOf` no construtor, a cópia acontece uma vez, 1.000 referências, e o getter devolve a mesma lista imutável sem copiar de novo.

## Operações que devolvem objetos novos

Num objeto imutável, "somar" não altera nada: cria outro objeto com o resultado, como o `toUpperCase` da `String` ou o `plusDays` da `LocalDate`. Quem chama precisa guardar o retorno:

```java executar
final class Dinheiro {
    private final long centavos;

    Dinheiro(long centavos) {
        this.centavos = centavos;
    }

    Dinheiro somar(Dinheiro outro) {
        return new Dinheiro(centavos + outro.centavos);
    }

    long getCentavos() {
        return centavos;
    }
}

Dinheiro a = new Dinheiro(1050);
Dinheiro b = a.somar(new Dinheiro(250));
a.somar(new Dinheiro(999));
System.out.println(a.getCentavos() + " " + b.getCentavos());
```

```saida
1050 1300
```

E se alguém tentar escrever um método que altera um campo `final`, o compilador recusa:

```java nao-compila
final class Ponto {
    private final int x;

    Ponto(int x) {
        this.x = x;
    }

    void mover(int dx) {
        x += dx;
    }
}
```

> [!PROVA]
> Ao avaliar se uma classe é imutável, procure as falhas: um setter, um campo não `final` ou não `private`, a classe não `final` com construtor acessível, e principalmente um getter que devolve um array, uma lista ou outro objeto mutável sem cópia. Basta uma falha para a resposta ser "não é imutável".

Desde o Java 16, os **records** geram boa parte dessa receita automaticamente, como você verá na temporada de [Java moderno](/assistir/junior-t5-e01). As cópias defensivas de campos mutáveis, porém, continuam sendo responsabilidade de quem escreve.

> [!CONVERSA]
> **Objeto mutável:** Comigo é prático: mudou o valor, chamo um `set` e pronto.
>
> **Objeto imutável:** E por isso todo mundo que te recebe precisa se perguntar se alguém vai te mudar pelas costas. Comigo, ninguém precisa copiar nada.
>
> **Objeto mutável:** Mas você cria um objeto novo a cada operação.
>
> **Objeto imutável:** Crio, e objetos pequenos e de vida curta são baratos. Em troca, posso ser compartilhado entre threads, guardado em cache e usado como chave de `HashMap` sem medo.
>
> **Objeto mutável:** Como chave de mapa eu sou um risco mesmo: se mudo depois de entrar, o mapa me perde.

> [!IA]
> Peça uma "classe imutável" e a IA costuma acertar o `final` e o `private final`, mas esquecer a cópia defensiva de listas e arrays, principalmente na entrada. Também é comum ela gerar setters por hábito. Confira os dois pontos: o construtor copia o que recebe, e nenhum getter devolve um objeto mutável interno.

## Na IDE

- **Coleção exposta.** As inspeções "Return of 'Collection' or array field" e "Assignment to 'Collection' or array field from parameter" apontam exatamente os dois furos da cópia defensiva.
- **Gerar getters.** **Alt + Insert**, "Getter", gera os métodos de leitura no padrão JavaBeans, com `is` para `boolean`; escolha só os campos que precisam ser lidos de fora.
- **Campo que pode ser `final`.** A inspeção "Field may be 'final'" sugere `final` para campos atribuídos só no construtor.

## Por baixo dos panos

Imutabilidade não é só organização: é uma garantia que a JVM ajuda a cumprir. A especificação dá aos campos `final` uma semântica especial no modelo de memória (JLS 17.5): depois que o construtor termina, qualquer thread que receba o objeto enxerga os valores dos campos `final`, sem `synchronized` nem `volatile`, desde que o `this` não tenha vazado durante a construção. Por isso objetos imutáveis podem ser compartilhados livremente entre threads.

Também é a imutabilidade que permite os caches que você já viu: o [pool de strings](/assistir/estagiario-t5-e05) e o cache de `Integer` só funcionam porque ninguém consegue alterar um objeto compartilhado. E o `clone()` de um array faz uma cópia **rasa**: copia as referências, não os objetos. Para um `String[]`, isso basta, porque `String` é imutável; para um array de objetos mutáveis, como `StringBuilder[]`, a cópia defensiva precisa descer um nível.

## Resumo para a prova

- Encapsular: campos `private`, acesso por métodos que mantêm as regras do objeto
- Convenção JavaBeans: `getX`, `setX` e `isX` para `boolean`
- Imutável: classe `final`, campos `private final`, sem setters, cópias defensivas, operações devolvem objetos novos
- `final` numa referência impede trocá-la, não alterar o objeto
- Getter que devolve array ou lista interna sem cópia quebra a imutabilidade
- `List.copyOf` copia; `Collections.unmodifiableList` é só uma visão da original
- `clone()` de array é cópia rasa
