Uma média de notas pode receber duas notas ou vinte. `String.format` recebe quantos valores o texto pedir. Para isso, Java tem os **varargs** (*variable arguments*): um último parâmetro que aceita zero, um ou muitos argumentos do mesmo tipo. Por fora, parece mágica; por dentro, é só um array, e as regras da prova saem todas daí.

## Declarar e chamar

O parâmetro varargs é escrito com reticências depois do tipo: `int... notas`. Dentro do método, `notas` é um `int[]` comum, com `length` e índices. Quem chama pode passar os valores separados por vírgula, nenhum valor, ou um array pronto:

```java executar
public class Media {
    static double media(int... notas) {
        if (notas.length == 0) return 0; //> Sem argumentos chega um array vazio, nunca null.
        int soma = 0;
        for (int n : notas) {
            soma += n;
        }
        return (double) soma / notas.length;
    }

    public static void main(String[] args) {
        System.out.println(media(7, 8, 10));
        System.out.println(media(5));
        System.out.println(media());
        System.out.println(media(new int[] {6, 9}));
    }
}
```

```saida
8.333333333333334
5.0
0.0
7.5
```

Chamado sem argumentos, o método recebe um array **vazio**, nunca `null`. O `main` também pode ser declarado com varargs: `public static void main(String... args)` é tão válido quanto a versão com `String[]`.

![Três chamadas e o que o javac gera para cada uma: media(7, 8, 10) vira media(new int[] {7, 8, 10}); media() vira media(new int[] {}), um array vazio; media(arr) passa o próprio array](/figuras/varargs-vira-array.svg "Varargs é escrita abreviada: o compilador monta o array na chamada, e o método só vê um int[].")

> [!ANTES]
> Antes do Java 5, de 2004, um método com número variável de argumentos recebia um `Object[]` declarado, e quem chamava montava o array à mão: `MessageFormat.format("{0} tem {1} anos", new Object[] {"Ana", Integer.valueOf(20)})`. Os varargs, o autoboxing e o `String.format` chegaram juntos nessa versão, e a mesma chamada encolheu para `String.format("%s tem %d anos", "Ana", 20)`.

> [!LAPIS]
> Com `static int f(int a, int... r) { return a + r.length; }`, quais são os resultados de `f(5)`, `f(5, 1, 1)` e `f(5, new int[] {9, 9, 9})`?
>
> **Resposta:** `5`, `7` e `8`. O primeiro argumento sempre vai para `a`. Em `f(5)`, `r` é um array vazio: 5 + 0. Em `f(5, 1, 1)`, `r` tem 2 elementos. E o array pronto vira o próprio `r`, com 3 elementos: o valor 9 nem é usado, só o tamanho.

## As regras da declaração

O varargs precisa ser o **último** parâmetro, e só pode haver **um** por método. Parâmetros comuns vêm antes:

```java executar
public class Log {
    static String linha(String nivel, Object... partes) {
        StringBuilder sb = new StringBuilder("[" + nivel + "]");
        for (Object p : partes) {
            sb.append(' ').append(p);
        }
        return sb.toString() + " (" + partes.length + ")";
    }

    public static void main(String[] args) {
        System.out.println(linha("INFO", "pedido", 42, true));
        System.out.println(linha("WARN"));
    }
}
```

```saida
[INFO] pedido 42 true (3)
[WARN] (0)
```

Fora dessas posições, não compila. Faz sentido: com um varargs no meio, o compilador não saberia onde terminam os argumentos dele e onde começam os seguintes.

```java nao-compila
public class Ordem {
    static void registrar(String... tags, int nivel) {
    }
}
```

```java nao-compila
public class Dois {
    static void m(int... a, String... b) {
    }
}
```

## Varargs e arrays: quase a mesma coisa

Para a assinatura, `int...` e `int[]` são o mesmo tipo: uma classe não pode ter `m(int[])` e `m(int...)` ao mesmo tempo. A diferença está só em quem chama. Um método varargs aceita um array; um método com parâmetro array **não** aceita valores soltos:

```java nao-compila
public class SoArray {
    static int somar(int[] valores) {
        return valores.length;
    }

    public static void main(String[] args) {
        System.out.println(somar(1, 2, 3));
    }
}
```

Como o parâmetro é um array, ele pode ser `null`, se alguém passar `null` explicitamente. O cast decide o que o `null` é: o array inteiro ou um elemento dele.

> [!PENSE]
> No programa abaixo, `contar` é chamado três vezes: sem nada, com `null` convertido para `String[]` e com `null` convertido para `String`. Os três chegam ao método do mesmo jeito?

```java executar
public class Nulo {
    static int contar(String... itens) {
        return itens == null ? -1 : itens.length;
    }

    public static void main(String[] args) {
        System.out.println(contar());
        System.out.println(contar((String[]) null));
        System.out.println(contar((String) null));
    }
}
```

```saida
0
-1
1
```

Com `Object...`, um array passado sozinho é tratado como **o próprio array de argumentos**, e não como um argumento só. Para que ele vire um único elemento, é preciso o cast para `Object`:

```java executar
public class Embrulho {
    static int quantos(Object... itens) {
        return itens.length;
    }

    public static void main(String[] args) {
        String[] nomes = {"a", "b", "c"};
        System.out.println(quantos((Object[]) nomes));
        System.out.println(quantos((Object) nomes)); //> O cast faz o array inteiro virar um argumento só.
        System.out.println(quantos(nomes, nomes));
    }
}
```

```saida
3
1
2
```

> [!PERGUNTAS]
> **P:** O método pode alterar o array de varargs?
>
> **R:** Pode, como qualquer array. Se quem chamou passou um array pronto, ele vê a mudança; se passou valores soltos, o array foi criado só para a chamada, e ninguém de fora o enxerga.
>
> **P:** Varargs funciona com qualquer tipo?
>
> **R:** Com primitivos, objetos e genéricos. Com genéricos, porém, o compilador emite um aviso de *heap pollution*, assunto da temporada de genéricos.
>
> **P:** Quando vale a pena usar?
>
> **R:** Quando chamar com um número variável de valores é o uso natural, como em `String.format`, `List.of` ou um método de log. Se quase todo mundo passa uma lista que já existe, receba uma `List`.

## Varargs na sobrecarga

Como você viu no [episódio anterior](/assistir/junior-t2-e02), varargs é a **última** fase da escolha: só entra se nenhuma versão aceitar os argumentos sem ele. Entre duas versões varargs, vale a mais específica (`int...` vence `long...`), e as que não têm relação deixam a chamada ambígua:

```java nao-compila
public class Ambiguo {
    static void m(int... v) { }
    static void m(Integer... v) { }

    public static void main(String[] args) {
        m(1, 2);
    }
}
```

> [!PROVA]
> Três pegadinhas recorrentes: varargs fora da última posição; chamar um método de parâmetro `int[]` com valores soltos; e achar que a chamada sem argumentos passa `null`, quando passa um array vazio. E num método com `m(int x)` e `m(int... x)`, a chamada `m(5)` escolhe a versão sem varargs.

## Por baixo dos panos

Varargs é açúcar sintático. O método é compilado com um parâmetro array comum, com o descritor `([I)D` no caso de `media`, e uma marca, a flag `ACC_VARARGS`, que avisa o compilador de quem chamar que ele pode receber valores soltos. Na chamada `media(7, 8, 10)`, o `javac` gera o código de `new int[] {7, 8, 10}` ali mesmo, antes do `invokestatic`.

Isso tem um custo: **cada chamada aloca um array**, mesmo com zero argumentos. Em código muito chamado, o custo aparece. É por isso que `List.of` tem onze versões fixas, de zero a dez elementos, e só usa varargs a partir do décimo primeiro, e que o `EnumSet.of` faz o mesmo. Varargs com tipos genéricos ainda têm um problema próprio, a *poluição do heap*, que a anotação `@SafeVarargs` existe para tratar; você a verá na temporada de genéricos.

> [!MATEMATICA]
> Quanto custa esse array de cada chamada? Um array de 3 referências ocupa 16 bytes de cabeçalho mais 3 × 4 = 12 de referências: 28, arredondados para **32 bytes**. Um método de log com varargs, chamado um milhão de vezes por segundo com 3 argumentos, cria 1.000.000 × 32 = 32 MB de arrays por segundo, todos lixo logo depois. É por isso que bibliotecas de log oferecem versões com 1, 2 e 3 parâmetros fixos.

> [!DESEMPENHO]
> Em código chamado com muita frequência, evite que o caminho comum passe pelo varargs: ofereça sobrecargas com os números de parâmetros mais usados e deixe o varargs só para os casos raros, como fazem `List.of` e `EnumSet.of`. Fora desses pontos quentes, a alocação é barata e não vale complicar a API.

> [!IA]
> A IA usa varargs com naturalidade, mas costuma errar os casos de borda: diz que a chamada sem argumentos passa `null` ou não percebe que um `String[]` passado para `Object...` se espalha em vários argumentos. Peça que ela diga o `length` do array recebido em cada chamada, e confira rodando.

## Na IDE

- **Array desnecessário.** `media(new int[] {7, 8})` recebe o aviso "Redundant array creation for calling varargs method", e o **Alt + Enter** deixa só os valores.
- **Argumento confuso.** Passar `null` ou um array para um `Object...` aparece como "Confusing argument to varargs method", com as duas interpretações para escolher pelo cast.
- **Ver o array.** No depurador, o parâmetro varargs aparece como um array comum, com o `length` e os elementos.

## Resumo para a prova

- `tipo... nome` declara varargs; dentro do método, é um array
- Só um varargs por método, e sempre na última posição
- Aceita zero ou mais valores, ou um array pronto
- Sem argumentos, o método recebe um array vazio, não `null`
- `m(int[])` e `m(int...)` têm a mesma assinatura e não coexistem
- Método com parâmetro array não aceita valores soltos
- Varargs é a última fase da resolução de sobrecarga
- `main(String... args)` é uma assinatura válida
