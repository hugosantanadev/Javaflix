Até aqui, todo programa da trilha fez uma coisa de cada vez: uma linha depois da outra, numa única linha de execução. Um servidor que atende milhares de usuários, uma interface que não pode travar enquanto baixa um arquivo e um cálculo que deveria usar todos os núcleos do processador precisam de **várias** linhas de execução ao mesmo tempo. Em Java, cada uma delas é uma **thread**. Esta temporada começa pelo básico: criar, iniciar e esperar threads.

## Processos e threads

Um **processo** é um programa em execução, com memória própria, isolada dos outros processos pelo sistema operacional. Uma **thread** é uma sequência de instruções dentro de um processo. Todas as threads de um processo compartilham o mesmo heap, e cada uma tem a sua própria pilha de chamadas.

Todo programa Java já começa com uma thread, chamada `main`, que executa o método `main`. A JVM ainda mantém outras em segundo plano, como as do coletor de lixo e do compilador JIT.

```java executar
public class Principal {
    public static void main(String[] args) {
        Thread atual = Thread.currentThread();
        System.out.println(atual.getName() + " " + atual.getPriority() + " " + atual.isDaemon());
    }
}
```

```saida
main 5 false
```

## Duas formas de criar uma thread

A classe `Thread` representa uma thread, e o código que ela executa fica no método `run()`. Há duas formas de fornecê-lo:

1. **Estender `Thread`** e sobrescrever `run()`
2. **Implementar `Runnable`**, a interface funcional com `void run()`, e passar o objeto ao construtor de `Thread`, quase sempre como lambda

A segunda é a preferida: separa a tarefa (o `Runnable`) do mecanismo que a executa (a `Thread`), e deixa a classe livre para estender outra. É a mesma separação que os executores do [episódio 3](/assistir/senior-t1-e03) aproveitam.

```java executar
public class Criando {
    static class Somadora extends Thread {
        int total;

        @Override
        public void run() {
            for (int i = 1; i <= 100; i++) {
                total += i;
            }
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Somadora a = new Somadora();
        a.start();

        int[] produto = {1};
        Thread b = new Thread(() -> {
            for (int i = 1; i <= 5; i++) {
                produto[0] *= i;
            }
        }, "calculadora");
        b.start();

        a.join();
        b.join();
        System.out.println(a.total + " " + produto[0] + " " + b.getName());
    }
}
```

```saida
5050 120 calculadora
```

`join()` faz a thread atual esperar até a outra terminar. Sem ele, o `main` poderia ler `total` antes de a soma acabar. O episódio 2 explora o `join` e o ciclo de vida inteiro.

## start() e run()

A armadilha mais famosa do assunto: quem inicia a thread é `start()`. Chamar `run()` diretamente é uma chamada de método comum, que executa o código na thread **atual**, sem criar thread nenhuma. E uma thread só pode ser iniciada uma vez: um segundo `start()` lança `IllegalThreadStateException`.

```java executar
public class StartOuRun {
    public static void main(String[] args) throws InterruptedException {
        Runnable tarefa = () -> System.out.println("rodando em " + Thread.currentThread().getName());
        Thread t = new Thread(tarefa, "ajudante");

        t.run();
        System.out.println(t.getState());
        t.start();
        t.join();
        System.out.println(t.getState());
        try {
            t.start();
        } catch (IllegalThreadStateException e) {
            System.out.println("uma thread não reinicia");
        }
    }
}
```

```saida
rodando em main
NEW
rodando em ajudante
TERMINATED
uma thread não reinicia
```

## A ordem não é garantida

Com duas threads em execução, quem decide qual roda em cada instante é o **escalonador** do sistema operacional. Duas threads que imprimem em laço podem intercalar as linhas de forma diferente a cada execução. Nenhum dos programas desta temporada depende dessa ordem: todos usam `join` ou outras ferramentas de espera para que a saída seja sempre a mesma. Na prova, uma questão sobre a saída de threads sem sincronização tem como resposta "a ordem não é garantida".

As **prioridades**, de 1 (`MIN_PRIORITY`) a 10 (`MAX_PRIORITY`), com 5 como padrão, são só uma sugestão ao escalonador, que pode ignorá-las. Nenhum programa correto depende delas.

## Threads daemon e exceções

Uma thread **daemon** é de serviço: a JVM termina quando só restam threads daemon rodando, sem esperar por elas. `setDaemon(true)` precisa ser chamado **antes** do `start()`; com a thread já viva, lança `IllegalThreadStateException`. Uma thread herda a condição de daemon de quem a criou, e a `main` não é daemon.

Uma exceção não tratada dentro de `run()` encerra só aquela thread; o `main` continua. Por padrão, ela é impressa no erro padrão como `Exception in thread "nome"`. Um `UncaughtExceptionHandler` permite tratá-la:

```java executar
public class Falhas {
    public static void main(String[] args) throws InterruptedException {
        Thread t = new Thread(() -> {
            throw new IllegalStateException("falhou");
        }, "trabalhadora");
        t.setUncaughtExceptionHandler((thread, erro) -> System.out.println(thread.getName() + " -> " + erro.getMessage()));
        t.start();
        t.join();
        System.out.println("o main continua");
    }
}
```

```saida
trabalhadora -> falhou
o main continua
```

> [!PROVA]
> `start()` cria a thread e chama `run()` nela; `run()` direto executa na thread atual. `start()` duas vezes lança `IllegalThreadStateException`, assim como `setDaemon` numa thread viva. Sem sincronização, a ordem entre threads é imprevisível, e prioridades não a garantem.

## Por baixo dos panos

Antes das threads virtuais do Java 21, toda `Thread` era uma **thread de plataforma**: um invólucro fino sobre uma thread do sistema operacional, na proporção de uma para uma. Criar uma pede ao sistema uma pilha própria, em geral de 1 MB reservado por padrão nas plataformas de 64 bits, e trocar de uma thread para outra, a *troca de contexto*, exige salvar e restaurar registradores no núcleo do sistema. Por isso threads de plataforma são caras: um servidor aguenta alguns milhares, não milhões. As threads virtuais do [episódio 5](/assistir/senior-t1-e05) atacam exatamente esse limite.

Compartilhar o heap é o que torna as threads úteis e perigosas. Duas threads que alteram o mesmo objeto sem coordenação podem perder atualizações, e uma pode nem enxergar o que a outra escreveu, por causa dos caches de cada núcleo. As regras de quando uma escrita fica visível para outra thread estão no **modelo de memória do Java**, o capítulo 17 da especificação. O `join` é uma dessas garantias: tudo o que a thread fez antes de terminar fica visível para quem fez o `join`. A [próxima temporada](/assistir/senior-t2-e01) trata de compartilhar dados com segurança.

## Resumo para a prova

- Toda aplicação começa na thread `main`; `Thread.currentThread()` devolve a thread atual
- Criar: estender `Thread` ou passar um `Runnable` (de preferência uma lambda) ao construtor
- `start()` inicia; `run()` direto não cria thread; `start()` duas vezes lança `IllegalThreadStateException`
- `join()` espera a thread terminar
- A ordem entre threads não é garantida; prioridades (1 a 10, padrão 5) são só sugestão
- `setDaemon(true)` antes do `start`; a JVM não espera threads daemon
- Exceção não tratada encerra só a thread dela
