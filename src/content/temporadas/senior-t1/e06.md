Um servidor precisa saber, em qualquer ponto do atendimento de uma requisição, quem é o usuário, qual é o identificador da requisição para o log, qual transação está aberta. Passar essas informações como parâmetro por todas as camadas polui cada assinatura no caminho. Por décadas, a resposta do Java foi o `ThreadLocal`. Com milhões de threads virtuais, ele mostra seus limites, e o Java 25 tornou definitiva a alternativa: os **scoped values** (JEP 506). Este episódio fecha a temporada com eles e com uma prévia da **concorrência estruturada**, ainda em preview.

## O problema do ThreadLocal

Um `ThreadLocal<T>` guarda um valor separado para cada thread: `set` grava na thread atual, `get` lê da thread atual. Ele tem três defeitos de projeto:

- **É mutável**: qualquer código no caminho pode chamar `set` e trocar o valor, e descobrir quem trocou exige rastrear o programa inteiro.
- **Não tem fim definido**: o valor fica na thread até alguém chamar `remove()`. Numa thread de pool, que atende uma tarefa depois da outra, o valor de uma tarefa **vaza** para a próxima.
- **Herdar custa caro**: um `InheritableThreadLocal` copia os valores para cada thread filha criada, o que pesa com milhões de threads virtuais.

```java executar
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class Vazamento {
    static final ThreadLocal<String> USUARIO = ThreadLocal.withInitial(() -> "anônimo");

    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newSingleThreadExecutor();
        pool.submit(() -> {
            USUARIO.set("ana");
            System.out.println("tarefa 1: " + USUARIO.get());
        }).get();
        pool.submit(() -> System.out.println("tarefa 2: " + USUARIO.get())).get();
        pool.submit(() -> USUARIO.remove()).get();
        pool.submit(() -> System.out.println("tarefa 3: " + USUARIO.get())).get();
        pool.shutdown();
    }
}
```

```saida
tarefa 1: ana
tarefa 2: ana
tarefa 3: anônimo
```

A tarefa 2 nunca gravou nada, mas enxergou a `ana` da tarefa 1, porque as duas rodaram na mesma thread do pool. Num servidor, isso é um usuário vendo os dados de outro.

## ScopedValue: um valor com escopo

Um `ScopedValue<T>`, do pacote `java.lang`, também é lido de qualquer ponto do código, mas é **associado** a um valor só durante a execução de um trecho, e desassociado sozinho no fim:

```java executar
public class Escopo {
    static final ScopedValue<String> USUARIO = ScopedValue.newInstance();

    static void registrar(String acao) {
        System.out.println(USUARIO.orElse("anônimo") + " " + acao);
    }

    public static void main(String[] args) {
        registrar("abriu o site");
        ScopedValue.where(USUARIO, "ana").run(() -> {
            registrar("entrou");
            ScopedValue.where(USUARIO, "suporte").run(() -> registrar("assumiu a sessão"));
            registrar("voltou a navegar");
        });
        registrar("fechou o site");
        System.out.println(USUARIO.isBound());
    }
}
```

```saida
anônimo abriu o site
ana entrou
suporte assumiu a sessão
ana voltou a navegar
anônimo fechou o site
false
```

`where(chave, valor)` prepara a associação, e `run` executa a lambda com ela ativa. Dentro dela, e em todo método chamado a partir dela, `USUARIO.get()` devolve `"ana"`. Não existe `set`: para mudar o valor num trecho, faz-se uma **nova associação aninhada**, que vale só lá dentro; quando ela termina, o valor anterior volta. Quando o `run` termina, normalmente ou com exceção, a associação desaparece. Não há como esquecer o `remove()`.

| Método | O que faz |
|---|---|
| `ScopedValue.newInstance()` | Cria a chave, em geral num campo `static final` |
| `ScopedValue.where(chave, valor)` | Prepara uma associação; pode ser encadeado com mais `.where(...)` |
| `.run(Runnable)` / `.call(operação)` | Executa com as associações ativas; `call` devolve um resultado |
| `get()` | O valor associado; sem associação, lança `NoSuchElementException` |
| `isBound()` | Se há valor associado na thread atual |
| `orElse(outro)` / `orElseThrow(fornecedor)` | O valor, ou uma alternativa quando não há associação |

```java executar
import java.util.NoSuchElementException;

public class Resultados {
    static final ScopedValue<String> USUARIO = ScopedValue.newInstance();
    static final ScopedValue<Integer> NIVEL = ScopedValue.newInstance();

    static String descrever() {
        return USUARIO.get() + " nível " + NIVEL.get();
    }

    public static void main(String[] args) {
        String texto = ScopedValue.where(USUARIO, "bia").where(NIVEL, 3).call(Resultados::descrever);
        System.out.println(texto);
        try {
            descrever();
        } catch (NoSuchElementException e) {
            System.out.println("fora do escopo: " + e.getMessage());
        }
        ScopedValue.where(USUARIO, "caio").run(() -> {
            Thread filha = Thread.ofVirtual().start(() -> System.out.println("a thread filha vê? " + USUARIO.isBound()));
            try {
                filha.join();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });
    }
}
```

```saida
bia nível 3
fora do escopo: ScopedValue not bound
a thread filha vê? false
```

A última linha mostra um detalhe importante: uma thread criada à mão **não herda** as associações. Elas só passam, automaticamente, para as subtarefas da concorrência estruturada, a seguir.

> [!VERSAO]
> Scoped values começaram como incubadora no Java 20, passaram por preview do 21 ao 24 e se tornaram definitivos no Java 25 (JEP 506), sem precisar de `--enable-preview`. As primeiras prévias tinham os atalhos `ScopedValue.runWhere` e `callWhere`, removidos antes da versão final; o caminho é sempre `where(...).run(...)` ou `where(...).call(...)`.

## Concorrência estruturada (preview)

Com um `ExecutorService`, as tarefas que um método dispara não têm vínculo com ele. Se um método envia duas consultas e a primeira falha, a segunda continua rodando à toa; se a thread do método for interrompida, as tarefas nem ficam sabendo. A **concorrência estruturada** propõe que subtarefas obedeçam à estrutura do código, como as chamadas de método: começam num bloco e terminam, obrigatoriamente, antes que ele acabe.

A API é a `StructuredTaskScope`, que no Java 25 está na **quinta preview** (JEP 505). O código abaixo só compila com `javac --release 25 --enable-preview` e só roda com `java --enable-preview`, e por isso não é executado pelo verificador do site; a API ainda pode mudar.

```java
import java.util.concurrent.StructuredTaskScope;
import java.util.concurrent.StructuredTaskScope.Subtask;

public class Painel {
    static final ScopedValue<String> USUARIO = ScopedValue.newInstance();

    static String buscarPedidos() throws InterruptedException {
        Thread.sleep(200);
        return "3 pedidos de " + USUARIO.get();
    }

    static int buscarPontos() throws InterruptedException {
        Thread.sleep(100);
        return 1200;
    }

    public static void main(String[] args) {
        ScopedValue.where(USUARIO, "ana").run(() -> {
            try (var escopo = StructuredTaskScope.open()) {
                Subtask<String> pedidos = escopo.fork(Painel::buscarPedidos);
                Subtask<Integer> pontos = escopo.fork(Painel::buscarPontos);
                escopo.join();
                System.out.println(pedidos.get() + ", " + pontos.get() + " pontos");
            } catch (StructuredTaskScope.FailedException e) {
                System.out.println("falhou: " + e.getCause().getMessage());
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });
    }
}
```

```saida
3 pedidos de ana, 1200 pontos
```

`open()` abre o escopo, `fork` inicia cada subtarefa numa thread virtual nova, e `join()` espera. As subtarefas **herdam** os scoped values de quem as criou: `buscarPedidos` enxerga `ana` sem receber parâmetro. O try-with-resources garante que nenhuma subtarefa sobrevive ao bloco.

O escopo aberto com `open()` segue a política "todas ou nenhuma": se uma subtarefa falha, as outras são **canceladas** (interrompidas) na hora, e `join()` lança `FailedException` com a causa. Se `buscarPontos` lançasse `IllegalStateException("serviço de pontos fora do ar")` enquanto `buscarPedidos` ainda dormia, a saída seria `falhou: serviço de pontos fora do ar`, sem esperar os pedidos. Outras políticas vêm de um `Joiner` passado ao `open`:

| Escopo | `join()` |
|---|---|
| `open()` | Espera todas terminarem com sucesso; na primeira falha, cancela as outras e lança `FailedException` |
| `open(Joiner.allSuccessfulOrThrow())` | Igual, mas devolve um `Stream` com as subtarefas concluídas |
| `open(Joiner.anySuccessfulResultOrThrow())` | Devolve o resultado da primeira que der certo e cancela as outras |
| `open(Joiner.awaitAll())` | Espera todas, com ou sem falhas; cada `Subtask` informa seu `state()` |

O `anySuccessfulResultOrThrow` é o `invokeAny` do [episódio 4](/assistir/senior-t1-e04), agora com a garantia de que as perdedoras terminam antes de o bloco acabar.

> [!PROVA]
> `ScopedValue` é definitivo no Java 25: chave em `static final`, valor associado com `where(...).run(...)` ou `call(...)`, lido com `get()`, que lança `NoSuchElementException` sem associação. Não tem `set`; associações aninhadas valem só no bloco interno. Threads criadas à mão não herdam o valor. `StructuredTaskScope` é preview no Java 25, e recursos em preview não caem nas provas.

## Por baixo dos panos

Cada thread guarda uma referência para o seu conjunto atual de associações, uma pequena estrutura **imutável** encadeada à anterior. `where(...).run(...)` cria um conjunto novo que aponta para o atual, troca a referência, executa a lambda e, num `finally`, devolve a referência antiga. Por isso o aninhamento funciona e nada vaza: desfazer uma associação é só voltar um ponteiro. Para que `get()` seja rápido mesmo dentro de laços, a JVM mantém por thread um pequeno cache dos valores lidos recentemente.

A imutabilidade também barateia a herança. Quando a `StructuredTaskScope` cria uma subtarefa, a thread filha recebe a **mesma referência** ao conjunto de associações do pai, sem copiar nada, em tempo constante. É seguro porque ninguém pode alterá-lo, e porque o escopo estruturado garante que as filhas terminam antes de o pai sair do bloco, quando as associações deixariam de valer. O `InheritableThreadLocal`, ao contrário, precisa copiar um mapa inteiro a cada thread criada.

Note que imutável é a **associação**, não o objeto: um `ScopedValue<List<String>>` aponta sempre para a mesma lista durante o escopo, mas a lista em si pode ser alterada, como no desafio deste episódio.

## Resumo para a prova

- `ThreadLocal` é mutável, vive até o `remove()` e vaza entre tarefas de um pool
- `ScopedValue.newInstance()` cria a chave; `ScopedValue.where(chave, valor).run(...)` ou `.call(...)` associa durante o bloco
- `get()` sem associação lança `NoSuchElementException`; `isBound()`, `orElse` e `orElseThrow` evitam a exceção
- Sem `set`: uma associação aninhada vale só no bloco interno, e a anterior volta depois
- A associação some ao fim do bloco, mesmo com exceção; threads criadas à mão não herdam
- Definitivo no Java 25 (JEP 506); `StructuredTaskScope` ainda é preview (JEP 505)
