Um servidor web tradicional atende cada requisição numa thread: lê a requisição, consulta o banco, chama outro serviço, monta a resposta. Quase todo esse tempo a thread passa **esperando** a rede ou o disco, sem usar o processador. Como threads de plataforma são caras, o servidor limita o pool a algumas centenas, e sob carga as requisições fazem fila mesmo com a CPU ociosa. A saída antiga era o estilo assíncrono, com callbacks e `CompletableFuture`, que escala mas é difícil de ler e depurar. O Java 21 trouxe outra saída: as **threads virtuais** (JEP 444), tão baratas que dá para criar uma por tarefa, aos milhões, mantendo o código simples e bloqueante de sempre.

## Criando threads virtuais

Uma thread virtual continua sendo um `java.lang.Thread`: `join`, `interrupt`, `sleep` e `getState` funcionam igual. O que muda é a criação. Não há construtor público para elas; `new Thread(...)` sempre cria uma thread de plataforma. As formas são:

| Forma | O que faz |
|---|---|
| `Thread.startVirtualThread(tarefa)` | Cria e inicia uma thread virtual |
| `Thread.ofVirtual().start(tarefa)` | O mesmo, por meio de um construtor (`Thread.Builder`) |
| `Thread.ofVirtual().name("v-", 0).unstarted(tarefa)` | Cria sem iniciar, com nomes numerados a partir de 0 |
| `Thread.ofVirtual().factory()` | Uma `ThreadFactory` que produz threads virtuais |
| `Executors.newVirtualThreadPerTaskExecutor()` | Um `ExecutorService` que cria uma thread virtual nova para cada tarefa |

`Thread.ofPlatform()` é o construtor equivalente para threads de plataforma, e `isVirtual()` diz de que tipo é uma thread.

```java executar
public class Criando {
    public static void main(String[] args) throws InterruptedException {
        Thread.Builder construtor = Thread.ofVirtual().name("trabalhador-", 1);
        Thread a = construtor.start(() -> System.out.println("oi de " + Thread.currentThread().getName()));
        a.join();
        Thread b = construtor.unstarted(() -> { });
        Thread c = Thread.startVirtualThread(() -> { });
        c.join();

        System.out.println(b.getName() + " " + b.getState() + " [" + c.getName() + "]");
        System.out.println(a.isVirtual() + " " + new Thread(() -> { }).isVirtual() + " " + Thread.currentThread().isVirtual());
    }
}
```

```saida
oi de trabalhador-1
trabalhador-2 NEW []
true false false
```

O construtor numera cada thread que produz, iniciada ou não. Sem `name`, uma thread virtual não tem nome: `getName()` devolve uma string vazia. E a thread `main` é de plataforma.

## O que muda em relação às threads de plataforma

| | Plataforma | Virtual |
|---|---|---|
| Criação | `new Thread`, `Thread.ofPlatform()` | `Thread.ofVirtual()`, `startVirtualThread`, executor por tarefa |
| Daemon | Herda de quem criou; pode mudar antes do `start` | **Sempre** daemon; `setDaemon(false)` lança `IllegalArgumentException` |
| Prioridade | 1 a 10, padrão 5 | Sempre 5; `setPriority` é ignorado |
| Nome padrão | `Thread-0`, `Thread-1`... | Vazio |
| Custo | Uma thread do sistema operacional, pilha de cerca de 1 MB | Algumas centenas de bytes no heap, que crescem conforme a pilha |

```java executar
public class Diferencas {
    public static void main(String[] args) {
        Thread v = Thread.ofVirtual().unstarted(() -> { });
        v.setPriority(Thread.MAX_PRIORITY);
        System.out.println(v.isDaemon() + " " + v.getPriority());
        try {
            v.setDaemon(false);
        } catch (IllegalArgumentException e) {
            System.out.println("recusado: " + e.getMessage());
        }

        Thread.ofVirtual().start(() -> {
            try {
                Thread.sleep(500);
            } catch (InterruptedException e) {
                return;
            }
            System.out.println("nunca aparece");
        });
        System.out.println("fim do main");
    }
}
```

```saida
true 5
recusado: 'false' not legal for virtual threads
fim do main
```

Por serem daemon, threads virtuais não seguram a JVM: o `main` terminou, e o programa acabou sem esperar a que dormia. Quem precisa do resultado tem de esperar por ela com `join` ou com um executor.

## Uma thread por tarefa

O executor `newVirtualThreadPerTaskExecutor()` não tem pool: cada `submit` cria uma thread virtual nova, e não há fila. Com tarefas que passam o tempo esperando, isso permite rodar dezenas de milhares ao mesmo tempo:

```java executar
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class DezMil {
    public static void main(String[] args) throws Exception {
        List<Future<Integer>> futuros = new ArrayList<>();
        try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 1; i <= 10_000; i++) {
                int n = i;
                futuros.add(executor.submit(() -> {
                    Thread.sleep(1000);
                    return n;
                }));
            }
        }
        long soma = 0;
        for (Future<Integer> f : futuros) {
            soma += f.get();
        }
        System.out.println(soma);
    }
}
```

```saida
50005000
```

As 10 mil tarefas dormem um segundo cada, e o programa termina em pouco mais de um segundo, porque todas dormem **ao mesmo tempo**. Com um `newFixedThreadPool(100)`, levaria 100 segundos. O try-with-resources espera todas terminarem no `close()`, e por isso os `get()` depois dele já não bloqueiam.

## Quando usar e quando não usar

Threads virtuais ganham em **vazão**, não em velocidade: uma tarefa não roda mais rápido numa thread virtual, mas muitas mais tarefas que esperam podem estar em andamento ao mesmo tempo.

- **Servem** para tarefas que passam a maior parte do tempo bloqueadas: chamadas HTTP, consultas ao banco, leitura de arquivos, filas.
- **Não ajudam** em tarefas que usam a CPU o tempo todo, como compressão ou cálculos pesados. Para essas, um pool com uma thread por núcleo continua sendo o certo.
- **Não as coloque num pool.** Elas são baratas; o pool existia para economizar threads caras. Para limitar o acesso a um recurso escasso, como no máximo 20 conexões ao banco, use um `Semaphore`, assunto da [próxima temporada](/assistir/senior-t2-e04), em vez de limitar o número de threads.
- **Cuidado com `ThreadLocal`** usado como cache de objetos caros: com um milhão de threads, são um milhão de cópias. Os *scoped values* do [próximo episódio](/assistir/senior-t1-e06) são a alternativa.

> [!VERSAO]
> No Java 21, uma thread virtual que bloqueia dentro de um bloco ou método `synchronized` fica **presa** (*pinning*) à thread de plataforma que a executa, e a impede de rodar outras threads virtuais. Por isso a recomendação, no 21, era trocar `synchronized` por `ReentrantLock` em código que bloqueia. O Java 24 (JEP 491) eliminou essa limitação: hoje, só a chamada a código nativo ainda prende a thread.

> [!PROVA]
> Threads virtuais são `Thread`, criadas por `Thread.ofVirtual()`, `Thread.startVirtualThread` ou `Executors.newVirtualThreadPerTaskExecutor()`, nunca por `new Thread`. São sempre daemon, com prioridade 5 fixa e sem nome por padrão. `setDaemon(false)` lança `IllegalArgumentException`. Melhoram a vazão de tarefas bloqueantes, não a velocidade de tarefas de CPU.

## Por baixo dos panos

A JVM executa as threads virtuais sobre um pequeno conjunto de threads de plataforma, as **carregadoras** (*carrier threads*), de um `ForkJoinPool` próprio com uma thread por núcleo do processador. Quando uma thread virtual chama uma operação que bloquearia, como `sleep`, uma leitura de socket ou o `take` de uma fila, ela é **desmontada**: os quadros da sua pilha são copiados para o heap, e a carregadora fica livre para montar outra thread virtual. Quando a operação conclui, a thread virtual volta à fila do escalonador e é remontada, possivelmente em outra carregadora. Imprimir uma thread virtual em execução mostra isso, algo como `VirtualThread[#27]/runnable@ForkJoinPool-1-worker-1`.

Para isso funcionar, as partes bloqueantes do JDK, como `Thread.sleep`, os sockets e as classes de `java.util.concurrent`, foram reescritas para desmontar em vez de bloquear a thread do sistema. Por isso não é preciso mudar o código: o mesmo `InputStream.read()` que prendia uma thread de plataforma apenas suspende a virtual. A pilha de uma thread virtual vive no heap como um objeto comum, coletado quando a thread termina, e é isso que permite milhões delas: o custo passa a ser proporcional à profundidade real da pilha, não a uma reserva fixa de memória.

## Resumo para a prova

- Criar: `Thread.ofVirtual().start/unstarted`, `Thread.startVirtualThread`, `Executors.newVirtualThreadPerTaskExecutor()`; `new Thread` é sempre de plataforma
- `isVirtual()` identifica; a thread `main` é de plataforma
- Sempre daemon (`setDaemon(false)` lança `IllegalArgumentException`), prioridade fixa 5, nome vazio por padrão
- Uma thread virtual por tarefa, sem pool; o executor também é `AutoCloseable`
- Ganham em vazão de tarefas bloqueantes; não aceleram tarefas de CPU
- Bloquear desmonta a thread virtual da carregadora; no Java 21, `synchronized` causava *pinning*, resolvido no 24
