O `ExecutorService` do [episódio anterior](/assistir/senior-t1-e03) executa tarefas assim que há uma thread livre. Dois pedidos comuns ficaram de fora: rodar uma tarefa **mais tarde** ou **de tempos em tempos**, como um lembrete ou uma limpeza de cache a cada minuto, e enviar um **lote** de tarefas de uma vez, esperando todas ou só a primeira que der certo. Este episódio cobre o `ScheduledExecutorService` e os métodos `invokeAll` e `invokeAny`.

## ScheduledExecutorService

`ScheduledExecutorService` estende `ExecutorService` com quatro métodos de agendamento. Ele sai de `Executors.newScheduledThreadPool(n)` ou de `Executors.newSingleThreadScheduledExecutor()`:

| Método | Devolve | Quando roda |
|---|---|---|
| `schedule(Callable<V>, atraso, unidade)` | `ScheduledFuture<V>` | Uma vez, depois do atraso |
| `schedule(Runnable, atraso, unidade)` | `ScheduledFuture<?>` | Uma vez, depois do atraso |
| `scheduleAtFixedRate(Runnable, inicial, periodo, unidade)` | `ScheduledFuture<?>` | Repetidamente, em intervalos contados do **início** de cada execução |
| `scheduleWithFixedDelay(Runnable, inicial, atraso, unidade)` | `ScheduledFuture<?>` | Repetidamente, com o atraso contado a partir do **fim** de cada execução |

Os dois métodos repetitivos só aceitam `Runnable`: uma tarefa que roda para sempre não tem um resultado final para devolver. Passar a eles uma lambda que devolve valor não compila. E como o tipo declarado importa, um `ExecutorService` que guarda um executor agendado não enxerga `schedule`; a variável precisa ser `ScheduledExecutorService`.

```java executar
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.ScheduledFuture;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

public class Agenda {
    public static void main(String[] args) throws Exception {
        ScheduledExecutorService agendador = Executors.newScheduledThreadPool(1);
        ScheduledFuture<String> lembrete = agendador.schedule(() -> "lembrete disparado", 200, TimeUnit.MILLISECONDS);
        System.out.println("agendado; pronto? " + lembrete.isDone());
        System.out.println(lembrete.get());

        AtomicInteger tiques = new AtomicInteger();
        CountDownLatch tres = new CountDownLatch(3);
        ScheduledFuture<?> relogio = agendador.scheduleAtFixedRate(() -> {
            int n = tiques.incrementAndGet();
            if (n <= 3) {
                System.out.println("tique " + n);
                tres.countDown();
            }
        }, 0, 100, TimeUnit.MILLISECONDS);
        tres.await();
        relogio.cancel(false);
        System.out.println("cancelado: " + relogio.isCancelled());
        agendador.shutdown();
    }
}
```

```saida
agendado; pronto? false
lembrete disparado
tique 1
tique 2
tique 3
cancelado: true
```

O `get()` do lembrete espera os 200 ms e devolve o valor do `Callable`. A tarefa periódica nunca termina sozinha: quem a para é o `cancel`. O `CountDownLatch` é um contador que começa em 3; cada `countDown()` desconta um, e o `await()` bloqueia o `main` até chegar a zero. Ele e outros sincronizadores aparecem na [próxima temporada](/assistir/senior-t2-e04). O `if (n <= 3)` evita que um quarto tique escape entre o `await` e o `cancel`.

## Taxa fixa ou atraso fixo

A diferença entre os dois métodos repetitivos aparece quando a tarefa demora. Imagine um período de 100 ms e uma tarefa que leva 30 ms:

| | 1ª execução | 2ª execução | 3ª execução |
|---|---|---|---|
| `scheduleAtFixedRate` | começa em 0 ms | começa em 100 ms | começa em 200 ms |
| `scheduleWithFixedDelay` | começa em 0 ms | começa em 130 ms | começa em 260 ms |

A **taxa fixa** mantém o compasso, como um relógio. O **atraso fixo** garante um intervalo de descanso entre o fim de uma e o começo da próxima. Se a tarefa de taxa fixa demorar mais que o período, a próxima só começa quando a anterior acabar: execuções da mesma tarefa periódica **nunca se sobrepõem**.

## Quando a tarefa periódica falha

Se uma execução lança exceção, as próximas são **canceladas em silêncio**, e nada é impresso. A única pista fica no `ScheduledFuture`: ele passa a estar terminado, e o `get()`, que normalmente esperaria para sempre, lança `ExecutionException` com a causa.

```java executar
import java.util.concurrent.ExecutionException;
import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.ScheduledFuture;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

public class Falha {
    public static void main(String[] args) throws InterruptedException {
        ScheduledExecutorService agendador = Executors.newSingleThreadScheduledExecutor();
        AtomicInteger execucoes = new AtomicInteger();
        ScheduledFuture<?> tarefa = agendador.scheduleWithFixedDelay(() -> {
            if (execucoes.incrementAndGet() == 3) {
                throw new IllegalStateException("sensor desconectado");
            }
        }, 0, 10, TimeUnit.MILLISECONDS);
        try {
            tarefa.get();
        } catch (ExecutionException e) {
            System.out.println(execucoes.get() + " execuções; parou com: " + e.getCause().getMessage());
        }
        System.out.println(tarefa.isDone());
        agendador.shutdown();
    }
}
```

```saida
3 execuções; parou com: sensor desconectado
true
```

Por isso, uma tarefa periódica de produção costuma envolver o corpo inteiro num `try/catch` que registra o erro e deixa a repetição continuar.

No `shutdown()`, um executor agendado ainda roda as tarefas de execução única que estavam esperando o atraso, mas **cancela** as periódicas. Sem essa regra, um agendador com uma tarefa periódica nunca terminaria.

## invokeAll: todas as tarefas

`invokeAll` recebe uma coleção de `Callable`, envia todas e **bloqueia** até que todas terminem, com sucesso ou falha. Devolve uma `List<Future<T>>` na mesma ordem da coleção, com todos os `Future` já prontos. Há uma versão com prazo: o que não terminar a tempo é cancelado.

```java executar
import java.io.IOException;
import java.util.List;
import java.util.concurrent.Callable;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;

public class Todas {
    public static void main(String[] args) throws InterruptedException {
        ExecutorService pool = Executors.newFixedThreadPool(3);
        List<Callable<String>> tarefas = List.of(
            () -> { Thread.sleep(300); return "lenta"; },
            () -> "rápida",
            () -> { throw new IOException("quebrou"); });
        List<Future<String>> resultados = pool.invokeAll(tarefas);
        for (Future<String> f : resultados) {
            try {
                System.out.println(f.isDone() + " " + f.get());
            } catch (ExecutionException e) {
                System.out.println(f.isDone() + " falhou: " + e.getCause().getMessage());
            }
        }
        List<Future<String>> comPrazo = pool.invokeAll(tarefas, 100, TimeUnit.MILLISECONDS);
        System.out.println(comPrazo.stream().map(Future::isCancelled).toList());
        pool.shutdown();
    }
}
```

```saida
true lenta
true rápida
true falhou: quebrou
[true, false, false]
```

A tarefa lenta aparece primeiro mesmo terminando por último, porque a lista segue a ordem de envio. Na segunda chamada, só ela estoura o prazo de 100 ms e é cancelada.

## invokeAny: a primeira que der certo

`invokeAny` também recebe uma coleção de `Callable`, mas devolve **um resultado** do tipo `T`, não um `Future`: o da primeira tarefa que terminar **com sucesso**. As outras são canceladas. Falhas são ignoradas enquanto houver chance de sucesso; se todas falharem, lança `ExecutionException`. É o padrão de consultar vários espelhos de um serviço e ficar com quem responder primeiro.

```java executar
import java.io.IOException;
import java.util.List;
import java.util.concurrent.Callable;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class Qualquer {
    public static void main(String[] args) throws InterruptedException {
        ExecutorService pool = Executors.newFixedThreadPool(3);
        List<Callable<String>> espelhos = List.of(
            () -> { throw new IOException("espelho 1 fora do ar"); },
            () -> { Thread.sleep(3000); return "espelho 2"; },
            () -> { Thread.sleep(100); return "espelho 3"; });
        List<Callable<String>> quebrados = List.of(
            () -> { throw new IOException("a"); },
            () -> { throw new IOException("b"); });
        try {
            System.out.println("baixado do " + pool.invokeAny(espelhos));
            pool.invokeAny(quebrados);
        } catch (ExecutionException e) {
            System.out.println("todos falharam: " + e.getCause().getClass().getSimpleName());
        } finally {
            pool.shutdown();
        }
    }
}
```

```saida
baixado do espelho 3
todos falharam: IOException
```

O espelho 1 falha na hora, mas o `invokeAny` segue esperando. O espelho 3 responde em 100 ms e vence; o espelho 2, ainda dormindo, é cancelado e interrompido, e por isso o programa não espera os 3 segundos dele para terminar.

> [!PROVA]
> `schedule` aceita `Runnable` e `Callable`; `scheduleAtFixedRate` e `scheduleWithFixedDelay` só `Runnable`. Os métodos de agendamento só existem em `ScheduledExecutorService`. `invokeAll` devolve `List<Future<T>>` na ordem de envio e espera todas; `invokeAny` devolve `T` e espera só a primeira com sucesso. Os dois recebem `Collection` de `Callable` e bloqueiam a thread que chama.

## Por baixo dos panos

O `ScheduledThreadPoolExecutor`, a classe por trás das fábricas agendadas, guarda as tarefas numa fila de prioridade ordenada pelo instante de disparo, a `DelayedWorkQueue`, que é um heap binário. As threads do pool pedem a próxima tarefa à fila, e a fila as faz esperar até o instante da primeira. Uma tarefa periódica, ao terminar, calcula o próximo disparo e **se recoloca** na fila: na taxa fixa, somando o período ao disparo anterior; no atraso fixo, somando o atraso ao momento atual. Como só volta à fila depois de terminar, nunca roda duas vezes ao mesmo tempo, e quando lança exceção simplesmente não volta.

Antes do Java 5, o agendamento era feito com `java.util.Timer`, que usa uma única thread: uma tarefa lenta atrasa todas as outras, e uma exceção não tratada mata o `Timer` inteiro. O `ScheduledExecutorService` resolve os dois problemas e é a escolha recomendada.

O `invokeAny` usa internamente um `ExecutorCompletionService`, que entrega os `Future` na ordem em que **terminam**, não na de envio. Essa classe também está disponível diretamente, para quando se quer processar cada resultado assim que fica pronto.

## Resumo para a prova

- `Executors.newScheduledThreadPool(n)` e `newSingleThreadScheduledExecutor()` devolvem `ScheduledExecutorService`
- `schedule(tarefa, atraso, unidade)` roda uma vez e aceita `Callable` ou `Runnable`
- `scheduleAtFixedRate` conta o período do início; `scheduleWithFixedDelay`, do fim; os dois só aceitam `Runnable`
- Uma exceção cancela as próximas execuções da tarefa periódica; o `get()` a revela
- `invokeAll` devolve `List<Future<T>>` na ordem da coleção, depois que todas terminam
- `invokeAny` devolve o resultado da primeira que terminar com sucesso e cancela as outras
