Criar uma `Thread` para cada tarefa funciona em exemplos, mas não escala: threads de plataforma são caras de criar, e um servidor que abrisse uma por requisição cairia sob carga. O pacote `java.util.concurrent`, do Java 5, separa as duas coisas: você descreve **tarefas**, e um **executor** decide em que threads elas rodam, reaproveitando um conjunto delas, o *pool*. Este episódio cobre o `ExecutorService`, as tarefas com resultado (`Callable`) e o `Future`, que representa um resultado que ainda vai chegar.

## Executores prontos

A classe `Executors` tem fábricas para os tipos mais comuns:

| Fábrica | Comportamento |
|---|---|
| `newSingleThreadExecutor()` | Uma thread; as tarefas rodam uma de cada vez, na ordem de envio |
| `newFixedThreadPool(n)` | `n` threads fixas; as tarefas excedentes esperam numa fila |
| `newCachedThreadPool()` | Cria threads sob demanda e reaproveita as ociosas |
| `newScheduledThreadPool(n)` | Para tarefas agendadas, assunto do [próximo episódio](/assistir/senior-t1-e04) |
| `newVirtualThreadPerTaskExecutor()` | Uma thread virtual por tarefa (Java 21), no [episódio 5](/assistir/senior-t1-e05) |

## Runnable e Callable

| | `Runnable` | `Callable<V>` |
|---|---|---|
| Método | `void run()` | `V call() throws Exception` |
| Devolve valor | Não | Sim |
| Lança exceção checked | Não | Sim |

Um `ExecutorService` aceita os dois. `execute(Runnable)` só dispara a tarefa e devolve `void`. `submit(...)` devolve um `Future`, por onde se acompanha a tarefa e se obtém o resultado: com um `Callable<V>`, um `Future<V>`; com um `Runnable`, um `Future<?>` cujo `get()` devolve `null`.

```java executar
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class Tarefas {
    public static void main(String[] args) throws Exception {
        ExecutorService executor = Executors.newSingleThreadExecutor();
        try {
            Future<Integer> resposta = executor.submit(() -> 6 * 7);
            Future<?> semRetorno = executor.submit(() -> System.out.println("tarefa sem retorno"));
            System.out.println(resposta.get() + " " + semRetorno.get() + " " + resposta.isDone());

            Future<Integer> falha = executor.submit(() -> {
                if (true) {
                    throw new IllegalStateException("dado inválido");
                }
                return 1;
            });
            try {
                falha.get();
            } catch (ExecutionException e) {
                System.out.println("falhou: " + e.getCause().getMessage());
            }
        } finally {
            executor.shutdown();
        }
    }
}
```

```saida
tarefa sem retorno
42 null true
falhou: dado inválido
```

A primeira linha vem antes da segunda porque o `main` só imprime depois do `get()` da segunda tarefa, que espera ela terminar. Uma tarefa enviada com `execute` não daria essa garantia: sem `Future`, não há como esperar por ela.

## Future: o resultado que vai chegar

| Método | O que faz |
|---|---|
| `get()` | Espera a tarefa terminar e devolve o resultado |
| `get(tempo, unidade)` | Espera até o prazo; depois, lança `TimeoutException` |
| `isDone()` | Diz se terminou (normalmente, com exceção ou cancelada) |
| `cancel(boolean)` | Tenta cancelar; com `true`, interrompe a thread que a executa |
| `isCancelled()` | Diz se foi cancelada antes de terminar |

Uma exceção lançada pela tarefa **não** aparece no momento em que acontece: fica guardada no `Future`, e o `get()` a relança embrulhada numa `ExecutionException`, com a original em `getCause()`. Uma tarefa enviada com `execute`, que não tem `Future`, perde a exceção para o tratador padrão da thread.

```java executar
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.TimeoutException;

public class Prazos {
    public static void main(String[] args) throws Exception {
        ExecutorService executor = Executors.newSingleThreadExecutor();
        Future<String> lenta = executor.submit(() -> {
            Thread.sleep(500);
            return "pronto";
        });
        try {
            lenta.get(50, TimeUnit.MILLISECONDS);
        } catch (TimeoutException e) {
            System.out.println("ainda não terminou: " + lenta.isDone());
        }
        System.out.println(lenta.get() + " " + lenta.isDone());
        executor.shutdown();
    }
}
```

```saida
ainda não terminou: false
pronto true
```

O `TimeoutException` só desiste de **esperar**: a tarefa continua rodando, e o segundo `get()` a recebe.

## Encerrando o executor

As threads de um pool não são daemon. Um programa que esquece de encerrar o executor **nunca termina**: o `main` acaba, mas a JVM continua esperando as threads do pool, que esperam por tarefas que nunca virão.

| Método | Efeito |
|---|---|
| `shutdown()` | Para de aceitar tarefas; as já enviadas terminam normalmente |
| `shutdownNow()` | Tenta interromper as tarefas em execução e devolve a lista das que nem começaram |
| `awaitTermination(tempo, unidade)` | Espera o fim de tudo, até o prazo; devolve se conseguiu |
| `isShutdown()` / `isTerminated()` | Se recebeu o pedido de encerramento / se já terminou tudo |

Enviar uma tarefa depois do `shutdown()` lança `RejectedExecutionException`. O padrão comum é `shutdown()` seguido de `awaitTermination`, num `finally`.

```java executar
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.RejectedExecutionException;
import java.util.concurrent.TimeUnit;

public class Encerrando {
    public static void main(String[] args) throws InterruptedException {
        ExecutorService executor = Executors.newFixedThreadPool(2);
        executor.submit(() -> System.out.println("última tarefa"));
        executor.shutdown();
        System.out.println(executor.isShutdown() + " " + executor.awaitTermination(1, TimeUnit.SECONDS) + " " + executor.isTerminated());
        try {
            executor.submit(() -> System.out.println("tarde demais"));
        } catch (RejectedExecutionException e) {
            System.out.println("recusada depois do shutdown");
        }
    }
}
```

```saida
última tarefa
true true true
recusada depois do shutdown
```

> [!VERSAO]
> Desde o Java 19, `ExecutorService` implementa `AutoCloseable`, e pode ser usado num try-with-resources: o `close()` chama `shutdown()` e espera todas as tarefas terminarem. No Java 17, o mesmo código não compila.

```java executar java21
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class ComRecurso {
    public static void main(String[] args) throws Exception {
        try (ExecutorService executor = Executors.newFixedThreadPool(2)) {
            Future<String> f = executor.submit(() -> "dentro do try");
            System.out.println(f.get());
        }
        System.out.println("executor fechado");
    }
}
```

```saida
dentro do try
executor fechado
```

> [!PROVA]
> `submit` devolve `Future`; `execute` devolve `void`. `Callable.call()` devolve valor e pode lançar checked; `Runnable.run()` não. `get()` embrulha a exceção da tarefa em `ExecutionException`. Sem `shutdown`, o programa não termina. Depois do `shutdown`, `submit` lança `RejectedExecutionException`.

## Por baixo dos panos

Todos os executores de `Executors`, exceto o de threads virtuais e o `ForkJoinPool`, são configurações de uma mesma classe, `ThreadPoolExecutor`: um número mínimo e máximo de threads, uma fila de tarefas e uma política para quando a fila enche. O `newFixedThreadPool(n)` usa `n` threads e uma `LinkedBlockingQueue` sem limite; o `newCachedThreadPool()` começa sem threads, cria quantas forem precisas e descarta as que ficam 60 segundos ociosas. Cada thread do pool é um laço: tira uma tarefa da fila, executa, volta à fila.

O `Future` devolvido por `submit` é um `FutureTask`, que embrulha a tarefa e guarda o resultado ou a exceção num campo. O `get()` estaciona a thread que chama até a tarefa terminar e a acorda quando o resultado chega. O Java 8 acrescentou o `CompletableFuture`, que permite encadear ações sem bloquear (`thenApply`, `thenCombine`), e o Java 19 deu ao `Future` os métodos `resultNow()` e `state()`, que consultam o resultado sem esperar.

## Resumo para a prova

- Fábricas: `newSingleThreadExecutor`, `newFixedThreadPool(n)`, `newCachedThreadPool`
- `execute(Runnable)` devolve `void`; `submit` devolve `Future`
- `Callable<V>.call()` devolve `V` e lança `Exception`; `Future` de `Runnable` devolve `null`
- `get()` espera; `get(prazo)` lança `TimeoutException`; a exceção da tarefa chega como `ExecutionException`
- Sempre encerre: `shutdown()` deixa terminar, `shutdownNow()` interrompe; depois, `submit` é recusado
- Java 19+: `ExecutorService` é `AutoCloseable` e funciona em try-with-resources
