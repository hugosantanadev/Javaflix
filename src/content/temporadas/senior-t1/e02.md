Uma thread passa por estados bem definidos, do momento em que é criada até terminar. Saber em qual estado ela está, como fazê-la esperar e, principalmente, como pedir que ela pare são as bases para o resto da temporada. O último ponto é o mais sutil: em Java, não se mata uma thread; pede-se educadamente que ela termine, com a **interrupção**.

## Os seis estados

O enum `Thread.State` tem seis valores, e `getState()` informa o atual:

| Estado | Quando |
|---|---|
| `NEW` | Criada, ainda sem `start()` |
| `RUNNABLE` | Executando ou pronta para executar, esperando a CPU |
| `BLOCKED` | Esperando para entrar num bloco `synchronized` ocupado |
| `WAITING` | Esperando sem prazo: `join()`, `wait()` |
| `TIMED_WAITING` | Esperando com prazo: `sleep(ms)`, `join(ms)`, `wait(ms)` |
| `TERMINATED` | O `run()` terminou, normalmente ou com exceção |

Não existe estado "RUNNING" separado: rodando ou na fila da CPU, a thread está em `RUNNABLE`. E de `TERMINATED` não há volta.

```java executar
import java.util.concurrent.CountDownLatch;

public class Estados {
    public static void main(String[] args) throws InterruptedException {
        CountDownLatch dormindo = new CountDownLatch(1);
        Thread t = new Thread(() -> {
            dormindo.countDown();
            try {
                Thread.sleep(1000);
            } catch (InterruptedException e) {
                System.out.println("acordada antes da hora");
            }
        });
        System.out.println(t.getState());
        t.start();
        dormindo.await();
        Thread.sleep(200);
        System.out.println(t.getState());
        t.interrupt();
        t.join();
        System.out.println(t.getState());
    }
}
```

```saida
NEW
TIMED_WAITING
acordada antes da hora
TERMINATED
```

O `CountDownLatch` garante que a thread já chegou ao `sleep` antes de o `main` olhar o estado. Ferramentas como ele, que fazem uma thread esperar por outra, são o assunto da [próxima temporada](/assistir/senior-t2-e04).

## sleep e join

`Thread.sleep(ms)` suspende a thread **atual** pelo tempo pedido, no mínimo. É um método estático: `t.sleep(1000)` compila, mas faz dormir a thread que executa a linha, não `t`. `sleep` não libera nenhuma trava que a thread tenha.

`t.join()` faz a thread atual esperar até `t` terminar; `join(ms)` desiste depois do prazo. Os dois declaram `InterruptedException`, que é checked: quem os chama precisa tratá-la ou declará-la.

```java executar
public class Esperando {
    public static void main(String[] args) throws InterruptedException {
        StringBuilder log = new StringBuilder();
        Thread lenta = new Thread(() -> {
            try {
                Thread.sleep(300);
            } catch (InterruptedException e) {
                return;
            }
            log.append("lenta terminou; ");
        });
        lenta.start();
        lenta.join(50);
        log.append("desisti de esperar; ");
        System.out.println(lenta.isAlive());
        lenta.join();
        System.out.println(log + "" + lenta.isAlive());
    }
}
```

```saida
true
desisti de esperar; lenta terminou; false
```

## Interrupção: pedir para parar

`t.interrupt()` não para `t`. Ele liga uma **marca** na thread, e o que acontece depende do que ela está fazendo:

- Se `t` está bloqueada em `sleep`, `join` ou `wait`, ela acorda com uma `InterruptedException`, e a marca é **desligada**
- Se `t` está rodando código comum, nada acontece de imediato; cabe a ela conferir a marca com `isInterrupted()` e decidir parar

```java executar
public class Interrupcao {
    public static void main(String[] args) throws InterruptedException {
        Thread laco = new Thread(() -> {
            long voltas = 0;
            while (!Thread.currentThread().isInterrupted()) {
                voltas++;
            }
            System.out.println("laço parou; marca = " + Thread.currentThread().isInterrupted());
        });
        laco.start();
        Thread.sleep(50);
        laco.interrupt();
        laco.join();

        Thread.currentThread().interrupt();
        System.out.println(Thread.interrupted() + " " + Thread.interrupted());

        Thread.currentThread().interrupt();
        try {
            Thread.sleep(10);
        } catch (InterruptedException e) {
            System.out.println("sleep com a marca ligada lança na hora; marca = " + Thread.currentThread().isInterrupted());
        }
    }
}
```

```saida
laço parou; marca = true
true false
sleep com a marca ligada lança na hora; marca = false
```

Repare na diferença entre os dois métodos de consulta: `t.isInterrupted()` só lê a marca, enquanto o estático `Thread.interrupted()` lê a marca da thread atual **e a desliga**. Por isso o segundo `interrupted()` deu `false`.

> [!ATENCAO]
> Engolir a `InterruptedException` com um `catch` vazio apaga o pedido de parada: a marca já foi desligada, e quem interrompeu nunca será atendido. Se não puder tratar, relance a exceção ou religue a marca com `Thread.currentThread().interrupt()`.

> [!PROVA]
> `sleep` é estático e afeta a thread atual. `sleep`, `join` e `wait` declaram `InterruptedException`, que é checked. `interrupt()` só liga uma marca; uma thread bloqueada acorda com exceção e tem a marca desligada. `isInterrupted()` só lê; `Thread.interrupted()` lê e desliga.

## Por que não existe "matar"

O Java 1.0 tinha `Thread.stop()`, que encerrava a thread à força, lançando um erro no ponto em que ela estivesse. O problema: a thread podia estar no meio de uma atualização, com um objeto meio alterado e travas soltas, e o programa seguia com dados corrompidos. O método foi depreciado no Java 1.2 e, desde o Java 20, só lança `UnsupportedOperationException`. A interrupção cooperativa existe porque só a própria thread sabe onde é seguro parar.

## Por baixo dos panos

Quando uma thread dorme ou espera, a JVM não a deixa girando num laço: ela pede ao sistema operacional que a tire da fila da CPU (`futex` no Linux, objetos de evento no Windows). A thread não consome processador até ser acordada pelo fim do prazo, pelo término da thread esperada ou por uma interrupção. A marca de interrupção é um campo da própria `Thread`; `interrupt()` liga esse campo e, se a thread estiver estacionada, a acorda. Os métodos bloqueantes conferem a marca ao começar e ao acordar, e é assim que um `sleep` chamado com a marca já ligada lança a exceção na hora.

O estado `BLOCKED`, que não apareceu nos exemplos, é exclusivo da espera por um monitor de `synchronized`. Uma thread em `lock()` de um `ReentrantLock`, por exemplo, aparece como `WAITING`, porque esses travamentos usam outro mecanismo, o `LockSupport.park`. A distinção aparece em *thread dumps* e é assunto da próxima temporada.

## Resumo para a prova

- Estados: `NEW`, `RUNNABLE`, `BLOCKED`, `WAITING`, `TIMED_WAITING`, `TERMINATED`; não existe `RUNNING`
- `sleep(ms)` é estático e não libera travas; `join()` espera a thread terminar; `join(ms)` com prazo
- `sleep`, `join` e `wait` lançam `InterruptedException` (checked)
- `interrupt()` liga a marca; em espera, a thread acorda com exceção e a marca é desligada
- `isInterrupted()` lê; `Thread.interrupted()` lê e desliga
- Não engula `InterruptedException`; relance ou religue a marca
