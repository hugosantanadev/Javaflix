Uma stream é uma sequência de elementos que passa por um **pipeline** de operações: uma fonte, zero ou mais operações intermediárias e uma operação terminal. Ela não guarda dados como uma coleção; descreve um cálculo sobre eles. Esta temporada cobre a API inteira, que é um dos maiores blocos da prova. Começamos por como criar uma stream e pelas operações do meio do caminho, que têm uma propriedade decisiva: são **preguiçosas**.

## Anatomia de um pipeline

```text
fonte          intermediárias              terminal
lista.stream() .filter(...).map(...)       .toList()
```

- A **fonte** fornece os elementos: uma coleção, um array, um gerador
- As **intermediárias** transformam a stream e devolvem outra stream: `filter`, `map`, `sorted`, `limit`
- A **terminal** produz o resultado e encerra a stream: `toList`, `count`, `forEach`, `reduce`

Três regras valem sempre. Nada acontece até a operação terminal. A fonte não é modificada: `map` não altera a lista original, cria valores novos. E uma stream só pode ser consumida **uma vez**: chamar uma segunda operação terminal lança `IllegalStateException: stream has already been operated upon or closed`.

## Criando streams

| Fonte | Exemplo |
|---|---|
| Coleção | `lista.stream()` |
| Valores soltos | `Stream.of("a", "b")`, `Stream.empty()`, `Stream.ofNullable(x)` |
| Array | `Arrays.stream(array)` ou `Arrays.stream(array, de, ate)` |
| Gerador infinito | `Stream.iterate(1, n -> n * 2)`, `Stream.generate(() -> "x")` |
| Gerador com fim (Java 9) | `Stream.iterate(1, n -> n < 20, n -> n * 3)` |
| Faixa de números | `IntStream.range(1, 4)` (exclui o 4), `IntStream.rangeClosed(1, 4)` (inclui) |
| Texto | `"abc".chars()`, um `IntStream` com os códigos |

```java executar
import java.util.Arrays;
import java.util.stream.Collectors;
import java.util.stream.IntStream;
import java.util.stream.Stream;

public class Fontes {
    public static void main(String[] args) {
        System.out.println(Stream.iterate(1, n -> n * 2).limit(5).toList());
        System.out.println(Stream.iterate(1, n -> n < 20, n -> n * 3).toList());
        System.out.println(Stream.generate(() -> "x").limit(3).collect(Collectors.joining()));
        System.out.println(IntStream.range(1, 4).boxed().toList() + " " + IntStream.rangeClosed(1, 4).sum());
        System.out.println(Arrays.stream(new int[] {3, 4, 5}, 1, 3).sum() + " " + Stream.ofNullable(null).count());
    }
}
```

```saida
[1, 2, 4, 8, 16]
[1, 3, 9]
xxx
[1, 2, 3] 10
9 0
```

`Stream.iterate` e `Stream.generate` sem limite produzem streams **infinitas**. Elas funcionam porque o `limit` e as operações de curto-circuito param a produção; sem eles, um `toList` ou um `sorted` nunca terminaria, e a prova adora perguntar o que um código assim imprime: nada, porque trava.

## As operações intermediárias

| Operação | O que faz | Observação |
|---|---|---|
| `filter(Predicate)` | Mantém quem passa no teste | |
| `map(Function)` | Transforma cada elemento | Pode mudar o tipo |
| `distinct()` | Remove repetidos, por `equals` | Guarda estado |
| `sorted()` / `sorted(Comparator)` | Ordena | Precisa ver todos os elementos |
| `limit(n)` / `skip(n)` | Corta o começo ou o resto | `limit` é de curto-circuito |
| `takeWhile` / `dropWhile` (Java 9) | Pega ou descarta enquanto a condição vale | Param no primeiro que falha |
| `peek(Consumer)` | Observa cada elemento sem mudá-lo | Para depuração |
| `mapMulti` (Java 16) | Emite zero ou mais valores por elemento | Alternativa ao `flatMap` |

```java executar
import java.util.Comparator;
import java.util.stream.Stream;

public class Intermediarias {
    public static void main(String[] args) {
        System.out.println(Stream.of(1, 2, 3, 4, 1, 2).distinct().skip(1).limit(2).toList());
        System.out.println(Stream.of(1, 2, 3, 10, 1).takeWhile(n -> n < 3).toList() + " " + Stream.of(1, 2, 3, 10, 1).dropWhile(n -> n < 3).toList());
        System.out.println(Stream.of("b", "C", "a").sorted().toList() + " " + Stream.of("b", "C", "a").sorted(Comparator.reverseOrder()).toList());
        System.out.println(Stream.of(1, 2, 3, 4).<String>mapMulti((n, saida) -> {
            if (n % 2 == 0) {
                saida.accept(n + "a");
                saida.accept(n + "b");
            }
        }).toList());
    }
}
```

```saida
[2, 3]
[1, 2] [3, 10, 1]
[C, a, b] [b, a, C]
[2a, 2b, 4a, 4b]
```

Repare em `takeWhile` e `dropWhile`: eles não filtram a stream inteira. `takeWhile(n -> n < 3)` para no 3 e ignora o 1 que vem depois; `dropWhile` descarta só até o primeiro elemento que falha e mantém o resto, inclusive o 1 final.

## Preguiça e a ordem real de execução

As intermediárias só **descrevem** o trabalho. Quando a terminal pede um elemento, ele percorre o pipeline inteiro antes do próximo começar, como numa linha de montagem. E se a terminal se satisfaz antes do fim, o resto nem é processado:

```java executar
import java.util.stream.Stream;

public class Preguica {
    public static void main(String[] args) {
        Stream<String> pipeline = Stream.of("um", "dois", "tres", "quatro")
            .filter(x -> {
                System.out.print("F:" + x + " ");
                return x.length() > 2;
            })
            .map(x -> {
                System.out.print("M:" + x + " ");
                return x.toUpperCase();
            });
        System.out.println("pipeline montado");
        System.out.println(pipeline.findFirst().get());

        Stream.of(3, 1, 2)
            .peek(x -> System.out.print("antes" + x + " "))
            .sorted()
            .forEach(x -> System.out.print("depois" + x + " "));
        System.out.println();
    }
}
```

```saida
pipeline montado
F:um F:dois M:dois DOIS
antes3 antes1 antes2 depois1 depois2 depois3 
```

Nada foi impresso antes de "pipeline montado". Depois, "um" foi filtrado e descartado, "dois" passou pelo filtro e pelo `map`, e o `findFirst` ficou satisfeito: "tres" e "quatro" nunca foram tocados. O `sorted` é diferente: ele é uma **barreira**, porque precisa ver todos os elementos antes de entregar o primeiro.

> [!PROVA]
> Sem operação terminal, nenhuma lambda do pipeline executa: um `peek` com `println` não imprime nada. Os elementos passam um de cada vez pelo pipeline inteiro, exceto nas operações que guardam estado, como `sorted`. E reutilizar uma stream lança `IllegalStateException`.

## Por baixo dos panos

Cada operação intermediária cria um novo estágio numa lista ligada de objetos, os *pipeline stages*, sem processar nada. A operação terminal percorre essa lista de trás para a frente e monta uma cadeia de `Sink`: objetos com um método `accept`, em que cada um faz o seu trabalho e repassa o resultado ao próximo. Então ela pede os elementos à fonte, por um `Spliterator`, e os empurra pela cadeia.

O pipeline também carrega **características** da fonte, como `SIZED` (o tamanho é conhecido) e `SORTED`. Elas permitem atalhos: desde o Java 9, `lista.stream().peek(...).count()` nem executa o `peek`, porque o tamanho já é conhecido e nada no pipeline pode mudá-lo. Com um `filter` no meio, o tamanho deixa de ser conhecido, e o pipeline executa. É uma das razões pelas quais a documentação desaconselha depender de efeitos colaterais em lambdas de streams.

## Resumo para a prova

- Pipeline: fonte, intermediárias (preguiçosas) e uma terminal, que dispara tudo
- A fonte não é alterada; a stream só pode ser consumida uma vez
- `iterate` e `generate` são infinitas sem `limit`; `range` exclui o fim, `rangeClosed` inclui
- `takeWhile` para no primeiro que falha; `dropWhile` descarta só o começo
- Os elementos passam um a um pelo pipeline; `sorted` e `distinct` guardam estado
- Operações de curto-circuito, como `findFirst` e `limit`, deixam elementos sem processar
