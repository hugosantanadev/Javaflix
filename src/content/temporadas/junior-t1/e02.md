No episódio anterior, os objetos nasciam vazios e os campos eram preenchidos depois, um por um. Isso deixa uma janela em que o objeto existe num estado sem sentido: uma conta sem titular, um produto sem preço. O **construtor** fecha essa janela: é o código que roda no momento do `new`, recebe os dados necessários e entrega o objeto já pronto para uso.

## Declarando um construtor

Um construtor tem o **mesmo nome da classe** e **nenhum tipo de retorno**, nem `void`:

```java executar
class Produto {
    String nome;
    double preco;

    Produto(String nome, double preco) {
        this.nome = nome;
        this.preco = preco;
    }
}

Produto p = new Produto("Caneta", 2.5);
System.out.println(p.nome + " " + p.preco);
```

```saida
Caneta 2.5
```

A regra do "nenhum tipo de retorno" é cobrada ao pé da letra. Com `void`, deixa de ser construtor e vira um método comum que, por acaso, tem o nome da classe. Compila, mas só roda quando chamado:

```java executar
class Sino {
    String som = "dim";

    void Sino() {
        som = "dom";
    }
}

Sino s = new Sino();
System.out.println(s.som);
s.Sino();
System.out.println(s.som);
```

```saida
dim
dom
```

## O construtor padrão

Se a classe não declara **nenhum** construtor, o compilador cria um: sem parâmetros, com o mesmo modificador de acesso da classe, que só chama o construtor da superclasse. É por isso que `new Conta()` funcionava no episódio anterior. Mas basta declarar um único construtor, com qualquer lista de parâmetros, para o padrão deixar de existir:

```java nao-compila
class Pedido {
    int numero;

    Pedido(int numero) {
        this.numero = numero;
    }
}

Pedido p = new Pedido();
```

Se a classe precisa das duas formas, declara-se o construtor sem parâmetros explicitamente.

## `this` para os campos

Quando o parâmetro tem o mesmo nome do campo, o parâmetro **esconde** o campo dentro do construtor (*shadowing*). O nome sozinho se refere ao parâmetro; o campo é `this.nome`, em que `this` é a referência para o objeto que está sendo construído. Esquecer o `this` compila e falha em silêncio:

```java executar
class Cliente {
    String nome;

    Cliente(String nome) {
        nome = nome;
    }
}

Cliente c = new Cliente("Bia");
System.out.println(c.nome);
```

```saida
null
```

`nome = nome` atribui o parâmetro a ele mesmo, e o campo continua com o valor padrão.

## Vários construtores e `this(...)`

Uma classe pode ter vários construtores, desde que as listas de parâmetros sejam diferentes (a mesma regra da sobrecarga de métodos, assunto da [próxima temporada](/assistir/junior-t2-e02)). Para não repetir código, um construtor pode chamar outro com `this(...)`:

```java executar
class Retangulo {
    int largura, altura;

    Retangulo() {
        this(1);
        System.out.println("sem argumentos");
    }

    Retangulo(int lado) {
        this(lado, lado);
        System.out.println("quadrado " + lado);
    }

    Retangulo(int largura, int altura) {
        this.largura = largura;
        this.altura = altura;
        System.out.println("completo " + largura + "x" + altura);
    }
}

Retangulo r = new Retangulo();
System.out.println(r.largura * r.altura);
```

```saida
completo 1x1
quadrado 1
sem argumentos
1
```

A ordem da saída mostra a pilha de chamadas: o construtor sem argumentos chama o de um, que chama o de dois. O mais interno termina primeiro, e cada um continua de onde parou.

Até o Java 21, `this(...)` precisa ser o **primeiro comando** do construtor. Qualquer coisa antes dele não compila:

```java nao-compila
class Hora {
    int h, m;

    Hora(int h) {
        System.out.println("criando");
        this(h, 0);
    }

    Hora(int h, int m) {
        this.h = h;
        this.m = m;
    }
}
```

E construtores que se chamam em ciclo também não compilam, porque nunca terminariam:

```java nao-compila
class Ciclo {
    Ciclo() {
        this(1);
    }

    Ciclo(int x) {
        this();
    }
}
```

> [!VERSAO]
> O Java 25 flexibilizou a regra (JEP 513, *Flexible Constructor Bodies*): agora podem vir comandos **antes** de `this(...)` ou `super(...)`, desde que não usem o objeto em construção, como validar os argumentos. Na prova 1Z0-829 e na 1Z0-830, a regra antiga continua valendo: a chamada vem primeiro.

```java compila java25
class Hora {
    int h, m;

    Hora(int minutos) {
        if (minutos < 0) throw new IllegalArgumentException("negativo");
        this(minutos / 60, minutos % 60);
    }

    Hora(int h, int m) {
        this.h = h;
        this.m = m;
    }
}
```

## `this` como valor

`this` é uma referência como outra qualquer: pode ser devolvida, passada como argumento ou comparada. Devolver `this` permite encadear chamadas, o estilo *fluente* que você já usou no `StringBuilder`:

```java executar
class Pedido {
    StringBuilder itens = new StringBuilder();
    int quantidade;

    Pedido adicionar(String item) {
        if (quantidade > 0) itens.append(", ");
        itens.append(item);
        quantidade++;
        return this;
    }
}

Pedido p = new Pedido().adicionar("café").adicionar("pão").adicionar("suco");
System.out.println(p.quantidade + ": " + p.itens);
```

```saida
3: café, pão, suco
```

`this` só existe dentro de código de instância: num método `static`, não há objeto, e usá-lo não compila. Esse é o assunto do [episódio 4](/assistir/junior-t1-e04).

## Por baixo dos panos

No bytecode, todo construtor vira um método especial chamado `<init>`, que devolve `void`. O `javap -c` mostra que o construtor padrão gerado pelo compilador tem só duas instruções úteis: carregar `this` e chamar o `<init>` da superclasse. E os inicializadores de campo, como o `= new StringBuilder()` do `Pedido`, não ficam num lugar separado: o compilador **copia** esse código para o começo de cada construtor, logo depois da chamada ao `super`. Construtores que começam com `this(...)` não recebem a cópia, porque o construtor chamado já vai fazê-lo. É por isso que a ordem de inicialização, assunto do [episódio 5](/assistir/junior-t1-e05), é tão previsível.

A JVM também garante que nenhum código use um objeto antes de o `<init>` da classe `Object` ter rodado: o verificador de bytecode rejeita qualquer classe que tente. A regra do "`this(...)` primeiro" era uma forma conservadora de garantir isso no código-fonte; o Java 25 trocou-a por uma análise mais precisa, que só proíbe o que de fato usaria o objeto incompleto.

## Resumo para a prova

- Construtor: mesmo nome da classe, sem tipo de retorno; com `void`, é um método
- O construtor padrão só existe se a classe não declarar nenhum
- O construtor padrão não tem parâmetros e tem o acesso da classe
- Parâmetro com o nome do campo o esconde: use `this.campo`
- `nome = nome` compila e não altera o campo
- `this(...)` chama outro construtor; até o Java 21, tem de ser o primeiro comando
- Construtores que se chamam em ciclo não compilam
- `this` não existe em contexto `static`
