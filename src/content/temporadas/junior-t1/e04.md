Até agora, cada objeto tinha os seus próprios campos. Mas algumas informações pertencem à **classe**, não a um objeto: quantas contas já foram abertas, a taxa de juros que vale para todas, uma função de cálculo que não depende de estado nenhum. Para isso existe o modificador `static`. Um membro `static` existe uma única vez, ligado à classe, e é compartilhado por todos os objetos dela, mesmo que nenhum objeto tenha sido criado.

## Campos `static`

```java executar
public class Placar {
    static int total; //> Um só, guardado na classe.
    int pontos; //> Um por objeto.

    void marcar() {
        total++;
        pontos++;
    }

    public static void main(String[] args) {
        Placar a = new Placar();
        Placar b = new Placar();
        a.marcar();
        a.marcar();
        b.marcar();
        System.out.println(a.pontos + " " + b.pontos + " " + total + " " + Placar.total);
    }
}
```

```saida
2 1 3 3
```

Cada placar tem os seus `pontos`, mas só existe um `total`, que os três `marcar()` incrementam. Fora da classe, o jeito correto de acessá-lo é pelo nome dela: `Placar.total`. Dentro da classe, o nome sozinho basta.

![A classe Placar guarda um único static total igual a 3; os objetos apontados por a e b guardam os próprios pontos, 2 e 1, e os dois apontam para a mesma classe](/figuras/static-e-instancia.svg "O campo static mora na classe, e existe mesmo sem nenhum objeto. Os de instância moram em cada objeto.")

> [!CONVERSA]
> **Campo de instância:** Cada objeto tem o seu exemplar de mim. Mil contas, mil saldos.
>
> **Campo static:** E de mim só existe um, na classe. Mil contas, uma taxa de juros.
>
> **Campo de instância:** Eu nasço com o objeto e vou embora com ele.
>
> **Campo static:** Eu nasço quando a classe é carregada e fico enquanto ela estiver na memória. Até sem nenhum objeto.
>
> **Campo de instância:** Então quem guardar o nome do cliente em você...
>
> **Campo static:** ...vai ver todos os clientes com o nome do último cadastrado. Nome é com você.

Java também aceita acessar um membro `static` por uma referência, como `a.total`. Funciona, mas engana: o compilador olha só o **tipo** da variável e troca a expressão por `Placar.total`. O objeto nem é consultado, e por isso nem uma referência nula causa problema.

> [!PENSE]
> No programa abaixo, `c` é `null`, e a linha seguinte faz `c.modo`. Pela regra do episódio anterior, deveria lançar `NullPointerException`. Vai?

```java executar
public class Config {
    static String modo = "produção";

    public static void main(String[] args) {
        Config c = null;
        System.out.println(c.modo); //> Vira Config.modo na compilação: o null nem é consultado.
        Config.modo = "teste";
        System.out.println(modo);
    }
}
```

```saida
produção
teste
```

## Métodos `static`

Um método `static` pertence à classe e é chamado sem objeto, como `Math.max(2, 3)` ou o próprio `main`. Como não há objeto, **não há `this`**, e o método não pode usar diretamente nenhum campo ou método de instância:

```java nao-compila
public class Contador {
    int valor;

    public static void main(String[] args) {
        valor = 10;
    }
}
```

O erro diz *non-static variable valor cannot be referenced from a static context*: de qual contador seria esse `valor`? A solução é criar um objeto e acessar por ele, `new Contador().valor = 10`. O caminho inverso é livre: métodos de instância podem usar membros `static` à vontade, porque eles existem sempre.

| De onde | Membros `static` | Membros de instância |
|---|---|---|
| Método de instância | sim, direto | sim, direto |
| Método `static` | sim, direto | só por meio de uma referência |

> [!LAPIS]
> Qual é a saída?
>
> ```java
> class Ingresso {
>     static int vendidos;
>     int numero;
>     Ingresso() { numero = ++vendidos; }
> }
>
> Ingresso x = new Ingresso();
> Ingresso y = new Ingresso();
> Ingresso z = y;
> new Ingresso();
> System.out.println(x.numero + " " + z.numero + " " + Ingresso.vendidos);
> ```
>
> **Resposta:** `1 2 3`. São três `new`, e cada construtor incrementa o mesmo `vendidos` antes de copiá-lo para o próprio `numero`. `z` não cria nada: aponta para o ingresso de `y`, o segundo. O terceiro ingresso foi criado sem variável nenhuma, mas contou do mesmo jeito.

> [!ERRO]
> Declarar como `static` um dado que é de cada objeto: `static String nome;` numa classe `Cliente`. Compila, e o primeiro teste passa, porque só há um cliente. Com dois, o segundo sobrescreve o nome do primeiro, e todos passam a ter o nome do último. Só é `static` o que é da classe inteira.

## Constantes e classes utilitárias

Um campo `static final` é uma **constante**: um valor só, que não muda. A convenção é escrevê-lo em maiúsculas, com sublinhados. Atribuir de novo a uma constante não compila. Classes que só têm membros `static`, como `Math` e `Arrays`, costumam ter um construtor `private`, para que ninguém crie objetos inúteis delas:

```java executar
class Conversor {
    static final double POLEGADA_EM_CM = 2.54;

    private Conversor() {
    }

    static double paraCm(double polegadas) {
        return polegadas * POLEGADA_EM_CM;
    }
}

public class Tela {
    public static void main(String[] args) {
        System.out.println(Conversor.paraCm(2) + " " + Conversor.POLEGADA_EM_CM);
    }
}
```

```saida
5.08 2.54
```

> [!ANTES]
> Em C, um dado compartilhado pelo programa inteiro é uma variável **global**, declarada fora de qualquer função e acessível de qualquer lugar. O Java, de 1995, não tem variáveis globais: tudo pertence a alguma classe. O campo `static` é o substituto, com nome e acesso controlados pela classe. A palavra `static` veio do C, em que já significava "existe durante o programa todo, não só durante a chamada".

> [!MATEMATICA]
> Quanto custa cada escolha? Um campo `double` de instância ocupa 8 bytes em **cada** objeto: com um milhão de contas, 1.000.000 × 8 = 8.000.000 bytes, cerca de **8 MB**, só para guardar a mesma taxa de juros repetida. Como `static`, são 8 bytes no total, uma vez só. A diferença vai além da memória: mudar a taxa como `static` é uma atribuição; como campo de instância, um milhão de atribuições.

## `import static`

O `import static` traz membros `static` de outra classe para serem usados sem o nome dela. Pode importar um membro específico ou todos, com `*`:

```java executar
import static java.lang.Math.max;
import static java.lang.Math.PI;

public class Circulo {
    public static void main(String[] args) {
        double raio = max(2, 3);
        System.out.println(Math.round(PI * raio * raio));
    }
}
```

```saida
28
```

A ordem das palavras é cobrada: é `import static`, nunca `static import`. E um `import` comum não importa métodos nem campos, só tipos:

```java nao-compila
static import java.lang.Math.max;

public class Errado {
    public static void main(String[] args) {
        System.out.println(max(1, 2));
    }
}
```

> [!PROVA]
> Três detalhes que a prova adora. Um `import static java.lang.Math.max;` importa **todas** as versões de `max`, porque o import é por nome, sem parâmetros. Se a classe declarar um método com o mesmo nome, o da classe tem prioridade. E importar o mesmo nome estático de duas classes diferentes só dá erro quando o nome é **usado**, por ambiguidade.

> [!IA]
> A IA costuma usar `static` com cuidado em código novo, mas, para "facilitar o acesso", às vezes transforma em `static` campos que deveriam ser de cada objeto, ou cria uma lista `static` como cache que nunca é limpo. Ao revisar o que ela gerou, pergunte de cada campo `static`: é um só para a aplicação inteira?

## Na IDE

- **Acesso pela referência.** O IntelliJ marca `c.modo` com "Static member 'Config.modo' accessed via instance reference" e troca por `Config.modo` com **Alt + Enter**.
- **Método que poderia ser `static`.** Um método que não usa nada da instância recebe a sugestão "Method can be 'static'".
- **Classe utilitária.** Uma classe só com membros `static` e sem construtor `private` recebe o aviso "Utility class without 'private' constructor".

## Por baixo dos panos

Os campos `static` ficam guardados junto da classe, não dos objetos. Na HotSpot, desde o Java 8, eles moram no objeto `Class` que representa a classe no heap (o *espelho* da classe), enquanto os metadados, como o bytecode dos métodos, ficam no *Metaspace*, uma área de memória fora do heap. Como o objeto `Class` é uma raiz do [coletor de lixo](/assistir/junior-t1-e03) enquanto a classe estiver carregada, tudo o que um campo `static` aponta continua vivo: uma lista `static` que só cresce é uma das causas mais comuns de vazamento de memória em Java.

No bytecode, a chamada a um método `static` usa a instrução `invokestatic`, que não recebe objeto nenhum, e o método a chamar é decidido na compilação, pelo tipo declarado. Métodos de instância usam `invokevirtual`, que escolhe o método em tempo de execução, pela classe real do objeto. Essa diferença é a raiz de um tema da temporada de herança: métodos `static` não são sobrescritos, só **escondidos**. Os campos `static` são lidos com `getstatic`, e a primeira execução de um `getstatic` ou `invokestatic` numa classe ainda não inicializada dispara a inicialização dela, assunto do [próximo episódio](/assistir/junior-t1-e05).

## Resumo para a prova

- Membro `static` existe uma vez por classe, compartilhado por todos os objetos
- Acesse pelo nome da classe; pela referência funciona, até com `null`, porque só o tipo importa
- Métodos `static` não têm `this` e não acessam membros de instância sem uma referência
- Métodos de instância acessam membros `static` livremente
- `static final` é constante: não pode receber outro valor
- `import static` importa membros `static`; `static import` não compila
- `import` comum só importa tipos, não métodos nem campos
