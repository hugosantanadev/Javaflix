Até aqui, você usou objetos prontos: `String`, `StringBuilder`, arrays. Agora é hora de criar os seus. Uma **classe** é o molde: diz quais dados cada objeto guarda (os **campos**) e o que ele sabe fazer (os **métodos**). Um **objeto** é uma instância concreta desse molde, criada com `new`, com os próprios valores. E a variável que "guarda" um objeto, na verdade, guarda só o endereço dele: uma **referência**. Quase toda questão de orientação a objetos da prova depende de entender essa última frase.

## Classe e objeto

```java executar
class Conta {
    String titular;
    double saldo;
    boolean ativa;

    void depositar(double valor) {
        saldo += valor; //> O saldo do objeto em que o método foi chamado.
    }
}

Conta a = new Conta();
a.titular = "Ana";
a.depositar(150.0);
Conta b = new Conta(); //> Outro objeto: campos próprios, com os valores padrão.
System.out.println(a.titular + " " + a.saldo + " " + a.ativa);
System.out.println(b.titular + " " + b.saldo + " " + b.ativa);
```

```saida
Ana 150.0 false
null 0.0 false
```

Cada `new Conta()` cria um objeto separado, com o seu próprio `titular`, `saldo` e `ativa`. O operador ponto acessa os membros de um objeto específico: `a.depositar(150.0)` mexe só no saldo de `a`. Dentro do método, `saldo` se refere ao campo do objeto em que o método foi chamado.

> [!ANTES]
> Classes e objetos nasceram no Simula 67, uma linguagem norueguesa de 1967 feita para simulações: cada navio de um porto simulado era um objeto. O Smalltalk, nos anos 1970, levou a ideia ao extremo, e o C++, nos anos 1980, a levou para a indústria, mas com gerenciamento de memória manual. O Java, de 1995, juntou as classes do C++ com a coleta de lixo do Smalltalk: ninguém libera objetos à mão.

## Campos têm valor padrão; variáveis locais, não

Repare no objeto `b`: ninguém atribuiu nada, e mesmo assim os campos têm valores. Campos recebem o **valor padrão** do tipo assim que o objeto é criado, os mesmos das posições de [array](/assistir/estagiario-t6-e01): `0`, `0.0`, `false`, o caractere 0 ou `null`.

Variáveis **locais** (declaradas dentro de métodos) não recebem valor nenhum. Lê-las antes de atribuir é erro de compilação, como você viu no episódio de [variáveis](/assistir/estagiario-t1-e04):

```java nao-compila
int total;
System.out.println(total);
```

> [!PROVA]
> A pergunta "isso compila?" muitas vezes depende de onde a variável foi declarada. Um campo `int contador;` lido sem atribuição vale 0. Uma variável local `int contador;` lida sem atribuição não compila. E o compilador analisa os caminhos: se algum `if` puder pular a atribuição, também não compila.

## A variável guarda uma referência

`Conta a = new Conta();` faz três coisas: declara uma variável do tipo `Conta`, cria um objeto no heap e guarda na variável a **referência** para ele. Atribuir uma variável a outra copia a referência, não o objeto.

> [!PENSE]
> No trecho abaixo, `p2` recebe `p1` e muda o `y`. Depois, `p3` é criado com os mesmos valores. Quantos objetos `Ponto` existem? E quais pares são "iguais" pelo `==`?

```java executar
class Ponto {
    int x, y;
}

Ponto p1 = new Ponto();
p1.x = 3;
Ponto p2 = p1; //> Copia a referência: um objeto, dois nomes.
p2.y = 7;
Ponto p3 = new Ponto();
p3.x = 3;
p3.y = 7;
System.out.println(p1.x + "," + p1.y + " " + (p1 == p2) + " " + (p1 == p3));
p2 = null; //> Apaga a referência guardada em p2, não o objeto.
System.out.println(p1.x + "," + p1.y);
```

```saida
3,7 true false
3,7
```

`p1` e `p2` apontam para o mesmo objeto: mudar por um dos nomes muda o que o outro enxerga. `p3` tem os mesmos valores, mas é outro objeto, e `==` entre referências pergunta "é o **mesmo** objeto?", exatamente como com [strings](/assistir/estagiario-t5-e05). Fazer `p2 = null` apaga a referência guardada em `p2`, não o objeto: `p1` continua apontando para ele.

![Na pilha do método main, as variáveis p1, p2 e p3; no heap, dois objetos Ponto com x 3 e y 7; as setas de p1 e p2 chegam ao mesmo objeto, e a de p3, ao outro](/figuras/pilha-e-heap.svg "As variáveis guardam setas. O == compara as setas; os valores dentro dos objetos não entram na conta.")

> [!LAPIS]
> Qual é a saída? E qual objeto fica sem nenhuma referência?
>
> ```java
> class Caixa { int v; }
>
> Caixa a = new Caixa();
> Caixa b = new Caixa();
> a.v = 1;
> b.v = 2;
> a = b;
> b.v = 3;
> System.out.println(a.v);
> ```
>
> **Resposta:** `3`. Depois de `a = b`, as duas variáveis apontam para o segundo objeto, e mudar `b.v` muda o que `a` enxerga. O primeiro objeto, o do `v = 1`, ficou sem nenhuma referência: ninguém mais consegue chegar nele, e o coletor de lixo pode apagá-lo.

## `null` e a `NullPointerException`

Uma variável de referência pode não apontar para nada: `null`. Ler um campo ou chamar um método por uma referência nula lança `NullPointerException`. O caso mais comum é um campo de tipo objeto que ninguém inicializou:

```java executar
class Pessoa {
    String nome;
    int idade;
}

Pessoa p = new Pessoa();
System.out.println(p.idade + " " + p.nome);
try {
    System.out.println(p.nome.length());
} catch (NullPointerException e) {
    System.out.println("NullPointerException");
}
```

```saida
0 null
NullPointerException
```

Imprimir `null` não é problema: a concatenação o transforma no texto "null". O erro só aparece quando se tenta **usar** o objeto que não existe. Desde o Java 14, a mensagem da exceção diz exatamente qual referência era nula, o que facilita muito a depuração.

> [!ERRO]
> Declarar um campo de tipo objeto e usá-lo sem inicializar: `List<String> itens;` num campo e, num método, `itens.add("x")`. O campo vale `null`, e o `add` lança `NullPointerException`. Inicialize na declaração (`List<String> itens = new ArrayList<>();`) ou no construtor.

> [!PERGUNTAS]
> **P:** Cada objeto guarda uma cópia dos métodos?
>
> **R:** Não. O código dos métodos fica uma vez só, na classe. Cada objeto guarda apenas os próprios campos e um ponteiro para a classe, e é por esse ponteiro que a JVM acha o método certo.
>
> **P:** Quem apaga os objetos que ninguém usa?
>
> **R:** O coletor de lixo. Quando nenhuma referência alcança um objeto, a memória dele pode ser reaproveitada. Não existe `delete` em Java.
>
> **P:** Então referência é ponteiro?
>
> **R:** Quase: é um endereço, mas sem aritmética. Não dá para somar a ele nem ler a memória vizinha, e é isso que deixa a JVM mover objetos de lugar.
>
> **P:** E para comparar dois objetos pelo conteúdo?
>
> **R:** O `equals` herdado de `Object` faz o mesmo que o `==`. Para comparar conteúdo, a classe precisa sobrescrever o `equals`, assunto de um episódio deste cargo.

## Membros de uma classe

Uma classe pode declarar, em qualquer ordem:

| Membro | Exemplo |
|---|---|
| Campos | `double saldo;` |
| Métodos | `void depositar(double v) { ... }` |
| Construtores | `Conta(String titular) { ... }` |
| Blocos de inicialização | `{ ... }` e `static { ... }` |
| Tipos aninhados | `class Extrato { ... }` |

Construtores são o assunto do [próximo episódio](/assistir/junior-t1-e02), e os blocos de inicialização, do [quinto](/assistir/junior-t1-e05). Sem nenhum `toString` próprio, imprimir um objeto mostra o nome da classe, um `@` e um número em hexadecimal, como `Conta@1b6d3586`, o mesmo formato que você viu nos arrays.

> [!IA]
> Ao gerar classes, a IA costuma deixar campos de coleção sem inicializar ou inicializá-los só em um dos construtores. Também é comum ela explicar o `==` entre objetos como "compara os valores". Peça que ela liste quais campos podem estar `null` depois de cada construtor, e confira rodando com um objeto recém-criado.

## Na IDE

- **Ver o objeto.** No depurador, cada objeto aparece como `{Ponto@812}`; duas variáveis com o mesmo número apontam para o mesmo objeto.
- **Avisos de `null`.** O IntelliJ analisa os caminhos e marca "Method invocation 'length' may produce 'NullPointerException'" quando uma referência pode estar vazia.
- **Gerar código.** **Alt + Insert** dentro da classe gera construtores, getters, `toString` e `equals` a partir dos campos.

## Por baixo dos panos

`new Conta()` vira três instruções de bytecode: `new` reserva a memória e zera os campos (é daí que vêm os valores padrão), `dup` duplica a referência na pilha, e `invokespecial` chama o construtor `<init>`. Reservar memória é barato: cada thread tem um pedaço do heap só dela, a *TLAB*, e alocar é só avançar um ponteiro, sem trava nenhuma. Por isso criar objetos pequenos em Java custa poucos nanossegundos.

Na memória, cada objeto começa com um **cabeçalho**: uma palavra com dados de controle (o hash de identidade, o estado de trava e a idade para o coletor de lixo) e um ponteiro para a classe, que é como a JVM sabe de que tipo o objeto é. Na HotSpot, com as opções padrão, o cabeçalho ocupa 12 bytes, e o tamanho total é arredondado para múltiplos de 8. Um `Ponto` com dois `int` ocupa 12 + 4 + 4 = 20, arredondados para 24 bytes. O Java 25 oficializou os cabeçalhos compactos (JEP 519), de 8 bytes, ativados com `-XX:+UseCompactObjectHeaders`.

> [!MATEMATICA]
> A mesma conta vale para qualquer classe: cabeçalho de 12 bytes, mais os campos, arredondado para múltiplo de 8. A `Conta` do começo tem uma referência (`titular`, 4 bytes com referências comprimidas), um `double` (8) e um `boolean` (1): 12 + 4 + 8 + 1 = 25, arredondados para **32**. Um milhão de contas ocupam 32 MB só nos objetos `Conta`, fora as `String` dos titulares. Trocar o `boolean` por outro campo de 1 byte não muda nada: ainda cabe nos 32.

Já a referência guardada na variável é como um ponteiro do [C](/assistir/aprendiz-t2-e02), mas sem aritmética: não dá para somar 4 a ela nem ler a memória vizinha. É essa restrição que permite à JVM mover objetos de lugar durante a coleta de lixo e atualizar as referências sem que o programa perceba.

## Resumo para a prova

- Classe é o molde; cada `new` cria um objeto independente
- Campos recebem valor padrão; variáveis locais precisam ser atribuídas antes de lidas
- A variável guarda uma referência; atribuir copia a referência, não o objeto
- `==` entre objetos compara identidade, não conteúdo
- `null` não aponta para nada; usar um membro dele lança `NullPointerException`
- Concatenar ou imprimir `null` funciona e dá "null"
- Atribuir `null` a uma variável não apaga o objeto, só aquela referência
