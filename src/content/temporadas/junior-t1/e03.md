Em C, quem reserva memória com `malloc` precisa devolvê-la com `free`, no momento certo: cedo demais, o programa lê lixo; tarde demais ou nunca, a memória vaza. Java não tem `free`. Quem decide quando um objeto pode ser destruído é o **coletor de lixo** (*garbage collector*, ou GC). O programador não controla esse momento, mas a prova exige que você saiba exatamente **quando um objeto passa a poder ser coletado**.

## Pilha e heap

Cada chamada de método ganha um *quadro* na **pilha** (*stack*) da thread, com os parâmetros e as variáveis locais. Os objetos moram no **heap**, uma área compartilhada. Uma variável local de tipo objeto fica na pilha, mas guarda só a referência para o objeto no heap:

```text
 PILHA (main)                HEAP
 ┌───────────────┐
 │ a  ──────────────────▶  [Caixa "B"]
 │ b   null      │
 │ c  ──────────────────▶  [Caixa "C"]
 └───────────────┘          [Caixa "A"]   ← ninguém aponta: elegível
```

Quando o método termina, o quadro some, e com ele as variáveis locais. Os objetos continuam no heap até o GC recolhê-los.

## Quando um objeto fica elegível

Um objeto pode ser coletado quando **nenhuma referência alcançável** aponta mais para ele. A frase que a prova usa é "elegível para a coleta de lixo" (*eligible for garbage collection*). Há três formas comuns de isso acontecer: a variável recebe `null`, a variável passa a apontar para outro objeto, ou a variável deixa de existir, porque o bloco ou o método terminou.

```java executar
class Caixa {
    String nome;

    Caixa(String nome) {
        this.nome = nome;
    }
}

Caixa a = new Caixa("A");
Caixa b = new Caixa("B");
Caixa c = a;
a = b;
b = null;
System.out.println(a.nome + " " + c.nome);
c = new Caixa("C");
System.out.println(a.nome + " " + c.nome);
```

```saida
B A
B C
```

Para responder questões assim, desenhe as setas a cada linha. Depois de `b = null`, a caixa "B" ainda é apontada por `a`, e a caixa "A" ainda é apontada por `c`: nenhuma é elegível. Só quando `c` passa a apontar para a caixa "C" a caixa "A" fica sem nenhuma referência. É o desenho acima.

Variáveis criadas dentro de um bloco deixam de existir no fim dele, e os objetos que só elas apontavam ficam elegíveis. Fora do bloco, o nome nem existe mais:

```java nao-compila
for (int i = 0; i < 3; i++) {
    StringBuilder sb = new StringBuilder("volta " + i);
}
System.out.println(sb);
```

> [!PROVA]
> "Elegível" não quer dizer "coletado". A prova pergunta quando um objeto **pode** ser coletado, nunca quando ele **será**. O GC roda quando a JVM decide, e pode nunca rodar num programa curto. `System.gc()` é só uma **sugestão**: a JVM pode ignorá-la, e nenhuma questão pode garantir que ela coletou algo.

## Ilhas de objetos

O que importa é ser **alcançável** a partir do programa, não ter alguma referência. Dois objetos que apontam um para o outro, mas que ninguém de fora alcança, formam uma *ilha de isolamento* e são elegíveis:

```java executar
class No {
    No outro;
}

No x = new No();
No y = new No();
x.outro = y;
y.outro = x;
System.out.println(x.outro.outro == x);
x = null;
y = null;
System.out.println("os dois nós estão inalcançáveis");
```

```saida
true
os dois nós estão inalcançáveis
```

Cada nó ainda tem uma referência apontando para ele, a do outro nó, mas nenhuma variável do programa chega até eles. Os dois são elegíveis.

## `finalize`, `System.gc()` e a forma certa de liberar recursos

Toda classe herda de `Object` um método `finalize()`, que o GC **poderia** chamar antes de destruir o objeto. Ele nunca foi confiável: pode rodar muito tarde, em qualquer thread, ou simplesmente não rodar. Ficou obsoleto no Java 9 e está marcado para remoção desde o Java 18 (JEP 421). Na prova, a resposta certa sobre `finalize` é sempre "não há garantia de que ele seja chamado".

```java executar
for (int i = 0; i < 100_000; i++) {
    new StringBuilder("temporário " + i);
}
System.gc();
System.out.println("o programa segue, com ou sem coleta");
```

```saida
o programa segue, com ou sem coleta
```

Memória, o GC resolve. Mas arquivos, conexões e *sockets* são recursos do sistema operacional, limitados, que precisam ser fechados **na hora certa**, não quando o GC quiser. Para isso existe o `try` com recursos: tudo o que for declarado entre os parênteses, desde que implemente `AutoCloseable`, é fechado no fim do bloco, mesmo se houver exceção. Com vários recursos, separados por ponto e vírgula, eles são fechados na ordem **inversa** da abertura. Você o verá em detalhes na temporada de exceções:

```java executar
class Conexao implements AutoCloseable {
    String nome;

    Conexao(String nome) {
        this.nome = nome;
        System.out.println("abrindo " + nome);
    }

    public void close() {
        System.out.println("fechando " + nome);
    }
}

try (Conexao c = new Conexao("banco")) {
    System.out.println("usando " + c.nome);
}
System.out.println("depois do try");
```

```saida
abrindo banco
usando banco
fechando banco
depois do try
```

## Por baixo dos panos

O GC não procura o lixo: procura o que está **vivo**. Ele parte das *raízes* (as variáveis locais de todos os quadros de todas as threads, os campos `static` das classes carregadas e algumas referências internas da JVM), segue cada referência e marca tudo o que alcança. O que sobrou sem marca é lixo. É por isso que ilhas são coletadas: elas não são alcançadas a partir de nenhuma raiz. Contar referências, a técnica do Python e do Swift, não basta sozinha justamente por causa dos ciclos.

A HotSpot aposta na **hipótese geracional**: a maioria dos objetos morre jovem. Os objetos nascem na geração jovem (o *Eden*, onde fica a [TLAB](/assistir/junior-t1-e01) de cada thread), e uma coleta rápida copia os poucos sobreviventes para outra área, liberando o resto de uma vez, sem olhar o lixo um a um. Quem sobrevive a várias coletas é promovido à geração velha, coletada com menos frequência. Desde o Java 9, o coletor padrão é o **G1**, que divide o heap em regiões e tenta manter as pausas abaixo de uma meta, 200 ms por padrão. Para pausas menores que 1 ms, existem o ZGC, geracional desde o Java 21, e o Shenandoah, que fazem quase todo o trabalho enquanto o programa roda.

Durante parte da coleta, as threads do programa param (*stop-the-world*). Por isso, criar milhões de objetos temporários tem um custo que vai além da alocação, e boa parte da otimização de sistemas Java de baixa latência é sobre reduzir a pressão no GC.

## Resumo para a prova

- Objetos ficam no heap; variáveis locais e parâmetros, na pilha
- Elegível = nenhuma referência alcançável; acontece com `null`, reatribuição ou fim do escopo
- Desenhe as referências linha a linha para contar os objetos elegíveis
- Ilhas de objetos que só apontam uns para os outros são elegíveis
- Elegível não é coletado: o GC roda quando a JVM decide
- `System.gc()` é só uma sugestão
- `finalize()` está obsoleto e pode nunca ser chamado
- Recursos como arquivos e conexões se fecham com `try` com recursos, não com o GC
