Uma classe bem escrita esconde os detalhes e expõe só o necessário. Os **modificadores de acesso** dizem quem pode ver cada membro, e o **pacote** é a fronteira que define o que é "de dentro" e o que é "de fora". São quatro níveis, e a prova cobra cada um, especialmente o `protected`, o mais mal compreendido de todos.

## Os quatro níveis

| Modificador | Mesma classe | Mesmo pacote | Subclasse em outro pacote | Qualquer lugar |
|---|---|---|---|---|
| `private` | sim | não | não | não |
| nenhum (*package-private*) | sim | sim | não | não |
| `protected` | sim | sim | sim, com uma condição | não |
| `public` | sim | sim | sim | sim |

Cada nível inclui o anterior: do mais fechado ao mais aberto, `private`, nenhum, `protected`, `public`. Quando não há modificador, o acesso é de pacote. Não existe uma palavra para isso: `default` é outra coisa, usada em interfaces, e escrito num campo não compila:

```java nao-compila
class Errado {
    default int valor = 1;
}
```

> [!ANTES]
> O C++ tem `public`, `protected` e `private`, e uma quarta saída: declarar uma classe ou função como `friend`, o que lhe dá acesso a tudo. O Java, de 1995, não copiou o `friend`. No lugar dele, criou o acesso de **pacote**: classes que trabalham juntas ficam no mesmo pacote e se enxergam, sem precisar abrir nada para o resto do programa.

## `private` é por classe, não por objeto

Um membro `private` só é visível dentro da classe que o declara. Mas a regra é sobre o **código**, não sobre o objeto: um método da classe `Conta` pode ler o campo `private` de **outra** conta.

> [!PENSE]
> No exemplo abaixo, `a.temMaisQue(b)` lê o `saldo` de `b`, que é `private`. Um objeto pode mexer no `private` de outro?

```java executar
public class Conta {
    private double saldo;

    Conta(double saldo) {
        this.saldo = saldo;
    }

    boolean temMaisQue(Conta outra) {
        return saldo > outra.saldo; //> Outro objeto, mesma classe: o private continua visível.
    }

    public static void main(String[] args) {
        Conta a = new Conta(100);
        Conta b = new Conta(50);
        System.out.println(a.temMaisQue(b) + " " + a.saldo);
    }
}
```

```saida
true 100.0
```

O `main` também está dentro de `Conta`, então lê `a.saldo` sem problema. De outra classe, mesmo no mesmo arquivo, não compila:

```java nao-compila
class Cofre {
    private int segredo = 42;
}

public class Ladrao {
    public static void main(String[] args) {
        Cofre c = new Cofre();
        System.out.println(c.segredo);
    }
}
```

## Acesso de pacote e `protected` no mesmo pacote

Classes no mesmo arquivo estão no mesmo pacote. Ali, membros sem modificador e `protected` são visíveis livremente:

```java executar
class Catalogo {
    int itens = 3;
    protected String nome = "Verão";
    private String codigo = "V25"; //> Só o código da própria Catalogo enxerga.

    String resumo() {
        return nome + " (" + codigo + "): " + itens;
    }
}

public class Vitrine {
    public static void main(String[] args) {
        Catalogo c = new Catalogo();
        c.itens++;
        System.out.println(c.nome + " " + c.itens);
        System.out.println(c.resumo());
    }
}
```

```saida
Verão 4
Verão (V25): 4
```

`Vitrine` não vê `codigo`, mas o método `resumo`, que é da própria `Catalogo`, vê. É o padrão do encapsulamento: o campo fica escondido e um método controla o que sai.

> [!PERGUNTAS]
> **P:** Por que não deixar tudo `public` e evitar dor de cabeça?
>
> **R:** Porque tudo o que é `public` vira compromisso: qualquer classe pode passar a depender daquilo, e mudar depois quebra quem usa. O que é `private` pode ser trocado à vontade, desde que os métodos públicos continuem iguais.
>
> **P:** Todo campo `private` precisa de um *getter* e um *setter*?
>
> **R:** Não. Um *setter* para tudo é quase o mesmo que um campo `public`. Exponha só o que quem usa precisa, e com regras: um `depositar(valor)` que recusa negativos é melhor que um `setSaldo`.
>
> **P:** `protected` é mais fechado que o acesso de pacote?
>
> **R:** É mais aberto: inclui o pacote inteiro e ainda as subclasses de fora.

> [!ENGENHARIA]
> Siga o **princípio do menor privilégio**: declare cada membro com o acesso mais restrito que funcione, começando por `private`, e abra só quando houver um motivo. Campos, quase sempre `private`; métodos auxiliares, `private` ou de pacote; `public` só para o que é, de fato, a interface da classe.

> [!MATEMATICA]
> O acesso define quantas classes podem passar a depender de um membro. Numa aplicação com 20 pacotes de 15 classes, um membro `private` pode ser usado por **1** classe; um de pacote, por até **15**; um `public`, por até 20 × 15 = **300**. Para renomear o campo, você confere 1, 15 ou 300 classes. Por isso fechar o acesso deixa o código mais fácil de mudar.

## `protected` fora do pacote

Fora do pacote, `protected` libera o acesso só para **subclasses** (classes que estendem a outra com `extends`, assunto da [temporada 3](/assistir/junior-t3-e01)). E com uma condição que derruba muita gente: a subclasse acessa o membro pela herança, isto é, por `this` ou por referências do **próprio tipo dela**. Por uma referência do tipo da superclasse, não compila:

```java
// arquivo animais/Animal.java
package animais;

public class Animal {
    protected String som = "...";
    String habitat = "terra";   // sem modificador: só no pacote animais
}

// arquivo zoo/Cachorro.java
package zoo;

import animais.Animal;

public class Cachorro extends Animal {
    void testar(Animal outro, Cachorro irmao) {
        System.out.println(som);          // compila: herdado
        System.out.println(this.som);     // compila
        System.out.println(irmao.som);    // compila: referência do tipo Cachorro
        System.out.println(outro.som);    // NÃO compila: referência do tipo Animal
        System.out.println(habitat);      // NÃO compila: outro pacote
    }
}
```

A lógica: `Cachorro` herdou o direito de mexer no `som` **dos cachorros**. Um `Animal` qualquer poderia ser um gato, de outra hierarquia, e `Cachorro` não tem nada a ver com ele.

> [!PROVA]
> Nas questões de `protected`, olhe três coisas: o pacote de quem acessa, se quem acessa é subclasse e o **tipo da referência** usada no acesso. No mesmo pacote, `protected` funciona como acesso de pacote. Fora dele, só subclasses, e só por referências do tipo delas.

> [!COMPILADOR]
> Você é o `javac`. Quais linhas desta classe não compilam?
>
> ```java
> public class A {
>     private int a;
>     protected static int b;
>     public private int c;
>     void m() { private int d = 1; }
>     int e;
> }
> ```
>
> **Resposta:** a linha de `c` e a de `d`. Um membro só pode ter um modificador de acesso, e `public private` são dois. E variáveis locais não aceitam modificador de acesso nenhum: elas só existem dentro do método. `protected static` é uma combinação válida.

## Onde cada modificador cabe

Classes de topo (as que não estão dentro de outra) só podem ser `public` ou sem modificador, e cada arquivo tem no máximo uma `public`, com o nome do arquivo. Variáveis locais e parâmetros não aceitam modificadores de acesso, porque só existem dentro do método:

```java nao-compila
private class Segredo {
}
```

```java nao-compila
public class Local {
    public static void main(String[] args) {
        private int x = 1;
        System.out.println(x);
    }
}
```

Um membro `public` de uma classe sem modificador também não é visível fora do pacote: para usar um membro, é preciso enxergar a classe primeiro. Os pacotes em si, o `package` e os `import`, você viu no episódio de [anatomia de um programa](/assistir/estagiario-t1-e02). Vale lembrar que `import pacote.*` não importa os subpacotes, e que o pacote `java.lang` é importado sempre.

> [!IA]
> Ao gerar classes, a IA costuma pôr *getters* e *setters* `public` para todos os campos, por hábito, o que desfaz o encapsulamento. Em questões de `protected` entre pacotes, também é comum ela esquecer a regra do tipo da referência. Peça que ela justifique cada membro `public` e confira o caso de `protected` compilando.

## Na IDE

- **Acesso que pode ser menor.** A inspeção "Declaration access can be weaker" aponta membros mais abertos do que o uso exige e oferece fechá-los com **Alt + Enter**.
- **Erro de acesso.** Ao usar um `private` de fora, o **Alt + Enter** oferece abrir o acesso; antes de aceitar, pergunte se não deveria existir um método para isso.
- **Ver a estrutura.** **Ctrl + F12** lista os membros da classe com ícones de cadeado que mostram o acesso de cada um.

## Por baixo dos panos

O acesso é conferido duas vezes. O compilador recusa o código, mas a JVM confere de novo ao ligar as classes: se alguém compilar uma classe contra uma versão antiga de outra, em que o campo era `public`, e depois rodar com a versão nova, em que ele virou `private`, a execução falha com `IllegalAccessError`. É uma das razões pelas quais mudar a visibilidade de algo público numa biblioteca é uma mudança incompatível.

Até o Java 10, classes aninhadas que acessavam membros `private` uma da outra exigiam um truque: o compilador gerava métodos sintéticos, com nomes como `access$000`, que furavam a regra por baixo. O Java 11 introduziu os *nestmates* (JEP 181): a classe de topo e suas aninhadas formam um ninho, e a JVM passou a entender que membros `private` são visíveis dentro do ninho inteiro. E acima disso tudo há os **módulos**, que você verá no cargo Pleno: um `public` dentro de um módulo só é visível fora dele se o pacote for exportado.

## Resumo para a prova

- Do mais fechado ao mais aberto: `private`, nenhum, `protected`, `public`
- Sem modificador é acesso de pacote; `default` não é modificador de acesso
- `private` é por classe: um objeto acessa o `private` de outro objeto da mesma classe
- `protected` = pacote + subclasses em outros pacotes
- Fora do pacote, a subclasse só acessa `protected` por `this` ou por referência do próprio tipo
- Classes de topo: só `public` ou nenhum; no máximo uma `public` por arquivo
- Variáveis locais e parâmetros não aceitam modificadores de acesso
