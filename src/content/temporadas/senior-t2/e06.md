Os streams paralelos apareceram no [Pleno](/assistir/pleno-t6-e06): `parallel()` divide o pipeline entre os núcleos, e operações como `toList`, `findFirst` e `forEachOrdered` mantêm a ordem de encontro. Agora, com threads, travas e coleções concorrentes na bagagem, dá para entender o que acontece por trás e onde o paralelismo quebra programas. A regra de ouro dos streams paralelos é uma só: **as lambdas não podem compartilhar estado mutável**. Este episódio mostra por quê, como reduzir e coletar com segurança e o framework que executa tudo isso, o fork/join.

## Efeitos colaterais: o erro mais comum

Num stream paralelo, cada lambda roda ao mesmo tempo em várias threads do `ForkJoinPool` comum, **e também na thread que chamou** a operação terminal. Qualquer estado fora da lambda que ela altere vira um dado compartilhado sem proteção:

```java
List<Integer> resultado = new ArrayList<>();
IntStream.range(0, 10_000).parallel().forEach(resultado::add);
System.out.println(resultado.size());
```

Este trecho não tem saída fixa. O `ArrayList` não é thread-safe: duas threads podem gravar na mesma posição, e uma adição se perde; ou o array interno cresce no meio de uma escrita, e sai uma `ArrayIndexOutOfBoundsException`. Em algumas execuções, por sorte, imprime 10000. Uma lista sincronizada evita a corrupção, mas ainda deixa os elementos fora de ordem e faz as threads disputarem a mesma trava. O certo é deixar o stream montar o resultado:

```java executar
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.stream.IntStream;
import java.util.stream.Stream;

public class Efeitos {
    public static void main(String[] args) {
        List<Integer> sincronizada = Collections.synchronizedList(new ArrayList<>());
        IntStream.range(0, 10_000).parallel().forEach(sincronizada::add);
        List<Integer> coletada = IntStream.range(0, 10_000).parallel().boxed().toList();
        System.out.println(sincronizada.size() + " " + coletada.size());
        System.out.println(coletada.subList(0, 5) + " " + coletada.equals(IntStream.range(0, 10_000).boxed().toList()));
        List<String> nomes = Stream.of("ana", "bia", "caio").parallel().collect(ArrayList::new, ArrayList::add, ArrayList::addAll);
        System.out.println(nomes);
    }
}
```

```saida
10000 10000
[0, 1, 2, 3, 4] true
[ana, bia, caio]
```

A lista coletada sai **na ordem**, idêntica à sequencial. A última linha usa o `collect` de três argumentos: um **fornecedor** que cria um contêiner novo, um **acumulador** que adiciona um elemento e um **combinador** que junta dois contêineres. Em paralelo, cada pedaço do stream ganha a própria `ArrayList`, e no fim elas são combinadas em ordem. Ninguém compartilha nada, e por isso não precisa de trava.

O mesmo vale para lambdas com **estado**: um `map` que consulta e altera um contador ou um conjunto de "já vistos" produz resultados diferentes a cada execução em paralelo. Lambdas de streams devem ser **sem estado** e **sem efeitos colaterais**.

## reduce em paralelo

Em paralelo, `reduce(identidade, acumulador)` reduz cada pedaço separadamente, **começando cada um pela identidade**, e depois combina os resultados parciais. Daí as duas exigências:

- A **identidade** precisa ser neutra: `0` para soma, `1` para produto, `""` para concatenação. Com `reduce(10, Integer::sum)`, o 10 entra uma vez por pedaço, e o resultado depende de quantos pedaços houve.
- O **acumulador** precisa ser **associativo**: `(a + b) + c` igual a `a + (b + c)`. Subtração não é, e `reduce(0, (a, b) -> a - b)` em paralelo dá resultados diferentes conforme a divisão.

Quando o tipo do resultado é diferente do tipo dos elementos, entra a versão de **três argumentos**: `reduce(identidade, acumulador, combinador)`. O acumulador junta um resultado parcial e um elemento; o combinador junta dois resultados parciais.

```java executar
import java.util.List;
import java.util.stream.Stream;

public class Reduzir {
    public static void main(String[] args) {
        List<String> palavras = List.of("fork", "join", "pool", "stream", "paralelo");
        int letras = palavras.parallelStream().reduce(0, (soma, p) -> soma + p.length(), Integer::sum);
        String juntas = palavras.parallelStream().reduce("", String::concat);
        StringBuilder sb = Stream.of("a", "b", "c").parallel().collect(StringBuilder::new, StringBuilder::append, StringBuilder::append);
        System.out.println(letras + " " + juntas + " " + sb);
    }
}
```

```saida
26 forkjoinpoolstreamparalelo abc
```

A concatenação sai em ordem mesmo em paralelo: a concatenação de `String` é associativa, e o `reduce` combina os pedaços respeitando a ordem de encontro. O que não é garantido é a ordem **de execução** das lambdas, não a do resultado.

## Coletores concorrentes

`Collectors.groupingBy` e `toMap`, em paralelo, montam um mapa por pedaço e depois os **mesclam**, o que custa caro com muitos grupos. As versões `groupingByConcurrent` e `toConcurrentMap` usam um único `ConcurrentMap`, preenchido por todas as threads ao mesmo tempo, sem mescla. Em troca, abrem mão da ordem: dentro de cada grupo, os elementos podem aparecer em qualquer ordem.

```java executar
import java.util.TreeMap;
import java.util.concurrent.ConcurrentMap;
import java.util.stream.Collectors;
import java.util.stream.Stream;

public class Grupos {
    public static void main(String[] args) {
        ConcurrentMap<Integer, Long> porTamanho = Stream.of("ana", "bia", "caio", "duda", "eduardo", "li")
            .parallel()
            .collect(Collectors.groupingByConcurrent(String::length, Collectors.counting()));
        System.out.println(new TreeMap<>(porTamanho));
        ConcurrentMap<String, Integer> tamanhos = Stream.of("ana", "caio").parallel()
            .collect(Collectors.toConcurrentMap(s -> s, String::length));
        System.out.println(new TreeMap<>(tamanhos));
    }
}
```

```saida
{2=1, 3=2, 4=2, 7=1}
{ana=3, caio=4}
```

O método `unordered()` também ajuda: ele avisa que a ordem não importa, e operações como `limit`, `distinct` e `findFirst` deixam de pagar o custo de mantê-la.

## O framework fork/join

Por trás dos streams paralelos está o framework **fork/join** do Java 7, que também pode ser usado diretamente. A ideia é dividir para conquistar: uma tarefa grande se divide em duas menores, que se dividem de novo, até ficarem pequenas o bastante para resolver em sequência. Uma tarefa que devolve resultado estende `RecursiveTask<V>`; uma sem resultado, `RecursiveAction`. As duas implementam `compute()`.

```java executar
import java.util.concurrent.ForkJoinPool;
import java.util.concurrent.RecursiveTask;

public class Soma extends RecursiveTask<Long> {
    private static final int LIMITE = 10_000;
    private final long[] numeros;
    private final int inicio;
    private final int fim;

    Soma(long[] numeros, int inicio, int fim) {
        this.numeros = numeros;
        this.inicio = inicio;
        this.fim = fim;
    }

    @Override
    protected Long compute() {
        if (fim - inicio <= LIMITE) {
            long total = 0;
            for (int i = inicio; i < fim; i++) {
                total += numeros[i];
            }
            return total;
        }
        int meio = (inicio + fim) / 2;
        Soma esquerda = new Soma(numeros, inicio, meio);
        Soma direita = new Soma(numeros, meio, fim);
        esquerda.fork();
        long resultadoDireita = direita.compute();
        return esquerda.join() + resultadoDireita;
    }

    public static void main(String[] args) {
        long[] numeros = new long[1_000_000];
        for (int i = 0; i < numeros.length; i++) {
            numeros[i] = i + 1;
        }
        long total = ForkJoinPool.commonPool().invoke(new Soma(numeros, 0, numeros.length));
        System.out.println(total);
    }
}
```

```saida
500000500000
```

`fork()` agenda a metade esquerda para rodar em outra thread do pool; a thread atual calcula a direita ela mesma, com `compute()`, em vez de ficar parada; e `join()` espera o resultado da esquerda. Chamar `fork` nas duas metades e `join` nas duas também funciona, mas desperdiça a thread atual. `invoke` envia a tarefa raiz e espera o resultado.

> [!PROVA]
> Lambdas de streams paralelos não devem alterar estado compartilhado: um `ArrayList` alterado num `forEach` paralelo pode perder elementos. `reduce` paralelo exige identidade neutra e operação associativa; a versão de três argumentos usa um combinador. `collect(fornecedor, acumulador, combinador)` dá um contêiner por pedaço. `parallelStream()` é método de `Collection`, não de `Stream`. Um stream, paralelo ou não, só pode ser consumido uma vez: a segunda operação terminal lança `IllegalStateException`.

## Por baixo dos panos

O `ForkJoinPool` dá a cada thread operária uma **fila dupla** (*deque*) própria. Um `fork()` empurra a tarefa no topo da fila da própria thread, que continua tirando trabalho desse mesmo topo, em ordem de pilha, aproveitando os dados ainda quentes no cache. Uma thread que fica sem trabalho **rouba** tarefas do fundo da fila de outra, onde estão as maiores, ainda não divididas. Esse **roubo de trabalho** (*work stealing*) equilibra a carga sem um coordenador central, e quase sem disputa, porque dona e ladra mexem em pontas opostas da fila.

O pool comum tem, por padrão, uma thread a menos que o número de núcleos, porque a thread que chama a operação terminal também trabalha. O tamanho pode ser ajustado com a propriedade `java.util.concurrent.ForkJoinPool.common.parallelism`. Como esse pool é único para o processo inteiro, uma lambda que bloqueia, esperando rede ou disco, prende uma thread que todos os streams paralelos do programa dividem. Para trabalho bloqueante, threads virtuais; para trabalho de CPU com muitos dados, streams paralelos ou fork/join.

## Resumo para a prova

- Lambdas de streams paralelos: sem estado e sem efeitos colaterais; prefira `collect`, `toList` e `reduce`
- `reduce(identidade, acumulador)`: identidade neutra, acumulador associativo; `reduce` de três argumentos acrescenta o combinador
- `collect(fornecedor, acumulador, combinador)`: um contêiner por pedaço, combinados em ordem
- `groupingByConcurrent` e `toConcurrentMap` preenchem um único mapa concorrente, sem garantia de ordem
- Fork/join: `RecursiveTask<V>` e `RecursiveAction`, com `compute`, `fork`, `join` e `invoke`
- `parallelStream()` só em `Collection`; um stream só pode ser consumido uma vez
