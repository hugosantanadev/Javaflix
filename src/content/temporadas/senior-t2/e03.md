O `synchronized` do [episódio 1](/assistir/senior-t2-e01) é simples e seguro: a trava é adquirida na entrada do bloco e liberada na saída, sem esquecimento possível. Essa simplicidade cobra um preço. Uma thread que espera uma trava `synchronized` espera **para sempre**: não dá para desistir depois de um tempo, nem tentar sem esperar, nem responder a uma interrupção. O pacote `java.util.concurrent.locks` traz travas explícitas, objetos que se adquirem e liberam por métodos, com todas essas opções.

## A interface Lock

| Método | O que faz |
|---|---|
| `lock()` | Adquire a trava, esperando o quanto for preciso |
| `unlock()` | Libera a trava |
| `tryLock()` | Tenta adquirir **sem esperar**; devolve `true` se conseguiu |
| `tryLock(tempo, unidade)` | Espera até o prazo; devolve se conseguiu; lança `InterruptedException` |
| `lockInterruptibly()` | Espera, mas desiste com `InterruptedException` se a thread for interrompida |
| `newCondition()` | Cria uma condição de espera ligada à trava |

A implementação mais usada é a `ReentrantLock`. Com ela, a liberação é responsabilidade sua, e o único jeito seguro de garanti-la é um `finally`. O padrão é sempre o mesmo: `lock()` **antes** do `try`, `unlock()` no `finally`.

```java executar
import java.util.concurrent.locks.ReentrantLock;

public class Basico {
    private final ReentrantLock trava = new ReentrantLock();
    private int valor;

    void incrementar() {
        trava.lock();
        try {
            valor++;
        } finally {
            trava.unlock();
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Basico contador = new Basico();
        Runnable somar = () -> {
            for (int i = 0; i < 1_000_000; i++) {
                contador.incrementar();
            }
        };
        Thread a = new Thread(somar);
        Thread b = new Thread(somar);
        a.start();
        b.start();
        a.join();
        b.join();
        System.out.println(contador.valor);

        ReentrantLock trava = contador.trava;
        trava.lock();
        trava.lock();
        System.out.println(trava.getHoldCount() + " " + trava.isHeldByCurrentThread());
        trava.unlock();
        System.out.println(trava.getHoldCount() + " " + trava.isLocked());
        trava.unlock();
        System.out.println(trava.getHoldCount() + " " + trava.isLocked());
    }
}
```

```saida
2000000
2 true
1 true
0 false
```

Como o nome diz, a trava é **reentrante**: a mesma thread pode adquiri-la de novo, e um contador, o `getHoldCount()`, registra quantas vezes. Ela só fica livre quando o número de `unlock()` iguala o de `lock()`. Esquecer um `unlock` deixa a trava presa, e todas as outras threads esperam para sempre. Chamar `unlock()` sem segurar a trava lança `IllegalMonitorStateException`.

## Tentar sem esperar

`tryLock()` é o que o `synchronized` não tem: a thread **pergunta** se a trava está livre e, se não estiver, segue fazendo outra coisa. A versão com prazo espera no máximo o tempo informado. Diferente da versão sem argumentos, ela declara `InterruptedException`, uma exceção checked: chamar `tryLock(100, TimeUnit.MILLISECONDS)` sem tratá-la não compila.

```java executar
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

public class Tentativa {
    public static void main(String[] args) throws InterruptedException {
        ReentrantLock trava = new ReentrantLock();
        CountDownLatch tentou = new CountDownLatch(1);
        trava.lock();
        Thread outra = new Thread(() -> {
            System.out.println("tryLock imediato: " + trava.tryLock());
            tentou.countDown();
            try {
                boolean conseguiu = trava.tryLock(2, TimeUnit.SECONDS);
                System.out.println("tryLock com prazo: " + conseguiu);
                if (conseguiu) {
                    trava.unlock();
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });
        outra.start();
        tentou.await();
        trava.unlock();
        outra.join();
    }
}
```

```saida
tryLock imediato: false
tryLock com prazo: true
```

O `main` segura a trava até a outra thread fazer a primeira tentativa, que por isso falha. Depois, libera; a segunda tentativa, que estava esperando, consegue. Note o `if (conseguiu)` antes do `unlock`: só se libera o que se adquiriu.

Outras opções do `ReentrantLock`:

- **Justiça**: `new ReentrantLock(true)` cria uma trava *fair*, que entrega a vez à thread que espera há mais tempo. A padrão, `false`, permite que uma thread recém-chegada passe na frente, o que rende mais, mas pode deixar alguém esperando muito. `isFair()` informa o modo.
- **Interrupção**: `lockInterruptibly()` desiste se a thread for interrompida; o `lock()` comum ignora a interrupção e continua esperando.
- **Condições**: `newCondition()` cria objetos `Condition`, com `await()`, `signal()` e `signalAll()`, os equivalentes de `wait`, `notify` e `notifyAll`. Uma mesma trava pode ter várias condições, como "fila não cheia" e "fila não vazia", o que o `synchronized` não permite. Como no `wait`, `await()` exige segurar a trava; sem ela, lança `IllegalMonitorStateException`.

## ReadWriteLock: muitos leitores, um escritor

Em muitos dados compartilhados, como um cache ou uma configuração, as leituras são muito mais frequentes que as escritas. Ler ao mesmo tempo não tem perigo; o problema é ler enquanto alguém escreve. Uma `ReadWriteLock` tem duas travas ligadas:

- A **de leitura**, `readLock()`, pode ser segurada por **várias** threads ao mesmo tempo, desde que ninguém esteja escrevendo.
- A **de escrita**, `writeLock()`, é **exclusiva**: só é concedida quando ninguém está lendo nem escrevendo.

A implementação é a `ReentrantReadWriteLock`. A interface `ReadWriteLock` não tem `lock()` nem `unlock()`: só os dois métodos que devolvem as travas.

```java executar
import java.util.concurrent.locks.ReentrantReadWriteLock;

public class Leitura {
    public static void main(String[] args) throws InterruptedException {
        ReentrantReadWriteLock rw = new ReentrantReadWriteLock();
        rw.readLock().lock();
        Thread outra = new Thread(() -> {
            boolean leu = rw.readLock().tryLock();
            boolean escreveu = rw.writeLock().tryLock();
            System.out.println("outra thread lê: " + leu + ", escreve: " + escreveu + ", leitores: " + rw.getReadLockCount());
            if (leu) {
                rw.readLock().unlock();
            }
        });
        outra.start();
        outra.join();
        rw.readLock().unlock();

        rw.writeLock().lock();
        System.out.println("escrita: " + rw.isWriteLocked() + ", leitores: " + rw.getReadLockCount());
        rw.readLock().lock();
        rw.writeLock().unlock();
        System.out.println("rebaixada: " + rw.isWriteLocked() + ", leitores: " + rw.getReadLockCount());
        rw.readLock().unlock();
    }
}
```

```saida
outra thread lê: true, escreve: false, leitores: 2
escrita: true, leitores: 0
rebaixada: false, leitores: 1
```

Enquanto o `main` lê, outra thread também consegue ler, mas não escrever. O final mostra o **rebaixamento**: quem segura a trava de escrita pode adquirir a de leitura e então soltar a de escrita, sem deixar ninguém escrever no meio. O caminho contrário, **promover** uma leitura a escrita, não existe: uma thread que segura a leitura e pede a escrita fica esperando a si mesma para sempre.

> [!PROVA]
> Padrão: `lock()` antes do `try`, `unlock()` no `finally`. `unlock()` sem a trava lança `IllegalMonitorStateException`. `ReentrantLock` é reentrante: tantos `unlock` quantos `lock`. `tryLock()` devolve `boolean` na hora; `tryLock(tempo, unidade)` declara `InterruptedException`. `Lock` é interface: `new Lock()` não compila. `ReadWriteLock` só tem `readLock()` e `writeLock()`.

## Por baixo dos panos

`ReentrantLock` não usa o monitor do objeto, e sim o `AbstractQueuedSynchronizer` (AQS), uma classe base que quase todo o `java.util.concurrent` compartilha: `ReentrantLock`, `ReentrantReadWriteLock`, `Semaphore` e `CountDownLatch` são construídos sobre ele. O AQS guarda um único `int volatile`, o **estado**, e uma fila de threads em espera. No `ReentrantLock`, o estado é o contador de posse: 0 significa livre. Adquirir é um CAS de 0 para 1; se falhar, a thread entra na fila e é estacionada com `LockSupport.park()`. O `unlock` decrementa o estado e, ao chegar a 0, acorda a primeira da fila com `unpark()`.

Na `ReentrantReadWriteLock`, o mesmo `int` é dividido ao meio: os 16 bits altos contam as leituras, os 16 baixos contam a posse da escrita. A trava justa difere da injusta num único teste: antes de tentar o CAS, ela verifica se já há alguém na fila, e se houver, entra no fim.

Há ainda a `StampedLock`, do Java 8, com um modo de **leitura otimista**: a thread lê sem travar nada, recebe um carimbo e, no fim, confere se alguma escrita aconteceu no meio; se aconteceu, refaz a leitura com a trava de verdade. É mais rápida quando escritas são raras, mas não é reentrante e é bem mais fácil de usar errado.

## Resumo para a prova

- `Lock` é interface; `ReentrantLock` é a implementação; sempre `unlock()` no `finally`
- Reentrante: `getHoldCount()` conta as aquisições, e cada uma exige seu `unlock()`
- `unlock()` sem posse e `await()` sem a trava lançam `IllegalMonitorStateException`
- `tryLock()` não espera; `tryLock(tempo, unidade)` espera até o prazo e lança `InterruptedException`
- `lockInterruptibly()` responde à interrupção; `new ReentrantLock(true)` é justa
- `ReadWriteLock`: leitura compartilhada, escrita exclusiva; rebaixar é possível, promover não
