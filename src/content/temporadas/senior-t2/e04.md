As coleções do pacote `java.util`, como `ArrayList` e `HashMap`, **não são thread-safe**: duas threads que as alteram ao mesmo tempo podem perder elementos, corromper a estrutura interna ou entrar num laço infinito. Os episódios anteriores mostraram como proteger dados com travas, mas proteger cada acesso a um mapa à mão é trabalhoso e fácil de errar. O pacote `java.util.concurrent` traz coleções já preparadas para várias threads, e também os **sincronizadores**, objetos que coordenam threads umas com as outras.

## Iterar e alterar: ConcurrentModificationException

Mesmo com uma thread só, as coleções comuns não aceitam ser alteradas durante uma iteração. Cada uma guarda um contador de modificações, e o iterador confere se ele mudou a cada `next()`. Se mudou, lança `ConcurrentModificationException`: o nome fala de concorrência, mas a causa mais comum é um laço como este.

```java executar
import java.util.ArrayList;
import java.util.List;

public class Iterando {
    public static void main(String[] args) {
        List<String> nomes = new ArrayList<>(List.of("ana", "bia", "caio"));
        try {
            for (String n : nomes) {
                if (n.startsWith("a")) {
                    nomes.remove(n);
                }
            }
        } catch (RuntimeException e) {
            System.out.println(e.getClass().getSimpleName());
        }
        nomes.removeIf(n -> n.startsWith("b"));
        System.out.println(nomes);
    }
}
```

```saida
ConcurrentModificationException
[caio]
```

A forma correta de remover durante uma varredura é `removeIf` ou o `remove()` do próprio `Iterator`. A verificação é feita com a melhor das intenções, mas **não é garantida**: remover o penúltimo elemento, por exemplo, faz o laço terminar antes da conferência, sem exceção nenhuma.

## Wrappers sincronizados

A forma mais antiga de tornar uma coleção thread-safe é `Collections.synchronizedList(lista)`, `synchronizedMap(mapa)` e similares. Elas devolvem um invólucro em que **todo método** é `synchronized` numa mesma trava. Funcionam, mas têm dois problemas:

- Só uma thread acessa a coleção por vez, mesmo para ler: sob carga, todas fazem fila.
- Operações compostas continuam inseguras. Um "se não contém, adiciona" são duas chamadas, e outra thread pode agir entre elas. E iterar exige um `synchronized (lista)` manual em volta do laço inteiro, como diz o Javadoc.

## ConcurrentHashMap

O `ConcurrentHashMap` permite leituras sem trava e escritas simultâneas em partes diferentes do mapa. Mais importante, oferece operações compostas **atômicas**:

| Método | Faz atomicamente |
|---|---|
| `putIfAbsent(k, v)` | Grava só se a chave não existir |
| `computeIfAbsent(k, f)` | Calcula e grava só se a chave não existir |
| `merge(k, v, f)` | Grava `v` se a chave não existir; senão, combina o valor atual com `v` |
| `compute(k, f)` | Recalcula o valor a partir do atual |

Ele **não aceita `null`**, nem como chave nem como valor: `put` com `null` lança `NullPointerException`. Num mapa concorrente, um `get` que devolve `null` precisa significar uma coisa só, "a chave não existe". E seus iteradores são **fracamente consistentes**: nunca lançam `ConcurrentModificationException`, e podem ou não refletir alterações feitas durante a iteração.

```java executar
import java.util.List;
import java.util.Map;
import java.util.TreeMap;
import java.util.concurrent.ConcurrentHashMap;

public class Contagem {
    public static void main(String[] args) throws InterruptedException {
        Map<String, Integer> contagem = new ConcurrentHashMap<>();
        List<String> palavras = List.of("java", "thread", "java", "trava", "java", "thread");
        Thread[] threads = new Thread[4];
        for (int t = 0; t < threads.length; t++) {
            threads[t] = new Thread(() -> {
                for (String p : palavras) {
                    contagem.merge(p, 1, Integer::sum);
                }
            });
            threads[t].start();
        }
        for (Thread t : threads) {
            t.join();
        }
        System.out.println(new TreeMap<>(contagem));
        contagem.computeIfAbsent("lock", k -> k.length());
        contagem.computeIfAbsent("java", k -> 0);
        System.out.println(contagem.get("lock") + " " + contagem.get("java"));
        try {
            contagem.put("nulo", null);
        } catch (NullPointerException e) {
            System.out.println("null não é aceito");
        }
    }
}
```

```saida
{java=12, thread=8, trava=4}
4 12
null não é aceito
```

Quatro threads contam as mesmas seis palavras, e nenhum incremento se perde, porque cada `merge` é atômico. O `TreeMap` só serve para imprimir em ordem; a ordem do `ConcurrentHashMap`, como a do `HashMap`, não é definida. O segundo `computeIfAbsent` não faz nada, porque `java` já existe.

## Outras coleções concorrentes

| Coleção | Substitui | Característica |
|---|---|---|
| `ConcurrentHashMap` | `HashMap` | Operações compostas atômicas; sem `null` |
| `ConcurrentSkipListMap` / `ConcurrentSkipListSet` | `TreeMap` / `TreeSet` | Ordenadas, sem trava global |
| `CopyOnWriteArrayList` / `CopyOnWriteArraySet` | `ArrayList` / conjunto pequeno | Cada escrita copia o array; iteração sobre um retrato |
| `ConcurrentLinkedQueue` / `ConcurrentLinkedDeque` | `LinkedList` como fila | Fila sem trava, sem limite |
| `ArrayBlockingQueue` / `LinkedBlockingQueue` | Fila com espera | `put` espera espaço; `take` espera item |

A `CopyOnWriteArrayList` cria um array novo a cada alteração. Escrever é caro, mas ler e iterar não precisa de trava nenhuma: o iterador percorre o array que existia quando foi criado, e alterações feitas durante a iteração **não aparecem** nele nem causam exceção. Serve para listas muito lidas e pouco alteradas, como uma lista de ouvintes de eventos.

As `BlockingQueue` são a peça central do padrão **produtor e consumidor**. Cada operação existe em versões que se comportam diferente quando a fila está cheia ou vazia:

| | Lança exceção | Devolve valor especial | Espera | Espera com prazo |
|---|---|---|---|---|
| Inserir | `add(e)` | `offer(e)` → `false` | `put(e)` | `offer(e, tempo, unidade)` |
| Remover | `remove()` | `poll()` → `null` | `take()` | `poll(tempo, unidade)` |

`put` e `take` declaram `InterruptedException`. A `ArrayBlockingQueue` exige a capacidade no construtor; a `LinkedBlockingQueue` pode ser criada sem limite.

## Sincronizadores

Três classes coordenam threads sem que elas compartilhem dados:

- **`CountDownLatch(n)`**: um contador que só desce. Cada `countDown()` desconta um, e `await()` bloqueia até chegar a zero. Não pode ser reiniciado. Serve para "esperar que N coisas aconteçam".
- **`CyclicBarrier(n, acao)`**: um ponto de encontro. Cada thread que chama `await()` espera até que `n` threads tenham chegado; então a ação opcional roda uma vez, todas seguem, e a barreira se rearma para a próxima rodada.
- **`Semaphore(n)`**: um conjunto de `n` permissões. `acquire()` pega uma, esperando se não houver; `release()` devolve; `tryAcquire()` tenta sem esperar. Serve para limitar quantas threads usam um recurso ao mesmo tempo, como no máximo 20 conexões ao banco.

```java executar
import java.util.concurrent.BrokenBarrierException;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.CyclicBarrier;
import java.util.concurrent.Semaphore;
import java.util.concurrent.atomic.AtomicInteger;

public class Sincronizadores {
    public static void main(String[] args) throws Exception {
        CountDownLatch prontos = new CountDownLatch(3);
        for (int i = 0; i < 3; i++) {
            new Thread(prontos::countDown).start();
        }
        prontos.await();
        System.out.println("latch: todos prontos, contagem " + prontos.getCount());

        AtomicInteger rodada = new AtomicInteger();
        CyclicBarrier barreira = new CyclicBarrier(3, () -> System.out.println("barreira: rodada " + rodada.incrementAndGet() + " completa"));
        Thread[] corredores = new Thread[3];
        for (int i = 0; i < 3; i++) {
            corredores[i] = new Thread(() -> {
                try {
                    for (int r = 0; r < 2; r++) {
                        barreira.await();
                    }
                } catch (InterruptedException | BrokenBarrierException e) {
                    Thread.currentThread().interrupt();
                }
            });
            corredores[i].start();
        }
        for (Thread t : corredores) {
            t.join();
        }

        Semaphore vagas = new Semaphore(2);
        System.out.println("semáforo: " + vagas.tryAcquire() + " " + vagas.tryAcquire() + " " + vagas.tryAcquire());
        vagas.release();
        System.out.println("vagas livres: " + vagas.availablePermits());
    }
}
```

```saida
latch: todos prontos, contagem 0
barreira: rodada 1 completa
barreira: rodada 2 completa
semáforo: true true false
vagas livres: 1
```

A barreira é usada duas vezes pelas mesmas três threads, e a ação roda uma vez por rodada. O semáforo começa com duas permissões: a terceira tentativa falha, e o `release()` devolve uma.

> [!PROVA]
> Alterar uma `ArrayList` durante um for-each lança, em geral, `ConcurrentModificationException`, mesmo com uma thread. `ConcurrentHashMap` não aceita `null` e tem `merge`, `computeIfAbsent` e `putIfAbsent` atômicos. `CopyOnWriteArrayList` itera sobre um retrato e não lança exceção. `BlockingQueue`: `offer`/`poll` não esperam, `put`/`take` esperam e lançam `InterruptedException`. `CyclicBarrier` se reinicia; `CountDownLatch` não.

## Por baixo dos panos

O `ConcurrentHashMap` do Java 8 em diante é um array de **baldes**, como o `HashMap`. Inserir num balde vazio é um único CAS, sem trava. Quando o balde já tem elementos, a thread sincroniza **só no primeiro nó daquele balde**, e por isso threads que escrevem em baldes diferentes não se atrapalham. Leituras não travam nada: os campos dos nós são `volatile`, e um `get` sempre vê um nó completo. Quando um balde acumula muitos elementos, a lista vira uma árvore balanceada, como no `HashMap`. Para crescer, o mapa cria um array maior e as próprias threads que estão escrevendo ajudam a transferir os baldes, cada uma pegando uma faixa.

A `ConcurrentSkipListMap` é uma *skip list*: uma lista ligada ordenada com várias camadas de atalhos, que permite busca em tempo logarítmico e inserção com CAS, sem precisar rebalancear uma árvore inteira sob trava. E `CountDownLatch` e `Semaphore` são, como a `ReentrantLock` do [episódio anterior](/assistir/senior-t2-e03), construídos sobre o `AbstractQueuedSynchronizer`: no latch, o estado é a contagem; no semáforo, o número de permissões livres.

## Resumo para a prova

- `ArrayList`, `HashMap` e companhia não são thread-safe; alterar durante a iteração lança `ConcurrentModificationException`
- `Collections.synchronizedX` trava tudo numa trava só; iteração e operações compostas exigem sincronização manual
- `ConcurrentHashMap`: sem `null`, iteradores fracamente consistentes, `merge`/`compute`/`putIfAbsent` atômicos
- `CopyOnWriteArrayList`: escrita copia o array, iterador vê um retrato
- `BlockingQueue`: `offer`/`poll` devolvem `false`/`null`; `put`/`take` esperam; `ArrayBlockingQueue` exige capacidade
- `CountDownLatch` (não reinicia), `CyclicBarrier` (reinicia, com ação), `Semaphore` (permissões)
