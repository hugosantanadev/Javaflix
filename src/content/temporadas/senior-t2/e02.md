O [episódio anterior](/assistir/senior-t2-e01) resolveu a condição de corrida com `synchronized`. Funciona, mas tem custo: cada thread que encontra a trava ocupada fica bloqueada, e para algo tão pequeno quanto somar 1 num contador isso é exagero. O pacote `java.util.concurrent.atomic` oferece variáveis que se atualizam de forma **atômica sem trava**, e a palavra-chave `volatile` resolve o outro problema que o `synchronized` cobria: a **visibilidade**.

## O problema da visibilidade

Cada núcleo do processador tem seus caches, e o compilador JIT pode guardar o valor de um campo num registrador em vez de lê-lo da memória a cada vez. Sem nenhuma sincronização, **nada garante** que uma thread enxergue o que outra gravou. O exemplo clássico é uma bandeira de parada:

```java
public class SemVolatile {
    private static boolean parar = false;

    public static void main(String[] args) throws InterruptedException {
        Thread trabalhadora = new Thread(() -> {
            while (!parar) {
                // trabalha
            }
        });
        trabalhadora.start();
        Thread.sleep(100);
        parar = true;
        trabalhadora.join();
    }
}
```

Este programa pode **nunca terminar**. O JIT percebe que o laço não altera `parar` e pode transformar o teste num `while (true)`, lendo o campo uma vez só. Se termina ou não depende da JVM, do processador e do momento, e esse é o pior tipo de defeito.

## volatile

Um campo marcado com `volatile` tem duas garantias:

1. **Visibilidade**: toda leitura enxerga a última escrita feita por qualquer thread. O valor não fica preso num registrador ou num cache.
2. **Ordem**: o que uma thread gravou **antes** de escrever num `volatile` fica visível para quem **ler** esse `volatile` depois. O compilador e o processador não podem reordenar acessos através dele de forma que quebre isso.

```java executar
public class Parada {
    private static volatile boolean parar = false;

    public static void main(String[] args) throws InterruptedException {
        Thread trabalhadora = new Thread(() -> {
            long voltas = 0;
            while (!parar) {
                voltas++;
            }
            System.out.println("trabalhadora parou");
        });
        trabalhadora.start();
        Thread.sleep(100);
        parar = true;
        trabalhadora.join();
        System.out.println("fim");
    }
}
```

```saida
trabalhadora parou
fim
```

O que `volatile` **não** faz é tornar operações compostas atômicas. Um `volatile int contador` com `contador++` em duas threads continua perdendo incrementos: a leitura e a escrita são, cada uma, visíveis, mas outra thread ainda pode agir entre as duas. `volatile` serve para um campo que uma thread escreve e outras leem, como bandeiras e configurações publicadas; não para contadores.

O compilador também tem regras: `volatile` só marca **campos**, nunca variáveis locais, e não pode ser combinado com `final`, que já garante visibilidade do valor depois da construção.

## Variáveis atômicas

As classes `AtomicInteger`, `AtomicLong`, `AtomicBoolean` e `AtomicReference<V>` guardam um valor e oferecem operações compostas que acontecem **inteiras ou não acontecem**, sem trava. Elas também têm a semântica de visibilidade de `volatile`.

| Método | Faz | Devolve |
|---|---|---|
| `get()` / `set(v)` | Lê / grava | O valor / nada |
| `incrementAndGet()` / `decrementAndGet()` | Soma / subtrai 1 | O valor **novo** |
| `getAndIncrement()` / `getAndDecrement()` | Soma / subtrai 1 | O valor **antigo** |
| `addAndGet(d)` / `getAndAdd(d)` | Soma `d` | Novo / antigo |
| `getAndSet(v)` | Grava `v` | O antigo |
| `compareAndSet(esperado, novo)` | Grava `novo` só se o valor atual for `esperado` | `true` se gravou |
| `updateAndGet(f)` / `getAndUpdate(f)` | Aplica a função | Novo / antigo |
| `accumulateAndGet(x, f)` | Combina o atual com `x` pela função | O novo |

A regra para não errar: o nome diz a ordem. Em `getAndIncrement`, primeiro *get*, depois *increment*, e por isso devolve o antigo, como o `x++`. Em `incrementAndGet`, o contrário, como o `++x`.

```java executar
import java.util.concurrent.atomic.AtomicInteger;

public class Atomicos {
    public static void main(String[] args) throws InterruptedException {
        AtomicInteger n = new AtomicInteger(5);
        System.out.println(n.getAndIncrement() + " " + n.incrementAndGet() + " " + n.get());
        System.out.println(n.getAndAdd(10) + " " + n.addAndGet(10) + " " + n.decrementAndGet());
        System.out.println(n.compareAndSet(26, 0) + " " + n.compareAndSet(26, 1) + " " + n.get());
        System.out.println(n.updateAndGet(x -> x + 3) + " " + n.accumulateAndGet(10, Math::max));

        AtomicInteger contador = new AtomicInteger();
        Runnable somar = () -> {
            for (int i = 0; i < 1_000_000; i++) {
                contador.incrementAndGet();
            }
        };
        Thread a = new Thread(somar);
        Thread b = new Thread(somar);
        a.start();
        b.start();
        a.join();
        b.join();
        System.out.println(contador.get());
    }
}
```

```saida
5 7 7
7 27 26
true false 0
3 10
2000000
```

O `compareAndSet(26, 0)` grava porque o valor era 26; o segundo falha porque já não é. Os operadores `++` e `+=` não funcionam em objetos atômicos, e as regras de `volatile` também são conferidas pelo compilador:

```java nao-compila
import java.util.concurrent.atomic.AtomicInteger;

public class Regras {
    private final volatile int limite = 10;

    void contar(AtomicInteger n) {
        n++;
    }
}
```

As duas linhas falham: `final volatile` é uma combinação ilegal, e `n++` exige um tipo numérico, não um objeto.

Um cuidado com `AtomicReference`: o `compareAndSet` compara com `==`, **identidade**, não com `equals`. Um `AtomicReference<String>` que guarda `new String("a")` não troca o valor com `compareAndSet("a", "b")`, porque o literal `"a"` é outro objeto.

## Muitas threads somando: LongAdder

Com dezenas de threads incrementando o mesmo `AtomicLong`, todas disputam a mesma posição de memória, e muitas tentativas falham e se repetem. O `LongAdder` espalha a soma em várias células, uma por thread em disputa, e só as junta quando se pede o resultado com `sum()`. Escreve muito mais rápido sob disputa, mas `sum()` não é um retrato instantâneo se houver threads somando ao mesmo tempo. Serve para métricas e contadores de estatística; para gerar ids, que precisam do valor exato a cada incremento, use `AtomicLong`.

> [!PROVA]
> `volatile` garante visibilidade e ordem, mas não atomicidade: `x++` num campo `volatile` ainda tem corrida. Só marca campos, e não combina com `final`. `incrementAndGet` devolve o novo valor; `getAndIncrement`, o antigo. `compareAndSet` devolve `boolean` e só grava se o valor atual for o esperado. Objetos atômicos não aceitam `++`.

## Por baixo dos panos

As classes atômicas se apoiam numa instrução do processador chamada **compare-and-swap** (CAS), que no x86 é a `lock cmpxchg`: ela compara um endereço de memória com um valor esperado e, só se forem iguais, grava o novo, tudo numa única operação indivisível que nenhum outro núcleo pode interromper. Operações como `updateAndGet` são um laço sobre o CAS: ler o valor, calcular o novo, tentar o `compareAndSet`; se outra thread mudou o valor no meio, o CAS falha e o laço tenta de novo. Ninguém fica bloqueado, e por isso esse estilo se chama *lock-free*. No JDK atual, o acesso é feito por `VarHandle`, a API pública que substituiu o uso interno de `sun.misc.Unsafe`.

Um `volatile` também vira instruções específicas. No x86, cada escrita num `volatile` é seguida de uma **barreira de memória**, que obriga o núcleo a esvaziar seu buffer de escrita antes de seguir, e o JIT fica proibido de manter o campo num registrador. Por isso ler e escrever `volatile` é um pouco mais caro que um campo comum, embora bem mais barato que uma trava disputada.

O CAS tem uma armadilha teórica, o problema **ABA**: o valor muda de A para B e volta para A entre a leitura e o CAS, e o CAS acha que nada mudou. Para valores numéricos isso raramente importa; para estruturas de dados com referências, o `AtomicStampedReference` acrescenta um número de versão que muda a cada escrita.

## Resumo para a prova

- Sem sincronização, uma thread pode nunca enxergar a escrita de outra
- `volatile`: visibilidade e ordem, sem atomicidade; só em campos, nunca com `final`
- `AtomicInteger`, `AtomicLong`, `AtomicBoolean`, `AtomicReference`: operações compostas atômicas sem trava
- `incrementAndGet` devolve o novo; `getAndIncrement`, o antigo; `addAndGet`/`getAndAdd` idem
- `compareAndSet(esperado, novo)` devolve `true` se gravou; em `AtomicReference`, compara com `==`
- `LongAdder` para contadores muito disputados; `AtomicLong` quando cada valor importa
