Travas resolvem a condição de corrida, mas trazem uma família própria de defeitos: threads que deixam de avançar. Não há exceção, nem mensagem de erro, nem uso de CPU em alguns casos: o programa simplesmente para de fazer o que devia. Os três problemas clássicos são o **deadlock**, o **livelock** e a **starvation**, e a prova pede que você saiba reconhecer cada um.

## Deadlock: o impasse

Duas threads transferem dinheiro entre as mesmas contas, em sentidos opostos. Cada transferência trava a conta de origem e depois a de destino. A primeira thread trava A e vai pedir B; a segunda trava B e vai pedir A. Cada uma segura o que a outra precisa, e as duas esperam **para sempre**. Isso é um **deadlock**, ou impasse.

O exemplo abaixo provoca o impasse de propósito: um `CountDownLatch` garante que as duas threads já seguram a primeira trava antes de pedir a segunda. O `main` usa o `ThreadMXBean`, a API de monitoramento da JVM, para detectar o ciclo. As threads são daemon para que o programa possa terminar mesmo com elas presas.

```java executar
import java.lang.management.ManagementFactory;
import java.lang.management.ThreadInfo;
import java.lang.management.ThreadMXBean;
import java.util.Arrays;
import java.util.concurrent.CountDownLatch;

public class Impasse {
    public static void main(String[] args) throws InterruptedException {
        Object contaA = new Object();
        Object contaB = new Object();
        CountDownLatch ambasSeguram = new CountDownLatch(2);

        Thread t1 = new Thread(() -> transferir(contaA, contaB, ambasSeguram), "de-A-para-B");
        Thread t2 = new Thread(() -> transferir(contaB, contaA, ambasSeguram), "de-B-para-A");
        t1.setDaemon(true);
        t2.setDaemon(true);
        t1.start();
        t2.start();

        ThreadMXBean jvm = ManagementFactory.getThreadMXBean();
        long[] presas = null;
        while (presas == null) {
            Thread.sleep(50);
            presas = jvm.findDeadlockedThreads();
        }
        ThreadInfo[] info = jvm.getThreadInfo(presas);
        Arrays.sort(info, (x, y) -> x.getThreadName().compareTo(y.getThreadName()));
        for (ThreadInfo i : info) {
            System.out.println(i.getThreadName() + ": " + i.getThreadState() + ", espera a trava de " + i.getLockOwnerName());
        }
    }

    static void transferir(Object de, Object para, CountDownLatch ambasSeguram) {
        synchronized (de) {
            ambasSeguram.countDown();
            try {
                ambasSeguram.await();
            } catch (InterruptedException e) {
                return;
            }
            synchronized (para) {
                System.out.println("nunca chega aqui");
            }
        }
    }
}
```

```saida
de-A-para-B: BLOCKED, espera a trava de de-B-para-A
de-B-para-A: BLOCKED, espera a trava de de-A-para-B
```

Threads presas em `synchronized` ficam no estado `BLOCKED`. Com `ReentrantLock.lock()`, o impasse é o mesmo, mas o estado aparece como `WAITING`, porque a thread é estacionada pela fila do AQS. Num programa real, sem latch, o impasse só acontece quando a intercalação calha, talvez uma vez por semana em produção. A ferramenta `jstack <pid>`, ou `jcmd <pid> Thread.print`, mostra o estado de todas as threads e, havendo ciclo, a mensagem `Found one Java-level deadlock`.

Um deadlock exige quatro condições ao mesmo tempo, as **condições de Coffman**:

1. **Exclusão mútua**: o recurso só pode ser usado por uma thread por vez.
2. **Posse e espera**: a thread segura um recurso enquanto espera outro.
3. **Sem preempção**: ninguém pode tomar o recurso de quem o segura.
4. **Espera circular**: há um ciclo de threads, cada uma esperando a seguinte.

Quebrar qualquer uma impede o impasse.

## Evitando o deadlock

A técnica mais usada quebra a **espera circular**: todas as threads adquirem as travas **na mesma ordem global**. Se toda transferência trava primeiro a conta de menor id, as duas threads disputam a mesma primeira trava, e o ciclo não se forma.

```java executar
import java.util.concurrent.locks.ReentrantLock;

public class Ordem {
    static class Conta {
        final int id;
        int saldo;
        final ReentrantLock trava = new ReentrantLock();

        Conta(int id, int saldo) {
            this.id = id;
            this.saldo = saldo;
        }
    }

    static void transferir(Conta de, Conta para, int valor) {
        Conta primeira = de.id < para.id ? de : para;
        Conta segunda = de.id < para.id ? para : de;
        primeira.trava.lock();
        try {
            segunda.trava.lock();
            try {
                de.saldo -= valor;
                para.saldo += valor;
            } finally {
                segunda.trava.unlock();
            }
        } finally {
            primeira.trava.unlock();
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Conta a = new Conta(1, 1000);
        Conta b = new Conta(2, 1000);
        Thread t1 = new Thread(() -> {
            for (int i = 0; i < 100_000; i++) {
                transferir(a, b, 1);
            }
        });
        Thread t2 = new Thread(() -> {
            for (int i = 0; i < 100_000; i++) {
                transferir(b, a, 1);
            }
        });
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println(a.saldo + " " + b.saldo + " total " + (a.saldo + b.saldo));
    }
}
```

```saida
1000 1000 total 2000
```

Duzentas mil transferências em sentidos opostos, sem impasse e sem perder um centavo.

Outra técnica é **desistir com prazo**: adquirir a segunda trava com `tryLock(tempo, unidade)` e, se falhar, **soltar a primeira** e tentar de novo mais tarde. Isso quebra a "posse e espera". No exemplo, o `main` segura `b` o tempo todo; a outra thread pega `a`, espera `b` por 100 ms, desiste e devolve `a`:

```java executar
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

public class Desiste {
    public static void main(String[] args) throws InterruptedException {
        ReentrantLock a = new ReentrantLock();
        ReentrantLock b = new ReentrantLock();
        b.lock();
        Thread t = new Thread(() -> {
            a.lock();
            try {
                if (b.tryLock(100, TimeUnit.MILLISECONDS)) {
                    try {
                        System.out.println("transferiu");
                    } finally {
                        b.unlock();
                    }
                } else {
                    System.out.println("desistiu e soltou a trava de a");
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            } finally {
                a.unlock();
            }
        });
        t.start();
        t.join();
        b.unlock();
        System.out.println(a.isLocked() + " " + b.isLocked());
    }
}
```

```saida
desistiu e soltou a trava de a
false false
```

Por fim, **segurar menos**: não chamar código desconhecido (um *callback*, um método sobrescrevível) enquanto segura uma trava, e preferir estruturas que não precisem de duas travas, como as classes atômicas e as coleções concorrentes.

## Livelock: ocupados sem avançar

Duas pessoas se encontram num corredor estreito. Cada uma dá um passo para o lado para deixar a outra passar, ao mesmo tempo, para o mesmo lado. Depois as duas voltam, juntas. Ninguém está parado, mas ninguém passa. Isso é um **livelock**: as threads continuam executando e mudando de estado, mas respondendo uma à outra de forma que nenhuma progride.

Em código, aparece justamente na técnica do `tryLock`: duas threads que pegam a primeira trava, falham na segunda, soltam e tentam de novo **no mesmo ritmo** podem repetir esse ciclo indefinidamente, com a CPU em 100%. A correção é quebrar a simetria, esperando um tempo **aleatório** antes de tentar de novo.

## Starvation: sempre na fila

**Starvation**, ou inanição, é quando uma thread até poderia avançar, mas nunca recebe a vez, porque outras sempre ganham a disputa. Causas comuns:

- Uma trava **injusta** (o padrão), em que threads recém-chegadas passam na frente de quem espera. Uma `ReentrantLock(true)` atende por ordem de chegada.
- Threads que seguram uma trava por muito tempo, repetidamente, deixando as outras com janelas mínimas.
- Prioridades: o escalonador pode favorecer sempre as mais altas, embora prioridades sejam só sugestões.

| Problema | As threads estão... | Progresso | Correção típica |
|---|---|---|---|
| Deadlock | Bloqueadas, esperando em ciclo | Nenhum | Ordem global de travas, `tryLock` com prazo |
| Livelock | Ativas, reagindo umas às outras | Nenhum | Espera aleatória antes de tentar de novo |
| Starvation | Algumas ativas, outras sempre esperando | Só de algumas | Travas justas, seções críticas curtas |

> [!PROVA]
> Deadlock: threads bloqueadas para sempre, cada uma esperando uma trava que outra segura. Livelock: threads ativas que não progridem. Starvation: uma thread nunca consegue o recurso. Nenhum dos três lança exceção. Adquirir travas sempre na mesma ordem evita deadlock. Nas questões de saída, um deadlock possível significa que o resultado "não é determinado" ou que o programa "pode travar".

## Por baixo dos panos

O `findDeadlockedThreads` funciona porque a JVM sabe, para cada thread bloqueada, qual monitor ela espera e quem é o dono desse monitor. Com isso, monta um grafo "espera por" entre threads e procura ciclos nele. Para as travas de `java.util.concurrent`, o AQS registra o dono num campo (`exclusiveOwnerThread`), e a JVM consegue incluí-las na busca, chamadas de *ownable synchronizers*. O `jstack` usa a mesma informação ao imprimir o despejo de threads.

A JVM **não desfaz** um deadlock. Não há como forçar uma thread a soltar um monitor sem quebrar a consistência dos dados que ele protegia, e por isso a única saída, depois que o impasse se forma, é reiniciar o processo. Bancos de dados, ao contrário, detectam impasses entre transações e abortam uma delas, desfazendo o que ela fez, algo possível porque transações têm *rollback*. Em Java, a prevenção é a única defesa.

## Resumo para a prova

- Deadlock: ciclo de threads esperando travas umas das outras; ficam `BLOCKED` (monitor) ou `WAITING` (`Lock`)
- As quatro condições: exclusão mútua, posse e espera, sem preempção, espera circular
- Prevenção: ordem global de aquisição, `tryLock` com prazo soltando o que já tem, menos travas aninhadas
- Livelock: threads ativas sem progresso; corrija com espera aleatória
- Starvation: uma thread nunca ganha a vez; travas justas e seções críticas curtas ajudam
- `jstack` e `ThreadMXBean.findDeadlockedThreads()` detectam deadlocks; a JVM não os desfaz
