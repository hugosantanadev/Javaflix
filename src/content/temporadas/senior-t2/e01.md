A [temporada anterior](/assistir/senior-t1-e01) criou threads, executores e tarefas, mas sempre evitou um ponto: duas threads **mexendo no mesmo dado**. Todos os exemplos dividiam o trabalho em partes separadas e juntavam os resultados no fim. No mundo real, threads compartilham contadores, mapas, saldos e filas, e é aí que a programação concorrente fica difícil. Esta temporada trata de escrever código **thread-safe**: código que continua correto não importa como o escalonador intercale as threads.

## A condição de corrida

Duas threads somam 1 milhão cada no mesmo contador. O resultado deveria ser 2 milhões:

```java
public class Corrida {
    static int contador = 0;

    public static void main(String[] args) throws InterruptedException {
        Runnable somar = () -> {
            for (int i = 0; i < 1_000_000; i++) {
                contador++;
            }
        };
        Thread a = new Thread(somar);
        Thread b = new Thread(somar);
        a.start();
        b.start();
        a.join();
        b.join();
        System.out.println(contador);
    }
}
```

Este código não tem saída fixa: cada execução imprime um número diferente, quase sempre bem menor que 2 milhões, como 1460195 numa e 1048803 na seguinte. O motivo é que `contador++` **não é uma operação só**. São três passos: ler o valor, somar 1 e gravar de volta. Se as duas threads leem 41 ao mesmo tempo, as duas gravam 42, e um incremento se perde.

Isso é uma **condição de corrida** (*race condition*): o resultado depende da ordem exata em que as threads executam. O nome do trecho que lê e altera um dado compartilhado é **seção crítica**, e o defeito só aparece quando duas threads estão nela ao mesmo tempo. Por isso condições de corrida são traiçoeiras: o programa passa nos testes, e falha uma vez em mil em produção.

Há dois padrões clássicos de corrida:

- **Ler, modificar, gravar**: `contador++`, `saldo = saldo - valor`, `lista.set(i, lista.get(i) + 1)`
- **Verificar e depois agir**: `if (!mapa.containsKey(k)) mapa.put(k, v)`, `if (instancia == null) instancia = new Objeto()`. Entre a verificação e a ação, outra thread pode mudar o que foi verificado.

## synchronized: um de cada vez

Todo objeto Java tem uma **trava** embutida, também chamada de **monitor**. Um bloco `synchronized (objeto)` só começa depois que a thread **adquire** a trava daquele objeto, e a **libera** ao sair do bloco, normalmente ou com exceção. Enquanto uma thread segura a trava, qualquer outra que tente entrar num bloco sincronizado no **mesmo objeto** fica bloqueada, no estado `BLOCKED`, esperando a vez.

Um método marcado com `synchronized` é um atalho para um bloco que envolve o corpo inteiro:

| Declaração | Trava usada |
|---|---|
| `synchronized void m()` | A do próprio objeto, `this` |
| `static synchronized void m()` | A do objeto `Class`, como `Contador.class` |
| `synchronized (obj) { ... }` | A do objeto `obj` |

```java executar
public class Sincronizado {
    private int valor;

    synchronized void incrementar() {
        valor++;
    }

    synchronized int valor() {
        return valor;
    }

    public static void main(String[] args) throws InterruptedException {
        Sincronizado contador = new Sincronizado();
        Runnable somar = () -> {
            for (int i = 0; i < 1_000_000; i++) {
                contador.incrementar();
            }
        };
        Thread a = new Thread(somar);
        Thread b = new Thread(somar);
        a.start();
        b.start();
        a.join();
        b.join();
        System.out.println(contador.valor());
    }
}
```

```saida
2000000
```

Agora as duas threads disputam a mesma trava, a do objeto `contador`, e os três passos do incremento nunca se intercalam. A leitura em `valor()` também é sincronizada, e não por acaso: `synchronized` garante, além da exclusão, a **visibilidade**. Tudo o que uma thread gravou antes de liberar uma trava fica visível para a próxima thread que adquirir a mesma trava. Sem isso, uma thread poderia ler um valor antigo, guardado no cache de outro núcleo.

## As regras da trava

A exclusão só existe entre blocos que usam **o mesmo objeto**. Dois métodos de instância sincronizados de objetos diferentes não se excluem; um método `static synchronized` e um de instância também não, porque usam travas diferentes.

As travas do Java são **reentrantes**: uma thread que já segura uma trava pode entrar de novo em outro bloco com a mesma trava, sem travar a si mesma. Um método sincronizado pode chamar outro do mesmo objeto. `Thread.holdsLock(obj)` diz se a thread atual segura a trava de `obj`:

```java executar
public class Travas {
    static synchronized void estatico() {
        System.out.println("estático: " + Thread.holdsLock(Travas.class));
    }

    synchronized void deInstancia() {
        System.out.println("instância: " + Thread.holdsLock(this) + " " + Thread.holdsLock(Travas.class));
        reentrar();
    }

    synchronized void reentrar() {
        System.out.println("reentrou: " + Thread.holdsLock(this));
    }

    public static void main(String[] args) {
        Travas t = new Travas();
        Object trava = new Object();
        System.out.println("fora: " + Thread.holdsLock(trava));
        synchronized (trava) {
            System.out.println("dentro: " + Thread.holdsLock(trava));
        }
        estatico();
        t.deInstancia();
    }
}
```

```saida
fora: false
dentro: true
estático: true
instância: true false
reentrou: true
```

O compilador também impõe regras:

- A expressão do bloco precisa ser uma **referência**: `synchronized (n)` com `n` do tipo `int` não compila. Se a referência for `null`, o bloco lança `NullPointerException`.
- Construtores não podem ser `synchronized`; ninguém mais enxerga o objeto enquanto ele é construído.
- Métodos `abstract` e métodos de interface não podem ser `synchronized`, porque a trava é um detalhe da implementação.

```java nao-compila
public class Regras {
    int n = 0;

    synchronized Regras() {
    }

    void somar() {
        synchronized (n) {
            n++;
        }
    }
}
```

Na prática, prefira sincronizar num campo `private final Object trava = new Object()` em vez de `this`: assim, nenhum código externo consegue segurar a mesma trava e atrapalhar a sua classe. E nunca sincronize em literais de `String` nem em `Integer` em cache, que são compartilhados pela JVM inteira.

## wait e notify

Às vezes uma thread precisa esperar uma **condição**, como uma fila deixar de estar vazia. Os métodos `wait()`, `notify()` e `notifyAll()`, de `Object`, fazem isso usando a mesma trava: `wait()` libera a trava e dorme até ser notificado; `notifyAll()` acorda quem espera. Os três só podem ser chamados **segurando a trava** do objeto; caso contrário, lançam `IllegalMonitorStateException`. Eles são a base histórica das filas e sincronizadores, mas hoje quase sempre se usam as classes prontas de `java.util.concurrent`, como as do [episódio 4](/assistir/senior-t2-e04).

> [!PROVA]
> `contador++` não é atômico. Métodos `synchronized` de instância travam `this`; os `static`, o objeto `Class`. A exclusão só vale para a mesma trava. Travas são reentrantes. `synchronized` exige uma referência (primitivo não compila; `null` lança `NullPointerException`) e não pode marcar construtores nem métodos abstratos. `wait`/`notify` fora da trava lançam `IllegalMonitorStateException`.

## Por baixo dos panos

O bloco `synchronized` vira duas instruções de bytecode, `monitorenter` e `monitorexit`. O compilador ainda gera uma tabela de exceções que garante a liberação da trava se o bloco lançar exceção:

```text
 6: monitorenter
 7: aload_0
 8: dup
 9: getfield      #13   // Field valor:I
12: iconst_1
13: iadd
14: putfield      #13   // Field valor:I
17: aload_1
18: monitorexit
19: goto          27
22: astore_2            // caminho da exceção
23: aload_1
24: monitorexit
25: aload_2
26: athrow
```

O `contador++` aparece aqui em três instruções, `getfield`, `iadd` e `putfield`, exatamente os três passos que a condição de corrida intercala. Um método `synchronized` não gera instruções: ele recebe a marca `ACC_SYNCHRONIZED`, e a própria JVM adquire a trava ao entrar.

A trava fica no **cabeçalho** de cada objeto, numa palavra de 64 bits chamada *mark word*. Quando não há disputa, a JVM trava com uma única instrução atômica do processador (um *compare-and-swap*) sobre esse cabeçalho, sem envolver o sistema operacional. Só quando duas threads disputam de fato a trava é que ela é **inflada** para um monitor completo, com uma fila de threads bloqueadas, e a thread que espera é suspensa pelo sistema operacional. Por isso `synchronized` sem disputa é barato, e com muita disputa, caro.

## Resumo para a prova

- Condição de corrida: o resultado depende da intercalação; `x++` e "verificar e depois agir" não são atômicos
- `synchronized` dá exclusão mútua e visibilidade, para quem usa a mesma trava
- Método de instância trava `this`; `static synchronized` trava `Classe.class`; bloco trava o objeto informado
- Travas são reentrantes; `Thread.holdsLock(obj)` informa se a thread atual segura a trava
- Não compila: `synchronized` em primitivo, em construtor e em método abstrato; `synchronized (null)` lança `NullPointerException`
- `wait`, `notify` e `notifyAll` exigem a trava; sem ela, `IllegalMonitorStateException`
