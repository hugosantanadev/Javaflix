Generics existem para o compilador. Depois de conferir os tipos, o `javac` os apaga, e o bytecode volta a falar de `Object`, como antes do Java 5. Esse processo se chama **type erasure**, apagamento de tipos. Ele explica todas as restrições do [primeiro episódio](/assistir/pleno-t2-e01) e algumas das questões mais traiçoeiras da prova.

> [!ANTES]
> Antes do Java 5, toda coleção era o que hoje o apagamento produz: uma `List` de `Object`, com os casts escritos à mão. O bytecode de uma classe genérica atual é quase igual ao de 2003; a diferença é que o compilador escreve os casts por você e garante que eles não falham, a menos que um raw type ou um cast sem verificação entre no caminho.

## O que o apagamento faz

O compilador segue quatro regras:

1. Cada parâmetro de tipo vira o seu **primeiro limite**, ou `Object` se não houver limite
2. Tipos parametrizados viram raw: `List<String>` vira `List`
3. Casts são inseridos onde um valor genérico é usado com o tipo específico
4. Métodos-ponte são gerados quando preciso para manter o polimorfismo

| Declaração | Depois do apagamento |
|---|---|
| `class Caixa<T> { T valor; }` | `Object valor` |
| `class Medida<N extends Number> { N valor; }` | `Number valor` |
| `<T extends Comparable<T>> T maior(List<T> l)` | `Comparable maior(List l)` |
| `<T extends Number & Comparable<T>> T f(T t)` | `Number f(Number t)` |

> [!LAPIS]
> Escreva o apagamento de: (a) `<T extends Comparable<T>> T maior(T a, T b)`; (b) os campos de `class Par<A, B extends Number> { A primeiro; B segundo; }`; (c) `List<Map<String, Integer>> agrupar()`.
>
> **Resposta:** (a) `Comparable maior(Comparable a, Comparable b)`, pelo primeiro limite. (b) `Object primeiro; Number segundo;`. (c) `List agrupar()`: argumentos de tipo somem por inteiro, em qualquer profundidade.

Na execução, só sobra uma classe para todas as parametrizações, e com ela um único conjunto de campos estáticos:

```java executar
import java.util.ArrayList;
import java.util.List;

public class MesmaClasse {
    static class Contador<T> {
        static int criados = 0;

        Contador() {
            criados++;
        }
    }

    public static void main(String[] args) {
        List<String> textos = new ArrayList<>();
        List<Integer> numeros = new ArrayList<>();
        System.out.println(textos.getClass() == numeros.getClass()); //> Uma classe só para as duas listas.
        System.out.println(textos.getClass().getName());

        new Contador<String>();
        new Contador<Double>();
        System.out.println(Contador.criados);
    }
}
```

```saida
true
java.util.ArrayList
2
```

> [!PENSE]
> Se `List<String>` e `List<Integer>` são a mesma classe na execução, o que acontece com dois métodos `imprimir(List<String>)` e `imprimir(List<Integer>)` na mesma classe? O que sobra para distinguir um do outro no bytecode?

## Consequência 1: não há sobrecarga por parametrização

Dois métodos que só diferem no argumento de tipo ficam com a mesma assinatura depois do apagamento, e o compilador os recusa:

```java nao-compila
import java.util.List;

public class Impressora {
    void imprimir(List<String> textos) { }
    void imprimir(List<Integer> numeros) { }
}
```

A mensagem é `name clash: ... have the same erasure`. O mesmo vale entre classes: uma subclasse que declara `processar(List<Integer>)` quando a superclasse tem `processar(List<String>)` não sobrescreve nem sobrecarrega, e não compila. Mudar só o tipo de retorno também não resolve.

## Consequência 2: o tipo não existe na execução

Tudo o que precisaria conhecer `T` ou `List<String>` durante a execução é proibido:

- `obj instanceof List<String>`, quando `obj` é um `Object`; `obj instanceof List<?>` é permitido
- `List<String>.class`; só existe `List.class`
- `new T()`, `new T[n]` e `new List<String>[n]`; `new List<?>[n]` é permitido
- `catch (T e)` e classes genéricas que estendem `Throwable`

Desde o Java 16, `instanceof` aceita um tipo parametrizado quando o compilador consegue garantir o resultado: com `List<String> l`, `l instanceof ArrayList<String>` compila, porque `l` já é uma lista de `String`.

Quando um método genérico precisa do tipo na execução, a saída é recebê-lo como argumento, um **token de tipo** `Class<T>`:

```java executar
import java.lang.reflect.Array;
import java.util.ArrayList;

public class TokenDeTipo {
    static <T> T criar(Class<T> tipo) throws ReflectiveOperationException {
        return tipo.getDeclaredConstructor().newInstance();
    }

    @SuppressWarnings("unchecked")
    static <T> T[] arrayDe(Class<T> tipo, int tamanho) {
        return (T[]) Array.newInstance(tipo, tamanho); //> O token diz o tipo real do array.
    }

    public static void main(String[] args) throws ReflectiveOperationException {
        StringBuilder sb = criar(StringBuilder.class);
        sb.append("criado por reflexão");
        System.out.println(sb);

        String[] nomes = arrayDe(String.class, 3);
        System.out.println(nomes.length + " " + nomes.getClass().getSimpleName());

        ArrayList<?> lista = criar(ArrayList.class);
        System.out.println(lista.isEmpty());
    }
}
```

```saida
criado por reflexão
3 String[]
true
```

O próprio `ArrayList` faz diferente: guarda os elementos num `Object[]` e faz o cast para `E` ao devolvê-los.

## Consequência 3: poluição do heap

Um raw type, ou um cast sem verificação, deixa entrar numa `List<String>` algo que não é `String`. Nada falha na hora. O erro aparece depois, no ponto onde o compilador inseriu o cast, às vezes muito longe da causa:

```java executar
import java.util.ArrayList;
import java.util.List;

public class Poluicao {
    @SuppressWarnings({"rawtypes", "unchecked"})
    static void legado(List lista) {
        lista.add(42); //> Nada confere: o raw type aceita.
    }

    public static void main(String[] args) {
        List<String> nomes = new ArrayList<>();
        nomes.add("Ana");
        legado(nomes);
        System.out.println(nomes.size() + " " + nomes);
        Object o = nomes.get(1);
        System.out.println("como Object: " + o);
        try {
            String s = nomes.get(1);
        } catch (ClassCastException e) {
            System.out.println("ClassCastException ao ler como String");
        }
    }
}
```

```saida
2 [Ana, 42]
como Object: 42
ClassCastException ao ler como String
```

Ler como `Object` não exige cast e funciona; ler como `String` dispara o `checkcast` inserido pelo compilador. Para achar o culpado, `Collections.checkedList(lista, String.class)` devolve uma lista que confere o tipo a cada inserção, e a exceção sai no `add` errado.

O mesmo risco aparece em métodos *varargs* genéricos, como `<T> List<T> listaDe(T... itens)`: o array criado para os argumentos é de um tipo não confiável, e o compilador avisa sobre *possible heap pollution*. Quem tem certeza de que o método não abusa do array marca-o com `@SafeVarargs`, como fazem `List.of` e `Arrays.asList`.

> [!ENGENHARIA]
> Prefira listas a arrays em código genérico, a recomendação do *Effective Java*. Arrays conhecem o tipo na execução e conferem cada gravação, lançando `ArrayStoreException`; generics conferem na compilação e apagam o tipo. Misturar os dois, como em `T[]`, exige casts sem verificação, que falham longe da causa quando o array sai da classe.

> [!PROVA]
> Um tipo é **reificável** quando existe por inteiro na execução: primitivos, classes não genéricas, raw types, parametrizações só com `?` (`List<?>`) e arrays desses tipos. Só tipos reificáveis podem aparecer em `instanceof` com `Object`, em `new` de array e em `catch`.

## Pontes: como o polimorfismo sobrevive

Uma classe que implementa `Comparable<Nome>` declara `compareTo(Nome)`. Depois do apagamento, porém, a interface exige `compareTo(Object)`. Para a sobrescrita continuar funcionando, o compilador gera um **método-ponte** `compareTo(Object)`, que faz o cast e chama o seu método. A reflexão mostra os dois:

```java executar
import java.lang.reflect.Method;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public class Ponte {
    record Nome(String valor) implements Comparable<Nome> {
        @Override
        public int compareTo(Nome outro) {
            return valor.compareTo(outro.valor);
        }
    }

    public static void main(String[] args) {
        List<String> linhas = new ArrayList<>();
        for (Method m : Nome.class.getDeclaredMethods()) {
            if (m.getName().equals("compareTo")) {
                linhas.add(m.getParameterTypes()[0].getSimpleName() + " ponte=" + m.isBridge());
            }
        }
        Collections.sort(linhas);
        linhas.forEach(System.out::println);
    }
}
```

```saida
Nome ponte=false
Object ponte=true
```

É a ponte que lança `ClassCastException` quando alguém, por um raw `Comparable`, chama `compareTo("texto")` num `Nome`. No stack trace, ela aparece como `Nome.compareTo` apontando para a linha da declaração da classe, já que não existe no código-fonte.

> [!PERGUNTAS]
> **P:** O apagamento deixa o programa mais lento?
>
> **R:** Não. Os casts inseridos são baratos, e não há uma cópia do código por tipo. O custo que existe é outro: o *boxing* de `List<Integer>`, porque `T` não pode ser primitivo.
>
> **P:** Posso chamar um método-ponte?
>
> **R:** Não pelo código-fonte: ele é sintético. Aparece na reflexão, com `isBridge()`, no `javap` e nos stack traces.
>
> **P:** O Kotlin escapa do apagamento?
>
> **R:** Na JVM, não: o apagamento é da plataforma. O Kotlin oferece `reified` em funções `inline`, que copiam o corpo da função em cada chamada e, com isso, conhecem o tipo ali.

> [!MATEMATICA]
> Por que não existe `instanceof List<String>` na execução: para responder, a JVM teria de olhar todos os elementos da lista, um trabalho O(*n*). Numa lista de 1 milhão de itens, seria 1 milhão de verificações, e a resposta ainda poderia mudar no próximo `add`. Arrays fazem o contrário: guardam o tipo do componente e conferem cada gravação em O(1), uma comparação por elemento gravado.

> [!IA]
> Ao explicar o apagamento, assistentes de IA costumam dizer que generics "não existem no bytecode", e erram: o atributo `Signature` guarda os tipos das declarações, e é por isso que o `TypeReference` do Jackson funciona. Também sugerem `(T[]) new Object[n]` para criar arrays genéricos, que compila e explode com `ClassCastException` quando o array sai da classe.

## Na IDE

- **Ver o bytecode.** No IntelliJ, *View > Show Bytecode* mostra o código compilado da classe aberta, com os `checkcast` inseridos e os métodos-ponte marcados como `ACC_BRIDGE`.
- **Casts sem verificação.** A IDE sublinha em amarelo casts como `(T[]) new Object[n]`, com o mesmo aviso que o `javac` dá com `-Xlint:unchecked`.
- **Achar a poluição.** No depurador, a aba *Variables* mostra a classe real de cada elemento: um `Integer` dentro de uma `List<String>` aparece com o nome da classe errada.

## Por baixo dos panos

O apagamento não é total. O atributo `Signature` do arquivo `.class` guarda os tipos genéricos das **declarações**: de campos, de métodos e da superclasse. Um objeto `ArrayList<String>` não sabe que guarda `String`, mas uma classe declarada como `extends ArrayList<String>` sabe, e a reflexão consegue ler:

```java executar
import java.lang.reflect.ParameterizedType;
import java.util.ArrayList;
import java.util.List;

public class TipoQueSobrevive {
    static abstract class Referencia<T> {
        String tipo() {
            ParameterizedType p = (ParameterizedType) getClass().getGenericSuperclass();
            return p.getActualTypeArguments()[0].getTypeName();
        }
    }

    static class ListaDeTextos extends ArrayList<String> { }

    public static void main(String[] args) {
        System.out.println(new Referencia<List<Integer>>() { }.tipo());
        System.out.println(ListaDeTextos.class.getGenericSuperclass().getTypeName());
    }
}
```

```saida
java.util.List<java.lang.Integer>
java.util.ArrayList<java.lang.String>
```

As chaves `{ }` depois de `new Referencia<List<Integer>>()` criam uma subclasse anônima, e a declaração dela grava `List<Integer>` no `.class`. É o truque do *super type token*, usado pelo `TypeReference` do Jackson e pelo `TypeToken` do Gson para desserializar JSON em tipos genéricos.

Por que apagar? Em 2004, havia milhões de linhas compiladas usando `List` sem tipo. Com o apagamento, uma biblioteca podia adotar generics sem quebrar os binários dos clientes, e cada projeto migrava no seu ritmo. Brian Goetz, arquiteto da linguagem, conta a decisão no texto *In Defense of Erasure*. O C# escolheu o caminho oposto e precisou criar uma segunda biblioteca de coleções. O preço do Java são as restrições desta aula, e o Projeto Valhalla estuda como permitir `List<int>` no futuro sem abrir mão da compatibilidade.

## Resumo para a prova

- `T` vira o primeiro limite, ou `Object`; `List<String>` vira `List`
- Uma única classe e um único conjunto de campos `static` para todas as parametrizações
- Métodos que só diferem no argumento de tipo não compilam: mesmo apagamento
- Proibido: `instanceof List<String>` a partir de `Object`, `List<String>.class`, `new T()`, `new T[]`, `new List<String>[]`
- Poluição do heap: o erro aparece no cast inserido pelo compilador, não onde o valor errado entrou
- Métodos-ponte mantêm a sobrescrita depois do apagamento
