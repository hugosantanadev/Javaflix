Não são só classes que têm parâmetros de tipo. Um método pode declarar os seus próprios, e a biblioteca padrão está cheia deles: `List.of`, `Arrays.asList`, `Collections.sort` e `Optional.of` são métodos genéricos. Este episódio mostra como declará-los, onde fica o `<T>` (a prova testa a posição) e como o compilador descobre sozinho o tipo de cada chamada.

## Declarando um método genérico

A lista de parâmetros de tipo vem **depois dos modificadores e antes do tipo de retorno**. A partir dali, o método pode usar `T` no retorno, nos parâmetros e no corpo:

```java executar
import java.util.List;

public class Utilitarios {
    static <T> T ultimo(List<T> lista) {
        return lista.get(lista.size() - 1);
    }

    static <K, V> String descrever(K chave, V valor) {
        return chave + " -> " + valor;
    }

    public static void main(String[] args) {
        String nome = ultimo(List.of("Ana", "Bia", "Caio"));
        int numero = ultimo(List.of(3, 1, 4));
        System.out.println(nome + " " + numero);
        System.out.println(descrever("pi", 3.14));
    }
}
```

```saida
Caio 4
pi -> 3.14
```

A mesma chamada `ultimo` devolve `String` numa linha e `Integer` na outra, sem cast. A posição do `<T>` é rígida:

| Declaração | Compila? |
|---|---|
| `public static <T> T ultimo(List<T> l)` | Sim |
| `static public <T> T ultimo(List<T> l)` | Sim, a ordem dos modificadores é livre |
| `public <T> void imprimir(T t)` | Sim, método de instância |
| `public static T <T> ultimo(List<T> l)` | Não, o `<T>` veio depois do retorno |
| `<T> public static T ultimo(List<T> l)` | Não, o `<T>` veio antes dos modificadores |

```java nao-compila
public class Ordem {
    <T> public static T primeiro(T a) {
        return a;
    }
}
```

## Métodos genéricos dentro de classes genéricas

Um método `static` não enxerga o `T` da classe, porque não pertence a nenhuma instância parametrizada. Se ele precisa de um tipo, declara o seu. É o caso das *fábricas estáticas*, como `Caixa.de(valor)`. Já um método de instância pode **somar** um parâmetro novo aos da classe, como `R` em `mapear`:

```java executar
import java.util.function.Function;

public class Transformacoes {
    static class Caixa<T> {
        private final T valor;

        Caixa(T valor) {
            this.valor = valor;
        }

        static <T> Caixa<T> de(T valor) {
            return new Caixa<>(valor);
        }

        <R> Caixa<R> mapear(Function<T, R> funcao) {
            return new Caixa<>(funcao.apply(valor));
        }

        T valor() {
            return valor;
        }
    }

    public static void main(String[] args) {
        Caixa<String> nome = Caixa.de("generics");
        Caixa<Integer> tamanho = nome.mapear(String::length);
        Caixa<Boolean> grande = tamanho.mapear(n -> n > 5);
        System.out.println(nome.valor() + " " + tamanho.valor() + " " + grande.valor());
    }
}
```

```saida
generics 8 true
```

O `<T>` de `de` é outro `T`, sem relação com o da classe. Ele só tem o mesmo nome por convenção. Sem a declaração própria, `static Caixa<T> de(T valor)` não compila: `non-static type variable T cannot be referenced from a static context`.

## A sombra: um T que esconde outro

Num método de **instância**, redeclarar `<T>` cria um tipo novo que esconde o da classe. O código parece certo, mas os dois `T` são diferentes, e o compilador recusa misturá-los:

```java nao-compila
public class Caixa<T> {
    private T valor;

    <T> T trocar(T novo) {
        T antigo = valor;
        return novo;
    }
}
```

A mensagem fala em `T#1` e `T#2`, um para cada declaração. A correção é tirar o `<T>` do método.

## Inferência: o compilador descobre o tipo

Quase nunca se escreve o argumento de tipo de um método genérico. O compilador o **infere** a partir de três fontes: os argumentos da chamada, o tipo esperado no destino (o lado esquerdo de uma atribuição, o retorno, o parâmetro de outro método) e as lambdas. Quando os argumentos têm tipos diferentes, ele procura o supertipo comum mais específico:

```java executar
import java.util.Collections;
import java.util.List;

public class Inferencia {
    static <T> T escolher(boolean primeiro, T a, T b) {
        return primeiro ? a : b;
    }

    static int contar(List<String> nomes) {
        return nomes.size();
    }

    public static void main(String[] args) {
        String texto = escolher(true, "sim", "não");
        Number numero = escolher(false, 1, 2.5);
        var misturado = escolher(true, "a", 1);
        System.out.println(texto + " " + numero + " " + misturado);
        System.out.println(contar(Collections.emptyList()));
    }
}
```

```saida
sim 2.5 a
0
```

Para `escolher(false, 1, 2.5)`, o destino `Number` resolve: `T` é `Number`. Para `escolher(true, "a", 1)` com `var`, o compilador calcula um **tipo interseção**, algo como `Object & Serializable & Comparable<...>`, os supertipos que `String` e `Integer` têm em comum. A variável só oferece os métodos dessa interseção:

```java nao-compila
public class Mistura {
    static <T> T escolher(T a, T b) {
        return a;
    }

    public static void main(String[] args) {
        var x = escolher("a", 1);
        System.out.println(x.length());
    }
}
```

> [!ATENCAO]
> Dentro de `escolher`, `primeiro ? a : b` opera sobre `T`, não sobre números. Por isso `escolher(true, 1, 2.5)` devolve o `Integer` 1, enquanto a expressão direta `true ? 1 : 2.5` promove para `double` e vale `1.0`.

## Testemunha de tipo explícita

Quando a inferência não basta, ou para forçar um tipo, você passa o argumento de tipo explicitamente, entre o ponto e o nome do método. Isso exige algo antes do ponto: o nome da classe, para métodos estáticos, ou `this`, para métodos de instância.

```java compila
import java.util.List;

public class Testemunha {
    static <T> T primeiro(List<T> lista) {
        return lista.get(0);
    }

    <T> T ultimo(List<T> lista) {
        return lista.get(lista.size() - 1);
    }

    void usar(List<String> nomes) {
        String a = Testemunha.<String>primeiro(nomes);
        String b = this.<String>ultimo(nomes);
        Object c = Testemunha.<Object>primeiro(List.of(1, "dois"));
    }
}
```

`<String>primeiro(nomes)`, sem o qualificador, não compila. Construtores também podem ser genéricos, com a testemunha logo depois do `new` (`new <String>Etiqueta("ok")`), mas isso é raro fora da prova.

> [!PROVA]
> Três coisas caem juntas: a posição do `<T>` (depois dos modificadores, antes do retorno), a sombra de um `<T>` de método sobre o da classe e a testemunha explícita, que exige `Classe.` ou `this.` antes dela.

## Por baixo dos panos

A inferência acontece só na compilação. O capítulo 18 da especificação a descreve como um sistema de restrições: cada parâmetro de tipo vira uma *variável de inferência*, cada argumento e o destino geram limites, e o compilador resolve o sistema. Esse algoritmo foi reescrito no Java 8 pela JEP 101, *Generalized Target-Type Inference*. Antes dela, `contar(Collections.emptyList())` não compilava: o compilador não olhava para o parâmetro de `contar` e deduzia `List<Object>`. Era preciso escrever `Collections.<String>emptyList()`.

Como o tipo some depois da compilação, um único objeto pode servir a todos os `T`. `Collections.emptyList()` devolve sempre a mesma lista imutável:

```java executar
import java.util.Collections;
import java.util.List;

public class UmaSoLista {
    public static void main(String[] args) {
        List<String> textos = Collections.emptyList();
        List<Integer> numeros = Collections.emptyList();
        System.out.println((Object) textos == numeros);
    }
}
```

```saida
true
```

O cast para `Object` é necessário: comparar `textos == numeros` diretamente não compila (`incomparable types`), porque o compilador sabe que `List<String>` e `List<Integer>` são tipos distintos. Na execução, porém, os dois são a mesma referência.

## Resumo para a prova

- O `<T>` do método vem depois dos modificadores e antes do tipo de retorno
- Métodos `static` não usam o `T` da classe; declaram o próprio
- Um `<T>` em método de instância esconde o `T` da classe
- A inferência usa os argumentos, o destino e as lambdas; com tipos diferentes, chega a uma interseção
- Testemunha explícita: `Classe.<Tipo>metodo()` ou `this.<Tipo>metodo()`, nunca sem qualificador
- Desde o Java 8, o tipo do parâmetro que recebe a chamada também entra na inferência
