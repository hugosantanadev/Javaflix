O [episódio anterior](/assistir/pleno-t2-e04) usou wildcards em variáveis e parâmetros. Este junta as peças que faltam: **limites nos parâmetros de tipo** (`<T extends Number>`), os limites recursivos de `Comparable` e a regra que decide entre `extends` e `super` em qualquer assinatura, o PECS. É o conteúdo que separa quem usa a API de coleções de quem entende por que ela é declarada daquele jeito.

## Limites em parâmetros de tipo

`<T extends Number>` restringe `T` a `Number` e seus subtipos. Em troca, dentro do código, `T` ganha os métodos de `Number`. Aqui, `extends` vale tanto para classes quanto para interfaces:

```java executar
import java.util.List;

public class Limites {
    static class Estatistica<N extends Number> {
        private final List<N> valores;

        Estatistica(List<N> valores) {
            this.valores = valores;
        }

        double media() {
            double soma = 0;
            for (N n : valores) {
                soma += n.doubleValue();
            }
            return soma / valores.size();
        }
    }

    static <T extends Comparable<T>> T maior(T a, T b) {
        return a.compareTo(b) >= 0 ? a : b;
    }

    public static void main(String[] args) {
        System.out.println(new Estatistica<>(List.of(7, 8, 10)).media());
        System.out.println(new Estatistica<>(List.of(2.5, 3.5)).media());
        System.out.println(maior("abacaxi", "banana") + " " + maior(3, 7));
    }
}
```

```saida
8.333333333333334
3.0
banana 7
```

Um argumento fora do limite não compila: `type argument String is not within bounds of type-variable N`.

```java nao-compila
public class ForaDoLimite {
    static class Medida<N extends Number> {
        N valor;
    }

    public static void main(String[] args) {
        Medida<String> m = new Medida<>();
    }
}
```

E `maior(1, 2.5)` também não: `T` precisaria ser `Integer` e `Double` ao mesmo tempo, e nenhum dos dois é `Comparable` do outro.

## Vários limites

Um parâmetro pode ter vários limites separados por `&`. No máximo um deles é classe, e ela vem **primeiro**; os demais são interfaces. O apagamento usa o primeiro limite.

| Declaração | Compila? |
|---|---|
| `<T extends Number & Comparable<T>>` | Sim |
| `<T extends Comparable<T> & Serializable>` | Sim, duas interfaces |
| `<T extends Runnable>` | Sim, `extends` também serve para interface |
| `<T extends Comparable<T> & Number>` | Não, a classe precisa vir primeiro |
| `<T extends Number & Integer>` | Não, só pode haver uma classe |
| `<T super Integer>` | Não, `super` só existe em wildcards |

```java nao-compila
public class OrdemDosLimites {
    static <T extends Comparable<T> & Number> T menor(T a, T b) {
        return a.compareTo(b) <= 0 ? a : b;
    }
}
```

A mensagem é `interface expected here`: depois do `&`, o compilador espera interfaces.

## Limites recursivos e o problema das subclasses

`<T extends Comparable<T>>` diz "um `T` que sabe se comparar com outro `T`". Funciona para `String` e `Integer`, mas falha numa situação comum: uma subclasse que herda o `compareTo` do pai. `Maca` estende `Fruta`, que implementa `Comparable<Fruta>`. Então `Maca` é `Comparable<Fruta>`, não `Comparable<Maca>`:

```java nao-compila
import java.util.List;

public class SemSuper {
    static class Fruta implements Comparable<Fruta> {
        int peso;

        public int compareTo(Fruta outra) {
            return Integer.compare(peso, outra.peso);
        }
    }

    static class Maca extends Fruta { }

    static <T extends Comparable<T>> T maior(List<T> itens) {
        return itens.get(0);
    }

    static void testar(List<Maca> macas) {
        Maca m = maior(macas);
    }
}
```

A correção é aceitar um `Comparable` de **qualquer supertipo** de `T`: `<T extends Comparable<? super T>>`. É assim que `Collections.sort` e `Collections.max` são declarados:

```java executar
import java.util.List;

public class ComSuper {
    static class Fruta implements Comparable<Fruta> {
        final String nome;
        final int peso;

        Fruta(String nome, int peso) {
            this.nome = nome;
            this.peso = peso;
        }

        public int compareTo(Fruta outra) {
            return Integer.compare(peso, outra.peso);
        }
    }

    static class Maca extends Fruta {
        Maca(String nome, int peso) {
            super(nome, peso);
        }
    }

    static <T extends Comparable<? super T>> T maior(List<? extends T> itens) {
        T melhor = itens.get(0);
        for (T item : itens) {
            if (item.compareTo(melhor) > 0) {
                melhor = item;
            }
        }
        return melhor;
    }

    public static void main(String[] args) {
        List<Maca> macas = List.of(new Maca("gala", 150), new Maca("fuji", 210), new Maca("verde", 180));
        Maca pesada = maior(macas);
        System.out.println(pesada.nome);
    }
}
```

```saida
fuji
```

O mesmo padrão aparece em `Enum<E extends Enum<E>>`: é ele que faz `compareTo` de um enum aceitar só constantes do mesmo enum.

## PECS: Producer Extends, Consumer Super

Joshua Bloch resumiu a escolha entre os wildcards numa sigla. Olhe cada parâmetro do ponto de vista do método:

- Se ele **produz** valores de `T` para o método, que só os lê, use `? extends T`
- Se ele **consome** valores de `T`, que o método escreve ou entrega a ele, use `? super T`
- Se faz as duas coisas, use o tipo exato `T`

A biblioteca padrão segue a regra à risca:

| Método | Assinatura | Quem produz, quem consome |
|---|---|---|
| `Collections.copy` | `(List<? super T> dest, List<? extends T> src)` | `src` produz, `dest` consome |
| `Collection.addAll` | `(Collection<? extends E> c)` | `c` produz |
| `List.sort` | `(Comparator<? super E> c)` | o comparador consome elementos |
| `Iterable.forEach` | `(Consumer<? super T> action)` | a ação consome |
| `Stream.map` | `(Function<? super T, ? extends R> mapper)` | consome `T`, produz `R` |

Na prática, isso significa que um `Comparator<Object>` ordena uma `List<Integer>` e um `Consumer<Object>` percorre qualquer lista:

```java executar
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;
import java.util.function.Consumer;

public class Pecs {
    static <T> void copiar(List<? super T> destino, List<? extends T> origem) {
        for (T item : origem) {
            destino.add(item);
        }
    }

    public static void main(String[] args) {
        List<Number> numeros = new ArrayList<>();
        copiar(numeros, List.of(1, 2));
        copiar(numeros, List.of(3.5));
        System.out.println(numeros);

        Comparator<Object> porTexto = Comparator.comparing(Object::toString);
        List<Integer> inteiros = new ArrayList<>(List.of(10, 9, 100));
        inteiros.sort(porTexto);

        Consumer<Object> imprimir = o -> System.out.print("<" + o + ">");
        inteiros.forEach(imprimir);
        System.out.println();
    }
}
```

```saida
[1, 2, 3.5]
<10><100><9>
```

Comparados como texto, "10" vem antes de "100", que vem antes de "9".

> [!PROVA]
> Diante de uma assinatura com wildcards, pergunte o que o método faz com cada parâmetro. Lê? `extends`. Escreve ou entrega valores? `super`. E lembre que `Comparator`, `Consumer` e `Predicate` **consomem**: por isso aparecem com `? super T`.

## Wildcard ou parâmetro de tipo?

Muitas assinaturas podem ser escritas das duas formas. `<T> void copiar(List<? super T> d, List<? extends T> o)` equivale a `<T, S extends T> void copiar(List<T> d, List<S> o)`. Algumas diretrizes:

- Se um parâmetro de tipo aparece **uma só vez** na assinatura, troque-o por um wildcard: `void imprimir(List<?> l)` em vez de `<T> void imprimir(List<T> l)`
- Se é preciso relacionar dois parâmetros, ou um parâmetro e o retorno, use um `T` com nome
- Não use wildcards no **tipo de retorno**: quem chama teria de lidar com eles

## Por baixo dos panos

A assinatura de `Collections.max` parece ter um limite inútil:

```java executar
import java.lang.reflect.Method;
import java.util.Collection;
import java.util.Collections;

public class AssinaturaDoMax {
    public static void main(String[] args) throws NoSuchMethodException {
        Method max = Collections.class.getMethod("max", Collection.class);
        System.out.println(max.getReturnType().getSimpleName());
        System.out.println(max.toGenericString());
    }
}
```

```saida
Object
public static <T extends java.lang.Object & java.lang.Comparable<? super T>> T java.util.Collections.max(java.util.Collection<? extends T>)
```

Todo tipo já estende `Object`, então `T extends Object & Comparable<...>` diz o mesmo que `T extends Comparable<...>` para o compilador. A diferença está no apagamento, que usa o **primeiro** limite. Com `Object` na frente, o método compilado devolve `Object`, exatamente como o `max` do Java 1.4. Sem ele, devolveria `Comparable`, e todo programa compilado antes do Java 5 que chamasse `Collections.max` quebraria com `NoSuchMethodError`. É o apagamento a serviço da compatibilidade, de novo.

O padrão `T extends Comparable<T>`, em que o tipo aparece no próprio limite, tem nome na teoria de tipos: *F-bounded polymorphism*, descrito em 1989 por Canning, Cook, Hill, Olthoff e Mitchell, anos antes do lançamento do Java.

## Resumo para a prova

- `<T extends X>` aceita `X` e subtipos; `extends` serve para classe e interface
- Vários limites: `<T extends Classe & Interface1 & Interface2>`, com a classe primeiro e no máximo uma
- `super` nunca aparece em declaração de parâmetro de tipo
- `<T extends Comparable<? super T>>` aceita subclasses que herdam o `compareTo` do pai
- PECS: quem produz usa `extends`, quem consome usa `super`; `Comparator`, `Consumer` e `Predicate` consomem
- O apagamento usa o primeiro limite, e por isso `Collections.max` começa com `Object &`
