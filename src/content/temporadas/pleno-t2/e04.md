Um `Integer` é um `Number`. Mesmo assim, uma `List<Integer>` **não** é uma `List<Number>`. Essa é a regra de generics que mais surpreende, e os wildcards (`?`, `? extends` e `? super`) existem para contorná-la com segurança. Na prova, eles aparecem em questões de "qual linha compila" que exigem conferir cada atribuição e cada `add` com cuidado.

> [!ANTES]
> Antes do Java 5, a única coleção com tipo era o array, covariante desde o Java 1.0. Sem generics, era o jeito de escrever métodos como `Arrays.sort(Object[])` e `Arrays.equals(Object[], Object[])` para arrays de qualquer tipo. O preço dessa escolha é a `ArrayStoreException`, que existe até hoje. Os wildcards, do Java 5, deram às coleções a mesma flexibilidade com a verificação feita pelo compilador.

## Invariância: por que List<Integer> não é List<Number>

Imagine que fosse permitido. Bastaria uma referência mais geral para colocar um `Double` numa lista de inteiros:

```java nao-compila
import java.util.ArrayList;
import java.util.List;

public class Invariancia {
    public static void main(String[] args) {
        List<Integer> inteiros = new ArrayList<>();
        List<Number> numeros = inteiros;
        numeros.add(2.5);
    }
}
```

Por isso tipos genéricos são **invariantes**: `List<A>` e `List<B>` não têm relação de herança, mesmo que `A` estenda `B`. Arrays fizeram a escolha oposta, são **covariantes**, e pagam com uma verificação na execução:

```java executar
public class Covariancia {
    public static void main(String[] args) {
        Integer[] inteiros = {1, 2, 3};
        Number[] numeros = inteiros; //> Arrays são covariantes: compila.
        System.out.println(numeros[0]);
        try {
            numeros[1] = 2.5;
        } catch (ArrayStoreException e) {
            System.out.println("ArrayStoreException: " + e.getMessage());
        }
    }
}
```

```saida
1
ArrayStoreException: java.lang.Double
```

O array sabe o tipo dos seus elementos na execução e recusa o `Double`. Uma lista genérica não sabe, por causa do [apagamento](/assistir/pleno-t2-e03), então a proteção precisa vir do compilador.

## Os três wildcards

Um wildcard, ou coringa, troca um tipo exato por uma família de tipos. Ele só aparece no **uso** de um tipo genérico, em variáveis, parâmetros e retornos:

| Forma | Aceita | Lê como | Pode adicionar |
|---|---|---|---|
| `List<?>` | Qualquer lista | `Object` | Só `null` |
| `List<? extends Number>` | `List<Number>`, `List<Integer>`, `List<Double>`... | `Number` | Só `null` |
| `List<? super Integer>` | `List<Integer>`, `List<Number>`, `List<Object>` | `Object` | `Integer` e subclasses |

> [!PENSE]
> Em `List<? extends Number>`, por que não dá para adicionar um `Integer`, se um `Integer` é um `Number`? Pense no pior caso: que lista pode estar do outro lado da variável?

## Coringa sem limite: List<?>

`List<?>` significa "lista de algum tipo que não sei qual é". Serve para métodos que não dependem do tipo dos elementos. Ela é diferente de `List<Object>`, que é invariante como qualquer outra e só aceita exatamente `List<Object>`:

```java executar
import java.util.Arrays;
import java.util.List;

public class SemLimite {
    static int contarNulos(List<?> lista) { //> Aceita lista de qualquer tipo.
        int n = 0;
        for (Object item : lista) {
            if (item == null) {
                n++;
            }
        }
        return n;
    }

    public static void main(String[] args) {
        List<String> nomes = Arrays.asList("Ana", null, "Caio");
        List<Integer> notas = Arrays.asList(null, null, 7);
        System.out.println(contarNulos(nomes) + " " + contarNulos(notas));
    }
}
```

```saida
1 2
```

Se o parâmetro fosse `List<Object>`, nenhuma das duas chamadas compilaria. Dentro do método, os elementos são lidos como `Object`, e o único valor que se pode adicionar é `null`, que pertence a todo tipo.

> [!ERRO]
> Declarar o parâmetro como `List<Object>` achando que ele aceita qualquer lista. A chamada com uma `List<String>` falha com `incompatible types: List<String> cannot be converted to List<Object>`. Para um método que só lê os elementos como objetos, o tipo certo é `List<?>`.

## Limite superior: ? extends

`List<? extends Number>` é "lista de `Number` ou de algum subtipo". Qualquer elemento lido é, com certeza, um `Number`, então dá para **ler** com esse tipo. Mas não dá para **escrever**: a lista pode ser de `Double`, e o compilador não aceita colocar um `Integer` nela.

```java executar
import java.util.List;

public class LimiteSuperior {
    static double soma(List<? extends Number> numeros) {
        double total = 0;
        for (Number n : numeros) {
            total += n.doubleValue();
        }
        return total;
    }

    public static void main(String[] args) {
        List<Integer> inteiros = List.of(1, 2, 3);
        List<Double> precos = List.of(9.5, 0.5);
        System.out.println(soma(inteiros) + " " + soma(precos));
    }
}
```

```saida
6.0 10.0
```

```java nao-compila
import java.util.ArrayList;
import java.util.List;

public class SemEscrita {
    public static void main(String[] args) {
        List<? extends Number> numeros = new ArrayList<Integer>();
        numeros.add(3);
    }
}
```

A mensagem fala de `CAP#1`, o nome que o compilador dá ao tipo desconhecido: `int cannot be converted to CAP#1`.

## Limite inferior: ? super

`List<? super Integer>` é "lista de `Integer` ou de algum supertipo". O inverso do caso anterior: dá para **escrever** um `Integer`, porque cabe em qualquer uma dessas listas, mas a leitura só garante `Object`.

```java executar
import java.util.ArrayList;
import java.util.List;

public class LimiteInferior {
    static void preencher(List<? super Integer> destino, int quantos) {
        for (int i = 1; i <= quantos; i++) {
            destino.add(i * 10); //> Um Integer cabe em qualquer lista de supertipo.
        }
    }

    public static void main(String[] args) {
        List<Number> numeros = new ArrayList<>();
        List<Object> coisas = new ArrayList<>();
        coisas.add("início");
        preencher(numeros, 2);
        preencher(coisas, 3);
        Object primeiro = coisas.get(0);
        System.out.println(numeros + " " + coisas + " " + primeiro);
    }
}
```

```saida
[10, 20] [início, 10, 20, 30] início
```

Uma `List<Double>` não poderia ser passada a `preencher`: `Double` não é supertipo de `Integer`. E `Integer x = destino.get(0)` não compilaria dentro do método, porque a lista pode ser de `Object`.

> [!CONVERSA]
> **? extends Number:** Comigo você lê tranquilo: tudo o que sai é um `Number`.
>
> **? super Integer:** Comigo você escreve tranquilo: todo `Integer` cabe.
>
> **? extends Number:** Mas quem tenta escrever em mim leva um não do compilador. Eu posso ser uma lista de `Double`.
>
> **? super Integer:** E quem lê de mim só recebe `Object`. Eu posso ser uma lista de `Object`.
>
> **? extends Number:** Então dividimos o trabalho: eu para quem produz dados, você para quem consome. O próximo episódio dá um nome a isso.

> [!PROVA]
> Para cada linha, pergunte: **qual é o pior caso?** Em `? extends Number`, o pior caso para escrever é uma lista de um subtipo que você não conhece, então nada entra. Em `? super Integer`, o pior caso para ler é uma `List<Object>`, então só sai `Object`. Em `? super IOException`, `add(new FileNotFoundException())` compila, e `add(new Exception())` não.

## Quais atribuições valem

Com os wildcards, as parametrizações ganham uma hierarquia própria. Todas estas linhas compilam:

```java compila
import java.util.ArrayList;
import java.util.List;

public class Atribuicoes {
    void exemplos() {
        List<? extends Number> a = new ArrayList<Integer>();
        List<? extends Number> b = new ArrayList<Number>();
        List<? super Integer> c = new ArrayList<Number>();
        List<? super Integer> d = new ArrayList<Object>();
        List<?> e = new ArrayList<String>();
        List<? extends Object> f = new ArrayList<String>();
        List<? extends Integer> g = new ArrayList<Integer>();
        List<? extends Number> h = g;
    }
}
```

Já `List<? super Number> x = new ArrayList<Integer>()` não compila: `Integer` não é supertipo de `Number`. E `List<?>` e `List<? extends Object>` são equivalentes.

> [!LAPIS]
> Compila ou não? (a) `List<? extends Number> a = new ArrayList<Double>();` (b) `List<? super Double> b = new ArrayList<Number>();` (c) `List<? super Number> c = new ArrayList<Double>();` (d) `List<?> d = new ArrayList<? extends Number>();`
>
> **Resposta:** (a) Compila: `Double` é subtipo de `Number`. (b) Compila: `Number` é supertipo de `Double`. (c) Não compila: `Double` não é supertipo de `Number`. (d) Não compila: o coringa não entra na criação do objeto.

> [!MATEMATICA]
> Quantas listas um parâmetro aceita: `List<Number>` aceita exatamente 1 parametrização. `Number` tem 14 subclasses diretas no JDK, de `Integer` e `Long` a `BigDecimal` e `AtomicInteger`, então `List<? extends Number>` aceita pelo menos 1 + 14 = **15**, mais qualquer subclasse sua. Sem o coringa, seriam 15 métodos sobrecarregados, que nem compilariam juntos: todos teriam o mesmo apagamento, `List`.

## Onde o coringa não entra

O `?` descreve um tipo desconhecido, então não pode aparecer onde é preciso um tipo concreto:

- Na criação de objetos: `new ArrayList<?>()` e `new ArrayList<? extends Number>()` não compilam
- Na declaração de parâmetros de tipo: `class Caixa<?>` não compila
- Na lista de supertipos: `class X implements Comparable<?>` não compila
- Como testemunha explícita: `Util.<?>metodo()` não compila

## Captura de coringa

Às vezes um método com `List<?>` precisa escrever na lista um valor que veio dela mesma, como numa troca de posições. O compilador recusa, porque não sabe que os dois `?` são o mesmo tipo. A saída é um método auxiliar genérico que **captura** o coringa num `T` com nome:

```java executar
import java.util.ArrayList;
import java.util.List;

public class Troca {
    static void trocar(List<?> lista, int i, int j) {
        trocarAjudante(lista, i, j);
    }

    private static <T> void trocarAjudante(List<T> lista, int i, int j) {
        T temp = lista.get(i); //> Com o T capturado, ler e escrever é seguro.
        lista.set(i, lista.get(j));
        lista.set(j, temp);
    }

    public static void main(String[] args) {
        List<String> letras = new ArrayList<>(List.of("a", "b", "c"));
        trocar(letras, 0, 2);
        List<Integer> numeros = new ArrayList<>(List.of(1, 2));
        trocar(numeros, 0, 1);
        System.out.println(letras + " " + numeros);
    }
}
```

```saida
[c, b, a] [2, 1]
```

A API pública fica simples, com `List<?>`, e o auxiliar faz o trabalho com o tipo capturado.

> [!IA]
> Assistentes de IA confundem as direções: sugerem `? extends` num parâmetro em que o método escreve, ou trocam `List<?>` por `List<Object>` "para simplificar", o que quebra as chamadas com `List<String>`. Para cada parâmetro, pergunte se o método lê dele, escreve nele ou faz os dois, e confira a sugestão da IA contra essa resposta.

## Na IDE

- **Ver o tipo capturado.** `Ctrl+Shift+P` sobre uma expressão `List<?>` mostra o tipo com `capture of ?`, o mesmo `CAP#1` das mensagens do `javac`.
- **Sugestão de coringa.** A inspeção *Can use bounded wildcard*, desligada por padrão, aponta parâmetros que só leem ou só escrevem e sugere `? extends` ou `? super`.
- **A família de tipos.** `Ctrl+H` sobre `Number` mostra as subclasses que um `? extends Number` aceita.

## Por baixo dos panos

A cada uso de uma expressão do tipo `List<?>`, o compilador aplica a **conversão de captura** (JLS 5.1.10): inventa um tipo novo, sem nome no código, que representa aquele `?`. É o `CAP#1` das mensagens de erro, ou `capture#1-of ?` em outras ferramentas. Dois usos geram duas capturas diferentes, e por isso `lista.set(i, lista.get(j))` falha: o valor lido é do `CAP#1` de uma leitura, e o `set` espera o de outra.

O Java decide a variância **no uso** (*use-site variance*): quem escreve `List<? extends Number>` escolhe, em cada variável, se quer ler ou escrever. Kotlin, C# e Scala permitem decidir **na declaração** (*declaration-site variance*): em Kotlin, `interface Fonte<out T>` torna toda `Fonte<Integer>` uma `Fonte<Number>`, sem coringa nenhum. Como o apagamento, os wildcards somem no bytecode, e `List<? extends Number>` vira só `List`.

O sistema também tem limites conhecidos. Em 2016, Nada Amin e Ross Tate publicaram *Java and Scala's Type Systems are Unsound*, mostrando que a combinação de wildcards com `null` permite escrever um programa sem casts e sem raw types que compila e lança `ClassCastException`. O caso é artificial e não afeta código do dia a dia.

## Resumo para a prova

- Generics são invariantes: `List<Integer>` não é `List<Number>`; arrays são covariantes e lançam `ArrayStoreException`
- `List<?>`: aceita qualquer lista, lê `Object`, só adiciona `null`; é diferente de `List<Object>`
- `? extends T`: lê como `T`, não adiciona nada além de `null`
- `? super T`: adiciona `T` e subtipos, lê como `Object`
- Coringa não entra em `new`, em declaração de parâmetro de tipo, em supertipo nem em testemunha
- Um método auxiliar genérico captura o coringa quando é preciso ler e escrever
