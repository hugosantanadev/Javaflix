Até o Java 5, uma `List` guardava `Object`, e quem lia um elemento precisava fazer cast torcendo para acertar o tipo. Generics trocaram essa torcida por uma verificação do compilador: você declara o que a coleção guarda, e o erro aparece na compilação, não em produção. Esta temporada cobre como declarar e usar tipos genéricos, o que acontece com eles depois de compilados e os wildcards, o assunto que mais derruba candidatos na prova.

## O problema que generics resolvem

Sem generics, a lista aceita qualquer coisa, e o erro só aparece quando alguém tenta usar o elemento:

```java executar
import java.util.ArrayList;
import java.util.List;

public class SemGenerics {
    public static void main(String[] args) {
        List nomes = new ArrayList();
        nomes.add("Ana");
        nomes.add(42);
        for (Object o : nomes) {
            try {
                String nome = (String) o;
                System.out.println(nome.toUpperCase());
            } catch (ClassCastException e) {
                System.out.println("não era texto: " + o);
            }
        }
    }
}
```

```saida
ANA
não era texto: 42
```

Com o tipo declarado, o mesmo engano nem compila, e o cast desaparece do código:

```java nao-compila
import java.util.ArrayList;
import java.util.List;

public class ComGenerics {
    public static void main(String[] args) {
        List<String> nomes = new ArrayList<>();
        nomes.add("Ana");
        nomes.add(42);
    }
}
```

## Declarando uma classe genérica

Uma classe genérica declara um ou mais **parâmetros de tipo** entre `<` e `>`, logo depois do nome. Dentro dela, `T` funciona como um tipo qualquer: de campo, de parâmetro, de retorno e de variável local. Quem usa a classe fornece o **argumento de tipo**: em `Caixa<String>`, `T` é o parâmetro e `String` é o argumento, e `Caixa<String>` é um *tipo parametrizado*.

```java executar
public class Deposito {
    static class Caixa<T> {
        private T conteudo;

        void guardar(T item) {
            conteudo = item;
        }

        T abrir() {
            return conteudo;
        }

        boolean vazia() {
            return conteudo == null;
        }
    }

    public static void main(String[] args) {
        Caixa<String> bilhete = new Caixa<>();
        bilhete.guardar("parabéns");
        String texto = bilhete.abrir();
        System.out.println(texto.toUpperCase());

        Caixa<Integer> moedas = new Caixa<>();
        System.out.println(moedas.vazia());
        moedas.guardar(25);
        int valor = moedas.abrir();
        System.out.println(valor * 2);
    }
}
```

```saida
PARABÉNS
true
50
```

A mesma classe serve a qualquer tipo, e cada uso é conferido: `bilhete.guardar(10)` não compilaria. Repare que `moedas.abrir()` devolve `Integer`, desembalado para `int` automaticamente.

O nome do parâmetro pode ser qualquer identificador (`<Item>` compila), mas a convenção é uma letra maiúscula, e a prova a segue:

| Letra | Uso comum |
|---|---|
| `E` | Elemento de uma coleção |
| `K` e `V` | Chave e valor de um mapa |
| `T` | Um tipo qualquer |
| `N` | Número |
| `R` | Resultado, como em `Function<T, R>` |
| `S`, `U`, `V` | Segundo, terceiro e quarto tipos |

## O operador diamante

Desde o Java 7, `new Caixa<>()` deduz o argumento de tipo pelo lado esquerdo. Desde o Java 9, o diamante também vale para classes anônimas. Ele só existe do lado do `new`: `Caixa<> c = new Caixa<String>()` não compila.

Cuidado com `var`. Sem tipo à esquerda, o diamante não tem de onde deduzir e escolhe `Object`:

```java executar
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

public class Diamante {
    public static void main(String[] args) {
        Map<String, List<Integer>> notas = new HashMap<>();
        notas.put("Ana", new ArrayList<>());
        notas.get("Ana").add(9);

        var mistura = new ArrayList<>();
        mistura.add("texto");
        mistura.add(3.14);

        System.out.println(notas + " " + mistura);
    }
}
```

```saida
{Ana=[9]} [texto, 3.14]
```

`mistura` é um `ArrayList<Object>` e aceita qualquer coisa. Já esquecer o diamante, como em `List<String> l = new ArrayList();`, cria um *raw type*: compila, com um aviso.

> [!PROVA]
> `var lista = new ArrayList<>();` compila e cria um `ArrayList<Object>`. Questões de "qual é a saída" escondem isso adicionando um `String` e um `Integer` na mesma lista.

## Vários parâmetros e records genéricos

Os parâmetros são separados por vírgula, e records também podem ser genéricos:

```java executar
public class Pares {
    record Par<A, B>(A primeiro, B segundo) {
        Par<B, A> invertido() {
            return new Par<>(segundo, primeiro);
        }
    }

    public static void main(String[] args) {
        Par<String, Integer> idade = new Par<>("Bia", 31);
        Par<Integer, String> trocado = idade.invertido();
        System.out.println(idade);
        System.out.println(trocado.primeiro() + 1);
    }
}
```

```saida
Par[primeiro=Bia, segundo=31]
32
```

## Interfaces genéricas: três formas de implementar

Uma interface genérica declara o parâmetro do mesmo jeito. Quem a implementa pode **fixar o tipo**, **continuar genérico** ou, em código antigo, usar o **raw type**:

```java executar
import java.util.ArrayList;
import java.util.List;

public class Repositorios {
    interface Repositorio<T> {
        void salvar(T item);
        T buscar(int id);
    }

    static class RepositorioEmMemoria<T> implements Repositorio<T> {
        private final List<T> itens = new ArrayList<>();

        public void salvar(T item) { itens.add(item); }
        public T buscar(int id) { return itens.get(id); }
    }

    static class RepositorioDeNomes implements Repositorio<String> {
        private final List<String> nomes = new ArrayList<>();

        public void salvar(String nome) { nomes.add(nome.trim()); }
        public String buscar(int id) { return nomes.get(id); }
    }

    public static void main(String[] args) {
        Repositorio<Double> precos = new RepositorioEmMemoria<>();
        precos.salvar(9.9);
        Repositorio<String> nomes = new RepositorioDeNomes();
        nomes.salvar("  Caio ");
        System.out.println(precos.buscar(0) + " [" + nomes.buscar(0) + "]");
    }
}
```

```saida
9.9 [Caio]
```

Ao fixar `Repositorio<String>`, os métodos passam a receber e devolver `String`. Na forma raw, `T` vira `Object`:

```java compila
interface Repositorio<T> {
    void salvar(T item);
}

class RepositorioCru implements Repositorio {
    public void salvar(Object item) { }
}
```

Misturar as duas não funciona: implementar `Repositorio<String>` com `salvar(Object)` não compila, porque o método não sobrescreve `salvar(String)`.

## O que não dá para fazer com T

Algumas operações são proibidas. A razão de quase todas é o *type erasure*, tema do [episódio 3](/assistir/pleno-t2-e03): em tempo de execução, `T` não existe.

- **Tipos primitivos como argumento**: `List<int>` não compila; use `List<Integer>` e deixe o autoboxing trabalhar
- **Criar instâncias ou arrays de `T`**: `new T()` e `new T[10]` não compilam
- **Usar `T` em membros `static`**: há um único campo estático para `Caixa<String>` e `Caixa<Integer>`, então ele não pode ter o tipo de nenhuma das duas
- **Classes genéricas que estendem `Throwable`**: o `catch` precisaria saber o tipo exato na execução

```java nao-compila
public class Registro<T> {
    private static T ultimo;
}
```

```java nao-compila
public class Fabrica<T> {
    T criar() {
        return new T();
    }
}
```

Declarar um campo `T[] itens` ou um parâmetro `T... valores` é permitido. O problema é só **criar** o array.

## Raw types

Usar um tipo genérico sem argumentos, como `List` em vez de `List<String>`, cria um *raw type*. Ele existe para o código anterior ao Java 5 continuar compilando. O compilador avisa (`uses unchecked or unsafe operations`), mas compila, e toda a verificação de tipo some.

> [!PROVA]
> Aviso não é erro. Se a questão pergunta se o código compila, um raw type com aviso de `unchecked` compila. O erro, quando vem, aparece na execução, como `ClassCastException`.

## Por baixo dos panos

Existe uma única classe `Caixa` no bytecode, sirva ela a `String` ou a `Integer`. O compilador confere os tipos, troca `T` por `Object` e insere um cast onde o valor é usado. Compilando o `Deposito` e rodando `javap -c`, a linha `String texto = bilhete.abrir();` aparece assim:

```text
invokevirtual  // Method Deposito$Caixa.abrir:()Ljava/lang/Object;
checkcast      // class java/lang/String
```

O método devolve `Object`, e o `checkcast` é o cast que você deixou de escrever. A informação genérica não se perde de todo: o arquivo `.class` guarda as assinaturas originais num atributo `Signature` (`()TT;` para `abrir`). É por ele que o compilador sabe que uma biblioteca compilada declara `List<E>`, e é ele que a reflexão lê. A JVM, porém, ignora esse atributo ao executar.

Outras linguagens fizeram diferente. Os templates de C++ geram uma cópia do código para cada tipo usado, e o C# guarda os argumentos de tipo na execução, o que permite `new T()`. O Java escolheu manter o bytecode compatível com as bibliotecas que já existiam, e as restrições desta aula são o preço disso.

## Resumo para a prova

- Em `Caixa<String>`, `T` é o parâmetro de tipo e `String` é o argumento
- O diamante deduz o tipo pelo lado esquerdo; com `var`, deduz `Object`
- Diamante com classe anônima é permitido desde o Java 9
- Records e interfaces podem ser genéricos; quem implementa fixa o tipo, continua genérico ou usa raw
- Não pode: primitivos como argumento, `new T()`, `new T[]`, `T` em membros `static`, genérico estendendo `Throwable`
- Raw type compila com aviso e perde a verificação de tipo
