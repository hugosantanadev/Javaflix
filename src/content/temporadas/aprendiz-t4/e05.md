`HashMap` e `TreeMap` são, provavelmente, as estruturas mais usadas em qualquer sistema Java. Por fora, as duas guardam pares de chave e valor. Por dentro, uma é uma **tabela hash** e a outra é uma **árvore**, e entender cada uma explica por que uma tem acesso O(1) e a outra O(log n), por que uma mantém a ordem e a outra não, e por que esquecer o `hashCode` faz um `HashSet` "perder" objetos.

## Árvores

Uma **árvore** é uma estrutura hierárquica: um nó **raiz** no topo, cada nó com zero ou mais **filhos**, e nenhum ciclo. Nós sem filhos são **folhas**. A **altura** é o número de níveis do caminho mais longo da raiz até uma folha. Você usa árvores o tempo todo: as pastas do sistema de arquivos, o HTML de uma página (o DOM), um JSON, e a árvore sintática que o [compilador](/assistir/aprendiz-t2-e03) monta.

Numa **árvore binária**, cada nó tem no máximo dois filhos: esquerdo e direito.

## Árvore binária de busca

Uma **árvore binária de busca** (BST, *binary search tree*) acrescenta uma regra: para todo nó, os valores da subárvore esquerda são **menores** e os da direita são **maiores**. Buscar fica parecido com a [busca binária](/assistir/aprendiz-t4-e02): compare com a raiz e desça para um dos lados.

```text
            50
          /    \
        30      70
       /  \    /  \
     20   40  60   80
```

Buscar, inserir e remover custam O(h), em que h é a altura. Numa árvore **equilibrada**, h ≈ log₂ n. Mas a forma depende da ordem de inserção:

```java executar
public class Arvore {
    static class No {
        int valor;
        No esq, dir;

        No(int valor) {
            this.valor = valor;
        }
    }

    static No inserir(No raiz, int v) {
        if (raiz == null) {
            return new No(v);
        }
        if (v < raiz.valor) {
            raiz.esq = inserir(raiz.esq, v);
        } else {
            raiz.dir = inserir(raiz.dir, v);
        }
        return raiz;
    }

    static void emOrdem(No n, StringBuilder sb) {
        if (n == null) {
            return;
        }
        emOrdem(n.esq, sb);
        sb.append(n.valor).append(' ');
        emOrdem(n.dir, sb);
    }

    static int altura(No n) {
        return n == null ? 0 : 1 + Math.max(altura(n.esq), altura(n.dir));
    }

    public static void main(String[] args) {
        No equilibrada = null;
        for (int v : new int[] {50, 30, 70, 20, 40, 60, 80}) {
            equilibrada = inserir(equilibrada, v);
        }
        No torta = null;
        for (int v = 1; v <= 7; v++) {
            torta = inserir(torta, v);
        }
        StringBuilder sb = new StringBuilder();
        emOrdem(equilibrada, sb);
        System.out.println(sb.toString().trim());
        System.out.println(altura(equilibrada) + " " + altura(torta));
    }
}
```

```saida
20 30 40 50 60 70 80
3 7
```

Duas lições. Primeiro, o percurso **em ordem** (esquerda, nó, direita) visita os valores ordenados: uma BST é uma forma de manter dados sempre em ordem. Segundo, inserir valores já ordenados gera uma árvore "torta", com cada nó só com filho direito: altura 7, uma lista ligada disfarçada, com busca O(n).

## Árvores balanceadas

Para garantir O(log n) em qualquer ordem de inserção, existem árvores que **se rebalanceiam**, girando nós depois de cada inserção ou remoção. As mais conhecidas são a **AVL** (1962) e a **rubro-negra** (*red-black*). O `TreeMap` e o `TreeSet` do Java são árvores rubro-negras, e a documentação garante log(n) para `get`, `put`, `containsKey` e `remove`. Como a árvore está sempre em ordem, eles oferecem operações que um `HashMap` não tem:

```java executar
TreeMap<Integer, String> notas = new TreeMap<>(Map.of(90, "A", 80, "B", 70, "C", 60, "D"));
System.out.println(notas);
System.out.println(notas.floorKey(85) + " " + notas.ceilingKey(85));
System.out.println(notas.headMap(80) + " " + notas.firstKey() + " " + notas.lastKey());
```

```saida
{60=D, 70=C, 80=B, 90=A}
80 90
{60=D, 70=C} 60 90
```

`floorKey(85)` é a maior chave ≤ 85, e `ceilingKey(85)` a menor ≥ 85: com isso, achar a nota de uma pontuação é uma linha. `headMap(80)` devolve as chaves menores que 80.

A `PriorityQueue` usa outra árvore, o **heap binário**: uma árvore em que cada pai é menor que os filhos, guardada num array (os filhos do índice i ficam em 2i + 1 e 2i + 2). O menor está sempre na raiz, e inserir ou retirar custa O(log n).

## Tabelas hash

Uma tabela hash é um array de "baldes" (*buckets*). Para guardar uma chave, calcula-se um número a partir dela, o **hash**, e o hash escolhe o balde. Buscar repete a conta e vai direto ao balde: O(1), sem comparar com os outros elementos.

```text
"ana".hashCode() = 96724  →  96724 mod 16 = 4  →  balde 4 (numa tabela de 16 baldes)
```

O `HashMap` real ainda mistura os bits altos do hash com os baixos antes de escolher o balde, e usa `hash & (capacidade - 1)` no lugar do `mod`, como você viu na [aritmética modular](/assistir/aprendiz-t3-e04).

Duas chaves diferentes podem cair no mesmo balde: é a **colisão**, inevitável quando há mais chaves possíveis que baldes. O `HashMap` resolve com **encadeamento**: cada balde guarda uma pequena lista. Na busca, ele vai ao balde e compara o hash e o `equals` só com quem está lá.

O desempenho depende de as chaves se espalharem bem. O `HashMap` controla isso com o **fator de carga** (0,75 por padrão): quando o número de elementos passa de 75% da quantidade de baldes, ele dobra o array e redistribui tudo. Com capacidade inicial 16, o primeiro redimensionamento acontece ao inserir o 13º elemento. Desde o Java 8, um balde com muitas colisões (8 ou mais) vira uma pequena árvore rubro-negra, e o pior caso cai de O(n) para O(log n).

Colisões acontecem até com strings curtas. O `hashCode` de `String` é s[0]·31ⁿ⁻¹ + s[1]·31ⁿ⁻² + ... + s[n−1], e com isso:

```java executar
System.out.println("Aa".hashCode() + " " + "BB".hashCode());

Set<List<Integer>> conjunto = new HashSet<>();
List<Integer> chave = new ArrayList<>(List.of(1));
conjunto.add(chave);
chave.add(2);
System.out.println(conjunto.contains(chave) + " " + conjunto.size());
```

```saida
2112 2112
false 1
```

"Aa" é 65 · 31 + 97 = 2112, e "BB" é 66 · 31 + 66 = 2112. A segunda parte mostra um bug real: a lista foi guardada no balde do hash de `[1]`; depois de alterada, o hash mudou, e `contains` procura no balde errado. O elemento continua lá dentro (o tamanho é 1), mas ficou inalcançável. **Nunca altere um objeto usado como chave** enquanto ele estiver num `HashMap` ou `HashSet`.

## O contrato de `equals` e `hashCode`

Para uma tabela hash funcionar, a classe da chave precisa seguir o contrato definido em `Object`:

- Se `a.equals(b)`, então `a.hashCode() == b.hashCode()`.
- O contrário não é exigido: hashes iguais podem ser de objetos diferentes (colisão).
- Pela contrapositiva da primeira regra, hashes **diferentes** garantem objetos diferentes. É isso que permite à tabela descartar candidatos sem chamar `equals`.

Quem sobrescreve `equals` e esquece o `hashCode` quebra o contrato:

```java executar
import java.util.HashSet;
import java.util.Set;

public class SemHash {
    static class Cpf {
        final String numero;

        Cpf(String numero) {
            this.numero = numero;
        }

        @Override
        public boolean equals(Object o) {
            return o instanceof Cpf c && c.numero.equals(numero);
        }
    }

    record CpfRecord(String numero) {}

    public static void main(String[] args) {
        Set<Cpf> a = new HashSet<>();
        a.add(new Cpf("123"));
        System.out.println(a.contains(new Cpf("123")));

        Set<CpfRecord> b = new HashSet<>();
        b.add(new CpfRecord("123"));
        System.out.println(b.contains(new CpfRecord("123")));
    }
}
```

```saida
false
true
```

Os dois `Cpf` são iguais pelo `equals`, mas cada um tem o `hashCode` herdado de `Object`, ligado à identidade do objeto. A busca vai ao balde errado e nem chega a chamar o `equals`. O `record` gera `equals` e `hashCode` coerentes automaticamente, a partir dos componentes.

## `HashMap` ou `TreeMap`?

| | `HashMap` / `HashSet` | `TreeMap` / `TreeSet` |
|---|---|---|
| Estrutura | tabela hash com encadeamento | árvore rubro-negra |
| `get`, `put`, `remove` | O(1) em média | O(log n) garantido |
| Ordem de iteração | nenhuma garantida | ordem das chaves |
| A chave precisa de | `equals` e `hashCode` coerentes | `Comparable` ou um `Comparator` |
| Consultas por faixa | não tem | `floorKey`, `ceilingKey`, `headMap`, `subMap` |

Se precisar só de busca rápida, `HashMap`. Se precisar das chaves em ordem ou de consultas por faixa ("o próximo horário livre depois das 14h"), `TreeMap`. E se precisar da **ordem de inserção**, existe o `LinkedHashMap`.

## Resumo

- BST: menores à esquerda, maiores à direita; operações O(altura)
- Percurso em ordem de uma BST visita os valores ordenados
- Inserir dados ordenados numa BST simples gera altura n; árvores balanceadas garantem log n
- `TreeMap`/`TreeSet` são árvores rubro-negras: O(log n) e chaves em ordem
- `PriorityQueue` é um heap binário guardado num array
- Tabela hash: hash escolhe o balde; colisões vão para a mesma lista; O(1) em média
- Fator de carga 0,75: com 16 baldes, redimensiona no 13º elemento; desde o Java 8, baldes cheios viram árvores
- `equals` igual exige `hashCode` igual; sobrescreva os dois, ou use `record`
- Não altere objetos que são chaves de `HashMap` ou elementos de `HashSet`
