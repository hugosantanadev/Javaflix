Quase todo sistema guarda dados num banco relacional, como PostgreSQL, MySQL ou Oracle, e conversa com ele em SQL. O **JDBC** (*Java Database Connectivity*) é a API do Java para isso, no pacote `java.sql`. Frameworks como JPA e Spring Data, que a trilha de backend cobre, funcionam por cima dele. Este episódio e o próximo são cobrados só na prova **1Z0-829**, do Java 17; as provas do Java 21 e do 25 tiraram o JDBC do programa.

## Interfaces e drivers

O `java.sql` é quase todo feito de **interfaces**. Quem as implementa é o **driver** de cada banco, um JAR que o fabricante distribui. O código da aplicação só conhece as interfaces, e trocar de banco é, em boa parte, trocar o driver e a URL.

| Interface | Papel |
|---|---|
| `Driver` | A porta de entrada do driver; quase nunca usada diretamente |
| `Connection` | Uma sessão com o banco |
| `Statement` | Executa SQL fixo |
| `PreparedStatement` | Executa SQL com parâmetros, assunto do [próximo episódio](/assistir/senior-t5-e05) |
| `CallableStatement` | Chama procedimentos armazenados no banco |
| `ResultSet` | As linhas devolvidas por uma consulta |

A conexão sai de `DriverManager.getConnection(url, usuario, senha)`. A **URL** tem três partes: `jdbc`, o nome do banco e os detalhes de onde encontrá-lo, como `jdbc:postgresql://localhost:5432/loja` ou `jdbc:mysql://servidor/loja`. Desde o JDBC 4.0, do Java 6, os drivers se registram sozinhos, como provedores do serviço `java.sql.Driver` do [episódio de serviços](/assistir/senior-t4-e03); o antigo `Class.forName("org.postgresql.Driver")` não é mais necessário.

O JDK não traz nenhum banco nem driver. Sem um driver no classpath, `getConnection` lança `SQLException`, e é isso que se vê ao executar:

```java executar
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;
import java.util.Collections;

public class SemDriver {
    public static void main(String[] args) {
        System.out.println("drivers registrados: " + Collections.list(DriverManager.getDrivers()).size());
        String url = "jdbc:postgresql://localhost:5432/loja";
        try (Connection conexao = DriverManager.getConnection(url, "app", "segredo")) {
            System.out.println("conectado");
        } catch (SQLException e) {
            System.out.println(e.getMessage());
            System.out.println("SQLState: " + e.getSQLState() + ", código: " + e.getErrorCode());
        }
        System.out.println(Connection.class.getModule().getName() + " " + Connection.class.isInterface());
    }
}
```

```saida
drivers registrados: 0
No suitable driver found for jdbc:postgresql://localhost:5432/loja
SQLState: 08001, código: 0
java.sql true
```

A `SQLException` traz o **SQLState**, um código padronizado de cinco caracteres (`08001` é "não foi possível conectar"), e o **código de erro**, específico de cada banco. É uma exceção **checked**: todo método do JDBC declara `throws SQLException`. Os exemplos com banco deste episódio são **compilados** pelo verificador do site, mas não executados, porque não há banco disponível.

## Executando SQL com Statement

Um `Statement` é criado pela conexão e tem três métodos de execução:

| Método | Para | Devolve |
|---|---|---|
| `executeQuery(sql)` | `SELECT` | Um `ResultSet` |
| `executeUpdate(sql)` | `INSERT`, `UPDATE`, `DELETE` e comandos como `CREATE TABLE` | Um `int`: quantas linhas foram afetadas |
| `execute(sql)` | Qualquer comando | `true` se o resultado for um `ResultSet`, `false` se for uma contagem |

Depois de um `execute`, o resultado é lido com `getResultSet()` ou `getUpdateCount()`. Usar `executeQuery` com um `UPDATE`, ou `executeUpdate` com um `SELECT`, lança `SQLException` em tempo de execução.

```java compila
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.sql.Statement;

public class Consulta {
    public static void main(String[] args) throws SQLException {
        String url = "jdbc:postgresql://localhost:5432/loja";
        try (Connection conexao = DriverManager.getConnection(url, "app", "segredo");
             Statement comando = conexao.createStatement();
             ResultSet linhas = comando.executeQuery("SELECT id, nome, preco FROM produto ORDER BY nome")) {
            while (linhas.next()) {
                int id = linhas.getInt("id");
                String nome = linhas.getString(2);
                double preco = linhas.getDouble("preco");
                System.out.println(id + " " + nome + " " + preco);
            }
            int alterados = comando.executeUpdate("UPDATE produto SET preco = preco * 1.1");
            boolean temResultado = comando.execute("SELECT COUNT(*) FROM produto");
            System.out.println(alterados + " " + temResultado);
        }
    }
}
```

## Percorrendo o ResultSet

Um `ResultSet` funciona como um **cursor**. Ele começa **antes** da primeira linha, e cada `next()` avança uma linha e devolve se ela existe. Por isso o padrão é `while (linhas.next())`, e uma consulta que deve trazer no máximo uma linha usa `if (linhas.next())`. Ler uma coluna antes do primeiro `next()`, ou depois do último, lança `SQLException`.

Cada coluna da linha atual é lida com um `get` do tipo certo, `getInt`, `getString`, `getDouble`, `getBoolean`, `getDate`, `getObject`, que aceita:

- o **nome** da coluna, sem diferenciar maiúsculas de minúsculas: `getString("nome")`;
- ou a **posição** da coluna na consulta, **começando em 1**, não em 0: `getString(2)`.

Uma coluna inexistente ou uma posição inválida, como `getString(0)`, lançam `SQLException`. Um valor `NULL` do banco vira `null` nos `get` de objetos, mas `0` ou `false` nos de primitivos; nesses, `wasNull()` informa se a última coluna lida era `NULL`.

## Fechando na ordem certa

Conexões são caras e limitadas: o banco aceita um número máximo delas. Toda `Connection`, `Statement` e `ResultSet` precisa ser fechada, e o try-with-resources faz isso **na ordem inversa da abertura**, mesmo com exceção. Fechar um `Statement` também fecha o `ResultSet` dele, e fechar a `Connection` fecha os `Statement`. O mesmo mecanismo, com recursos de mentira, mostra a ordem:

```java executar
public class Ordem {
    static class Recurso implements AutoCloseable {
        private final String nome;

        Recurso(String nome) {
            this.nome = nome;
            System.out.println("abre " + nome);
        }

        @Override
        public void close() {
            System.out.println("fecha " + nome);
        }
    }

    public static void main(String[] args) {
        try (Recurso conexao = new Recurso("conexão");
             Recurso comando = new Recurso("comando");
             Recurso resultado = new Recurso("resultado")) {
            System.out.println("lendo as linhas");
            throw new IllegalStateException("falha no meio");
        } catch (IllegalStateException e) {
            System.out.println("tratando: " + e.getMessage());
        }
    }
}
```

```saida
abre conexão
abre comando
abre resultado
lendo as linhas
fecha resultado
fecha comando
fecha conexão
tratando: falha no meio
```

Os recursos são fechados **antes** do `catch` rodar. Em aplicações reais, as conexões costumam vir de um `DataSource` com um *pool*, como o HikariCP: o `close()` devolve a conexão ao pool em vez de encerrá-la, e o código continua o mesmo.

> [!PROVA]
> `DriverManager.getConnection(url, usuario, senha)`; URL `jdbc:banco:detalhes`. `executeQuery` devolve `ResultSet`; `executeUpdate`, `int`; `execute`, `boolean`. O `ResultSet` começa antes da primeira linha: chame `next()` antes de ler. Colunas por nome ou por posição a partir de **1**. Todos os métodos lançam `SQLException`, checked. Feche tudo com try-with-resources, na ordem inversa.

## Por baixo dos panos

Quando `getConnection` é chamado, o `DriverManager` percorre os drivers registrados e pergunta a cada um, com `acceptsURL`, se ele entende aquela URL; o primeiro que aceitar abre a conexão. Os drivers são encontrados pelo `ServiceLoader`, nos arquivos `META-INF/services/java.sql.Driver` dos JARs, na primeira vez em que o `DriverManager` é usado. Por isso a mensagem é "No suitable driver found": nenhum driver aceitou a URL.

A conexão é, na prática, um **socket TCP** aberto com o servidor do banco, falando o protocolo próprio dele. Abrir um custa caro: o aperto de mão TCP, muitas vezes TLS, e a autenticação, somando dezenas de milissegundos. Um `ResultSet` também não traz necessariamente todas as linhas de uma vez: o driver busca em lotes, cujo tamanho pode ser ajustado com `setFetchSize`, e cada `next()` que esgota o lote faz outra ida ao banco. É por isso que pools de conexão e consultas que trazem só as colunas e linhas necessárias fazem tanta diferença no desempenho de uma aplicação.

## Resumo para a prova

- JDBC: interfaces em `java.sql`, implementadas pelo driver; drivers se registram sozinhos desde o JDBC 4.0
- `DriverManager.getConnection(url, usuario, senha)`; URL começa com `jdbc:`
- `executeQuery` (`ResultSet`), `executeUpdate` (`int`), `execute` (`boolean`)
- `ResultSet`: cursor antes da primeira linha; `while (rs.next())`; colunas por nome ou índice a partir de 1
- `NULL` vira `null` em objetos e `0`/`false` em primitivos; `wasNull()` desfaz a dúvida
- `SQLException` é checked; feche `ResultSet`, `Statement` e `Connection` com try-with-resources
