O [episódio anterior](/assistir/senior-t5-e04) executou SQL fixo com `Statement`. Na prática, quase todo comando tem partes que vêm de fora: o login digitado, o preço máximo de uma busca, o id de um pedido. Montar esse SQL concatenando texto abre a porta para a falha de segurança mais explorada da web, a **injeção de SQL**. Este episódio fecha a temporada com o `PreparedStatement`, que resolve isso, com as **transações**, que garantem que um conjunto de alterações aconteça inteiro ou não aconteça, e com o `CallableStatement`.

## A injeção de SQL

Considere uma tela de login que monta a consulta juntando os textos digitados:

```java executar
public class Injecao {
    static String montarConsulta(String login, String senha) {
        return "SELECT id FROM usuario WHERE login = '" + login + "' AND senha = '" + senha + "'";
    }

    public static void main(String[] args) {
        System.out.println(montarConsulta("ana", "segredo"));
        System.out.println(montarConsulta("admin' --", "qualquer"));
        System.out.println(montarConsulta("x' OR '1'='1", "x' OR '1'='1"));
    }
}
```

```saida
SELECT id FROM usuario WHERE login = 'ana' AND senha = 'segredo'
SELECT id FROM usuario WHERE login = 'admin' --' AND senha = 'qualquer'
SELECT id FROM usuario WHERE login = 'x' OR '1'='1' AND senha = 'x' OR '1'='1'
```

Na segunda linha, o `--` é um comentário em SQL: tudo o que vem depois, inclusive a verificação da senha, é ignorado, e o invasor entra como `admin`. Na terceira, o `OR '1'='1'` torna a condição sempre verdadeira. O problema é que o banco não tem como saber onde termina o **código** SQL e onde começam os **dados**: tudo virou um texto só.

## PreparedStatement: código e dados separados

Um `PreparedStatement` recebe o SQL com **marcadores** `?` no lugar dos valores, e os valores são passados à parte, com métodos `set`. O banco recebe o comando e os parâmetros separados, e um parâmetro é **sempre** tratado como um valor, nunca como SQL: o login `x' OR '1'='1` é procurado literalmente na coluna.

| Método | Faz |
|---|---|
| `conexao.prepareStatement(sql)` | Cria o comando com os `?` |
| `setString(1, valor)`, `setInt`, `setLong`, `setBigDecimal`, `setDate`, `setObject` | Preenche o `?` da posição informada, **a partir de 1** |
| `setNull(2, Types.VARCHAR)` | Envia um `NULL` |
| `executeQuery()`, `executeUpdate()`, `execute()` | Executa, **sem** argumentos |
| `addBatch()` e `executeBatch()` | Junta várias execuções e as envia de uma vez; devolve um `int[]` |

Os parâmetros continuam valendo depois da execução: dá para trocar só alguns e executar de novo, ou chamar `clearParameters()`. Executar com algum `?` sem valor lança `SQLException`. E chamar `executeQuery(sql)`, com o SQL como argumento, num `PreparedStatement` também lança `SQLException`: esse método é herdado de `Statement` e não deve ser usado aqui.

```java compila
import java.math.BigDecimal;
import java.sql.Connection;
import java.sql.Date;
import java.sql.DriverManager;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.sql.Statement;
import java.time.LocalDate;

public class Preparado {
    public static void main(String[] args) throws SQLException {
        String url = "jdbc:postgresql://localhost:5432/loja";
        try (Connection conexao = DriverManager.getConnection(url, "app", "segredo")) {
            String inserir = "INSERT INTO produto (nome, preco, cadastro) VALUES (?, ?, ?)";
            try (PreparedStatement ps = conexao.prepareStatement(inserir, Statement.RETURN_GENERATED_KEYS)) {
                ps.setString(1, "caneta");
                ps.setBigDecimal(2, new BigDecimal("3.50"));
                ps.setDate(3, Date.valueOf(LocalDate.of(2025, 9, 16)));
                int inseridas = ps.executeUpdate();
                try (ResultSet chaves = ps.getGeneratedKeys()) {
                    if (chaves.next()) {
                        System.out.println(inseridas + " linha, id " + chaves.getLong(1));
                    }
                }
            }
            try (PreparedStatement ps = conexao.prepareStatement("SELECT id, nome FROM produto WHERE preco <= ? AND nome LIKE ?")) {
                ps.setBigDecimal(1, new BigDecimal("10"));
                ps.setString(2, "c%");
                try (ResultSet rs = ps.executeQuery()) {
                    while (rs.next()) {
                        System.out.println(rs.getLong("id") + " " + rs.getString("nome"));
                    }
                }
                ps.setBigDecimal(1, new BigDecimal("100"));
                ps.setString(2, "m%");
                try (ResultSet rs = ps.executeQuery()) {
                    System.out.println(rs.next());
                }
            }
            try (PreparedStatement ps = conexao.prepareStatement("UPDATE produto SET preco = ? WHERE id = ?")) {
                for (long id = 1; id <= 3; id++) {
                    ps.setBigDecimal(1, new BigDecimal("9.99"));
                    ps.setLong(2, id);
                    ps.addBatch();
                }
                int[] porComando = ps.executeBatch();
                System.out.println(porComando.length);
            }
        }
    }
}
```

O `RETURN_GENERATED_KEYS` pede ao banco as chaves geradas por ele, como um id autoincrementado, lidas depois com `getGeneratedKeys()`. O mesmo `PreparedStatement` de busca foi executado duas vezes, com parâmetros diferentes.

## Datas e outros tipos

O JDBC tem tipos próprios para datas: `java.sql.Date` (só data), `java.sql.Time` (só hora) e `java.sql.Timestamp` (data e hora). Todos convertem de e para `java.time`. Desde o JDBC 4.2, do Java 8, também é possível passar os tipos de `java.time` direto com `setObject` e lê-los com `getObject(coluna, LocalDate.class)`.

```java executar
import java.sql.Connection;
import java.sql.Time;
import java.sql.Timestamp;
import java.sql.Types;
import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.LocalTime;

public class TiposSql {
    public static void main(String[] args) {
        java.sql.Date data = java.sql.Date.valueOf(LocalDate.of(2025, 9, 16));
        Timestamp momento = Timestamp.valueOf(LocalDateTime.of(2025, 9, 16, 14, 30));
        Time hora = Time.valueOf(LocalTime.of(14, 30));
        System.out.println(data + " | " + momento + " | " + hora);
        System.out.println(data.toLocalDate().plusDays(1) + " " + momento.toLocalDateTime().getHour());
        System.out.println(Types.VARCHAR + " " + Types.INTEGER);
        try {
            java.sql.Date.valueOf("16/09/2025");
        } catch (IllegalArgumentException e) {
            System.out.println("formato inválido");
        }
    }
}
```

```saida
2025-09-16 | 2025-09-16 14:30:00.0 | 14:30:00
2025-09-17 14
12 4
formato inválido
```

`java.sql.Date.valueOf(String)` só aceita o formato `aaaa-mm-dd`. As constantes de `Types` identificam os tipos SQL, e são elas que `setNull` e `registerOutParameter` pedem.

## Transações

Por padrão, a conexão está em **auto-commit**: cada comando é uma transação própria, confirmada assim que termina. Para que vários comandos formem uma unidade, como debitar uma conta e creditar outra, desliga-se o auto-commit e confirma-se tudo no fim:

| Método | Faz |
|---|---|
| `setAutoCommit(false)` | Começa a agrupar os comandos numa transação |
| `commit()` | Confirma tudo o que foi feito desde o último `commit` |
| `rollback()` | Desfaz tudo desde o último `commit` |
| `setSavepoint()` / `setSavepoint(nome)` | Marca um ponto intermediário e devolve um `Savepoint` |
| `rollback(savepoint)` | Desfaz só o que veio depois do ponto marcado |
| `setTransactionIsolation(nivel)` | Escolhe o isolamento, como `TRANSACTION_READ_COMMITTED` |

Chamar `setAutoCommit(true)` no meio de uma transação também a confirma. E o que acontece ao fechar uma conexão com uma transação pendente fica **a critério de cada driver**, pela especificação: alguns confirmam, outros desfazem. O código correto sempre termina com `commit` ou `rollback`.

```java compila
import java.math.BigDecimal;
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.PreparedStatement;
import java.sql.SQLException;
import java.sql.Savepoint;

public class Transacao {
    static void transferir(Connection conexao, long de, long para, BigDecimal valor) throws SQLException {
        String debitar = "UPDATE conta SET saldo = saldo - ? WHERE id = ? AND saldo >= ?";
        String creditar = "UPDATE conta SET saldo = saldo + ? WHERE id = ?";
        boolean autoCommitAntes = conexao.getAutoCommit();
        conexao.setAutoCommit(false);
        try (PreparedStatement d = conexao.prepareStatement(debitar);
             PreparedStatement c = conexao.prepareStatement(creditar)) {
            d.setBigDecimal(1, valor);
            d.setLong(2, de);
            d.setBigDecimal(3, valor);
            if (d.executeUpdate() == 0) {
                throw new SQLException("saldo insuficiente");
            }
            Savepoint depoisDoDebito = conexao.setSavepoint("debito");
            c.setBigDecimal(1, valor);
            c.setLong(2, para);
            if (c.executeUpdate() == 0) {
                conexao.rollback(depoisDoDebito);
                throw new SQLException("conta de destino não existe");
            }
            conexao.commit();
        } catch (SQLException e) {
            conexao.rollback();
            throw e;
        } finally {
            conexao.setAutoCommit(autoCommitAntes);
        }
    }

    public static void main(String[] args) throws SQLException {
        try (Connection conexao = DriverManager.getConnection("jdbc:postgresql://localhost:5432/banco", "app", "segredo")) {
            conexao.setTransactionIsolation(Connection.TRANSACTION_READ_COMMITTED);
            transferir(conexao, 1, 2, new BigDecimal("100.00"));
        }
    }
}
```

## CallableStatement

Para chamar um **procedimento armazenado** no banco, usa-se o `CallableStatement`, criado com `prepareCall` e uma sintaxe de escape: `{call nome(?, ?)}`, ou `{? = call nome(?)}` para funções. Parâmetros de entrada são preenchidos com `set`; os de saída precisam ser registrados antes com `registerOutParameter(posicao, Types.X)` e lidos depois com `get`.

```java compila
import java.sql.CallableStatement;
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;
import java.sql.Types;

public class Procedimento {
    public static void main(String[] args) throws SQLException {
        try (Connection conexao = DriverManager.getConnection("jdbc:postgresql://localhost:5432/loja", "app", "segredo");
             CallableStatement cs = conexao.prepareCall("{call total_pedidos(?, ?)}")) {
            cs.setLong(1, 42);
            cs.registerOutParameter(2, Types.INTEGER);
            cs.execute();
            System.out.println(cs.getInt(2));
        }
    }
}
```

> [!PROVA]
> `PreparedStatement` com `?`; índices dos parâmetros a partir de 1; executar sem argumentos. Parâmetro sem valor: `SQLException`. `executeBatch()` devolve `int[]`. Auto-commit é o padrão; `setAutoCommit(false)`, `commit()`, `rollback()`, `setSavepoint()` e `rollback(savepoint)`. `CallableStatement`: `prepareCall("{call proc(?)}")`, `registerOutParameter` para saída. Fechar com transação pendente depende do driver.

## Por baixo dos panos

Quando o driver cria um `PreparedStatement`, ele pode enviar o SQL ao banco para ser **preparado**: o banco o analisa, monta o plano de execução e devolve um identificador. Nas execuções seguintes, o driver manda só o identificador e os valores, num formato binário do protocolo, sem texto SQL nenhum. Por isso a injeção é impossível: os valores nunca passam pelo analisador de SQL. E por isso reutilizar o mesmo `PreparedStatement` é mais rápido, e lotes com `addBatch` mais ainda, porque viajam numa só ida ao banco.

Uma transação, no banco, é sustentada por um **registro de escrita antecipada** (*write-ahead log*): cada alteração é gravada primeiro num log, e o `commit` só termina quando esse registro está salvo no disco. Se o servidor cair no meio, as transações confirmadas são refeitas a partir do log, e as não confirmadas são descartadas. É essa a garantia de **atomicidade** e de **durabilidade**, duas das propriedades ACID; o nível de isolamento controla a terceira, o que uma transação enxerga das outras que estão em andamento.

## Resumo para a prova

- Concatenar entradas no SQL permite injeção; `PreparedStatement` separa código e dados
- `prepareStatement(sql)` com `?`; `setXxx(indice, valor)` a partir de 1; `setNull(indice, Types.X)`
- `executeQuery()`, `executeUpdate()` e `execute()` sem argumentos; `addBatch()` e `executeBatch()` (`int[]`)
- `RETURN_GENERATED_KEYS` e `getGeneratedKeys()`; `java.sql.Date`, `Time` e `Timestamp` convertem para `java.time`
- Transações: `setAutoCommit(false)`, `commit`, `rollback`, `setSavepoint`, `rollback(savepoint)`, níveis de isolamento
- `CallableStatement`: `prepareCall("{call proc(?, ?)}")`, `registerOutParameter`, `get` depois do `execute`
