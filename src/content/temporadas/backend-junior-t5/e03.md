As tabelas da loja se ligam por chaves estrangeiras, como no [episódio de JOINs](/assistir/backend-junior-t3-e02): um pedido pertence a um cliente e tem vários itens, e cada item aponta para um produto. No JPA, essas ligações viram **relacionamentos** entre objetos: `pedido.getCliente()` devolve um `Cliente`, e `pedido.getItens()`, uma lista. O ORM traduz a navegação em SQL, e é aqui que ele mais ajuda e mais surpreende, porque o momento em que o SQL acontece deixa de ser óbvio. Todo o SQL deste episódio foi gerado pelo Hibernate 7.4.

## Muitos para um

O lado "muitos" é o que guarda a chave estrangeira, e por isso é o mais simples de mapear. Cada pedido tem um cliente:

```java
@Entity
@Table(name = "pedidos")
public class Pedido {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "cliente_id")
    private Cliente cliente;

    @OneToMany(mappedBy = "pedido", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<ItemPedido> itens = new ArrayList<>();
}
```

```sql
create table pedidos (cliente_id bigint not null, id bigint generated by default as identity, primary key (id))
alter table if exists pedidos add constraint FKg7202lk0hwxn04bmdl2thth5b foreign key (cliente_id) references clientes
```

O `@JoinColumn` diz o nome da coluna da chave estrangeira, e o `optional = false` a torna `not null`. O nome da restrição é gerado pelo Hibernate; com migrações, você escolhe nomes legíveis.

## Um para muitos

Do outro lado, o cliente pode conhecer os seus pedidos:

```java
@OneToMany(mappedBy = "cliente")
private List<Pedido> pedidos = new ArrayList<>();
```

O `mappedBy` é o detalhe mais importante dos relacionamentos: ele diz que **este lado não é o dono** da relação, e que a coluna está mapeada no atributo `cliente` da outra classe. O lado dono, o do `@ManyToOne`, é o único que o Hibernate olha para gravar a chave estrangeira. Mudar só a lista do cliente não muda nada no banco; mudar o `cliente` do pedido, sim. Por isso, num relacionamento bidirecional, os dois lados precisam ser mantidos juntos, de preferência num método só:

```java
public Pedido(Cliente cliente) {
    this.cliente = cliente;
    cliente.getPedidos().add(this);
}
```

Sem o `mappedBy`, o Hibernate entenderia dois relacionamentos independentes e criaria uma tabela intermediária `clientes_pedidos`, que ninguém pediu.

## Cascata e remoção de órfãos

Os itens só existem dentro de um pedido. Com `cascade = CascadeType.ALL`, as operações no pedido se propagam para os itens: persistir o pedido persiste os itens novos. Com `orphanRemoval = true`, um item retirado da lista é apagado do banco:

```java
public void adicionar(Produto produto, int quantidade) {
    itens.add(new ItemPedido(this, produto, quantidade, produto.getPreco()));
}

public void removerItem(int indice) {
    itens.remove(indice);
}
```

```text
--- persist do pedido com dois itens (cascade)
insert into pedidos (cliente_id,id) values (?,default)
insert into itens_pedido (pedido_id,preco_unitario,produto_id,quantidade,id) values (?,?,?,?,default)
insert into itens_pedido (pedido_id,preco_unitario,produto_id,quantidade,id) values (?,?,?,?,default)

--- remover um item da lista (orphanRemoval)
select p1_0.id,p1_0.cliente_id from pedidos p1_0 where p1_0.id=?
select i1_0.pedido_id,i1_0.id,i1_0.preco_unitario,i1_0.produto_id,i1_0.quantidade from itens_pedido i1_0 where i1_0.pedido_id=?
delete from itens_pedido where id=?
```

Um único `em.persist(pedido)` gravou três linhas, e um `itens.remove(1)` virou um `DELETE`. É a relação de **composição**: o item pertence ao pedido. A cascata **não** se aplica a associações entre entidades independentes: apagar um pedido não deve apagar o cliente nem o produto, e por isso o `@ManyToOne` acima não tem `cascade`.

## Carregamento preguiçoso

Ao buscar um pedido, o Hibernate não traz o cliente nem os itens:

```text
--- ler o pedido e o total
select p1_0.id,p1_0.cliente_id from pedidos p1_0 where p1_0.id=?
cliente é proxy? true
select i1_0.pedido_id,i1_0.id,i1_0.preco_unitario,i1_0.produto_id,i1_0.quantidade from itens_pedido i1_0 where i1_0.pedido_id=?
total: 609.70
select c1_0.id,c1_0.nome from clientes c1_0 where c1_0.id=?
nome do cliente: Ana Lima
```

O pedido veio só com o `cliente_id`. No lugar do cliente, o Hibernate colocou um ***proxy***: um objeto de uma subclasse de `Cliente`, gerada em tempo de execução, que sabe o id e só busca o resto quando um método é chamado, o `getNome()`. A lista de itens também é uma coleção especial, que busca os itens no primeiro acesso, aqui o `total()`. É o **carregamento preguiçoso** (*lazy loading*): só se busca o que é usado.

Os padrões do JPA são diferentes para cada tipo de relacionamento:

| Relacionamento | Padrão | Recomendação |
|---|---|---|
| `@ManyToOne`, `@OneToOne` | `EAGER`: busca junto, sempre | Declarar `fetch = FetchType.LAZY` |
| `@OneToMany`, `@ManyToMany` | `LAZY` | Manter |

O `EAGER` parece prático, mas é uma armadilha: cada busca de itens traria os produtos, que trariam as suas categorias, e assim por diante, em consultas que ninguém pediu. Marque tudo como `LAZY` e busque junto, explicitamente, só quando precisar, como mostra o [próximo episódio](/assistir/backend-junior-t5-e04).

## LazyInitializationException

O preço do carregamento preguiçoso aparece quando a transação já terminou:

```text
--- coleção preguiçosa fora da transação
select p1_0.id,p1_0.cliente_id from pedidos p1_0 where p1_0.id=?
LazyInitializationException: Cannot lazily initialize collection of role 'br.com.javaflix.loja.Pedido.itens' with key '1' (no session)
```

O pedido foi buscado dentro de uma transação, e a lista de itens foi acessada depois, quando o contexto de persistência já estava fechado. Não há mais conexão para buscar os itens. É uma das exceções mais famosas do Java, e a correção é sempre a mesma: buscar o que vai ser usado **dentro** da transação, num serviço com `@Transactional`, e devolver um DTO pronto.

> [!ATENCAO]
> O Spring Boot liga, por padrão, o `spring.jpa.open-in-view`, que mantém o contexto aberto até o fim da requisição HTTP. Isso esconde a `LazyInitializationException`, mas deixa a serialização do JSON disparar consultas e segura uma conexão do banco durante toda a requisição. O próprio Spring Boot emite um aviso na inicialização. Desligue com `spring.jpa.open-in-view=false` e resolva os carregamentos no serviço.

## Muitos para muitos

Um produto tem várias tags, e uma tag está em vários produtos. O `@ManyToMany` cria a tabela associativa:

```java
@ManyToMany
@JoinTable(name = "produto_tags",
        joinColumns = @JoinColumn(name = "produto_id"),
        inverseJoinColumns = @JoinColumn(name = "tag_id"))
private Set<Tag> tags = new HashSet<>();
```

```text
create table produto_tags (produto_id bigint not null, tag_id bigint not null, primary key (produto_id, tag_id))

--- muitos para muitos
select t1_0.produto_id,t1_1.id,t1_1.nome from produto_tags t1_0 join tags t1_1 on t1_1.id=t1_0.tag_id where t1_0.produto_id=?
insert into produto_tags (produto_id,tag_id) values (?,?)
```

O `Set` evita a mesma tag duas vezes. E repare que `itens_pedido` não foi mapeada como `@ManyToMany` entre pedidos e produtos: ela tem dados próprios, a quantidade e o preço da época, e por isso virou uma entidade, a `ItemPedido`, com dois `@ManyToOne`. Na prática, quase toda associação de muitos para muitos acaba ganhando um dado próprio, como a data em que a tag foi aplicada, e a entidade intermediária costuma ser o caminho mais seguro desde o começo.

## Por baixo dos panos

O proxy do cliente é um objeto de uma subclasse criada em tempo de execução, com a biblioteca ByteBuddy, que sobrescreve cada método: o primeiro acesso a qualquer coisa além do id dispara a consulta, guarda o objeto real e passa a delegar a ele. É por isso que as entidades não podem ser `final`. O mecanismo é o mesmo do `java.lang.reflect.Proxy`, que funciona com interfaces:

```java executar
import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Proxy;
import java.util.Map;

public class Preguicoso {
    interface Cliente {
        long getId();
        String getNome();
    }

    record ClienteReal(long id, String nome) implements Cliente {
        public long getId() { return id; }
        public String getNome() { return nome; }
    }

    static final Map<Long, String> TABELA = Map.of(7L, "Ana Lima");
    static boolean sessaoAberta = true;

    /** Devolve um "cliente" que só vai ao banco quando algo além do id for pedido. */
    static Cliente referencia(long id) {
        ClienteReal[] carregado = new ClienteReal[1];
        return (Cliente) Proxy.newProxyInstance(Cliente.class.getClassLoader(), new Class<?>[] {Cliente.class},
                (proxy, metodo, args) -> {
                    if (metodo.getName().equals("getId")) return id;
                    if (carregado[0] == null) {
                        if (!sessaoAberta) {
                            throw new IllegalStateException("could not initialize proxy [Cliente#" + id + "] - no session");
                        }
                        System.out.println("   select c.id, c.nome from clientes c where c.id=" + id);
                        carregado[0] = new ClienteReal(id, TABELA.get(id));
                    }
                    try {
                        return metodo.invoke(carregado[0], args);
                    } catch (InvocationTargetException e) {
                        throw e.getCause();
                    }
                });
    }

    public static void main(String[] args) {
        Cliente c = referencia(7);
        System.out.println("pedido carregado, cliente ainda não");
        System.out.println("id: " + c.getId());
        System.out.println("nome: " + c.getNome());
        System.out.println("nome de novo: " + c.getNome());

        Cliente outro = referencia(7);
        sessaoAberta = false;
        try {
            outro.getNome();
        } catch (IllegalStateException e) {
            System.out.println("fora da sessão: " + e.getMessage());
        }
    }
}
```

```saida
pedido carregado, cliente ainda não
id: 7
   select c.id, c.nome from clientes c where c.id=7
nome: Ana Lima
nome de novo: Ana Lima
fora da sessão: could not initialize proxy [Cliente#7] - no session
```

O id veio de graça, porque estava na chave estrangeira do pedido; o nome custou uma consulta, uma vez só; e, sem sessão, o proxy não tem como buscar, exatamente como a `LazyInitializationException` da aula. A cascata e a remoção de órfãos também são uma comparação: no fim da transação, o Hibernate confere cada coleção com a fotografia de quando foi carregada, insere os elementos novos e apaga os que sumiram. O desafio deste episódio implementa essa comparação.

## Resumo

- `@ManyToOne` + `@JoinColumn` fica no lado que tem a chave estrangeira, o dono da relação
- `@OneToMany(mappedBy = ...)` é o lado inverso: mudar só a lista não grava nada; mantenha os dois lados juntos
- `cascade = CascadeType.ALL` e `orphanRemoval = true` para composição, como itens de um pedido; nunca cascata para entidades independentes
- `@ManyToOne` é `EAGER` por padrão: declare `LAZY` em todos os relacionamentos
- Carregamento preguiçoso usa proxies e coleções especiais; fora da transação, `LazyInitializationException`
- Desligue o `open-in-view` e carregue o necessário no serviço, devolvendo DTOs
- `@ManyToMany` com `@JoinTable`; quando a associação tem dados próprios, ela vira uma entidade
