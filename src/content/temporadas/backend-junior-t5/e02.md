Com o `EntityManager` do [episódio anterior](/assistir/backend-junior-t5-e01), cada busca ainda exige escrever uma consulta. O **Spring Data JPA** elimina até isso: você declara uma **interface** com os métodos que quer, e o Spring cria a implementação sozinho, na inicialização, deduzindo a consulta do **nome do método**. É a forma como quase todo projeto Spring acessa o banco. Todo o SQL deste episódio foi gerado de verdade pelo Spring Data JPA 4.1 com o Hibernate 7.4.

> [!ANTES]
> Antes do Spring Data, de 2011, cada entidade tinha o seu **DAO**: uma interface e uma classe com os mesmos métodos repetidos, `buscarPorId`, `listarTodos`, `salvar`, cada um com três ou quatro linhas de `EntityManager`. Projetos com 50 entidades tinham 100 arquivos quase iguais. O Spring Data trocou essas classes por uma interface, e a implementação passou a ser gerada.

## Um repositório

```java
public interface ProdutoRepository extends JpaRepository<Produto, Long> {
}
```

Só isso. Os dois tipos genéricos são a entidade e o tipo do id, e a interface já herda dezenas de métodos prontos:

| Método | Faz |
|---|---|
| `save(entidade)` / `saveAll(lista)` | Insere, se o id for nulo, ou atualiza |
| `findById(id)` | Busca pelo id, devolvendo um `Optional` |
| `findAll()` / `findAll(Sort)` / `findAll(Pageable)` | Busca todos, ordenados ou paginados |
| `count()` / `existsById(id)` | Conta e verifica existência |
| `deleteById(id)` / `delete(entidade)` | Remove |

```text
--- saveAll
insert into produtos (criado_em,nome,preco,status,id) values (?,?,?,?,default)
insert into produtos (criado_em,nome,preco,status,id) values (?,?,?,?,default)
insert into produtos (criado_em,nome,preco,status,id) values (?,?,?,?,default)
insert into produtos (criado_em,nome,preco,status,id) values (?,?,?,?,default)
ids: [1, 2, 3, 4]
--- findById
select p1_0.id,p1_0.criado_em,p1_0.nome,p1_0.preco,p1_0.status from produtos p1_0 where p1_0.id=?
Optional[Produto[id=2, nome=Mouse sem fio, preco=129.90, status=ATIVO]]
```

O repositório é injetado como qualquer bean, e cada método roda numa transação própria, de só leitura para as buscas.

> [!PENSE]
> A interface não tem nenhuma classe que a implemente no seu projeto, e mesmo assim o `ProdutoService` recebe um objeto que funciona. De onde vem esse objeto, e em que momento ele é criado?

## Consultas derivadas do nome

O Spring Data lê o nome de um método declarado na interface e monta a consulta. O nome começa com o que fazer (`find`, `count`, `exists`, `delete`), seguido de `By` e das condições, que usam os nomes dos **atributos da entidade**:

```java
List<Produto> findByNomeContainingIgnoreCase(String trecho);
List<Produto> findByPrecoBetweenOrderByPrecoAsc(BigDecimal minimo, BigDecimal maximo);
long countByStatus(Status status);
boolean existsByNome(String nome);
Optional<Produto> findFirstByStatusOrderByPrecoDesc(Status status);
```

```text
--- findByNomeContainingIgnoreCase("MO")
select ... from produtos p1_0 where upper(p1_0.nome) like upper(?) escape '\'
[Produto[id=2, nome=Mouse sem fio, ...], Produto[id=3, nome=Monitor 27, ...]]

--- findByPrecoBetweenOrderByPrecoAsc(200, 400)
select ... from produtos p1_0 where p1_0.preco between ? and ? order by p1_0.preco
[Produto[id=4, nome=Headset, preco=259.90, ...], Produto[id=1, nome=Teclado mecânico, preco=349.90, ...]]

--- countByStatus(ATIVO)
select count(p1_0.id) from produtos p1_0 where p1_0.status=?
4

--- existsByNome("Headset")
select p1_0.id from produtos p1_0 where p1_0.nome=? fetch first ? rows only
true

--- findFirstByStatusOrderByPrecoDesc(ATIVO)
select ... from produtos p1_0 where p1_0.status=? order by p1_0.preco desc fetch first ? rows only
Optional[Produto[id=3, nome=Monitor 27, preco=1899.00, status=ATIVO]]
```

O `Containing` virou um `like`, com o valor envolvido em `%` e com os caracteres especiais escapados; o `IgnoreCase`, um `upper` dos dois lados; o `exists` busca só um id e para na primeira linha. As palavras mais usadas:

| No nome | Vira |
|---|---|
| `And`, `Or` | `and`, `or` |
| `Between`, `LessThan`, `GreaterThanEqual` | `between`, `<`, `>=` |
| `Containing`, `StartingWith`, `EndingWith` | `like '%x%'`, `like 'x%'`, `like '%x'` |
| `IgnoreCase` | `upper(...) = upper(...)` |
| `IsNull`, `IsNotNull` | `is null`, `is not null` |
| `In` | `in (...)` |
| `OrderBy...Asc` / `Desc` | `order by` |
| `First`, `Top3` | `fetch first 1 / 3 rows only` |

Um nome errado não compila em SQL inválido: a aplicação **não sobe**. Um método `findByNomee`, com o atributo digitado errado, produz:

```text
Cannot create query for method [RepositorioErrado.findByNomee(java.lang.String)];
No property 'nomee' found for type 'Produto'; Did you mean 'nome'
```

> [!DICA]
> Nomes derivados são ótimos até umas duas condições. Um `findByStatusAndPrecoGreaterThanAndNomeContainingIgnoreCaseOrderByPrecoDesc` está pedindo para virar uma consulta escrita, com `@Query`.

## @Query

Com `@Query`, a consulta é escrita em **JPQL**, a linguagem de consultas do JPA: parecida com SQL, mas sobre **entidades e atributos**, não sobre tabelas e colunas. O Hibernate a traduz para o SQL do banco:

```java
@Query("select p from Produto p where p.preco > :valor and p.status = br.com.javaflix.loja.Status.ATIVO")
List<Produto> ativosAcimaDe(BigDecimal valor);
```

```text
select ... from produtos p1_0 where p1_0.preco>? and p1_0.status='ATIVO'
```

Os parâmetros `:valor` são ligados pelos nomes dos parâmetros do método. Para SQL puro, específico do banco, há `@Query(value = "...", nativeQuery = true)`, que abre mão da portabilidade.

> [!LAPIS]
> Escreva a consulta derivada que busca os produtos com status informado e preço entre dois valores, do mais caro para o mais barato, e a mesma consulta com `@Query`.
>
> **Resposta:** `List<Produto> findByStatusAndPrecoBetweenOrderByPrecoDesc(Status status, BigDecimal minimo, BigDecimal maximo)`; e `@Query("select p from Produto p where p.status = :status and p.preco between :minimo and :maximo order by p.preco desc")`. A segunda é mais longa, mas aguenta mudanças sem virar um nome enorme.

## Projeções

Buscar a entidade inteira para mostrar dois campos é desperdício. Uma consulta pode montar um DTO direto, com `select new`:

```java
public record ResumoProduto(String nome, BigDecimal preco) {}

@Query("select new br.com.javaflix.loja.ResumoProduto(p.nome, p.preco) from Produto p order by p.nome")
List<ResumoProduto> resumos();
```

```text
select p1_0.nome,p1_0.preco from produtos p1_0 order by p1_0.nome
[ResumoProduto[nome=Headset, preco=259.90], ResumoProduto[nome=Monitor 27, preco=1899.00], ...]
```

O SQL busca só as duas colunas, e o resultado não é uma entidade gerenciada: não entra no contexto de persistência nem passa pela verificação de sujeira.

> [!PERGUNTAS]
> **P:** `findById` ou `getReferenceById`?
>
> **R:** `findById` busca e devolve um `Optional`. `getReferenceById` devolve um *proxy* sem consultar o banco, útil para ligar um relacionamento sem carregar a entidade inteira; se o id não existir, o erro só aparece quando o *proxy* for usado.
>
> **P:** `CrudRepository` ou `JpaRepository`?
>
> **R:** `JpaRepository` estende os outros e acrescenta paginação, `flush` e operações em lote. Num projeto com JPA, ele é o padrão.
>
> **P:** Posso pôr regra de negócio no repositório?
>
> **R:** Não: o repositório só busca e guarda. As regras ficam no serviço e nas entidades.

## Paginação

Um parâmetro `Pageable` pagina e ordena qualquer consulta, e o retorno `Page` traz, além dos itens, o total:

```java
Page<Produto> findByStatus(Status status, Pageable pagina);

repo.findByStatus(Status.ATIVO, PageRequest.of(1, 2, Sort.by("preco")));
```

```text
select ... from produtos p1_0 where p1_0.status=? order by p1_0.preco offset ? rows fetch first ? rows only
select count(p1_0.id) from produtos p1_0 where p1_0.status=?
[Produto[id=1, nome=Teclado mecânico, ...], Produto[id=3, nome=Monitor 27, ...]] página 1 de 2, total 4
```

As páginas começam em **0**: `PageRequest.of(1, 2)` é a segunda página. E repare na segunda consulta: o `Page` precisa do total para calcular quantas páginas existem, e faz um `count` a cada chamada. Em tabelas enormes, esse `count` pode custar mais que a própria busca; o tipo `Slice` dispensa o total e só diz se há uma próxima página.

> [!MATEMATICA]
> O preço do total: um `Page` faz duas consultas, a da página e um `count`. Se o filtro obriga o banco a percorrer 80 milhões de linhas, a uns 10 milhões por segundo, o `count` custa uns **8 segundos** a cada página aberta, enquanto a página em si busca 20 linhas em milissegundos. Um `Slice` pede 21 linhas: se vierem 21, há uma próxima página, e o total nunca é calculado.

## save e atualizações em massa

O `save` decide pelo id: com id nulo, faz `persist`; com id preenchido, faz `merge`. Numa entidade destacada, isso significa buscar de novo antes de atualizar:

```text
--- save de uma entidade existente, fora de transação
select ... from produtos p1_0 where p1_0.id=?            ← o findById
select ... from produtos p1_0 where p1_0.id=?            ← o merge do save
update produtos set criado_em=?,nome=?,preco=?,status=? where id=?
```

Dentro de uma transação, com a entidade gerenciada, nem o `save` seria necessário: a verificação de sujeira faria o `UPDATE`. Para alterar muitas linhas de uma vez, carregar cada entidade é lento; uma consulta `@Modifying` executa um único `UPDATE`:

```java
@Modifying
@Query("update Produto p set p.preco = p.preco * :fator where p.status = :status")
int reajustarTodos(BigDecimal fator, Status status);
```

```text
update produtos p1_0 set preco=(p1_0.preco*cast(? as numeric(10,2))) where p1_0.status=?
linhas: 4
```

O cuidado: atualizações em massa vão direto ao banco, sem passar pelo contexto de persistência. Entidades já carregadas na mesma transação ficam com os valores antigos na memória, e precisam ser recarregadas.

> [!ERRO]
> Chamar `save` dentro de um laço para atualizar milhares de linhas: cada iteração faz um `merge` (que pode incluir um `SELECT`) e um `UPDATE`, e o contexto acumula todas as entidades até o fim da transação. Para uma regra que vale para todas as linhas, como um reajuste, uma consulta `@Modifying` faz o mesmo trabalho com um único comando.

> [!IA]
> Consultas derivadas são um bom terreno para a IA, mas ela inventa atributos que a entidade não tem e cria nomes enormes. Dê a entidade junto com o pedido, e peça `@Query` quando houver mais de duas condições. Como um nome errado impede a aplicação de subir, rodar os testes do repositório já confere tudo.

## Na IDE

- **Autocompletar de métodos.** No IntelliJ Ultimate, ao digitar `findBy` numa interface de repositório, a IDE sugere os atributos da entidade e as palavras-chave.
- **JPQL com verificação.** Dentro de um `@Query`, a IDE reconhece o JPQL, completa entidades e atributos e marca em vermelho um atributo que não existe.
- **Ver o SQL gerado.** Com `logging.level.org.hibernate.SQL=DEBUG`, o console mostra o SQL de cada método chamado nos testes.

## Por baixo dos panos

Quem implementa a interface `ProdutoRepository`? Ninguém escreveu uma classe para ela. Na inicialização, o Spring Data encontra as interfaces que estendem `Repository` e, para cada uma, cria um ***proxy dinâmico*** com `java.lang.reflect.Proxy`: um objeto que implementa a interface e encaminha toda chamada para um único método, o `invoke`. Os métodos herdados, como `findById`, são delegados a uma implementação padrão, a `SimpleJpaRepository`. Os métodos declarados por você são analisados uma vez, na inicialização: o nome é quebrado em partes, cada parte é conferida contra os atributos da entidade, e a consulta resultante é preparada e guardada. É por isso que um nome errado impede a aplicação de subir, e não falha só quando o método for chamado. A análise do nome cabe em poucas linhas:

```java executar
import java.util.ArrayList;
import java.util.List;

public class MiniDerivada {
    static String minuscula(String s) {
        return Character.toLowerCase(s.charAt(0)) + s.substring(1);
    }

    static String parametro(int[] contador, boolean maiusculas) {
        String p = "?" + (++contador[0]);
        return maiusculas ? "upper(" + p + ")" : p;
    }

    static String condicao(String trecho, int[] contador) {
        boolean ignorar = trecho.endsWith("IgnoreCase");
        if (ignorar) trecho = trecho.substring(0, trecho.length() - "IgnoreCase".length());
        String operador = "";
        for (String s : List.of("Between", "Containing", "GreaterThan", "LessThan", "IsNull")) {
            if (trecho.endsWith(s)) operador = s;
        }
        String campo = "p." + minuscula(trecho.substring(0, trecho.length() - operador.length()));
        if (ignorar) campo = "upper(" + campo + ")";
        return switch (operador) {
            case "Between" -> campo + " between " + parametro(contador, false) + " and " + parametro(contador, false);
            case "Containing" -> campo + " like " + parametro(contador, ignorar);
            case "GreaterThan" -> campo + " > " + parametro(contador, ignorar);
            case "LessThan" -> campo + " < " + parametro(contador, ignorar);
            case "IsNull" -> campo + " is null";
            default -> campo + " = " + parametro(contador, ignorar);
        };
    }

    static String jpql(String metodo) {
        String acao = metodo.startsWith("count") ? "select count(p)" : "select p"; //> O começo do nome decide entre contar e buscar.
        String resto = metodo.substring(metodo.indexOf("By") + 2);
        String ordem = "";
        if (resto.contains("OrderBy")) {
            String o = resto.substring(resto.indexOf("OrderBy") + 7);
            resto = resto.substring(0, resto.indexOf("OrderBy"));
            boolean desc = o.endsWith("Desc");
            o = o.replaceAll("(Asc|Desc)$", "");
            ordem = " order by p." + minuscula(o) + (desc ? " desc" : "");
        }
        int[] contador = {0};
        List<String> partes = new ArrayList<>();
        for (String c : resto.split("And")) partes.add(condicao(c, contador)); //> Cada And separa uma condição.
        return acao + " from Produto p where " + String.join(" and ", partes) + ordem;
    }

    public static void main(String[] args) {
        for (String m : List.of("findByNomeContainingIgnoreCase", "findByPrecoBetweenOrderByPrecoAsc",
                "countByStatus", "findByStatusAndPrecoGreaterThanOrderByPrecoDesc", "findByCategoriaIsNull")) {
            System.out.println(m + "\n   " + jpql(m));
        }
    }
}
```

```saida
findByNomeContainingIgnoreCase
   select p from Produto p where upper(p.nome) like upper(?1)
findByPrecoBetweenOrderByPrecoAsc
   select p from Produto p where p.preco between ?1 and ?2 order by p.preco
countByStatus
   select count(p) from Produto p where p.status = ?1
findByStatusAndPrecoGreaterThanOrderByPrecoDesc
   select p from Produto p where p.status = ?1 and p.preco > ?2 order by p.preco desc
findByCategoriaIsNull
   select p from Produto p where p.categoria is null
```

As três primeiras são as mesmas consultas que o Spring Data gerou na aula, em JPQL, antes de o Hibernate traduzi-las para SQL. O desafio deste episódio completa o quadro: um `Proxy` que implementa uma interface de repositório em tempo de execução.

## Resumo

- `interface ProdutoRepository extends JpaRepository<Produto, Long>` traz `save`, `findById`, `findAll`, `count`, `deleteById` e outros
- Consultas derivadas do nome: `findBy`, `countBy`, `existsBy` com `And`, `Between`, `Containing`, `IgnoreCase`, `OrderBy`, `First`
- Nomes com atributos errados impedem a aplicação de subir
- `@Query` com JPQL, sobre entidades e atributos; `nativeQuery` para SQL puro
- Projeções com `select new` e `record`s: só as colunas necessárias, sem entidades gerenciadas
- `Pageable` e `Page`, com páginas a partir de 0 e um `count` extra; `Slice` evita o `count`
- `save` faz `persist` ou `merge`; `@Modifying` atualiza em massa sem passar pelo contexto
- O repositório é um `Proxy` dinâmico criado na inicialização
