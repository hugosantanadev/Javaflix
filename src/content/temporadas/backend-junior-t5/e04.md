O carregamento preguiçoso do [episódio anterior](/assistir/backend-junior-t5-e03) busca só o que é usado. O problema é que ele busca **um de cada vez**. Uma tela que lista pedidos com o nome do cliente faz uma consulta para os pedidos e mais uma para cada cliente: é o **problema N+1**, o defeito de desempenho mais comum em aplicações com JPA. Ele não aparece nos testes, com três pedidos, e derruba a produção, com três mil. Todo o SQL deste episódio foi gerado pelo Hibernate 7.4, com quatro pedidos de três clientes.

## O N+1 ao vivo

O código parece inocente:

```java
List<Pedido> pedidos = em.createQuery("select p from Pedido p order by p.id", Pedido.class).getResultList();
for (Pedido p : pedidos) {
    System.out.println("pedido " + p.getId() + ": " + p.getCliente().getNome());
}
```

```text
select p1_0.id,p1_0.cliente_id from pedidos p1_0 order by p1_0.id
select c1_0.id,c1_0.nome from clientes c1_0 where c1_0.id=?
pedido 1: Ana Lima
select c1_0.id,c1_0.nome from clientes c1_0 where c1_0.id=?
pedido 2: Bruno Souza
pedido 3: Ana Lima
select c1_0.id,c1_0.nome from clientes c1_0 where c1_0.id=?
pedido 4: Carla Dias
consultas: 4
```

Uma consulta trouxe os pedidos (o "1"), e cada `getNome()` num cliente ainda não carregado disparou outra (o "N"). O pedido 3 não gerou consulta porque a Ana já estava no contexto de persistência. Com coleções é igual: contar os itens de cada pedido fez 1 + 4 consultas.

```text
select p1_0.id,p1_0.cliente_id from pedidos p1_0 order by p1_0.id
select i1_0.pedido_id,i1_0.id,i1_0.preco_unitario,i1_0.produto_id,i1_0.quantidade from itens_pedido i1_0 where i1_0.pedido_id=?
pedido 1: 2 itens
select i1_0.pedido_id,i1_0.id,i1_0.preco_unitario,i1_0.produto_id,i1_0.quantidade from itens_pedido i1_0 where i1_0.pedido_id=?
pedido 2: 1 itens
...
consultas: 5
```

Cada consulta é rápida, mas cada uma é uma ida e volta ao banco pela rede. Uma página com 50 pedidos, o cliente e os itens de cada um faz 101 consultas, e o tempo da requisição passa a ser 101 vezes a latência da rede.

![Diagrama de sequência: no N+1, quatro idas ao banco; com join fetch, uma só](/figuras/n-mais-um.svg "Os mesmos dados, pedidos de duas formas. No N+1, cada cliente custa uma ida e volta ao banco.")

> [!MATEMATICA]
> O custo do N+1 é uma multiplicação. Com N itens, são 1 + N consultas; com busca em lote de tamanho L, 1 + ⌈N / L⌉, em que ⌈ ⌉ arredonda para cima. Se cada ida e volta leva 2 ms, 500 pedidos custam (1 + 500) × 2 ms ≈ 1 s no N+1 e (1 + ⌈500 / 10⌉) × 2 ms = 102 ms com lote de 10, contra uma única ida e volta no `join fetch`. O número de consultas cresce **linearmente** com os dados, O(N), e o do `join fetch` fica constante, O(1).

> [!ATENCAO]
> Trocar `LAZY` por `EAGER` **não** resolve. Numa consulta JPQL, o Hibernate busca os relacionamentos `EAGER` logo depois, também um por um. Na mesma listagem, com o cliente `EAGER`, as três consultas de clientes saíram antes do laço, e a listagem que só contava itens passou de 5 para 8 consultas, porque passou a carregar clientes que nem usava.

## Como enxergar

O N+1 é invisível no código e evidente no log. Durante o desenvolvimento, deixe o SQL aparecer:

```properties
logging.level.org.hibernate.SQL=DEBUG
spring.jpa.properties.hibernate.generate_statistics=true
logging.level.org.hibernate.session.metrics=DEBUG
```

As duas últimas linhas fazem o Hibernate resumir cada sessão. Este é um trecho do resumo da primeira listagem:

```text
HHH000401: Logging session metrics:
	13100 ns acquiring 1 JDBC connections
	555000 ns preparing 4 JDBC statements
	630200 ns executing 4 JDBC statements
```

Quatro comandos para mostrar quatro pedidos é o sinal. Num teste, a mesma contagem está em `SessionFactory.getStatistics().getPrepareStatementCount()`, e um teste que falha quando o número de consultas cresce com os dados pega o N+1 antes da produção.

## JOIN FETCH

A correção mais direta é dizer, na consulta, o que buscar junto:

```java
em.createQuery("select p from Pedido p join fetch p.cliente order by p.id", Pedido.class)
```

```text
select p1_0.id,p1_0.cliente_id,c1_0.id,c1_0.nome from pedidos p1_0 join clientes c1_0 on c1_0.id=p1_0.cliente_id order by p1_0.id
pedido 1: Ana Lima
pedido 2: Bruno Souza
pedido 3: Ana Lima
pedido 4: Carla Dias
consultas: 1
```

Uma consulta só, com os clientes já preenchidos. Repare na diferença: um `join` comum, sem `fetch`, serve para filtrar (`where c.nome = :nome`), mas **não** preenche o relacionamento, e o N+1 continua. O `fetch` é o que manda carregar.

Com coleções, o `join fetch` também resolve, e o resultado tem uma linha por item:

```text
select p1_0.id,p1_0.cliente_id,i1_0.pedido_id,i1_0.id,i1_0.preco_unitario,i1_0.produto_id,i1_0.quantidade from pedidos p1_0 join itens_pedido i1_0 on p1_0.id=i1_0.pedido_id order by p1_0.id
pedidos na lista: 4
consultas: 1
```

Seis linhas voltaram do banco, e a lista tem quatro pedidos: desde a versão 6, o Hibernate junta as linhas repetidas do mesmo pedido sozinho. No Hibernate 5, era preciso escrever `select distinct p`, e você ainda vai encontrar esse `distinct` em código antigo.

## @EntityGraph

No Spring Data, o mesmo efeito vem de uma anotação no repositório, sem escrever a consulta:

```java
public interface PedidoRepository extends JpaRepository<Pedido, Long> {

    @EntityGraph(attributePaths = "cliente")
    List<Pedido> findAllByOrderByIdAsc();
}
```

```text
select p1_0.id,p1_0.cliente_id,c1_0.id,c1_0.nome from pedidos p1_0 join clientes c1_0 on c1_0.id=p1_0.cliente_id order by p1_0.id
```

É o mesmo SQL do `join fetch`. O `attributePaths` aceita vários atributos e caminhos, como `{"cliente", "itens.produto"}`. A vantagem é reaproveitar consultas derivadas e o `findAll` com outro plano de busca, sem mudar o mapeamento da entidade.

## Busca em lote

Quando não dá para prever o que vai ser usado, existe uma rede de proteção: o Hibernate pode buscar os relacionamentos preguiçosos **em lote**. Com uma propriedade:

```properties
spring.jpa.properties.hibernate.default_batch_fetch_size=10
```

o mesmo laço do começo, sem mudar uma linha de código, faz duas consultas:

```text
select p1_0.id,p1_0.cliente_id from pedidos p1_0 order by p1_0.id
select c1_0.id,c1_0.nome from clientes c1_0 where c1_0.id in (?,?,?,?,?,?,?,?,?,?)
binding parameter (1:BIGINT) <- [1]
binding parameter (2:BIGINT) <- [2]
binding parameter (3:BIGINT) <- [3]
binding parameter (4:BIGINT) <- [null]
...
binding parameter (10:BIGINT) <- [null]
consultas: 2
```

No primeiro `getNome()`, o Hibernate não buscou só a Ana: buscou todos os clientes pendentes no contexto, até dez de uma vez. As posições que sobram vão como `null`, para que o comando tenha sempre o mesmo formato e o banco reaproveite o plano de execução. Com 500 pedidos de 500 clientes, seriam 1 + 50 consultas, e não 1 + 500. A anotação `@BatchSize(size = 10)`, numa coleção ou numa classe de entidade, faz o mesmo só ali.

## Duas armadilhas do JOIN FETCH

**Duas listas de uma vez.** Buscar um cliente com os pedidos e os itens de cada pedido parece natural, mas:

```text
MultipleBagFetchException: cannot simultaneously fetch multiple bags: [br.com.javaflix.loja.Pedido.itens, br.com.javaflix.loja.Cliente.pedidos]
```

Para o Hibernate, uma `List` sem ordem definida é um *bag*, e buscar dois *bags* na mesma consulta é proibido: o resultado seria o produto cartesiano das duas coleções, e não haveria como separar as linhas repetidas. Busque em consultas separadas, uma para cada coleção, ou use a busca em lote. Trocar `List` por `Set` faz o erro sumir, mas o produto cartesiano continua lá, e com coleções grandes ele é pior que o N+1.

**Paginação.** Um `join fetch` de coleção com `setMaxResults` tem um problema: o limite do SQL conta linhas do JOIN, e não pedidos. Por muito tempo, o Hibernate resolveu isso trazendo **todas** as linhas e paginando na memória, com o aviso `HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory`, e ele ainda faz isso em alguns casos. Com uma tabela grande, é um desastre silencioso. A forma segura é paginar em dois passos: primeiro os ids, depois os pedidos com os itens.

```java
List<Long> ids = em.createQuery("select p.id from Pedido p order by p.id", Long.class)
        .setFirstResult(2).setMaxResults(2).getResultList();
List<Pedido> pagina = em.createQuery(
        "select p from Pedido p join fetch p.itens where p.id in :ids order by p.id", Pedido.class)
        .setParameter("ids", ids).getResultList();
```

```text
select p1_0.id from pedidos p1_0 order by p1_0.id offset ? rows fetch first ? rows only
select p1_0.id,p1_0.cliente_id,i1_0.pedido_id,i1_0.id,i1_0.preco_unitario,i1_0.produto_id,i1_0.quantidade from pedidos p1_0 join itens_pedido i1_0 on p1_0.id=i1_0.pedido_id where p1_0.id in (?,?) order by p1_0.id
página: [3=2 itens, 4=2 itens]
```

## Projeção: nem entidades

Para uma tela que só mostra dados, a resposta mais eficiente costuma ser não carregar entidades. Uma projeção em DTO, como no [episódio de Spring Data](/assistir/backend-junior-t5-e02), traz exatamente as colunas da tela, numa consulta:

```java
em.createQuery("""
        select new br.com.javaflix.loja.ResumoPedido(p.id, c.nome, count(i))
        from Pedido p join p.cliente c join p.itens i
        group by p.id, c.nome order by p.id""", ResumoPedido.class)
```

```text
select p1_0.id,c1_0.nome,count(i1_0.id) from pedidos p1_0 join clientes c1_0 on c1_0.id=p1_0.cliente_id join itens_pedido i1_0 on p1_0.id=i1_0.pedido_id group by p1_0.id,c1_0.nome order by p1_0.id
ResumoPedido[pedido=1, cliente=Ana Lima, itens=2]
ResumoPedido[pedido=2, cliente=Bruno Souza, itens=1]
ResumoPedido[pedido=3, cliente=Ana Lima, itens=1]
ResumoPedido[pedido=4, cliente=Carla Dias, itens=2]
```

Sem proxies, sem coleções preguiçosas, sem fotografias para a verificação de sujeira e sem risco de N+1. A contagem foi feita pelo banco, que é bom nisso. Aqui o `join` sem `fetch` é o certo: ele só liga as tabelas para a consulta.

| Situação | Ferramenta |
|---|---|
| Sei o que a tela usa e vou alterar as entidades | `join fetch` ou `@EntityGraph` |
| Só leitura, para mostrar ou devolver como JSON | Projeção em DTO |
| Acessos difíceis de prever, rede de proteção geral | `default_batch_fetch_size` |
| Coleção com paginação | Dois passos: ids, depois `join fetch` |

## Por baixo dos panos

A diferença entre o N+1 e a busca em lote é só a forma de pedir os mesmos dados. O programa simula as duas, contando as idas ao banco:

```java executar
import java.util.HashMap;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Map;
import java.util.Set;

public class Consultas {
    record Pedido(int id, int clienteId) {}

    static final List<Pedido> PEDIDOS = List.of(new Pedido(1, 7), new Pedido(2, 8), new Pedido(3, 7), new Pedido(4, 9));
    static final Map<Integer, String> CLIENTES = Map.of(7, "Ana Lima", 8, "Bruno Souza", 9, "Carla Dias");
    static int consultas;

    static List<Pedido> buscarPedidos() {
        consultas++;
        System.out.println("   select id, cliente_id from pedidos");
        return PEDIDOS;
    }

    static String buscarCliente(int id) {
        consultas++;
        System.out.println("   select nome from clientes where id=" + id);
        return CLIENTES.get(id);
    }

    static Map<Integer, String> buscarClientes(Set<Integer> ids) {
        consultas++;
        System.out.println("   select id, nome from clientes where id in " + ids.toString().replace('[', '(').replace(']', ')'));
        Map<Integer, String> nomes = new HashMap<>();
        for (int id : ids) nomes.put(id, CLIENTES.get(id));
        return nomes;
    }

    public static void main(String[] args) {
        System.out.println("um por vez, como o proxy preguiçoso:");
        consultas = 0;
        Map<Integer, String> contexto = new HashMap<>();
        for (Pedido p : buscarPedidos()) {
            contexto.computeIfAbsent(p.clienteId(), Consultas::buscarCliente);
        }
        System.out.println("consultas: " + consultas);

        System.out.println("em lote:");
        consultas = 0;
        List<Pedido> pedidos = buscarPedidos();
        Set<Integer> ids = new LinkedHashSet<>();
        for (Pedido p : pedidos) ids.add(p.clienteId());
        Map<Integer, String> nomes = buscarClientes(ids);
        System.out.println("consultas: " + consultas + ", pedido 3 é da " + nomes.get(pedidos.get(2).clienteId()));
    }
}
```

```saida
um por vez, como o proxy preguiçoso:
   select id, cliente_id from pedidos
   select nome from clientes where id=7
   select nome from clientes where id=8
   select nome from clientes where id=9
consultas: 4
em lote:
   select id, cliente_id from pedidos
   select id, nome from clientes where id in (7, 8, 9)
consultas: 2, pedido 3 é da Ana Lima
```

O `computeIfAbsent` faz o papel do contexto de persistência, que evitou buscar a Ana duas vezes. A busca em lote só funciona porque os ids já são conhecidos antes do primeiro acesso: estão na coluna `cliente_id` de cada pedido, e os proxies guardam esses ids. O desafio deste episódio reproduz o lote limitado do Hibernate, com as posições vazias preenchidas com `null`.

## Resumo

- N+1: uma consulta para a lista e uma para cada relacionamento acessado; cresce com os dados
- `EAGER` não resolve: em JPQL, ele também busca um por um, e busca mesmo o que não é usado
- Enxergue com `org.hibernate.SQL=DEBUG` e as estatísticas da sessão; teste o número de consultas
- `join fetch` e `@EntityGraph` buscam junto, numa consulta; `join` sem `fetch` só filtra
- `default_batch_fetch_size` transforma N consultas em N dividido pelo tamanho do lote
- Nada de duas listas no mesmo `join fetch`, nem `join fetch` de coleção com paginação: pagine os ids primeiro
- Para telas de leitura, projeção em DTO: uma consulta, só as colunas necessárias
