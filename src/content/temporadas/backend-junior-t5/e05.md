Até aqui, as tabelas da loja nasceram do `spring.jpa.hibernate.ddl-auto=create`: o Hibernate lia as entidades e criava tudo do zero a cada subida. Para estudar, é ótimo. Em produção, seria apagar os pedidos de todos os clientes a cada deploy. O banco de uma aplicação real evolui junto com o código, e cada mudança precisa ser aplicada **uma vez**, **na ordem certa** e **em todos os ambientes**: no seu computador, no do colega, no de testes e no de produção. É o trabalho das **migrações**, e o Flyway é a ferramenta mais usada para isso no mundo Java. Tudo o que aparece neste episódio saiu de execuções reais do Flyway 12.4 com o Spring Boot 4.1.

## Por que não o ddl-auto

| Valor | O que faz | Onde usar |
|---|---|---|
| `create` | Apaga e recria as tabelas a cada subida | Estudo e protótipos |
| `create-drop` | Como `create`, e apaga tudo ao encerrar | Testes |
| `update` | Acrescenta tabelas e colunas que faltam | Em lugar nenhum que importe |
| `validate` | Só confere se as entidades batem com o banco | Produção, junto com migrações |
| `none` | Nada | Quando outra ferramenta cuida do esquema |

O `update` parece a solução, mas não renomeia, não apaga, não converte dados e não deixa registro do que fez. Renomear um atributo vira uma coluna nova, vazia, ao lado da antiga. E ninguém revisa o que ele vai fazer antes de ele fazer.

## Flyway no Spring Boot

No Spring Boot 4, a integração com o Flyway tem um *starter* próprio:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-flyway</artifactId>
</dependency>
```

No Spring Boot 3, bastava a dependência `org.flywaydb:flyway-core`. Desde o Flyway 10, o suporte à maioria dos bancos fica em módulos separados: para PostgreSQL, acrescente `org.flywaydb:flyway-database-postgresql`. O H2, usado aqui, já vem no núcleo.

As migrações são arquivos SQL em `src/main/resources/db/migration`, e o nome segue uma regra:

```text
V1__criar_tabelas.sql
│ │ └─ descrição, com _ no lugar dos espaços
│ └─ dois sublinhados
└─ V de versionada, seguido da versão
```

A versão é um número, que pode ter partes: `V1_1__dados_iniciais.sql` é a versão 1.1. A ordem é numérica, parte por parte: 1, 1.1, 2, 3, 10. Em ordem alfabética, `V10` viria antes de `V2`, e o Flyway não comete esse erro. A primeira migração cria o esquema que as entidades esperam, agora com nomes de restrições escolhidos por você:

```sql
create table clientes (
    id bigint generated by default as identity primary key,
    nome varchar(255)
);

create table pedidos (
    id bigint generated by default as identity primary key,
    cliente_id bigint not null,
    constraint fk_pedidos_cliente foreign key (cliente_id) references clientes (id)
);
```

E o Hibernate deixa de criar tabelas e passa a conferi-las:

```properties
spring.jpa.hibernate.ddl-auto=validate
```

## A primeira subida

Na inicialização, antes do JPA, o Spring Boot chama o Flyway:

```text
Schema history table "PUBLIC"."flyway_schema_history" does not exist yet
Successfully validated 2 migrations (execution time 00:00.013s)
Creating Schema History table "PUBLIC"."flyway_schema_history" ...
Current version of schema "PUBLIC": << Empty Schema >>
Migrating schema "PUBLIC" to version "1 - criar tabelas"
Migrating schema "PUBLIC" to version "2 - criar tags"
Successfully applied 2 migrations to schema "PUBLIC", now at version v2 (execution time 00:00.019s)
```

Na segunda subida, sem arquivos novos:

```text
Successfully validated 2 migrations (execution time 00:00.018s)
Current version of schema "PUBLIC": 2
Schema "PUBLIC" is up to date. No migration necessary.
```

O Flyway sabe o que já rodou porque anota cada migração numa tabela própria, a `flyway_schema_history`. Depois de mais uma versão e de uma migração repetível, que aparecem adiante, ela ficou assim:

```text
installed_rank | version | description                              | type  | script                          | checksum   | success
-1             | null    | << Flyway Schema History table created >> | TABLE |                                 | null       | true
1              | 1       | criar tabelas                            | SQL   | V1__criar_tabelas.sql           | 904878999  | true
2              | 2       | criar tags                               | SQL   | V2__criar_tags.sql              | -349610853 | true
3              | 3       | adicionar email cliente                  | SQL   | V3__adicionar_email_cliente.sql | 1773768441 | true
4              | null    | view resumo pedidos                      | SQL   | R__view_resumo_pedidos.sql      | 234268674  | true
```

A primeira linha é o registro da criação da própria tabela. As outras dizem qual arquivo rodou, em que ordem, se deu certo, e um *checksum*: um número calculado a partir do conteúdo do arquivo.

## Uma mudança, uma migração nova

O cliente ganhou e-mail. A mudança vira um arquivo novo, nunca uma edição do antigo:

```sql
-- V3__adicionar_email_cliente.sql
alter table clientes add column email varchar(120);

create unique index ux_clientes_email on clientes (email);
```

```text
Current version of schema "PUBLIC": 2
Migrating schema "PUBLIC" to version "3 - adicionar email cliente"
```

E se alguém editar a `V1`, já aplicada, para trocar um `varchar(255)` por `varchar(100)`? O checksum muda, e a aplicação não sobe:

```text
Validate failed: Migrations have failed validation
Migration checksum mismatch for migration version 1
-> Applied to database : 904878999
-> Resolved locally    : 1650659164
Either revert the changes to the migration, or run repair to update the schema history.
```

É uma proteção, e das boas: a `V1` editada nunca rodaria nos bancos que já estão na versão 3, e cada ambiente acabaria com um esquema diferente. Desfaça a edição e escreva uma `V4` com o `alter table`. O `repair`, citado na mensagem, reescreve os checksums da tabela de histórico para baterem com os arquivos, e só faz sentido quando a diferença foi proposital e inofensiva, como um comentário corrigido.

## Fora de ordem

Duas pessoas trabalham em *branches* diferentes. Uma cria a `V3` e ela chega a produção; a outra cria, depois, uma `V2_1`. Na subida seguinte:

```text
Validate failed: Migrations have failed validation
Detected resolved migration not applied to database: 2.1.
To ignore this migration, set -ignoreMigrationPatterns='*:ignored'. To allow executing this migration, set -outOfOrder=true.
```

O Flyway se recusa a aplicar uma versão menor que a atual, porque ela foi escrita sem saber da `V3`. Quase sempre, a correção é renomear o arquivo para a próxima versão livre, a `V4`. O `outOfOrder=true` existe, mas aplica uma mudança numa ordem que ninguém testou. Alguns times usam data e hora como versão, como `V20251019_1030__adicionar_email.sql`, para que duas pessoas dificilmente escolham o mesmo número.

## Quando uma migração falha

Uma `V4` com um erro na segunda linha, num nome de tabela:

```sql
alter table produtos add column descricao varchar(500);

create index ix_produtos_descricao on produto (descricao);
```

```text
Migrating schema "PUBLIC" to version "4 - descricao produto"
Migration of schema "PUBLIC" to version "4 - descricao produto" failed! Please restore backups and roll back database and code!
Message    : Table "PRODUTO" not found; SQL statement:
create index ix_produtos_descricao on produto (descricao) [42102-240]
Line       : 3
```

E na subida seguinte:

```text
Detected failed migration to version 4 (descricao produto).
Please remove any half-completed changes then run repair to fix the schema history.
```

O H2, como o MySQL, confirma cada comando de DDL na hora: a coluna `descricao` ficou criada, o índice não, e a migração ficou registrada como falha. Alguém precisa desfazer a metade aplicada e rodar o `repair`. No PostgreSQL, que executa DDL dentro de transações, o Flyway desfaz a migração inteira, e basta corrigir o arquivo. Nos dois casos, a lição é a mesma: migrações pequenas, de uma mudança cada, testadas no mesmo banco de produção, como mostra a [temporada de testes](/assistir/backend-junior-t6-e05).

## Migrações repetíveis

Uma *view*, uma função ou uma *procedure* são substituídas inteiras, e não alteradas. Para elas, existe a migração repetível, com `R__` e sem versão:

```sql
-- R__view_resumo_pedidos.sql
create or replace view resumo_pedidos as
select p.id as pedido, c.nome as cliente, count(i.id) as itens
from pedidos p
join clientes c on c.id = p.cliente_id
join itens_pedido i on i.pedido_id = p.id
group by p.id, c.nome;
```

Ela roda depois de todas as versionadas, e de novo sempre que o checksum mudar. Acrescentar uma coluna à *view* fez o Flyway reaplicá-la, com uma linha nova no histórico:

```text
Current version of schema "PUBLIC": 3
Migrating schema "PUBLIC" with repeatable migration "view resumo pedidos"
Successfully applied 1 migration to schema "PUBLIC" (execution time 00:00.006s)
```

## O validate do Hibernate

Com `ddl-auto=validate`, o Hibernate confere as entidades contra o banco na inicialização. Um atributo `telefone` acrescentado ao `Cliente` sem a migração correspondente:

```text
Schema validation: missing column [telefone] in table [clientes]
```

A aplicação não sobe, o que é muito melhor que subir e falhar no primeiro `INSERT`. E quando o Flyway não encontra os arquivos, por um diretório errado, o mesmo erro aparece de outra forma:

```text
Skipping filesystem location: ... (not found)
No migrations found. Are your locations set up correctly?
Schema "PUBLIC" is up to date. No migration necessary.
Schema validation: missing table [clientes]
```

Leia o log do Flyway antes do erro do Hibernate: "No migrations found" quer dizer que o problema é o caminho, e não o mapeamento.

## Duas situações do dia a dia

**Banco que já existia.** Para adotar o Flyway num banco em produção, `spring.flyway.baseline-on-migrate=true` registra o estado atual como uma versão de partida, a *baseline*, e só as migrações seguintes são aplicadas.

**Mudar sem parar.** Renomear `nome` para `nome_completo` num único `alter table` quebra a versão antiga da aplicação, que ainda está no ar durante o deploy. A forma segura é em etapas, chamada de *expand and contract*: uma migração cria a coluna nova e copia os dados; a aplicação passa a usar a nova; uma migração posterior, num deploy seguinte, apaga a antiga.

## Por baixo dos panos

O núcleo do Flyway cabe em poucas linhas: conferir os checksums do que já rodou, aplicar o que falta em ordem e anotar. O checksum é um CRC32 de cada linha do arquivo, sem as quebras de linha:

```java executar
import java.nio.charset.StandardCharsets;
import java.util.ArrayList;
import java.util.List;
import java.util.zip.CRC32;

public class MiniFlyway {
    record Migracao(int versao, String descricao, String sql) {}

    record Aplicada(int versao, int checksum) {}

    static final List<Aplicada> historico = new ArrayList<>();

    /** Como o Flyway: CRC32 de cada linha, sem as quebras de linha. */
    static int checksum(String sql) {
        CRC32 crc = new CRC32();
        sql.lines().forEach(linha -> crc.update(linha.getBytes(StandardCharsets.UTF_8)));
        return (int) crc.getValue();
    }

    static void migrar(List<Migracao> migracoes) {
        for (Aplicada a : historico) {
            Migracao local = migracoes.stream().filter(m -> m.versao() == a.versao()).findFirst().orElseThrow();
            int noArquivo = checksum(local.sql());
            if (noArquivo != a.checksum()) {
                System.out.println("falhou: checksum da versão " + a.versao() + " mudou (banco " + a.checksum() + ", arquivo " + noArquivo + ")");
                return;
            }
        }
        int atual = historico.isEmpty() ? 0 : historico.getLast().versao();
        int aplicadas = 0;
        for (Migracao m : migracoes) {
            if (m.versao() > atual) {
                System.out.println("aplicando versão " + m.versao() + " - " + m.descricao());
                historico.add(new Aplicada(m.versao(), checksum(m.sql())));
                aplicadas++;
            }
        }
        System.out.println(aplicadas == 0 ? "nada a fazer, versão " + atual : "agora na versão " + historico.getLast().versao());
    }

    public static void main(String[] args) {
        Migracao v1 = new Migracao(1, "criar clientes", "create table clientes (id bigint primary key, nome varchar(255));\n");
        Migracao v2 = new Migracao(2, "criar pedidos", "create table pedidos (id bigint primary key, cliente_id bigint not null);\n");
        Migracao v3 = new Migracao(3, "adicionar email cliente", """
                alter table clientes add column email varchar(120);

                create unique index ux_clientes_email on clientes (email);
                """);

        System.out.println("--- primeira subida");
        migrar(List.of(v1, v2));
        System.out.println("--- nova versão no projeto");
        migrar(List.of(v1, v2, v3));
        System.out.println("--- sem mudanças");
        migrar(List.of(v1, v2, v3));
        System.out.println("--- alguém editou a versão 1");
        Migracao v1Editada = new Migracao(1, "criar clientes", "create table clientes (id bigint primary key, nome varchar(100));\n");
        migrar(List.of(v1Editada, v2, v3));
        System.out.println("histórico: " + historico);
    }
}
```

```saida
--- primeira subida
aplicando versão 1 - criar clientes
aplicando versão 2 - criar pedidos
agora na versão 2
--- nova versão no projeto
aplicando versão 3 - adicionar email cliente
agora na versão 3
--- sem mudanças
nada a fazer, versão 3
--- alguém editou a versão 1
falhou: checksum da versão 1 mudou (banco 1495486932, arquivo 545872952)
histórico: [Aplicada[versao=1, checksum=1495486932], Aplicada[versao=2, checksum=-2057541187], Aplicada[versao=3, checksum=1773768441]]
```

Repare no checksum da versão 3: **1773768441**, o mesmo número que o Flyway real gravou na tabela de histórico da aula, para o mesmo arquivo. Como as quebras de linha ficam de fora do cálculo, um arquivo salvo com `\r\n` no Windows e com `\n` no Linux tem o mesmo checksum, e o Git não quebra a validação. O Flyway de verdade ainda guarda tudo numa tabela, aplica cada migração numa transação quando o banco permite, trava a tabela de histórico para que duas instâncias da aplicação não migrem ao mesmo tempo e entende versões com partes, como 2.1, o assunto do desafio.

## Resumo

- `ddl-auto=create` e `update` não servem para produção; use migrações e `ddl-auto=validate`
- No Spring Boot 4, `spring-boot-starter-flyway`; arquivos em `db/migration`, com nomes `V<versão>__<descrição>.sql`
- A `flyway_schema_history` anota cada migração com o checksum; versões em ordem numérica, parte por parte
- Nunca edite uma migração aplicada: escreva uma nova; o checksum denuncia a edição
- Versão menor que a atual é recusada; renomeie para a próxima versão livre
- Migrações pequenas: em bancos sem DDL transacional, uma falha deixa metade aplicada
- `R__` para *views* e funções, reaplicadas quando mudam; *baseline* para bancos que já existiam
