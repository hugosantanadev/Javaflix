Na [temporada de SQL](/assistir/backend-junior-t3-e01), cada consulta era escrita à mão, e no [episódio de JDBC](/assistir/senior-t5-e04) cada linha do `ResultSet` era copiada para um objeto, coluna por coluna. Numa aplicação com dezenas de tabelas, esse trabalho repetitivo é grande e fácil de errar. Um **ORM** (*object-relational mapping*) faz a tradução sozinho: você descreve como uma classe corresponde a uma tabela, e ele gera o SQL para gravar, buscar, alterar e apagar. No Java, o padrão é o **JPA** (*Jakarta Persistence*), uma especificação, e a implementação mais usada é o **Hibernate**. Todo o SQL deste episódio foi gerado de verdade pelo Hibernate 7.4, com o Spring Boot 4.1 e um banco H2 em memória.

## Uma entidade

Uma **entidade** é uma classe cujos objetos são linhas de uma tabela:

```java
@Entity
@Table(name = "produtos")
public class Produto {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 60)
    private String nome;

    @Column(nullable = false, precision = 10, scale = 2)
    private BigDecimal preco;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private Status status;

    @Column(name = "criado_em", nullable = false)
    private LocalDateTime criadoEm;

    protected Produto() {
    }

    public Produto(String nome, BigDecimal preco) {
        this.nome = nome;
        this.preco = preco;
        this.status = Status.ATIVO;
        this.criadoEm = LocalDateTime.now();
    }

    public void reajustar(BigDecimal novoPreco) { this.preco = novoPreco; }
    public void esgotar() { this.status = Status.ESGOTADO; }

    // getters
}
```

| Anotação | Faz |
|---|---|
| `@Entity` | Marca a classe como entidade |
| `@Table(name = ...)` | O nome da tabela; sem ela, o nome vem da classe |
| `@Id` | A chave primária |
| `@GeneratedValue(IDENTITY)` | O banco gera o id, com uma coluna de identidade |
| `@Column(...)` | Nome, nulidade, tamanho, precisão e escala da coluna |
| `@Enumerated(EnumType.STRING)` | Guarda o nome da constante do `enum`, não a posição |
| `@Transient` | Um campo que não vai para o banco |

O Spring Boot traduz os nomes de *camel case* para *snake case*: o campo `criadoEm` iria para a coluna `criado_em` mesmo sem o `name`. O construtor sem argumentos é exigido pelo JPA, que cria os objetos por reflexão; ele pode ser `protected`, para que o código da aplicação use o construtor completo. E a entidade tem comportamento, como `reajustar` e `esgotar`, em vez de *setters* para tudo.

## A tabela

Com `spring.jpa.hibernate.ddl-auto=create`, o Hibernate cria a tabela a partir da entidade, na inicialização:

```sql
create table produtos (
    preco numeric(10,2) not null,
    criado_em timestamp(6) not null,
    id bigint generated by default as identity,
    nome varchar(60) not null,
    status enum ('ATIVO','DESCONTINUADO','ESGOTADO') not null,
    primary key (id)
)
```

Cada tipo Java virou um tipo SQL: `Long` em `bigint`, `String` em `varchar` com o tamanho do `length` (o padrão seria 255), `BigDecimal` em `numeric` com a precisão e a escala pedidas, e `LocalDateTime` em `timestamp`. O `enum` virou, no H2, uma coluna do tipo `enum`; em bancos sem esse tipo, o Hibernate usa um texto com uma restrição que só aceita os valores do `enum`.

O `ddl-auto` é ótimo para estudar e para testes, e perigoso em produção: o `create` apaga as tabelas a cada inicialização, e o `update` tenta alterá-las sozinho, sem nunca remover nada e sem controle de versão. Em produção, o valor é `validate`, que só confere se as tabelas batem com as entidades, ou `none`, com o esquema mantido por **migrações**, assunto do [último episódio da temporada](/assistir/backend-junior-t5-e05).

> [!ATENCAO]
> Nunca use `@Enumerated(EnumType.ORDINAL)`, que é o padrão quando a anotação é omitida. Ele grava a **posição** da constante: `ATIVO` vira 0, `ESGOTADO` vira 1. Se alguém acrescentar uma constante no meio do `enum`, todos os registros antigos passam a significar outra coisa, sem erro nenhum.

## O EntityManager

O `EntityManager` é a porta de entrada do JPA, e cada um mantém um **contexto de persistência**: o conjunto das entidades que ele está acompanhando, as **gerenciadas**. Uma entidade passa por quatro estados:

| Estado | Significa |
|---|---|
| Nova (*transient*) | Criada com `new`, o JPA ainda não sabe dela |
| Gerenciada (*managed*) | Está no contexto: as mudanças nela viram SQL no fim da transação |
| Destacada (*detached*) | Já esteve num contexto que foi fechado; mudanças nela são ignoradas |
| Removida (*removed*) | Marcada para `DELETE` no fim da transação |

O comportamento real, com o SQL que o Hibernate registrou em cada passo, cada um numa transação:

```text
--- 1. persist
antes do persist: Produto[id=null, nome=Teclado mecânico, preco=349.90, status=ATIVO]
insert into produtos (criado_em,nome,preco,status,id) values (?,?,?,?,default)
depois do persist: Produto[id=1, nome=Teclado mecânico, preco=349.90, status=ATIVO]

--- 2. find duas vezes na mesma transação
select p1_0.id,p1_0.criado_em,p1_0.nome,p1_0.preco,p1_0.status from produtos p1_0 where p1_0.id=?
mesmo objeto: true

--- 3. alterar sem chamar save
select p1_0.id,p1_0.criado_em,p1_0.nome,p1_0.preco,p1_0.status from produtos p1_0 where p1_0.id=?
alterado na memória, fim da transação:
update produtos set criado_em=?,nome=?,preco=?,status=? where id=?

--- 4. alterar fora de transação (objeto destacado)
select p1_0.id,p1_0.criado_em,p1_0.nome,p1_0.preco,p1_0.status from produtos p1_0 where p1_0.id=?
nenhum SQL: Produto[id=1, nome=Teclado mecânico, preco=379.90, status=ESGOTADO]
select p1_0.id,p1_0.criado_em,p1_0.nome,p1_0.preco,p1_0.status from produtos p1_0 where p1_0.id=?
no banco: Produto[id=1, nome=Teclado mecânico, preco=379.90, status=ATIVO]

--- 5. merge do destacado
select p1_0.id,p1_0.criado_em,p1_0.nome,p1_0.preco,p1_0.status from produtos p1_0 where p1_0.id=?
update produtos set criado_em=?,nome=?,preco=?,status=? where id=?

--- 6. remove
select p1_0.id,p1_0.criado_em,p1_0.nome,p1_0.preco,p1_0.status from produtos p1_0 where p1_0.id=?
delete from produtos where id=?
```

Cada passo ensina uma regra:

1. O `persist` torna a entidade gerenciada. Com `IDENTITY`, o `INSERT` sai na hora, porque o id só existe depois que o banco o gera; o objeto ganha o `id=1`.
2. Dois `find` do mesmo id na mesma transação fazem **um** `SELECT` e devolvem **o mesmo objeto**: o contexto funciona como um cache, o **cache de primeiro nível**.
3. Alterar uma entidade gerenciada basta: no fim da transação, o Hibernate compara cada entidade com o estado em que ela foi lida e gera o `UPDATE` das que mudaram. É a **verificação de sujeira** (*dirty checking*), e é por isso que não existe um `update()` no JPA.
4. Fora da transação, a entidade está destacada: alterá-la não gera SQL, e o banco continua com o valor antigo.
5. O `merge` copia o estado de um objeto destacado para uma entidade gerenciada, que ele busca, e o `UPDATE` sai no fim da transação.
6. O `remove` marca a entidade, e o `DELETE` sai no fim da transação.

Para ver o SQL assim, com os valores, configure `logging.level.org.hibernate.SQL=DEBUG` e `logging.level.org.hibernate.orm.jdbc.bind=TRACE`. A propriedade `spring.jpa.show-sql=true`, comum em tutoriais, imprime direto no console, sem passar pelo sistema de logs, e não deve ir para produção.

## Regras para entidades

- A classe não pode ser `final`, e nem os métodos que acessam dados: o Hibernate cria subclasses, os *proxies*, para carregar dados sob demanda, assunto do [episódio 4](/assistir/backend-junior-t5-e04).
- `record`s não servem como entidades: são `final` e imutáveis. Servem, e muito bem, como DTOs.
- Cuidado com `equals` e `hashCode` baseados no `id`: uma entidade nova ainda não tem id, e muda de `hashCode` ao ser persistida, o que quebra um `HashSet` que já a continha.
- Não devolva entidades direto na API. Um campo novo na tabela apareceria no JSON sem ninguém decidir, e os relacionamentos podem disparar consultas extras ou laços infinitos na serialização. Converta para um DTO.

## Por baixo dos panos

Na inicialização, o Hibernate lê por **reflexão** as anotações de cada entidade e monta um **metamodelo**: para cada classe, a tabela, as colunas, os tipos e como gerar o id. A partir dele, prepara o SQL de inserção, busca, alteração e remoção de cada entidade, uma vez só. Um gerador de `INSERT` a partir de anotações cabe em poucas linhas:

```java executar
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;
import java.lang.reflect.Field;
import java.math.BigDecimal;
import java.time.LocalDateTime;
import java.util.ArrayList;
import java.util.Arrays;
import java.util.Comparator;
import java.util.List;
import java.util.StringJoiner;

public class MiniOrm {
    @Retention(RetentionPolicy.RUNTIME)
    @Target(ElementType.TYPE)
    @interface Tabela { String value(); }

    @Retention(RetentionPolicy.RUNTIME)
    @Target(ElementType.FIELD)
    @interface Id {}

    @Retention(RetentionPolicy.RUNTIME)
    @Target(ElementType.FIELD)
    @interface Transiente {}

    @Tabela("produtos")
    static class Produto {
        @Id Long id;
        String nome;
        BigDecimal preco;
        LocalDateTime criadoEm;
        @Transiente String rascunho = "não vai para o banco";

        Produto(String nome, BigDecimal preco) {
            this.nome = nome;
            this.preco = preco;
            this.criadoEm = LocalDateTime.of(2025, 9, 16, 14, 30);
        }
    }

    /** criadoEm vira criado_em, como na estratégia de nomes padrão do Spring Boot. */
    static String coluna(String campo) {
        return campo.replaceAll("([A-Z])", "_$1").toLowerCase();
    }

    static String insert(Object entidade, List<Object> parametros) throws IllegalAccessException {
        Class<?> classe = entidade.getClass();
        StringJoiner colunas = new StringJoiner(", ");
        StringJoiner marcadores = new StringJoiner(", ");
        Field[] campos = classe.getDeclaredFields();
        Arrays.sort(campos, Comparator.comparing(Field::getName));
        for (Field f : campos) {
            if (f.isAnnotationPresent(Id.class) || f.isAnnotationPresent(Transiente.class) || f.isSynthetic()) continue;
            f.setAccessible(true);
            colunas.add(coluna(f.getName()));
            marcadores.add("?");
            parametros.add(f.get(entidade));
        }
        return "insert into " + classe.getAnnotation(Tabela.class).value() + " (" + colunas + ") values (" + marcadores + ")";
    }

    public static void main(String[] args) throws Exception {
        List<Object> parametros = new ArrayList<>();
        System.out.println(insert(new Produto("Teclado mecânico", new BigDecimal("349.90")), parametros));
        System.out.println("parâmetros: " + parametros);
    }
}
```

```saida
insert into produtos (criado_em, nome, preco) values (?, ?, ?)
parâmetros: [2025-09-16T14:30, Teclado mecânico, 349.90]
```

As colunas saíram em ordem alfabética, como no `INSERT` real do Hibernate, que também ordena os atributos pelo nome: além de dar um SQL estável, isso é necessário porque a reflexão não garante a ordem dos campos. O id ficou de fora, porque o banco o gera, e o campo transiente também. Os valores vão como **parâmetros**, nunca concatenados no SQL, o que elimina a injeção de SQL.

A verificação de sujeira é a outra metade da mágica: ao carregar uma entidade, o Hibernate guarda uma cópia dos valores lidos, uma **fotografia**; no fim da transação, compara cada entidade gerenciada com a sua fotografia, campo a campo, e gera `UPDATE` só para as que mudaram. O desafio deste episódio implementa esse contexto de persistência.

## Resumo

- JPA é a especificação; Hibernate é a implementação; o ORM gera o SQL a partir do mapeamento
- `@Entity`, `@Table`, `@Id`, `@GeneratedValue(IDENTITY)`, `@Column`, `@Enumerated(EnumType.STRING)`
- Construtor sem argumentos (pode ser `protected`), classe não `final`, `record`s só como DTOs
- `ddl-auto=create` para estudar; em produção, `validate` ou `none` com migrações
- Nunca `EnumType.ORDINAL`: acrescentar uma constante muda o significado dos dados antigos
- Estados: nova, gerenciada, destacada e removida; `persist`, `find`, `merge` e `remove`
- O contexto de persistência é um cache por transação, e a verificação de sujeira gera os `UPDATE`s sozinha
