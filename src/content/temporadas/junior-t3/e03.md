Polimorfismo quer dizer "muitas formas": uma variável do tipo `Forma` pode apontar para um retângulo, um círculo ou qualquer forma inventada amanhã, e cada uma responde a `area()` do seu jeito. É o recurso que permite escrever código que trabalha com o tipo geral sem saber dos tipos específicos. Para usá-lo e responder às questões, basta separar duas perguntas: o que o **compilador** deixa chamar, e o que a **JVM** executa.

## Tipo da referência e tipo do objeto

Em `Forma f = new Circulo(1);` há dois tipos. O da **referência** (`Forma`) decide, na compilação, quais métodos podem ser chamados. O do **objeto** (`Circulo`) decide, na execução, qual implementação de um método de instância roda.

```java executar
class Forma {
    double area() { return 0; }
    String nome() { return "forma"; }
}

class Retangulo extends Forma {
    double l, a;
    Retangulo(double l, double a) { this.l = l; this.a = a; }
    @Override double area() { return l * a; }
    @Override String nome() { return "retângulo"; }
}

class Circulo extends Forma {
    double r;
    Circulo(double r) { this.r = r; }
    @Override double area() { return Math.round(Math.PI * r * r * 100) / 100.0; }
    @Override String nome() { return "círculo"; }
}

Forma[] formas = {new Retangulo(2, 3), new Circulo(1), new Forma()};
for (Forma f : formas) {
    System.out.println(f.nome() + ": " + f.area());
}
```

```saida
retângulo: 6.0
círculo: 3.14
forma: 0.0
```

O laço não sabe que tipos existem; cada objeto executa a sua versão. Acrescentar um `Triangulo` amanhã não muda uma linha desse laço.

O outro lado da moeda: pela referência `Forma`, só se chama o que `Forma` declara. Mesmo que o objeto tenha mais métodos, o compilador não os enxerga:

```java nao-compila
class Animal {
    String som() { return "..."; }
}

class Cachorro extends Animal {
    @Override String som() { return "au"; }
    String buscar() { return "bolinha"; }
}

Animal a = new Cachorro();
System.out.println(a.som());
System.out.println(a.buscar());
```

Para chamar `buscar`, é preciso uma referência do tipo `Cachorro`, o que exige um **cast**, assunto do [próximo episódio](/assistir/junior-t3-e04).

## O que não é polimórfico

Só **métodos de instância** sobrescritos seguem o objeto. Campos e métodos `static` seguem a referência. Se a subclasse declara um campo com o mesmo nome de um campo da superclasse, ela o **esconde**, e os dois coexistem no objeto:

```java executar
class Pai {
    String nome = "pai";
    String getNome() { return nome; }
}

class Filho extends Pai {
    String nome = "filho";
    @Override String getNome() { return nome; }
}

Filho f = new Filho();
Pai p = f;
System.out.println(p.nome + " " + f.nome + " " + p.getNome());
```

```saida
pai filho filho
```

`p` e `f` apontam para o mesmo objeto. O campo é escolhido pelo tipo da variável; o método, pelo objeto. Esconder campos é legal, mas quase sempre um erro de projeto: com campos `private` e getters, o problema nem aparece.

| Elemento | Escolhido por |
|---|---|
| Quais membros podem ser usados | tipo da referência, na compilação |
| Método de instância sobrescrito | tipo do objeto, na execução |
| Campo | tipo da referência |
| Método `static` | tipo da referência |
| Sobrecarga (qual assinatura) | tipos declarados dos argumentos, na compilação |

## A armadilha do construtor

Um construtor que chama um método sobrescrevível pode executar o código da subclasse **antes** de os campos dela serem inicializados, porque o construtor da superclasse roda primeiro, como você viu no [episódio 1](/assistir/junior-t3-e01):

```java executar
class Base {
    Base() {
        System.out.println("Base vê: " + descrever());
    }

    String descrever() {
        return "base";
    }
}

class Sub extends Base {
    private String nome = "sub";
    private int numero = 7;

    @Override
    String descrever() {
        return nome + " " + numero;
    }
}

Sub s = new Sub();
System.out.println("depois: " + s.descrever());
```

```saida
Base vê: null 0
depois: sub 7
```

Quando o construtor de `Base` roda, o objeto já é um `Sub`, então a chamada vai para a versão de `Sub`, mas os inicializadores dela ainda não executaram. O Effective Java é taxativo: construtores nunca devem chamar métodos que possam ser sobrescritos.

> [!PROVA]
> Para cada chamada numa questão de polimorfismo, faça duas perguntas. Compila? Olhe o tipo da referência: o método existe nele? Se compila, o que roda? Para método de instância, olhe o objeto real; para campo e método `static`, a referência. E desconfie de qualquer construtor que chama um método da própria classe.

## Por baixo dos panos

A chamada `f.area()` vira um `invokevirtual`, que consulta a tabela de métodos virtuais da classe real do objeto, como você viu no [episódio anterior](/assistir/junior-t3-e02). Uma indireção a mais por chamada parece pouco, mas impede a otimização mais importante do JIT: o *inlining*, que copia o corpo do método para o lugar da chamada.

Por isso a HotSpot observa os tipos que realmente passam por cada ponto de chamada. Se só aparece um tipo (chamada **monomórfica**), o JIT gera uma checagem rápida de tipo seguida do código do método, já embutido. Com dois tipos (**bimórfica**), duas checagens. Com três ou mais (**megamórfica**), desiste e usa a tabela. E se só existe uma implementação carregada, a análise da hierarquia de classes (*CHA*) trata a chamada como direta; se uma subclasse nova for carregada depois, a JVM desfaz a otimização (*deoptimization*) e recompila. O resultado é que o polimorfismo costuma ser gratuito no caso comum, e marcar métodos como `final` para "ganhar desempenho" quase nunca faz diferença.

## Resumo para a prova

- O tipo da referência decide o que pode ser chamado; o tipo do objeto decide qual método de instância roda
- Pela referência da superclasse, métodos exclusivos da subclasse não compilam sem cast
- Campos e métodos `static` não são polimórficos: seguem a referência
- Campo de mesmo nome na subclasse esconde o da superclasse; os dois existem no objeto
- Método chamado no construtor da superclasse pode rodar a versão da subclasse com campos ainda não inicializados
- Parâmetros e arrays do tipo da superclasse aceitam qualquer subclasse
