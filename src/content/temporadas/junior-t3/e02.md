Sobrescrever (*override*) é redeclarar, na subclasse, um método herdado, para que os objetos dela façam aquilo de outro jeito. Parece simples, e a ideia é. Mas o compilador confere uma lista de regras para garantir que a subclasse continue cumprindo o contrato da superclasse, e cada regra vira uma questão de prova. Este episódio é sobre essa lista.

## Sobrescrever e `@Override`

```java executar
class Notificacao {
    String enviar(String msg) {
        return "genérica: " + msg;
    }
}

class Email extends Notificacao {
    @Override
    String enviar(String msg) {
        return "e-mail: " + msg; //> A versão de Email substitui a de Notificacao.
    }
}

class Sms extends Notificacao {
    @Override
    public String enviar(String msg) { //> Acesso mais aberto que o original: permitido.
        return "SMS: " + msg.substring(0, Math.min(msg.length(), 10));
    }
}

System.out.println(new Email().enviar("Seu pedido saiu"));
System.out.println(new Sms().enviar("Seu pedido saiu"));
System.out.println(new Notificacao().enviar("oi"));
```

```saida
e-mail: Seu pedido saiu
SMS: Seu pedido
genérica: oi
```

A anotação `@Override` é opcional, mas valiosa: ela pede ao compilador que confirme que o método realmente sobrescreve algo. Um erro de digitação, ou um parâmetro de tipo diferente, criaria em silêncio um método **novo** (uma sobrecarga), e o `@Override` transforma isso em erro de compilação:

```java nao-compila
class Forma {
    double area(double escala) {
        return 0;
    }
}

class Circulo extends Forma {
    @Override
    double area(int escala) { //> int em vez de double: seria uma sobrecarga, e o @Override acusa.
        return 3.14 * escala;
    }
}
```

> [!PERGUNTAS]
> **P:** Se o `@Override` é opcional, por que todo mundo usa?
>
> **R:** Porque ele transforma um engano silencioso num erro de compilação. Sem ele, `toString()` com um "s" minúsculo trocado, ou `equals(Produto)` no lugar de `equals(Object)`, compila e cria um método novo que ninguém chama.

## As regras

| Regra | O que a subclasse pode fazer |
|---|---|
| Assinatura | exatamente a mesma: nome e tipos dos parâmetros |
| Acesso | o mesmo ou **mais** aberto, nunca mais fechado |
| Retorno | o mesmo tipo ou um **subtipo** (retorno covariante); primitivos, só o mesmo |
| Exceções verificadas | as mesmas, menos ou mais específicas; nunca novas ou mais amplas |
| `final`, `static`, `private` | não podem ser sobrescritos |

A lógica de todas é a mesma: quem usa a superclasse não pode ser surpreendido. Se a superclasse promete um método `public`, a subclasse não pode escondê-lo:

```java nao-compila
class Base {
    public void salvar() { }
}

class Filha extends Base {
    void salvar() { }
}
```

> [!ERRO]
> O `javac` explica a regra violada numa segunda linha: `error: salvar() in Filha cannot override salvar() in Base`, seguido de `attempting to assign weaker access privileges; was public`. Quem lê só a primeira linha não descobre o motivo. Leia sempre a mensagem inteira.

> [!PENSE]
> Quem chama `Fabrica.criar()` espera um `Object`. Se a subclasse devolver uma `String`, essa pessoa é surpreendida?

Se a superclasse promete devolver um `Object`, devolver uma `String` cumpre a promessa, porque toda `String` é um `Object`. Esse é o **retorno covariante**:

```java executar
class Fabrica {
    Object criar() {
        return "algo";
    }
}

class FabricaDeTexto extends Fabrica {
    @Override
    String criar() {
        return "texto pronto";
    }
}

FabricaDeTexto f = new FabricaDeTexto();
String s = f.criar();
System.out.println(s.toUpperCase());
```

```saida
TEXTO PRONTO
```

Com primitivos, não há subtipos: `long` não é um `int`, e o retorno precisa ser idêntico.

```java nao-compila
class Medidor {
    int medir() {
        return 1;
    }
}

class MedidorPreciso extends Medidor {
    long medir() {
        return 1L;
    }
}
```

Com **exceções verificadas** (como `IOException`, que você verá na temporada de exceções), vale o mesmo raciocínio: quem chama a superclasse só se preparou para as exceções que ela declara. A subclasse pode declarar menos, mas não acrescentar:

```java nao-compila
import java.io.IOException;

class Leitor {
    void ler() {
    }
}

class LeitorDeArquivo extends Leitor {
    @Override
    void ler() throws IOException {
    }
}
```

Exceções não verificadas, como `IllegalStateException`, ficam de fora dessa regra e podem ser declaradas à vontade.

> [!CONVERSA]
> **Superclasse:** Eu prometi um `public void ler()` sem exceções verificadas. Quem me chama escreveu o código contando com isso.
>
> **Subclasse:** Então eu posso abrir mais o acesso, devolver algo mais específico, lançar menos...
>
> **Superclasse:** Tudo o que deixa a promessa igual ou melhor. Esconder o método ou lançar uma `IOException` nova quebraria quem já me usa.
>
> **Subclasse:** Ou seja, posso ser mais generosa que você, nunca mais exigente.

> [!ANTES]
> O `@Override` chegou no Java 5, em 2004, junto com as anotações, e só para métodos de classes; usá-lo em métodos de interface passou a valer no Java 6. O retorno covariante também é do Java 5. Antes disso, quem sobrescrevia `Object clone()` devolvia `Object`, e cada chamada precisava de um cast: `(Ponto) p.clone()`.

## O que não se sobrescreve

Um método `final` não pode ser sobrescrito: é a forma de a superclasse garantir um comportamento.

```java nao-compila
class Seguranca {
    final boolean autorizar(String usuario) {
        return usuario.equals("admin");
    }
}

class SegurancaFalsa extends Seguranca {
    boolean autorizar(String usuario) {
        return true;
    }
}
```

Métodos `static` não são sobrescritos, e sim **escondidos** (*hidden*): a versão chamada é escolhida pelo tipo declarado, na compilação, como você viu ao estudar o [`invokestatic`](/assistir/junior-t1-e04). Já os métodos de instância seguem o objeto real:

```java executar
class Pai {
    static String quem() { return "Pai"; }
    String eu() { return "Pai"; }
}

class Filho extends Pai {
    static String quem() { return "Filho"; }
    @Override
    String eu() { return "Filho"; }
}

Pai p = new Filho();
System.out.println(p.quem() + " " + p.eu());
System.out.println(Pai.quem() + " " + Filho.quem());
```

```saida
Pai Filho
Pai Filho
```

Misturar os dois não compila: um método de instância não pode "sobrescrever" um `static`, nem o contrário.

```java nao-compila
class Pai {
    void salvar() { }
}

class Filho extends Pai {
    static void salvar() { }
}
```

E um método `private` nem é herdado. Declarar um método de mesmo nome na subclasse cria um método **independente**, que o código da superclasse nunca chama:

```java executar
class Motor {
    private String tipo() { return "genérico"; }

    String descrever() {
        return "motor " + tipo();
    }
}

class MotorEletrico extends Motor {
    String tipo() { return "elétrico"; }
}

System.out.println(new MotorEletrico().descrever());
```

```saida
motor genérico
```

> [!MATEMATICA]
> A chamada virtual custa uma consulta na tabela: ler a classe do objeto, ler a entrada N, saltar. São duas leituras de memória a mais que uma chamada direta, cerca de 1 ns. Num laço de 100 milhões de chamadas, 100 ms no pior caso. Na prática, o JIT percebe quando só uma classe aparece naquele ponto e troca a chamada virtual por uma direta, às vezes embutindo o corpo do método, e o custo cai para perto de zero.

> [!PROVA]
> Diante de um método redeclarado numa subclasse, pergunte, nesta ordem: a assinatura é igual? (se não, é sobrecarga); o original é `private`? (se sim, é um método novo); é `static` dos dois lados? (se sim, é esconder); depois confira acesso, retorno e exceções. Um `@Override` num método que não sobrescreve nada é erro de compilação.

> [!IA]
> Ao gerar uma subclasse, a IA às vezes escreve `equals(MinhaClasse outro)` ou `compareTo(Object o)` com o tipo errado, e o código compila como sobrecarga. Exija `@Override` em todo método que deveria sobrescrever; se a IA esquecer, acrescente e compile.

## Na IDE

- **Gerar a sobrescrita.** **Ctrl + O** (*Override Methods*) lista os métodos herdados e gera a assinatura certa, já com `@Override`.
- **Ver quem sobrescreve.** O ícone na margem ao lado do método (um círculo com seta) leva à versão da superclasse ou às sobrescritas; **Ctrl + Alt + B** lista as implementações.
- **Inspeção.** "Missing @Override annotation" marca os métodos que sobrescrevem sem a anotação, e **Alt + Enter** a acrescenta.

## Por baixo dos panos

Cada classe carregada tem uma **tabela de métodos virtuais** (a *vtable*), com uma entrada por método de instância que pode ser sobrescrito. A subclasse herda a tabela da superclasse e, para cada método sobrescrito, troca o ponteiro **na mesma posição**. Uma chamada `invokevirtual` vira: pegue a classe real do objeto, olhe a entrada de índice N da tabela dela, pule para lá. É por isso que `descrever()` de `Base`, chamando `nome()`, executa a versão da subclasse. Métodos `private`, `static` e construtores não entram na tabela: são chamados diretamente, com `invokespecial` ou `invokestatic`.

![As tabelas de métodos de Base e Derivada com as mesmas posições; só a posição 1, nome, aponta para um código novo na Derivada](/figuras/tabela-de-metodos.svg "A subclasse herda a tabela e troca só as entradas que sobrescreve.")

O retorno covariante tem um detalhe curioso. Para a JVM, `Object criar()` e `String criar()` são métodos **diferentes**, porque o descritor inclui o retorno, como você viu na [sobrecarga](/assistir/junior-t2-e02). O `javac` resolve gerando em `FabricaDeTexto` um terceiro método, sintético, o *método ponte*: `Object criar()`, que só chama `String criar()`. O `javap -p` mostra os dois. Já o `@Override` nem chega ao bytecode: é uma anotação só para o compilador.

## Resumo para a prova

- Sobrescrever: mesma assinatura, na subclasse, para um método de instância herdado
- Acesso igual ou mais aberto; retorno igual ou subtipo; primitivos, retorno idêntico
- Exceções verificadas: nunca novas nem mais amplas; não verificadas, livres
- `final` não pode ser sobrescrito; `static` é escondido, e misturar `static` com instância não compila
- Método `private` com o mesmo nome na subclasse é um método novo
- `@Override` num método que não sobrescreve nada não compila
- Parâmetros de tipos diferentes na subclasse criam uma sobrecarga, não uma sobrescrita
