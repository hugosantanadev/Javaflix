Todo objeto herda de `Object` três métodos que quase toda classe de verdade precisa sobrescrever: `toString`, que diz como o objeto aparece em texto; `equals`, que diz quando dois objetos são "iguais"; e `hashCode`, o número que permite às coleções encontrá-lo depressa. Os dois últimos têm um **contrato** que, quando quebrado, produz os bugs mais estranhos do Java: um `HashSet` que aceita duplicatas, um `contains` que não acha o que está lá dentro.

## As versões herdadas de `Object`

Sem sobrescrita, `equals` compara **identidade**, como `==`, e `toString` devolve o nome da classe, um `@` e o `hashCode` em hexadecimal:

```java executar
class Ponto {
    int x, y;
    Ponto(int x, int y) { this.x = x; this.y = y; }
}

public class Padrao {
    public static void main(String[] args) {
        Ponto a = new Ponto(1, 2);
        Ponto b = new Ponto(1, 2);
        System.out.println(a.equals(b) + " " + a.equals(a));
        String texto = a.toString();
        System.out.println(texto.startsWith("Ponto@") + " " + texto.substring(6).equals(Integer.toHexString(a.hashCode())));
    }
}
```

```saida
false true
true true
```

Para pontos, produtos e CPFs, isso raramente é o que se quer. Dois pontos com as mesmas coordenadas são o mesmo ponto, para quem usa a classe.

## Sobrescrevendo os três

```java executar
import java.util.HashSet;
import java.util.Objects;
import java.util.Set;

final class Produto {
    private final String codigo;
    private final String nome;

    Produto(String codigo, String nome) {
        this.codigo = codigo;
        this.nome = nome;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true; //> Atalho: o mesmo objeto é sempre igual a si.
        if (!(o instanceof Produto)) return false; //> Também cobre o null.
        Produto outro = (Produto) o;
        return codigo.equals(outro.codigo);
    }

    @Override
    public int hashCode() {
        return Objects.hash(codigo); //> Os mesmos campos do equals.
    }

    @Override
    public String toString() {
        return nome + " (" + codigo + ")";
    }
}

public class Catalogo {
    public static void main(String[] args) {
        Produto a = new Produto("X1", "Caneta");
        Produto b = new Produto("X1", "Caneta azul");
        Set<Produto> estoque = new HashSet<>();
        estoque.add(a);
        estoque.add(b);
        System.out.println(a.equals(b) + " " + (a.hashCode() == b.hashCode()));
        System.out.println(estoque.size() + " " + estoque);
        System.out.println("Item: " + a);
    }
}
```

```saida
true true
1 [Caneta (X1)]
Item: Caneta (X1)
```

> [!PENSE]
> `a` e `b` têm nomes diferentes. Por que o `HashSet` guardou só um dos dois?

A receita do `equals`: se é o mesmo objeto, `true`; se o outro não é do tipo (o que inclui `null`, porque `null instanceof` dá `false`), `false`; senão, compare os campos que definem a identidade, aqui o código. O `hashCode` usa **os mesmos campos**, e `Objects.hash` monta um número a partir deles. O `toString` é chamado sozinho pelo `println` e pela concatenação.

> [!CONVERSA]
> **equals:** Eu decido se dois objetos são iguais. Comparo os campos que importam e pronto.
>
> **hashCode:** E eu decido em que balde cada objeto mora. Se você disser que dois são iguais e eu mandá-los para baldes diferentes, o `HashSet` nunca vai encontrá-los juntos.
>
> **equals:** Então toda vez que eu mudar de critério...
>
> **hashCode:** ...eu mudo junto. Sempre os mesmos campos. Quem sobrescreve um de nós sem o outro está pedindo bug.

## O contrato

| `equals` precisa ser | Significa |
|---|---|
| Reflexivo | `x.equals(x)` é `true` |
| Simétrico | se `x.equals(y)`, então `y.equals(x)` |
| Transitivo | se `x.equals(y)` e `y.equals(z)`, então `x.equals(z)` |
| Consistente | o resultado não muda se os objetos não mudarem |
| Seguro com `null` | `x.equals(null)` é `false`, sem exceção |

E a regra que amarra os dois: **objetos iguais pelo `equals` precisam ter o mesmo `hashCode`**. O contrário não é exigido: objetos diferentes podem ter o mesmo `hashCode` (uma colisão), e isso é normal. Sobrescrever só o `equals` quebra as coleções baseadas em hash, porque elas procuram primeiro pelo `hashCode`:

```java executar
import java.util.HashSet;
import java.util.Set;

class Cpf {
    private final String numero;

    Cpf(String numero) {
        this.numero = numero;
    }

    @Override
    public boolean equals(Object o) {
        return o instanceof Cpf && ((Cpf) o).numero.equals(numero);
    }
}

public class Cadastro {
    public static void main(String[] args) {
        Set<Cpf> cpfs = new HashSet<>();
        cpfs.add(new Cpf("123"));
        System.out.println(new Cpf("123").equals(new Cpf("123")));
        System.out.println(cpfs.contains(new Cpf("123")));
    }
}
```

```saida
true
false
```

Os dois CPFs são iguais pelo `equals`, mas cada um tem o `hashCode` herdado, diferente, e o `HashSet` procura no lugar errado.

![Um HashSet com oito baldes: o primeiro Cpf vai para o balde 2 e o segundo, com outro hashCode herdado, procura no balde 6, vazio, e o equals nunca roda](/figuras/baldes-do-hashset.svg "O hashCode escolhe o balde; o equals só compara dentro dele.")

> [!ERRO]
> Sobrescrever o `equals` e esquecer o `hashCode`. O código compila sem aviso, os testes com `List` passam, e o bug aparece só quando o objeto vai para um `HashSet` ou vira chave de `HashMap`: duplicatas aceitas, buscas que não acham nada. Gere os dois juntos, sempre.

## A armadilha da assinatura

O `equals` de `Object` recebe um **`Object`**. Escrever `equals(Moeda outra)` não sobrescreve nada: cria uma sobrecarga, que só é escolhida quando o argumento é declarado como `Moeda`. As coleções chamam `equals(Object)` e nunca a encontram:

```java executar
import java.util.List;

class Moeda {
    final String codigo;
    Moeda(String codigo) { this.codigo = codigo; }

    public boolean equals(Moeda outra) {
        return outra != null && codigo.equals(outra.codigo);
    }
}

public class Cambio {
    public static void main(String[] args) {
        Moeda a = new Moeda("BRL");
        Moeda b = new Moeda("BRL");
        Object c = b;
        List<Moeda> lista = List.of(a);
        System.out.println(a.equals(b) + " " + a.equals(c) + " " + lista.contains(b));
    }
}
```

```saida
true false false
```

> [!PERGUNTAS]
> **P:** Se `a.equals(b)` deu `true`, por que `lista.contains(b)` deu `false`?
>
> **R:** Porque o `contains` foi escrito para qualquer objeto e chama `equals(Object)`. A versão com `Moeda` é um método à parte, que só o compilador escolhe quando o argumento é declarado como `Moeda`.

Com `@Override`, o erro aparece na hora:

```java nao-compila
class Moeda {
    String codigo;

    @Override
    public boolean equals(Moeda outra) {
        return codigo.equals(outra.codigo);
    }
}
```

> [!PROVA]
> Nas questões de `equals` e `hashCode`, confira a assinatura (`public boolean equals(Object o)` e `public int hashCode()`, ambos `public`, porque não se fecha o acesso de um método herdado), se os dois usam os mesmos campos e se a classe é usada em `HashSet` ou `HashMap`. `Objects.equals(a, b)` compara tratando `null` dos dois lados. Os **records**, na temporada de [Java moderno](/assistir/junior-t5-e01), geram os três métodos automaticamente.

> [!ANTES]
> Antes do Java 7, não existia a classe `Objects`, e todo `equals` repetia a conferência de `null` à mão: `codigo == null ? outro.codigo == null : codigo.equals(outro.codigo)`. O `hashCode` era montado com a conta do 31 escrita linha a linha. Hoje, além de `Objects.equals` e `Objects.hash`, os records (Java 16) geram os dois métodos sozinhos.

> [!IA]
> Ao gerar `equals` e `hashCode`, a IA às vezes inclui campos que mudam com o tempo, como `saldo` ou `status`. Um objeto guardado num `HashSet` cujo campo muda depois fica no balde antigo e não é mais encontrado. Peça que use só os campos que identificam o objeto e que nunca mudam, como código ou CPF.

> [!MATEMATICA]
> Com um `hashCode` bem espalhado, um `HashSet` de 1 milhão de elementos acha um objeto com 1 ou 2 comparações de `equals`, em média. Com um `hashCode` constante (`return 1;`), que é legal pelo contrato, todos caem no mesmo balde: até 1.000.000 de comparações numa busca. Desde o Java 8, um balde com mais de 8 elementos vira uma árvore, e o pior caso cai para cerca de log₂ 1.000.000 ≈ 20 comparações, se a classe for `Comparable`.

## Na IDE

- **Gerar os dois juntos.** **Alt + Insert**, *equals() and hashCode()*, abre um assistente em que você escolhe os campos, e a IDE gera os dois métodos usando os mesmos.
- **Inspeção.** "equals() and hashCode() not paired" marca a classe que sobrescreve só um deles.
- **Ver o `toString` no depurador.** O painel *Variables* mostra o resultado do `toString` ao lado de cada objeto, o que torna um bom `toString` uma ferramenta de depuração.

## Por baixo dos panos

O `hashCode` herdado de `Object` **não** é o endereço de memória, ao contrário do que muita gente pensa: os objetos mudam de lugar a cada coleta de lixo, e o número precisa ser fixo. Na HotSpot, ele é sorteado na primeira chamada, por um gerador pseudoaleatório de cada thread, e guardado no cabeçalho do objeto, na mesma palavra que guarda o estado de trava, como você viu no [episódio de objetos](/assistir/junior-t1-e01).

Um `HashMap` usa o `hashCode` para escolher o *balde* (uma posição de um array interno), e só dentro do balde compara com `equals`, como na tabela hash do [episódio de estruturas de dados](/assistir/aprendiz-t4-e05). O `hashCode` da `String` é a soma de cada caractere multiplicado por potências de 31, `s[0]·31ⁿ⁻¹ + ... + s[n-1]`, e fica guardado num campo depois da primeira vez. O 31 é primo e ímpar, e `31 * i` vira `(i << 5) - i`, uma conta barata. Colisões existem: "Aa" e "BB" têm o mesmo `hashCode`, 2112, e mesmo assim são diferentes pelo `equals`.

## Resumo para a prova

- Sem sobrescrita: `equals` compara identidade; `toString` dá `Classe@hexadecimal`
- `equals`: reflexivo, simétrico, transitivo, consistente e `false` para `null`
- Iguais pelo `equals` exigem o mesmo `hashCode`; o contrário não é exigido
- Sobrescrever só o `equals` quebra `HashSet` e `HashMap`
- A assinatura é `public boolean equals(Object o)`; com outro parâmetro, é sobrecarga
- `equals` e `hashCode` precisam ser `public`
- `Objects.equals` e `Objects.hash` ajudam a escrever os dois
- O `hashCode` padrão não é o endereço de memória
