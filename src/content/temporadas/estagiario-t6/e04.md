Os oito tipos primitivos são rápidos e econômicos, mas não são objetos: não podem ficar numa `List`, não podem ser `null` e não têm métodos. Para cada um, Java tem uma classe **wrapper** que embrulha o valor num objeto. O compilador converte de um para o outro sozinho, e é nessas conversões automáticas que moram as armadilhas favoritas da prova. No fim, a classe `Math`, com os métodos de cálculo que a prova também cobra.

## Os oito wrappers

| Primitivo | Wrapper | Converter texto em primitivo |
|---|---|---|
| `byte` | `Byte` | `Byte.parseByte("1")` |
| `short` | `Short` | `Short.parseShort("1")` |
| `int` | `Integer` | `Integer.parseInt("1")` |
| `long` | `Long` | `Long.parseLong("1")` |
| `float` | `Float` | `Float.parseFloat("1.5")` |
| `double` | `Double` | `Double.parseDouble("1.5")` |
| `char` | `Character` | não tem; use `s.charAt(0)` |
| `boolean` | `Boolean` | `Boolean.parseBoolean("true")` |

Repare em `Integer` e `Character`: são os dois nomes que não são só o primitivo com inicial maiúscula. Os métodos `parseXxx` devolvem o **primitivo**; os `valueOf` devolvem o **wrapper**. Os construtores, como `new Integer(42)`, estão marcados como obsoletos e para remoção desde o Java 16.

```java executar
int a = Integer.parseInt("42");
Integer b = Integer.valueOf("42");
double c = Double.parseDouble("3.5");
boolean d = Boolean.parseBoolean("TRUE");
int e = Integer.parseInt("ff", 16); //> O segundo argumento é a base: ff em hexadecimal é 255.
System.out.println(a + b + " " + c + " " + d + " " + e); //> a + b vem antes do texto: 42 + 42 = 84.
try {
    Integer.parseInt("4.2");
} catch (NumberFormatException ex) {
    System.out.println(ex.getMessage());
}
```

```saida
84 3.5 true 255
For input string: "4.2"
```

`parseBoolean` ignora maiúsculas e devolve `false` para qualquer texto que não seja "true", sem lançar exceção. Já os números são exigentes: "4.2" não é um `int`, e o resultado é `NumberFormatException`. O segundo argumento de `parseInt` é a base, como no episódio de [bases numéricas](/assistir/aprendiz-t1-e01).

> [!CONVERSA]
> **int:** Eu sou 4 bytes e mais nada. Moro direto na variável, sem endereço, sem cabeçalho.
>
> **Integer:** E eu sou um objeto: tenho métodos, posso entrar numa `List` e posso ser `null` quando o valor ainda não existe.
>
> **int:** Esse seu `null` é justamente o problema. Quando alguém me pede o seu valor e você está vazio, quem leva a culpa é a linha que parecia uma soma inocente.
>
> **Integer:** Em compensação, o compilador nos converte sozinho, um no outro. Ninguém precisa escrever `intValue()`.
>
> **int:** E é por isso que ninguém vê quando a conversão falha.

## Autoboxing e unboxing

**Autoboxing** é o compilador embrulhar um primitivo quando o contexto pede um objeto; **unboxing** é o contrário. `Integer x = 5;` vira `Integer x = Integer.valueOf(5);`, e `int y = x;` vira `int y = x.intValue();`. O problema é que um wrapper pode ser `null`, e desembrulhar `null` lança `NullPointerException` numa linha que não tem nenhuma chamada de método visível:

```java executar
Integer estoque = null;
try {
    int total = estoque + 1; //> Unboxing escondido: estoque.intValue() num null.
} catch (NullPointerException e) {
    System.out.println("NullPointerException ao desembrulhar");
}
```

```saida
NullPointerException ao desembrulhar
```

> [!ERRO]
> Guardar um valor que pode faltar num wrapper e usá-lo numa conta: `Integer desconto = mapa.get(produto); preco - desconto`. Se o produto não estiver no mapa, `desconto` é `null` e a subtração lança `NullPointerException`. Teste o `null` antes, ou use um valor padrão, como `mapa.getOrDefault(produto, 0)`.

> [!ANTES]
> O autoboxing chegou no Java 5, em 2004, junto com os generics. Antes, guardar um número numa lista era `lista.add(new Integer(5))`, e ler de volta, `((Integer) lista.get(0)).intValue()`. O código ficou bem mais limpo, e os desembrulhos invisíveis viraram uma nova fonte de `NullPointerException`.

O autoboxing também não faz duas conversões de uma vez. `Long l = 42;` exigiria alargar `int` para `long` e depois embrulhar, e isso não é permitido:

```java nao-compila
Long l = 42;
```

Com `42L` compila, e `long l = 42;` também, porque aí só há o alargamento.

## O cache e o `==`

`Integer.valueOf` guarda prontos os objetos de -128 a 127. Dentro dessa faixa, dois autoboxings do mesmo valor devolvem **o mesmo objeto**, e `==` dá `true` por acaso. Fora dela, cada autoboxing cria um objeto novo. É a mesma armadilha do [pool de strings](/assistir/estagiario-t5-e05).

> [!PENSE]
> No trecho abaixo, `a == b` compara dois `Integer` com 127, e `c == d`, dois com 128. Os dois pares têm o mesmo valor dentro. Os dois `==` vão dar o mesmo resultado?

```java executar
Integer a = 127, b = 127;
Integer c = 128, d = 128;
System.out.println((a == b) + " " + (c == d) + " " + c.equals(d));
Long grande = 127L;
System.out.println(a.equals(127) + " " + grande.equals(127) + " " + (grande == 127));
```

```saida
true false true
true false true
```

Na segunda linha, `grande.equals(127)` dá `false`: o 127 vira um `Integer`, e o `equals` dos wrappers exige o **mesmo tipo**. Já `grande == 127` compara um wrapper com um primitivo, e aí o wrapper é desembrulhado e a comparação é numérica.

![Uma caixa com os objetos do cache, de -128 a 127; a e b apontam para o mesmo objeto 127 do cache, enquanto c e d apontam cada um para um objeto 128 próprio, fora do cache](/figuras/cache-do-integer.svg "Dentro da faixa, o valueOf devolve o objeto pronto. Fora dela, cria um novo a cada chamada.")

> [!LAPIS]
> Qual é a saída?
>
> ```java
> Integer a = 50, b = 50;
> Integer c = 500, d = 500;
> int e = 500;
> System.out.println((a == b) + " " + (c == d) + " " + (c == e));
> ```
>
> **Resposta:** `true false true`. O 50 está no cache, então `a` e `b` são o mesmo objeto. O 500 não está: `c` e `d` são objetos diferentes. Em `c == e`, um lado é primitivo, `c` é desembrulhado e a comparação é entre números.

> [!PROVA]
> Um clássico: numa `List<Integer>`, `remove(1)` remove o elemento do **índice** 1, porque existe um `remove(int)` e o compilador prefere o método que não precisa de autoboxing. Para remover o **valor** 1, é preciso `remove(Integer.valueOf(1))`.

```java executar
List<Integer> lista = new ArrayList<>(List.of(10, 20, 30, 1));
lista.remove(1);
System.out.println(lista);
lista.remove(Integer.valueOf(1));
System.out.println(lista);
```

```saida
[10, 30, 1]
[10, 30]
```

## A classe `Math`

Todos os métodos são estáticos. Os que a prova mais cobra, com o tipo de retorno, que é onde estão as pegadinhas:

| Método | Devolve |
|---|---|
| `max`, `min`, `abs` | o mesmo tipo do argumento (`int`, `long`, `float` ou `double`) |
| `pow`, `sqrt`, `cbrt` | sempre `double` |
| `floor`, `ceil` | `double`: o inteiro abaixo ou acima, como número real |
| `round(double)` | `long`; `round(float)` devolve `int` |
| `random()` | `double` de 0.0 (incluído) a 1.0 (excluído) |

```java executar
System.out.println(Math.max(3, 7) + " " + Math.min(-2, 5) + " " + Math.abs(-4.5));
System.out.println(Math.pow(2, 10) + " " + Math.sqrt(16) + " " + Math.cbrt(27));
System.out.println(Math.round(2.5) + " " + Math.round(-2.5) + " " + Math.round(2.4f));
System.out.println(Math.floor(-1.5) + " " + Math.ceil(-1.5) + " " + Math.ceil(1.2));
```

```saida
7 -2 4.5
1024.0 4.0 3.0
3 -2 2
-2.0 -1.0 2.0
```

O `round` arredonda o meio **para cima**, no sentido do infinito positivo: 2.5 vira 3, mas -2.5 vira -2. E `floor` de um negativo vai para longe do zero: o inteiro abaixo de -1.5 é -2.

![Uma reta numérica de -3 a 3 com os pontos 2.5 e -2.5: setas de floor vão para a esquerda, para 2 e -3; setas de ceil e round vão para a direita, para 3 e -2](/figuras/arredondamentos.svg "Para round, o empate vai sempre para o lado do infinito positivo, seja qual for o sinal.")

Como `round(double)` devolve `long`, guardá-lo num `int` sem cast não compila:

```java nao-compila
int arredondado = Math.round(2.5);
```

Para sortear um inteiro de 1 a 6, multiplica-se o `random` por 6, corta-se a parte decimal e soma-se 1.

> [!MATEMATICA]
> A fórmula geral para um inteiro de `min` a `max`, os dois incluídos, é `(int) (Math.random() * (max - min + 1)) + min`. O `random()` vai de 0 até quase 1; multiplicado por `max - min + 1`, vai de 0 até quase esse número, e o cast corta para os inteiros de 0 a `max - min`. Somando `min`, chega-se de `min` a `max`. Para um dado, 6 − 1 + 1 = 6 valores: de 0 a 5, mais 1. Para sortear de 10 a 20, são 20 − 10 + 1 = **11** valores: `(int) (Math.random() * 11) + 10`.

```java executar
boolean dentro = true;
for (int i = 0; i < 1000; i++) {
    int dado = (int) (Math.random() * 6) + 1;
    if (dado < 1 || dado > 6) dentro = false;
}
System.out.println(dentro);
```

```saida
true
```

> [!IA]
> A IA raramente compara wrappers com `==` em código novo, mas não costuma apontar isso ao revisar código existente, porque os testes com números pequenos passam. Também é comum ela escrever `list.remove(i)` numa `List<Integer>` querendo remover um valor. Peça a revisão explícita de `==` entre wrappers, de `remove` em listas de `Integer` e de unboxing de valores que podem ser `null`.

## Na IDE

- **`==` entre wrappers.** O IntelliJ marca a comparação com o aviso "Number objects are compared using '==', not 'equals()'", e o **Alt + Enter** troca pelo `equals`.
- **Boxing desnecessário.** `Integer.valueOf(5)` onde um `int` bastaria aparece como "Unnecessary boxing", com a correção automática.
- **Ver o objeto.** No depurador, um `Integer` aparece com um número de identidade, como `{Integer@812}`: com 127, `a` e `b` mostram o mesmo número; com 128, números diferentes.

## Por baixo dos panos

O cache fica numa classe interna, a `Integer.IntegerCache`, que cria os 256 objetos quando a classe `Integer` é carregada. O limite de cima pode ser aumentado com a opção `-XX:AutoBoxCacheMax`, e a especificação só garante a faixa de -128 a 127: por isso `c == d` com 128 é um comportamento em que nunca se deve confiar. `Byte`, `Short`, `Long` e `Character` têm caches parecidos; `Float` e `Double` não têm nenhum.

Embrulhar custa caro. Um `int` ocupa 4 bytes; um `Integer` é um objeto de 16 bytes no heap, mais a referência para ele. Uma `List<Integer>` com um milhão de números ocupa várias vezes a memória de um `int[]` e espalha os valores pelo heap, longe do cache. É o problema que o projeto Valhalla quer resolver, com classes de valor que se comportam como objetos mas são guardadas como primitivos.

Os métodos de `Math` são *intrínsecos*: o JIT troca `Math.sqrt` por uma única instrução do processador. E o [complemento de dois](/assistir/aprendiz-t3-e02) aparece aqui também: `Math.abs(Integer.MIN_VALUE)` é negativo, porque o positivo correspondente não cabe num `int`. Quando estouro é inaceitável, os métodos `Exact` lançam exceção em vez de dar a volta, e `floorMod` dá o resto sempre com o sinal do divisor:

```java executar
System.out.println(Math.abs(Integer.MIN_VALUE));
try {
    Math.addExact(Integer.MAX_VALUE, 1);
} catch (ArithmeticException e) {
    System.out.println(e.getMessage());
}
System.out.println(Math.floorMod(-7, 3) + " " + (-7 % 3));
```

```saida
-2147483648
integer overflow
2 -1
```

## Resumo para a prova

- `parseXxx` devolve o primitivo; `valueOf` devolve o wrapper; texto inválido lança `NumberFormatException`
- `Boolean.parseBoolean` nunca lança exceção: só "true", sem diferenciar maiúsculas, vira `true`
- Desembrulhar `null` lança `NullPointerException`
- `Long l = 42` não compila: o autoboxing não alarga antes de embrulhar
- Cache de -128 a 127: `==` entre wrappers só "funciona" nessa faixa; use `equals`
- `equals` entre wrappers de tipos diferentes é sempre `false`
- `list.remove(1)` remove pelo índice; `remove(Integer.valueOf(1))`, pelo valor
- `pow`, `sqrt`, `floor` e `ceil` devolvem `double`; `round(double)` devolve `long`
- `round` arredonda o meio para cima: `round(-2.5)` é -2
