O **Spring** é o framework mais usado em backends Java, e o coração dele não é a parte web nem a de banco de dados: é um **contêiner** que cria os objetos da aplicação e os liga uns aos outros. Essa ideia, a **inversão de controle**, e a técnica que a realiza, a **injeção de dependências**, explicam quase tudo o que o Spring faz, das anotações às mensagens de erro na inicialização. Entendê-las antes de escrever o primeiro controller evita horas de confusão com "bean não encontrado".

## O problema

Um serviço de pedidos precisa calcular o frete. O jeito mais direto é criar o calculador lá dentro:

```java
public class PedidoService {
    private final FreteCorreios frete = new FreteCorreios();

    public BigDecimal total(BigDecimal itens, BigDecimal pesoKg) {
        return itens.add(frete.calcular(pesoKg));
    }
}
```

Funciona, mas o `PedidoService` ficou **acoplado** aos Correios. Trocar de transportadora exige mudar o serviço; testá-lo exige calcular um frete de verdade, talvez chamando a API dos Correios; e cada classe que precisa de frete cria o seu próprio, com a sua própria configuração.

A saída é inverter quem decide: o serviço declara **do que precisa**, uma interface `Frete`, e recebe a implementação pronta pelo construtor. Quem monta os objetos escolhe qual:

```java executar
import java.math.BigDecimal;

public class InjecaoManual {
    interface Frete {
        BigDecimal calcular(BigDecimal pesoKg);
    }

    static class FreteCorreios implements Frete {
        public BigDecimal calcular(BigDecimal pesoKg) {
            return new BigDecimal("12.00").add(pesoKg.multiply(new BigDecimal("2.50")));
        }
    }

    static class PedidoService {
        private final Frete frete;

        PedidoService(Frete frete) {
            this.frete = frete;
        }

        BigDecimal total(BigDecimal itens, BigDecimal pesoKg) {
            return itens.add(frete.calcular(pesoKg));
        }
    }

    public static void main(String[] args) {
        PedidoService producao = new PedidoService(new FreteCorreios());
        System.out.println("produção: " + producao.total(new BigDecimal("100.00"), new BigDecimal("2")));

        PedidoService teste = new PedidoService(peso -> BigDecimal.ZERO);
        System.out.println("teste, com frete grátis falso: " + teste.total(new BigDecimal("100.00"), new BigDecimal("2")));
    }
}
```

```saida
produção: 117.00
teste, com frete grátis falso: 100.00
```

Isso é **injeção de dependências**, e não precisa de framework nenhum. O mesmo `PedidoService` funciona com o frete real e com um falso, criado com uma *lambda*, para o teste. O problema é que numa aplicação de verdade há centenas de classes, e alguém precisa criá-las na ordem certa e passar cada dependência para quem precisa dela. É esse trabalho que o Spring assume.

## O contêiner do Spring

Na **inversão de controle**, o seu código não cria os objetos de que depende: um contêiner os cria e os entrega. No Spring, o contêiner é o `ApplicationContext`, e cada objeto que ele gerencia é um **bean**. Há duas formas de declarar um bean:

| Forma | Quando usar |
|---|---|
| Anotar a classe com `@Component`, ou com um estereótipo: `@Service`, `@Repository`, `@Controller`, `@RestController` | Classes suas; o Spring as encontra varrendo os pacotes |
| Um método `@Bean` numa classe `@Configuration` | Classes de bibliotecas, que você não pode anotar, ou que precisam de configuração na criação |

```java
@Service
public class PedidoService {
    private final Frete frete;

    public PedidoService(Frete frete) {
        this.frete = frete;
    }
}

@Configuration
public class ClientesHttp {
    @Bean
    HttpClient httpClient() {
        return HttpClient.newBuilder().connectTimeout(Duration.ofSeconds(2)).build();
    }
}
```

Os estereótipos são todos `@Component` para o contêiner; a diferença é de intenção, e o `@Repository` ainda traduz exceções do banco para as do Spring. A varredura começa no pacote da classe com `@SpringBootApplication` e desce pelos subpacotes: uma classe anotada num pacote fora dessa árvore simplesmente não é encontrada.

### Injeção pelo construtor

Quando uma classe tem um só construtor, o Spring o usa e injeta cada parâmetro com o bean do tipo correspondente, sem anotação nenhuma. É a forma recomendada: os campos podem ser `final`, a classe não pode ser criada sem as suas dependências, e um teste a monta com `new`, sem Spring. Existe também a injeção em campo, com `@Autowired` direto no atributo, comum em código antigo e em tutoriais, mas que esconde as dependências, impede o `final` e obriga o teste a usar reflexão ou o próprio Spring.

## Quando o Spring não sabe o que injetar

Todas as mensagens abaixo são reais, do Spring Framework 7 e do Spring Boot 4.1.

**Mais de um candidato.** Com duas implementações de `Frete` e um parâmetro do tipo `Frete`:

```text
NoUniqueBeanDefinitionException: No qualifying bean of type 'Frete' available:
expected single matching bean but found 2: correios,transportadora
```

Numa aplicação Spring Boot, o erro vem num relatório mais legível, na inicialização:

```text
***************************
APPLICATION FAILED TO START
***************************

Description:

Parameter 0 of constructor in br.com.javaflix.loja.PedidoService required a single bean, but 2 were found:
	- correios: defined in file [...\br\com\javaflix\loja\Correios.class]
	- transportadora: defined in file [...\br\com\javaflix\loja\Transportadora.class]

Action:

Consider marking one of the beans as @Primary, updating the consumer to accept multiple beans,
or using @Qualifier to identify the bean that should be consumed
```

O próprio relatório lista as saídas:

- **`@Primary`** em uma das implementações: ela vence quando houver ambiguidade.
- **`@Qualifier("transportadora")`** no parâmetro: escolhe pelo nome do bean, que por padrão é o nome da classe com a inicial minúscula.
- **Receber todas**: um parâmetro `List<Frete>` recebe as duas, e um `Map<String, Frete>`, as duas indexadas pelo nome. É o caminho quando a escolha depende de cada pedido, como "o frete mais barato".
- **O nome do parâmetro**: se ele coincidir com o nome de um bean, como `Frete correios`, o Spring usa esse bean. Funciona, mas é frágil: renomear a variável muda o comportamento.

**Nenhum candidato.** Esqueceu a anotação, ou a classe está fora do pacote varrido:

```text
NoSuchBeanDefinitionException: No qualifying bean of type 'Frete' available:
expected at least 1 bean which qualifies as autowire candidate.
```

**Dependência circular.** `A` precisa de `B` no construtor, e `B` precisa de `A`:

```text
BeanCurrentlyInCreationException: Error creating bean with name 'a': Requested bean is currently in creation:
Is there an unresolvable circular reference or an asynchronous initialization dependency?
```

Com injeção pelo construtor, não há ordem possível para criar os dois. Com injeção em campo, o Spring conseguia contornar, criando um deles pela metade; desde o Spring Boot 2.6, isso também falha por padrão. Um ciclo quase sempre indica um desenho a corrigir: as duas classes fazem coisas demais, e a parte que as duas usam merece uma terceira classe.

## Escopos

Por padrão, cada bean é um **singleton**: o contêiner cria **uma** instância e a entrega a todos que a pedirem. Com `@Scope("prototype")`, cada pedido recebe uma instância nova:

```text
singleton: true
prototype: false
```

Esses são os resultados de `ctx.getBean("x") == ctx.getBean("x")` para um bean de cada escopo. Aplicações web têm ainda os escopos `request` e `session`, com uma instância por requisição ou por sessão.

> [!ATENCAO]
> Um singleton atende todas as requisições ao mesmo tempo, em threads diferentes. Um campo mutável num `@Service`, como `private BigDecimal ultimoTotal`, é compartilhado entre os usuários e vira uma condição de corrida, como as do [episódio de código thread-safe](/assistir/senior-t2-e01). Serviços devem ser **sem estado**: os dados de cada operação vivem nas variáveis locais e nos parâmetros.

## Ciclo de vida

O contêiner também avisa quando um bean fica pronto e quando vai ser destruído. Um método anotado com `@PostConstruct` roda depois que as dependências foram injetadas, por exemplo para carregar um cache; um com `@PreDestroy`, quando a aplicação está encerrando, para fechar recursos. Beans criados por `@Bean` que implementam `AutoCloseable` são fechados automaticamente.

## Por baixo dos panos

Como o Spring cria os objetos sem que você escreva `new`? Na inicialização, ele lê as classes dos pacotes varridos e os métodos `@Bean`, e registra uma **definição** para cada bean: a classe, o escopo, como criá-lo. Depois, para cada singleton, escolhe o construtor e, por **reflexão**, descobre os tipos dos parâmetros; para cada um, procura entre as definições as que são compatíveis com o tipo, cria essa dependência primeiro, de forma recursiva, e finalmente chama o construtor. A instância vai para um cache, e quem pedir o mesmo bean de novo recebe a mesma. O essencial cabe num contêiner de cinquenta linhas:

```java executar
import java.lang.reflect.Constructor;
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

public class MiniContainer {
    interface Frete { String nome(); }

    public static class Correios implements Frete {
        public String nome() { return "Correios"; }
    }

    public static class Transportadora implements Frete {
        public String nome() { return "Transportadora"; }
    }

    public static class Calculadora {
        private final Frete frete;

        public Calculadora(Frete frete) {
            this.frete = frete;
        }

        public String descrever() { return "pedido com frete " + frete.nome(); }
    }

    private final List<Class<?>> registradas = new ArrayList<>();
    private final Map<Class<?>, Object> singletons = new HashMap<>();

    MiniContainer registrar(Class<?>... classes) {
        registradas.addAll(List.of(classes));
        return this;
    }

    <T> T obter(Class<T> tipo) throws Exception {
        List<Class<?>> candidatas = registradas.stream().filter(tipo::isAssignableFrom).toList();
        if (candidatas.isEmpty()) {
            throw new IllegalStateException("nenhum bean do tipo " + tipo.getSimpleName());
        }
        if (candidatas.size() > 1) {
            throw new IllegalStateException("esperava 1 bean do tipo " + tipo.getSimpleName() + ", achou "
                    + candidatas.stream().map(Class::getSimpleName).toList());
        }
        Class<?> classe = candidatas.get(0);
        Object pronto = singletons.get(classe);
        if (pronto == null) {
            Constructor<?> construtor = classe.getConstructors()[0];
            Object[] argumentos = new Object[construtor.getParameterCount()];
            for (int i = 0; i < argumentos.length; i++) {
                argumentos[i] = obter(construtor.getParameterTypes()[i]);
            }
            pronto = construtor.newInstance(argumentos);
            singletons.put(classe, pronto);
        }
        return tipo.cast(pronto);
    }

    static void tentar(String titulo, MiniContainer c) {
        try {
            System.out.println(titulo + ": " + c.obter(Calculadora.class).descrever());
        } catch (Exception e) {
            System.out.println(titulo + ": ERRO, " + e.getMessage());
        }
    }

    public static void main(String[] args) throws Exception {
        tentar("um frete", new MiniContainer().registrar(Correios.class, Calculadora.class));
        tentar("dois fretes", new MiniContainer().registrar(Correios.class, Transportadora.class, Calculadora.class));
        tentar("nenhum frete", new MiniContainer().registrar(Calculadora.class));
        MiniContainer c = new MiniContainer().registrar(Correios.class, Calculadora.class);
        System.out.println("o mesmo objeto nas duas vezes: " + (c.obter(Calculadora.class) == c.obter(Calculadora.class)));
    }
}
```

```saida
um frete: pedido com frete Correios
dois fretes: ERRO, esperava 1 bean do tipo Frete, achou [Correios, Transportadora]
nenhum frete: ERRO, nenhum bean do tipo Frete
o mesmo objeto nas duas vezes: true
```

Os três cenários e os três erros são os mesmos do Spring de verdade. O Spring faz muito mais em cima disso: lê as definições sem carregar as classes, aplica `@Primary` e `@Qualifier`, detecta ciclos, chama os métodos de ciclo de vida e, principalmente, pode entregar no lugar do seu objeto um ***proxy***, um objeto intermediário que envolve o seu. É assim que um `@Transactional` abre e fecha transações em volta de cada chamada sem que você escreva uma linha: quem recebe o `PedidoService` injetado recebe, na verdade, o proxy dele.

## Resumo

- Injeção de dependências: a classe recebe o que precisa, de preferência pelo construtor, em vez de criar
- Inversão de controle: o contêiner (`ApplicationContext`) cria os beans e os liga
- Beans: `@Component` e estereótipos (`@Service`, `@Repository`, `@RestController`) ou métodos `@Bean` em `@Configuration`
- A varredura começa no pacote da classe `@SpringBootApplication`
- Ambiguidade: `@Primary`, `@Qualifier` ou receber `List`/`Map` de todos; falta: `NoSuchBeanDefinitionException`; ciclos falham na inicialização
- Singleton é o escopo padrão: serviços sem estado mutável
- Por baixo: definições, reflexão nos construtores, criação recursiva, cache de singletons e proxies
