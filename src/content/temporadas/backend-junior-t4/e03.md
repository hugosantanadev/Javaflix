Um **controller** é a fronteira entre o HTTP e o Java: ele recebe a requisição, extrai o que interessa do caminho, da query string e do corpo, chama o serviço que tem a regra de negócio e transforma o resultado numa resposta, com o status e o JSON certos. O Spring MVC faz quase todo esse trabalho a partir de anotações, inclusive as respostas de erro que o [episódio de desenho de APIs](/assistir/backend-junior-t2-e02) recomendava. Todas as trocas mostradas neste episódio foram executadas contra a API abaixo, com o Spring Boot 4.1.

## Uma API de produtos

```java
@RestController
@RequestMapping("/produtos")
public class ProdutoController {

    private final ProdutoService service;

    public ProdutoController(ProdutoService service) {
        this.service = service;
    }

    @GetMapping
    public List<Produto> listar(@RequestParam(defaultValue = "0") int pagina,
                                @RequestParam(defaultValue = "20") int tamanho) {
        return service.listar(pagina, tamanho);
    }

    @GetMapping("/{id}")
    public ResponseEntity<Produto> buscar(@PathVariable long id) {
        return service.buscar(id)
                .map(ResponseEntity::ok)
                .orElse(ResponseEntity.notFound().build());
    }

    @PostMapping
    public ResponseEntity<Produto> criar(@RequestBody NovoProduto novo) {
        Produto criado = service.criar(novo);
        return ResponseEntity.created(URI.create("/produtos/" + criado.id())).body(criado);
    }

    @PutMapping("/{id}")
    public ResponseEntity<Produto> substituir(@PathVariable long id, @RequestBody NovoProduto dados) {
        return service.substituir(id, dados)
                .map(ResponseEntity::ok)
                .orElse(ResponseEntity.notFound().build());
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    public void apagar(@PathVariable long id) {
        service.apagar(id);
    }

    @GetMapping("/busca")
    public List<Produto> buscarPorNome(@RequestParam String nome) {
        return service.buscarPorNome(nome);
    }
}
```

`Produto` e `NovoProduto` são `record`s: `Produto(long id, String nome, BigDecimal preco)`, a resposta, e `NovoProduto(String nome, BigDecimal preco)`, o que o cliente pode enviar, sem o `id`. O `@RestController` é um `@Controller` em que o retorno de cada método vira o corpo da resposta, convertido para JSON pelo Jackson; o `@RequestMapping` na classe define o prefixo comum dos caminhos.

Cada forma de retorno decide o status de um jeito:

| Retorno | Resposta |
|---|---|
| Um objeto ou lista | `200`, com o objeto em JSON |
| `ResponseEntity<T>` | Status, cabeçalhos e corpo escolhidos no código: `ok(...)`, `created(uri)`, `notFound()`, `noContent()` |
| `void` com `@ResponseStatus` | O status da anotação, sem corpo |

## De onde vêm os dados

| Anotação | Lê | Exemplo |
|---|---|---|
| `@PathVariable` | Um trecho do caminho | `/produtos/{id}` → `long id` |
| `@RequestParam` | A query string | `?pagina=1` → `int pagina` |
| `@RequestBody` | O corpo, convertido do JSON | `NovoProduto novo` |
| `@RequestHeader` | Um cabeçalho | `@RequestHeader("Idempotency-Key") String chave` |
| `@CookieValue` | Um cookie | `@CookieValue("sessao") String sessao` |

O `@RequestParam` é **obrigatório** por padrão; com `defaultValue`, ou com `required = false`, deixa de ser. E os valores chegam convertidos para o tipo do parâmetro: `int`, `long`, `LocalDate`, um `enum`.

## Os erros que o Spring trata sozinho

Com `spring.mvc.problemdetails.enabled=true` no `application.properties`, os erros de entrada saem no formato Problem Details da RFC 9457, sem uma linha de código:

```text
GET /produtos/abc
HTTP 400
Content-Type: application/problem+json
{"detail":"Failed to convert 'id' with value: 'abc'","instance":"/produtos/abc","status":400,"title":"Bad Request"}

GET /produtos/busca
HTTP 400
{"detail":"Required parameter 'nome' is not present.","instance":"/produtos/busca","status":400,"title":"Bad Request"}

PATCH /produtos/1
HTTP 405
Allow: GET, DELETE, PUT
{"detail":"Method 'PATCH' is not supported.","instance":"/produtos/1","status":405,"title":"Method Not Allowed"}

POST /produtos   com Content-Type: text/plain
HTTP 415
{"detail":"Content-Type 'text/plain;charset=UTF-8' is not supported.","instance":"/produtos","status":415,"title":"Unsupported Media Type"}

POST /produtos   com {"nome": "Headset",
HTTP 400
{"detail":"Failed to read request","instance":"/produtos","status":400,"title":"Bad Request"}

GET /produtos/1   com Accept: application/xml
HTTP 406
{"detail":"Acceptable representations: [application/json, application/*+json].","instance":"/produtos/1","status":406,"title":"Not Acceptable"}
```

São exatamente os status do [primeiro episódio da temporada de HTTP](/assistir/backend-junior-t2-e01): `405` com o `Allow`, `415` para um corpo num formato que a API não lê, `406` quando o cliente só aceita um formato que ela não produz. Repare também que `GET /produtos/busca` chegou ao método de busca, e não ao `/{id}` com o valor "busca": quando dois caminhos casam, o Spring prefere o que tem mais trechos literais.

## Controllers finos

O controller traduz HTTP, e só. Regras de negócio, como "o estoque não pode ficar negativo", ficam no serviço, que não sabe nada de HTTP e pode ser chamado por um controller, por uma fila de mensagens ou por um teste. Um controller que faz cálculos, acessa o banco e monta e-mails é difícil de testar e de reaproveitar. Pela mesma razão do [episódio de JSON](/assistir/backend-junior-t2-e03), o `@RequestBody` recebe um DTO, como o `NovoProduto`, e não a entidade do banco.

O `Location` acima é um caminho relativo, o que os clientes aceitam. Para gerar o endereço completo, com o host e a porta da requisição, há o `ServletUriComponentsBuilder.fromCurrentRequest().path("/{id}").buildAndExpand(criado.id()).toUri()`.

## Por baixo dos panos

Toda requisição chega primeiro a um único servlet, o **`DispatcherServlet`**, o "controlador de frente" do Spring MVC. Na inicialização, o `RequestMappingHandlerMapping` percorre os beans `@Controller`, lê as anotações de cada método por **reflexão** e monta uma tabela de rotas. A cada requisição, o `DispatcherServlet`:

1. Consulta a tabela e escolhe o método, preferindo os caminhos mais específicos; se o caminho existe com outro método, responde `405`.
2. Resolve cada parâmetro com o **resolvedor** da sua anotação: o de `@PathVariable` lê o caminho, o de `@RequestBody` escolhe um conversor de mensagem pelo `Content-Type`, e um serviço de conversão transforma texto em `long`, `int` ou datas.
3. Chama o método.
4. Converte o retorno com o conversor de mensagem compatível com o `Accept` do cliente, o Jackson para JSON.
5. Se algo lançou exceção, um **resolvedor de exceções** a transforma na resposta de erro.

Os passos 1 a 3 cabem num despachante de quarenta linhas, com anotações próprias:

```java executar
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;
import java.lang.reflect.Method;
import java.lang.reflect.Parameter;
import java.util.HashMap;
import java.util.Map;

public class MiniDispatcher {
    @Retention(RetentionPolicy.RUNTIME)
    @Target(ElementType.METHOD)
    @interface Get { String value(); }

    @Retention(RetentionPolicy.RUNTIME)
    @Target(ElementType.PARAMETER)
    @interface Variavel { String value(); }

    public static class ProdutoController {
        @Get("/produtos/{id}")
        public String buscar(@Variavel("id") long id) {
            return id == 2 ? "{\"id\":2,\"nome\":\"Mouse sem fio\"}" : null;
        }

        @Get("/produtos")
        public String listar() {
            return "[{\"id\":1},{\"id\":2}]";
        }
    }

    static Map<String, String> casar(String modelo, String caminho) {
        String[] m = modelo.split("/"), c = caminho.split("/");
        if (m.length != c.length) return null;
        Map<String, String> variaveis = new HashMap<>();
        for (int i = 0; i < m.length; i++) {
            if (m[i].startsWith("{")) variaveis.put(m[i].substring(1, m[i].length() - 1), c[i]);
            else if (!m[i].equals(c[i])) return null;
        }
        return variaveis;
    }

    static String despachar(Object controller, String caminho) throws Exception {
        for (Method metodo : controller.getClass().getMethods()) {
            Get get = metodo.getAnnotation(Get.class);
            if (get == null) continue;
            Map<String, String> variaveis = casar(get.value(), caminho);
            if (variaveis == null) continue;
            Parameter[] params = metodo.getParameters();
            Object[] argumentos = new Object[params.length];
            for (int i = 0; i < params.length; i++) {
                String texto = variaveis.get(params[i].getAnnotation(Variavel.class).value());
                try {
                    argumentos[i] = params[i].getType() == long.class ? Long.parseLong(texto) : texto;
                } catch (NumberFormatException e) {
                    return "400 Failed to convert '" + params[i].getAnnotation(Variavel.class).value() + "' with value: '" + texto + "'";
                }
            }
            Object resultado = metodo.invoke(controller, argumentos);
            return resultado == null ? "404" : "200 " + resultado;
        }
        return "404 nenhuma rota";
    }

    public static void main(String[] args) throws Exception {
        ProdutoController controller = new ProdutoController();
        for (String caminho : new String[] {"/produtos", "/produtos/2", "/produtos/99", "/produtos/abc", "/clientes"}) {
            System.out.println("GET " + caminho + " -> " + despachar(controller, caminho));
        }
    }
}
```

```saida
GET /produtos -> 200 [{"id":1},{"id":2}]
GET /produtos/2 -> 200 {"id":2,"nome":"Mouse sem fio"}
GET /produtos/99 -> 404
GET /produtos/abc -> 400 Failed to convert 'id' with value: 'abc'
GET /clientes -> 404 nenhuma rota
```

A anotação `@Variavel` precisa dizer o nome da variável porque, sem a opção `-parameters` do compilador, os nomes dos parâmetros não sobrevivem no bytecode. O Spring Boot liga essa opção no parent, e por isso o `@PathVariable long id` funciona sem repetir o `"id"`. O Spring de verdade monta a tabela de rotas uma vez, na inicialização, em vez de varrer os métodos a cada requisição, e o desafio deste episódio acrescenta as peças que faltam: a escolha entre rotas pelo método HTTP, a prioridade dos caminhos literais, os parâmetros da query string e o `405`.

## Resumo

- `@RestController` + `@RequestMapping("/produtos")`; `@GetMapping`, `@PostMapping`, `@PutMapping`, `@PatchMapping`, `@DeleteMapping`
- `@PathVariable`, `@RequestParam` (obrigatório, a menos que tenha `defaultValue`), `@RequestBody`, `@RequestHeader`
- Retorno direto dá `200`; `ResponseEntity` escolhe status e cabeçalhos: `created(uri)` para `201`, `notFound()`, `noContent()`
- Com Problem Details ligado, o Spring responde sozinho `400` (conversão, parâmetro ausente, JSON quebrado), `405` com `Allow`, `415` e `406`
- Caminhos literais têm prioridade sobre os com variáveis
- Controllers finos: só HTTP; regras no serviço; DTOs no `@RequestBody`
- Por baixo: `DispatcherServlet`, tabela de rotas montada por reflexão, resolvedores de argumentos, conversores de mensagem
