A mesma aplicação roda no seu computador, nos testes automáticos, em homologação e em produção, e em cada lugar ela precisa de valores diferentes: o endereço do banco, a senha, o tempo limite de um pagamento, se o e-mail é enviado de verdade ou só impresso no console. Nada disso deve estar no código. O Spring Boot lê a **configuração externa** de várias fontes, numa ordem de prioridade bem definida, e a entrega para a aplicação já convertida e validada. Os **perfis** agrupam as diferenças de cada ambiente. As saídas deste episódio foram obtidas rodando a mesma aplicação com o Spring Boot 4.1, mudando só a configuração.

## application.properties

O arquivo `src/main/resources/application.properties` guarda os valores padrão:

```properties
spring.application.name=loja
loja.nome=Loja Javaflix
loja.frete.gratis-a-partir=200.00
loja.frete.taxa-fixa=19.90
loja.tempo-limite-pagamento=15m
loja.cupons-ativos=BEMVINDO,FRETE10
```

O mesmo pode ser escrito em YAML, no `application.yml`, com a hierarquia por indentação. Os dois formatos são equivalentes; o importante é escolher um por projeto.

```yaml
loja:
  nome: Loja Javaflix
  frete:
    gratis-a-partir: 200.00
    taxa-fixa: 19.90
  tempo-limite-pagamento: 15m
```

As propriedades `spring.*`, `server.*`, `logging.*` e `management.*` configuram o próprio Spring Boot; o prefixo `loja` é da aplicação.

## Lendo a configuração

Para um valor solto, há o `@Value`, com um padrão depois dos dois-pontos:

```java
public Relatorio(@Value("${loja.suporte.email:suporte@loja.exemplo}") String suporte) { ... }
```

Para um grupo de propriedades, o melhor é um `record` com `@ConfigurationProperties`, que liga o prefixo inteiro de uma vez, converte cada valor para o tipo do componente e pode validar tudo na inicialização:

```java
@Validated
@ConfigurationProperties("loja")
public record LojaProperties(
        @NotBlank String nome,
        @Valid Frete frete,
        Duration tempoLimitePagamento,
        List<String> cuponsAtivos) {

    public record Frete(@NotNull BigDecimal gratisAPartir, BigDecimal taxaFixa) {}
}
```

Com `@ConfigurationPropertiesScan` na classe principal, o `LojaProperties` vira um bean e pode ser injetado como qualquer outro. O resultado, com o arquivo acima:

```text
LojaProperties[nome=Loja Javaflix, frete=Frete[gratisAPartir=200.00, taxaFixa=19.90], tempoLimitePagamento=PT15M, cuponsAtivos=[BEMVINDO, FRETE10]]
```

Três conversões aconteceram sozinhas: `gratis-a-partir`, em *kebab case*, chegou ao componente `gratisAPartir`; `15m` virou a `Duration` de 15 minutos, `PT15M`; e a lista separada por vírgulas virou uma `List<String>`. Essa flexibilidade nos nomes, a **vinculação relaxada**, é o que permite a mesma propriedade vir de um arquivo, da linha de comando ou de uma variável de ambiente.

## Perfis

Um **perfil** é um nome, como `dev` ou `prod`, que ativa um arquivo e beans extras. O arquivo `application-dev.properties` só é lido com o perfil `dev` ativo, e os valores dele **sobrepõem** os do `application.properties`:

```properties
# application-dev.properties
loja.frete.taxa-fixa=0.00
loja.suporte.email=dev@loja.exemplo
```

```properties
# application-prod.properties
loja.tempo-limite-pagamento=10m
```

Beans também podem depender de perfis. Em desenvolvimento, o notificador só imprime; em produção, envia e-mail:

```java
@Component
@Profile("!prod")
public class NotificadorConsole implements Notificador { ... }

@Component
@Profile("prod")
public class NotificadorEmail implements Notificador { ... }
```

O perfil é ativado com `spring.profiles.active`, que pode vir de qualquer fonte de configuração. Sem perfil nenhum:

```text
No active profile set, falling back to 1 default profile: "default"
perfis ativos: []
LojaProperties[nome=Loja Javaflix, frete=Frete[gratisAPartir=200.00, taxaFixa=19.90], tempoLimitePagamento=PT15M, cuponsAtivos=[BEMVINDO, FRETE10]]
suporte: suporte@loja.exemplo
[console] pedido 42 confirmado
```

Com `--spring.profiles.active=dev` na linha de comando:

```text
The following 1 profile is active: "dev"
perfis ativos: [dev]
LojaProperties[nome=Loja Javaflix, frete=Frete[gratisAPartir=200.00, taxaFixa=0.00], tempoLimitePagamento=PT15M, cuponsAtivos=[BEMVINDO, FRETE10]]
suporte: dev@loja.exemplo
[console] pedido 42 confirmado
```

A taxa e o e-mail de suporte vieram do arquivo do perfil; o resto, do arquivo padrão.

## A ordem de prioridade

Quando a mesma propriedade aparece em mais de uma fonte, vence a de **maior prioridade**. As principais, da mais forte para a mais fraca:

| Fonte | Exemplo |
|---|---|
| Argumentos de linha de comando | `java -jar loja.jar --loja.frete.gratis-a-partir=99` |
| Variáveis de ambiente | `LOJA_FRETE_GRATISAPARTIR=150` |
| `application-{perfil}.properties` | `application-prod.properties` |
| `application.properties` | O arquivo do projeto |
| Padrões no código | `@Value("${x:padrao}")` |

As variáveis de ambiente seguem uma regra de nomes, porque o sistema operacional não aceita pontos nem hífens nelas: os pontos viram `_`, os hífens somem e tudo vai para maiúsculas. Com `SPRING_PROFILES_ACTIVE=prod` e `LOJA_FRETE_GRATISAPARTIR=150` no ambiente:

```text
The following 1 profile is active: "prod"
LojaProperties[nome=Loja Javaflix, frete=Frete[gratisAPartir=150, taxaFixa=19.90], tempoLimitePagamento=PT10M, cuponsAtivos=[BEMVINDO, FRETE10]]
[e-mail] pedido 42 confirmado
```

O frete veio da variável de ambiente, o tempo limite do arquivo `prod`, e o notificador de produção foi o escolhido. Com a variável **e** um argumento `--loja.frete.gratis-a-partir=99`, o argumento vence:

```text
LojaProperties[nome=Loja Javaflix, frete=Frete[gratisAPartir=99, taxaFixa=19.90], tempoLimitePagamento=PT15M, cuponsAtivos=[BEMVINDO, FRETE10]]
```

É essa ordem que torna o mesmo JAR implantável em qualquer lugar: o arquivo do projeto tem os padrões, e cada ambiente ajusta o que precisa por variáveis de ambiente, que é como Docker e Kubernetes passam configuração para os programas.

## Configuração errada não sobe

Com `@Validated` no `LojaProperties`, uma configuração inválida impede a aplicação de subir, com um relatório que diz qual propriedade, qual valor e de onde ele veio:

```text
***************************
APPLICATION FAILED TO START
***************************

Description:

Binding to target br.com.javaflix.loja.LojaProperties failed:

    Property: loja.nome
    Value: ""
    Origin: "loja.nome" from property source "commandLineArgs"
    Reason: não deve estar em branco

Action:

Update your application's configuration
```

Um valor que não pode ser convertido tem o mesmo tratamento:

```text
Failed to bind properties under 'loja.tempo-limite-pagamento' to java.time.Duration:

    Property: loja.tempo-limite-pagamento
    Value: "quinze"
    Origin: "loja.tempo-limite-pagamento" from property source "commandLineArgs"
    Reason: failed to convert java.lang.String to java.time.Duration (caused by java.lang.IllegalArgumentException: 'quinze' is not a valid duration)
```

Falhar na inicialização é muito melhor do que subir e quebrar na primeira compra, às três da manhã.

## Segredos

> [!ATENCAO]
> Senhas, tokens e chaves de API não vão para o `application.properties` versionado no Git. O arquivo pode referenciar uma variável, como `spring.datasource.password=${DB_PASSWORD}`, e o valor real chega pelo ambiente: uma variável no servidor, um *secret* do Kubernetes ou um cofre de segredos. Se um segredo chegou a ser commitado, ele está vazado e precisa ser trocado, mesmo que o commit seja apagado.

## Por baixo dos panos

O `Environment` do Spring guarda uma lista ordenada de **fontes de propriedades**: os argumentos de linha de comando, as variáveis de ambiente, os arquivos de cada perfil ativo, o arquivo padrão. Ler uma propriedade é percorrer a lista e parar na primeira fonte que a tem. Para as variáveis de ambiente, o nome é traduzido antes da busca. A resolução cabe em poucas linhas:

```java executar
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class Fontes {
    record Fonte(String nome, Map<String, String> valores) {}

    /** loja.frete.gratis-a-partir vira LOJA_FRETE_GRATISAPARTIR: pontos viram _, hífens somem, tudo em maiúsculas. */
    static String comoVariavelDeAmbiente(String propriedade) {
        return propriedade.replace("-", "").replace('.', '_').toUpperCase();
    }

    static String resolver(List<Fonte> fontes, String propriedade) {
        for (Fonte f : fontes) {
            String chave = f.nome().equals("variáveis de ambiente") ? comoVariavelDeAmbiente(propriedade) : propriedade;
            String valor = f.valores().get(chave);
            if (valor != null) return valor + "  (de " + f.nome() + ")";
        }
        return "não definida";
    }

    static Map<String, String> mapa(String... pares) {
        Map<String, String> m = new LinkedHashMap<>();
        for (int i = 0; i < pares.length; i += 2) m.put(pares[i], pares[i + 1]);
        return m;
    }

    public static void main(String[] args) {
        Fonte base = new Fonte("application.properties", mapa(
                "loja.frete.gratis-a-partir", "200.00",
                "loja.frete.taxa-fixa", "19.90",
                "loja.tempo-limite-pagamento", "15m"));
        Fonte prod = new Fonte("application-prod.properties", mapa("loja.tempo-limite-pagamento", "10m"));
        Fonte ambiente = new Fonte("variáveis de ambiente", mapa("LOJA_FRETE_GRATISAPARTIR", "150"));
        Fonte linha = new Fonte("linha de comando", mapa("loja.frete.gratis-a-partir", "99"));

        List<Fonte> emOrdem = List.of(linha, ambiente, prod, base);
        for (String p : List.of("loja.frete.gratis-a-partir", "loja.frete.taxa-fixa", "loja.tempo-limite-pagamento", "loja.suporte.email")) {
            System.out.println(p + " = " + resolver(emOrdem, p));
        }
        System.out.println("sem a linha de comando: loja.frete.gratis-a-partir = "
                + resolver(List.of(ambiente, prod, base), "loja.frete.gratis-a-partir"));
        System.out.println("variável de ambiente de loja.frete.gratis-a-partir: " + comoVariavelDeAmbiente("loja.frete.gratis-a-partir"));
    }
}
```

```saida
loja.frete.gratis-a-partir = 99  (de linha de comando)
loja.frete.taxa-fixa = 19.90  (de application.properties)
loja.tempo-limite-pagamento = 10m  (de application-prod.properties)
loja.suporte.email = não definida
sem a linha de comando: loja.frete.gratis-a-partir = 150  (de variáveis de ambiente)
variável de ambiente de loja.frete.gratis-a-partir: LOJA_FRETE_GRATISAPARTIR
```

São os mesmos valores que a aplicação real recebeu nos cenários da aula. A segunda metade do trabalho é o **vínculo**: o `Binder` do Spring Boot percorre os componentes do `record`, traduz cada nome para *kebab case*, procura a propriedade, converte o texto para o tipo do componente e, para componentes que também são `record`s, repete o processo com o prefixo mais longo. O desafio deste episódio implementa esse vínculo.

## Resumo

- `application.properties` (ou `.yml`) guarda os padrões; prefixos próprios, como `loja.*`, para a aplicação
- `@Value("${chave:padrao}")` para valores soltos; `@ConfigurationProperties` com `record` para grupos, com conversão e `@Validated`
- Vinculação relaxada: `gratis-a-partir` no arquivo, `gratisAPartir` no Java, `LOJA_FRETE_GRATISAPARTIR` no ambiente
- Perfis: `application-{perfil}.properties` e `@Profile`; ativados com `spring.profiles.active`
- Prioridade: linha de comando > variáveis de ambiente > arquivo do perfil > arquivo padrão
- Configuração inválida impede a inicialização, com um relatório da propriedade, do valor e da origem
- Segredos nunca no Git: `${DB_PASSWORD}` e o valor real vindo do ambiente
