Uma API recebe dados de quem ela não controla: aplicativos com defeitos, versões antigas, pessoas testando limites e, às vezes, atacantes. Toda entrada precisa ser **validada** antes de chegar à regra de negócio, e todo erro precisa virar uma resposta clara, com o status certo e sem vazar detalhes internos. O Spring resolve as duas coisas com o **Bean Validation**, que declara as regras em anotações, e com os **tratadores de exceção**, que centralizam a tradução de erros em respostas HTTP. Tudo o que aparece aqui foi executado com o Spring Boot 4.1 e o Hibernate Validator, a implementação padrão do Bean Validation.

> [!ANTES]
> Antes do Bean Validation, padronizado em 2009 como JSR 303, cada camada validava do seu jeito: um `if` no controller, outro no serviço, uma terceira regra no JavaScript da página, e as três divergiam com o tempo. As anotações no próprio objeto puseram a regra num lugar só, lida tanto pelo Spring quanto pelo Hibernate.

## Bean Validation

Com o starter `spring-boot-starter-validation`, as regras ficam no próprio DTO:

```java
public record NovoProduto(
        @NotBlank @Size(max = 40) String nome,
        @NotNull @DecimalMin("0.01") BigDecimal preco,
        @Min(0) int estoque) {}
```

| Anotação | Exige |
|---|---|
| `@NotNull` | Que o valor exista |
| `@NotBlank` | Texto não nulo e com algo além de espaços |
| `@NotEmpty` | Texto ou coleção não nulo e não vazio |
| `@Size(min, max)` | Tamanho de texto ou coleção dentro dos limites |
| `@Min`, `@Max` | Inteiros dentro dos limites |
| `@DecimalMin`, `@DecimalMax` | Decimais, como preços, dentro dos limites |
| `@Positive`, `@PositiveOrZero` | Números maiores que zero, ou que não sejam negativos |
| `@Email` | Texto em formato de e-mail |
| `@Pattern(regexp)` | Texto que casa com uma expressão regular |
| `@Past`, `@Future` | Datas no passado ou no futuro |

As regras só são verificadas quando alguém pede: no controller, com `@Valid` antes do `@RequestBody`.

> [!PENSE]
> O formulário do aplicativo já impede o preço negativo. Por que a API precisa validar de novo? Quem mais, além do aplicativo, consegue mandar uma requisição para ela?

```java
@PostMapping
public ResponseEntity<Produto> criar(@Valid @RequestBody NovoProduto novo) { ... }
```

Parâmetros simples também podem ter regras, que o Spring verifica sozinho desde a versão 6.1:

```java
@GetMapping
public List<Produto> listar(@RequestParam(defaultValue = "0") @Min(0) int pagina,
                            @RequestParam(defaultValue = "20") @Min(1) @Max(100) int tamanho) { ... }
```

> [!ATENCAO]
> Todas as anotações, menos `@NotNull` e as suas variações, consideram o `null` **válido**. Um `@DecimalMin("0.01") BigDecimal preco` aceita um preço ausente; para exigi-lo, é preciso o `@NotNull` junto. É por isso que o `preco` acima tem as duas.

## O que acontece sem tratamento

Com `spring.mvc.problemdetails.enabled=true` e nenhum código de tratamento, a API responde assim:

```text
POST /produtos   com {"nome":"","preco":0,"estoque":-1}
HTTP 400
{"detail":"Invalid request content.","instance":"/produtos","status":400,"title":"Bad Request"}

GET /produtos?tamanho=500
HTTP 400
{"detail":"Validation failure","instance":"/produtos","status":400,"title":"Bad Request"}

GET /produtos/99   (o serviço lança ProdutoNaoEncontradoException)
HTTP 500
{"timestamp":"2026-10-19T18:25:21.919Z","status":500,"error":"Internal Server Error","path":"/produtos/99"}
```

Os status de validação estão certos, mas o cliente não sabe **quais** campos estão errados. E as exceções do próprio domínio, como "produto não encontrado" ou "estoque insuficiente", viram `500`: para o Spring, qualquer exceção que ele não conhece é uma falha do servidor. Duas coisas estão certas, porém: o *stack trace* foi para o log, e não para a resposta, e a mensagem da exceção também ficou de fora, porque o Spring Boot, por padrão, não a inclui.

> [!ERRO]
> A "correção" rápida para o `500` genérico é devolver `e.getMessage()` no corpo. Funciona para as exceções do seu domínio, mas vale também para as inesperadas, e a mensagem de uma falha de banco pode trazer o endereço do servidor, a consulta e até a senha. Trate as exceções conhecidas uma a uma, e deixe a genérica com uma mensagem fixa.

## Um tratador central

Um bean anotado com `@RestControllerAdvice` reúne o tratamento de erros de todos os controllers. Cada método `@ExceptionHandler` diz que exceção trata e devolve um `ProblemDetail`, a classe do Spring que representa o corpo da RFC 9457:

```java
@RestControllerAdvice
public class TratadorDeErros extends ResponseEntityExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(TratadorDeErros.class);

    record CampoInvalido(String campo, String mensagem) {}

    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(MethodArgumentNotValidException e,
            HttpHeaders headers, HttpStatusCode status, WebRequest request) {
        List<CampoInvalido> erros = e.getBindingResult().getFieldErrors().stream()
                .map(f -> new CampoInvalido(f.getField(), f.getDefaultMessage()))
                .sorted(Comparator.comparing(CampoInvalido::campo))
                .toList();
        ProblemDetail p = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "O corpo tem campos inválidos.");
        p.setTitle("Dados inválidos");
        p.setProperty("erros", erros);
        return ResponseEntity.badRequest().body(p);
    }

    @ExceptionHandler(ProdutoNaoEncontradoException.class)
    ProblemDetail naoEncontrado(ProdutoNaoEncontradoException e) {
        ProblemDetail p = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
        p.setTitle("Produto não encontrado");
        p.setType(URI.create("https://api.loja.exemplo/erros/produto-nao-encontrado"));
        return p;
    }

    @ExceptionHandler(EstoqueInsuficienteException.class)
    ProblemDetail semEstoque(EstoqueInsuficienteException e) {
        ProblemDetail p = ProblemDetail.forStatusAndDetail(HttpStatus.UNPROCESSABLE_CONTENT, e.getMessage());
        p.setTitle("Estoque insuficiente");
        p.setType(URI.create("https://api.loja.exemplo/erros/estoque-insuficiente"));
        return p;
    }

    @ExceptionHandler(Exception.class)
    ProblemDetail inesperado(Exception e) {
        log.error("Erro inesperado", e);
        ProblemDetail p = ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR,
                "Ocorreu um erro inesperado. Tente de novo mais tarde.");
        p.setTitle("Erro interno");
        return p;
    }
}
```

O método para erros de parâmetros, `handleHandlerMethodValidationException`, é sobrescrito do mesmo jeito. As mesmas requisições, agora:

```text
POST /produtos   com {"nome":"","preco":0,"estoque":-1}
HTTP 400
{"detail":"O corpo tem campos inválidos.","instance":"/produtos","status":400,"title":"Dados inválidos",
 "erros":[{"campo":"estoque","mensagem":"deve ser maior que ou igual à 0"},
          {"campo":"nome","mensagem":"não deve estar em branco"},
          {"campo":"preco","mensagem":"deve ser maior que ou igual a 0.01"}]}

GET /produtos?tamanho=500
HTTP 400
{"detail":"Parâmetros inválidos.","instance":"/produtos","status":400,"title":"Dados inválidos",
 "erros":[{"campo":"tamanho","mensagem":"deve ser menor que ou igual à 100"}]}

GET /produtos/99
HTTP 404
{"detail":"O produto 99 não existe.","instance":"/produtos/99","status":404,"title":"Produto não encontrado",
 "type":"https://api.loja.exemplo/erros/produto-nao-encontrado"}

POST /produtos/2/baixa?quantidade=5
HTTP 422
{"detail":"O produto 2 tem 2 unidades, e o pedido pede 5.","instance":"/produtos/2/baixa","status":422,
 "title":"Estoque insuficiente","type":"https://api.loja.exemplo/erros/estoque-insuficiente"}

GET /produtos/quebra   (lança IllegalStateException("conexão com o banco recusada: senha=segredo123"))
HTTP 500
{"detail":"Ocorreu um erro inesperado. Tente de novo mais tarde.","instance":"/produtos/quebra","status":500,"title":"Erro interno"}
```

As mensagens de validação vieram em português porque a requisição tinha `Accept-Language: pt-BR`: o Hibernate Validator traz traduções, inclusive com os seus tropeços, como a crase de "igual à 0". Para mensagens próprias, use o atributo `message`, como `@NotBlank(message = "informe o nome")`. E o erro inesperado mostra a regra mais importante: o cliente recebe uma mensagem genérica, e a mensagem verdadeira, com a senha, fica só no log, onde quem opera o sistema pode vê-la.

> [!MATEMATICA]
> Por que listar todos os campos inválidos de uma vez: um formulário com 3 campos errados, numa rede com 200 ms de ida e volta. Se a API devolvesse só o primeiro erro, o usuário corrigiria e reenviaria três vezes: 3 × 200 = **600 ms** de rede, mais o tempo de corrigir cada um. Com a lista completa, uma resposta basta: **200 ms**, e o usuário corrige tudo de uma vez.

> [!DICA]
> Por que estender `ResponseEntityExceptionHandler`? Com a propriedade `spring.mvc.problemdetails.enabled`, o Spring Boot registra o seu próprio tratador, que já cuida das exceções do Spring MVC, inclusive as de validação. Um `@ExceptionHandler(MethodArgumentNotValidException.class)` comum, num advice à parte, não chega a ser chamado. Estendendo `ResponseEntityExceptionHandler`, o seu advice passa a ser o tratador dessas exceções, e o do Spring Boot deixa de ser criado.

> [!PERGUNTAS]
> **P:** Valido no DTO ou na entidade?
>
> **R:** No DTO, o formato da entrada: obrigatório, tamanho, faixa. Na entidade e no serviço, as regras do negócio. As restrições do banco ficam como última barreira.
>
> **P:** `400` ou `422` para um campo inválido?
>
> **R:** Os dois são usados. Este curso usa `400` para formato e validação de campos e `422` para regras de negócio, como estoque. O importante é escolher e ser consistente na API inteira.
>
> **P:** Como validar uma regra que depende de dois campos, como "data final depois da inicial"?
>
> **R:** Com um método no próprio record anotado com `@AssertTrue`, ou com uma anotação própria aplicada à classe.

## Exceções de domínio

O serviço não deveria conhecer HTTP, e por isso lança exceções que falam a língua do negócio, como `ProdutoNaoEncontradoException` e `EstoqueInsuficienteException`, e o tratador as traduz em status. Uma hierarquia ajuda: uma classe `ErroDeNegocio`, da qual as regras violadas herdam, permite um único tratador com `422` para todas, e tratadores mais específicos para as que precisam de outro status ou título. A outra opção, anotar a exceção com `@ResponseStatus(HttpStatus.NOT_FOUND)`, funciona, mas não produz um Problem Details completo e espalha decisões de HTTP pelas classes do domínio.

> [!IA]
> Ao gerar o tratador de erros, a IA costuma devolver `e.getMessage()` para todas as exceções e esquecer o `ResponseEntityExceptionHandler`, e o advice dela não é chamado para os erros de validação. Peça explicitamente a lista de campos no `400`, a mensagem genérica no `500` e o log da exceção completa; e teste com uma exceção cuja mensagem tenha uma "senha".

## Na IDE

- **Ver as regras de um campo.** No IntelliJ, segurar **Ctrl** sobre uma anotação como `@DecimalMin` mostra a documentação e o que ela aceita, inclusive o comportamento com nulos.
- **Depurar o tratador.** Um *breakpoint* condicional em `Exception` (*Run > View Breakpoints > Java Exception Breakpoints*) para a execução no momento em que a exceção é lançada.
- **Testar com `.http`.** Guarde no arquivo `.http` uma requisição inválida para cada regra; elas viram uma bateria de testes manuais rápida.

## Por baixo dos panos

Como o validador sabe que regras aplicar? Por **reflexão**, como o Jackson e o Spring MVC: ele lê as anotações de cada componente do `record`, obtém o valor pelo método de acesso e confere cada regra. As anotações do Bean Validation são `@Retention(RUNTIME)` e podem ser aplicadas aos componentes de um `record`, de onde chegam aos campos e aos métodos de acesso. O essencial cabe em trinta linhas:

```java executar
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;
import java.lang.reflect.RecordComponent;
import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.List;

public class MiniValidador {
    @Retention(RetentionPolicy.RUNTIME)
    @Target(ElementType.RECORD_COMPONENT)
    @interface NaoVazio {}

    @Retention(RetentionPolicy.RUNTIME)
    @Target(ElementType.RECORD_COMPONENT)
    @interface Minimo { String value(); }

    @Retention(RetentionPolicy.RUNTIME)
    @Target(ElementType.RECORD_COMPONENT)
    @interface TamanhoMax { int value(); }

    record NovoProduto(@NaoVazio @TamanhoMax(40) String nome, @Minimo("0.01") BigDecimal preco, @Minimo("0") int estoque) {}

    static List<String> validar(Record objeto) throws ReflectiveOperationException {
        List<String> erros = new ArrayList<>();
        for (RecordComponent c : objeto.getClass().getRecordComponents()) {
            Object valor = c.getAccessor().invoke(objeto);
            if (c.isAnnotationPresent(NaoVazio.class) && (valor == null || valor.toString().isBlank())) { //> A única regra que recusa o nulo.
                erros.add(c.getName() + ": não deve estar em branco");
            }
            TamanhoMax max = c.getAnnotation(TamanhoMax.class);
            if (max != null && valor != null && valor.toString().length() > max.value()) { //> Nulo passa: quem barra o nulo é outra regra.
                erros.add(c.getName() + ": tamanho deve ser no máximo " + max.value());
            }
            Minimo min = c.getAnnotation(Minimo.class);
            if (min != null && valor != null && new BigDecimal(valor.toString()).compareTo(new BigDecimal(min.value())) < 0) {
                erros.add(c.getName() + ": deve ser maior que ou igual a " + min.value());
            }
        }
        return erros;
    }

    public static void main(String[] args) throws Exception {
        System.out.println(validar(new NovoProduto("Headset", new BigDecimal("259.90"), 5)));
        System.out.println(validar(new NovoProduto(" ", new BigDecimal("0"), -1)));
        System.out.println(validar(new NovoProduto("Monitor ultra-largo curvo de 49 polegadas", null, 0)));
    }
}
```

```saida
[]
[nome: não deve estar em branco, preco: deve ser maior que ou igual a 0.01, estoque: deve ser maior que ou igual a 0]
[nome: tamanho deve ser no máximo 40]
```

O terceiro caso repete a armadilha da aula: o preço nulo passou, porque o `@Minimo`, como o `@DecimalMin`, só olha valores presentes. Do lado dos erros, o Spring guarda, para cada advice, um mapa de tipo de exceção para método tratador. Quando uma exceção sobe de um controller, ele procura o tratador do tipo mais próximo na hierarquia da exceção: um `@ExceptionHandler(ErroDeNegocio.class)` trata as subclasses dela, a menos que uma tenha o seu próprio tratador, e o `@ExceptionHandler(Exception.class)` fica como rede de segurança. O desafio deste episódio implementa essa busca.

> [!LAPIS]
> Os tratadores registrados são para `Exception` (500), `ErroDeNegocio` (422) e `ProdutoNaoEncontrado` (404), e `ProdutoNaoEncontrado` estende `ErroDeNegocio`. Qual responde a `ProdutoNaoEncontrado`, a `EstoqueInsuficiente extends ErroDeNegocio` e a `NullPointerException`?
>
> **Resposta:** 404, 422 e 500. O Spring sobe a hierarquia a partir da exceção lançada e para no primeiro tipo que tem tratador: o próprio `ProdutoNaoEncontrado`; o `ErroDeNegocio`, pai do `EstoqueInsuficiente`; e só a `Exception` para a `NullPointerException`.

## Resumo

- `spring-boot-starter-validation` e anotações no DTO: `@NotBlank`, `@Size`, `@NotNull`, `@DecimalMin`, `@Min`, `@Max`, `@Email`
- `@Valid` no `@RequestBody`; parâmetros com anotações são validados sozinhos
- Menos o `@NotNull`, todas as regras aceitam `null`
- Sem tratamento, validação dá um `400` genérico, e exceções de domínio dão `500`
- `@RestControllerAdvice` estendendo `ResponseEntityExceptionHandler`: lista os campos inválidos e traduz exceções de domínio em `404` e `422`
- Erros inesperados: mensagem genérica para o cliente, detalhes no log
- O tratador escolhido é o do tipo mais próximo na hierarquia da exceção
