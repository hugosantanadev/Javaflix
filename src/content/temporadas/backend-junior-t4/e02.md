O Spring Framework existe desde 2003, e por muitos anos começar um projeto com ele significava horas de configuração: escolher versões compatíveis de dezenas de bibliotecas, declarar beans em XML, instalar um servidor Tomcat e implantar a aplicação nele. O **Spring Boot**, de 2014, inverteu isso com três ideias: dependências agrupadas e com versões já testadas juntas, os **starters**; configuração automática baseada no que está no classpath, a **autoconfiguração**; e um servidor web embutido, que faz da aplicação um JAR comum, executável com `java -jar`. Este episódio cria um projeto do zero e mostra o que acontece quando ele sobe. Tudo o que aparece aqui foi executado com o Spring Boot 4.1.1.

## O Spring Initializr

Projetos novos nascem no **Spring Initializr**, em `start.spring.io`, que também está embutido no IntelliJ e no VS Code. As escolhas:

| Opção | Escolha comum |
|---|---|
| Project | Maven ou Gradle (Kotlin) |
| Language | Java |
| Spring Boot | A versão estável mais recente, sem `SNAPSHOT` nem `M1` |
| Group / Artifact | `br.com.javaflix` / `loja` |
| Packaging | Jar |
| Java | 21 ou 25, versões com suporte longo |
| Dependencies | Spring Web, Validation, Spring Data JPA, o driver do banco, Actuator |

O resultado é um ZIP com um projeto pronto para abrir na IDE:

```text
loja/
├── mvnw, mvnw.cmd, .mvn/          o wrapper do Maven
├── pom.xml
└── src/
    ├── main/
    │   ├── java/br/com/javaflix/loja/LojaApplication.java
    │   └── resources/
    │       ├── application.properties
    │       ├── static/            arquivos servidos como estão (HTML, CSS, imagens)
    │       └── templates/         modelos de páginas, se houver
    └── test/java/br/com/javaflix/loja/LojaApplicationTests.java
```

## O pom.xml

```xml
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>4.1.1</version>
</parent>

<properties>
    <java.version>21</java.version>
</properties>

<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-webmvc</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-actuator</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-webmvc-test</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>

<build>
    <plugins>
        <plugin>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-maven-plugin</artifactId>
        </plugin>
    </plugins>
</build>
```

Repare que nenhuma dependência tem `<version>`. O **parent** importa um BOM, como o do [episódio de Maven](/assistir/backend-junior-t1-e05), com as versões de centenas de bibliotecas testadas juntas, e ainda configura os plugins: a versão do Java, a codificação UTF-8 e a opção `-parameters` do compilador, que guarda os nomes dos parâmetros para o Spring. Cada **starter** é uma dependência que agrupa outras: o `spring-boot-starter-webmvc` traz o Spring MVC, o Tomcat embutido e o Jackson. No Spring Boot 4, ele se chama `webmvc`; nos projetos com Spring Boot 3, `spring-boot-starter-web`. O `spring-boot-maven-plugin` é o que transforma o projeto num JAR executável.

## A classe principal

```java
@SpringBootApplication
public class LojaApplication {

    public static void main(String[] args) {
        SpringApplication.run(LojaApplication.class, args);
    }

}
```

O `@SpringBootApplication` junta três anotações: `@SpringBootConfiguration`, que faz da classe uma `@Configuration`; `@ComponentScan`, que varre o pacote dela e os subpacotes atrás de componentes; e `@EnableAutoConfiguration`, que liga a autoconfiguração. O `SpringApplication.run` cria o contêiner do [episódio anterior](/assistir/backend-junior-t4-e01), sobe o servidor web e devolve o controle quando tudo está pronto.

> [!DICA]
> Se outro programa já estiver usando a porta 8080, a aplicação não sobe e o relatório de falha diz "Port 8080 was already in use". Escolha outra porta com `server.port=8081` no `application.properties`, ou com `--server.port=8081` na linha de comando.

## O JAR executável

O `java -jar` funciona porque o `spring-boot-maven-plugin` **reempacota** o JAR comum num formato próprio, com todas as dependências dentro. O desta aplicação tem 21 MB e este `MANIFEST.MF`:

```text
Main-Class: org.springframework.boot.loader.launch.JarLauncher
Start-Class: br.com.javaflix.loja.LojaApplication
Spring-Boot-Version: 4.1.1
Spring-Boot-Classes: BOOT-INF/classes/
Spring-Boot-Lib: BOOT-INF/lib/
```

O `java` chama o `JarLauncher`, uma classe do Spring Boot gravada na raiz do JAR, que monta um classpath com as suas classes, em `BOOT-INF/classes`, e os 43 JARs de dependências, em `BOOT-INF/lib`, e só então chama o `main` da `Start-Class`. Um único arquivo é tudo o que o servidor de produção, ou a imagem Docker, precisa.

## Autoconfiguração

Ninguém declarou um Tomcat, um `DispatcherServlet` ou um `JsonMapper` do Jackson, e todos existem. Cada um veio de uma **autoconfiguração**: uma classe `@Configuration` do próprio Spring Boot, aplicada só quando as suas **condições** são atendidas. As mais comuns:

| Condição | Aplica a configuração se |
|---|---|
| `@ConditionalOnClass` | Uma classe está no classpath, por exemplo o driver do PostgreSQL |
| `@ConditionalOnMissingBean` | Você **não** declarou um bean daquele tipo |
| `@ConditionalOnProperty` | Uma propriedade tem certo valor |
| `@ConditionalOnWebApplication` | A aplicação é web |

Rodando com `--debug`, o Spring Boot imprime o **relatório de condições**, com o que foi aplicado e por quê. Trechos reais:

```text
CONDITIONS EVALUATION REPORT

Positive matches:
-----------------

   DispatcherServletAutoConfiguration matched:
      - @ConditionalOnClass found required class 'org.springframework.web.servlet.DispatcherServlet' (OnClassCondition)
      - found 'session' scope (OnWebApplicationCondition)

   JacksonAutoConfiguration#jacksonJsonMapper matched:
      - @ConditionalOnMissingBean (types: tools.jackson.databind.json.JsonMapper; SearchStrategy: all) did not find any beans (OnBeanCondition)

Negative matches:
-----------------

   AopAutoConfiguration.AspectJAutoProxyingConfiguration:
      Did not match:
         - @ConditionalOnClass did not find required class 'org.aspectj.weaver.Advice' (OnClassCondition)
```

O `@ConditionalOnMissingBean` é o que torna tudo isso ajustável: o Spring Boot só cria o `JsonMapper` dele se você não tiver criado o seu. Declarar um `@Bean JsonMapper` com as suas configurações **substitui** o automático, sem desligar nada. É a regra geral do Spring Boot: ele oferece um padrão razoável e sai do caminho quando você define o seu.

## Actuator

O starter do **Actuator** acrescenta endpoints de operação, usados por monitoramento e orquestradores como o Kubernetes:

```text
$ curl http://localhost:8080/actuator/health
{"groups":["liveness","readiness"],"status":"UP"}
```

Por padrão, só o `health` fica exposto pela web; o `/actuator` lista os links dos expostos. Outros, como `info`, `metrics` e `env`, são ligados com `management.endpoints.web.exposure.include=health,info,metrics`. O `env`, que mostra as propriedades da aplicação, e o `heapdump` nunca devem ficar públicos em produção.

## Por baixo dos panos

O que o `SpringApplication.run` faz? Primeiro, olha o classpath para decidir o tipo de aplicação: com o Spring MVC presente, web com servlets; com o WebFlux, reativa; com nenhum dos dois, uma aplicação comum. Depois cria o contêiner, registra os beans dos pacotes varridos e lê os **candidatos a autoconfiguração**. No Spring Boot 4, eles estão espalhados por módulos, um por tecnologia, e cada módulo lista os seus num arquivo de texto, o `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`. Nesta aplicação, onze JARs têm esse arquivo, com 91 candidatos ao todo; o do `spring-boot-webmvc` começa assim:

```text
org.springframework.boot.webmvc.autoconfigure.DispatcherServletAutoConfiguration
org.springframework.boot.webmvc.autoconfigure.WebMvcAutoConfiguration
org.springframework.boot.webmvc.autoconfigure.WebMvcObservationAutoConfiguration
```

Cada candidato tem as suas condições avaliadas, e só os aprovados viram beans: 258 definições, ao todo, nesta aplicação de uma classe só. Em seguida, o contêiner cria os singletons, o servidor embutido abre a porta, e o evento `ApplicationReadyEvent` avisa que a aplicação está pronta. A avaliação de uma condição `@ConditionalOnClass` é, no fundo, tentar carregar a classe pelo nome sem inicializá-la:

```java executar
import java.util.List;

public class AutoConfig {
    record Configuracao(String nome, String classeExigida) {}

    static boolean existe(String classe) {
        try {
            Class.forName(classe, false, AutoConfig.class.getClassLoader());
            return true;
        } catch (ClassNotFoundException e) {
            return false;
        }
    }

    public static void main(String[] args) {
        List<Configuracao> candidatas = List.of(
                new Configuracao("ClienteHttpAutoConfiguration", "java.net.http.HttpClient"),
                new Configuracao("BancoAutoConfiguration", "javax.sql.DataSource"),
                new Configuracao("PostgresAutoConfiguration", "org.postgresql.Driver"),
                new Configuracao("JacksonAutoConfiguration", "tools.jackson.databind.json.JsonMapper"));
        System.out.println("Positive matches:");
        for (Configuracao c : candidatas) {
            if (existe(c.classeExigida())) System.out.println("   " + c.nome() + ": found required class '" + c.classeExigida() + "'");
        }
        System.out.println("Negative matches:");
        for (Configuracao c : candidatas) {
            if (!existe(c.classeExigida())) System.out.println("   " + c.nome() + ": did not find required class '" + c.classeExigida() + "'");
        }
    }
}
```

```saida
Positive matches:
   ClienteHttpAutoConfiguration: found required class 'java.net.http.HttpClient'
   BancoAutoConfiguration: found required class 'javax.sql.DataSource'
Negative matches:
   PostgresAutoConfiguration: did not find required class 'org.postgresql.Driver'
   JacksonAutoConfiguration: did not find required class 'tools.jackson.databind.json.JsonMapper'
```

Esse programa roda só com o JDK, então o `HttpClient` e o `DataSource` existem, e o driver do PostgreSQL e o Jackson, não. O segundo argumento `false` do `Class.forName` é importante: ele carrega a classe sem executar os inicializadores estáticos, para que testar a presença de uma biblioteca não tenha efeitos colaterais. Na verdade, o Spring Boot é ainda mais cuidadoso: ele lê as anotações das autoconfigurações direto do bytecode, sem nem carregar as classes, para que a avaliação seja rápida e uma condição que falha não cause um `NoClassDefFoundError`.

## Resumo

- `start.spring.io` gera o projeto: Maven ou Gradle, versão do Boot, do Java e os starters
- O `spring-boot-starter-parent` traz as versões testadas e configura os plugins, inclusive o `-parameters`
- Starters agrupam dependências: `spring-boot-starter-webmvc` traz Spring MVC, Tomcat e Jackson
- `@SpringBootApplication` = configuração + varredura de componentes + autoconfiguração
- `./mvnw spring-boot:run` ou `java -jar`: o JAR reempacotado tem as dependências em `BOOT-INF/lib` e o `JarLauncher`
- Autoconfiguração com condições (`@ConditionalOnClass`, `@ConditionalOnMissingBean`, `@ConditionalOnProperty`); `--debug` mostra o relatório
- Um bean seu do mesmo tipo substitui o automático; o Actuator expõe `/actuator/health`
